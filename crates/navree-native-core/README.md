# navree-native-core

The runtime core of Navree Native: everything a native client does that is not drawing, placement or talking to the system. Navigation, the tree store, forms, and every conversation with the server are written once, here, and every client runs them: SwiftUI on Apple's systems, Jetpack Compose on Android, and whatever comes after.

The core is a pure function of state and event.

```rust
use navree_native::{Client, FormFactor, Platform};
use navree_native_core::{Config, Core, Event};

let mut core = Core::new(Config::new("https://shop.example", Client::new(Platform::Ios, FormFactor::Phone)));
let update = core.send(Event::Start);   // what changed, and what to do about it
let view = core.view();                 // what a client draws from
```

- `Core::new(Config) -> Core`
- `Core::send(&mut self, Event) -> Update`, where `Update { changed: Vec<Change>, effects: Vec<Effect> }`
- `Core::view(&self) -> &ViewState`, and `Core::part(&Query)` for one part of it as JSON
- `Core::snapshot(&self) -> Snapshot`, what a client stores so the app starts again where the person was

The core never does I/O, reads no clock and rolls no dice: the random bytes a sign-in needs are asked of the client, like everything else. It asks for a request, a timer or a stream with an **effect**, and learns what came of it from a later **event**. So every rule in it is tested with plain values, and four clients cannot drift apart.

A client keeps no state of its own about anything in the view state. Scroll positions, carets and the text of a field while it is being typed are the toolkit's.

## The loop

1. Something happens: the app starts, the person taps, a request is answered, a timer runs out.
2. The client sends it as one event and gets an update.
3. For each entry of `changed`, the client reads that part of the view state again and draws from it.
4. The client carries out each effect, in order. What comes of an effect is a later event.

## The C interface

`include/navree_core.h`, five functions. Everything that crosses is UTF-8 JSON, as a pointer and a length.

| Function | Takes | Gives |
|---|---|---|
| `navree_core_new(config, len)` | a `Config` | a core, or `NULL` when the configuration does not read |
| `navree_core_send(core, event, len)` | an `Event` | an `Update`, or `{"error":"..."}` |
| `navree_core_view(core, query, len)` | a `Query`, or nothing for all of it | that part of the `ViewState`, or `{"error":"..."}` |
| `navree_bytes_free(bytes)` | bytes the core gave | |
| `navree_core_free(core)` | a core | |

With the feature `jni` the crate also exports the four native methods of the Kotlin class `com.navree.core.Core` (`nativeNew`, `nativeSend`, `nativeView`, `nativeFree`), which take and return `ByteArray`s of the same JSON and keep the handle as a `Long`.

**What a client must guarantee.** Events are sent in the order things happened, from one thread at a time: the simplest way is to call only from the thread that draws. A lock inside the handle keeps two calls made at once from running together, so a mistake costs order, never memory. Freeing the handle while another thread is in a call waits for that call; a call during or after the free answers an error (the handle's own few bytes are kept for the life of the process, so nothing reads freed memory). Bytes passed in stay valid for the call. Every answer is given back once. No call panics across the boundary: a failure inside the core, or while a call's own input is read, answers `{"error":"...","stopped":true}` and stops the core for good (nothing it had queued is sent, and every later call answers the same), so a client that sees `stopped` (it tests the mark, never the words) says the app must be started again; an input that merely does not read is only an error, with no `stopped`, and the core goes on.

**Stack.** A call may be made from a thread with 512 KiB of stack, which is what a secondary thread has on Apple's systems. Reading a tree as deep as the protocol allows takes more than that, so the core reads each answer on a thread of its own with 4 MiB, and waits for it; everything else it does with such a tree fits the caller's thread. `tests/stack.rs` runs all of it on 512 KiB in a debug build. A tree deeper than the protocol allows is refused before it is read.

**How large an answer may be.** An answer's body holds at most `MAX_BODY` bytes (8 MiB), and one answer at most `MAX_NODES` nodes (100,000, across its screen, its ops and their rows, where what stands in a tree without being a node, a table's rows, the items of a list of facts, the points of a chart, counts as one node each) and `MAX_OPS` ops (1,000); the constants are in `navree-native`, beside `MAX_DEPTH`. Past any of them the answer fails as one that could not be read: the body is not read at all, and a shell that large is not drawn. An id or a name an answer gives that the core builds handles and keys from (a node's id, a form's, a region's, a list's or a table row's id, a field's name, a row's key, an op's target) is at most `MAX_ID` bytes (256; the longest recorded is 36, a UUID): an answer with a longer one fails the same way, before anything is named from it, because a form's handle is the start of the name of every field of it that has no id of its own; a handle longer than 64 bytes gives its first 48 and a 64-bit number made of all of it (FNV-1a, sixteen hex digits), so a long id is not copied into every name and two long ids that begin alike do not share their fields' names (`tests/scale.rs`). A form with no id is named from at most that much of its address. A name an answer repeats (forms of one id, fields of one name) gets `~2`, `~3`, ... and the next suffix of each stem is remembered, so naming costs what is repeated and not its square (`tests/scale.rs`: 99,000 fields of one name in 1.6 s and 30,000 forms of one id in 0.4 s, in a debug build on this machine). The core copies the body it is handed into the call before it can look at its size, so its refusal of a body past `MAX_BODY` is a second guard and comes after the copy: a client's transport refuses a body larger than `MAX_BODY` before it hands it over (by the length the response announces, and by the bytes that have arrived), and answers the core with a failure as for any answer it could not read. What the core is handed from the device's store (a snapshot, a kept page, `boot`) it wrote itself. The icon shapes an answer keeps in its icon table are written into every icon that names one, so they are added up first (once for each such icon) and the answer fails when they come to more than `MAX_BODY`; nothing is copied before the sum is known. The largest answers recorded so far hold about 30 KB, 410 nodes and 13 ops; `tests/scale.rs` reads one of about 4 MB and 80,000 nodes. Each op still looks through the screen for its target, and an op that changes a form looks through all of it again, so an answer costs about its such ops times the screen's nodes, and the cap on ops does not bound that. `MAX_WORK` does (4,000,000 visits to a node, in `navree-native`): the work of an answer is counted as it will be done, each op that looks through the screen being charged the nodes the screen holds when it runs (counted as for `MAX_NODES`, and with what the ops before it brought), and when the sum would pass it the answer is refused whole (below), as one that would take the screen past its largest size is. The number comes from a measurement (`tests/scale.rs`, `what_a_visit_to_a_node_costs`, run in a release build on a desktop processor): a visit costs 15 ns for an op that only searches (`focus`), 36 to 95 ns for `append`, `morph` and `remove`, and 232 ns for a `merge` (which also reads the whole screen again); four million visits are a second of the dearest. A phone is slower. An index of ids kept as the screen changes would bring the work down to what each op touches; it is not built.

**How large a screen may be.** A page that comes as one answer is held to `MAX_NODES`; what comes to a screen over time (rows by cursor, the changes of a list kept up to date, a region's answer, an op) is held to `MAX_SCREEN_NODES` (400,000: four times that), counted the same way. An answer's changes are applied whole or not at all: before its first op the core works out whether what its ops bring would take the screen past that size, or what its ops that look through the screen ask for would pass `MAX_WORK`; if so none of the ops that change the screen is applied, but what costs nothing on it is carried out, in its order (a toast, a new address, a move, a reload, a sign-out and the `navigate` after it, a reply to the device), so a save that worked still says so and goes where it meant to; a `report` of `size` says so; the person is told the screen is loading while it will be fetched again, and gets the failure a screen that could not be read gets when it will not (nothing is said of a screen they were taken away from); the screen is marked out of date, so it is fetched again, once (a reload of the answer's is that fetch, and is carried out only while the screen is still owed one): the count of refusals belongs to the screen, survives its page being shown again, and is set back only when an answer of ops is applied to it or the person acts on it (a tap, a pull to refresh, a retry, more rows). A page that carries ops is one answer: when its ops would be refused against its own screen it is not drawn either and fails as one that could not be read, with its retry, and nothing is fetched again by itself. An answer to a part of the screen (the rows after a list's last or before its first, a region) that is refused does not make the screen out of date and is not counted against it: fetching the page again would put its first rows in place of the ones the person loaded, so the list keeps its rows and the part shows its failure (a list's failed state, or a region's), with its retry. A list that asked for more rows and was refused shows its failed state, with its retry, and keeps its `more`; a live list whose changes were refused stops asking for them (it asks again when its stream next speaks). The same holds for rows that come as a whole page and for a region's answer. The core keeps the screen's weight beside it, adds to it as things arrive and counts the screen afresh only when the figure would decide the question, so a page of rows still costs the page, not the list. (`tests/scale.rs`) A `merge`, and the rows of a table, are matched with the rows already there through sets, so they cost what they bring and what is there, never the two multiplied (`tests/scale.rs`: a merge of 40,000 rows and 20,000 gone into 40,000 took 55 s before, and half a second after, in a debug build).

`src/ffi.rs` is the only file with `unsafe` in it.

## Config

```json
{"origin": "https://shop.example",
 "also": ["https://*.shop.example"],
 "app_id": "com.charkha.supply",
 "client": {"platform": "ios", "os": "26.1", "form": "phone", "app": "1.4.0", "lib": "0.1.0", "vocab": 0,
            "scheme": "light", "contrast": "normal", "text_percent": 100,
            "locale": "en-IN", "tz": "Asia/Kolkata", "caps": ["share", "clipboard", "open_url"]},
 "back_to_first": false,
 "deep_links": "routes",
 "cache": {"pages": 24, "persist": true},
 "undrawable": ["chart", "input:colour"],
 "views": ["shelf-map"],
 "sign_in": {"paths": ["/auth/*/redirect"], "callback": "shop", "native": ["apple"]}}
```

Only `origin` and `client` are required. `origin` must be `https` (`loopback_http: true` allows plain `http` for the machine itself, for development). `also` lists other origins the app treats as its own. `app_id` is the app's own name with its system (the bundle id, the package name): a sign-in is handed over to the app by it and the device's push token is registered for it, and without it neither is started. `client` is the protocol's own description of a client, sent with every request; its `caps` name the device features this build has, by the protocol's names (`share`, `clipboard`, `open_url`, `scan_code`, `location_once`, …). A control that calls a feature the build lacks is drawn as the call's stand-in says, or not at all. `sign_in.native` names the providers this build signs in with through the system's own sheet (`apple` on Apple's systems, `google` on Android); a sign-in with any other goes the web's way. `back_to_first` is Android's back, which leads to the first destination before it leaves the app. `undrawable` names the kinds this build of the client can't draw yet: a page that holds one is shown in the web view.

## Addresses

Every address the core is given, by a page, an answer, a redirect, a link from outside or the web view, is read before anything is done with it, and read as it is: nothing is trimmed and nothing is repaired. What does not read leads nowhere.

- Text that is empty, starts with `#`, has white space at either end, or holds anywhere a control character, a backslash, or a space other than the ASCII space does not read. An ASCII space inside an address is kept.
- A host is ASCII letters, digits, `-` and `.`, or an IPv6 literal in brackets. A name in another script is written in its ASCII form (`xn--…`). The origins in the configuration are held to the same rules.
- An address with a name before its host (`user@host`) does not read.
- A path that starts with `//` once its dot segments (`.`, `..`, `%2e`) are taken out does not read. An empty segment further inside stays, as a browser keeps it.
- A scheme is read by what an address starts with, never by `://` somewhere in it: `/x?a=b://c` is a path and a query on the app's origin.

**Every address a client is given to fetch, to stream from or to show in the web view is a whole address**, `scheme://host[:port]/path[?query]`, built from the parts that were read, on the app's own origin or one it allows (`also`). The text that came in never goes out as it came: the path, the query and a fragment are written as a browser sends them, percent-encoded by the URL standard's path, special-query and fragment sets for `http` and `https` (non-ASCII as its UTF-8, a space as `%20`; `[` and `]` in a query stay). An escape already written stays; any other `%` is written `%25`. The address in the view state (`screens[n].url`) is the form that was read, not encoded. A request whose address is not one of these is never sent: it fails as an answer of 502 does. A stream is never opened, and a page is never put in the web view (the screen fails).

**Pictures.** The core writes the source of every picture (`image.src`, `avatar.src`, a feed row's `actor`, a message's `avatar`) in a tree it takes in, from a page, a region, an op, a list's rows or the shell's user menu, before a client sees it; a relative source in a part of a page (a region, a list's rows) is read against the page, as a browser reads it against the document: a source on one of the app's origins becomes its whole address; a whole `https` address of another host is kept, written again from its parts (a client loads it or not by its own list of picture hosts); a picture written into the page itself (a source that starts with `data:image/`, as a QR code or a small chart is) stays exactly as it came, since it is no address and nothing is fetched for it; anything else (`http` to another host, another `data:` source, a broken address) becomes empty, which a client draws as its placeholder. A client never resolves a picture's source itself.

**A client asks again.** Before it fetches an address, streams from it or loads it in the web view, a client asks "is this ours?" of what **its platform's own parser** reads, because that parser is what connects: the text holds no white space, control character or backslash; the platform reads it as `http` or `https` with no user information; and its scheme, host and port are an origin of the app (`*.name` for one label or more under `name`, at a label's edge; plain `http` only to a loopback host when the build allows it). `vectors/addresses.json` holds the addresses every client must read the same way as the core: `resolve` (how an address found on a page reads, and the whole address that leaves; what turns on the path, such as `//` after dot segments, is decided here, by the core alone) and `ours` (only cases the client's rule above decides). The core's tests run them, and so must each client's.

**Places on two origins.** Where an app allows other origins (`also`), two addresses are the same place only when their origin and path both are: a destination, the screen a table or a page moves to, what a cover stands for and where an answer came from are compared that way, so the other origin's `/orders` is not the Orders destination. The shell's routes and the paths a sign-in goes by are the home origin's: an address on another origin matches none of them, and a link from outside to one is not let in by them. (`transcripts/origin-places.json`)

**What opens outside.** An `open_url` effect holds only a whole `http` or `https` address that reads, written again from its parts (its fragment kept), or a `mailto`, `tel`, `sms` or `geo` one, as written except that the number part of a `tel` or `sms` address (up to its first `;`, `?` or `#`) leaves without its ASCII spaces (`tel:+91 98140 12345` opens as `tel:+919814012345`), so every system is handed one form. The system's own (mail, the dialler, messages, maps) open only when a tap stands behind them: a link or a button the person tapped, a message's button, a device call, a link tapped in the web view. An answer by itself (a redirect, a `navigate` or `navigate_external` op, the way in after a session ended) may take the person to a web page outside the app, such as a payment page, and never to those: what it asked is refused and said with a `report` (`what: "address"`, the kind and the scheme only). (`transcripts/outside-taps.json`) A newer app (`upgrade`) is offered only at an `https` address; any other is dropped, and `upgrade.url` is empty.

## Events

Every event is an object whose `t` names it. A field shown with `?` may be left out.

| `t` | Fields | When |
|---|---|---|
| `start` | | The app started, or the person asked to try again after it failed to. |
| `response` | `request`, `status?`, `content_type?`, `location?`, `headers?`, `body?`, `url?`, `error?`, `left?` | A `fetch` was answered. `headers` holds the answer's headers whose names start with `x-navree-`, and its `cache-control`, each as `[name, value]`; a page is kept only when its `cache-control`, when passed, does not say `no-store` (`transcripts/keep-cache-control.json`). A redirect is handed over as it came, with its `status` and `location`: the core checks where it leads and asks again. `error` (`offline`, `timeout`, `other`) when no answer came. A transport that follows redirects itself gives the last address as `url`, and stops with `left` at one that leaves the app's origins. |
| `select` | `destination` | The person chose a top-level destination. |
| `act` | `screen?`, `action`, `form?`, `overlay?`, `text?`, `now?`, `ask?`, `from?` | The person tapped something that has an action. `action` is the node's own. `form` and `overlay` are the ids of the form and of the sheet, dialog or popover the control stands in. `now` is the time in seconds since 1970, given when the action is a device call: a call whose ticket has run out is not started. `ask` is the question the control asks first, as the node holds it: the core then holds the action and puts the question in the screen's `question`. `from` is the id of the part tapped, when it has one: a screen the action opens keeps it (see the view state). |
| `answer` | `screen`, `question`, `yes` | The person answered the screen's question. Yes runs what the control was about to do. |
| `field` | `screen`, `form?`, `field`, `value` | The person changed a field. `value` is `{"t":"text","text":"…"}`, `{"t":"flag","on":true}`, `{"t":"many","values":[…]}`, `{"t":"files","files":[{"token","name","type","size"}]}`, `{"t":"range","from":"…","to":"…"}` for the two ends of a range, `{"t":"phone","text":"…","country":"IN"}` for a phone number with the country the person picked, or `{"t":"none"}`. A field whose node says what happens as it changes (`changed`) needs nothing more from the client: the core sends the form or runs the commands. The form it sends is the one the field stands in, sent to the address the form names (a change may not name another: it would send the form's data to an endpoint the form did not name, so an apply needs a button; an app that wrote a field whose `changed` names another address now only gets a `report` of `changed`), found by the handle the core gave it (`form`), never looked up again by the id the server gave the form: two rows of a list may hold forms the server calls alike, and a `changed` that names its own form by the server's id is that form. (`transcripts/changed-own-form.json`) A `field` event whose value is the one the field already holds changes nothing and starts nothing, so a client that tells the core of a value it put in itself (typing it back, a restore) starts no send. That holds for a table's query form too: re-tapping the chosen segment is not a refresh, and the core says nothing changed, so a client shows no pending mark for it. (`transcripts/field-changed.json`) |

| `choose` | `screen`, `table`, `row?`, `on`, `across?` | The person ticked or cleared a row of a table whose rows can be chosen; every row it holds when `row` is left out. With `across`, every record that matches the table's query, which a table offers with `select.across`. |
| `tab` | `screen`, `id`, `index` | The person chose another tab of a set of tabs. |
| `random` | `request`, `bytes` | The bytes a `random` effect asked for, as hex. |
| `push_token` | `token`, `environment?` | The system gave the device a push token, or changed it: sent at every launch and at every change. |

| `move` | `screen`, `item`, `from`, `to`, `before?` | The person dragged the row `item` from the list `from` into the list `to`, before the row `before` or at the end. |
| `search` | `screen`, `text` | The person searched with the screen's own search (`screen.search`). |
| `back` | | The system's back. |
| `pop_to` | `screen` | The person went back to a screen further down the stack. |
| `dismissed` | `screen` | The person took a sheet or cover away. |

| `more` | `screen`, `id`, `before?` | The end of a list or table is near; with `before`, the start of a list that has rows before its first. |

## Updates

```json
{"changed":[{"t":"nav"},{"t":"screen","id":3}],
 "effects":[{"t":"fetch","request":4,"method":"get","url":"https://shop.example/orders/1",
             "headers":[["x-navree-native","1"],["x-navree-client","platform=ios; form=phone; vocab=0"],
                        ["accept","application/vnd.navree.native+json"]],
             "timeout_ms":30000}]}
```

`changed` names parts of the view state. Each is read with the query of the same shape (`"t"` becomes `"part"`).

| Change | The part |
|---|---|
| `app` | The app's name, theme and user. |
| `nav` | Where the person is: `stage`, `failure`, `upgrade`, `destinations` with their stacks, `selected`, `modals`, `front`, `can_go_back`, `window`. |
| `screen` (`id`) | Everything about one screen. `null` when no stack holds it any more. |
| `form` (`screen`, `form`) | The state of one form, and nothing else of the screen. |
| `rows` (`screen`, `id`, `from`, `count`) | `count` rows were added at the end of a list or table, starting at `from`, and nothing else of the screen changed. The part holds those rows, the state of the forms in them, and what the list says of itself: `more`, `loading` and `failed`; for a list also `before`, `loading_before` and `failed_before`; for a table whose rows can be chosen also `selected`, the ids of every row chosen. A `count` of 0 says only that this state changed: a tick, or a fetch that began or ended. A client that does not read rows by themselves reads the screen. |
| `redraw` (`screen`, `id`, `rows`, `gone`) | Some rows of a list or table changed, and nothing else of the screen but what the list says of itself. Each id in `rows` is a row that is new, has new content or stands in a new place; the ids in `gone` left. The part gives each named row as `{"id", "before", "node"}` (a table's as `"row"`), in the list's order, where `before` is the id of the row it stands before now, or `null` at the end. A client takes out the rows that left and the rows named, then puts the named ones in from the last to the first, each before its `before`. A client that does not redraw rows by themselves reads the screen. |
| `messages` | The messages waiting to be shown. |

One more part is read without a change to say so: `{"part":"snapshot"}`, below.

## Effects

| `t` | Fields | What the client does |
|---|---|---|
| `fetch` | `request`, `method`, `url`, `headers`, `body?`, `timeout_ms`, `xsrf?` | Sends the request with its cookies, follows no redirect, and answers with a `response` event carrying `request`. `method` is `get`, `post` or `delete`. `body` is `{"t":"form","text":"a=1&b=2"}` (send `text` as it is), `{"t":"multipart","parts":[…]}` (write the parts, putting in the bytes kept under each `token`) or `{"t":"json","text":"{…}"}` (send `text` as it is, which may be empty: the framework's own routes speak JSON, and the answer's body is handed back as any other). With `xsrf`, the `XSRF-TOKEN` cookie, decoded, also goes in `x-xsrf-token`. A request for one region or for a list's next rows carries `x-navree-region` with the region's id, percent-encoded: each byte of its UTF-8 outside `!` to `~`, and `%`, is written as `%` and two hex digits, so a plain ASCII id goes as it is. `url` is a whole address on one of the app's origins (see "Addresses"). |
| `cancel` | `request` | May drop the request: its answer is no longer wanted. |
| `open_url` | `url`, `inside?` | Opens the address outside the app; with `inside`, in the system's browser inside the app. Only a whole `http` or `https` address, or a `mailto`, `tel`, `sms` or `geo` one, and the last four only when a tap stands behind them. |
| `sign_in` | `url`, `callback?`, `ephemeral?` | Opens the system's sign-in session, and answers with `sign_in_done`. With `ephemeral`, the session shares nothing with the system's browser. |
| `message` | `id`, `tone`, `text?`, `title?`, `notice?`, `action?` | Shows a short message, and answers with `message_shown` when it has gone. `notice` is a message of the core's own, for the client to word. |
| `haptic` | `kind` | Plays a haptic. |
| `device` | `call`, `device`, `posts?`, `options?` | Runs a device call: one a tap started, or one of the few a server's reply may start. `device` is the call as the protocol writes it (`{"f":"share","title":"…"}`), except that a share's `href` (the app's page shared) and `file` (the app's file the client fetches and shares), and a passkey's `options` (the route the client fetches the request's options from), are whole addresses on the app's origin, written as a picture's source is, and left out when they do not read as one; an address left out is said in a `report` of `device`, by its name and never the address. With `posts`, answers with `device_result`, and the core sends the result where it goes. `options` is what the server gave for the call to start with, which the core asked for: the passkey request for `confirm`, the nonce for `platform_sign_in`. The client asks the server for nothing itself. |
| `random` | `request`, `bytes` | Hands the core that many bytes from the system's secure random generator, with a `random` event. They are a secret: never logged, never used for anything else. |
| `forget_session` | | Forgets the session: every cookie of the app's origins, in the web view's store too. |
| `cache_read` | `key` | Reads what is kept under the key, and answers with `cache`. |
| `cache_write` | `key`, `value?` | Keeps the value under the key; without a value, takes the key away. |
| `cache_clear` | | Throws away everything kept. |
| `announce` | `text?`, `notice?`, `count?` | Says it to assistive technology. |
| `copy` | `text`, `sensitive?` | Puts the text on the clipboard. With `sensitive`, as a secret the system should not show or sync. |
| `timer`, `cancel_timer` | `timer`, `ms` | Answers with a `timer` event after that long; or no longer. |
| `stream_open`, `stream_close` | `stream`, `url`, `headers` | Opens a stream of server-sent events at `url`, a whole address on one of the app's origins, and answers with `stream` events; or closes it. Only an event's name is passed on. The client does not reconnect by itself: the core asks. |
| `exit` | | There is nothing to go back to: the system takes the back. |
| `report` | `what`, `detail` | Something the app's developers will want to know. `what` is `address` when an address an answer gave (a link, a redirect, a form's target, a region's or a list's source, a shell entry) does not read and was not followed: `detail` names the kind and the address's scheme and host (or `a path`), never its path, once for an event. `what` is `changed` when a field's change asked for something only a tap may start (copying, another form, another address for the form's data, going somewhere, a request, a device call, closing): it was not done, and each kind is said once while the core runs. |

## The view state

```json
{"stage": "ready",
 "app": {"name": "Charkha Supply Co.", "home": "/", "user": {…}},
 "destinations": [{"label": "Orders", "href": "/orders", "badge": "12", "items": [], "stack": [2, 3]}],
 "selected": 0,
 "modals": [{"present": "sheet", "locked": false, "stack": [4]}],
 "front": 4,
 "can_go_back": true,
 "window": {"width": "compact"},
 "screens": {"3": {
     "id": 3, "url": "/orders/1",
     "content": {"t": "native", "screen": {…}},
     "loading": false, "refreshing": false, "cached": false, "status": 200, "chrome": true,
     "overlays": ["refund"],
     "states": {"row-1": ["selected"]},
     "forms": {"refund": {"pending": false, "fields": {
         "refund-amount": {"name": "amount", "value": {"t": "text", "text": "10"}, "errors": []}}}},
     "regions": {"figures": {"loading": false}},
     "lists": {"feed": {"loading": true, "failed": false}}}},
 "messages": [{"id": 1, "tone": "success", "text": "Refunded ₹10.00"}]}
```

- `stage`: `starting`, `ready`, `failed` (with `failure`) or `upgrade` (with `upgrade`). An `upgrade` whose `url` is empty offers nothing to open.
- A screen's `content` is `{"t":"blank"}`, `{"t":"native","screen":…}` (a screen of the protocol) or `{"t":"web","url","title?","why","serial"}` (load the address in the web view, a whole address on one of the app's origins; load it again when `serial` moves on).
- **The tree is ready to draw.** What is open, hidden, disabled or waiting is already in it: a sheet's `open`, a stack's `hidden`, a button's `pending`. A state that has no field in the tree is in `states`, by the node's id.
- **Every form and every field has an id that is its own on its screen.** A form that came with none goes by `@` and its address. `forms` holds each form's state by that id, and each field's by the field's id: what it holds now, and what is wrong with it. A client draws a field's value and messages from here, never from the node.
- `overlays` lists the sheets, dialogs and popovers that are open, the last opened last.
- `modals[].present` is `sheet`, `full` or `task` (something the person finishes or cancels, presented as each system presents one). `modals[].locked`: the person can't take it away (the sign-in a session that ended was sent to).
- `question`: what a control asked before it acts, `{"id","title","text?","confirm","cancel?"}`, there until an `answer` event.
- A link to a top-level destination selects it. A link that itself says `present: push` is the exception: its screen is stacked on the one it stands on, in the stack the person is in, also when the address is a destination's own (a card on the first destination that opens another destination's page as a detail, with a way back). The destination's own stack is untouched. (`transcripts/push-destination.json`)
- `from`: the id of the part whose action opened the screen, on the screen it was opened from, as the `act` event named it. A screen that was pushed or presented has it, also when the action waited for a question; a screen changed in place (a day step, a replace) and a destination's first screen do not gain one. A client that grows a screen out of a card (`transition: zoom`) shrinks it back into the same card, and the snapshot keeps it for a launch that is restored. (`transcripts/opened-from.json`)
- A field's state may hold `options` (what a search on the server found, drawn in place of the control's own), `more` (there are options after these) and `searching`.

The whole of it, with every event, effect and query, is in `schema/navree-native-core.schema.json`.

## Signing in, signing out, and push

- **A sign-in in the system's session, handed over.** The session has cookies of its own, so a sign-in in it signs nobody in here. When the shell names the hand-over's routes (`sign_in.start`, `sign_in.exchange`), the core asks for 48 random bytes, makes from them a verifier (which stays in the core) and a `state`, and opens the session at the start route with the verifier's SHA-256 (`code_challenge`, `S256`), the `state`, the app's id and its system. The return is taken only while a session the core opened is open, and only with that `state`; a return that comes any other way is not used and shows nothing. The `callback` the shell names is handed to the system only when it is an `https` address on one of the app's origins or a link of the scheme the app was built with (`sign_in.callback`); otherwise the sign-in does not start, and the person is told it failed. A return is taken only on the way back the sign-in named (the shell's `callback`, or, when it names none, the app's scheme) and is compared with this sign-in's `state` before anything else is read of it: one that came back another way, or with another `state`, or none, is not this sign-in's, and nothing changes (the sign-in stays open). With no callback in the shell, a link on the app's scheme that carries a `code`, a `state` or an `error` is a return, never a page. With this sign-in's `state`, `error=access_denied` is the person saying no: it ends the sign-in as closing the sheet does, and nobody is told it failed; any other `error` is a sign-in that failed. (`transcripts/sign-in-declined.json`) The code is posted to the exchange route with the verifier, as JSON, and only an answer of `200` is a sign-in: the shell is fetched again, and the shell says who is signed in. One at a time: one started while a session is open takes its place. (`transcripts/hand-over.json`) The systems are named as the server's list of apps names them: `apple` (the bundle id) and `android` (the package name). The core carries the hand-over for a Windows app too, as `windows` (the package family name of a packaged app, the id it was built with otherwise, as the client gives `app_id`), but the framework's server does not accept Windows apps yet: its start route answers `400`, so sign-in through the browser is not available on Windows until it does. On Windows the sign-in runs in the person's own browser, whose cookies are not the app's: the hand-over is the only way a sign-in there reaches the app, so with no hand-over routes in the shell a sign-in address is refused (the person is told it failed, and a `report` of `sign_in` says why) and nothing that comes back from the browser is opened as a page. (`transcripts/hand-over-windows.json`, `transcripts/sign-in-windows-plain.json`)
- **A second step.** When the route of a sign-in the app carried out itself (`platform_sign_in`) says a second step is still to come, its page (the call's `second_step`, else the shell's) is opened inside the app, as a task over what is there, with `?next=` the address underneath. When a write from that page leads away, it goes and the shell is fetched again. (`transcripts/second-step.json`)
- **Push.** The client hands the core the device's token with `push_token`. The core posts it to the route the shell names (`device.push.register`), as JSON with the app's id, when somebody is signed in; again when the token changes; and for the next person who signs in. No client makes that request. Asking the person's permission is the `register_push` call, whose result says only what they answered. (`transcripts/push.json`)
- **Signing out on purpose.** A reply that carries `signed_out`: everything of the person's goes at once, the token is taken away at the same route with a `delete`, and when that is answered the client is told to forget the session's cookies (`forget_session`); then the app starts again from the shell and lands where the reply's `navigate` said. A session that ran out is not this: the way in is put up over the work, and the work stays. (`transcripts/signed-out.json`)

SHA-256 is the `sha2` crate, pure Rust. The core makes nothing random itself.

## A launch that is restored

`{"part":"snapshot"}` gives what a client stores when the app leaves the front: the stack of each destination and what is presented over them, each screen's address and title and the part it was opened from, what the person typed into forms and did not send, and which sheets of a page were open. It holds no tree and nothing secret: no token, no ticket, no verifier of a sign-in, no file. What was typed is kept only for kinds on a short list of what is safe to keep: plain text, email, numbers, a phone number, a web address, a search, several lines, a tick, a choice, a date, a slider, a colour, a range; and of text, only when what a system may fill it with (`autofill`) is nothing or names a person's name, address or way to reach them. Of what is typed, never kept: a field the page marks as a password, a one-time code or a card's (by its kind, or by an `autofill` that names one), or of a kind this build does not know (an unknown kind of text is drawn as plain text, echoed as it is typed, and never kept; a page that writes a new secret kind for newer clients should also write `autofill` for older ones). What the page does not mark is kept: a plain or number field the page does not mark is kept, whatever it holds (a PIN, an Aadhaar or PAN number, a card's number written as plain text), so a page that wants such a field never kept marks it. It names the person it was taken for by a hash of their id. A person the shell names without an id can't be told from another of the same name and email, so nothing is kept in a snapshot for them (it holds no stack and no typed word) and none is put back for them: a snapshot belongs to an id. (`transcripts/snapshot-no-id.json`)

When the system has ended the app, the client sends `restore` with the snapshot in place of `start`. The shell is fetched as at any start. If it names the same person, the stacks are put back (only this launch's shell's word counts: a shell kept on the device puts nothing back), each screen with its address and title and nothing to show yet; the screen in front is fetched at once, the others as they come to the front, and what was typed goes back into a screen when its page arrives. A snapshot of another version (`version` is 1), another origin or another person, or one that does not read, is not used: the app starts as it does the first time, and says so with a `report`. While a snapshot waits for the shell, asking for a snapshot gives the waiting one back as it was, so a place the person had is not lost to a snapshot made of the bars alone. It is dropped only when a shell answers for somebody else or for nobody, when the answer is not a shell (a `report` says so), or when the person signs out; a shell that could not be reached leaves it waiting, and when the shell then names the same person its stacks are put back over the first page that was asked for meanwhile, unless the person has already moved on: gone to another destination or screen, or begun something on that page (words typed into it that differ from what it gave, a send from it on its way or waiting, a search, a row of a table chosen, another tab chosen), in which case the page stays and the snapshot is dropped with a `report`. Before this launch's shell has answered, and for a person named without an id, a snapshot asked for holds nothing and has `person_unknown: true`: **a client does not store it**, so that a visitor's blank snapshot never replaces a person's, and what is on screen is never labelled with a person the server has not named in this launch. One restored with `person_unknown` is not used. (`transcripts/snapshot.json`, `transcripts/snapshot-refused.json`, `transcripts/keep-restore.json`)

## Lists and tables that change

- **A list kept up to date.** A list that says the revision its rows are at (`since`), where to ask what changed (`changes`) and the stream that says when (`live`) is kept up to date by the core: a burst of messages costs one ask, and the answer is a `merge` op. A row that changed takes the place of the one with its id, new rows join at the end the op names, rows that left go, and what the person typed into a row that stays is kept. (`transcripts/live-list.json`) What a stream says is taken by the page on the screen: while the screen's page is being fetched (a pull to refresh, a screen that was out of date coming back), a live region or list asks nothing of the page that is going, and once the new page is shown it asks what it owes (a list since the new page's revision); a fetch the new page took away is not counted as out, so the region goes on hearing its stream. A screen that comes back to the front under a stream another screen kept open catches up at once, as it does when its stream opens again. (`transcripts/live-page-on-its-way.json`, `tests/live.rs`)
- **Rows by cursor, both ways.** `more` loads the rows after the last, and with `before` the ones before the first. A table's next rows come as a `rows` op; one row is changed by `row`, which keeps whether it is chosen, and taken out by `remove`. (`transcripts/table-rows.json`)
- **Rows chosen.** The ids of the rows chosen go with the form the table's `select` names, under the name it gives, after the form's own fields and before the pair of the button that sent it. A row that can't be chosen (`unchoosable`) is passed over by "all" and never sent. When the person takes every record that matches (`across`), what stands for that is sent in place of the ids, until a row is cleared or the table's region is fetched again. (`transcripts/table-words.json`)
- **Changes that name their rows.** A merge, a row drawn again, a row taken out, rows that join the start, a move and what is under a row opening or shutting are each a `redraw` change that names the rows, so a client draws those again and not the screen.
- **A day pager.** A step to another day (the pager's `previous`, `next` or `today`, sent as a plain `navigate`) takes the day's place on the screen: the screen keeps its place in its stack, and back does not lead through the days. A day picked in the system's date control is the pager's `pick` address sent with the day as the action's `text` (`YYYY-MM-DD`); the core asks for it under the name the pager gives, and not at all for a day outside the pager's first and last. (`transcripts/health-charts.json`)
- **The pager in a screen's bar.** A screen may carry its pager as its own (`screen.pager`) and not among its parts. It steps and picks the same way, and when a screen has both, the one in the bar is asked first. Ops reach it as they reach a part: the scores it holds are found by their own id (they stand between the screen's actions and its body in document order), a `morph` or a `replace` that brings a `day_pager` for the pager's id takes its place, and a `remove` of that id takes it away with what it holds. (`transcripts/bar-pager.json`)
- **Parts added to a composed screen.** An `append` and a `prepend` add to a `card`, to `layers` and to a `carousel` as they add to a stack or a list: to the part's children, never to a card's menu. A part whose id the target already holds is passed over. A `shape` holds nothing, and the two rooms of an `adaptive` part are not one list, so neither is added to: name the stack inside. (`transcripts/composed-ops.json`)
- **Tabs.** Of a set of tabs with an id, the selected one shows. A lazy region in another tab is fetched when its tab is chosen (`tab`). A tab that is a link takes the screen to its page. (`transcripts/tabs.json`)
- **Rows moved.** A row the person dragged stands where they put it at once; the move is posted as `item`, `from`, `to`, `before` and `position`, with the list's own fields; the row and the lists are named by the app's own keys where the page gave them, and by their ids where it did not. A move the server refuses, or that fails on the way, puts the row back. A row moves within its list and between the lists of one `group`, never into a full one. (`transcripts/reorder.json`)

## What the core sends for the client

- **Every post is marked `xsrf`.** The client sends the session's token as the `x-xsrf-token` header, from the `XSRF-TOKEN` cookie, as a browser's runtime does with every post. A token the page wrote into a form or an action goes as it came, beside it. So a post from a menu that an answer brought, which has no page to take a token from, is sent like any other. (`transcripts/menu-post.json`)
- **A field's own doing.** A field that says `changed` sends its form as it changes (at once for a tick or a pick, when the typing pauses for text) or runs commands with what it holds. No one tapped, so a change may only change what the screen shows and send the form the field stands in: copying, sending another form, going to an address, a request of its own and a device call wait for a tap, and each kind refused is said once with a `report`. (`transcripts/field-changed.json`, `transcripts/changed-limits.json`)
- **Searched options.** The search of a choice is asked when the typing pauses, never for fewer characters than the control asks for. The answer is the field's because the request that asked was for it, whatever name the field in the answer has, and an answer to an older search is dropped. (`transcripts/searched-choice.json`)
- **A confirmation.** The core posts the call's ticket to the challenge route the call names, as JSON, and hands the client what came back with the `device` effect. The client shows the system's passkey sheet and nothing else; the assertion is posted where the call said, as `credential`, without the ticket, which the challenge spent. (`transcripts/device-call.json`)
- **A phone number's country.** A phone field that names a country sends it as a second field beside the number: the one the person picked, or the one the page came with. (`transcripts/phone-country.json`)
- **A sign-in with a provider.** The core asks the nonce route, hands the client the nonce, and posts the token the provider's sheet gave to the app's sign-in route as JSON, with the state the nonce came with. Only an answer that is the person signed in counts as one: the shell and the screen are then fetched again. An answer that says a second step is still to come signs nobody in; the person is told (`second_step`) and the page is asked again. (`transcripts/platform-sign-in.json`)

## What a redirect means

The core follows redirects itself, and a redirect means one of three things.

- **The session ended.** An answer of 401 that carries a `navigate` op, or a redirect that lands on an address the shell's routes present with no chrome as a full cover or a sheet. The way in is put up over what the person was doing, as the route says, and can't be taken away. When a write from it leads somewhere else, it goes, and the person is back where they were. (`transcripts/session-ended.json`)
- **The page has moved.** Any other redirect of a plain request. The screen takes the address the answer came from, and nothing is presented over anything. (`transcripts/page-moved.json`)
- **A post was done.** A redirect, or a `navigate` op, in the answer to a write. Out of a presented screen and back to what is under it; back to a screen already in the stack; or in place of the screen that posted. A `navigate` op that says how to `present` its screen is obeyed instead. (`transcripts/post-landing.json`, `transcripts/form-redirect.json`)
- **A write that did not come back whole.** An answer to a write that failed (a timeout, another connection failure, a 5xx) or was too large to read still counts as a write for what is kept and for the other screens: the server may have written before it failed; a write that never left the device is not a write: with no network nothing kept is emptied for it. A write the server took (a status below 400) whose answer is past one of the protocol's caps is saved: the person is told so with the notice `saved_not_refreshed` (saved, and the screen could not be brought up to date), never `failed`. (`reduce::tests`)

A redirect that leaves the app's origins opens outside the app and is never fetched. One whose address does not read (see "Addresses") is not followed: the request failed, as a sixth redirect in a row does. (`transcripts/addresses.json`)

## What the core keeps current

- **The shell.** Every answer names the shell it was written beside, in its `shell` field or its `x-navree-shell` header. When that differs from the shell the core holds, the shell is fetched again, once for each new name.
- **The app.** An answer whose `app` (or `build`) differs from the last one empties the pages kept.
- **The person.** When the shell's user becomes nobody, every screen is emptied and what was kept is thrown away, but the addresses stay, so the same person signing in again is back where they were. When it becomes someone else, nothing of the person before stays, not even where they were.
- **A newer server.** A kind of node, action, command, control or op this build has never heard of costs that one thing: its stand-in is drawn, or the page is the web view's, or the screen is fetched again. A word a closed list lacks is read as the field's default.

## What is kept between launches

With `cache.persist`, the core hands the client things to keep for the next launch, with `cache_write`, under keys the client need not understand. A kept page is a **head start**: it is shown at once, marked as kept (`cached`), nothing is sent from it, and the fresh answer takes its place as soon as it arrives. It can therefore be on the screen for a moment after the session it was answered for has ended, until the core learns that; a page that must never be, even for a moment, is not marked as keepable.

- **The shell**, always: the app opens with its bars drawn from the shell kept on the device, but only the app's name and its top-level destinations (label and icon): not the context line, the group labels, the items below the top level, the counts beside destinations, nor the person or their menu, until this launch's shell has answered and named them. Two kinds of "no shell": when this launch's shell request **did not get through** (no network, a timeout, a 5xx, a 429) the kept bars stay, the screens show their could-not-load state with its retry, a waiting snapshot keeps waiting, and the shell is asked for again (when the person retries, when the app comes to the front, after a pause that starts at two seconds and doubles up to a minute, and, only while the shell's own last failure was the network's or a timeout, when a request of the app gets through, once in each pause; the pause is not kept while the app is in the background, and an answer that says the app is too old ends the asking; the same whichever comes first, that request's failure or the kept shell being read, as with no network the request fails before the file is read); when the answer **is not a shell** (a 404 or another status, another type, one that does not read, another major) the kept shell is replaced by the blank one, which has no context line and one destination, and stays so until a real shell answers. (`transcripts/shell-retry.json`, `transcripts/keep.json`) The app's name and its top-level destinations are drawn before the server names anybody, so an app that gates a tab by role, or names itself by tenant, shows them to whoever opens the device: such an app should not ask the client to keep its shell (leave `cache.persist` off). (`transcripts/keep-shell.json`) With a snapshot waiting, no screen is opened under the kept shell while the shell is asked: the snapshot is put back, or not, once it answers. (`transcripts/keep-restore.json`)
- **A page**, only when it was asked for with a `get` and its answer was a whole page (not a region or a list's rows), with success, carrying `x-navree-keep: 1`. The server sends the header when the page's `Cache-Control` does not say `no-store` (`View::cache("private, no-cache")`, or `native::Answer::cache` for a screen written for native clients lets a page be kept), and only on an answer to a `GET` or `HEAD`. Any other answer for an address (an error, a redirect, an answer to a post, a page for the web view, ops alone, an answer without the header) takes away what was kept for it. A page is kept under its whole address as it leaves the core, so two spellings of one address are one page. Pages kept in memory while the app runs are as before. (`transcripts/keep.json`, `transcripts/keep-answers.json`)
- **What is kept has an owner**: the person, or the visitor, its pages were answered for, written beside the list in `boot`. A person is named by the id the shell's answer gives in `x-navree-person`, and always by name and email. Two are the same person when both have an id and the ids are equal (two people of one name are two people), or when either has none and the name and email are equal, so an answer that lost its id (a proxy, a server rolled back) wipes no screen and nothing typed. What is kept, though, belongs to a visitor or to an id, never to a name: a person named without an id keeps nothing and reads nothing, and what was kept is emptied once. Pages are kept for a signed-in person only when the server's answers name the person, which the framework's own sign-in does; an app that signs people in its own way gives the framework its principal (`CurrentPrincipal`) for that. (`transcripts/keep-ids.json`, `transcripts/keep-person.json`, `transcripts/keep-who.json`) **A kept page is read, and a page is written, only when this launch's shell has answered over the network as a shell and named that owner**, whatever order the answers come in; every answer of the shell asks again. Before that, a kept page is not even read. A shell that names someone else empties everything kept first. An answer that is not a shell (a 404, another type, one that does not read) names nobody and makes nothing readable. A `boot` with no owner (written by an older build), or whose kept shell does not read, is emptied, not taken. A shell that can't be reached: no kept page is drawn, and the screen shows what a screen that could not load shows. The fresh answer always takes a kept page's place. (`transcripts/keep-owner.json`)
- **A page is kept under the person its own answer was made for.** Every native answer names that person in `x-navree-person` (as the shell's answer does; nobody signed in, no header), and the core compares every answer with the person the shell named: a difference is the news that the session changed without the app being told (a sign-in in the web view, a session that ran out). Nothing of that answer is kept, what is kept is emptied, in memory too, and the shell is asked again; a `report` says it once. A session belongs to a host: an answer from another origin the app allows is never kept, and is compared only when it names a person (a session cookie shared across subdomains); one that names nobody says nothing of the person the shell named, and one that names another person than the shell did only makes the core ask for the shell again (once, while none is on its way) and say so: it empties nothing and clears nobody, since only the shell's own answer decides who is signed in. (`transcripts/keep-session.json`, `transcripts/keep-also.json`) An answer that did not get through to the app (a 5xx or a 429, what a proxy or a gateway in front of it answers while the app restarts or sheds load) and names nobody is not compared: it is not the app's word on who is signed in, it is never kept, and the next answer that gets through is compared as every answer is. One of those that names a person is compared, and every other answer that names nobody is too: a 401 or a 403 that names nobody is still the news that the session ended. A server that answers its own 5xx for a signed-in person names the person on it (the framework names every native answer that passes its authentication). (`transcripts/keep-unreached.json`) The core writes a page only when that person is the store's owner and the person this launch's shell named. A sign-in, a way in that has done its work and a session's end clear who the shell named until a shell asked after them answers; a shell request on its way at that moment is dropped and asked again. (`transcripts/keep-sign-in.json`)
- **The session can change where the core is not told.** A page in the web view shares the cookies, and a session can run out while the app is away. So after a page was shown in the web view, a link came from one, or the app came back to the front, nothing kept, in memory or on the device, is drawn until a shell asked after that has named the person again. That shell is asked for at once, so head starts and keeping are back as soon as it answers; a shell answer asked before it is dropped whole, neither shown nor kept. (`transcripts/keep-unseen.json`, `transcripts/keep-stale-shell.json`)
- **Taking away and emptying reach the device whatever the core holds.** Any read answered without the header before the list was read (a page, a search form's query, an answer for the web view) is taken away once the list is read and holds it. Nothing is written to the device for a page that was never kept. A write, a new build and a change of person empty the device's store even when nothing is listed. The build the pages were answered by is kept beside them, so a deploy between launches empties them. (`transcripts/keep-store.json`)
- **A kept page is drawn only for the read that asked for it.** A read that was on its way when what is kept was emptied (a change of person, a write, a new build), or that was never asked, is dropped when its answer comes. (`transcripts/keep-reads.json`)

**One core for the app.** A client runs one core for the app, not one for each window or scene: what is kept on the device is one store, and a core is the one that knows whose it is. Pages are kept under their owner (`page:<id>:<address>`, `page:visitor:<address>`), so two cores over one store, one naming a person and one a visitor, never read or write each other's pages; but `boot` is one list, so a second core makes the first lose its head starts. (`two_cores_over_one_store_never_mix_their_owners_pages` in `src/reduce.rs`)

**What a client must do with what it keeps** (the cache and the snapshot): store it so that it can't be read while the device is locked, where the system offers that; store no snapshot that says `person_unknown`; leave it out of backups and of a move to another device; and empty it on `forget_session` and `cache_clear`, in the order the effects arrive.

## The conversations

`transcripts/` holds each conversation with a server as a sequence of events in and the updates expected out, to be read by a person and replayed by the tests: opening the app, pages, every way a link is presented, route rules, back, refresh, forms (messages at fields, one send at a time, redirects, files), every op and command, regions, live regions, lists by cursor, the table's query, the web view's page, an app too old, kinds a build has never heard of, a session that ends, a page that moved, where a post leads, device calls, a sign-in with a provider, a sign-in handed over from the system's session, a second step, push, signing out on purpose, a launch that is restored, tabs, lists that change by revision, tables row by row, rows moved, fields that act as they change, ranges, searched options, ticked menu items, questions, a post from a menu an answer brought, tasks, the health charts and a day pager stepped in place, a pager in a screen's bar, parts added to a card and a carousel, the part a screen was opened from, a destination's page pushed as a detail, failures, answers nobody waits for any more, links from outside, addresses that do not read and an id in another script, a change of person, and what is kept between launches. The bodies in `transcripts/fixtures/store` are what the store demo answered; those in `fixtures/made` are written by hand.

`NAVREE_CORE_TRANSCRIPTS=write cargo test -p navree-native-core --test transcripts` writes the expected updates and the schema file again after a change that is meant.
