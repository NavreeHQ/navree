# Open issues left by the framework build integrators

- [W0-integrate-1] Spec §3 contradicts itself: it says a crate may depend only on lower layers, but its table lets navree-config (L1) depend on navree-contracts (L1). The graph test follows the table. navree-config now only dev-depends on contracts, but the spec owner should still reword the rule.
- [W0-integrate-1] A singleton that stores an AppContext, for example from `r.app()`, creates an Arc cycle, so the app's memory is never freed. This is harmless for a long-running process but leaks in tests that boot many apps; prefer `r.lazy::<T>()`, which holds the app weakly.
- [W0-integrate-1] AppContext::get, try_get and get_named search every provider each time they are called. navree-http should resolve optional services such as `dyn Authenticator` once, when the router is built, not on every request.
- [W0-integrate-1] If a configured (for_root) module is found after a plain import of the same module was already registered, the graph walk restarts. In that case `register` can run more than once for some modules during that one boot; this is documented in the code.
- [W0-integrate-1] A provider registered with `.lifecycle::<T>()` must be a singleton. A request-scoped one fails at boot with MissingRequestScope, and boot-time validation does not catch this.
- [W0-integrate-1] Tests of ConfigModule with no for_root and of ConfigSources::defaults() read the real APP_* environment variables. A developer machine with conflicting APP_ variables could make them fail.
- [W1-integrate-1] navree-access/Cargo.toml contains only the pure engine's dependencies. Task 22 must add back navree-kernel, navree-contracts, navree-config, navree-http, navree-db, navree-cache, axum, http, moka, sea-orm, sea-orm-migration, tokio and tracing, plus the dev-dependencies navree-testing and tempfile. All of these edges are already allowed.
- [W1-integrate-1] Five crates each have their own 'list or comma-separated string' deserializer: navree-log, navree-view, navree-http-client, navree-crypto and navree-http. A shared helper in navree-config would be cleaner but is not required.
- [W1-integrate-1] navree-cache: MemoryStore has no size limit, and there is no Redis store yet (CacheStoreKind is #[non_exhaustive], so one can be added).
- [W1-integrate-1] The navree-http and navree-events log-capture tests use `tracing::subscriber::set_default` in multi-test binaries. Because of a tracing-core 0.1.36 quirk, a callsite whose interest is first computed on a thread with no subscriber can stay disabled. I checked the reasoning and ran the navree-http binary 25 times with no failure. If these tests ever flake, move them into their own test binary, as navree-http-client did.
- [W1-integrate-1] navree-http-client cannot pick up the current request's RequestId automatically; callers must pass `.with_request_id(&id)`.
- [W2-integrate-1] No test boots navree-testing and navree-db together: the hierarchy forbids either crate from dev-depending on the other. My probe showed they work together; the Task 31 facade full-stack tests should keep a test like it.
- [W2-integrate-1] A DbErr raised while the Uow layer commits (for example from a change observer) becomes a plain 500 through AppError::internal. It does not go through the map_error mappers, so a constraint violation detected only at commit is not a 409. **Correction 2026-10-26:** a constraint violation detected at COMMIT (for example a deferred foreign key) does map to 409, as a test in target/docs-check/review shows; the error layer sits outside the unit of work (navree-db http.rs, uow.rs). Observer errors still need checking.
- [W2-integrate-1] navree-testing's TempDirGuard deletes its directory on a best-effort basis. On Windows, a TestApp dropped without `shutdown()` may leave its SQLite files in %TEMP%, because the pool is still open. Tests should call `app.shutdown().await`.
- [W2-integrate-1] Open worker followups for later waves: - navree-api cannot document query parameters, because ApiMeta has no params field. - utoipa gives every `Page<T>` the schema name `Page`; CRM modules should call `m.api_schema::<T>()` or navree-db should name each one. - The Scalar docs page loads its script from jsdelivr with no SRI hash (for the security review). - navree-http does not map MultipartError itself; only apps with StorageModule get 4xx instead of 500 for multipart errors. - Optional: navree-http could re-export `http::Method` for the macros.
- [W2-integrate-1] The navree-db `postgres` feature has only been compiled, never run against a real PostgreSQL server.
- [W3-integrate-1] The facade (crates/navree) is still the Task 31 stub. Worker followups for it are pending: `pub use navree_session/access/validation/queue/audit/schedule/notify` and the prelude entries. navree-macros' generated code needs `navree::http` and `navree::access` at the facade root.

- [W5-integrate-1] crm-web BFF (owned by the crm-web agent, not touched here): login must handle `{two_factor_required, challenge_token, expires_in}` without setting cookies, and add a `/api/auth/2fa/verify` step that stores tokens the way login does. `PATCH /api/auth/me/password` returns a new TokenPair, and the BFF must replace its token cookies with it. Regenerated OpenAPI types now show the login 200 response as LoginResult = LoginResponse | TwoFactorChallenge.
- [W5-integrate-1] crm-api (Wave 6; apps/crm-api is still a stub): set `auth.password_reset.url` (e.g. http://localhost:3000/reset-password) and `auth.verification.base_url` or `app.url`. Register QueueModule so account mails go through jobs: without a dispatcher, Mailer::queue sends inline after the commit, so forgot-password answers a registered email more slowly than an unknown one (timing-based email enumeration).
- [W5-integrate-1] Security review candidates (Task 39): `POST /auth/2fa/enable` and `POST /auth/2fa/recovery-codes` need only a bearer token, not the password, so a stolen access token can mint new recovery codes. navree-http ValidSignature answers 401 'Invalid signature.' where Laravel uses 403. Forgot-password and reset-password have no per-IP route throttle: only the global per-IP limit and the per-email resend throttle apply. Access tokens stay valid until they expire after a password change or reset (stateless JWT, by design).
- [W5-integrate-1] Optional, not done: navree-macros doctest expansion naming (`crate::kernel` inside the facade's own doctests; worked around with hidden imports). `LoginOutcome` and `TwoFactorProof` are not in the facade prelude; they are reachable as `navree::auth::*`.
- [W6-integrate-1] navree-api cannot document query parameters or non-JSON bodies: `GET /api/v1/contacts/export` (text/csv) has no response schema, and the list filters are described in route descriptions plus `api_schema` components (CompanyFilters, CompanySort, ContactFilters). Framework routes without response schemas: `/api/me/abilities` and `/api/access/*` (navree-access has no utoipa), `/broadcasting/auth`, `/app/{key}`, `/health/*`, `/metrics`. Every operation also lists the `cookie` security scheme, which the JWT-only CRM does not use.
- [W6-integrate-1] OpenAPI names vs crm-web's hand-written types (Task 38 fixes types.ts): `CreateUser`/`UpdateUser` (web: UserCreateInput/UserUpdateInput), `UserRole` (web: Role), `Stage` (web: DealStage), `SubjectType` (web: ActivitySubjectType). There is no `PageMeta` component: every page schema (CRM and framework) inlines `meta`. `__type` is a one-value enum on Company/Contact and a string with an example on Deal/Activity/User. The `user` in login and `/api/auth/me` is documented as `UserResource` without `roles` (W4b issue).
- [W6-integrate-1] navree-access: the record loader behind `#[can(.., from = "id")]` has no soft-delete scope, so a user whose rules deny the action gets 403 (not 404) on a soft-deleted company or contact, which reveals that it existed; handlers check `deleted_at` themselves. navree-validation's `AsyncRule::exists` cannot add `deleted_at IS NULL`, so services re-check deleted companies.
- [W6-integrate-1] navree-validation: serde errors (wrong type, unknown enum value) are reported before and instead of the garde rules, one at a time: `{"name": "", "size": "huge"}` reports only `size`. crm-companies works around missing required fields with `#[serde(default)]` plus rules.
- [W6-integrate-1] crm-api has no committed `.env`; without `APP_KEY` the API signs JWTs with a random per-process key, so tokens (and crm-web's BFF cookies) stop working after every restart. Whoever runs the API for crm-web or Playwright should export `APP_KEY` (`base64:<32 bytes>`, e.g. from `cargo run -p crm-api -- key:generate`).
- [orm-adopt-crates] navree-schema's `uuid` column is `CHAR(36)` on MySQL (`UUID` on MariaDB 10.7+), but navree-orm and SeaORM bind a `Uuid` as its 16 bytes there (`Value::Uuid`), which suits the `binary(16)` columns SeaORM migrations create and not a `CHAR(36)` one: inserting a `Uuid` field into a schema-builder `uuid` column fails on MySQL (invalid string value) or stores the raw bytes. Either the schema builder makes `uuid` a `BINARY(16)` on MySQL, or the ORM binds `Uuid` values as their hyphenated text there (reading already accepts both). This is why the framework's table-creating migrations were not rewritten with the builder.
- [orm-adopt-crates] Left on SeaORM inside the adopted crates, by design: writes of users, webhook endpoints, social accounts and workspace rows (through `Repo`, for their audit trails), the queue's `jobs`, `job_batches` and `operations` tables (hand-written atomic reservations, optimistic version checks and counters), and navree-notify's read-state methods (`Notifier::notifications`, `unread_count`, `mark_as_read`, `mark_all_as_read`), whose public signatures take any SeaORM `ConnectionTrait`, which the ORM's `Executor` does not cover. navree-oauth's grant flows and navree-social's reads could move to the ORM next (their models are ready).
