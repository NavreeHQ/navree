# Open issues left by the framework build integrators

- [W0-integrate-1] Spec §3 contradicts itself: it says a crate may depend only on lower layers, but its table lets keel-config (L1) depend on keel-contracts (L1). The graph test follows the table. keel-config now only dev-depends on contracts, but the spec owner should still reword the rule.
- [W0-integrate-1] A singleton that stores an AppContext, for example from `r.app()`, creates an Arc cycle, so the app's memory is never freed. This is harmless for a long-running process but leaks in tests that boot many apps; prefer `r.lazy::<T>()`, which holds the app weakly.
- [W0-integrate-1] AppContext::get, try_get and get_named search every provider each time they are called. keel-http should resolve optional services such as `dyn Authenticator` once, when the router is built, not on every request.
- [W0-integrate-1] If a configured (for_root) module is found after a plain import of the same module was already registered, the graph walk restarts. In that case `register` can run more than once for some modules during that one boot; this is documented in the code.
- [W0-integrate-1] A provider registered with `.lifecycle::<T>()` must be a singleton. A request-scoped one fails at boot with MissingRequestScope, and boot-time validation does not catch this.
- [W0-integrate-1] Tests of ConfigModule with no for_root and of ConfigSources::defaults() read the real APP_* environment variables. A developer machine with conflicting APP_ variables could make them fail.
- [W1-integrate-1] keel-access/Cargo.toml contains only the pure engine's dependencies. Task 22 must add back keel-kernel, keel-contracts, keel-config, keel-http, keel-db, keel-cache, axum, http, moka, sea-orm, sea-orm-migration, tokio and tracing, plus the dev-dependencies keel-testing and tempfile. All of these edges are already allowed.
- [W1-integrate-1] Five crates each have their own 'list or comma-separated string' deserializer: keel-log, keel-view, keel-http-client, keel-crypto and keel-http. A shared helper in keel-config would be cleaner but is not required.
- [W1-integrate-1] keel-cache: MemoryStore has no size limit, and there is no Redis store yet (CacheStoreKind is #[non_exhaustive], so one can be added).
- [W1-integrate-1] The keel-http and keel-events log-capture tests use `tracing::subscriber::set_default` in multi-test binaries. Because of a tracing-core 0.1.36 quirk, a callsite whose interest is first computed on a thread with no subscriber can stay disabled. I checked the reasoning and ran the keel-http binary 25 times with no failure. If these tests ever flake, move them into their own test binary, as keel-http-client did.
- [W1-integrate-1] keel-http-client cannot pick up the current request's RequestId automatically; callers must pass `.with_request_id(&id)`.
- [W2-integrate-1] No test boots keel-testing and keel-db together: the hierarchy forbids either crate from dev-depending on the other. My probe showed they work together; the Task 31 facade full-stack tests should keep a test like it.
- [W2-integrate-1] A DbErr raised while the Uow layer commits (for example from a change observer) becomes a plain 500 through AppError::internal. It does not go through the map_error mappers, so a constraint violation detected only at commit is not a 409.
- [W2-integrate-1] keel-testing's TempDirGuard deletes its directory on a best-effort basis. On Windows, a TestApp dropped without `shutdown()` may leave its SQLite files in %TEMP%, because the pool is still open. Tests should call `app.shutdown().await`.
- [W2-integrate-1] Open worker followups for later waves: - keel-api cannot document query parameters, because ApiMeta has no params field. - utoipa gives every `Page<T>` the schema name `Page`; CRM modules should call `m.api_schema::<T>()` or keel-db should name each one. - The Scalar docs page loads its script from jsdelivr with no SRI hash (for the security review). - keel-http does not map MultipartError itself; only apps with StorageModule get 4xx instead of 500 for multipart errors. - Optional: keel-http could re-export `http::Method` for the macros.
- [W2-integrate-1] The keel-db `postgres` feature has only been compiled, never run against a real PostgreSQL server.
- [W3-integrate-1] The facade (crates/keel) is still the Task 31 stub. Worker followups for it are pending: `pub use keel_session/access/validation/queue/audit/schedule/notify` and the prelude entries. keel-macros' generated code needs `keel::http` and `keel::access` at the facade root.
- [W3-integrate-1] keel-api: the keel-access management routes have ApiMeta but no request or response schemas, because keel-access has no utoipa dependency. This is optional.
- [W3-integrate-1] Change observers run during commit, after the Uow is marked finished, so a ChangeObserver that dispatches a job still inserts on the pool and would block on SQLite. This was already the case before this wave and nothing does it today.
- [W3-integrate-1] PostgreSQL-only paths (FOR UPDATE, SKIP LOCKED in queue reservation, record loads FOR UPDATE) are written but untested, as spec §2 allows.
- [W4-integrate-1] docs/prd/keel-prd.md still describes problem+json, 422 and 419 (about a dozen places: lines 133, 173, 175, 177, 231, 317, 424, 712, 713, 820, 977, 982). The older task sections of the plan (Tasks 4, 14, 15, 17, 19, 21, 23) also still mention 422/419/problem, but spec §10 and Task 28a override them. I did not edit the docs.
- [W4-integrate-1] keel-session still serves `!GET /sanctum/csrf-cookie`, and keel-testing still has `TestClient::csrf_cookie()`. These are Sanctum-era pieces. keel-session is optional and the CRM does not import it, but the owner of the auth direction should decide whether to rename or keep them, given spec §10 says "No Sanctum CSRF-cookie endpoint".
- [W4-integrate-1] keel-auth (Task 28) and the facade crates/keel are still stubs, and this wave did not include auth-core. The ignored test `keel_new_output_compiles_against_the_workspace` can only run against the real facade once Task 31 (the facade) and Task 28 (keel-auth) land. It now passes against the stand-in facade in target/agents/cli/verify/keel, which uses a guest-only AuthModule.
- [W4-integrate-1] keel-cli `keel dev` does not keep the listening socket open across restarts (no listenfd), and if keel itself is killed forcibly the child server keeps running. Both are documented deviations; keeping the socket would need keel-http to accept an inherited listener.
- [W4b-integrate-1] A present but invalid JWT is a 401 on every route, public ones included, because keel-http runs the Authenticator before routing (per the plan: never silently treated as a guest). Clients must not send stale access tokens to /api/auth/login, /api/auth/refresh or /health/*. crm-web's BFF already doesn't.
- [W4b-integrate-1] jsonwebtoken's rust_crypto feature also pulls in rsa 0.9, which has advisory RUSTSEC-2023-0071 (Marvin attack). keel uses HS256 only, so the RSA code is never run; it is only an audit-noise and supply-chain item.
- [W4b-integrate-1] The OpenAPI schema of GET /api/auth/me and of `user` in login/register is `UserResource` without the fields a UserResourceExtension adds (e.g. CRM `roles`). The real response includes them; the generated TypeScript types will not.
- [W4b-integrate-1] Registration has no auth-specific rate limit; only keel-http's per-IP limit applies (PRD S5). Behind the BFF, http.trust_proxy is needed for per-client limits.
- [W4b-integrate-1] refresh_tokens rows grow with every refresh and there is no `auth:prune` command yet. Refresh-token lifetime slides: each rotation gets a fresh 30 days.
- [W4b-integrate-1] keel-auth keeps keel-mail, totp-rs and qrcode2 as unused dependencies for Task 30.
- [W4b-integrate-1] TestAppBuilder::fake_auth replaces keel-auth's authenticator completely, so a test cannot mix acting_as with real bearer tokens in one app.
- [W5-integrate-1] crm-web BFF (owned by the crm-web agent, not touched here): login must handle `{two_factor_required, challenge_token, expires_in}` without setting cookies, and add a `/api/auth/2fa/verify` step that stores tokens the way login does. `PATCH /api/auth/me/password` returns a new TokenPair, and the BFF must replace its token cookies with it. Regenerated OpenAPI types now show the login 200 response as LoginResult = LoginResponse | TwoFactorChallenge.
- [W5-integrate-1] crm-api (Wave 6; apps/crm-api is still a stub): set `auth.password_reset.url` (e.g. http://localhost:3000/reset-password) and `auth.verification.base_url` or `app.url`. Register QueueModule so account mails go through jobs: without a dispatcher, Mailer::queue sends inline after the commit, so forgot-password answers a registered email more slowly than an unknown one (timing-based email enumeration).
- [W5-integrate-1] Security review candidates (Task 39): `POST /auth/2fa/enable` and `POST /auth/2fa/recovery-codes` need only a bearer token, not the password, so a stolen access token can mint new recovery codes. keel-http ValidSignature answers 401 'Invalid signature.' where Laravel uses 403. Forgot-password and reset-password have no per-IP route throttle: only the global per-IP limit and the per-email resend throttle apply. Access tokens stay valid until they expire after a password change or reset (stateless JWT, by design).
- [W5-integrate-1] Optional, not done: keel-macros doctest expansion naming (`crate::kernel` inside the facade's own doctests; worked around with hidden imports). `LoginOutcome` and `TwoFactorProof` are not in the facade prelude; they are reachable as `keel::auth::*`.
- [W6-integrate-1] keel-api cannot document query parameters or non-JSON bodies: `GET /api/v1/contacts/export` (text/csv) has no response schema, and the list filters are described in route descriptions plus `api_schema` components (CompanyFilters, CompanySort, ContactFilters). Framework routes without response schemas: `/api/me/abilities` and `/api/access/*` (keel-access has no utoipa), `/broadcasting/auth`, `/app/{key}`, `/health/*`, `/metrics`. Every operation also lists the `cookie` security scheme, which the JWT-only CRM does not use.
- [W6-integrate-1] OpenAPI names vs crm-web's hand-written types (Task 38 fixes types.ts): `CreateUser`/`UpdateUser` (web: UserCreateInput/UserUpdateInput), `UserRole` (web: Role), `Stage` (web: DealStage), `SubjectType` (web: ActivitySubjectType). There is no `PageMeta` component: every page schema (CRM and framework) inlines `meta`. `__type` is a one-value enum on Company/Contact and a string with an example on Deal/Activity/User. The `user` in login and `/api/auth/me` is documented as `UserResource` without `roles` (W4b issue).
- [W6-integrate-1] keel-access: the record loader behind `#[can(.., from = "id")]` has no soft-delete scope, so a user whose rules deny the action gets 403 (not 404) on a soft-deleted company or contact, which reveals that it existed; handlers check `deleted_at` themselves. keel-validation's `AsyncRule::exists` cannot add `deleted_at IS NULL`, so services re-check deleted companies.
- [W6-integrate-1] keel-validation: serde errors (wrong type, unknown enum value) are reported before and instead of the garde rules, one at a time: `{"name": "", "size": "huge"}` reports only `size`. crm-companies works around missing required fields with `#[serde(default)]` plus rules.
- [W6-integrate-1] crm-api has no committed `.env`; without `APP_KEY` the API signs JWTs with a random per-process key, so tokens (and crm-web's BFF cookies) stop working after every restart. Whoever runs the API for crm-web or Playwright should export `APP_KEY` (`base64:<32 bytes>`, e.g. from `cargo run -p crm-api -- key:generate`).
