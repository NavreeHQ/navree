title: "Connecting an existing crate"
description: "Make a client crate a module with ClientModule, put a tower layer whose service can fail on the app with FallibleLayer, serve any tower service under a path with Mount, and serve a tonic server built elsewhere with TonicService, all behind the app's access checks."
---

A plugin often brings a crate that already exists: a client of a service, a tower middleware, a whole service written with tower, a tonic server generated from a `.proto`. Navree connects each one in a few lines, and keeps it inside the app: its configuration section, its readiness check, the request pipeline and the access check of every request or call.

The examples on this page are a ledger plugin. Its crate wraps a `KhataClient` from another crate, adds a timeout to every request, and serves the ledger under `/khata` for signed-in users.

## A client crate with ClientModule

`ClientModule::<T>::new(name)` makes a module of a client type `T`. `.options::<O>()` names its options: a `ConfigSection` that is `Clone`, read from its section at boot. `.connect(..)` builds the client once at boot from the options and a resolver for the app's other providers. `.health(..)` adds a readiness check named after the module, and `.shutdown(..)` a hook that runs at graceful shutdown:

```rust title="src/client.rs"
use navree::config::ConfigSection;
use navree::plugin::ClientModule;
use navree::prelude::*;
use serde::Deserialize;

/// The `khata` section.
#[derive(Clone, Deserialize, ConfigSection)]
#[config(key = "khata")]
pub struct KhataOptions {
    /// Where the ledger service answers.
    pub base_url: String,
}

/// The client the ledger crate gives.
pub struct KhataClient {
    pub base_url: String,
}

/// The ledger crate's client as a module of the plugin.
pub fn khata_client() -> ClientModule<KhataClient, KhataOptions> {
    ClientModule::<KhataClient>::new("khata")
        .options::<KhataOptions>()
        .connect(|options, _resolver| async move {
            Ok(KhataClient {
                base_url: options.base_url.clone(),
            })
        })
        .health(|client| async move {
            if client.base_url.starts_with("https://") {
                Ok(())
            } else {
                Err("the khata service is not on https".into())
            }
        })
        .plugin(navree::plugin_info!(namespace = "khata"))
}
```

```toml title="config/app.toml"
[khata]
base_url = "https://khata.example/ludhiana"
```

- **The client is exported** to every module as `KhataClient`, and under the module's name: `ctx.get_named::<KhataClient>("khata")`. Two `ClientModule`s of one client type with different names are two modules, each with its own client; the plain `KhataClient` is then ambiguous, so each is reached by its name. Several clients of one type (one ledger per city, say) are several `ClientModule`s, each with a name of its own and its options given in code.
- **Options in code**: `.for_root(KhataOptions { .. })` takes the options as they are, and the section is not read.
- **Order**: call `.options::<O>()` first. It keeps the name, the readiness check, the shutdown hook and the plugin, and drops a connect function given before it.
- **Boot errors**: without `.connect(..)` the boot fails with ``ClientModule `khata` has no connect function: call .connect(..)``, and a connect function that fails stops the boot with its error.
- **Readiness**: an `Ok` from the check is up, an error is down with its message. The message is shown in the readiness report, so it must hold no secret.
- **The plugin**: a plugin's modules are types of its own crate, or `ClientModule`s whose options type is: `.plugin(navree::plugin_info!())` ties the module to the crate that defines its options type. `.plugin(..)` needs an options type: without one, no type of the plugin's crate would tie the module to it.

Add the module to the app like any other: `.module(khata_client())`.

## Tower middleware

A tower layer whose service can fail (its `Error` is not `Infallible`), such as `tower::timeout::TimeoutLayer`, goes on the app with `FallibleLayer::new(layer)`: in a `GlobalLayer` with `AppRouter::layer`, on one hand-written route with `Endpoint::layer`, or on a router with `Router::route_layer`. The service's error answers as a 500 `AppError` with the error as its source, so the client sees `Internal server error`, and in any slot but `Edge` the log records the error and `m.map_error::<E>(..)` turns it into another answer; the `Edge` slot sits outside the app's error rendering, so there the error is neither mapped nor logged. A service that is not ready answers the same way. The ledger's module puts a timeout on every request:

```rust title="src/ledger.rs"
m.http_layer(GlobalLayer::new(
    LayerSlot::Context,
    "khata-timeout",
    |_ctx, router| {
        Ok(router.layer(FallibleLayer::new(tower::timeout::TimeoutLayer::new(
            Duration::from_secs(10),
        ))))
    },
))
.map_error::<tower::timeout::error::Elapsed>(|_| {
    Some(AppError::service_unavailable("The khata took too long."))
});
```

A request that takes longer than ten seconds gets a 503 with the message `The khata took too long.`. See [a layer whose service can fail](/docs/basics/middleware/#a-layer-whose-service-can-fail).

## A service under a path

`m.mount(Mount::new(prefix, service))` serves any tower service under a path prefix, inside the app's pipeline. The service answers the prefix and every path below it, for every method. A mount declares its access as a route does, and the declaration is required:

```rust title="src/ledger.rs"
use std::time::Duration;

use navree::http::extract::Request;
use navree::http::{AppRouter, FallibleLayer, GlobalLayer, LayerSlot, Mount};
use navree::plugin::prelude::*;
use navree::prelude::*;

use crate::client::KhataClient;

/// The ledger's entries: the service mounted under `/khata`.
async fn entries(request: Request) -> Result<String> {
    let ctx = request
        .extensions()
        .get::<AppContext>()
        .cloned()
        .ok_or_else(|| AppError::internal("the request has no app context"))?;
    let khata = ctx.get::<KhataClient>().await.map_err(AppError::internal)?;
    Ok(format!("{} {}", khata.base_url, request.uri().path()))
}

/// The plugin's own module: a timeout on every request, and the ledger under
/// `/khata` for signed-in users.
pub struct LedgerModule;

impl Module for LedgerModule {
    fn register(&self, m: &mut ModuleBuilder) {
        m.plugin(navree::plugin_info!(namespace = "khata"));
        m.http_layer(GlobalLayer::new(
            LayerSlot::Context,
            "khata-timeout",
            |_ctx, router| {
                Ok(router.layer(FallibleLayer::new(tower::timeout::TimeoutLayer::new(
                    Duration::from_secs(10),
                ))))
            },
        ))
        .map_error::<tower::timeout::error::Elapsed>(|_| {
            Some(AppError::service_unavailable("The khata took too long."))
        });
        m.mount(
            Mount::new("/khata", AppRouter::from_handler(entries))
                .authenticated()
                .throttle(60, Duration::from_secs(60)),
        );
    }
}
```

A guest's `GET /khata/entries` is a 401; a signed-in user's answers `https://khata.example/ludhiana /entries`. `use navree::plugin::prelude::*;` brings `m.mount`. The access declarations are a route's: `.public()`, `.authenticated()`, `.roles(&[..])`, `.permissions(&[..])` and `.can(action, subject)` (a type-level check: a mount has no path parameter to name a record), and `.guard(..)`, `.throttle(..)`, `.timeout(..)`, `.body_limit(..)` and `.name(..)` set the rest of a route's metadata.

### What the service sees

The service gets the request as the app received it, but for its URI: the scheme and authority as received, and for the path `/` followed by the rest of the path below the prefix, exactly as received, then `?` and the query as received. `/khata` arrives as `/`, `/khata/entries?month=kartik` as `/entries?month=kartik`. Nothing is decoded, so `%2F`, `%3F` and `%23` reach the service as they were sent, and can't turn into a segment, a query or a fragment (`/khata/v1/items%3Fx` arrives as `/v1/items%3Fx`). The router's decoded copy of the path is not passed on: read the path from the URI. A service decodes its own path, and must treat it as untrusted: the router doesn't refuse `:` or a drive letter.

With no `.methods(..)`, every method reaches the service, extension methods such as `PROPFIND` included, and `HEAD` and `OPTIONS` too. `.methods(&[Method::GET, Method::POST])` limits it to those: another method is a 405 with an `Allow` header, as for a route.

### What runs before it

Every request to a mount passes what a route's request passes, in the same order: the request id, the request context and the client address, the app's global layers (sessions and their CSRF check among them), authentication, then on every request the mount's access check, guards, throttle, timeout and body limit. A mount is one route for these: `.throttle(60, ..)` is one budget for every path and method under the prefix. The body is cut off at the mount's limit, also when it comes without a length.

A request with an `Upgrade` header (a WebSocket or h2c handshake) or the method `CONNECT` never reaches the service. One that reaches the mount is answered `501 Not Implemented`, after the access check:

```text wrap
A mounted service answers requests; it does not take over the connection.
```

With `.methods(..)`, a method the list leaves out, `CONNECT` among them, is answered `405 Method Not Allowed` by the router before the access check, as for a route.

gRPC, gRPC-Web and Connect calls on the HTTP port go to `GrpcModule` before any mount.

### Paths the router refuses

The router refuses some paths with a 400 before any mount or route sees them: a `.` or `..` segment, raw or percent-encoded (`/khata/%2e%2e/x`); a part of the rest of the path that is `.` or `..` once decoded (`/khata/a%2F..%2Fb`); `%00`; a backslash, raw or as `%5C`; and bytes that are not UTF-8 once decoded. The router lets an empty segment reach a mount, and the mount answers it with a 400, after the access check: `//` below the prefix, raw or once each `%2F` (in either case) is read as `/` (`/khata//x`, `/khata/%2Fetc/passwd`, `/khata/a%2F%2Fb`), is ``Invalid URL: the path has an empty segment``. A trailing slash after a segment is kept (`/khata/a/` arrives as `/a/`), but `/khata/` and the prefix in another case (`/KHATA/x`) are not found.

So a service whose own paths need such bytes can't be mounted as it is: an S3-compatible gateway, a proxy that carries a URL in its path, a WebDAV or Git server with such names.

### What it answers

A response the service writes goes out as written, error statuses included: its status, headers and body are the service's, so a 422 with no body or a plain-text one stays a 422, where a route's own would take the app's [JSON error shape](/docs/basics/errors/) as a 400. The pipeline adds `X-Request-Id`, and the default security headers where the service set none. What the mount answers itself takes the app's JSON error shape, as a route's errors do: the access check's refusals, the 501 and 400 above, a panic in the service (500 `Internal server error`, as in a handler), and an error the service returns instead of a response, which answers 500 with the error as its source, seen by the app's `m.map_error` mappings and recorded in the log, never sent. An error that comes from the body's limit or the server's read timeout answers 413 or 408, as the body extractors do. A Navree `AppRouter` mounted as the service answers its own `AppError`s through the app's error handling, as a route does.

The service reaches the app's providers through the `AppContext` in each request's extensions, as `entries` does above.

### Checked at boot

A mount fails the boot, with the app's other route problems, when:

- it has no access declaration, or one the app can't check (`.public()` with another declaration, a declaration that needs a user without a `dyn Authenticator`, roles, permissions or an ability without a `dyn RouteAuthorizer`): the route rule's texts, naming the mount, such as ``mount `/khata` in `LedgerModule` has no access declaration: add .public(), .authenticated(), .roles(..), .permissions(..) or .can(..) (deny by default)``;
- its prefix is not a plain path: it must start with `/` but not with `/_` (the framework's own paths), have no `{`, `}`, `*`, `..` or `//`, not end with `/`, and hold only segments a route path may hold;
- a route matches the prefix or a path below it, also through a `{param}` or `{*rest}` segment: an absolute route `GET /{workspace}/dashboard` reaches `/khata/dashboard`, and one at `/{*path}` reaches every prefix;
- another mount is at, under or above its prefix;
- `.methods(&[])` names no method.

`navree routes` lists each mount as one row, with the method `*` (or its methods), the path `/khata/{*rest}`, its access and its module, and ends with `N routes, M mounts`; `routes --json` marks it with `"mount": true`. `navree::http::route_table` returns the routes only.

## A tonic service

A tonic server built elsewhere, such as the `DealsServer` a crate generates from its `.proto` around its own implementation of the generated `Deals` trait, is served by `GrpcModule` with `TonicService`, behind the same call pipeline as a `#[grpc_service]` method:

```rust title="src/deals.rs"
use navree::grpc::{GrpcMethod, TonicService};
use navree::plugin::prelude::*;
use navree::prelude::*;

/// Serves the generated server behind the app's access checks: every
/// method needs a signed-in caller, except `GetDeal`.
pub struct KhataDealsModule;

impl Module for KhataDealsModule {
    fn register(&self, m: &mut ModuleBuilder) {
        m.tonic_service(
            TonicService::new(DealsServer::new(KhataDeals))
                .authenticated()
                .method(GrpcMethod::new("get_deal").public()),
        );
    }
}
```

- **Access**: the service default (`.public()`, `.authenticated()`, `.roles(..)`, `.permissions(..)`, `.can(action, subject)` and `.guard(..)`) covers every method without its own declaration; `.method(GrpcMethod::new(..))` gives one method its own, which replaces the default, guards included. A call to a method with neither is refused with `PERMISSION_DENIED`, and a path that names no method with `UNIMPLEMENTED`; neither reaches the server.
- **Method names**: name a method as the generated server trait spells it, `get_deal` for `GetDeal` and `get_http_status` for `GetHTTPStatus` (a leading `r#` is set aside). Another spelling fails the boot: ``gRPC method `GetDeal` of `crm.deals.v1.Deals` (module `KhataDealsModule`) is not a Rust method name: write `get_deal` (the name the generated server trait spells)``. A name in that form that matches no method of the server, a typo, can't be detected, so give the service default the strictest access and loosen it per method.
- **Checked at boot**: a service with no access declaration at all (a guard alone is none), a method of its own without one, a method declared twice, a method whose `can` names a field of the message (a wrapped server's messages aren't read before it runs: write the service with `#[grpc_service]` for a check on a record), and a service named like `GrpcModule`'s own health or reflection service while that one is on (set `grpc.health = false` to serve your own) each fail the boot, as do two services of one name.
- **Before the server reads a message** the call passes authentication, the access check, guards, the route authorizer and the deadline, so a refused call is answered without reading its messages. The server then runs in a unit of work, which commits when its response head is HTTP 200 with no error `grpc-status` and rolls back otherwise. A method that answers with a stream commits when its head is sent, and its messages run outside the unit of work. A head that carries an error `grpc-status` is answered with that status; one that is not HTTP 200 and carries no error `grpc-status` is answered with the gRPC status the gRPC specification gives its HTTP status, so a 503 stays `UNAVAILABLE`.
- **Streams**: once a call is let in, its request body is no longer held to the read pace of an upload, so a client or two-way stream may sit silent between messages. A unary call stays bounded by its deadline and the server's message limit.
- **Message limits**: `grpc.max_message_bytes` doesn't reach a server built elsewhere. Set its limits on the server before wrapping it (`DealsServer::new(..).max_decoding_message_size(..)`); tonic's own default decodes at most 4 MiB a message.

See [a server built elsewhere](/docs/microservices/grpc/#a-server-built-elsewhere) on the gRPC page for the whole example.
