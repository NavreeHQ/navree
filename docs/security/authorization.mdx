title: "Authorization"
description: "Roles, permissions and abilities, checked on routes, on loaded records and in SQL list filters, and shared with the front end."
---

[Authentication](/docs/security/authentication/) tells you who is calling; authorization decides what they may do. `navree-access` combines roles and permissions, stored in the database and managed at run time, with abilities: rules that allow or deny actions on subjects. You write the rules once, in Rust, and Navree uses them in four places:

- on routes, before the handler runs (`#[can(Update, Post, from = "id")]`);
- on a loaded record, in your services;
- in SQL, so a list returns exactly the rows the user may see;
- in the browser, where `@casl/ability` hides the buttons a user can't use. The API still checks every request.

## Setting up

<Badge feature="access" /> The `access` feature of the `navree` facade (part of the default `full` feature) brings `navree-access`. Add `AccessModule` to your app root with your abilities function and, optionally, a super-admin role:

```rust title="src/main.rs"
mod abilities;
mod modules;

use navree::prelude::*;

use crate::modules::posts::PostsModule;

fn main() -> Result<(), BoxError> {
    Navree::app()
        .module(ConfigModule::for_root(ConfigSources::defaults()))
        .module(CryptoModule::from_config())
        .module(HttpModule::from_config())
        .module(DatabaseModule::from_config())
        .module(AuthModule::from_config())
        .module(AccessModule::for_root(AccessOptions {
            abilities: abilities::define,
            super_admin_role: Some("admin".to_owned()),
        }))
        .module(PostsModule)
        .run()
}
```

`AccessModule` is global and needs `DatabaseModule`. It provides `AccessService` (manage roles and permissions) and `AbilityFactory` (each user's compiled abilities), and it registers navree-http's route authorizer, which checks `#[roles]`, `#[permissions]` and `#[can]`. Routes that declare those need the module: without it the app refuses to boot. A module that imports plain `AccessModule` reuses this configured instance.

The migration set `access` creates the tables `roles`, `permissions`, `role_permissions`, `user_roles`, `user_permissions` and `access_meta`. It runs after `auth`.

## Concepts

| Term | Meaning |
|---|---|
| Subject | A type of thing, named in PascalCase: `Post`, `Deal`. A model becomes a subject with `#[model(subject)]`. |
| Action | `read`, `create`, `update`, `delete`, `manage` (any action), or your own: `publish`, `move`. |
| Rule | Allows (`can`) or denies (`cannot`) an action on a subject, optionally only where conditions on the record hold and only for some fields. |
| Ability | One user's rules, in order. Navree builds it from your abilities function. |
| Role, permission | Stored in the database and managed at run time. A permission such as `posts.publish` becomes a rule. |

Abilities serialise to the JSON rule format of [CASL](https://casl.js.org), so the same rules mean the same thing in Rust and, through `@casl/ability`, in the browser.

### Subjects

Make each model you want to check a subject, and register it with `AccessModule::for_feature` in its module. A [navree-orm model](/docs/orm/workspaces-and-access/#access-control) is a subject through its `#[model(..)]` attribute:

```rust title="src/modules/posts/model.rs"
use navree::prelude::*;

/// Rules name it `Post`; permissions are `posts.<action>`.
#[derive(Model, Clone, Debug, Default, Serialize)]
#[model(table = "posts", timestamps, subject = "Post", permission_prefix = "posts")]
pub struct Post {
    pub id: Uuid,
    pub author_id: Uuid,
    pub title: String,
    pub body: String,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}
```

```rust title="src/modules/posts/mod.rs"
mod controller;
mod model;

use navree::prelude::*;

pub use controller::PostsController;
pub use model::Post;

#[module(
    imports = [AccessModule::for_feature::<Post>()],
    controllers = [PostsController],
)]
pub struct PostsModule;
```

`subject` alone names the subject after the struct and takes the table as the permission prefix; `policy = PostPolicy` adds the rules about it. `for_feature` maps the permission prefix to the subject, and lets routes load the model's records by route key (a UUID, an integer or a string): the ORM loads them in the request's unit of work, on navree-db's own transaction. A subject that isn't a model, such as `Report`, registers with `AccessModule::for_subject::<S>()` for its permission prefix alone. Users are a subject too: `navree::auth::User` is the subject `User`, with the prefix `users`. To check routes against users and to make `users.*` permissions apply, import `AccessModule::for_feature::<navree::auth::User>()`.

## Defining abilities

The abilities function receives the user's context and adds rules:

```rust title="src/abilities.rs"
use navree::prelude::*;

use crate::modules::posts::PUBLISH;

/// Who may do what with posts.
pub fn define(ctx: &AbilityCtx, rules: &mut Rules) {
    // Permissions from the user's roles: `posts.publish` → can publish Post.
    ctx.grant_permissions(rules);

    // Everyone, guests included, reads published posts.
    rules.can(READ, "Post").when(field("published").eq(true));

    let Some(user) = &ctx.user else {
        return;
    };
    let own = || field("author_id").eq(user.id);
    rules.can(READ, "Post").when(own());
    rules.can(CREATE, "Post");
    rules.can(UPDATE, "Post").fields(["title", "body"]).when(own());
    rules.can(PUBLISH, "Post").when(own());
    rules.can(DELETE, "Post").when(own());
    // Last, so it wins over the rules above.
    rules
        .cannot(DELETE, "Post")
        .when(field("locked").eq(true))
        .because("Locked posts are kept.");
}
```

`AbilityCtx` holds:

| Field | |
|---|---|
| `user` | `Some(AccessUser { id, roles })` for a signed-in user (`has_role`, `has_any_role`); `None` for guests |
| `permissions` | The user's permission strings, through their roles and granted directly, sorted |
| `team_id` | Inside a workspace request, `Some(workspace id)`, and `user.roles` and `permissions` describe the member's workspace role; `None` otherwise. See [How workspace roles reach access control](/docs/workspaces/members-and-roles/#how-workspace-roles-reach-access-control) |
| `organization_id` | Inside an [organization](/docs/workspaces/organizations/) request, or a workspace that belongs to one, `Some(organization id)`; `None` otherwise |
| `permission_subjects` | The permission prefix of every registered subject, for `grant_permissions` |

The function is a plain `fn(&AbilityCtx, &mut Rules)`: it can't capture state or query the database. Everything a rule decides on must be a role, a permission, or a column of the record being checked.

A custom action is a string, plus a marker type for route attributes and extractors:

```rust title="src/modules/posts/mod.rs"
/// `publish`, a custom action.
pub const PUBLISH: &str = "publish";

/// The `publish` action in `#[can]` and `Authorized<Post, Publish>`.
pub struct Publish;

impl ActionMarker for Publish {
    const NAME: &'static str = PUBLISH;
}
```

The built-in actions have constants (`READ`, `CREATE`, `UPDATE`, `DELETE`, `MANAGE`), marker types (`Read`, `Create`, `Update`, `Delete`, `Manage`) and `ALL`, the subject that matches every subject. All are in the prelude.

### The last matching rule wins

A check scans the rules from last to first, and the first rule that matches the action, the subject, the field and the record decides. No matching rule means no. So put `cannot` rules after the `can` rules they restrict: in the example, an author may delete their own posts, except locked ones.

| Rule part | Matches |
|---|---|
| `can`, `cannot` | Allows, or denies |
| Action | The action, or any action when the rule says `manage` |
| Subject | The subject, or any subject when the rule says `all` |
| `.when(..)` | Records whose columns satisfy the conditions |
| `.fields(..)` | Checks of those fields (see [Fields](#fields)) |
| `.because(..)` | Nothing: a reason that `access:explain` and the front end can show |

A check without a record is a **type-level** check: "may this user update some post?". A conditional `can` rule counts as a match, because some records may be allowed, and a conditional `cannot` rule is skipped. `ability.can(UPDATE, "Post", None)` is therefore true for an author, although they may update only their own posts.

`Rules::build` panics on an invalid rule (an unsupported operator, say), because rules are code. `Rules::try_build` returns the `RuleError` instead. In the module, an invalid rule makes every request of that user a 500, so test your abilities function (see [Testing](#testing)).

### Conditions

Conditions compare the record's columns with values:

```rust
rules.can(READ, "Invoice").when(
    field("status")
        .is_in(["sent", "paid"])
        .and(field("total_cents").gte(10_000)),
);
rules.can(READ, "Invoice").when(field("archived_at").eq(None::<&str>));
```

| Method | JSON operator |
|---|---|
| `eq`, `ne` | `$eq`, `$ne` |
| `lt`, `lte`, `gt`, `gte` | `$lt`, `$lte`, `$gt`, `$gte` |
| `is_in([..])`, `not_in([..])` | `$in`, `$nin` |

- Conditions combine with `.and(..)`, and several `.when(..)` calls on one rule combine the same way. There is no `$or`: write two rules.
- Only top-level columns work. Nested fields (`author.id`), `$exists`, `$regex` and the other MongoDB operators are rejected.
- Values can be booleans, integers, floats, strings, `Uuid`s, `DateTime<Utc>`s, `serde_json::Value`s and `Option`s, where `None` is `null`. Integers must be safe in JavaScript (at most 2^53 − 1); pass larger ones as strings.
- Types are never converted: `7` doesn't equal `"7"`. UUIDs compare as hyphenated lower-case strings, and timestamps as RFC 3339 UTC strings with microseconds, so text order is time order.
- `eq(None)` matches null. `ne(value)` matches null columns too, like SQL's `IS DISTINCT FROM`. `is_in` and `not_in` match null only through, or unless, a `null` in the list. Range operators never match null.

### Fields

`.fields([..])` limits a rule to some fields. In the example, an author may update the title and body of their own posts, and nothing else. A field-limited rule changes field checks only:

- `ability.can(UPDATE, "Post", Some(&post))` is true: the author may update the post;
- `ability.can_field(UPDATE, "Post", Some(&post), "author_id")` is false: they may not change its author.

A field-limited `cannot` rule never denies a whole-record check, only checks of its fields. `ability.permitted_fields(action, subject, record, &all_fields)` lists the allowed ones. In a handler, `Authorized::check_fields` turns the check into a 403:

```rust
post.check_fields(&input.changed_fields())?;
```

```json
{"statusCode": 403, "message": "You may not change these fields: author_id.", "error": "Forbidden", "code": "forbidden_fields"}
```

## Roles and permissions

### Permission strings

A permission is a string `<prefix>.<action>`. `ctx.grant_permissions(rules)` adds one unconditional `can` rule for each permission the user has:

| Permission | Rule |
|---|---|
| `posts.publish` | `can publish Post` (when a subject has the prefix `posts`) |
| `posts.*` | `can manage Post`: every action |
| `audit.read` | `can read audit`: a prefix no subject claims stands for itself |

The last row is how framework permissions work: the [audit log](/docs/security/audit-log/) route requires `audit.read`, and the role management routes require `roles.manage`. Grant them to a role like any other permission.

Without an abilities function, `AccessOptions::default()` uses `default_abilities`, which grants the user's permissions and nothing else.

A permission has at most 128 characters: ASCII letters, digits, `_`, `-`, `.`, `:` and `*`, starting with a letter or a digit, with a non-empty prefix and action. A role name has at most 64 of the same characters, without `*`.

### Describing permissions

A module, a plugin's among them, describes the permissions it uses, so the app and its tools can say what each one lets someone do:

```rust
use navree::plugin::Permission;
use navree::plugin::prelude::*;

m.permissions(&[
    Permission::new("announcements.read", "Read the workspace's announcements"),
    Permission::new("announcements.publish", "Publish an announcement to the workspace"),
]);
```

Describing a permission grants it to nobody. `m.permissions` describes, `#[permissions(..)]` on a route (`.permissions(&[..])` on a `RouteDef`) requires, as [Checking routes](#checking-routes) shows, and a person holds one only when the app grants it: a workspace role's list under `workspace.roles` in the app's configuration, or a role of navree-access (`access:grant editor announcements.publish`). Until then a [sidebar link](/docs/ui/app-shell/#links-other-modules-add) that asks for it, or a [Helm link or card](/docs/tools/helm/#links-and-cards-from-other-modules) whose check stands for it, is drawn only for the roles that already hold every permission ([below](#who-holds-the-permissions-plugins-describe)).

`navree::contracts::permission_catalog(ctx)` lists every permission the app's modules describe, with the module that described it, in module order:

```rust
for (module, permission) in navree::contracts::permission_catalog(&ctx) {
    println!("{} ({}): {}", permission.name, module.name, permission.description);
}
```

A name is two or more lower-case words joined by `.`, each a letter followed by up to 63 letters, digits or `_` (`announcements.publish`, `announcements.notice_board.publish`). A plugin that is not one of the framework's own packages describes only permissions that start with its namespace and `.`. Every subject its modules register takes a permission prefix inside its namespace (the namespace itself, or starting with it and `.`), whatever crate the subject's type is in, and so does a subject whose type is of its crate, whichever module registers it. Its namespace may not be the first word of a permission that another module describes, of the permission prefix of a subject another module registers, or of a permission or a subject that a route or another handler of another module declares and that is not the plugin's own (a plugin in the namespace `deals` next to the app's subject with the prefix `deals`, or next to the app's permission `deals.export`, stops the boot). A subject its modules register is named under its namespace too. [Subjects a plugin registers](#subjects-a-plugin-registers) and [A namespace the app already uses](#a-namespace-the-app-already-uses) have the texts. A name two modules describe is a warning, or a boot error when one of the two is such a plugin.

The name, namespace and prefix checks and the check of a name two modules describe run in `AccessModule` at boot. Without `AccessModule`, nothing checks them and nothing reads the descriptions, but roles still hold what `workspace.roles.{role}.permissions` lists, and no route can require a permission.

#### Who holds the permissions plugins describe

The roles that already hold every permission hold a plugin's too, from the moment it is installed:

- a workspace's `owner` (`all.*`), in that workspace;
- an organization's `owner`, in each of its workspaces: with organizations on, it enters each of them as its `owner`;
- an organization role the app maps to the workspace role `owner` (`workspace_role = "owner"` under `workspace.organizations.roles`), in each workspace of the organization its members reach;
- the app's super-admin role;
- any role the app grants `all.*`, in `workspace.roles` or with navree-access;
- a role the app's abilities function gives `manage` on `all` (`rules.can(MANAGE, ALL)`), app-wide.

A role granted one action on `all` holds that action of every plugin: `all.read` holds `announcements.read`. A role that already holds a permission under a plugin's namespace in your database or in `workspace.roles` from before the plugin was installed (`reports.view` before a plugin whose namespace is `reports`, say) holds the plugin's permission at once, and no boot check sees the stored grant. So a plugin does not guard a staff-only action with a permission that a workspace owner (in a SaaS app, a customer) holds.

### What a plugin may not grant

A plugin is code you add to your app. Within [what the boot checks inspect](#what-the-plugin-rules-are-and-are-not), the framework's registration APIs keep modules that act for a plugin that is not one of the framework's own packages from changing who may do what in your app without a line of yours. That includes a plain module in a second crate of the plugin, such as a `-core` crate beside it, whenever only modules acting for community plugins import it directly; if a module of your app imports that second crate's module directly too, it becomes yours, as [which modules act for a plugin](#which-modules-act-for-a-plugin) says. A module that acts for such a plugin stops the boot when it registers one of the things in the table below (a policy rule that only a real user brings out is left out instead). Your app registers the plugin's piece from a module of its own, and that line is the grant: the plugin ships the policy, the layer or the check, and your app decides to use it. The rules are not a sandbox, as the end of this section says. [Plugins](/docs/plugins/overview/) says what a plugin is and lists the other checks the boot makes.

A plugin may still describe its permissions, name its subjects and write rules on them, authorize the channels under its namespace, scope its own models under its namespace to workspaces, register scopes and hooks on its own models, and serve its own routes and mounts with layers of their own. The rules hold it to what is its own, which is what its namespace and its crate name.

| A plugin's module may not | What your app writes to use the plugin's piece |
|---|---|
| Write a policy rule on a subject that is not the plugin's, or on `all` ([policies](#policies-a-plugin-registers)) | `m.import(AccessModule::for_policy::<khata::InvoicePolicy>())` |
| Register a subject named outside its namespace ([subjects](#subjects-a-plugin-registers)) | `m.import(AccessModule::for_subject::<khata::Ledger>())` |
| Configure a module of another crate, as `for_root(..)` or `from_config()` does ([configured modules](#modules-a-plugin-configures)) | `AccessModule::for_root(..)` in your app's root, with the plugin importing `AccessModule` |
| Provide a permission check, the route authorizer, the authenticator, a sign-in strategy, the audit sink, a commit observer, the realtime backplane, or another provider that stands for the whole app ([what only the app provides](#what-only-the-app-provides)) | `m.multi(khata::permission_check())`, `m.strategy::<khata::LedgerStrategy>()`, `m.audit_sink_factory(khata::audit_sink())` |
| Add a layer that runs on every request ([rules for global layers](/docs/basics/middleware/#rules-for-global-layers)) | `m.http_layer(khata_timeout())` |
| Answer the app's errors: error pages or an error shell, or the mapping of an error type of another crate ([mapping your own errors](/docs/basics/errors/#mapping-your-own-errors)) | `m.error_pages(khata::pages())`, `m.map_error::<tower::timeout::error::Elapsed>(khata::timed_out)` |
| Decide who works as staff in the admin panel ([Helm](/docs/tools/helm/#workspaces)) | `m.helm_staff_workspaces(khata::may_enter)` |
| Authorize a realtime channel outside its namespace ([channels](/docs/digging-deeper/broadcasting/#authorizing-channels)) | `m.channel("orders.{id}", notices::authorize)` |
| Scope a subject that is not a model of its crate named under its namespace to workspaces ([data isolation](/docs/workspaces/isolation/#records-checked-by-route)) | `m.workspace_scoped::<notices::Notice>()` |
| Register a global scope on a model of another crate ([global scopes](/docs/orm/scopes-and-soft-deletes/#global-scopes)) | `m.global_scope::<Deal>("open", khata::open::<Deal>)` |
| Hook a model of another crate ([observers](/docs/orm/events-and-observers/#observers)) | `m.on_model::<Deal, _>(ModelEvent::Saving, khata::stamp::<Deal>)` |
| Register a command with the name of one of the framework's commands ([built-in commands](/docs/digging-deeper/cli/#the-built-in-commands)) | Nothing: a module of your app may take the name |
| Export a provider type that another module also exports | Keep the helper private to the plugin's module, or register it under a name |

Each refusal names the plugin, most name the module, and most say what to do: register the piece from a module of your app, or remove the plugin or update it. The plugin's namespace has rules of its own too. Its permissions and the subjects its modules register are named under it, and every module that acts for the plugin keeps the UI extensions, the static files and the island scripts it contributes under it. A module of your app may contribute a UI extension under `app`, or under a namespace no plugin and no part of the framework keeps: under `ui`, `navree` or another word the framework keeps, the boot stops. [Shipping a component in a plugin](/docs/ui/your-own-components/#shipping-it-in-a-plugin-ui-extension-files) has the texts. A plugin cannot take a word the framework keeps either, the names of the framework's configuration sections and packages and the first words of the permissions its modules declare on routes, descriptions and constants (`automations`, say) among them, and it cannot take a word your app already uses: see [a namespace the app already uses](#a-namespace-the-app-already-uses).

#### Which modules act for a plugin

The rules apply to a module that acts for a plugin that is not one of the framework's own packages. A module does when:

- it names the plugin with `m.plugin(..)`;
- it is in the crate the plugin names, whether or not it names the plugin: the framework reads the type of the module that the app or an importing module passed, and the type the module's id names, and it reads a module passed as a reference or in a `Box` or a `Pin` as the type inside (`&'static Helper` is `Helper`), and a trait object as its trait (`&'static dyn Part` is `Part`, so it is a module of the crate of `Part`). When the crates of two plugins both hold the type, the plugin with the longer crate name is the one, and between two plugins of one crate it is the one whose module your app lists first;
- it is a generic module that only modules acting for plugins import directly, such as the module `AccessModule::for_policy::<P>()` makes for a plugin's policy. When a module of your app imports it directly too, it is yours;
- it is a plain module outside the framework's crates, with no generic arguments and naming no plugin, that only modules acting for plugins that are not the framework's own import directly, such as a module in a `-core` crate beside the plugin (when two such plugins import it, the first in import order). When a module of your app imports it directly too, it is yours.

Every other module is a module of your app. `navree plugins` lists, under each plugin, every module that acts for it, which is the place to look when a refusal names a module you did not expect. Whenever a refusal names a module that does not call `m.plugin(..)` for that plugin itself, it says why the module acts for the plugin in brackets after the module name:

```text wrap
plugin `navree-plugin-guard` provides `dyn navree_contracts::permissions::PermissionCheck` in `Helper` (a module of the plugin's crate `navree_plugin_guard`), which answers the app's permission checks; only a module of the app registers it: remove the plugin or update it to a version that leaves it to the app, and to use the plugin's, register it from a module of the app
```

For a generic module, or a plain module of a second crate that only the plugin's modules import, the brackets say `(only the plugin's modules import it)`.

#### Policies a plugin registers

A plugin's policy writes rules only on the plugin's own subjects: the names under its namespace, such as `announcements.Announcement`. A rule on another subject, or on `all`, is refused in two places.

At boot, the framework calls the policy as each kind of user it knows of: a guest, a signed-in user with no role, one user for each role of the app (the built-in workspace roles `owner`, `admin`, `member` and `viewer`, each role named under `workspace.roles` or `workspace.organizations.roles` in the configuration, and the super-admin role), and a user with no role who holds every permission the plugin describes. A rule on another subject in any of those answers stops the boot, naming the policy, the module and the subject:

```text wrap
plugin `navree-plugin-announcements` registers the policy `navree_plugin_announcements::Everyone` in `AccessPolicy<navree_plugin_announcements::Everyone>` (only the plugin's modules import it), which writes a rule on `Post`; a plugin's policy writes rules on its own subjects only: remove the plugin or update it to a version whose policy keeps to them, and to apply the policy to `Post`, register it from a module of the app (AccessModule::for_policy)
```

A rule on `all` gets the same text without its last clause, the one about applying the policy, since no subject is left to apply it to.

The boot cannot ask as every user. A role you create only in your database (`night-shift`, made with `access:role`) is one it does not know, and a policy can write a rule for it. So every ability build keeps only the rules of a plugin's policy on its own subjects, a guest's and a member's inside a workspace among them. The first rule left out for each policy and subject is logged at the target `navree::security`:

```text wrap
left out a rule of plugin `navree-plugin-announcements`'s policy `navree_plugin_announcements::NightShift` on `Post`, not one of its own subjects
```

Each rule the policy keeps names the policy and the plugin in its `reason`. When the rule gave no `.because(..)` words of its own, `GET /api/me/abilities` returns:

```json wrap
{"action": "read", "reason": "policy `navree_plugin_announcements::NoticePolicy` of plugin `navree-plugin-announcements`", "subject": "announcements.Announcement"}
```

When the rule gave `.because(..)` words of its own (such as a denial's explanation), those words stay first with `(policy `..` of plugin `..`)` beside them, for example `"archived notices are closed (policy `navree_plugin_announcements::NoticePolicy` of plugin `navree-plugin-announcements`)"`. [`access:explain`](#explaining-a-decision) prints the same words. To apply a plugin's policy to anything, import it from a module of your app: `m.import(AccessModule::for_policy::<navree_plugin_announcements::Everyone>())`. A policy that a module of your app registers is yours, whoever else registers it too, and none of this applies to it; when modules of two community plugins register one policy name and no module of the app does, the policy runs once and only the first plugin's own subjects apply. A plugin's own rules are its decision: your abilities function runs after its policies, so a `cannot` there overrides them.

#### Subjects a plugin registers

A plugin names its subjects under its namespace, as it names its permissions: `announcements.Announcement` with the permission prefix `announcements`, for the namespace `announcements`. The namespace alone is a name too, and any other name is outside it. A subject named `Announcement`, or `all`, stops the boot:

```text wrap
plugin `navree-plugin-announcements` registers the subject `Announcement` in `AccessSubject<navree_plugin_announcements::Announcement>` (only the plugin's modules import it), a name outside its namespace `announcements`; a plugin's subjects are named under its namespace: remove the plugin or update it to a version that names them under `announcements.`, and to register `Announcement`, register it from a module of the app
```

So no subject of a plugin shares a name with one of yours, or stands for everything.

Every subject a plugin's module registers also takes a permission prefix under the namespace (the namespace itself, or the namespace, `.` and more), whatever crate its type is in: a type of a `-core` crate beside the plugin, or a `Box` of its own type, included. So does a subject whose type is of the plugin's crate, whichever module registers it. A prefix outside the namespace would make the permissions your app grants under that prefix check the plugin's subject:

```text wrap
plugin `navree-plugin-crm` registers the subject `crm.Pipeline` with the permission prefix `deals`, outside its namespace `crm`; the app's permissions under `deals` would check the plugin's subject: remove the plugin or update it to a version that keeps its permission prefixes under `crm`
```

The rule runs the other way too: a module that does not act for the plugin may not register a subject whose outer type is outside the plugin's named crate under the plugin's namespace (a `Box<T>` of the plugin's type or a type in a `-core` crate beside the plugin has an outer type in `alloc` or in that `-core` crate, so under the plugin's namespace a module acting for the plugin must register it).

```text wrap
plugin `navree-plugin-announcements` uses the namespace `announcements`, under which `AccessSubject<crm::Ledger>` registers the subject `announcements.Ledger`; the names under a plugin's namespace are its subjects: remove the plugin, or name the app's subject outside `announcements.`
```

A subject of a plugin that keeps a name outside its namespace is one only your app registers, from a module of its own, and its permission prefix stays under the namespace: `m.import(AccessModule::for_subject::<navree_plugin_announcements::Reports>())`.

#### Modules a plugin configures

A module that acts for a plugin may import a module of another crate by type, but not a configured one: another crate's `for_root(..)` or `from_config()`. A configured module decides how a crate behaves for the whole app, so your app configures it, once, in its root, and the plugin imports it plainly (`m.import(AccessModule)`), which reuses the instance your root configured, as [Setting up](#setting-up) says. A plugin may configure a module of its own crate.

```text wrap
plugin `navree-plugin-roster` configures the module `AccessModule` in `RosterModule` (for_root or from_config); only a module of the app configures a module of another crate: remove the plugin or update it to a version that imports `AccessModule` without configuring it, and configure `AccessModule` in a module of the app
```

When your app configures the module too, in either order, this is the only refusal. When only the plugin configures it, the configured module acts for the plugin, and the providers it registers are not refused again.

#### What only the app provides

A plugin's module may not register a provider that decides who may do what in the app, that sets the options of a module that does, or that stands for the whole app in another way: its audit trail, its commits, its broadcasts, its clock. It may not register one as a value, a factory or a multi-binding, named or not, exported or not. Each refusal names the provider, the module and what the provider does:

```text wrap
plugin `navree-plugin-guard` provides `dyn navree_contracts::permissions::PermissionCheck` in `Provides`, which answers the app's permission checks; only a module of the app registers it: remove the plugin or update it to a version that leaves it to the app, and to use the plugin's, register it from a module of the app
```

| Provider | The refusal says it |
|---|---|
| `dyn PermissionCheck` | answers the app's permission checks |
| `dyn RouteAuthorizer` | decides who may open the app's routes |
| `dyn Authenticator` | decides who a request is signed in as |
| `dyn Strategy` | signs requests in |
| `dyn WorkspaceGate` | decides who enters the app's workspaces |
| `dyn AuditSink` | receives the app's audit records |
| `AbilityFactory` | builds every user's abilities |
| `AccessOptions` | sets the options of the app's access rules |
| `AuthOptions` | sets the options of the app's sign-in |
| `HelmOptions` | sets the options of the app's admin panel |
| `WorkspaceConfig` | sets the options of the app's workspaces |
| `Shell` | is the app's shell |
| `dyn NativeShellPart` | says where the app's native clients sign in |
| `dyn Clock` | sets the time the app's sessions, signed links and invitations expire by |
| `dyn ChangeObserver` | sees, and can change, every write the app commits |
| `dyn MongoChangeObserver` | sees, and can change, every MongoDB write the app commits |
| `dyn Backplane` | carries every broadcast of the app's channels between its processes |
| `ModelEventFake` | silences the listeners of every model of the app |

A plugin ships the provider as a function, and your app registers it: `m.multi(khata::permission_check())` for a permission check, `m.strategy::<khata::LedgerStrategy>()` for a strategy. For an audit sink, `navree::audit::ModuleBuilderAuditExt` lets a module of your app add further sinks (`m.audit_sink::<OwnSink>()` for a sink built in that module, `m.audit_sink_value(..)` for a built value, or `m.audit_sink_factory(khata::audit_sink())` for a sink built by a plugin): with `AuditModule`, every audit entry and committed `Uow` model change record reaches both `AuditModule`'s log and each added sink, and without `AuditModule`, the added sinks form the app's `dyn AuditSink` and receive every `AuditSink::record` entry; the refusal of a plugin's own sink registration ends with `and to use the plugin's sink, add it from a module of the app (m.audit_sink, m.audit_sink_value or m.audit_sink_factory)`. A plugin can still register a sign-in policy with `m.sign_in_policy::<P>()`, because a policy can only refuse a sign-in, and a backplane as a driver with `m.backplane(..)`, which selects it by name with `realtime.backplane` and is not a provider.

#### A namespace the app already uses

A plugin's policies write the rules on every name under its namespace, so they would decide who may use anything of your app that is named there. The boot refuses a plugin whose namespace is the first word of a name your app uses:

- a permission that a module of your app describes;
- a permission that a route of your app, or another handler or item of it, requires and the plugin does not describe, or a subject that it checks and that is not registered as the plugin's (a permission prefix no subject registers stands for itself);
- the permission prefix of a subject that a module of your app registers, and `all`.

Each refusal names the plugin, the namespace and what it meets:

```text wrap
plugin `navree-plugin-khata` uses the namespace `khata`, the first word of the permission `khata.export` that `Khata` describes; a plugin's policies decide the names under its namespace, so they would decide who may use it: remove the plugin, or name it under another word in the app
```

```text wrap
plugin `navree-plugin-reports` uses the namespace `reports`, the first word of the permission `reports.view` that the route `GET /reports/sales` of `PostsModule` requires, and the plugin describes no permission of that name; a plugin's policies decide the names under its namespace, so they would decide who may use it: require a permission the plugin describes, or name the app's permission under another word
```

```text wrap
plugin `navree-plugin-ledger` uses the namespace `ledger`, the first word of the subject `ledger` that the route `GET /ledger/summary` of `LedgerModule` checks, and the plugin registers no subject of that name; a plugin's policies decide the names under its namespace, so they would decide who may use it: check a subject the plugin registers, or name the app's subject under another word
```

```text wrap
plugin `navree-plugin-deals` uses the namespace `deals`, which is the permission prefix of `Deal` (`AccessSubject<crm::Deal>`); a plugin's policies decide the names under its namespace: remove the plugin, or give the app's subject a permission prefix under another word
```

The boot reads what every handler and access-guarded value of your app declares, once the handlers are built, at the end of the boot: routes and mounts (read from `HttpServer` with its own options when `HttpModule` is in the app; if `HttpServer` cannot be resolved, the boot stops), the message and event handlers of navree-micro, gRPC methods (a wrapped tonic server's default and methods too), MCP tools, resources and prompts, GraphQL root fields, and the permissions and subjects carried as values on agent tools (including component tools of an assistant's generative UI catalogue, `navree-ai`), sidebar links (`navree-ui`), Helm links, cards and custom pages (`navree-helm`), settings groups (`navree-settings`), and sheet imports and exports (`navree-sheets`). Each kind is read where its module is in the app, so a message service with no HTTP module is read as well, and the refusal names the handler or item as it names a route: the mount `/khata` of `LedgerModule`, the message pattern `sales.month` of `SalesModule`, the agent tool `assistant.lookup` of `SalesModule`, or the Helm card `revenue` of `SalesModule`. An item of a module that acts for the plugin is the plugin's own and is not refused, and a plugin may describe and require what it likes under its own namespace. A route of your own, or any other handler or item, may use the plugin's own names on purpose: it may require a permission the plugin describes (`#[permissions("announcements.read")]` beside the announcements plugin) and check a subject that is registered as the plugin's (`#[can(Read, Announcement)]`), and the app boots. A subject is the plugin's when a module acting for the plugin registers it, or when its outer type is of the plugin's named crate and your app registers it. Any other name under the namespace is your app's own name under a word the plugin's policies decide, so the boot refuses it, and the text gives both ways out: use a name the plugin describes or registers, or name yours under another word. A realtime channel under a plugin's namespace has a rule of its own: see [Authorizing channels](/docs/digging-deeper/broadcasting/#authorizing-channels).

#### What the plugin rules are, and are not

The rules a plugin is held to, these and the others the boot checks, hold it to what it declares: what its modules register and what they name. They are not a sandbox. A crate linked into the app runs with the app's rights: its code can read the app's configuration, query its database and call other services as the app's own code can, whatever it registers. Add a plugin as you would add any other dependency, from a source you trust.

Whether a plugin is one of the framework's own packages, which these rules leave alone, is decided by names. The plugin's name is that of one of the framework's own packages, the crate it names is that package's crate, its version is the framework's, and the type of every one of its modules, read through a reference, a `Box`, a `Pin` or a trait object, is in that crate. The framework reads each module's type from the module itself when your app or an importing module passes it, so a crate cannot give a module another type. These are names, and a package can take them: one whose library is named like one of Navree's crates, at the framework's version, meets them all. The package's name and source matter as they do for any dependency.

What the rules leave alone:

- A plugin's rules on its own subjects are its decision. Your abilities function can override them.
- Code a plugin runs, its handlers, jobs and migrations, can call `AccessService` and the database as any code can, and what it writes, such as roles and grants, stays in your database when you take the plugin out. Its own routes declare their own access, and may be public.
- A plain module outside the framework's crates that names no plugin and is in no plugin's crate acts for a community plugin when only modules acting for community plugins import it directly; as soon as a module of your app imports it directly too (or adds it to the app), it is yours with everything it registers, just as a generic module is.
- The boot reads the permissions that modules describe, the permissions and subjects that your app's handlers declare (routes, mounts, message and event handlers, gRPC methods and services, MCP items and GraphQL root fields), and the permissions and subjects carried as values on agent tools (including generative UI component tools), sidebar links, Helm links, cards and custom pages, settings groups, and sheet imports and exports, against a plugin's namespace. It does not read a permission or subject checked in code (`permitted`, `ability.can`, a handler's own check, such as Helm's per-resource checks), action `.can(..)` checks on a generative UI `Catalog` (surface `.can(..)` checks registered through `m.assistant` are read as agent tools; a standalone `Catalog` not passed to `m.assistant` and action `.can(..)` checks are not), or a permission named in your configuration (such as `auth.impersonation.permission`).
- A plugin that goes around the registration APIs on purpose, with code of its own, is not stopped by a boot check.

### Managing roles in code

`AccessService` manages roles. Writes take the unit of work to run in: a request's `Uow`, or one from `db.uow(..)` in jobs, seeders and commands.

```rust
use navree::access::AccessService;
use navree::db::Db;

let uow = db.uow(None, None).await;
// `create_role` refuses a name that exists (`AccessError::RoleExists`), so a
// seeder that can run again asks first. `role` reads committed rows.
if access.role("editor").await?.is_none() {
    access.create_role(&uow, "editor", Some("Publishes anyone's posts")).await?;
}
access.grant(&uow, "editor", "posts.publish").await?;
access.grant(&uow, "editor", "posts.update").await?;
access.assign_role(&uow, editor_id, "editor").await?;
uow.commit().await?;
```

| Method | |
|---|---|
| `create_role(&uow, name, description)`, `delete_role(&uow, name)` | Deleting a role removes its grants and assignments |
| `grant(&uow, role, permission)`, `revoke(&uow, role, permission)` | Change one permission of a role |
| `sync_role_permissions(&uow, role, permissions)` | Make the role's permissions exactly these |
| `assign_role(&uow, user, role)`, `remove_role(&uow, user, role)` | Change one role of a user |
| `sync_user_roles(&uow, user, roles)` | Make the user's roles exactly these |
| `grant_to_user(&uow, user, permission)`, `revoke_from_user(&uow, user, permission)` | Permissions given to a user directly |
| `role(name)`, `roles()`, `roles_of(user)`, `permissions_of(user)` | Read roles and permissions (`RoleInfo` has `id`, `name`, `description`, `permissions`, `created_at`) |
| `explain(user, action, subject, id)` | The rule that decides a check; see [Explaining a decision](#explaining-a-decision) |

The `grant`, `revoke`, `assign_role`, `remove_role`, `grant_to_user` and `revoke_from_user` methods return `false` when there was nothing to change, and do nothing else, and the two `sync_` methods do nothing when the set is already right, so a seeder that uses them can run again safely. `create_role` is the exception: it answers `AccessError::RoleExists` for a role that is already there, and no method creates a role only when it is missing. Ask with `role(name)` first, as in the example (in a unit of work from `db.uow` it does not see a role that the same unit of work created and has not committed), or match on `RoleExists` and go on. The CRM's `crm-roles` seeder creates the missing roles and calls `sync_role_permissions` for each.

Each change that does something:

- bumps the **access version** in the same transaction, so every instance rebuilds its cached abilities on the next request (see [Caching](#caching-and-consistency));
- writes an `access.*` entry to the [audit log](/docs/security/audit-log/), when the app has one, once it commits;
- ends the real-time subscriptions of the users it affects (the user whose roles or direct permissions changed, or the members of a role that lost permissions), so they must authorize their private channels again.

## A super-admin role

With `super_admin_role: Some("admin".to_owned())`, users with the `admin` role get one more rule, `can manage all`, after the rules your function defines. Being last, it beats every `cannot`. They also pass every `#[roles(..)]` check.

The role is an ordinary role: create it and assign it like any other. The CRM makes `admin` its super-admin role, and its abilities function adds nothing for admins, so an admin's rules are only:

```json
[{"action": "manage", "subject": "all", "reason": "super admin"}]
```

## Checking routes

Route attributes declare who may call a route; [Access control on routes](/docs/basics/access-control/) covers them in full. Every declaration except `#[public]` requires a signed-in user first.

| Attribute | Passes when |
|---|---|
| `#[roles("admin", "editor")]` | The user has any of the roles (the super-admin role always passes) |
| `#[permissions("posts.export")]` | An unconditional rule grants the permission's action on its subject. Conditional rules don't count |
| `#[can(Create, Post)]` | The type-level check passes: the user may create some posts |
| `#[can(Update, Post, from = "id")]` | The post whose id is the `id` path parameter exists and the rules allow updating it |

A refusal is `403 Forbidden`, and with an audit log in the app it is recorded as an `access.denied` security entry naming the check, the route and the user:

```json wrap
{
  "kind": "security",
  "action": "access.denied",
  "actor_id": "01a17751-238d-7310-b5df-b4b75c48def9",
  "subject_type": "Post",
  "subject_id": "01a17751-2395-715f-931d-d822324d98fd",
  "metadata": {"action": "delete", "check": "can", "method": "DELETE", "route": "/api/v1/posts/{id}", "subject": "Post"}
}
```

A 403 that a handler returns itself (from `check_fields`, say) is recorded too, with `"check": "handler"`. Hand-written routes use `.roles(&[..])`, `.permissions(&[..])` and `.can("update", "Post", Some("id"))` on `RouteDef`.

Guests never pass `#[can]`, even when a rule allows guests: make such a route `#[public]` and filter what it returns with [`Accessible`](#list-filters-in-sql), as the posts index below does.

## Record checks

### Authorized

With `from = "id"`, the route authorizer loads the record before the handler runs and hands it over as `Authorized<M, A>`:

```rust title="src/modules/posts/controller.rs"
use navree::orm::access::AccessibleQuery;
use navree::prelude::*;

use super::model::Post;
use super::{Publish, UpdatePost};

#[injectable]
pub struct PostsController;

#[controller("/posts", version = "1")]
impl PostsController {
    /// Only the posts the caller may read.
    #[get("/")]
    #[public]
    async fn index(
        &self,
        uow: Uow,
        scope: Accessible<Post, Read>,
        page: PageQuery,
    ) -> Result<Page<Record<Post>>> {
        Ok(scope.query().latest().paginate(&uow, page).await?)
    }

    /// 404 when there is no such post, 403 when the rules say no.
    #[get("/{id}")]
    #[can(Read, Post, from = "id")]
    async fn show(&self, post: Authorized<Post, Read>) -> Json<Record<Post>> {
        Json(post.into_inner())
    }

    #[patch("/{id}")]
    #[can(Update, Post, from = "id")]
    async fn update(
        &self,
        post: Authorized<Post, Update>,
        Valid(Json(input)): Valid<Json<UpdatePost>>,
    ) -> Result<Json<Record<Post>>> {
        // 403 "You may not change these fields: author_id." when the
        // rule is limited to title and body.
        post.check_fields(&input.changed_fields())?;
        // ...
        Ok(Json(post.into_inner()))
    }

    #[post("/{id}/publish")]
    #[can(Publish, Post, from = "id")]
    async fn publish(&self, post: Authorized<Post, Publish>) -> Result<Json<Record<Post>>> {
        // ...
        Ok(Json(post.into_inner()))
    }
}
```

For a `from` route, the authorizer:

1. runs the type-level check;
2. loads the record by its primary key in the request's unit of work, with `SELECT ... FOR UPDATE` on PostgreSQL and MySQL (on SQLite the write transaction already serialises writers);
3. answers 404 when there is no such record, when it is soft-deleted, or when the id can't be one (not a UUID for a UUID key, say);
4. checks the rules against the record, and answers 403 when they say no;
5. keeps the record for the handler.

For a model, `Authorized<M, A>` dereferences to its `Record<M>` (which dereferences to the model, so `post.title` works), and `into_inner()` gives the `Record<M>`; `.into_inner()` on that gives the model. It also has `model()`, `record()` (the JSON the conditions saw), `ability()` and `check_fields(..)`. The extractor must match the route: `Authorized<Post, Update>` on a route without `#[can(Update, Post, from = ..)]` is a 500 that says so. So is a `from` route for a subject registered without `for_feature`.

Conditions see the record as JSON with one member per column, named like the column. UUIDs are hyphenated lower-case strings, timestamps RFC 3339 UTC strings with microseconds, and dates `YYYY-MM-DD`. The same JSON comes from `navree::orm::access::record_json(&record)` for an ORM model (`ability.authorize(Update, &record)` checks one directly), `navree::access::row_json(&row)` for a navree-db record.

<Callout type="warning" title="Soft-deleted records">

A soft-deleted record (its `deleted_at` is set) is a 404 before any rule is checked, so a user the rules refuse can't tell it was there. Lists, and records whose parent is soft-deleted, are the app's to filter.

</Callout>

### Checks in services

Some decisions depend on the input as well as the record. The `Abilities` extractor gives the user's compiled rules (`Arc<Ability>`), and `Authorized::ability()` the same. For a model's record, `AbilityExt` (in `navree::orm::access`) checks an action against it:

```rust
use navree::access::Ability;
use navree::orm::access::AbilityExt;

pub fn ensure_can_publish(ability: &Ability, post: &Record<Post>) -> Result<()> {
    // `Publish` is the action marker defined above.
    if !ability.allows(Publish, post) {
        return Err(AppError::forbidden().with_detail("You may not publish this post."));
    }
    Ok(())
}
```

`ability.authorize(Publish, post)?` is the same check with the 403 built in, and `ability.allows_action("publish", post)` takes the action by name. For a record that isn't a model, `ability.can(PUBLISH, "Post", Some(&row_json(&row)))` checks the JSON the conditions see.

The CRM's deal service does this when a `PATCH` changes a deal's stage, which needs `move` as well as `update`:

```rust title="crm/api/crates/crm-deals/src/service.rs"
let moving = input.stage.filter(|stage| *stage != deal.stage);
if moving.is_some() && !deal.ability().can(Move::NAME, DEAL, Some(deal.record())) {
    return Err(AppError::forbidden().with_detail("You may not move this deal"));
}
```

`CurrentAccess` gives more: the user's `roles`, `permissions`, access `version`, whether they are the `super_admin`, and the `ability`. Both extractors compute the user's access once per request, shared with the route authorizer.

Outside a request, such as in a job or a channel authorizer, ask the `AbilityFactory` for a user's permission, checked the way `#[permissions]` checks it:

```rust
let factory = ctx.get::<AbilityFactory>().await?;
if factory.has_permission(&principal, "reports.export").await? {
    // ...
}
```

Code that shouldn't depend on navree-access asks `navree::contracts::permitted(&ctx, &principal, "reports.export", workspace)` instead. `AccessModule` answers it with the user's global roles and permissions, and [`WorkspaceModule`](/docs/workspaces/members-and-roles/#checks-outside-a-request) with their role in the workspace, when one is given. [Operations](/docs/digging-deeper/batches-and-operations/#who-may-see-an-operation) decide who sees them this way.

## List filters in SQL

A list endpoint must return only the rows the user may see, and it must agree with the record check, or users see records they then can't open. `Accessible<E, A>` compiles the same rules into one SQL `CASE` expression, so a row is listed exactly when `can(A, E, row)` would be true. For an ORM model, `AccessibleQuery` (in `navree::orm::access`) applies it to the model's queries: `scope.query()` starts a query of the rows the user may see, `scope.apply(query)` narrows one you have. The CRM lists deals this way:

```rust title="crm/api/crates/crm-deals/src/service.rs"
pub async fn list(
    &self,
    uow: &Uow,
    scope: Accessible<Deal, Read>,
    list: &ListQuery,
) -> Result<Page<DealResource>> {
    let page = scope
        .apply(Deal::query())
        .list(list, &DealList::SPEC)?
        .with_all(DealResource::EMBEDS)
        .paginate(uow, list.page_request(&DealList::SPEC))
        .await?;
    Ok(page.map(|deal| deal.to_resource::<DealResource>()))
}
```

The `CASE` lists the conditional rules from last to first, so its first `WHEN` that holds is the rule a record check would pick. For a CRM sales rep deleting deals, the filter is:

```sql
CASE WHEN ("deals"."stage" IN ('won', 'lost')) THEN FALSE
     WHEN ("deals"."owner_id" = '01920000-0000-7000-8000-000000000003') THEN TRUE
     ELSE FALSE END
```

An unconditional rule turns into the `ELSE` (a rep reads every deal, so their read filter is `TRUE`), and an action with no rules into `FALSE`. The filter never yields `NULL`, so it is safe to negate.

- Columns are qualified with the model's table, and values are bound with the column's type, so UUID and timestamp columns compare like the stored values, and numbers are bound as the column's integer or float whatever the rule's JSON says (`3` or `3.5`; `amount > 3.5` on an integer column is `amount > 3`). A rule field that isn't a column is SQL `NULL`, as it is `null` in a record check.
- The filter is written for the query's database: `ne` is null-safe on each (`IS DISTINCT FROM` on PostgreSQL, `NOT (a <=> b)` on MySQL, `IS NOT` on SQLite). The tests check that record checks and list filters agree on random rule sets on all three. String comparisons agree with record checks under binary collation: SQLite's default, `COLLATE "C"` on PostgreSQL, a binary collation on MySQL.
- For queries the ORM doesn't build (a navree-db record, a report written in SQL), `scope.sql_filter(&columns)` compiles the filter with a column mapping (`TypedColumns` names the table and each column's type, or implement `SqlColumns` for joins or renamed columns) and `.to_statement(backend)` writes it as a portable fragment, SQL with `?` placeholders and its values. `ability.sql_filter_with(action, subject, &columns)` does the same from an `Ability`.

```rust
use navree::access::{Accessible, Read, TypedColumns};
use navree::db::record::Filter;
use navree::db::{Executor, Kind, Record};

let columns = TypedColumns::new("deals")
    .with("owner_id", Kind::Uuid)
    .with("stage", Kind::String);
let (sql, values) = scope.sql_filter(&columns).to_statement(uow.backend()).into_parts();
let deals = DealRow::select().filter(Filter::all().raw(sql, values)).all(&uow).await?;
```

## Abilities in the front end

`GET /api/me/abilities` returns the signed-in user's rules in CASL's JSON format, which `createMongoAbility` in `@casl/ability` accepts as is. For the author in the posts example:

```http wrap
HTTP/1.1 200 OK
Content-Type: application/json
ETag: "01a17751-238d-7310-b5df-b4b75c48def9-1-8cbacc2d30295bd4"
Cache-Control: private, no-cache

[
  {"action": "read", "conditions": {"published": true}, "subject": "Post"},
  {"action": "read", "conditions": {"author_id": "01a17751-238d-7310-b5df-b4b75c48def9"}, "subject": "Post"},
  {"action": "create", "subject": "Post"},
  {"action": "update", "conditions": {"author_id": "01a17751-238d-7310-b5df-b4b75c48def9"}, "fields": ["title", "body"], "subject": "Post"},
  {"action": "publish", "conditions": {"author_id": "01a17751-238d-7310-b5df-b4b75c48def9"}, "subject": "Post"},
  {"action": "delete", "conditions": {"author_id": "01a17751-238d-7310-b5df-b4b75c48def9"}, "subject": "Post"},
  {"action": "delete", "conditions": {"locked": true}, "inverted": true, "reason": "Locked posts are kept.", "subject": "Post"}
]
```

The ETag is `"<user>-<access version>-<hash of the rules>"`: it changes with any role or permission change, and when a deploy changes the rules. Send it back in `If-None-Match` to get a `304 Not Modified`.

The CRM's front end builds its ability from that array. Every API resource carries its subject type in `__type` (`"Deal"`, `"User"`), so CASL can check API records directly:

```ts title="crm/web/src/lib/casl/ability.ts"
export function createAppAbility(rules: readonly CaslRule[] = []): AppAbility {
  return createMongoAbility<AppAbility>(rules as RawRuleOf<AppAbility>[], {
    // `__type` is typed `string` for some resources in the OpenAPI document; the API always sends the subject name.
    detectSubjectType: (o) => (typeof o === "string" ? o : o.__type) as ExtractSubjectType<AppSubjects>,
  });
}
```

```tsx title="crm/web/src/app/(app)/companies/[id]/company-detail.tsx"
<Can I="update" this={c}>
  <CompanyFormDialog
    company={c}
    trigger={
      <Button variant="outline">
        <PencilIcon data-icon="inline-start" />
        Edit
      </Button>
    }
  />
</Can>
```

The browser's checks only decide what to show. In a few corners `@casl/ability` answers differently from Navree, which can only affect the UI because the API checks again:

- a column the record lacks is `null` to Navree and `undefined` to CASL, which `$eq: null` doesn't match;
- range operators never match `null` or a value of another type in Navree, where JavaScript would compare them;
- strings order by code point in Navree, by UTF-16 code unit in JavaScript.

`Ability::to_casl_json()` and `Ability::from_casl_json(..)` convert rules yourself. Parsing accepts only the operators listed under [Conditions](#conditions).

## Tokens with limited abilities

A [custom authentication strategy](/docs/security/authentication/#writing-your-own-strategy) can limit what a request may do by setting `token_abilities` on the `Principal` it returns: a list of permission strings such as `["deals.read"]`. The user's ability is then narrowed to the rules that grant those permissions; `"*"` keeps everything, and a malformed entry grants nothing. Rules keep their order and conditions, so a token never grants more than its user has. Access tokens from the JWT strategy are not limited.

## Caching and consistency

Each request reads the access version (one small query). A user's roles, permissions and compiled rules are cached in memory under their id and that version, for up to 10,000 users, and dropped after 10 minutes without use. Every change made through `AccessService` bumps the version in the same transaction as the change, so once it commits every instance rebuilds the abilities on the next request. No cache messages pass between instances.

Rows changed in the database directly don't bump the version, so the cache won't notice them. Go through `AccessService`, or call `AbilityFactory::clear_cache()`, which clears only the current process. A change to the abilities function takes effect when the app restarts.

`access:explain` and `AccessService::explain` show the rule that decides a check, with its number in definition order:

## The CRM's abilities

The reference CRM has three roles: `admin` (the super-admin role), `manager` and `rep`. Managers hold six permissions (`companies.manage`, `contacts.manage`, `contacts.export`, `deals.manage`, `activities.manage` and `users.read`); reps and admins hold none. Everything else is in its abilities function:

```rust title="crm/api/crates/crm-core/src/abilities.rs"
pub fn define(ctx: &AbilityCtx, rules: &mut Rules) {
    ctx.grant_permissions(rules);
    let Some(user) = &ctx.user else {
        return;
    };
    // The super-admin rule (`manage all`) comes from the access module.
    if user.has_role(ADMIN) || !user.has_any_role(&[MANAGER, REP]) {
        return;
    }
    for subject in [COMPANY, CONTACT, DEAL, ACTIVITY, USER] {
        rules.can(READ, subject);
    }
    for subject in [COMPANY, CONTACT, DEAL, ACTIVITY] {
        rules.can(CREATE, subject);
    }
    let own = || field("owner_id").eq(user.id);
    for subject in [COMPANY, CONTACT, ACTIVITY] {
        rules.can(UPDATE, subject).when(own());
        rules.can(DELETE, subject).when(own());
    }
    rules
        .can(COMPLETE, ACTIVITY)
        .when(field("assignee_id").eq(user.id));
    rules.can(COMPLETE, ACTIVITY).when(own());
    rules.can(UPDATE, DEAL).when(own());
    rules.can(MOVE, DEAL).when(own());
    rules.can(DELETE, DEAL).when(own());
    let closed = || field("stage").is_in([Stage::Won.as_str(), Stage::Lost.as_str()]);
    if !manages_deals(ctx) {
        // The delete rule below looks at the current stage only: moving a
        // closed deal back to an open stage would get around it.
        rules
            .cannot(MOVE, DEAL)
            .when(closed())
            .because(CLOSED_DEAL_MOVE_REASON);
    }
    rules
        .cannot(DELETE, DEAL)
        .when(closed())
        .because(CLOSED_DEAL_REASON);
}
```

- Everyone with a CRM role reads everything and creates records. Reps change and delete only what they own (`owner_id`), and complete the activities they own or are assigned.
- Managers get `manage` on every customer record through their permissions, so the owner conditions don't limit them.
- Won and lost deals are kept for reporting. The last rule stops even a manager from deleting one; only the admin's `manage all`, added after it, beats it. Reps can't move a closed deal either, or they could reopen it and then delete it.
- Users without a CRM role, and guests, get no rules at all.

The deal routes check these rules with `#[can]`, and the lists filter with `Accessible`:

```rust title="crm/api/crates/crm-deals/src/controller.rs"
#[post("/{id}/move")]
#[can(Move, Deal, from = "id")]
async fn move_deal(
    &self,
    uow: Uow,
    CurrentUser(user): CurrentUser,
    deal: Authorized<Deal, Move>,
    Valid(Json(input)): Valid<Json<MoveDeal>>,
) -> Result<Json<DealResource>> {
    let deal = self
        .deals
        .move_to(&uow, user.id, deal.into_inner(), input)
        .await?;
    Ok(Json(deal))
}
```

`Move`, `Export` and `Complete` are the CRM's custom action markers, in `crm-core/src/actions.rs`. The last two rules a rep's front end receives:

```json wrap
[
  {"action": "move", "conditions": {"stage": {"$in": ["won", "lost"]}}, "inverted": true, "reason": "Won and lost deals are kept for reporting; only managers reopen them.", "subject": "Deal"},
  {"action": "delete", "conditions": {"stage": {"$in": ["won", "lost"]}}, "inverted": true, "reason": "Won and lost deals are kept for reporting.", "subject": "Deal"}
]
```

## Testing

Test your abilities function as a plain function, with a context for each kind of user:

```rust title="src/abilities.rs"
#[cfg(test)]
mod tests {
    use std::collections::BTreeMap;
    use std::sync::Arc;

    use navree::access::{AbilityCtx, DELETE, Rules};
    use serde_json::json;
    use uuid::Uuid;

    use super::define;

    #[test]
    fn authors_cannot_delete_locked_posts() {
        let me = Uuid::now_v7();
        let subjects = Arc::new(BTreeMap::from([("posts".to_owned(), "Post".to_owned())]));
        let ctx = AbilityCtx::for_user(me, vec!["writer".into()], vec![]).with_subjects(subjects);
        let mut rules = Rules::new();
        define(&ctx, &mut rules);
        let ability = rules.build();

        let draft = json!({ "author_id": me, "locked": false });
        let locked = json!({ "author_id": me, "locked": true });
        assert!(ability.can(DELETE, "Post", Some(&draft)));
        assert!(!ability.can(DELETE, "Post", Some(&locked)));
    }
}
```

`AbilityCtx::guest()` builds a guest's context. The super-admin rule is added by the module, not by your function, so add `rules.can(MANAGE, ALL)` yourself to test it. The CRM's `crm-core/src/abilities.rs` checks a table of every action, subject and role this way.

For HTTP tests, give the test user roles through `AccessService` and send requests as them: with `TestApp::acting_as` when the app has no `AuthModule`, or with a real token (see [Authentication](/docs/security/authentication/#testing)). See [HTTP tests](/docs/testing/http-tests/).

## Limits

- Conditions are ANDed comparisons on the record's own columns: no `$or`, no nested fields, no relations.
- The abilities function can't read the database or other services.
- The roles you manage with `AccessService` are global. A member's role inside a workspace comes from [workspace membership](/docs/workspaces/members-and-roles/#how-workspace-roles-reach-access-control), and inside an organization from [the organization](/docs/workspaces/organizations/), not from these tables.
- The OpenAPI document has no schemas for `GET /api/me/abilities` and the `/api/access` routes.
