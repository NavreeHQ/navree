Navree authenticates API requests with tokens. A client signs in with an email address and a password and gets two tokens: a short-lived JWT **access token**, which it sends as `Authorization: Bearer` with every request, and an opaque **refresh token**, which it trades for a new pair when the access token expires. `navree-auth` provides the routes, the token handling, pluggable strategies and a `CurrentUser` extractor. Routes stay denied unless they say who may call them.

## How it works

- `POST /api/auth/login` checks the password and returns an access token (an HS256 JWT, valid 15 minutes) and a refresh token (an opaque string, valid 30 days).
- The client sends `Authorization: Bearer <access token>` with every request. The built-in JWT strategy verifies the signature and the expiry without touching the database.
- When the access token expires, the client posts its refresh token to `POST /api/auth/refresh` and gets a new pair. The old refresh token stops working; presenting it again revokes the whole session.
- `POST /api/auth/logout` revokes the session's refresh tokens.

<Diagram name="token-and-session" />

A browser app shouldn't hold the tokens in JavaScript at all. Pages your app draws, such as [Navree UI](/docs/ui/overview/) pages, sign the browser in on its [session cookie](/docs/basics/sessions-and-csrf/#signing-in-with-a-session) instead, with the same policies, throttles, two-factor authentication and audit trail. A separate web front end uses the [BFF pattern](#browser-apps-the-bff-pattern) below, which keeps the tokens in httpOnly cookies on your web server, as the reference CRM does.

## Setting up

<Badge feature="auth" /> The `auth` feature of the `navree` facade (part of the default `full` feature) brings `navree-auth` and the crates it builds on: `crypto`, `db`, `orm`, `http`, `validation`, `cache`, `mail`, `access` and `http-client`. Add `AuthModule` to your app root with the modules it needs:

```rust title="src/main.rs"
use navree::prelude::*;

fn main() -> Result<(), BoxError> {
    Navree::app()
        .module(ConfigModule::for_root(ConfigSources::defaults()))
        .module(CryptoModule::from_config()) // APP_KEY, Argon2id
        .module(HttpModule::from_config())
        .module(DatabaseModule::from_config())
        .module(CacheModule::from_config()) // optional: shares the login throttle
        .module(AuthModule::from_config()) // section `auth`
        .run()
}
```

| Module | Why |
|---|---|
| `CryptoModule` | Required. Hashes passwords with Argon2id and provides the key the JWTs are signed with. |
| `DatabaseModule` | Required. Stores users and refresh tokens. |
| `CacheModule` | Optional. The login throttle counts attempts in the app's cache, or in a private in-process cache without it. |
| `MailModule` | Optional. Sends the password reset and verification mails of the [account flows](/docs/security/account-flows/). |
| `AuditModule` | Optional. Records sign-ins and security events in the [audit log](/docs/security/audit-log/). |
| `AccessModule` | Optional. Roles, permissions and abilities: see [Authorization](/docs/security/authorization/). |

`AuthModule::from_config()` reads the `auth` configuration section (every key is listed under [Configuration](#configuration)). Invalid options fail the boot with a message that names the key, never a secret value.

### The application key

Sign tokens with a stable key. By default the JWT key is derived from the application key, so generate one and put it in `.env`:

```sh
navree key:generate
```

```text
base64:mfPeqWFuSe93GQYipIfV8X4lDcR0+9JZT0yRCGGfMPo=
```

```env title=".env"
APP_KEY=base64:mfPeqWFuSe93GQYipIfV8X4lDcR0+9JZT0yRCGGfMPo=
```

`navree key:generate` runs your app's `key:generate` command (it is `cargo run --quiet -- key:generate`). Like every app command, it boots the whole app first, so the database must be reachable. Without an application key or `auth.jwt.secret`, the app still boots but signs tokens with a random key per process. Every restart makes the access tokens already issued invalid, so clients have to refresh them, and two instances can't verify each other's tokens. The log warns about it. See [The signing key](#the-signing-key-jwt-secret-or-app_key) for the options.

### Migrations

`AuthModule` contributes the migration set `auth`, which creates the tables `users`, `refresh_tokens`, `password_reset_tokens`, `login_tokens` ([magic links and emailed codes](/docs/security/passwordless/)) and `passkeys` ([passkeys](/docs/security/passwordless/#passkeys)), and adds the [session columns](/docs/security/sessions/#the-session-columns) to `refresh_tokens`. A migration set of yours whose tables reference `users` runs after it:

```rust
MigrationSet::new("posts").after(["auth"])
```

The constant `navree::auth::AUTH_MIGRATIONS` holds the name `auth`. See [Migrations](/docs/database/migrations/).

### The users table

| Column | |
|---|---|
| `id` | UUID v7 |
| `name` | The display name |
| `email` | Unique; stored trimmed and in lower case, compared the same way |
| `password_hash` | The Argon2id PHC string. Never serialized, never in `Debug` output |
| `email_verified_at` | Set by [email verification](/docs/security/account-flows/#email-verification) |
| `two_factor_secret`, `two_factor_recovery_codes`, `two_factor_confirmed_at` | [Two-factor authentication](/docs/security/account-flows/#two-factor-authentication); never serialized |
| `created_at`, `updated_at` | UTC |

`navree::auth::User` is a model of Navree's ORM: query it with `User::query()` and its typed columns (`User::EMAIL`, `User::CREATED_AT`), or `User::find(&db, id)`. Its columns are fixed by `navree-auth`, and the module writes them itself (through `AuthService`), recording the change in the unit of work without the password hash or the two-factor data, so audit trails and other change observers never see them. It is also the access subject `User` (`#[model(subject = "User", permission_prefix = "users")]`), so an app registers it with `AccessModule::for_feature::<navree::auth::User>()`, and a route that checks a user takes `Authorized<User, Read>`, which dereferences to the `Record<User>`. To create a user outside `AuthService` (a sign-in module, an import), write it with `navree::auth::user::insert(&uow, user)`: it inserts the row and records the change event without the password hash or two-factor data. Keep app-specific data about users in a table of your own that references `users.id`, and add it to the API's user resource with a [user resource extension](#the-user-resource).

## The auth routes

The routes are mounted under `{http.api_prefix}{auth.routes_prefix}`, which is `/api/auth` by default.

| Route | Access | Success |
|---|---|---|
| `POST /api/auth/register` | Public; only when `auth.registration` is on | 201: the user and a token pair |
| `POST /api/auth/login` | Public; [throttled](#the-login-throttle) | 200: the user and a token pair, or a two-factor challenge |
| `POST /api/auth/refresh` | Public | 200: a new token pair |
| `POST /api/auth/logout` | Signed in | 204 |
| `GET /api/auth/me` | Signed in | 200: the user |

The other routes live on their own pages:

| Routes | Page |
|---|---|
| Profile and password changes, password reset, email verification, two-factor authentication | [Account flows](/docs/security/account-flows/) |
| `GET /api/auth/sessions`, `DELETE /api/auth/sessions/{id}`, `POST /api/auth/confirm` | [Sessions and step-up](/docs/security/sessions/) |
| `POST /api/auth/impersonate/{user}`, `DELETE /api/auth/impersonate` (when `auth.impersonation.enabled`) | [Impersonation](/docs/security/impersonation/) |
| `/api/auth/magic-link`, `/api/auth/otp`, `/api/auth/passkeys/*` (each when enabled) | [Passwordless sign-in](/docs/security/passwordless/) |
| `POST /api/auth/platform/login`, `POST /api/auth/platform/2fa/verify` (when `auth.platform.enabled`) | [Platform administrators](#platform-administrators) |
| `POST /api/auth/exchange` (when `auth.trusted_issuers` is not empty) | [Trusted token exchange](#trusted-token-exchange) |

Every error uses Navree's JSON error shape (see [Errors](/docs/basics/errors/)).

### Signing in

```http
POST /api/auth/login HTTP/1.1
Content-Type: application/json

{"email": "anu@example.com", "password": "correct horse battery"}
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIwMWExNzc0OC1lMjEx...",
  "expires_in": 900,
  "refresh_token": "01a17748-e21b-71c6-97cf-968b61f8e6b3.1ug0BGRxe4FaZwgRwDYO9BhvnHd3KPPgyzSJngXtYF3uZMZQ",
  "token_type": "Bearer",
  "user": {
    "__type": "User",
    "created_at": "2026-10-26T08:17:07.568377800Z",
    "email": "anu@example.com",
    "email_verified_at": null,
    "id": "01a17748-e211-72fc-abb3-836e604457d0",
    "name": "Anu Lakhotia"
  }
}
```

`expires_in` is the access token's lifetime in seconds. `user` is the [user resource](#the-user-resource). An account with two-factor authentication gets a challenge instead of tokens; the client finishes the sign-in with a code, as [Account flows](/docs/security/account-flows/#signing-in-with-a-second-factor) describes.

A wrong password and an unknown email get the same answer. For an unknown email Navree still verifies the password against a dummy hash, so the response time doesn't reveal which addresses have accounts:

```json
{"statusCode": 401, "message": "Invalid credentials", "error": "Unauthorized", "code": "invalid_credentials"}
```

A missing or malformed field is a 400 validation error: without a password, the message is `password should not be empty`.

### Calling the API

Send the access token in the `Authorization` header:

```http
GET /api/auth/me HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIwMWExNzc0OC1lMjEx...
```

```json
{
  "__type": "User",
  "created_at": "2026-10-26T08:17:07.568377800Z",
  "email": "anu@example.com",
  "email_verified_at": null,
  "id": "01a17748-e211-72fc-abb3-836e604457d0",
  "name": "Anu Lakhotia"
}
```

| Request | Response |
|---|---|
| No token on a route that needs a user | 401 `Unauthorized` |
| A forged or malformed JWT, another issuer or audience, a token of another type | 401 `Invalid token`, with `WWW-Authenticate: Bearer error="invalid_token"` |
| An expired JWT | 401 `Token expired`, with the same header |

A token that is present but invalid is a 401 on **every** route, public ones included. Navree never quietly treats such a request as a guest. A client that holds a stale access token should drop it rather than send it, in particular to `login` and `refresh`.

### Refreshing tokens

```http
POST /api/auth/refresh HTTP/1.1
Content-Type: application/json

{"refresh_token": "01a17748-e21b-71c6-97cf-968b61f8e6b3.1ug0BGRxe4FaZwgRwDYO9BhvnHd3KPPgyzSJngXtYF3uZMZQ"}
```

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIwMWExNzc0OC1lMjEx...",
  "expires_in": 900,
  "refresh_token": "01a17748-e21f-7764-92e3-307f059b7300.RqBqicxX3GwIxx8mYayt0ZgHxZAXLV81WoI65WWKWysYFRqw",
  "token_type": "Bearer"
}
```

The route is public: it needs no access token. The refresh token you sent is now spent, so store the new one. Sending a spent token again is treated as theft (see [Reuse detection](#reuse-detection)). An unknown, expired, revoked or spent token gets:

```json
{"statusCode": 401, "message": "Invalid refresh token", "error": "Unauthorized", "code": "invalid_refresh_token"}
```

### Signing out

```http
POST /api/auth/logout HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Content-Type: application/json

{"refresh_token": "01a17748-e21b-71c6-97cf-968b61f8e6b3.1ug0BGRxe4FaZwgRwDYO9BhvnHd3KPPgyzSJngXtYF3uZMZQ"}
```

The answer is always `204 No Content`. What gets revoked depends on the body:

| Body | Revokes |
|---|---|
| `{"refresh_token": "..."}` | That session: every refresh token of its family, if it belongs to the caller |
| `{"all": true}` | Every session of the caller, on every device |
| No body | Nothing (the call is still audited) |

Logout needs a valid access token, so one user can't end another's session. When the app has a real-time broadcaster, the user's WebSocket subscriptions end too (see [Broadcasting](/docs/digging-deeper/broadcasting/)). The access token itself keeps working until it expires: the client throws it away.

### Registering

`POST /api/auth/register` with `{"name", "email", "password"}` creates an account and signs it in: the answer is `201 Created` with the same body as a login. It is public by default; turn it off with `auth.registration = false`. The [Account flows](/docs/security/account-flows/#registration) page covers the password rules and what to do instead.

#### An address registered by someone else

Registering does not prove the address: the account can be used before its address is verified. So someone can register an account with another person's address before that person signs up, and sign in to it with the password they chose. When the owner later proves the address (the verification link, a [magic link or an emailed code](/docs/security/passwordless/)), the account becomes verified but keeps that password, any second factor or passkey set on it, and its sessions: the person who registered it can still sign in until the owner [resets the password](/docs/security/account-flows/#password-reset), which signs every session out, and removes any second factor or passkey they didn't add.

Navree has no setting yet that requires a verified address before a password sign-in. Until it does, either keep registration closed (`auth.registration = false`, accounts made by invitation or by an administrator), or require verification before use: a [sign-in policy](#sign-in-policies) that refuses `SignInMethod::Password` for an account whose `email_verified_at` is empty, with the verification mail sent at registration.

## Access tokens

Access tokens are JWTs signed with HS256 (HMAC-SHA-256), written and read by [`navree::crypto::jose`](/docs/security/signatures-and-keys/), Navree's own code. Here are the header and the claims of a real one:

```json
{"alg": "HS256", "typ": "JWT"}
```

```json
{
  "sub": "01a17748-e211-72fc-abb3-836e604457d0",
  "iat": 1793002627,
  "exp": 1793003527,
  "iss": "navree",
  "jti": "01a17748e21b71c697cf968dfe4f9f6d",
  "typ": "access",
  "sid": "01a17748-e21b-71c6-97cf-968b61f8e6b3",
  "auth_time": 1793002627
}
```

| Claim | |
|---|---|
| `sub` | The user's id |
| `iat`, `exp` | Issued at and expires at, in Unix seconds: `exp` is `iat` plus `auth.jwt.access_ttl_secs` (900) |
| `iss` | `auth.jwt.issuer` (`navree`) |
| `aud` | `auth.jwt.audience`, only when it is configured |
| `jti` | A unique token id |
| `typ` | What the token is for (below) |
| `sid` | The [session](/docs/security/sessions/) (refresh-token family) |
| `auth_time` | When the user last signed in or [confirmed](/docs/security/sessions/#confirming-the-password-or-a-code), in Unix seconds |
| `act` | For an [impersonation](/docs/security/impersonation/) session, `{"sub": <the impersonator's id>}` (RFC 8693) |
| `sign_in` | On challenge tokens only (a [two-factor](/docs/security/account-flows/#signing-in-with-a-second-factor) or a platform sign-in): how the user signed in (`{"method": "password"}`, `{"method": "social", "provider": "github"}`, ...), so the second step asks the [sign-in policies](#sign-in-policies) about the same method |

| `typ` | |
|---|---|
| `access` | An access token |
| `two_factor_setup` | The access token of a user who must [set up two-factor authentication](/docs/security/account-flows/#requiring-two-factor-authentication) first; it reaches only the setup routes |
| `platform` | The access token of a [platform session](#platform-administrators) |
| `two_factor_challenge`, `platform_challenge` | The challenge of a [two-factor login step](/docs/security/account-flows/#signing-in-with-a-second-factor) or a platform sign-in; never an access token |

The claims carry no roles or permissions: [authorization](/docs/security/authorization/) looks them up for each request (cached until they change), so a role change applies to the next request.

When it verifies a token, `JwtService` accepts only HS256 and checks, in this order. Every failure answers `401 Invalid token`, except the last:

- the size and the shape: at most 8 KiB (`navree::auth::MAX_TOKEN_LEN`), three unpadded base64url parts, a JSON header and a JSON object as the payload;
- the header: `alg` is `HS256`, so an unsigned `alg: none` token, an RSA, ECDSA or EdDSA algorithm named by the token, and another HMAC hash are all rejected. There is no `kid`: tokens carry none, and a token that names a key was not made by this service. There is no `crit`, and headers that point at keys (`jku`, `jwk`, `x5u`, `x5c`) are never followed;
- the signature, compared in constant time;
- the claims: `sub`, `iat`, `exp`, `iss`, `jti` and `typ` are all present and of the right kind; `nbf` has passed, if the token has one; `iss` matches, and so does `aud` when an audience is configured (when none is, a token that carries one is rejected);
- the token type, so a challenge token never works as an access token;
- `iat`, which can't be more than 30 seconds ahead of the app's `dyn Clock`;
- the expiry, last, with 30 seconds of leeway (`navree::auth::LEEWAY_SECS`). An expired token is `401 Token expired`, and only a token that is valid in every other way gets that answer.

Access tokens are stateless. Nothing revokes one before it expires: not a logout, not a password change. Keep `auth.jwt.access_ttl_secs` short; refresh tokens are the part that gets revoked.

You can sign and verify tokens yourself through `AuthService::jwt()`:

```rust
use navree::auth::TokenType;

let token = auth.jwt().sign_access(user.id)?;
let claims = auth.jwt().verify(&token, TokenType::Access)?;
assert_eq!(claims.sub, user.id);
```

## Refresh tokens

A refresh token looks like `<id>.<secret>`: the UUID v7 of its database row, a dot and 48 random base62 characters (about 285 bits). Navree stores only the SHA-256 digest of the whole token, so a copy of the database doesn't contain usable tokens. A refresh token is valid for `auth.jwt.refresh_ttl_secs` (30 days).

### Rotation and families

Each sign-in starts a **family**: one login session, on one device. Each refresh:

1. revokes the presented token, recording its successor in `replaced_by`;
2. issues the next token of the same family, valid for another 30 days from now.

The lifetime slides: a client that refreshes at least once every 30 days stays signed in. Signing out ends the family.

### Reuse detection

A refresh token is single use. If a token that was already exchanged comes back, two parties hold a copy of it, and Navree can't tell which one is the legitimate client. So it:

- revokes every token of the family, which signs the session out everywhere;
- answers `401 Invalid refresh token`;
- writes an `auth.refresh_reuse_detected` security entry to the [audit log](/docs/security/audit-log/).

Both the thief and the real user have to sign in again. The user's other sessions are not affected.

Two refreshes racing with the same token count as reuse too: the first one claims the token. A client that may refresh from several places at once (several tabs, parallel requests) must share one refresh call. The CRM's BFF keeps one refresh in flight per refresh token for exactly this reason.

A refresh runs in its own transaction, so the revocation of a reused family stands although the request fails. A token that is merely unknown, expired or revoked by a logout gets the same 401 and revokes nothing.

### The refresh_tokens table

| Column | |
|---|---|
| `id` | The part of the token before the `.` |
| `user_id`, `family_id` | The user and the login session |
| `token_hash` | SHA-256 of the whole token, lower-case hex |
| `expires_at`, `revoked_at` | Expiry, and when it was spent or revoked |
| `replaced_by` | The id of the token it was exchanged for |
| `ip`, `user_agent` | The client that received it (the user agent is cut to 512 characters) |
| `created_at` | |
| `authenticated_at`, `impersonator_id`, `audience` | The [session columns](/docs/security/sessions/#the-session-columns), copied to each successor |

<Callout type="warning" title="Old refresh tokens are kept">

Spent, revoked and expired rows are never deleted, and there is no command to prune them yet. On a busy app, delete old rows yourself, for example with a [scheduled](/docs/digging-deeper/scheduling/) command of your own.

</Callout>

## Protecting routes

Routes are denied by default: a route must declare who may call it. `#[controller]` refuses to compile a route without a declaration, and the app refuses to boot with a hand-written one. With `navree-auth` in the app, the declarations mean:

| Declaration | Who may call the route |
|---|---|
| `#[public]` | Anyone, guests included |
| `#[authenticated]` | Any signed-in user |
| `#[roles(..)]`, `#[permissions(..)]`, `#[can(..)]` | Signed-in users the access rules allow; see [Authorization](/docs/security/authorization/) |

[Access control on routes](/docs/basics/access-control/) covers the declarations in full. A guest on a protected route gets `401 Unauthorized`; a signed-in user who isn't allowed gets `403 Forbidden`.

Two more attributes add guards from `navree-auth` (they aren't access declarations, so a route still needs one of the above):

| Attribute | Refuses |
|---|---|
| `#[recent_auth(minutes = 10)]` | Sessions that didn't sign in or [confirm](/docs/security/sessions/#requiring-a-recent-sign-in) within the last 10 minutes: 403 `reauthentication_required` |
| `#[not_while_impersonating]` | [Impersonation](/docs/security/impersonation/#guarding-risky-routes) sessions: 403 `impersonation_forbidden` |

Both may sit on the impl block. For hand-written routes the guards are `navree::auth::recent_auth(duration)` and `navree::auth::not_while_impersonating()`, and `navree::auth::platform_session()` admits only [platform sessions](#platform-administrators).

## The current user

### CurrentUser

`CurrentUser` loads the signed-in user from the database, so a handler takes the user as an argument:

```rust title="src/modules/profile/mod.rs"
use navree::auth::UserResource;
use navree::prelude::*;

#[injectable]
pub struct ProfileController;

#[controller("/profile", version = "1")]
impl ProfileController {
    /// `GET /api/v1/profile`
    #[get("/")]
    #[authenticated]
    async fn show(&self, CurrentUser(user): CurrentUser) -> Json<UserResource> {
        Json(UserResource::from(&user))
    }
}

#[module(controllers = [ProfileController])]
pub struct ProfileModule;
```

It reads the `users` row once per request and keeps it for later extractors. It answers 401 for guests, and for a valid token whose user has been deleted since it was issued. Inside a request whose transaction is open, it reads through that transaction, so it never waits for a second database connection.

### CurrentPrincipal and ClientMeta

When you need only the user's id, `navree::http::CurrentPrincipal` gives you the request's `Principal` without a database query. `ClientMeta` gives the client's IP address, user agent and request id, which the `AuthService` methods take for their audit entries:

```rust
use navree::auth::ClientMeta;
use navree::http::CurrentPrincipal;
use navree::prelude::*;
use serde_json::{Value, json};

#[injectable]
pub struct WhoAmIController;

#[controller("/whoami")]
impl WhoAmIController {
    #[get("/")]
    #[authenticated]
    async fn show(
        &self,
        CurrentPrincipal(principal): CurrentPrincipal,
        meta: ClientMeta,
    ) -> Json<Value> {
        Json(json!({
            "user_id": principal.user_id,
            "ip": meta.ip,
            "user_agent": meta.user_agent,
        }))
    }
}
```

A `Principal` holds `user_id`, `via` (how the request authenticated: `AuthVia::Token` for JWTs), `token_abilities` (see [custom strategies](#writing-your-own-strategy)) and `session_id`.

For the access token itself, take `navree::auth::AccessClaims`: its session id, `auth_time` and impersonator (see [Reading the token's claims](/docs/security/sessions/#reading-the-tokens-claims)). `navree::auth::Actor` names the signed-in user and, in an impersonation session, the impersonator.

### The user resource

The auth routes answer with `UserResource`:

```json wrap
{"__type": "User", "id": "...", "name": "...", "email": "...", "email_verified_at": null, "created_at": "..."}
```

`__type` is the user's subject type for [abilities in the front end](/docs/security/authorization/#abilities-in-the-front-end). To add fields to it (in `GET /api/auth/me` and in the `user` of the login and register answers), implement `UserResourceExtension` and register it. The CRM adds each user's roles:

```rust title="crm/api/crates/crm-users/src/resource.rs"
use navree::access::AccessService;
use navree::auth::{User, UserResourceExtension};
use navree::openapi::Schema;
use navree::prelude::*;
use navree::{BoxError, BoxFuture};
use serde_json::{Map, Value};

/// Adds `roles` to the user resource of the auth routes.
#[injectable]
pub struct UserRolesExtension {
    access: Arc<AccessService>,
}

impl UserResourceExtension for UserRolesExtension {
    fn extend<'a>(
        &'a self,
        user: &'a User,
        fields: &'a mut Map<String, Value>,
    ) -> BoxFuture<'a, Result<(), BoxError>> {
        Box::pin(async move {
            let roles = self.access.roles_of(user.id).await?;
            fields.insert("roles".to_owned(), Value::from(roles));
            Ok(())
        })
    }

    fn schema_properties() -> Vec<(String, Schema, bool)> {
        vec![(
            "roles".to_owned(),
            Schema::array(Schema::string()).description("The user's role names, sorted."),
            true,
        )]
    }
}
```

```rust
// In the module's register function:
m.user_resource_extension::<UserRolesExtension>();
```

Extensions run in module dependency order and may overwrite fields. `AuthService::present(&user)` builds the same JSON for your own routes.

`schema_properties` puts the fields in the OpenAPI document's `UserResource`, so a client generated from it knows them.

## Strategies

Authentication is a chain of strategies, each one a way of recognising a request's credentials. `AuthModule` registers navree-http's authenticator, which runs every registered `dyn Strategy` in module dependency order, the built-in `JwtStrategy` (named `jwt`) first and, with the `session` feature, the built-in `SessionStrategy` (named `session`) second. Each strategy answers one of three ways:

| Answer | Meaning |
|---|---|
| `Ok(None)` | The request carries no credentials of this kind. The next strategy runs; if none recognises the request, it is a guest. |
| `Ok(Some(principal))` | Authenticated. Later strategies don't run. |
| `Err(error)` | Credentials of this kind are present but invalid. The request fails with `error` (usually a 401), even on a public route. It never falls through to another strategy or to a guest. |

`JwtStrategy` only claims `Authorization: Bearer` values shaped like a JWT: three base64url segments separated by dots. Other bearer values, such as an opaque API key or the scrape token of the `/metrics` endpoint, are left to other strategies and to route guards. It accepts tokens of type `access`, `platform` and `two_factor_setup` (the last only on the setup routes), stores the verified `AccessClaims` in the request, and for an impersonation token also a `navree::contracts::Impersonator`, which the unit of work and the audit log pick up.

`SessionStrategy` reads the user a browser [signed in on its session](/docs/basics/sessions-and-csrf/#signing-in-with-a-session) and checks on the server, on every request, that the sign-in is still live. It stores `AccessClaims` too (the user, the session as `sid`, the sign-in time as `auth_time`, no `jti`), so `#[recent_auth]`, `#[not_while_impersonating]`, the platform guard and the two-factor setup rule work the same for a browser as for a token. A sign-in that ended (signed out, revoked, past its end) makes the request a guest, never an error, so a stale cookie can always reach the sign-in page. It authenticates as `AuthVia::Session`.

### Writing your own strategy

`navree-auth` has no API keys of its own; the [OAuth server](/docs/packages/oauth-server/#personal-access-tokens) gives your users personal access tokens. A strategy is how you add API keys of your own design. This one accepts an `X-Api-Key` header and looks the key up in an `api_keys` table of your own (its [model](/docs/orm/models/), `ApiKey`, isn't shown):

```rust title="src/modules/api_keys/strategy.rs"
use http::request::Parts;
use navree::BoxFuture;
use navree::auth::Strategy;
use navree::contracts::{AuthVia, Principal};
use navree::crypto::sha256_hex;
use navree::db::Db;
use navree::prelude::*;

use super::entity::ApiKey; // the model of the `api_keys` table

/// `X-Api-Key: <key>` for scripts and integrations.
#[injectable]
pub struct ApiKeyStrategy {
    db: Arc<Db>,
}

impl Strategy for ApiKeyStrategy {
    fn name(&self) -> &'static str {
        "api-key"
    }

    fn authenticate<'a>(
        &'a self,
        parts: &'a mut Parts,
    ) -> BoxFuture<'a, Result<Option<Principal>, AppError>> {
        Box::pin(async move {
            // No header: not ours, let the next strategy look.
            let Some(key) = parts.headers.get("x-api-key") else {
                return Ok(None);
            };
            // Keys are stored as SHA-256 digests, never in plain text.
            let digest = sha256_hex(key.as_bytes());
            let found = ApiKey::query()
                .where_(ApiKey::KEY_HASH.eq(digest))
                .first(&self.db)
                .await
                .map_err(AppError::internal)?;
            // A key we don't know is a 401, never a guest.
            let Some(row) = found else {
                return Err(AppError::unauthenticated().with_detail("Invalid API key"));
            };
            Ok(Some(Principal {
                user_id: row.user_id,
                via: AuthVia::Token,
                // Narrows the user's abilities to these permissions.
                token_abilities: Some(row.abilities.split(',').map(str::to_owned).collect()),
                session_id: None,
            }))
        })
    }
}
```

Register it in a module with `strategy`, from `ModuleBuilderAuthExt` (in the prelude):

```rust title="src/modules/api_keys/mod.rs"
pub struct ApiKeysModule;

impl Module for ApiKeysModule {
    fn register(&self, m: &mut ModuleBuilder) {
        m.strategy::<ApiKeyStrategy>();
    }
}
```

The strategy runs after the JWT strategy, so a request with a valid bearer token is authenticated by the JWT and never reaches it. `token_abilities` limits what the key may do: with the access module, the user's abilities are narrowed to those permission strings (`deals.read`, or `*` for everything). `None` means unrestricted. See [Tokens with limited abilities](/docs/security/authorization/#tokens-with-limited-abilities).

## AuthService

`AuthService` is the API behind the routes, for seeders, commands and your own controllers. It is global, so any provider can inject `Arc<AuthService>`.

| Method | What it does |
|---|---|
| `register(&uow, NewUser { name, email, password })` | Creates an account with the password policy, in your unit of work |
| `create_user(name, email, password)` | Creates an account without the password policy (seeders, commands, tests) |
| `validate_user(email, password)` | The user, or `AuthError::InvalidCredentials` |
| `attempt_login(email, password, &meta)` | The login flow: throttle, password check, then `LoginOutcome::Authenticated { user, tokens }` or `LoginOutcome::TwoFactorRequired { user, challenge_token }` |
| `login(email, password, &meta)` | `attempt_login` for accounts without two-factor authentication; `AuthError::TwoFactorRequired` for the others |
| `sign_in(&user, method, &meta)` | Asks the [sign-in policies](#sign-in-policies) about `method`, then starts a session: what your own sign-in flows end with |
| `check_sign_in(&attempt, &meta)` | Asks the sign-in policies about a `SignInAttempt`; a refusal is audited as `auth.login_refused` |
| `two_factor_challenge(&user, &method)` | A two-factor challenge token that remembers how the user signed in, for `POST /api/auth/2fa/verify` |
| `issue_tokens(&user, meta)` | A new session without asking the sign-in policies (tests, seeders): an access token and the first refresh token of a new family (limited to the two-factor setup when the user [must set it up](/docs/security/account-flows/#requiring-two-factor-authentication)) |
| `refresh(refresh_token, meta)` | Rotates a refresh token |
| `logout(refresh_token, user_id, all)` | Ends one session, or all of them |
| `revoke_all_refresh_tokens(user_id)` | Ends every session of a user (refresh tokens only) |
| `revoke_all_credentials(user_id)` | Ends every credential of a user: sessions, and what other modules issued (see [offboarding](#offboarding-a-user-or-a-domain)) |
| `revoke_credentials_of_domain(domain)` | The same for every user of an email domain |
| `find_user(id)`, `find_by_email(email)` | Look up users |
| `update_password(user_id, password)` | Sets a password with the policy; sessions are left alone |
| `present(&user)` | The user resource, with its extensions |
| `jwt()` | The `JwtService` |
| `is_platform_admin(user_id)` | Whether the user holds a role of `auth.platform.roles` |
| `platform_login(email, password, &meta)`, `verify_platform_two_factor(challenge, proof, &meta)` | The [platform sign-in](#platform-administrators) |
| `exchange_token(token, &meta)` | [Trusted token exchange](#trusted-token-exchange) |

The account flows, sessions, impersonation and passwordless sign-in add more methods; see [Account flows](/docs/security/account-flows/#using-the-flows-from-code), [Sessions and step-up](/docs/security/sessions/#in-code), [Impersonation](/docs/security/impersonation/#in-code) and [Passwordless sign-in](/docs/security/passwordless/#in-code). Writes join the unit of work of the current task when there is an unfinished one (a request's, say) and otherwise commit their own transaction.

This console command creates an admin account with a random password, using the access module to assign the role:

```rust title="src/modules/admin/commands.rs"
use navree::access::AccessService;
use navree::auth::AuthService;
use navree::crypto::random_token;
use navree::db::Db;
use navree::kernel::{AppContext, CommandSpec};
use navree::prelude::*;

/// `admin:create <email> <name...>`: an admin account with a random
/// password, printed once.
pub fn create_admin() -> CommandSpec {
    CommandSpec::new(
        "admin:create",
        "Create an admin account: admin:create <email> <name>",
        |ctx: AppContext, args: Vec<String>| async move {
            let [email, name @ ..] = args.as_slice() else {
                return Err("usage: admin:create <email> <name>".into());
            };
            let auth = ctx.get::<AuthService>().await?;
            let access = ctx.get::<AccessService>().await?;
            let db = ctx.get::<Db>().await?;

            let password = random_token(20);
            let user = auth.create_user(&name.join(" "), email, &password).await?;

            let uow = db.uow(None, None).await;
            access.assign_role(&uow, user.id, "admin").await?;
            uow.commit().await?;

            println!("Created {} with the password {password}", user.email);
            Ok(())
        },
    )
}
```

Register it with `m.command(create_admin())` and run it with `navree admin:create anu@example.com Anu Lakhotia`. See [Console commands](/docs/digging-deeper/cli/).

## The signing key: JWT secret or APP_KEY

`AuthModule` picks the HS256 signing key when the app boots, in this order:

1. **`auth.jwt.secret`**, when it is set (in `.env` as `APP_AUTH__JWT__SECRET`). It must be at least 32 bytes long; a shorter one fails the boot. (`JwtService::new` called from code with a shorter secret pads it with zeros to 32 bytes, which is what HMAC does with a short key anyway.)
2. **A key derived from the application key** (`app.key`, or `APP_KEY`): an HMAC-SHA-256 of the key for the purpose `navree-auth.jwt`, from `Encrypter::derive_key`. The application key itself never signs anything.
3. **A random key per process**, with a warning in the log. Tokens stop working when the process restarts.

The derived key is the default, and it is enough for most apps: one secret to manage, and rotating `APP_KEY` rotates the JWT key with it. Set a dedicated `auth.jwt.secret` when you want to rotate the two independently.

There is one signing key and no key id: Navree does not keep old keys to verify with. Rotating the signing key, either way, invalidates every access token: requests get `401 Invalid token`. Refresh tokens don't depend on the key (they are stored as digests), so clients refresh and carry on. `app.previous_keys` doesn't help here: keys are derived from the current application key only.

<Callout type="note" title="HS256 only">

Tokens are signed with a shared secret, and only HS256 is supported: there are no RS256 keys or JWKS endpoint. (`navree::crypto::jose` signs with other algorithms; the access tokens do not use them.) Anything that can verify a token can also sign one, so don't hand the secret to other services. Every instance of your API needs the same key. To accept tokens that another system signs with its own keys, use [trusted token exchange](#trusted-token-exchange).

</Callout>

## The login throttle

`POST /api/auth/login` allows `auth.login_throttle_per_minute` (5) failed attempts per email address and client in a one-minute window. A client is an IPv4 address, or an IPv6 network (the first 64 bits of the address, `http.rate_limit_ipv6_prefix`), so rotating through the addresses of one IPv6 allocation gives no fresh attempts. The next attempt, even with the right password, gets a 429 until the window ends:

```http wrap
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/json

{"statusCode": 429, "message": "Too many login attempts. Please try again in 60 seconds.", "error": "Too Many Requests", "code": "too_many_login_attempts"}
```

- The same account from another address or network, and other accounts from the same client, are not affected.
- Each attempt is counted **before** the password is checked, so a burst of parallel guesses can't get more through than the limit. A successful login clears the count.
- A wrong `current_password` when changing the email or the password, or a wrong password when turning two-factor authentication off, counts against the same limit.
- The first refusal in each window is written to the audit log as `auth.throttled` (kind `security`), with the email address in its metadata.
- `auth.login_throttle_per_minute = 0` turns the throttle off.

The counters live in the app's cache when `CacheModule` is in the app, and in a private in-process cache otherwise. With the memory cache store, each API instance counts attempts on its own; with the [Redis store](/docs/digging-deeper/cache/#the-redis-store) (`cache.store = "redis"`), every instance shares the counts.

The throttle is only as good as the client address. Behind a reverse proxy or a BFF, list the proxy in `http.trusted_proxies`, or every client shares the proxy's address and one person's wrong passwords lock everyone out of that account. See [Rate limiting](/docs/basics/rate-limiting/).

Registration, the forgot-password route and the reset-password route have no attempt throttle of their own (forgot-password only limits how often it mails one address). Only navree-http's per-IP limit (`http.per_ip_rate_limit`, 600 requests a minute by default) applies to them.

## Platform administrators

Some people run the platform rather than use it: they manage every tenant, look at system health and help support. They sign in apart from the app, into the **platform audience**: a separate sign-in with its own throttle, two-factor authentication always, shorter sessions, and tokens that platform routes recognize.

```toml title="config/app.toml"
[auth.platform]
enabled = true
roles = ["platform-admin"]        # navree-access roles that may sign in
login_throttle_per_minute = 3     # failed platform sign-ins per email and IP
access_ttl_secs = 900
session_ttl_secs = 28800          # platform sessions end after 8 hours
break_glass = true                # sign-in policies can't lock administrators out (audited)
```

A platform administrator holds one of `roles` (from `AccessModule`) and has [two-factor authentication](/docs/security/account-flows/#two-factor-authentication) on. The sign-in always takes two steps:

```http
POST /api/auth/platform/login HTTP/1.1
Content-Type: application/json

{"email": "root@example.com", "password": "correct horse battery"}
```

```json
{
  "challenge_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "expires_in": 300,
  "two_factor_required": true
}
```

`POST /api/auth/platform/2fa/verify` with `{"challenge_token", "code"}` (or `recovery_code`) answers with the user and a token pair, like `POST /api/auth/2fa/verify`. The access token is of type `platform`.

- Wrong credentials and users without a platform role get the same `401 Invalid credentials`, recorded as `auth.login_failed` with `metadata.flow = "platform"`. An administrator without two-factor authentication gets `403 Two-factor authentication required` and sets it up through the app first.
- Failed attempts count against their own throttle (`login_throttle_per_minute`, 3), apart from the app's login throttle.
- A platform challenge works only at the platform route, and an app challenge only at the app's.
- Platform sessions end `session_ttl_secs` after the sign-in, however often they are refreshed through `POST /api/auth/refresh`. Each refresh checks the role again: a user who lost it is signed out.
- Platform administrators can't be [impersonated](/docs/security/impersonation/).
- Both steps ask the [sign-in policies](#sign-in-policies), as audience `platform`. With `break_glass = true` (the default), a refusal doesn't stop an administrator whose password, role and second factor check out: when single sign-on is enforced for their domain and the identity provider is down, they still reach the console. Every such sign-in is audited as `auth.break_glass` (kind `security`, `metadata.refused_code`) and logged under `navree::security`. With `break_glass = false` the refusal is the answer. Sign-ins to the app never break glass.

Platform routes refuse everything but platform sessions. Use the `PlatformAdmin` extractor, or the `platform_session()` guard on hand-written routes:

```rust title="src/modules/console/controller.rs"
use navree::auth::PlatformAdmin;
use navree::prelude::*;

#[injectable]
pub struct ConsoleController;

#[controller("/console")]
#[authenticated]
impl ConsoleController {
    /// `GET /api/console/whoami`: platform sessions only.
    #[get("/whoami")]
    async fn whoami(&self, PlatformAdmin(admin): PlatformAdmin) -> Json<String> {
        Json(format!("Signed in to the platform as {}", admin.email))
    }
}
```

`PlatformAdmin` loads the user; anything but a platform session gets 403 with the code `platform_session_required` ("A platform session is required"). Platform access tokens also work on the app's own routes, as the same user.

## Trusted token exchange

A sibling system (an older version of your product, a partner portal) can hand its signed-in users over without a second password prompt. It signs a short-lived JWT for the user with its own key, the client posts it to `POST /api/auth/exchange`, and Navree answers with a session. Configure each system under a name:

```toml title="config/app.toml"
[auth.trusted_issuers.legacy]
issuer = "https://legacy.example.com"           # the `iss` its tokens carry
jwks_url = "https://legacy.example.com/.well-known/jwks.json"
audience = "navree-app"                         # the `aud` they must carry
enabled = true                                  # the kill switch
max_lifetime_secs = 300                         # exp - iat at most 5 minutes
jwks_cache_secs = 3600
```

Set either `jwks_url` (fetched with the app's `HttpClient`, or a default client, and cached for `jwks_cache_secs`) or `public_key`: a PEM `PUBLIC KEY` (RSA, P-256 or Ed25519) or a JWK as JSON. Keep the PEM in `.env` (`APP_AUTH__TRUSTED_ISSUERS__LEGACY__PUBLIC_KEY`).

```http
POST /api/auth/exchange HTTP/1.1
Content-Type: application/json

{"token": "eyJhbGciOiJFUzI1NiIsImtpZCI6ImsxIn0.eyJpc3MiOiJodHRwczovL2xlZ2FjeS5leGFtcGxlLmNvbSIs..."}
```

The answer is the user and a token pair. A token is accepted when:

- its `iss` is a configured, enabled issuer;
- it is signed with RS256, ES256 or EdDSA by that issuer's key (the key with the token's `kid`, when it has one; an unknown `kid` fetches the key set again, at most once a minute);
- its `aud` (a string or a list) contains `audience`;
- `exp` and `iat` are present, it hasn't expired, `iat` and `nbf` aren't in the future (30 seconds of leeway each way), and it lives at most `max_lifetime_secs`;
- its `jti` hasn't been seen before: each token works once (the ids are kept in the app's cache until the token expires);
- its `email` belongs to a registered user, and `email_verified` isn't `false`.

A token for an account the [sign-in policies](#sign-in-policies) refuse (single sign-on enforced for its domain, say) gets their answer, such as `403 sso_required`. Every other refusal is `401 Invalid token`, whatever the reason; the reason goes to the log and to an `auth.token_exchange_failed` audit entry. Success is recorded as `auth.token_exchanged` with `metadata.issuer` (the name). The session that starts is an ordinary one: the [two-factor policy](/docs/security/account-flows/#requiring-two-factor-authentication) applies, but no second factor is asked for, because the issuer already authenticated the user. Set `enabled = false` to stop accepting an issuer's tokens at once. Unknown users are refused, never created.

Signatures are checked with `ring`; `alg: none`, HMAC algorithms and critical header extensions are refused.

## Browser apps: the BFF pattern

A token in `localStorage` can be read by any script that runs on the page, so one cross-site scripting bug leaks every session. Pages your app serves itself sign the browser in on its [session cookie](/docs/basics/sessions-and-csrf/#signing-in-with-a-session). For a separate web front end, such as a Next.js or Nuxt app, use a **backend-for-frontend** (BFF): the browser talks only to your web server, on the same origin, and never sees a token. The web server keeps the tokens in httpOnly cookies and calls Navree with `Authorization: Bearer`.

The BFF is one package, `@navree/bff` (`packages/js/bff`). `@navree/next` mounts it in a Next.js app and `@navree/nuxt` in a Nuxt app, and the CRM's two front ends, `crm/web` and `crm/nuxt`, use it that way:

- **Sign-in.** The browser posts its credentials to the BFF's `/api/auth/login`. The BFF calls Navree, stores the access token in a `navree_at` cookie (its `Max-Age` is `expires_in`) and the refresh token in `navree_rt` (30 days), both `HttpOnly; SameSite=Lax` and `Secure` in production, and returns only `{"user": ...}`. A two-factor challenge waits in a `navree_2fa` cookie that only `/api/auth/2fa` receives.
- **Requests.** Every other `/api/*` call is forwarded with the bearer token from the cookie. On a 401 the BFF refreshes once, updates both cookies and retries. Concurrent requests share one refresh call, because a second use of a refresh token would revoke the session. If the refresh fails, it clears the cookies and the browser goes back to the sign-in page.
- **Token responses.** When an `/api/auth/*` answer carries a token pair (changing the password returns one), the BFF puts it in the cookies and strips it from the body.
- **Sign-out.** The BFF revokes the refresh token at Navree, then clears the cookies.
- **CSRF.** Cookies are sent automatically, so every non-GET request must come from the app's own origin; anything else gets a 403.
- **Client addresses.** The BFF never passes on the browser's own `X-Forwarded-For`, which anyone can forge. It sends the browser's address only when reverse proxies in front of it vouch for it: set `NAVREE_TRUSTED_PROXY_HOPS` to their number.

```ts title="packages/js/bff/src/bff.ts"
function tokenCookies(tokens: TokenPair): string[] {
  const accessMaxAge = Math.max(1, Math.floor(tokens.expires_in ?? 900));
  return [
    cookie(names.access, tokens.access_token, { maxAge: accessMaxAge }),
    cookie(names.refresh, tokens.refresh_token, { maxAge: refreshMaxAge }),
  ];
}
```

On the API side, list the BFF's address in `http.trusted_proxies` so the API believes the `X-Forwarded-For` it sends. The login throttle and the per-IP limits then apply per browser. When the BFF knows no client address, every browser reaches the API from the BFF's address and shares its limits.

```toml title="crm/api/config/app.toml"
[http]
# The CRM's BFF calls from here for every browser and names the browser in
# X-Forwarded-For, so rate limits and the login throttle are per browser.
trusted_proxies = ["127.0.0.1", "::1"]
```

[A tour of the CRM](/docs/example-app/crm-tour/) shows the BFF in context. Native and mobile clients call the API directly and keep the tokens in the platform's secure storage.

| `auth.trusted_issuers.<name>.max_lifetime_secs` | `300` | The longest accepted `exp - iat` |
| `auth.trusted_issuers.<name>.jwks_cache_secs` | `3600` | How long a fetched key set is used |

Related settings: `app.key` (see [Encryption and hashing](/docs/security/encryption-and-hashing/)), the `hashing` section for password hashes, `http.trusted_proxies` for client addresses, and `http.signing_key` for the signed verification links.

From the environment, prefix the key with `APP_` and use `__` between levels: `APP_AUTH__JWT__SECRET`, `APP_AUTH__REGISTRATION=false`. Keep secrets in `.env`, never in `config/app.toml`. A new app's `config/app.toml` sets `auth.registration`; [`.env` and real environment variables override it](/docs/getting-started/configuration/#where-settings-come-from), so you can change that one from either.

To configure the module in code instead, pass `AuthOptions` to `AuthModule::for_root`:

```rust
use navree::auth::{AuthOptions, JwtOptions};

AuthModule::for_root(AuthOptions {
    registration: false,
    jwt: JwtOptions {
        issuer: "crm".to_owned(),
        audience: Some("crm-web".to_owned()),
        access_ttl_secs: 600,
        ..JwtOptions::default()
    },
    ..AuthOptions::default()
})
```

## Audit entries

With an [audit log](/docs/security/audit-log/) in the app, the module records:

| Action | Kind | When |
|---|---|---|
| `auth.register` | `auth` | An account was registered (after the commit) |
| `auth.login` | `auth` | A sign-in succeeded (`metadata.two_factor` says `totp` or `recovery_code` after a second factor) |
| `auth.login_failed` | `security` | Wrong credentials; `metadata.email`, and the user as actor when the email is known |
| `auth.login_refused` | `security` | A [sign-in policy](#sign-in-policies) refused a sign-in; `metadata.method`, `metadata.email`, `metadata.code`, `metadata.audience` (plus `provider`, `connection` or `issuer`) |
| `auth.break_glass` | `security` | A platform administrator signed in to the console past a sign-in policy refusal; `metadata.refused_code` |
| `auth.throttled` | `security` | The first refusal of a throttle window; `metadata.flow` and, for logins, `metadata.email` |
| `auth.refresh` | `auth` | A refresh token was rotated; `metadata.family_id` |
| `auth.refresh_reuse_detected` | `security` | A spent refresh token came back and its family was revoked |
| `auth.logout` | `auth` | `metadata.all` and `metadata.revoked` (how many tokens) |
| `auth.credentials_revoked` | `security` | [Offboarding](#offboarding-a-user-or-a-domain): `metadata.domain` (for a domain), `metadata.users`, `metadata.revoked` (the count of each kind) and `metadata.complete` |
| `auth.platform_login` | `auth` | A platform sign-in finished; `metadata.two_factor` and `metadata.session_id` |
| `auth.token_exchanged` | `auth` | A trusted issuer's token was accepted; `metadata.issuer` |
| `auth.token_exchange_failed` | `security` | One was refused; `metadata.issuer` (when known) and `metadata.reason` |

Entries carry the client's IP address, user agent and request id, and the impersonator in an [impersonation](/docs/security/impersonation/#the-audit-trail) session. Passwords and tokens are never recorded. The account flows, sessions, impersonation and passwordless sign-in add their own entries; see [Account flows](/docs/security/account-flows/#events-and-audit-entries), [Sessions and step-up](/docs/security/sessions/#audit-entries), [Impersonation](/docs/security/impersonation/#the-audit-trail) and [Passwordless sign-in](/docs/security/passwordless/#audit-entries).

## Testing

`TestApp::acting_as` works with the test authenticator, which `AuthModule` replaces. In an app with `AuthModule`, create a user and sign a real token for it:

```rust title="src/modules/profile/tests.rs"
use navree::auth::AuthService;
use navree::crypto::generate_key;
use navree::prelude::*;
use navree::testing::TestApp;
use serde_json::json;

use super::ProfileModule;

#[tokio::test]
async fn shows_the_signed_in_users_profile() {
    let app = TestApp::builder()
        .temp_database()
        .config("app.key", generate_key())
        // Fast hashing: tests don't need production-strength Argon2id.
        .config("hashing.memory_kib", 1024)
        .config("hashing.iterations", 1)
        .module(CryptoModule::from_config())
        .module(DatabaseModule::from_config())
        .module(AuthModule::from_config())
        .module(ProfileModule)
        .build()
        .await;

    let auth = app.get::<AuthService>().await;
    let user = auth
        .create_user("Anu Lakhotia", "anu@example.com", "correct horse battery")
        .await
        .unwrap();
    let token = auth.jwt().sign_access(user.id).unwrap();

    app.client()
        .get("/api/v1/profile")
        .bearer(&token)
        .send()
        .await
        .assert_status(200)
        .assert_json_path("email", json!("anu@example.com"));

    app.client()
        .get("/api/v1/profile")
        .send()
        .await
        .assert_error(401, "Unauthorized");
}
```

- To test the sign-in itself, post to `/api/auth/login` and read the tokens from the response. The CRM's test kit does this in `TestCrm::login_as`.
- `TestAppBuilder::fake_auth()` puts the test authenticator back, so `acting_as` works, but then real bearer tokens don't: you can't mix the two in one app.
- Override `dyn Clock` with a `FixedClock` to test expiry. The login throttle's windows run on the cache's timer, though, not on the app's clock: moving a `FixedClock` forward doesn't end a lockout. Use different email addresses, or set `auth.login_throttle_per_minute` to `0` in tests that don't test the throttle.

See [HTTP tests](/docs/testing/http-tests/) for the test client.

## Social sign-in, single sign-on and OAuth

Three packages build on `navree-auth` and its users:

- [Social sign-in](/docs/packages/social-sign-in/) lets people sign in with Google, GitHub, Apple, Microsoft and other providers, and links those accounts to Navree users.
- [Single sign-on](/docs/security/single-sign-on/) connects an organization or a workspace to its company's identity provider (SAML 2.0 or OpenID Connect) and can keep its people off passwords.
- The [OAuth server](/docs/packages/oauth-server/) issues tokens to third-party apps with OAuth 2.1 and OpenID Connect, with scopes and consent, and gives your users personal access tokens.

For API keys of your own design, [write a strategy](#writing-your-own-strategy).

### Sign-in policies

A sign-in policy decides whether a sign-in may go on. Every flow that signs a person in asks every registered policy **before** it issues a session, a token pair or a two-factor challenge, so a rule written once holds on every path:

| Path | Method (`SignInMethod`) | Asked |
|---|---|---|
| `POST /api/auth/login`, `POST /api/auth/register`, `PATCH /api/auth/me/password` | `Password` | Before the password is checked |
| `PATCH /api/auth/me` with a new email | `Password`, for the old address and the new one | Once the current password checks out, before anything changes: an account can't leave a domain that enforces single sign-on, or take an address of one |
| `POST /api/auth/magic-link` and `/magic-link/verify` | `MagicLink` | When a link is requested (no mail is sent) and when one is used |
| `POST /api/auth/otp` and `/otp/verify` | `Otp` | When a code is requested and when one is used |
| `POST /api/auth/passkeys/login` | `Passkey` | Once the passkey is verified, before the session |
| `POST /api/auth/exchange` | `TokenExchange { issuer }` | Once the token is verified, before the session |
| `POST /api/auth/2fa/verify` | the method of the first step | Again, before the code is checked |
| [Social sign-in](/docs/packages/social-sign-in/) | `Social { provider }` | On the provider's address before any account is created or linked, and on the account before the session |
| [Single sign-on](/docs/security/single-sign-on/) | `Sso { connection }` | On the identity provider's address before provisioning, and on the account before the session |
| `POST /api/auth/platform/login` and `/platform/2fa/verify` | `Password`, audience `Platform` | At both steps; see [break-glass](#platform-administrators) |

A policy implements `SignInPolicy` and is registered with `m.sign_in_policy::<P>()` (`ModuleBuilderAuthExt`). It gets a `SignInAttempt`: the email (trimmed and lower-cased), the user's id once the account is known, the method and the audience (`App` or `Platform`). `attempt.domain()` is the email's domain in one canonical spelling, whatever the form, identity provider or social provider sent: lower case ASCII, without a trailing dot, international names in their `xn--` form, full-width letters and the ideographic full stop mapped (`Ela@ACME.test.` and `ela@agra。test` both give `Some("acme.test")`). Compare it with domains written that way; `navree::auth::email_domain(email)` gives the same form for other comparisons. Every policy must allow; the first refusal is the answer, usually `AuthError::SignInRefused { code, message }`, a 403 with that code. Refusals are audited as `auth.login_refused` with the method, the email and the code.

```rust title="src/modules/security/policy.rs"
use navree::auth::{AuthError, SignInAttempt, SignInMethod, SignInPolicy};
use navree::prelude::*;

/// Contractors sign in with a passkey only.
#[injectable]
pub struct PasskeysForContractors;

impl SignInPolicy for PasskeysForContractors {
    fn check<'a>(&'a self, attempt: &'a SignInAttempt) -> BoxFuture<'a, Result<(), AuthError>> {
        Box::pin(async move {
            if attempt.domain() == Some("contractors.agra.com")
                && attempt.method != SignInMethod::Passkey
            {
                return Err(AuthError::SignInRefused {
                    code: "passkey_required".to_owned(),
                    message: "Sign in with your passkey".to_owned(),
                });
            }
            Ok(())
        })
    }
}
```

Register it in a module with `m.sign_in_policy::<PasskeysForContractors>()`. [Single sign-on](/docs/security/single-sign-on/#enforcement) registers the policy that sends the verified domains of an enforcing connection through that connection only (`sso_required`).

Your own sign-in flows end with `AuthService::sign_in(&user, method, &meta)`, which asks the policies and then starts the session, or call `check_sign_in(&attempt, &meta)` first and `issue_tokens` after. `check_password_sign_in(email)` asks about `Password` without an audit entry. `issue_tokens` alone asks nothing: keep it for tests and seeders. A two-factor challenge from `two_factor_challenge(&user, &method)` remembers the method, and `POST /api/auth/2fa/verify` asks the policies about it again, so a domain that came to enforce single sign-on between the two steps is refused.

Policies decide at sign-in. Sessions and tokens that started before a rule changed go on until they end: to cut everyone of a domain off at once, [revoke their credentials](#offboarding-a-user-or-a-domain). [Impersonation](/docs/security/impersonation/) is a support session opened by an administrator who already signed in, so it doesn't ask the policies; it has its own permission and audit trail.

### Offboarding a user or a domain

A policy only decides at sign-in, so when a rule starts to apply (single sign-on enforcement turns on for a domain, a contractor leaves), whatever the people already hold keeps working: refresh tokens, [personal access tokens](/docs/packages/oauth-server/#personal-access-tokens), OAuth grants and their tokens. One call ends all of them:

```rust
use navree::auth::AuthService;

async fn offboard(auth: &AuthService) -> Result<(), navree::auth::AuthError> {
    // Everyone whose email is on the domain.
    let ended = auth.revoke_credentials_of_domain("agra.com").await?;
    tracing::info!(users = ended.users, credentials = ended.total(), "offboarded agra.com");

    // Or one person: `ended.revoked("personal_access_tokens")` says how many of a kind.
    // auth.revoke_all_credentials(user_id).await?;
    Ok(())
}
```

`revoke_credentials_of_domain` reads the domain the way `SignInAttempt::domain()` does (`ACME.com.` is `agra.com`) and finds users whatever the spelling of their stored email. The returned `CredentialsRevoked` has `users` and a count per kind (`revoked(kind)`, `total()`):

| Kind | Issued by | Stops |
|---|---|---|
| `refresh_tokens` | `navree-auth` | Every sign-in session: the refresh token no longer rotates, and the user's real-time subscriptions end |
| `personal_access_tokens` | `navree-oauth` | The token is refused at once |
| `oauth_access_tokens`, `oauth_refresh_tokens` | `navree-oauth` | Tokens issued to apps; the refresh token no longer refreshes |
| `oauth_codes`, `oauth_device_codes` | `navree-oauth` | Approved authorization codes and device codes that were not exchanged yet |
| `oauth_authorizations` | `navree-oauth` | The remembered consent for each app is forgotten, so the app asks again |

Modules that issue credentials take part by registering a `CredentialRevoker` (`navree::contracts::CredentialRevoker`, with `m.credential_revoker::<R>()` from `ModuleBuilderRevocationExt`); `navree-oauth` registers one, so `navree-auth` and [single sign-on](/docs/security/single-sign-on/#offboarding) don't depend on it. Your own module can end its API keys or invitations the same way: `revoke_for_users(&[Uuid])` returns the count of each kind it ended. Every revoker runs even when one fails; the first failure comes back as `AuthError::Revocation { module, .. }` after the others finish, and the call can be repeated. The call is audited as `auth.credentials_revoked`.

Access tokens of `navree-auth` are signed and stateless: one a client already holds works until it expires (`auth.jwt.access_ttl_secs`, 15 minutes by default) but cannot be refreshed. OAuth access tokens and personal access tokens are looked up on every request and stop at once (other instances that cache lookups, `oauth.token_cache_secs`, may take up to that long). The scan that finds a domain's users reads every user's email in pages: it suits an offboarding, not a request.

## Limits

- **Tokens, not sessions.** `navree-auth` issues tokens only. Cookie sessions with CSRF protection are a separate, optional module ([Sessions and CSRF](/docs/basics/sessions-and-csrf/)) that `navree-auth` doesn't use.
- **Access tokens can't be revoked** before they expire, and they are signed with HS256 only. Ending a [session](/docs/security/sessions/) stops its refresh tokens, not its access tokens.
- **Refresh tokens are never pruned** from the database.
