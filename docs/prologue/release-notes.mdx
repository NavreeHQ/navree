## Navree 1.1.0

Navree 1.1.0 is a minor release. To update, run `cargo update` in your app, which takes it within the range your `Cargo.toml` allows, and `cargo install navree-cli --force` for the command-line tool.

### Added

- Radial charts in `navree::ui::charts`: `Ring` (one value from twelve o'clock, with a second lap past its goal), `Rings` (up to six values inside each other), `Gauge` (an open arc on any scale, with zones) and `DayClock` (24 wedges by value, category and level, with moments and an hour band). Each has its table and summary, and a size per screen width.
- Linear charts: `Meter` (segments of a whole, with shares, a legend and detail lines), `MiniColumns` (one stacked column per item), `ColorStrip` (a cell per item in its category's or band's colour) and `RangeScale` (a value on a gradient track). `Trend` draws an arrow and a signed change, and a `Stat` can carry one.
- Grid charts: `CalendarHeatmap` (a day per cell in weeks, a five-step scale, month labels and a "Less … More" legend), `MatrixHeatmap` (a diverging scale over pairs, focusable cells), `Scatter` (translucent points, with an identity line) and `RelationList` (pairs ranked by a signed value).
- Options for every chart: gradients, theme inks and glow (`Gradient`, `Ink`); colour by value or threshold (`ColorScale`); motion that is off by default and off under reduced motion (`Motion`, `CountUp`); axis, gridline and tick switches and padded or fixed domains (`Axis`, `Gridlines`, `Ticks`, `Domain`); reference levels and bands (`Reference`, `Zone`); point dots, an active dot, step curves over named levels and big-value tooltips (`Dots`, `ActiveDot`, `Curve`, `TooltipStyle`); `Chart::baseline`, `Chart::lanes` and `NumberFormat::clock`. `Sparkline`, `Progress` and `Bars` take the same paint, and draw what they drew before when none is set. Each chart family links a stylesheet of its own.
- App blocks: `AppSheet`, `AppFont` and `AppImage` (an app's own stylesheet, font and picture, compiled in and served by content hash), a `Stat` that grows into a dashboard tile (icon, unit, status, a small chart beside or under the figure, a link), `InfoTip`, `ChartSkeleton`, `BreathingGuide`, `Dock` (with `Dock::below`), `DayPager`, `CopyField`, `Grid::ratio` and `Grid::fit`. They share one stylesheet and load no script.
- Marketing blocks for a public site, drawn on the server with no script: `SitePage`, `SiteHeader`, `Hero`, `Section`, `LogoCloud`, `FeatureGrid`, `FeatureRows`, `StatBand`, `BrowserFrame` and `PhoneFrame`, `Testimonials`, `Pricing`, `Faq`, `CtaBand`, `Newsletter`, `LegalPage` and `SiteFooter` with its theme toggle. `Picture` writes `srcset`, `sizes`, AVIF and WebP sources and light and dark versions.
- `View::seo` writes a page's description, robots, canonical and language links, social cards and JSON-LD (escaped so no text can close the block), and `Seo::problems` lists what a search result would hold against the page. `Sitemap` and `RobotsTxt` answer as files.
- `AuthPages` draws the sign-in pages in the app's look (its shell's theme, sheets, fonts and title template, or `appearance`, `stylesheet`, `font`, `aside` and `view` without one), on `AuthLayout`. `AuthPages::sign_up()` adds a sign-up page when `auth.registration` is on, and `AuthPages::after_sign_out` sets where a signed-out browser goes.
- `AppPage::topbar` puts a page's own part in the middle of the top bar, and `Shell::title_template` with `AppPage::document_title` titles the browser tab apart from the heading. `ThemeMenu` shows only the modes when one theme is on offer.
- `RouteDef::on_guest_or`: one address that answers a guest with one handler and a signed-in reader with another, such as a public home page and the app's home.
- `csrf::SameOriginOnly`: a module names a path whose posts are checked by their origin in place of the CSRF token. `Session::is_resumed` says whether the request came with the session's cookie.

### Changed

- Every form of `AuthPages` needs the session's cookie: a state-changing request to those pages without it is refused with a 403 before anything runs. A form left open until its session expired is drawn again with "Your session expired. Please try again.", keeping nothing that was typed.
- `POST /auth/register` takes five requests a minute per client, as the sign-up page does.
- navree-ui's appearance route checks the request's origin in place of the CSRF token, so a theme toggle on a page cached for everyone works for a reader with a session too, and it goes back only to a path of this site.
- An `on_guest_or` answer to a signed-in reader goes out as `Cache-Control: private, no-store` unless its handler kept it private, without the headers a CDN reads in place of `Cache-Control`, and with `Vary: Cookie, Authorization`.
- A `ColorScale` on a `Gauge` or a `Ring` reads its thresholds as values in the chart's own units, as every other chart does.
- A `RelationList` is a named group of list rows a screen reader walks, not a picture; a `Gauge` on a scale that starts above zero says in its summary and table when the value is below or above the scale; a list cut at 50 says so under `only_significant()` too.
- Warm chart colours keep their hue in light mode: gradients and vivid stops take a deeper end per theme (`--chart-N-vivid`), so orange and amber no longer mix toward brown.

### Fixed

- A region whose answer held a lazy part of its own (a lazy tab inside a lazy tab) replaced the whole page with that answer. A page the toolkit draws for a region's fetch is now marked as the region's fragment.
- A light and dark toggle, or a theme menu without its themes, turned a page of another theme into the default theme: the appearance cookie now keeps only what was chosen.

### Security

- Login CSRF from a sibling subdomain, or from a browser that doesn't say where it posts from, is closed by refusing a sign-in page post without the session's cookie. Every such refusal is logged on `navree::security` and audited as `csrf.mismatch`.
- A signed-in reader's page at an `on_guest_or` address is kept out of shared caches whatever its handler set. A CDN or proxy in front must still skip its cache for requests that carry the session cookie, since several ignore `Vary: Cookie`; the docs say so.
- The security docs describe a risk that remains: someone can register an account with another person's address before that person signs up, and the account keeps their password after the owner verifies it. Keep registration closed, or refuse password sign-in for an unverified address with a sign-in policy, until a setting for it ships.

## Navree 1.0.2

Navree 1.0.2 is a patch release. To update, run `cargo update` in your app, which takes it within the range your `Cargo.toml` allows, and `cargo install navree-cli --force` for the command-line tool.

### Security

- Navigator's `query_database` and Lighthouse's tools could be made to run more than the one read-only statement they checked, and so to change the development database or write files: through hex strings (`X'..'`), custom type modifiers and, on SQLite, variables (`$a::..`), which the guard and the database read differently; on PostgreSQL through functions called in `FROM` (`pg_read_file`, `dblink`, `pg_terminate_backend`) and functions that run SQL text of their own (`ts_stat`, `query_to_xml`); and on a PostgreSQL server with `standard_conforming_strings` off, through a backslash before a quote. The database engine now holds the line. On SQLite the file is opened read-only, SQLite itself prepares the text and refuses anything after the first statement, refuses a statement it says writes (which covers `VACUUM`), and an authorizer allows only reading (no `PRAGMA` but the `data_version` FTS5 reads, no `ATTACH`, no transactions). On PostgreSQL each query is a single prepared statement in a read-only transaction, in a session that pins `standard_conforming_strings = on`, checks it, and pins it again inside the transaction (behind a pooler in transaction mode another client's `SET` could otherwise reach it). The statement guard also refuses those literals, types, parameters and functions, sends a statement only when it reads back unchanged, and refuses statements over 64 KB or nested over 1,000 expressions deep, which could crash Navigator.
- On PostgreSQL, `query_database` and Lighthouse's tools now refuse to run as a superuser, as a role that can become one (a member of a superuser role, or a superuser session with a lesser `role`), or as a member of `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program`, `pg_signal_backend` or `pg_signal_autovacuum_worker`, since such a role reaches the server's files, programs and other sessions from a query. They also refuse a role that may execute, whatever its privilege on the schema, a `SECURITY DEFINER` function of the database's own (not an extension's), a function in an untrusted language (`plpython3u`, `plperlu`, `pltclu`, or C outside an extension), or a function of an extension that reaches files, programs, other servers or the network (any extension with a foreign-data wrapper, `dblink`, `adminpack`, `http`, `pg_net`, `pg_background`, `pg_cron`, `pgagent`, `plproxy`, `orafce`, `aws_s3`, `aws_lambda`, `aws_commons`, `azure_storage`, `azure_ai`, `google_ml_integration`, `pgml`); the support functions of an aggregate it may execute count too (PostgreSQL checks `EXECUTE` on them against the aggregate's owner), and so does a foreign table it may `SELECT` from, directly or through views. The refusal names what it found. What an ordinary role can still reach is what the other extensions installed in the database give it (their C functions, and their own `SECURITY DEFINER` functions: PostGIS, pgcrypto, TimescaleDB, pgvector), a table read by a view it may read (the view reads its tables with its owner's rights; a foreign table there is refused, as above), and any extension Navigator doesn't know that adds a function reaching the network or a file.
- A query could make Navigator hold gigabytes: `printf('%.*c', 400000000, 'x')`, a recursive `zeroblob(..)` or `json_group_array` on SQLite, `repeat('x', 900000000)` or an `EXPLAIN` plan on PostgreSQL. SQLite now refuses to make a string or blob over 1 MB, and `navree mcp` caps SQLite's heap at 256 MB for its process (code that embeds Navigator sets its own cap with `database::limit_sqlite_heap`). PostgreSQL cuts each value to 4 KB before sending it (its own work ends with the 5 second timeout), and `EXPLAIN` is refused there. A query may answer at most 100 columns; every value over 4 KB comes back cut and ending with `… [cut]`, and an answer stops at about 1 MB of JSON, with `truncated` set (a single row that large keeps its first values and cuts the rest). Error messages are cut to 2 KB in what the tools return (PostgreSQL still sends the whole message, up to its 1 GB limit, and Navigator reads it once before cutting it). Lighthouse's tools read their own tables whole, up to 8 MB a value, so histograms and backtraces stay complete.
- `describe_schema` on PostgreSQL could list every table instead of the one asked for, given a table name with a backslash and a quote on a server with `standard_conforming_strings` off.
- The pgvector store wrote the field name of a comparison filter (`Filter::gt`, `gte`, `lt`, `lte`) into its SQL unescaped. Field names are bound parameters now.
- The UI runtime refuses a `data-ui-form` whose action is on another origin before sending it, and applies nothing from an answer that was redirected to another origin. One case is left: the browser follows a redirect before the runtime sees it, so on a page served without Navree's content security policy, a same-origin action that redirects to another origin (an open redirect in the app) sends the request there, with the session's `x-xsrf-token` header and, after a 307 or 308, the form's body, if that origin answers the browser's preflight. Navree's policy (`connect-src 'self'`) stops that request in the browser.

### Added

- `navree dock up` keeps a read-only role, `navree_reader`, in the PostgreSQL database, for Navigator. When Dock creates it, it may connect, use `public` and read its tables, now and later; Dock never grants it anything again, so a `REVOKE` stays. On every `up` it is made a plain login role whose sessions start read-only with a 5 second statement timeout (role defaults a session may change) and may write at most 64 MB of temporary files. Its password is its own, derived from the service's, and Dock sends the server only its SCRAM verifier. Like any role, it also has what PostgreSQL gives `PUBLIC`: `CONNECT`, `TEMP`, and `EXECUTE` on functions, extension C functions included.
- `NAVREE_MCP_DATABASE_URL`: the database `navree mcp` reads instead of the app's `database.url`, such as the same database through a read-only role.
- `NAVREE_MCP_ALLOW_PRIVILEGED_DATABASE_ROLE=1`: lets `navree mcp` query as a refused PostgreSQL role, with a warning each time it starts.
- `navree_navigator::DatabaseOptions`, `Navigator::with_database` and `run_stdio_with`, which carry those two settings for code that embeds Navigator, and `navree_navigator::database::limit_sqlite_heap` with `SQLITE_HEAP_LIMIT`, `MAX_VALUE_BYTES`, `MAX_ANSWER_BYTES`, `MAX_COLUMNS`, `MAX_MESSAGE_BYTES` and `CUT_MARK`.

### Changed

- Upgrading with Dock: run `navree dock up` once. It creates `navree_reader` in your running database (nothing is restarted), and from then on Navigator's `query_database`, `describe_schema` and Lighthouse's tools read the Dock database as that role. Until you do, they fail to connect and say that `navree dock up` creates the role. Dock's own user, `navree`, is a superuser, which `query_database` now refuses.
- Upgrading without Dock: on PostgreSQL, `navree mcp`'s `query_database` and Lighthouse's tools refuse a privileged role, and a development database often connects as a superuser. Create a read-only role (the refusal prints the SQL; the Navigator docs have it too) and set `NAVREE_MCP_DATABASE_URL` to its URL in your agent's MCP configuration, or set `NAVREE_MCP_ALLOW_PRIVILEGED_DATABASE_ROLE=1` to keep querying as before. A role that may execute `SECURITY DEFINER`, untrusted-language or network and file extension functions is refused too: revoke `EXECUTE` on the functions the refusal names. `describe_schema` is not affected.
- On SQLite, `query_database` no longer reads pragma table functions (`pragma_table_info`): `describe_schema` answers what they would. R*Tree tables can't be queried through `query_database` either: opening one prepares a write. FTS5 tables can.
- On PostgreSQL, `query_database` refuses `EXPLAIN`: the plan holds the query's constants at any size. Run it in `psql`, or ask `describe_schema` about the tables and indexes. SQLite's `EXPLAIN QUERY PLAN` still works.
- Dock refuses a `dock.toml` whose PostgreSQL `user` is `navree_reader`.
- Navigator's docs and tool descriptions say that hiding columns with secret-looking names in query results is a convenience, not a protection: a query can rename or wrap a column.

## Navree 1.0.1

Navree 1.0.1 is a patch release. To update, run `cargo update` in your app, which takes it within the range your `Cargo.toml` allows, and `cargo install navree-cli --force` for the command-line tool.

### Fixed

- `navree dev` on Linux restarted the server again and again with nothing edited: it took a file being opened or read (the server reading `.env` as it starts, `cargo build` reading `Cargo.toml`) for an edit. Only edits start a rebuild now, and a server busy writing `storage/` no longer delays one.

### Security

- The development install of `@navree/nuxt` takes node-forge 1.4.3, for the four advisories fixed in it. Only Nuxt's development HTTPS certificates use it; the published package does not depend on it.
- The fuzzing workspace takes rustix 1.1.6, for RUSTSEC-2026-0486; the main workspace already had it.

### Changed

- Dependencies: the minor and patch updates of the Rust crates and of the front-end packages.

## Navree 1.0.0

Navree is a framework for complete applications in Rust: the API, the background work, the screens and the tools that run them, in one binary. It is open source under MIT or Apache-2.0 and free to self-host. Every crate, the `navree` command-line tool, the starter kits and the `@navree/*` npm packages share one version number, and [the versioning page](/docs/prologue/versioning-and-support/) says what you can rely on across 1.x.

### Install it

```sh
cargo install navree-cli
navree new blog
```

You need Rust 1.95 or newer. Navree runs on Linux, macOS and Windows, with PostgreSQL (TimescaleDB by default), MySQL and MariaDB, SQLite or MongoDB. To add it to a project you already have, run `cargo add navree`. [Installation](/docs/getting-started/installation/) has the details for each system.

### Design decisions

- **Tokens for APIs, sessions for pages.** API clients get short-lived access tokens and rotating refresh tokens. A backend-for-frontend keeps them in httpOnly cookies for a separate web front end, and server-drawn pages use an encrypted session cookie with CSRF protection.
- **One error shape.** Every error is JSON in one shape, `{ "statusCode", "message", "error", "code" }`, with `errors` for validation failures. The `code` is stable, so a front end can translate it.
- **Real time is built in.** An in-process server speaks the Pusher protocol, and processes that don't serve sockets broadcast through it over a signed relay.
- **Routes deny by default.** A route without an access declaration does not compile.

### Security limits

Everything that reads untrusted input has limits you can state:

- **Connections.** The server bounds slow headers, slow bodies, idle connections, responses a client stops reading and connections per address ([Connection limits](/docs/getting-started/deployment/#connection-limits)).
- **Requests.** Body, form, multipart and WebSocket frame sizes are capped, a path that cannot be routed unambiguously is a 400, and the per-address rate limit counts an IPv6 client by its network.
- **Documents.** CSV, XLSX and the other spreadsheet formats, PDFs, images, Word files and inbound mail are read under limits on size, shape, nesting and work, and a file past a limit is refused with a clear message ([Imports and exports](/docs/packages/imports-and-exports/), [Documents](/docs/packages/documents/), [Inbound mail](/docs/digging-deeper/inbound-mail/)).
- **Rich text.** Input is sanitised by a configurable policy that caps the size and depth of what it reads ([Validation](/docs/basics/validation/)).
- **Outgoing requests.** The HTTP client refuses private addresses unless you allow them, and secrets in URLs stay out of logs and errors ([HTTP client](/docs/digging-deeper/http-client/)).
- **Pages.** A strict content security policy on every page: scripts, styles and requests from the page's own origin only ([Navree UI](/docs/ui/overview/)).
- **The supply chain.** Dependency advisories, licences and sources are checked on every change, every lockfile is scanned, and a fuzz target covers every parser of untrusted input.

### Known limits

- Access tokens are stateless, so signing out ends them when they expire, 15 minutes by default. Revocable access tokens are on the [roadmap](/docs/prologue/roadmap/).
- Queues run on the database, memory and Redis drivers. Other backends are on the roadmap.
- The `serve`, `queue:work` and `schedule:work` commands run under systemd and similar supervisors. Windows services are on the roadmap.
- `navree dev` restarts the server when your code changes, so requests fail for the moment of the restart.
- The SQLite driver bundles SQLite 3.53, which can return stale memory when it opens a database file together with a `-wal` file that someone else wrote ([RUSTSEC-2026-0459](https://rustsec.org/advisories/RUSTSEC-2026-0459)). Don't open SQLite files from untrusted sources. Run `cargo update` once sqlx 0.9.1 is released to get SQLite 3.54 or later.

What comes next is on the [roadmap](/docs/prologue/roadmap/).
