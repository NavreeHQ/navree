Navree is a framework for building complete applications in Rust: the API, the background work, the screens and the tools that keep it all running. It gives you an application architecture out of the box: features live in modules, modules declare what they import and export, and a dependency-injection container wires them together when the app boots, refusing to start if anything is missing. Around that structure sits everything a product needs, from routing and validation to workspaces, queues, monitoring and AI, designed together, documented together and released together. The code stays quick to test, safe to change and clear to whoever reads it next: a new teammate, or an AI agent.

You choose how to draw the screens. [Navree UI](/docs/ui/overview/) renders typed Rust components to HTML on the server, in the same binary as your API. A Next.js (React) or Nuxt (Vue) app can sit beside the API instead; [Choosing a UI](/docs/ui/choosing-a-ui/) says what each costs and gives. And if you already have a product or a design, two agent skills bring it into Navree: [Bring your product](/docs/getting-started/bring-your-product/) and [Bring your design](/docs/getting-started/bring-your-design/).

Navree runs on [Tokio](https://tokio.rs), [Hyper](https://hyper.rs) and [Tower](https://docs.rs/tower), works with data through its own [ORM](/docs/orm/getting-started/), which writes its SQL and runs it on [sqlx](https://docs.rs/sqlx) connections, validates input with its own `#[derive(Validate)]` rules, speaks TLS through rustls and hashes passwords with Argon2id. A whole application compiles to one binary.

This documentation describes Navree 1.2. The [release notes](/docs/prologue/release-notes/) list what it ships, and the [roadmap](/docs/prologue/roadmap/) says where it goes next.

## What Navree stands for

- **Modular by design.** Every feature is a module that declares what it imports, provides and exports. Apps stay navigable at five modules or five hundred.
- **Dependency injection.** A type-keyed container wires services at boot and refuses to start with a missing or private dependency, naming the module and the type.
- **API-first.** Versioned routes, validated input, one JSON error shape and an OpenAPI 3.1 document generated from your code.
- **Type-safe end to end.** Requests, queries, jobs, events and configuration are typed. If it compiles, it's wired.
- **Secure by default.** Routes deny until you allow them. Rotating refresh tokens, two-factor, Argon2id, encrypted cookies, CSRF, rate limits, security headers, an audit log and an SSRF guard ship on.
- **Workspaces built in.** Multi-tenancy at the workspace level: members, roles, invitations, and isolation by row, schema or database.
- **AI-native.** Agent skills, an MCP server for your coding agent, docs written for models as well as people, and an AI SDK for the product itself.
- **Screens your way.** Navree UI renders typed Rust components on the server with a strict content security policy, or a Next.js or Nuxt app sits beside the same API.
- **Observable.** Structured logs, traces, metrics, health checks and [Lighthouse](/docs/tools/lighthouse/) monitoring, self-hosted and on by default.
- **Scales out.** Start as one binary; split into services over NATS, Kafka, RabbitMQ, Redis Streams or gRPC without rewriting your modules.
- **Fast and frugal.** One binary, under 40 MB of memory under load and ready in milliseconds. [Performance](/performance/) has the measurements and how to reproduce them.

## What a Navree app looks like

An app is a root module that lists its modules, each configured once:

```rust title="src/app.rs"
pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(LoggerModule::from_config())
        .module(CryptoModule::from_config())
        .module(HttpModule::from_config())
        .module(DatabaseModule::from_config())
        .module(QueueModule::from_config())
        .module(ValidationModule::from_config())
        .module(AuthModule::from_config())
        .module(AccessModule::for_root(AccessOptions {
            abilities: abilities::define,
            super_admin_role: Some("admin".to_owned()),
        }))
        // ...
        .module(modules::tasks::TasksModule)
}
```

A feature module declares what it provides:

```rust title="src/modules/tasks/mod.rs"
#[module(
    imports = [AccessModule::for_feature::<Task>()],
    providers = [TaskService],
    controllers = [TaskController],
    exports = [TaskService],
    register = Self::wire,
)]
pub struct TasksModule;
```

A controller's routes say who may call them, and the framework enforces it before the handler runs:

```rust title="src/modules/tasks/controller.rs"
#[controller("/tasks", version = "1")]
impl TaskController {
    #[patch("/{id}")]
    #[can(Update, Task, from = "id")]
    async fn update(
        &self,
        uow: Uow,
        task: Authorized<Task, Update>,
        Valid(Json(input)): Valid<Json<UpdateTask>>,
    ) -> Result<Json<Model>> {
        task.check_fields(&input.changed_fields())?;
        let task = self.tasks.update(&uow, task.into_inner(), input).await?;
        Ok(Json(task))
    }
}
```

This route answers `PATCH /api/v1/tasks/{id}`. Before the handler runs, Navree authenticates the bearer token, loads the task, checks that the user's abilities allow updating it, and validates the body. The handler's writes run in the request's transaction, which commits when the response succeeds. [Your first app](/docs/getting-started/your-first-app/) builds this module from scratch.

## What's in the box

### The framework

Each module is its own crate, and the `navree` crate re-exports all of them, one Cargo feature each. The default `full` feature turns them all on.

| Area | Modules |
|---|---|
| Foundation | The kernel (module graph, dependency injection, lifecycle hooks, commands); typed configuration from `.env`, TOML files and `APP_*` variables; structured logging with redaction |
| HTTP | Controllers and route attributes on Navree's own router, deny-by-default access declarations, one JSON error shape (`{ "statusCode", "message", "error", "code" }`) with stable, translatable error codes, rate limits, CORS and security headers, signed URLs, maintenance mode |
| Validation | `#[derive(Validate)]` rules and `Valid<T>` extractors, one readable message per broken rule, async `unique` and `exists` rules |
| Database | An ORM with typed queries, relationships and eager loading, casts, events, scopes, soft deletes, factories and test helpers; a unit of work per request; per-module migrations written with a schema builder, seeders and pagination; TimescaleDB by default (PostgreSQL with hypertables), plain PostgreSQL, MySQL and MariaDB (through the same driver), SQLite (a file, with nothing to install), and MongoDB through a document driver |
| Security | JWT access tokens with rotating refresh tokens, pluggable authentication strategies, registration, password reset, email verification and two-factor authentication; roles, permissions and abilities with record checks and SQL list filters, shared with the front end; AES-256-GCM encryption and Argon2id hashing; an audit log |
| Workspaces | Workspaces, members, roles and invitations; the current workspace from a header, a subdomain, a path or a token; isolation by row, schema or database |
| Background work | Database and memory job queues with retries, backoff, unique and delayed jobs; events with synchronous and queued listeners; a scheduler on cron expressions that runs each task once across servers |
| Communication | Mail from templates over SMTP and the SES, Mailgun, Postmark and Resend APIs; notifications over mail, the database and broadcasts; a WebSocket server that speaks the Pusher protocol, with public, private and presence channels |
| Integrations | File storage on named disks with signed temporary URLs; an HTTP client with retries, timeouts, an SSRF policy and fakes; a cache with tags and locks; templates |
| Operations | Health and readiness probes, Prometheus metrics, an OpenAPI 3.1 document with a docs UI |
| Testing and tools | `TestApp` and an in-process test client with fakes; the `navree` CLI with `navree new`, code generators and a rebuilding dev server |

### Navree UI

[Navree UI](/docs/ui/overview/) is the `ui` feature of `navree`, on by default. A handler returns typed components and the toolkit renders them to HTML, with one stylesheet, a small runtime that loads only what a page uses, and a strict content security policy. It brings [forms](/docs/ui/forms/) from a validated struct, the [app shell](/docs/ui/app-shell/), a server-side [DataTable](/docs/ui/data-table/), [dates and times](/docs/ui/dates/), [themes](/docs/ui/themes/), a [live hub](/docs/ui/live-hub/) that tells pages what changed, and the [components](/docs/components/overview/), each with a live preview. It grows one module at a time: [Coming next](/docs/ui/coming-next/) lists what is still to come, in order. For a React or Vue front end, see [Next.js](/docs/frontend/nextjs/) and [Nuxt](/docs/frontend/nuxt/).

## Who Navree is for

Navree is for teams that build applications and want the structure decided before the first line of code:

- **API and product teams** building JSON APIs for web and mobile front ends, with users, permissions, background jobs, mail and real time.
- **SaaS builders** who need workspaces, billing, feature flags and an admin panel on day one, not in month six.
- **Systems that grow.** Start as a modular monolith and split modules into services when the load or the team calls for it. The [architecture patterns](/docs/patterns/overview/) show each shape.
- **Rust developers** who would rather build the product than choose, wire and maintain a dozen crates for every new service.
- **Teams that work with AI agents.** Every app has the same layout, every feature has an [agent skill](/docs/ai/agent-skills/), and [Navigator](/docs/ai/navigator/) lets the agent read your routes, modules and schema.
- **Teams with a product or a design already.** An agent skill rebuilds an old product, with its data, as a Navree app, and another turns a design into Navree UI pages. See [Bring your product](/docs/getting-started/bring-your-product/).

## How to read these docs

- **Getting started** installs Navree and builds a small API with authentication, access rules and tests. Start with [Your first app](/docs/getting-started/your-first-app/).
- **Architecture concepts** explains how an app is put together: the [request lifecycle](/docs/architecture/request-lifecycle/), [modules](/docs/architecture/modules/) and [providers](/docs/architecture/providers/). Read it once; everything else builds on it.
- **Architecture patterns** shows the shapes of system you can build: modular monolith, microservices, multi-tenant SaaS, event-driven, API-first and backend-for-frontend.
- **The basics, Security, Workspaces, Database and Digging deeper** are the reference, one page per feature. Read them when you need the feature.
- **UI and UI components** cover Navree UI, from [choosing a UI](/docs/ui/choosing-a-ui/) to every component; **Front end** covers Next.js and Nuxt.
- **Microservices, AI, Packages and Tools** cover the ecosystem.
- **Testing** and the **Example application** show how it all comes together.

A <Badge feature="queue" /> badge at the top of a page or section names the Cargo feature of `navree` it needs. Every page is also available as Markdown for AI agents: see [Docs for agents](/docs/ai/docs-for-agents/).
