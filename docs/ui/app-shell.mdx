The app shell gives every page of an app the same frame: a sidebar of grouped links, a top bar with a sidebar button and the breadcrumb, then the page with its title, actions and body. You define the shell once; each handler takes the `AppShell` extractor and returns an `AppPage`. The preview is drawn 1,100 px wide and scaled to the column; open it on its own to see it at full size, and narrow the window to see the phone layout.

```rust title="src/shell.rs"
use navree::ui::*;

pub fn shell() -> Shell {
    Shell::new("Cloudworks CRM")
        .context("Production")
        .group(
            NavGroup::new("Sales")
                .item(NavItem::new("Deals", "/deals").icon(icons::HANDSHAKE).count("312"))
                .item(NavItem::new("Contacts", "/contacts").icon(icons::USERS)),
        )
        .user(
            UserMenu::new("Gurpreet Singh", "gurpreet@example.com")
                .link("Profile", "/profile")
                .action("Sign out", "/sign-out"),
        )
}
```

## Registering it

Register the shell as a provider, and every handler can take `AppShell`: the shell applied to the request, with the current link marked, the sidebar collapsed or not, and any toast the last page left.

```rust title="src/app.rs"
m.factory(Factory::<Shell>::new(|_| async { Ok(Arc::new(shell())) }))
    .exports::<Shell>();
```

```rust title="src/deals/pages.rs"
async fn show(shell: AppShell) -> AppPage {
    shell
        .page("Sutlej Supply renewal")
        .crumb("Deals", "/deals")
        .actions(Button::primary("Edit").href("/deals/42/edit"))
        .body(Card::titled("Notes").body(Text::new("Two-year term, same price.")))
}
```

A module that serves pages of its own and has no business registering a shell for the whole app, such as a debugging tool, builds its own `Shell` and applies it with `Shell::for_request(path, &headers)`, which does what the extractor does, except drawing the links other modules add (`Shell::contributed`): those need the request's reader, so only the `AppShell` extractor draws them.

### The person and the workspace of a request

The shell you register is the whole app's, so what belongs to one request is set on the `AppShell` the extractor gives: `AppShell::context(text)` puts the line below the app's name for this request (the workspace's name) in place of `Shell::context`, and `AppShell::user_menu(menu)` puts the person signed in at the foot. The app's one `Shell` stays as it is. An app made by `navree new` does both in one extractor, `Desk`, in `src/ui/shell.rs`:

```rust title="src/ui/shell.rs"
let shell = AppShell::from_request_parts(parts)
    .await?
    .context(workspace.name.clone())
    .user_menu(menu.action("Sign out", "/sign-out"));
```

A `Desk` from an app made before 1.3 clones the registered `Shell`, sets `.context(..)` and `.user(..)` on the clone and applies it with `Shell::for_request`. It still works, but it draws none of the [links other modules add](#links-other-modules-add). To draw them, take `AppShell::from_request_parts(parts)` in place of the clone and `for_request`, set `.context(..)` and `.user_menu(..)` on it as above, and add `.contributed()` to the shell you register.

## On a phone

Below 768 px the sidebar is off-canvas. The top bar keeps its button, and pressing it slides the sidebar over the page as a sheet and moves the focus to its first link. Tapping outside the sheet, following one of its links or pressing `Esc` closes it. The page itself gets the whole width. ## The sidebar

- **Width:** 16 rem open, 3 rem collapsed to its icons. Give every top-level item an icon: the collapsed sidebar shows only that. A theme of your own sets the open width, the sidebar's insets and the gap between its blocks, its links' height, and the top bar's height and padding with the [sizes](/docs/ui/themes/#sizes) of its shape.
- **Collapsing:** the top bar's button and `Ctrl+B` (`Cmd+B` on a Mac) toggle it. The choice is kept in a cookie, so the next page renders the same way with no flash.
- **Phones:** below 768 px it becomes a sheet that slides over the page.
- **Items:** `.count(text)` puts a count at the end, `.sub(item)` nests an item under another, and `.current(true)` marks a link as the current page when several differ only in their query.
- **The user menu:** `.link` adds a page to read; `.action` adds a button that posts, for signing out or switching workspace. It works with JavaScript off and carries the session's CSRF token when there is one.
- **For one request:** `AppShell::user_menu(menu)` puts the person signed in at the foot, `AppShell::context(text)` sets the line below the app's name, `AppShell::header_slot(node)` puts something under the app's name, one gap between the sidebar's blocks below it (a workspace switcher, which `SwitcherVariant::Card` draws as a card lined up with the links' rows; `Shell::header_slot` for every page), and `AppShell::csrf(token)` gives the shell's own forms the session's token. The app's one `Shell` stays as it is.
- **Counts that come later:** `NavGroup::lazy(id, src)` makes a group a region fetched once the page is up, so a page never waits for its counts; `Shell::live_group(id, path)` draws the answer, the group with its counts. The source is an address on your site: one that is not a `LocalHref` (or is `#`) leaves the group with no source, and it is never fetched.
- **Your mark:** `Shell::logo(src)` draws a picture of yours in place of Navree's; see [the brand row](#the-brand-row).

## The brand row

The sidebar opens with the app's mark and name, linking home (`Shell::home`), and a line under the name (`Shell::context`: a workspace, a plan). The name is drawn in the `brand` style of the theme's [type scale](/docs/ui/themes/#type).

- **Your mark:** `Shell::logo(src)` draws a picture of yours in place of Navree's: a path on the app, an `https://` URL, or an [`AppImage`](/docs/ui/app-styles/#pictures) the toolkit serves. It is decorative, beside the app's name.
- **A dark mark:** `Shell::logo_dark(src)` is the mark on a dark sidebar, for a mark drawn for a light one. A page in light or in dark draws the one it needs; a page that follows the device draws a `<picture>`, and the browser picks the dark source with `prefers-color-scheme`.
- **A bare mark:** the mark stands in a 32 px tile of the theme's raised colour. `Shell::logo_style(LogoStyle::Bare)` draws it alone, 22 px, with no tile: the row is 30 px high, with 8 px at its sides and 10 px between the mark and the name.
- **A badge:** `Shell::badge(badge)` puts a [badge](/docs/components/badge/) at the end of the row, in place of the context line: a marker such as "Internal" or "Staging". `AppShell::badge(badge)` sets one for a request, in place of the shell's: the pages of a staff area. It hides with the name when the sidebar folds.

```rust
Shell::new("Kesar")
    .logo("/brand/kesar.svg")
    .logo_dark("/brand/kesar-dark.svg")
    .logo_style(LogoStyle::Bare)
    .badge(Badge::new("Internal").variant(BadgeVariant::Solid))
```

A bare or dark mark and a badge are drawn by the shell parts stylesheet, which a page links only when it draws one of them.

## The sidebar's foot

The person signed in stands at the foot of the sidebar: `Shell::user(menu)`, or `AppShell::user_menu(menu)` for a request. Their name is drawn in the `sidebar_user` style of the theme's [type scale](/docs/ui/themes/#type) and the line under it in the shell's muted text (the `shell_muted` [colour role](/docs/ui/themes/#colour-roles)).

- **Their picture:** `UserMenu::avatar(avatar)` draws an [avatar](/docs/components/avatar/) of yours in place of the person icon: their initials, round, or their photo.
- **The chevron:** `UserMenu::chevron(false)` leaves out the chevron at the end of the row. The row opens the menu either way, and tells assistive technology that it does.
- **Above the person:** `Shell::footer_slot(node)` puts something 12 px above the person, such as a tile with the plan's seats and a button to add some; `AppShell::footer_slot(node)` sets one for a request, in place of the shell's. It hides with the names when the sidebar folds, and a shell without one draws no box for it.

```rust
async fn home(shell: AppShell, person: Person) -> AppPage {
    shell
        .footer_slot(Card::titled("Seats").body(Stat::new("Left", "8 of 20")))
        .user_menu(
            UserMenu::new(person.name.clone(), person.email.clone())
                .avatar(Avatar::initials(person.name.clone()).shape(AvatarShape::Circle))
                .chevron(false)
                .action("Sign out", "/sign-out"),
        )
        .page("Home")
}
```

## Only what a reader may use

A button that answers "no" should not have been drawn. With the `access` feature, `navree::ui::ability` asks the reader's [abilities](/docs/security/authorization/) before the page draws a navigation item, a bulk action, a row action or any other part. `Requires::requires(action, subject)` gates a part, and `ByAbility` (implemented for `Ability`, which the `Abilities` extractor derefs to) keeps what the reader may see:

```rust
use navree::ui::ability::{ByAbility, Requires};
use navree::ui::{BulkAction, NavItem};

let items = ability.only([
    NavItem::new("Deals", "/deals").requires("read", "Deal"),
    NavItem::new("Reports", "/reports").requires("read", "Report"),
]);
let actions = ability.only([
    BulkAction::new("archive", "Archive").requires("update", "Deal"),
    BulkAction::new("delete", "Delete").requires("delete", "Deal"),
]);
```

`show` keeps one part or drops it, and `nav_group(group, items)` returns the group with the items the reader may use, or `None` when none are left, so an empty group is not drawn. The check is on the kind of subject, so a reader who may edit some deals sees the Edit button; the server still decides each record, and a route's guard refuses a request the page should not have offered.

## Links other modules add

A module, a plugin's among them, adds links to the app's sidebar with `m.nav_item(..)`, and asks for a [permission](/docs/security/authorization/#describing-permissions) a link needs. The module below is a plugin's, and belongs in the plugin's own crate (`navree-plugin-announcements`): `m.plugin(navree::plugin_info!(..))` names the crate it is written in, so pasted into an app's crate it would treat every subject of the app as the plugin's. A module of the app adds links the same way, without `m.plugin`:

```rust
use navree::plugin::Permission;
use navree::plugin::prelude::*;
use navree::prelude::*;
use navree::ui::{ShellNavItem, icons};

struct Announcements;

impl Module for Announcements {
    fn register(&self, m: &mut ModuleBuilder) {
        m.plugin(navree::plugin_info!(title = "Announcements"))
            .permissions(&[
                Permission::new("announcements.read", "Read the workspace's announcements"),
                Permission::new(
                    "announcements.publish",
                    "Publish an announcement to the workspace",
                ),
            ])
            .nav_item(
                ShellNavItem::new("Announcements", "/announcements")
                    .icon(icons::MEGAPHONE)
                    .permission("announcements.read"),
            )
            .nav_item(
                ShellNavItem::new("New announcement", "/announcements/new")
                    .permission("announcements.publish")
                    .order(-1),
            )
            .nav_item(ShellNavItem::new("Notice board", "/notice-board"));
    }
}
```

The app draws them by building its shell with `Shell::contributed()`: `Shell::new("Kesar").contributed()`. Without it the shell draws only its own groups, whatever modules add. The links come after the shell's own groups and are never merged into them. Each goes in the group it names with `.group(..)`, else in a group with the plugin's title, else in **More**; the groups come in the order of their first link, and inside a group the links come by `.order(n)`, lower first, then in the order the modules added them. A group none of whose links the reader may open is not drawn.

A link with a permission is drawn only for a reader who holds it, app-wide or in the workspace the request names, decided on the server for every request. A link without `.permission(..)` is public: every reader sees it, a guest too. Hiding a link is not access control: the page it leads to declares its own access, and a route without one fails the boot.

What that costs, and two readers who see only the links granted app-wide:

- Each link with a permission is one permission check per request, on every page drawn in the shell and every call of `GET /_navree/ui/navigation`; in a workspace each check reads the workspace and the reader's role there again, so keep such links few.
- A demo workspace's guest (`workspace.demo.guest_role`) holds no permission through that role, so a link that needs one is drawn for them only when it is granted app-wide.
- With `workspace.session_default`, a browser that has not chosen a workspace yet sees only the links granted app-wide, unless the handler takes `CurrentWorkspace` (or the starter kit's `Desk`) before `AppShell`, which gives it its first workspace.

An address that is not a path of the app (another site, a relative path, an empty one) stops the boot, and a link that asks for a permission no module describes with `m.permissions` is warned about at boot.

A front end that draws its own sidebar asks `GET /_navree/ui/navigation`, with the reader's cookie, for the same links: those the caller may open, and nothing about the others. Each link's icon comes as its view box and shapes, or `null`:

```json
{"items": [{"label": "Notice board", "href": "/notice-board", "group": "Announcements", "order": 0, "icon": null}]}
```

The answer is never kept by a cache (`Cache-Control: private, no-store`), and the route exists only when a module adds a link.

## Layouts and folding

`Shell::layout` places the navigation: a docked sidebar (the default), `ShellLayout::Inset` with the page in a card beside the sidebar, `ShellLayout::Floating` with the sidebar as a card, or `ShellLayout::Header` with the links in the top bar and each labelled group as a menu. `Shell::collapse` sets what folding does: `Collapse::Icons` (the default), `Collapse::Offcanvas` to slide it away, or `Collapse::Never`. On a phone every layout puts the links in a sheet. See [Themes](/docs/ui/themes/#layouts) for each one drawn.

`Shell::theme_menu()` adds the reader's theme and mode to the top bar; see [Themes](/docs/ui/themes/#the-theme-menu). An app that offers one theme (`Shell::themes([brand])`) has nothing to choose there, so the menu holds the modes only.

With `ShellLayout::Header` the app's mark and name stay in the top bar on a phone too, beside the menu button. `Shell::logo` takes the mark: a path, or an [`AppImage`](/docs/ui/app-styles/#pictures) the toolkit serves.

## The middle of the top bar

`AppPage::topbar(node)` puts what belongs to this page and this request in the middle of the top bar: a pager between days that depends on the day shown, a switch between views. It stands centred in the bar, between the navigation and the bar's own controls, and stays on a phone.

```rust
async fn today(shell: AppShell, day: Day) -> AppPage {
    shell
        .page(day.greeting())
        .topbar(DayPager::new("day", day.label()).previous(day.before_href()))
        .body(day.cards())
}
```

## The top bar and the page header

The top bar starts with the sidebar's button and a separator, then the breadcrumb, and ends with the shell's search and theme menu. The page header holds the title and the page's actions.

- **Actions in the top bar:** `AppPage::topbar_actions(nodes)` puts a detail page's buttons at the end of the top bar, before the search and the theme menu. On a phone too narrow for them they scroll sideways inside the bar, and the page never does.
- **The last crumb:** the breadcrumb ends with the page's title. `AppPage::current_crumb(label)` names it otherwise ("LDH-1" over a page titled "LDH-1, Ludhiana"), and `AppPage::current_crumb_mono()` draws it in the mono face, for a name that is a code. The heading and the browser's tab keep the title. The breadcrumb's size and its last part's weight are the `breadcrumb` style of the theme's [type scale](/docs/ui/themes/#type).
- **Beside and under the title:** `AppPage::title_aside(nodes)` puts badges after the title, on its line and wrapping under it when there is no room; `AppPage::subtitle(text)` puts a line of the shell's muted text 6 px under it.
- **In a native app:** the screen a native client draws takes the page's subtitle as its own, and the top bar's actions after the page's own actions, in its one row of actions.
- **The title's face:** `AppPage::title_face(Face::Mono)` draws the title in another face than the theme's page title takes: an invoice's number, a code.
- **No fold button:** with `Collapse::Never` the button is gone on wide screens, and the separator after it goes with it.

```rust
async fn invoice(shell: AppShell, invoice: Invoice) -> AppPage {
    shell
        .page(invoice.number.clone())
        .title_face(Face::Mono)
        .crumb("Invoices", "/invoices")
        .current_crumb_mono()
        .title_aside((
            Badge::new("Paid").variant(BadgeVariant::Success),
            Badge::new("Annual"),
        ))
        .subtitle("Wholesale · Ludhiana")
        .topbar_actions((Button::ghost("Download invoice"), Button::outline("Pause")))
}
```

What these draw is in the shell parts stylesheet, and the mono crumb in the parts stylesheet; a page links them only when it draws one.

## The title in the tab

The page's heading is also its title in the browser's tab, unless you say otherwise. `Shell::title_template("{} · Kesar")` writes every title through a template, `{}` standing for the page's own, and `AppPage::document_title("Today")` titles a page whose heading is a greeting ("Good evening, Simran") by what it is. Both keep the heading as it is.

## Fetched ahead of a click

Nothing is fetched ahead of a click unless you ask, link by link. `NavItem::prefetch()` fetches a sidebar item when the pointer rests on it or it takes focus, so the page is often there before the click; `NavItem::prefetch_eager()` fetches it as soon as the page is quiet. `AppPage::prefetch_crumbs()` does the same for a page's breadcrumb, and `Shell::prefetch_home()` for the app's name. Each costs a request the user may never need, so ask only for the places users usually go next, and only for pages whose `GET` changes nothing.

## Keyboard and accessibility

<UiA11y>

| Key | Does |
|---|---|
| `Ctrl+B`, `Cmd+B` | Collapses or expands the sidebar. |
| `Tab` | Moves through the sidebar, the top bar, then the page. |
| `Esc` | Closes the sidebar sheet on a phone. |

- The current page's link has `aria-current="page"`; the sidebar button has `aria-expanded`.
- The page is a `<main>` with `id="main"`, and the title is its `<h1>`.
- Every page has a labelled region for [toasts](/docs/components/toast/), and a toast left for the next page is already in it, so it shows with JavaScript off too.
