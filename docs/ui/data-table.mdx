`DataTable` draws rows from a query, and `#[derive(TableRow)]` on one struct says what can be done with each column. The same definition parses the URL into a `TableQuery`, builds the query through navree-orm with an allow-list, draws the table, exports CSV and checks bulk actions. Sort, filters, the page, the page size, hidden columns, widths and density live in the URL, so back, forward, reload and a shared link restore them, and it all works with JavaScript off. The [store example app](/showcase/store/) pages lakhs of orders with one.

```rust title="src/deals/table.rs"
#[derive(Clone, TableRow)]
#[table(sort = "-amount", per = 5, per_pages(5, 25, 100))]
pub struct Deal {
    #[col(skip)]
    pub id: i64,
    #[col(sortable, search, sticky, filter = text, link = "/deals/{id}", label = "Deal")]
    pub title: String,
    #[col(sortable, hide_on_mobile)]
    pub company: &'static str,
    #[col(badge = tone)]
    pub stage: &'static str,
    #[col(sortable, numeric, filter = range, label = "Amount (₹)")]
    pub amount: Money,
    #[col(sortable, filter = date, label = "Closes")]
    pub closes_on: chrono::NaiveDate,
}
```

In a handler, `TableQuery<Deal>` is an extractor. With the `ui` and `orm` features of `navree` (both on by default), `query.load` runs it on a model that derives `TableRow` itself. `query.load_as` maps each model record to a separate row type when the rows join or rename fields:

```rust title="src/deals/pages.rs"
async fn index(shell: AppShell, uow: Uow, query: TableQuery<Deal>) -> Result<AppPage> {
    let page = query.load(Deal::query(), &uow).await?;
    Ok(shell.page("Deals").body(DataTable::new("deals", &query, &page).caption("Deals")))
}
```

The previews on this page draw five rows from memory with `TablePage::new(rows, total)`, which is what `load` returns.

## Pages, not thousands of rows

Keep a table paged. 25 rows to a page is the default, and `per_pages` lets a reader choose another size. Each sort, filter or page is then one small request, and the browser redraws 25 rows. Measured on a slow phone (4x CPU, Slow 4G), a sort of a 25-row page took about 310 ms, the request included. A page holding 1,000 rows took 1.2 s to sort by a column of numbers, though it sorted them in the browser with no request: that time is the browser laying out a thousand rows, and nothing makes it shorter but fewer rows. The numbers, and how they were taken, are under [Speed](#speed).

## Columns

| Column option | Means |
|---|---|
| `sortable`, `search`, `filter = text\|range\|date\|select\|multi\|boolean\|relation` | what can be done with it; `kind = int` (or `text`, `money`, `float`, `decimal`, `date`, `datetime`, `bool`, `uuid`) when filter values bind as another type than the field's; `source = "companies.name"` when the column has another name |
| `sticky`, `sticky_end`, `hidden`, `locked`, `hide_on_mobile`, `width = 240`, `group = "Address"` | where it sits |
| `numeric`, `align = center`, `strong`, `truncate`, `wrap`, `link = "..."`, `badge = tone`, `options = LIST` | how it reads; `badge = tone` names a function that takes `&value` and returns the badge's `BadgeVariant`, and `options = LIST` shows the label of the matching `(value, label)` pair |

| On the table | Means |
|---|---|
| `#[table(cursor)]` | keyset pages, for huge tables |
| `#[table(capped = 10000)]`, `#[table(no_count)]` | count no further than this; or don't count, with Previous and Next only |
| `#[table(version = "col")]` | a column that changes with a row, compared before a bulk action |

## Columns a person may not use

`#[col(hidden)]` says how a column starts. It is not a permission. The table reads every column its definition lists, so a URL can show a hidden column with `cols=pay`, filter on it with `filter[pay][gte]=1`, sort by it with `sort=pay` and search it, and what comes back tells the person about a column the page never drew.

Where the handler knows what the person may do, take the column away for that request with `TableQuery::without_columns`, or name the columns they may use with `only_columns`:

```rust title="src/staff/pages.rs"
use navree::ui::{TableQuery, TableRow};

#[derive(Clone, TableRow)]
pub struct Employee {
    #[col(skip)]
    pub id: i64,
    #[col(sortable, search)]
    pub name: String,
    #[col(sortable)]
    pub city: String,
    #[col(sortable, numeric, hidden, label = "Pay (₹)")]
    pub pay: i64,
}

/// What a person may use of the staff table.
fn for_person(query: TableQuery<Employee>, may_see_pay: bool) -> TableQuery<Employee> {
    if may_see_pay {
        query
    } else {
        query.without_columns(["pay"])
    }
}
```

A column taken away is gone from every part of the table for that request: the columns shown and the column menu, the filters (a filter on it is ignored, as one on a column the table does not have is), the sort, the search, the filter bar, the widths, a saved view when it is applied, the cells of each row and the CSV export. The table never writes its name into a link it makes. Names that are not columns of the table are ignored, so one list of sensitive names can serve several tables, and calls add up: a column that was taken away stays taken away. With `only_columns` a misspelt name lets nothing in, where with `without_columns` it takes nothing away.

Make the same call on the `BulkRequest` of the table's bulk action, so that "all that match" selects by the filters the table was drawn with, and on the `ViewPost` before a view is saved:

```rust title="src/staff/pages.rs"
use navree::ui::BulkRequest;

fn bulk_for_person(request: BulkRequest<Employee>, may_see_pay: bool) -> BulkRequest<Employee> {
    if may_see_pay {
        request
    } else {
        request.without_columns(["pay"])
    }
}
```

## The URL

A table reads and writes the same list-query names as the API, so a link to a table and a request to the API are written alike. What each operator means, and how a Rust endpoint reads the query, is on the [list queries](/docs/basics/list-queries/) page. The [typed client](/docs/frontend/typed-client/#list-queries) page covers the JavaScript side.

```text
/deals?filter[stage][in]=won,lost&filter[amount][gte]=500000&search=sutlej&sort=-amount&page=2&per_page=25
```

| Column filter | In the URL |
|---|---|
| `text` | `filter[title][contains]=sutlej` |
| `select` | `filter[stage]=won` |
| `multi`, `relation` | `filter[stage][in]=won,lost` |
| `boolean` | `filter[active]=true` |
| `range`, `date` | `filter[amount][gte]=1&filter[amount][lte]=9` |
| empty | `filter[owner][null]=true` |

- **Search and order.** `search=text` is the box above the table. `sort=-amount,title` sorts by up to four columns, and `-` means descending. `sort=` with nothing after it asks for no order.
- **Pages.** A numbered table reads `page` and `per_page`; a `#[table(cursor)]` table reads `cursor`, `before` and `limit`. Each table ignores the other's names. The page size is always one the table offers. A cursor table's `cursor` and `before` are its own page state in the page's URL, written by its paging links: they are not the `next_cursor` and `prev_cursor` of a JSON `CursorPage`, and the two need not match.
- **Its own state.** `cols`, `w`, `fb`, `density`, `open` and `count` belong to the table and are not part of the list query.
- **Forgiving.** A table shows a page whatever the URL says. A value of the wrong kind, a column the definition doesn't list, or an operator a filter doesn't take is left out. The API answers the same mistakes with a 400 that names the parameter.

## Selection and bulk actions

`.bulk(url, actions)` adds a checkbox to each row and a bar of actions for the selection. The selection is kept per tab: ticked rows survive paging, sorting and filtering, and "all that match" survives paging and sorting and takes exclusions. An action posts the selection and the count the user saw; `BulkRequest::resolve` runs the same definition on your scoped query and refuses when the count or a row's version differs.

<UiPreview example="data-table/bulk" />

```rust title="src/deals/pages.rs"
async fn bulk(uow: Uow, request: BulkRequest<Deal>) -> Result<Reply> {
    let target = match request.resolve(Deal::query(), &uow).await? {
        Ok(target) => target,
        Err(refusal) => return Ok(request.refused(StatusCode::CONFLICT, refusal.message())),
    };
    let count = target.delete(&uow).await?;
    Ok(request.done(format!("Deleted {count}.")))
}
```

## Counts and amounts in lakhs and crores

The count under the table (`Showing 1 to 25 of 12,34,567 results`) and the cells of a `Money` column group their digits as `TableLabels::grouping` says: by thousands (`1,234,567`) by default, in lakhs and crores (`12,34,567`) with `Grouping::Indian`. A table that takes its words from navree-i18n (`TableLabels::from_locale(&locale)`) gets the grouping of the locale: `en-IN` and `hi` group in lakhs, `en` and `de` by thousands. To set it yourself:

```rust
let labels = TableLabels { grouping: Grouping::Indian, ..TableLabels::default() };
DataTable::new("deals", &query, &page).labels(&labels)
```

`Money::display_grouped(Grouping::Indian)` writes one amount the same way (`12,34,567.50`), and `Money::parse` reads either grouping back.

## Sorting in the browser

When a page holds every row of its result (the first page, with nothing after it), a click on the heading of a column of numbers or dates sorts the rows in the browser at once, and the heading's arrow moves with them. The runtime still follows the link, and the server's answer has the last word: it confirms the order and redraws the rest of the table. While it is on its way the table isn't marked busy, since it already shows the answer.

The browser sorts only what it can order exactly as the database does: numbers and dates whose cells show the value the column holds, empty cells first, ties by key in the column's direction. Every cell of such a column carries its value, so a cell drawn with `.cell(name, fn)` sorts by the value, not by what it shows. Text asks the server, since a database orders it by its own collation (case, accents), and so does a column that shows something other than what it sorts by, such as a company's name for a company id. An order by several columns, filters and search always ask the server. If the server can't answer, the rows, the headings and the table's form go back to the last order it confirmed.

## Several sticky columns at the end

`sticky` keeps a column at the start while the table scrolls sideways, and `sticky_end` keeps one at the end. A table can hold several of each (the stylesheet places up to four of each from its own edge), and the row's menu, when the table has one, is the last of the end columns. A column is `sticky` or `sticky_end`, not both.

## Searching words in a big table

The search box matches the text anywhere in a column marked `search` (`SearchMode::Contains`, the default). It works on every database with no index, and no index can serve it, so the whole table is read: fine to some tens of thousands of rows, and about a quarter of a second at a million on MySQL 8.4 for a word a tenth of the rows hold (0.6 s for a word only one row holds, since every row is still read; the medians `apps/ui-table-proof/tests/search_million_sql.rs` measures). `SearchMode::Words` matches the words of the text in any order through the database's full-text index: in the same test it finds a word one row of a million holds in about 4 ms, counts the 100,000 rows that hold a common word in about a quarter of a second, and holds a counted words search under two seconds. It finds words, not fragments (`renew` does not find `renewal`), and SQLite has no full-text condition, so there it is an error at load.

```rust
let query = TableQuery::<Customer>::parse("/customers", raw_query)
    .search_mode(SearchMode::Words);
```

Create the index in a migration. On PostgreSQL it is a text-search index. On MySQL and MariaDB it is a `FULLTEXT` index over exactly the `#[col(search)]` columns, in the same order: `FULLTEXT (title, notes)` for `title` and `notes`. When a searched column is [taken away](#columns-a-person-may-not-use) from the person asking, a words search reads the columns left as plain text, since the index also covers the column that is gone.

## Typing and choosing

A tick in a filter's list, a radio and a select apply at once. The search box and text filters wait for a pause in the typing: 100 ms, or what `.debounce(wait)` says, up to 5 s, for a search the database is slow to answer.

| `.prefetch()` | fetches the table's own links (sort, page, filter chips, details) when the pointer rests on one, so the next state is often there before the click; off unless asked |

## Saved views

`.views(&views, url)` adds a Views menu: a link for each view a person saved, and a form that saves the table's current state under a name. A view is a name and a query string, so applying one is following a link, and it goes through the same allow-list as any URL. `list_views`, `save_view` and `delete_view` keep the views in the table `navree_ui_table_views` (a collection of that name on MongoDB), found by an owner string and a table id that you give them.

The owner is whatever you scope views by, and the table knows nothing more of it: two people with the same owner string share their views. In an app with workspaces, put the workspace into the owner, so that each workspace's people have views of their own and a person who belongs to two workspaces keeps two sets:

```rust,ignore
use navree::db::Uow;
use navree::http::StatusCode;
use navree::ui::Reply;
use navree::ui::table::{TooManyViews, ViewOp, ViewPost, delete_view, save_view};

async fn views(
    uow: Uow,
    workspace: CurrentWorkspace,
    user: CurrentUser,
    post: ViewPost<Deal>,
) -> Result<Reply> {
    // The workspace is in the owner: these are the person's views in this workspace.
    let owner = format!("{}:{}", workspace.id, user.id);
    let text = match post.op() {
        ViewOp::Save => {
            let saved = save_view(&uow, &owner, "deals", post.name(), post.query(), post.is_default())
                .await;
            if let Err(error) = &saved
                && let Some(full) = TooManyViews::of(error)
            {
                return Ok(post.refused(StatusCode::UNPROCESSABLE_ENTITY, full.to_string()));
            }
            saved?;
            "View saved."
        }
        ViewOp::Delete => {
            delete_view(&uow, &owner, post.view()).await?;
            "View deleted."
        }
    };
    Ok(post.done(text))
}
```

An owner keeps at most 50 views of one table (`MAX_SAVED_VIEWS`). `save_view` refuses another with `TooManyViews` and writes nothing, not even a change of the default; `ViewPost::refused` answers the form with the reason, as above, and if you let the error go up it is the 500 any error from the store is. `list_views` shows at most 200. The count is read before the view is written, so two views that one owner saves in the same instant can both be saved when one place was left. Where columns are [taken away](#columns-a-person-may-not-use) from a person, make the same call on the `ViewPost` before saving, so that no view holds one.

## Exporting

`.export(url)` adds a link that carries the table's state to a route of yours, and `TableQuery::export_csv(builder, &uow, "deals.csv", map)` answers it with a CSV file of the current search, filters, sort and columns. It reads from your scoped query inside the request's unit of work, a chunk at a time, and keeps what it has written in memory only up to 8 MiB before it goes to a temporary file.

- **How many rows.** At most 100,000 (`DEFAULT_EXPORT_ROWS`). A result with more rows is cut there, and the response carries `x-navree-truncated: 1`. `query.export_limit(500_000)` raises the limit for one route, up to `MAX_EXPORT_ROWS` (2,000,000), which nothing passes. A result of exactly the limit is not cut, and says nothing.
- **In which order.** In the page's sort order, as long as every column of the sort is a column of the table being read. A sort by a column of a joined table (`source = "companies.name"`) writes the file in the order of the key instead, so it is not in the order the page showed. An export never pages by `OFFSET`: it goes on from the position of the last row it wrote, so the millionth row costs what the first does.
- **Which columns.** The columns shown, less any [taken away](#columns-a-person-may-not-use) from the person asking.

An export holds a unit of work, a connection and a temporary file for as long as it takes to write, and Navree does not limit how many run at once. Throttle the route that serves it, and keep it behind the sign-in and the ability that lets a person export. A route's throttle is on the [rate limiting](/docs/basics/rate-limiting/) page:

```rust
use std::time::Duration;

use http::Method;
use navree::http::RouteDef;

RouteDef::on(Method::GET, "/deals/export", || async { "the file" })
    .authenticated()
    .throttle(5, Duration::from_secs(60))
```

## Limits

- **One table per URL.** Its state lives in plain query parameters, so two tables on one page would share it: give the second its own route or [region](/docs/ui/regions/).
- **NULL is the smallest value on every store:** ascending puts NULLs first, descending last. On PostgreSQL, index such a column as `(col NULLS FIRST, id)`.
- **Huge tables** want an index per sort column, ending in the key. A search or text filter is `contains`, which reads every row unless the column has a trigram index on PostgreSQL. On numbered pages, a row added or deleted between pages moves what follows by one; `#[table(cursor)]` pages don't.
- **Stored views** are kept where the rows are: the table `navree_ui_table_views` on an SQL database, which you create in a migration, and the collection of that name on MongoDB, which MongoDB creates with the first view (index `(owner, table_id)` for a long list). An owner keeps at most 50 per table; see [Saved views](#saved-views).
- **A row's actions** are links, or a small form each, inside the row. If you draw your own controls in a cell, keep it that way: a submit button in every row tied to one form by `form=` makes Chromium recount the form's controls across the page for each one that moves, which on a phone costs most of a second per sort at 1,000 rows.

## Speed

Measured on the proof app's table, with a box, a menu of two actions and details on every row, over SQLite. Chromium, driven by Playwright with DevTools throttling; medians of five runs. The slow phone is 4x CPU and Slow 4G (150 ms latency, 1.6 Mbit/s). On the Windows laptop these ran on, a 4x setting slows page work more than four times, so read the order of the numbers rather than the decimals.

| Rows on the page | Sort | Tick a filter | Last key of a search | Next page | Open a row's details |
|---|---:|---:|---:|---:|---:|
| 25, paged (the default) | 314 ms | 309 ms | 398 ms | 327 ms | 279 ms |
| 100, paged | 533 ms | 582 ms | 409 ms | 493 ms | 340 ms |
| 1,000, all of them, sorted by a number in the browser | 1.2 s | 1.3 s | 409 ms | | 526 ms |
| 11, all of them, sorted by a number in the browser | 37 ms | | | | |

On a desktop with no throttling, a 25-row page sorts in 43 ms, a tick filters it in 44 ms, the last key of a search shows its result in 153 ms (100 of them the pause the table waits for), and a page of 1,000 rows sorts by a number in 228 ms.
