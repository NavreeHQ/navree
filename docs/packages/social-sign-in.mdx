## Quick start

The smallest setup: turn the feature on, list one provider and add the module after `AuthModule`. The rest of the page explains each part.

```toml title="Cargo.toml"
navree = { version = "1", features = ["social"] }
```

```toml title="config/app.toml"
[social]
redirect_base = "https://app.sutlej.example/auth/callback"

[social.providers.github]
client_id = "Iv1.8a61f9b3a7aba766"
```

```env title=".env"
APP_SOCIAL__PROVIDERS__GITHUB__CLIENT_SECRET=4f1c0e7b9a...
```

```rust
// src/app.rs, after AuthModule:
.module(SocialModule::from_config()) // section `social`
```

The module needs `HttpClientModule` and the database. Register `{redirect_base}/github` as the callback URL with GitHub. [How the flow works](#how-the-flow-works) shows the calls your backend-for-frontend makes.

## Introduction

<Badge feature="social" /> Many people would rather click "Continue with Google" than invent another password. `navree-social` adds that button to your app without changing how the rest of it works: a social sign-in ends with the same Navree user and the same access and refresh tokens as a [password login](/docs/security/authentication/), so every route, permission and audit entry behaves as before.

It covers the whole flow:

- **Providers:** Google, GitHub, Apple, Microsoft, GitLab (including self-hosted), Slack, LinkedIn, Discord and X built in, any OpenID Connect provider by its issuer URL, and your own through a trait.
- **A safe redirect:** the state parameter is sealed with your application key and carries a PKCE verifier and, for OpenID Connect, a nonce. It expires after 10 minutes and works once.
- **Verified identities:** ID tokens are checked against the provider's published keys (signature, issuer, audience, expiry and nonce) before Navree trusts them.
- **Linked accounts:** one user can sign in with a password, GitHub and Google. Accounts are linked automatically only when the provider has verified the email address and the user's own address is verified too.
- **Navree tokens:** the callback answers exactly like `POST /api/auth/login`, two-factor challenge included.
- **Native apps:** Sign in with Apple and Google from the system's own sheet on iPhone and Android, with a one-time nonce per attempt, and Apple's tokens revoked when the account is deleted, as the App Store requires.
- **Provider tokens** (optional), encrypted at rest and refreshed for you, for apps that call the provider's API later, such as syncing meetings from Google Calendar into CRM activities.

## Installation

Turn on the `social` feature of the `navree` facade. It is opt-in: the default `full` feature leaves it out.

```toml title="Cargo.toml"
[dependencies]
navree = { version = "1", features = ["social"] }
```

Add `SocialModule` after `AuthModule`. It calls the providers through the [HTTP client](/docs/digging-deeper/http-client/), so include `HttpClientModule`:

```rust title="src/app.rs"
Navree::app()
    .module(ConfigModule::for_root(sources))
    .module(CryptoModule::from_config())      // seals states, encrypts tokens
    .module(HttpModule::from_config())
    .module(HttpClientModule::from_config())
    .module(DatabaseModule::from_config())
    .module(CacheModule::from_config())       // remembers used states
    .module(AuthModule::from_config())
    .module(SocialModule::from_config())      // section `social`
    // ...
```

`CacheModule` is optional: without it, used states are remembered in the process, which is enough for a single instance. With several instances, give the cache a shared store so a state used on one instance is refused on the others.

The module contributes the migration set `social` (after `auth`), which creates `social_accounts`: one row per linked provider account, with the user, the provider, the provider's user id, the email, name, avatar and handle it reported, and the encrypted provider tokens when you store them. Deleting a user deletes their rows. The table is a navree-orm model, `social_account::Model`, so apps can read it with `social_account::Model::query()` and its typed columns such as `social_account::Model::PROVIDER`; the module's own writes record change events without the encrypted tokens.

## Configuration

Register an OAuth app with each provider, then list the providers in the `social` section. Each provider's callback URL is `{redirect_base}/{provider}`; register that exact URL with the provider:

```toml title="config/app.toml"
[social]
redirect_base = "https://app.acme.test/auth/callback"  # the front end's page
link_by_email = "verified"                             # verified | never

[social.providers.github]
client_id = "Iv1.8a61f9b3a7aba766"

[social.providers.google]
client_id = "481203-k2l9.apps.googleusercontent.com"
hosted_domain = "acme.test"   # optional: only this Google Workspace

[social.providers.microsoft]
client_id = "0f6c1d2e-8a3b-4c5d-9e7f-1a2b3c4d5e6f"
tenant = "organizations"      # common | organizations | consumers | <tenant id>
```

Client secrets go in `.env`:

```env title=".env"
APP_SOCIAL__PROVIDERS__GITHUB__CLIENT_SECRET=4f1c0e7b9a...
APP_SOCIAL__PROVIDERS__GOOGLE__CLIENT_SECRET=GOCSPX-7Hk2...
APP_SOCIAL__PROVIDERS__MICROSOFT__CLIENT_SECRET=Q8a8Q~mX2...
```

A provider without a `client_id`, an unknown provider type, a `redirect_base` that isn't an absolute URL, an Apple key that can't be read or a `custom` provider that isn't registered fails the boot, naming the key. Provider keys are lower-case letters, digits, `-` and `_`, and can't be `accounts` (that is a route). `SocialModule::for_root(SocialOptions { .. })` takes the same options in code.

### Providers

| Key | Provider | Notes |
|---|---|---|
| `google` | Google | OpenID Connect. `hosted_domain` limits sign-in to one Google Workspace domain (the `hd` claim is checked). |
| `github` | GitHub | Reads the primary verified email from the emails API. `url` and `api_url` point at GitHub Enterprise Server. |
| `apple` | Sign in with Apple | Needs `team_id`, `key_id` and `private_key` (the `.p8` key); Navree signs the ES256 client secret for you. Apple posts the callback (`response_mode=form_post`) and sends the name only on the first sign-in, in the `user` field; pass it on, and Navree stores it then. Apps on Apple's systems use the [native sign-in](#sign-in-from-native-apps). |
| `microsoft` | Microsoft Entra ID and personal accounts | `tenant` picks who may sign in. Microsoft lets account owners set their email address, so it counts as verified only with the `xms_edov` optional claim. |
| `gitlab` | GitLab | `url` for a self-hosted instance (default `https://gitlab.com`). |
| `slack` | Slack | OpenID Connect; `team` limits sign-in to one workspace (team id). |
| `linkedin` | LinkedIn | OpenID Connect. |
| `discord` | Discord | Only verified emails link accounts. |
| `x` | X | Add the `users.email` scope to read the confirmed email address. |

Any other OpenID Connect provider (Okta, Auth0, Keycloak, Zitadel, your company's SSO) works by its issuer. Navree reads its discovery document when the app starts, and again on first use if the provider couldn't be reached then. A document that names another issuer is refused:

```toml
[social.providers.okta]
type = "oidc"
name = "Okta"                        # shown in errors and in the accounts list
issuer = "https://agra.okta.com"
client_id = "0oa8f2kq1xYz3AbC4d5e"
scopes = ["openid", "profile", "email", "groups"]
```

Each provider asks for the scopes it needs to read a name and an email. Add more with `scopes`; they are requested in addition to the defaults. Every provider gets a PKCE challenge (S256) unless you set `pkce = false` for it.

How Navree reads the user:

- **Google, Apple, Microsoft and `oidc` providers:** from the ID token, verified against the provider's JSON Web Key Set (RS256, RS384, RS512, PS256, PS384, PS512, ES256, ES384 or EdDSA, never HMAC or `none`). Key sets are fetched over TLS and kept as long as the provider's `Cache-Control: max-age` says (between five minutes and a day; an hour without one), and fetched once more when a token names a key id the set lacks, at most every 30 seconds. That fetch runs apart from the others: a token signed with a key the cached set has is verified without waiting for it, and tokens that need the fetch share one. When the ID token has no email, Google and `oidc` providers fill it in from their userinfo endpoint.
- **GitLab, Slack and LinkedIn:** from their userinfo endpoints, with the access token.
- **GitHub, Discord and X:** from their APIs.

## How the flow works

<Diagram name="backend-for-frontend" />

Navree's auth is token-based and a browser app keeps the tokens in its [backend-for-frontend](/docs/patterns/backend-for-frontend/) (BFF), so a social sign-in runs through the BFF too:

1. The sign-in page links to a BFF route, say `/auth/social/github`. The BFF calls `GET /api/auth/social/github/redirect`, stores the returned `state` in a short-lived httpOnly cookie and redirects the browser to `url`.
2. The user approves at GitHub, and GitHub sends the browser to `https://app.acme.test/auth/callback/github?code=...&state=...`.
3. The BFF's callback page checks that the `state` in the URL equals the one in its cookie. That check binds the flow to this browser, so nobody can sign a victim into the attacker's account.
4. The BFF posts `{code, state}` to `POST /api/auth/social/github/callback` and gets the same answer as a login: it stores the tokens in its cookies, as it does for a password login, and sends the browser on to the app.

Apple posts `code`, `state` and `user` to the callback page instead of adding them to the URL, so that page accepts a `POST`, and the state cookie must be sent on that cross-site post (`SameSite=None; Secure`).

The first call:

```http
GET /api/auth/social/github/redirect?return_to=/deals HTTP/1.1
```

```json wrap
{
  "url": "https://github.com/login/oauth/authorize?response_type=code&client_id=Iv1.8a61f9b3a7aba766&redirect_uri=https%3A%2F%2Fapp.acme.test%2Fauth%2Fcallback%2Fgithub&scope=read%3Auser+user%3Aemail&state=nvs1.Bq2...&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256",
  "state": "nvs1.Bq2..."
}
```

The callback:

```http
POST /api/auth/social/github/callback HTTP/1.1
Content-Type: application/json

{ "code": "6f0a3d1e9b2c8f7a4e5d", "state": "nvs1.Bq2..." }
```

```json
{
  "user": { "__type": "User", "id": "01a17748-e211-72fc-abb3-836e604457d0", "name": "Anu Lakhotia", "email": "anu@example.com", "email_verified_at": "2026-10-26T08:17:07Z", "created_at": "2026-10-26T08:17:07Z" },
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh_token": "01a17748-e21b-71c6-97cf-968b61f8e6b3.1ug0BGRxe4Fa...",
  "token_type": "Bearer",
  "expires_in": 900,
  "return_to": "/deals"
}
```

`return_to` comes back from the sealed state, and only relative paths are accepted (`/deals`, never `https://...` or `//...`), so it can't send the browser to another site. A native app that signs in through the system browser (`ASWebAuthenticationSession`, Android's Custom Tabs) follows the same two calls; Sign in with Apple on Apple's systems and Sign in with Google on Android use the system's own sheet instead, as the [next section](#sign-in-from-native-apps) shows.

What can go wrong:

| Answer | `code` | When |
|---|---|---|
| 400 `Invalid or expired state` | `invalid_state` | The state was changed, issued for another provider or another app, has expired, or was used already |
| 400 `GitHub refused the sign-in: ...` | `provider_refused` | The provider refused the code (`invalid_grant`, `access_denied`, ...) |
| 400 `Google sent an invalid ID token` | `invalid_id_token` | The ID token's signature, issuer, audience, expiry or nonce is wrong |
| 400 `GitHub did not share an email address` | `missing_email` | A new user would be created, but the provider shared no email |
| 403 | `sign_in_not_allowed` | Another Google Workspace or Slack workspace, or an email outside `allowed_email_domains` |
| 403 `Registration is closed` | `registration_closed` | No matching user, and registration is off |
| 409 | `email_taken` | The email belongs to a user and linking doesn't apply: `link_by_email = "never"`, an address the provider didn't verify, or a user whose own address isn't verified yet (see [linking accounts](#linking-accounts)) |
| 403 | `sso_required` | The address or the account belongs to a domain that enforces [single sign-on](/docs/security/single-sign-on/#enforcement) (or another [sign-in policy](/docs/security/authentication/#sign-in-policies) refused it) |
| 429 | `too_many_login_attempts` | Too many callbacks from this address, or from this IPv6 network, a /64 by default (`auth.login_throttle_per_minute`, with `Retry-After`; see [IPv6 clients](/docs/basics/rate-limiting/#ipv6-clients)) |
| 502 | `provider_unavailable` | The provider couldn't be reached |

Every answer carries its `code` in the [error body](/docs/basics/errors/#error-codes), so your sign-in page can tell "registration is closed" from "use your work address" in the user's language.

## Sign-in from native apps

On a phone, Sign in with Apple and Sign in with Google don't go through a browser redirect. The system shows its own sheet (Apple's `ASAuthorizationController`, Android's Credential Manager) and hands the app a signed identity token, which the app posts to your server. Navree verifies the token and signs the person in exactly as the web callback does: the same linking rules, sign-in policies, two-factor challenge, events and audit entries.

The apps' ids come from the [association files' section](/docs/security/passwordless/), `auth.apps`, so you configure them once:

```toml title="config/app.toml"
[social.providers.apple]
client_id = "com.sutlej.orders.web"   # the Services ID of the web flow
team_id = "ABCDE12345"
key_id = "KEY1234567"                 # private_key from .env

[social.providers.google]
client_id = "481203-k2l9.apps.googleusercontent.com"  # the web client id

[auth.apps.apple.main]
team_id = "ABCDE12345"
bundle_id = "com.sutlej.orders"
```

- **Apple:** an identity token from an app is for its bundle id, so the audiences accepted are the `bundle_id`s of `auth.apps.apple`. Without an Apple app there, native Sign in with Apple answers 404 `native_sign_in_unavailable`.
- **Google:** the Android app passes the Google provider's `client_id` (the web client id) to Credential Manager as its server client id (`GetGoogleIdOption.Builder().setServerClientId(..)`), so that is the audience accepted. It is offered only when the site lists an Android app in `auth.apps.android` (`[auth.apps.android.main]` with its `package` and `fingerprints`): without one, native Sign in with Google answers 404 `native_sign_in_unavailable`, as Apple's does without an Apple app, and Google is the web flow only. On iPhone, sign in with Google through the system browser and the web flow.

### What the app sends

1. **Ask for a nonce** before showing the sheet:

   ```http
   POST /api/auth/social/apple/native/nonce HTTP/1.1
   ```

   ```json
   { "nonce": "Xk3v9Qm2...", "state": "nvs1.Bq2...", "expires_in": 300 }
   ```

   The `state` is the attempt, sealed like the web flow's: it is for this provider, expires after `expires_in` seconds (five minutes, or `social.state_ttl_secs` when shorter) and works once. Nothing is stored on the server.

2. **Show the sheet with the nonce.** Google takes it as it is (`setNonce(nonce)`). Apple takes its SHA-256, in lower-case hex (`request.nonce = sha256Hex(nonce)`); Apple puts the value it was given in the token, and the server compares that hashed form.

3. **Post the token with the state:**

   ```http
   POST /api/auth/social/apple/native HTTP/1.1
   Content-Type: application/json

   {
     "id_token": "eyJraWQiOiJXNldjT0tC...",
     "state": "nvs1.Bq2...",
     "authorization_code": "c3b1f2e0a9d84c...",
     "user": { "name": { "firstName": "Simran", "lastName": "Gill" } }
   }
   ```

   `authorization_code` (Apple only) is the credential's `authorizationCode`; see [revoking](#revoking-tokens-and-deleting-accounts). `user` carries the name Apple hands the app on the first sign-in only (`fullName`): it is used as a display name and never to find or link an account, and any email in it is ignored (the token's counts). Google posts `id_token` and `state` only.

The answer is the callback's: the user with an access and a refresh token, or the two-factor challenge.

An app that keeps navree-session's session cookie instead of tokens (feature `session`) posts the same body to `POST /api/auth/social/{provider}/native/session`, with the session's CSRF token as `X-XSRF-TOKEN` (`"remember": true` keeps it signed in for `auth.session.remember_days`). The session gets a new id and a new CSRF token, and the answer is the user, or `{"two_factor_required": true}`, finished with `POST /api/auth/session/2fa/verify`.

### What the server checks

The attempt is used up first (sealed by this app, for this provider, not expired, not used before), then the token:

- its signature, against the provider's published keys (Apple's `/auth/keys`, Google's certificates);
- its issuer (`https://appleid.apple.com`, `https://accounts.google.com`);
- its audience: one of the apps' ids above, nothing else (a token Apple made for another app, or for the web flow's Services ID, is refused);
- its expiry, and that it was issued after the attempt started and not in the future, with a minute's tolerance;
- its nonce: the attempt's (Apple's in the hashed form). A token taken from one attempt can't be posted with another, and an attempt can't be posted twice.

Each failure is a 400 `invalid_id_token` (or `invalid_state` for the attempt), and the post counts against `auth.login_throttle_per_minute` like the callback. A malformed post is a 400 `validation_failed` naming the fields. Then the [linking rules](#linking-accounts) apply as they are: an unverified email never links to an existing account, and an account whose own address isn't verified is never linked. Apple's private relay addresses (`...@privaterelay.appleid.com`) are verified ones.

`Social::native_nonce(provider)` and `Social::native_user(provider, &NativeSignIn)` are the routes' two steps, for your own routes: pass the user to `sign_in` (or `sign_in_session` with the feature `session`).

### Revoking tokens and deleting accounts

The App Store requires that an app offering account creation lets people delete their account in the app, and that deleting an account that used Sign in with Apple revokes its tokens with Apple. When the app sends `authorization_code`, Navree exchanges it at Apple's token endpoint with a client secret it signs for the app's bundle id (ES256, from the `.p8` key), checks that the ID token Apple returns names the same person, and keeps the refresh token encrypted in `social_accounts`, with the client it was issued to. When the site has an Apple app in `auth.apps.apple`, Sign in with Apple's tokens are kept whatever `store_tokens` says, from the web flow too, because revoking them needs them. A site with no Apple app keeps tokens only with `store_tokens`.

They are revoked at Apple (with `client_id` the bundle id or the Services ID they belong to), and the stored copies forgotten, when:

- the person disconnects Apple (`DELETE /api/auth/social/accounts/apple`, `Social::unlink`): an Apple that can't be reached answers 502 and leaves the account linked, to try again;
- you call `Social::revoke_tokens(user_id)`;
- you offboard the user with `AuthService::revoke_all_credentials(user_id)` (or `revoke_credentials_of_domain`): the module takes part as a credential revoker (kind `social_provider_tokens`);
- a magic link or an emailed code [gives an account whose address was never verified](/docs/security/passwordless/#proving-the-mailbox-of-an-unverified-account) to its mailbox's owner: the tokens are revoked as above, and the provider accounts linked to the user are then unlinked as well (kind `social_accounts`), so none of them signs in to it.

Stored Google tokens (`store_tokens`) are revoked the same way, at `https://oauth2.googleapis.com/revoke` (the provider's `url` changes the host). A token the provider no longer knows counts as revoked.

The call to the provider is made before your unit of work reads or writes anything, so no transaction waits on it. Only a provider that can't answer now (no connection, a `5xx`, `408` or `429`) stops the operation: it answers 502 (`provider_unavailable`) and nothing changes. A token the provider refuses for good (any other `4xx`, such as `invalid_client` after the key it was issued under was revoked), or one that can no longer be decrypted, is logged, audited as `social.token_revocation_refused` (with the provider, the status and the provider's error code), and forgotten all the same: the account is disconnected, or the offboarding goes on.

Navree has no account-deletion route of its own. Yours revokes first, then deletes the user (the `social_accounts` rows go with it):

```rust title="src/modules/account/controller.rs"
#[delete("/account")]
#[recent_auth]
async fn delete(&self, uow: Uow, CurrentUser(user): CurrentUser) -> Result<NoContent> {
    // Every session, token and Apple grant of the user ends first.
    self.auth.revoke_all_credentials(user.id).await?;
    User::query().where_key(user.id).delete(&uow).await?;
    Ok(NoContent)
}
```

### Apple's notifications

Apple tells your server when a person stops using Sign in with Apple with your app, deletes their Apple account or changes mail forwarding. Register `https://<your site>/api/auth/social/apple/notifications` as the server-to-server notification endpoint of your App ID. Apple posts `{"payload": "<JWS>"}`; Navree checks the signature against Apple's keys, the issuer, the audience (the Services ID or one of the bundle ids), that it is less than seven days old and that its `jti` wasn't handled before, then acts on the account it names:

| `type` | What Navree does |
|---|---|
| `consent-revoked` | Forgets the stored Apple tokens and signs the user out everywhere; the account stays linked |
| `account-deleted` | Removes the link (`social.unlinked`) and signs the user out everywhere. A user left with no way to sign in is yours to handle |
| `email-disabled`, `email-enabled` | Records it: mail to the private relay address stops or starts reaching the person |

Each emits `SocialProviderNotice` and is audited (`social.consent_revoked`, `social.account_deleted`, `social.email_disabled`, `social.email_enabled`). A forged or stale notification is a 400 `invalid_notification`; one about nobody linked here is accepted and ignored. `Social::receive_notification(provider, payload)` does the same in your own route.

## Linking accounts

When someone signs in with a provider, Navree looks for their user in this order:

1. **A linked account.** A `social_accounts` row for this provider and provider user id signs in its user, and is updated with what the provider reported this time.
2. **The same verified email.** With `link_by_email = "verified"` (the default), a user whose email matches an email the provider has **verified** gets the account linked, and is signed in, as long as the user's own address is verified too (`email_verified_at` is set). An unverified email never links: anyone can type any address into some providers. Neither does an account whose own address was never verified: someone may have registered it with a password before its owner came, and linking would sign the owner in to that account. The sign-in is refused with the 409 below and audited as `social.link_refused`. The owner proves the address first (the [verification link](/docs/security/account-flows/#email-verification), a [magic link or an emailed code](/docs/security/passwordless/)) and signs in with the provider again. A user that a social sign-in created has a verified address when the provider verified it, so a second provider with that address links.
3. **A new user.** With `social.registration` on (it defaults to `auth.registration`), Navree creates the user with the provider's name and email, marks the email as verified when the provider did, links the account and signs them in. The user has no password until they set one through [password reset](/docs/security/account-flows/#password-reset). A provider that shares no email address can't create a user (400).
4. **Otherwise** the callback answers 409, so the person signs in with their password and connects the provider from their settings (a person whose address is not verified yet verifies it first):

```json
{ "statusCode": 409, "message": "An account with this email already exists. Sign in, then connect GitHub in your settings.", "error": "Conflict", "code": "email_taken" }
```

With registration off and no matching user, the answer is 403 `Registration is closed`. Restrict who may sign up through a provider with `allowed_email_domains = ["acme.test"]`, per provider or for the whole section: only a verified address in one of those domains may sign in or sign up.

### Two-factor authentication

A user with [two-factor authentication](/docs/security/account-flows/#two-factor-authentication) gets the same challenge from the callback as from a password login (`two_factor_required`, `challenge_token`, `expires_in`), and finishes with `POST /api/auth/2fa/verify`. Set `social.two_factor = "skip"` to trust the provider's own second factor instead.

### Single sign-on and sign-in policies

A social sign-in asks navree-auth's [sign-in policies](/docs/security/authentication/#sign-in-policies) twice, with the method `Social { provider }`: about the address the provider reported, before any account is created or linked, and about the account, before the session or the two-factor challenge. When an organization [enforces single sign-on](/docs/security/single-sign-on/#enforcement) for `agra.com`, a Google or GitHub sign-in as `anu@agra.com` answers 403 `sso_required`, creates nothing, and a provider account linked earlier to an `@agra.com` user no longer signs them in. The refusal is audited as `auth.login_refused` with `metadata.provider`.

### Connecting and disconnecting providers

Signed-in users manage their providers with three routes:

| Route | Does |
|---|---|
| `GET /api/auth/social/accounts` | The user's linked accounts: `provider`, `provider_name`, `email`, `name`, `avatar_url`, `linked_at` |
| `POST /api/auth/social/{provider}/link` | `{code, state}` from a flow started with `GET .../redirect?intent=link`; links the account to the signed-in user (201) |
| `DELETE /api/auth/social/accounts/{provider}` | Disconnects the provider (204), revoking its stored tokens at Apple or Google first |

`GET .../redirect?intent=link` needs the user's access token too (401 without it): the state is sealed for that user, so only they can finish the link, and a link state can't sign anyone in. A signed-in user can connect a provider whether or not their own address is verified: the rule about verified addresses in [linking accounts](#linking-accounts) is for sign-ins that find a user by address. Linking an account that already belongs to another user is a 409 (`account_already_linked`), and so is connecting a second account of a provider the user has already connected (`provider_already_connected`). Disconnecting the last way a user can sign in (no password and no other provider) is a 409 too (`last_sign_in_method`), so nobody locks themselves out; disconnecting a provider that isn't connected is a 404 (`provider_not_connected`).

## Using the Social service

The routes are built on the `Social` service. Use it directly when you want your own routes, a different response or extra checks:

```rust title="src/modules/sso/controller.rs"
use navree::auth::{ClientMeta, LoginOutcome};
use navree::prelude::*;
use navree::social::{Social, SocialCallback, SocialRedirect};

#[injectable]
pub struct SsoController {
    social: Arc<Social>,
}

#[controller("/sso", version = "1")]
impl SsoController {
    /// `GET /api/v1/sso/okta`: where to send the browser.
    #[get("/okta")]
    #[public]
    async fn redirect(&self) -> Result<Json<SocialRedirect>> {
        Ok(Json(self.social.redirect("okta").await?))
    }

    /// `POST /api/v1/sso/okta`: `{code, state}` from the callback page.
    #[post("/okta")]
    #[public]
    async fn callback(
        &self,
        meta: ClientMeta,
        Json(callback): Json<SocialCallback>,
    ) -> Result<Json<serde_json::Value>> {
        let profile = self.social.user("okta", &callback).await?;
        let groups = profile.raw["groups"].as_array().cloned().unwrap_or_default();
        if !groups.iter().any(|g| g == "crm-users") {
            return Err(AppError::forbidden().with_detail("Ask IT for access to the CRM"));
        }
        match self.social.sign_in(&profile, &meta).await? {
            LoginOutcome::Authenticated { user, tokens } => Ok(Json(serde_json::json!({
                "user_id": user.id,
                "access_token": tokens.access_token,
                "refresh_token": tokens.refresh_token,
            }))),
            LoginOutcome::TwoFactorRequired { challenge_token, .. } => Ok(Json(serde_json::json!({
                "two_factor_required": true,
                "challenge_token": challenge_token,
            }))),
        }
    }
}
```

A `SocialError` returned with `?` keeps its answer (400 for a bad state, 409 for the linking rules, and so on).

| Method | What it does |
|---|---|
| `redirect(provider)` | The provider's authorization URL and the sealed `state` |
| `redirect_with(provider, RedirectOptions { scopes, params, return_to, intent, user_id })` | The same with extra scopes, extra query parameters (`prompt=consent`), a return path and the intent; `Intent::Link` needs the `user_id` it links to |
| `user(provider, &callback)` | Checks the state, exchanges the code and returns the `SocialUser` |
| `sign_in(&social_user, &meta)` | Finds, links or creates the user and issues tokens: a `LoginOutcome` |
| `link(&uow, user_id, &social_user)`, `unlink(&uow, user_id, provider)` | Connects or disconnects a provider |
| `accounts(user_id)` | The user's linked accounts (`LinkedAccount`) |
| `find_user(provider, provider_user_id)` | The linked user, if any |
| `token(user_id, provider)` | A current provider access token (see below) |
| `native_nonce(provider)`, `native_user(provider, &post)` | The two steps of a [native sign-in](#sign-in-from-native-apps) |
| `sign_in_session(&session, &social_user, remember, &meta)` | `sign_in` on navree-session's session (feature `session`): a `SessionSignIn` |
| `revoke_tokens(user_id)` | Revokes the user's stored Apple and Google tokens at the provider and forgets them |
| `receive_notification(provider, payload)` | Acts on one of Apple's server-to-server notifications |
| `providers()`, `provider_name(provider)` | The configured provider keys and their display names, for a sign-in page |

`SocialUser` has `provider`, `id` (the provider's user id), `name`, `email`, `email_verified`, `avatar_url`, `nickname`, `token` and `raw`, the provider's whole profile as JSON (the ID token's claims, or the API's user object). Build one with `SocialUser::new(provider, id)` and `.name(..)`, `.email(Some(..), verified)`, `.avatar_url(..)`, `.nickname(..)`, `.token(..)` and `.raw(..)`.

`sign_in` and the token refresh join the request's unit of work in a handler; `link` and `unlink` take yours. Linking and disconnecting emit their events and audit entries after the commit.

## Calling the provider's API later

To call the provider on the user's behalf after sign-in (read their Google Calendar, post to their Slack), ask for the scopes and store the tokens:

```toml
[social]
store_tokens = true

[social.providers.google]
client_id = "481203-k2l9.apps.googleusercontent.com"
scopes = ["https://www.googleapis.com/auth/calendar.readonly"]
# Ask Google for a refresh token:
params = { access_type = "offline", prompt = "consent" }
```

Tokens are encrypted with the application key before they're written to `social_accounts`, at every sign-in and link. `token` returns a current access token, refreshing it first when it has expired or expires within a minute:

```rust
let google = social.token(user.id, "google").await?; // Secret<String>
let events = http
    .get("https://www.googleapis.com/calendar/v3/calendars/primary/events")
    .bearer(google.expose())
    .send()
    .await?;
```

When the provider refuses the refresh (the user revoked access) or no refresh token was stored, `token` returns `SocialError::Reauthorize`, and the account stays linked for sign-in. Without stored tokens it returns `SocialError::NoToken`, and for a provider the user hasn't connected, `SocialError::NotLinked`. Returned from a handler with `?`, they answer 409 `reauthorization_required`, 404 `no_provider_token` and 404 `provider_not_connected`, so the front end can offer "Connect Google again".

## Your own provider

A provider that speaks neither OAuth 2.0 with a standard profile endpoint nor OpenID Connect gets a `SocialProvider` implementation. Implement its key and the two steps:

```rust title="src/modules/sso/zoho.rs"
use navree::BoxFuture;
use navree::prelude::*;
use navree::social::{
    AuthorizeUrl, ProviderConfig, ProviderToken, SocialError, SocialProvider, SocialUser,
};

#[injectable]
pub struct Zoho {
    http: Arc<navree::http_client::HttpClient>,
}

impl SocialProvider for Zoho {
    fn key(&self) -> &'static str {
        "zoho"
    }

    fn authorize_url(&self, _config: &ProviderConfig, url: AuthorizeUrl) -> AuthorizeUrl {
        url.endpoint("https://accounts.zoho.com/oauth/v2/auth")
            .scopes(["AaaServer.profile.Read"])
    }

    fn user<'a>(
        &'a self,
        _config: &'a ProviderConfig,
        token: ProviderToken,
    ) -> BoxFuture<'a, Result<SocialUser, SocialError>> {
        Box::pin(async move {
            let profile: serde_json::Value = self
                .http
                .get("https://accounts.zoho.com/oauth/user/info")
                .bearer(token.access_token.expose())
                .send()
                .await?
                .json()?;
            Ok(SocialUser::new("zoho", profile["ZUID"].to_string())
                .name(profile["Display_Name"].as_str().unwrap_or_default())
                .email(profile["Email"].as_str(), true)
                .token(token)
                .raw(profile))
        })
    }
}
```

Register it with `.module(SocialModule::for_feature::<Zoho>())` and configure it under its key, `[social.providers.zoho]`, with `type = "custom"` and `token_url`. Navree still does the state, PKCE, code exchange (sending the client secret in the form), linking and token issuing. `authorize_url` receives the URL with Navree's parameters, the configured scopes and parameters already in place; `config` has the provider's whole configuration, endpoint overrides included.

## Events and audit entries

| Event | `NAME` | When |
|---|---|---|
| `SocialAccountLinked` | `social.linked` | A provider account was linked, at sign-in or from settings |
| `SocialAccountUnlinked` | `social.unlinked` | A provider account was disconnected (by the person, or by Apple's `account-deleted`) |
| `SocialProviderNotice` | `social.provider_notice` | Apple notified a change, after Navree acted on it; `notice` is `consent_revoked`, `account_deleted`, `email_disabled` or `email_enabled` |

All carry `user_id`, `provider` and `provider_user_id`, and are emitted after the change commits, when `EventsModule` is in the app.

With the [audit log](/docs/security/audit-log/), sign-ins are recorded as `auth.login` with `metadata.provider` (`auth.two_factor_challenge` when a second factor is due; `metadata.via = "session"` on the session cookie), new users as `auth.register` with `metadata.provider`, links as `social.linked` and `social.unlinked`, a link refused because the account's own address is not verified as `social.link_refused` (with `metadata.provider` and `metadata.reason = "email_unverified"`), a stored token the provider would not revoke as `social.token_revocation_refused`, and Apple's notifications as `social.consent_revoked`, `social.account_deleted`, `social.email_disabled` and `social.email_enabled`. Provider tokens, identity tokens, authorization codes and the Apple key are never recorded, logged or put in an error.

## Testing

`Social::fake()` returns a `Social` that never calls a provider, and a `SocialFake` that decides what each code returns. States are still sealed and checked, so your tests go through the same steps as production:

```rust title="tests/social.rs"
use navree::prelude::*;
use navree::social::{Social, SocialUser};
use navree::testing::TestApp;
use serde_json::json;

#[tokio::test]
async fn a_new_github_user_gets_an_account_and_tokens() {
    let (social, fake) = Social::fake();
    fake.on_code(
        "github",
        "code-anu",
        SocialUser::new("github", "583231")
            .name("Anu Lakhotia")
            .email(Some("anu@example.com"), true),
    );

    let app = TestApp::builder()
        .temp_database()
        .config("app.key", navree::crypto::generate_key())
        .config("social.redirect_base", "https://app.acme.test/auth/callback")
        .config("social.providers.github.client_id", "test")
        .module(CryptoModule::from_config())
        .module(DatabaseModule::from_config())
        .module(AuthModule::from_config())
        .module(SocialModule::from_config())
        .override_value(Arc::new(social))
        .build()
        .await;

    let redirect = app
        .client()
        .get("/api/auth/social/github/redirect")
        .send()
        .await
        .assert_status(200);
    let state = redirect.json_value()["state"].as_str().unwrap().to_owned();

    app.client()
        .post("/api/auth/social/github/callback")
        .json(&json!({ "code": "code-anu", "state": state }))
        .send()
        .await
        .assert_status(200)
        .assert_json_path("user.email", json!("anu@example.com"));

    // The state works once.
    app.client()
        .post("/api/auth/social/github/callback")
        .json(&json!({ "code": "code-anu", "state": state }))
        .send()
        .await
        .assert_error(400, "Invalid or expired state");
}
```

| `SocialFake` | Does |
|---|---|
| `on_code(provider, code, user)` | Answers a code with a profile |
| `on_code_error(provider, code, error)` | Answers a code with a provider error (`access_denied`): a 400 `GitHub refused the sign-in: access_denied` |
| `on_refresh(provider, token)` | Answers token refreshes for `Social::token`; without it a refresh is refused (`SocialError::Reauthorize`) |
| `exchanged()` | The `(provider, code)` pairs exchanged so far |
| `on_id_token(provider, id_token, user)` | Answers a native sign-in posting that identity token with a profile (the attempt's state is still checked) |
| `revocations()` | The `(provider, provider user id)` pairs whose stored tokens were revoked (disconnecting, offboarding) |

A code the fake doesn't know is refused with `invalid_grant`, as a provider would, and an identity token it doesn't know with `invalid_id_token`. The fake reads Apple's notifications without checking their signature. The fake skips an `oidc` provider's discovery document. To test a provider integration itself, keep the real `Social`, point the provider's endpoint keys (`url`, `authorize_url`, `token_url`, `userinfo_url`, `jwks_url`) at a local mock server, and let the HTTP client reach it (`http_client.ssrf.allow_hosts = ["127.0.0.1"]`).

| Key | Default | Meaning |
|---|---|---|
| `social.redirect_base` | none | Callback URLs are `{redirect_base}/{provider}`; required |
| `social.routes` | `true` | Mounts the `/api/auth/social` routes |
| `social.registration` | `auth.registration` | Creates users on a first sign-in |
| `social.link_by_email` | `verified` | `verified` links a user whose own address is verified when the provider verified the same address; `never` doesn't link |
| `social.allowed_email_domains` | `[]` | When not empty, only verified addresses of these domains may sign in or sign up |
| `social.two_factor` | `require` | `require` or `skip` for users with two-factor authentication |

| `social.providers.<key>.name` | the provider's name, or the key | Shown in messages and in the accounts list |

| Route | Access |
|---|---|
| `GET /api/auth/social/{provider}/redirect` | Public (signed in with `?intent=link`) |
| `POST /api/auth/social/{provider}/callback` | Public; counted by the login throttle |
| `POST /api/auth/social/{provider}/native/nonce` | Public (`apple`, `google`) |

| `POST /api/auth/social/{provider}/link` | Signed in |
| `DELETE /api/auth/social/accounts/{provider}` | Signed in |
