A PDF is untrusted input, so [Documents](/docs/packages/documents/) reads one within limits. This page is the reference for them: what each limit is, what it counts, and what happens at it. The limits are fixed in the code and are not configuration keys.

## Reading text

A PDF is untrusted input, so reading one has limits. They come from the `navree-pdf` crate (the `pdf` feature, which `documents` and `media` turn on), are fixed in the code like the other limits of `Pdf`, and are not configuration keys.

Reading text, a page may take 128 MiB of work and the whole document 1 GiB. Everything the reader does is charged where it happens, so nothing a file can make it do is free. Work is the content decoded, counting a form again every time it is drawn; 256 bytes for each page, 4 for each operation whatever its operator, 16 more for each that shows text, 16 for each character code shown whether it reads as anything or not, 32 for each `Do` and 1 KiB more when it draws a form, and past eight operands a byte for every 32 of the memory they hold; 32 bytes for each object looked up, read before or not, through however many references; every byte a filter reads and writes on the way, and 1 KiB for each filter, whether the content turns out to be usable or not; the fonts the page reads: 1 KiB for each font read, the first time or again after it was dropped (below), a `ToUnicode` map's inflated bytes (up to 8 MiB, inflating them counted the same way) plus a sixteenth of the memory reading it builds, 16 bytes for each character width looked at, and for an encoding's `Differences` 8 bytes for each item and 8 for each byte of a glyph name; the actual text of marked content, each time it is decoded; 32 bytes for each line the glyphs form; and a byte for every 16 comparisons attaching marks (below).

The time a call takes is in proportion to this work: no byte of work costs more than three times a byte of the densest plain content, so a call on one file ends in bounded time.

## Fonts and glyph names

A font's `ToUnicode` map comes before its `Encoding`, and a code the map leaves out reads through the encoding the font names. Glyph names in `Differences` may be the names of the standard tables, `uniXXXX` (one group of four hex digits for each UTF-16 unit), `uXXXX` to `uXXXXXX`, with a suffix after a `.` or parts joined by `_`; one that cannot be read loses its one code, and a name over 127 bytes (the limit the format gives on a name) cannot be read. Values in stream and font dictionaries may be references, as the format allows.

When `text()` and `page_texts()` read a font's `ToUnicode` map, the one reader of the map holds it, as it reads, to caps that real maps stay far below: at most 64 codespace ranges (real maps have one to four; which codes of one and two bytes the codespace holds is a bit for each, so deciding costs the same however many ranges there are), 131,072 lines that map codes, 256 texts in the list of one range (a range written to the specification varies only its last byte), and 65,792 texts in all its lists. A map over a cap is refused, and a string in a map that never ends ends the map. A line whose text is over 512 bytes (the limit the format gives on one) is skipped. Fonts and maps are kept for the whole document within 256 MiB, each counted by what reading it builds: 8 bytes for each byte of a `ToUnicode` map, two ranges of 96 bytes for each line that maps codes (a range is one entry however many codes it covers, so one line over every four-byte code is one entry, and a later line that lands in a range splits it into pieces that share its text), the texts the lines and lists keep, 8 KiB for a map with a codespace, 160 bytes for each code an encoding's `Differences` names (256 at most, whatever the array's length: 41 KB for a font), and 4 bytes for each code a table of widths has room for (65,536 at most, 256 KB). Each map is read once for all the fonts that share it. Past 256 MiB, what was used longest ago is dropped, and read again when a page needs it; what the text being shown uses is not dropped, so the fonts can pass 256 MiB by the widths of one font (256 KB at most). A map or a font that would take more than 256 MiB on its own is refused.

## What a page may show

A page may also show 1,000,000 glyphs, counting every character code shown, also one that reads as nothing, produce 8 MiB of text (the whole document 64 MiB), nest saved graphics states (`q`) and marked content 256 deep each, and spend 50,000,000 comparisons attaching marks (accents, dots, vowel signs drawn apart) to the letters they sit on, each byte of text compared counting as one. Over any of them, `text()` and `page_texts()` return `DocumentsError::TooLarge`; a document within every limit gives the same text whatever the limits are, and dropping and reading a font again changes nothing in it. The actual text of marked content that is open counts against the text of a page, as it is decoded: a page may hold 8 MiB of it at once. For scale: a form drawn ten thousand times on a page fits in its work if the form holds at most 8 KiB of ordinary content (one operation in about 17 bytes), or 3 KiB of the densest, stored or Flate, and in its glyphs if the form shows at most 100; a line of sixty thousand glyphs is well within the comparisons.

## The budget of a document

Reading a PDF is held to a budget for the whole document, so that a small file cannot make the reader hold, look at or write more than it allows. Loading reads the header, the cross-reference (following incremental updates back through `/Prev`, 256 sections at most, and rebuilt by scanning the file for objects when it is broken or points at the wrong places) and the trailer; every object is read the first time it is needed, and counted as it is built. The objects a document's reading holds may be counted as 256 MiB: each object, string and dictionary entry, each object stream and cross-reference stream inflated (each up to 8 MiB; a stream that would inflate further is skipped with the objects in it, as a damaged one is, so a PDF whose page tree sits in one has no pages and `Pdf::from_bytes` refuses it), and each entry of the cross-reference. An object is 32 bytes where it sits: a dictionary is a list of entries (a map past sixteen), a name of up to 22 bytes is kept inside its entry, a stream is a pointer, and a block of memory is counted with the room it rounds up to. An edit lets go of an object stream, and of what it was counted as, with the last of its objects. What the process holds for them is at most twice what is counted, so 512 MiB at the most (1.15 times for a tagged spreadsheet of 10,000 rows, 1.95 for a dictionary of 700,000 keys); an allocator that copies a block to grow it holds the old one as well for a moment, 2.08 times at most. The bytes of a stream are the file's own and are not copied.

For scale, measured on documents an office suite writes (and, in the second column, the same rewritten with object streams), reading every object to edit them is counted as: a tagged spreadsheet of 6,000 rows, 150,000 objects, 17 MB (2.8 MB), 77 MiB (30%) and 76 MiB (30%) of the 256; the same of 10,000 rows, 250,000 objects, 31 MB (4.8 MB), 128 MiB (50%) either way; a book of 3,211 pages, 17 MB (10 MB), 30 MiB (12%) and 29 MiB (12%); a document of 80 images on 27 pages, 5 MB, under 1%; a deck of 120 pages, 1.2 MB, 4 MiB (2%). Reading the text of the book takes 35% of the 1 GiB of work, so a book of about 9,000 such pages is the most `text()` reads; the text of the others takes 2% or less. A tagged spreadsheet reaches the limit at about 20,000 rows (500,000 objects, 60 MB written plain, 9 MB in object streams); more objects than that are refused with `DocumentsError::TooLarge`.

The reader may look at 1 GiB: every byte counts each time it is looked at, including what a parse reached before it failed and what each filter reads and writes, whether the next filter works or not. On top of that, each object looked up costs 32 bytes, read before or not, so following references is never free; a chain of references stops at 8 and reads as a missing object (writers refer to an object directly, and a reference to a reference is already rare). Each entry of the cross-reference and each object an object stream lists cost 16, each filter 1 KiB, each string or stream decrypted 256 bytes, and a parse a byte for every 32 of the memory it builds. A stream has at most 8 filters. Scans move forward and tables are looked up by key, so time is linear in the file until the limit stops it. Objects of an object stream that all point at the same bytes are each counted, arrays and dictionaries nest at most 100 deep, and a file encrypted without a password to open it (an owner password that only restricts printing or copying; RC4 and AES of 40 to 256 bits) is decrypted as its objects are read and counted the same way. `page_count()`, `text()` and `title()` read only what they need; `merge`, `stamp`, `overlay` and `with_metadata` read every object and write the result unencrypted. A stream ends before the next object starts, whatever its `Length` says, and an edit writes at most the bytes of the files it read plus 256 MiB. An edit refuses a file when an object its pages need cannot be read: a node of the page tree, or what a page's contents, resources or boxes lead to (`DocumentsError::Pdf`), so that what it writes does not lose part of the file without a word. Any other object that cannot be read (one only an annotation or a thumbnail refers to) is dropped, and so is one a later section of the cross-reference marks free, unless something still refers to it.

## Editing

An edit has a budget of its own, as large again as the document's. It may make 1 GiB of work's worth of lookups, at 32 bytes each, and add what is counted as 256 MiB: every object it adds with its bytes, every array it copies, 512 bytes each time it changes a page and 1 KiB for resources of a page's own. It counts each before it holds it, and past the limit it stops there with `DocumentsError::TooLarge`. A page costs about 2.6 KiB of that at the most, and about 4 KiB of memory, so stamping every page is refused past about 100,000 pages. Saving compresses the streams that have no filter (and no parameters for one, nor a file their bytes are in) with Flate at its fastest level, for 4 KiB of work and 2 bytes for each of theirs; a stream under 64 bytes is not compressed, and one past what is left of the work is written as it is.

## Merging and overlays

`merge` and `overlay` read more than one document, and hold all of them to the limits of one: 256 MiB of memory and 1 GiB of work for the inputs together. Each input is read with what the ones before it left. What a merge keeps of an input (its pages and what they lead to; not its outlines, forms or tagged structure, and not the bytes of its streams, which are the input's own and aren't copied, so scanned documents merge whatever their images come to) is counted as memory taken from the limit for the inputs after it, and what it does not keep is counted only while the input is read, so many files of ordinary size merge, as forty of the books above would (the pages of each are about 3 MiB, and reading all of its objects takes at most 21 MiB of the 1 GiB of work), and a few that are each near the limit do not. The work of reading and editing each input is taken from the work that is left, and what is left is what compressing the output may take. An overlay is read with what its document left. The error names the limit that was left and says it is shared. A merge of inputs that are each within the limit but together are not is `DocumentsError::TooLarge`.

The output of a merge is the size of its inputs, so the caller holds what it passes in, except for copies: the same `Pdf` listed many times is one file in memory and many in the output, which is what a client's list of file ids with repeats asks for. What the copies after the first write is held to 1 GiB, so forty scanned files of 20 MiB merge and six thousand copies of a 1 MiB file are `DocumentsError::TooLarge`. An app that merges a list a client controls should bound the list as well. An output the process has no memory for is also `DocumentsError::TooLarge`, and doesn't abort it.

Over a limit, each of these returns `DocumentsError::TooLarge` (413), an overlay whose page content inflates past 64 MiB included; a file of a few kilobytes whose objects would take gigabytes is refused once they are counted as 256 MiB. A PDF that needs a password to open is `DocumentsError::Pdf`.

## Damaged files

The reader also takes what other readers take from a file that is a little damaged: a page or a page tree node with no `Type`, an integer too large for one inside an array, a dictionary or a content stream (read as a real), a key at the end of a dictionary with no value, a doubled minus, a closing `]`, `>` or brace with nothing open in a content stream, the word `stream` inside a string when the file is scanned for its objects, an object with nothing in it (read as null), a page or tree node given through a reference to a reference, and an object a later section marks free, which stays readable while a reference to it remains. A font name over 127 bytes names no font. Other bytes that cannot be made sense of end a page's content.

## What the limits add up to

Adding these up at the default limits, besides the file itself: `text()` holds at most about 1.1 GiB (512 MiB of objects, 256 MiB of fonts, 128 MiB of a page's content, about 160 MiB for a page's glyphs and 64 MiB of text; the operands of an operation are let go of before a form it draws is read, and open marked content holds at most 8 MiB), and an edit at most about 1.4 GiB plus twice the file (512 MiB of objects, up to 256 MiB of what it adds, and up to 512 MiB of what it writes as that grows; the list a page gets for its contents is as long as it is counted as, not grown by doubling). Edits that read more than one document are within the same sums, since their inputs share one set of limits. The test of these sums runs the shapes that come closest at a reduced scale and compares the process's peak with them.

## Page properties that move

`stamp`, `overlay` and `merge` move what pages inherit from the page tree onto each page. Anything larger than a box that many pages inherit stays one object that the pages refer to, and resources they share stay shared, so stamping a document grows it by its resources once, not once per page; a `Rotate` that is not a number is not inherited; a page object the page tree lists twice is stamped once, and a merge lists it once. The page's new `Contents` lists the streams its old one leads to, and nothing else: an item that does not lead to a stream is not written, and pages that share an array of them count each copy against what the edit may add. A box is four numbers, each read where it is, and anything else is no box: a page with no `MediaBox` is 612 by 792. Stamps and overlays are placed on what the page shows, its `MediaBox` cut to its `CropBox`, wherever that box starts.
