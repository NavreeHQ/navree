# Navree Native for Windows

The Windows client of Navree Native, written in C# on .NET 10 and WinUI 3. The runtime core (a Rust library with a C interface of five functions) decides everything that is not drawing or talking to the system; this client draws with the system's own controls and carries out what the core asks.

| Folder | What |
|---|---|
| `src/Navree.Core` | the bridge to the core: the five functions through `LibraryImport`, a safe handle, bytes given back with the core's own function |
| `src/Navree.Protocol` | the protocol's models |
| `src/Navree.Runtime` | the view state, events and effects, and the client that drives the core |
| `src/Navree.Design` | the rules as plain functions, with no UI types: what is the app's own address, the window's width classes, the words and icons, the tree walked |
| `src/Navree.Platform` | what the client does with the system that needs no window, as plain .NET: the connections (no redirect followed, only the app's origins), the cookies, what is kept on the device (protected for the Windows user the app runs as: see "What is kept on the device"), the wipe |
| `src/Navree.Presence` | the app's place in Windows as plain rules and the few calls of the system that need no window: what a build offers with and without package identity, the count on the taskbar, when a notification is due, the addresses of a jump list and of a sign-in's return, the notification-area icon |
| `src/Navree.Controls` | our own controls over WinUI 3 |
| `src/Navree.Shell` | the app: window, title bar, navigation, pages, the tree drawn with the system's own controls, every effect carried out, the web view held to the app's origins |
| `demo/Navree.Demo` | the demo app, which starts with no package identity and no registration |
| `demo/Navree.Demo.Packaged` | the same demo as an installable package, so the features that need package identity can be tried |
| `demo/Navree.Gallery` | each control in every state |
| `tests/*` | MSTest projects beside each library |

The product depends on the Windows App SDK and on what .NET itself ships. The test projects add MSTest. Every version is set in `Directory.Packages.props`.

## Building

1. Build the core as a DLL and put it where the projects find it:

   ```
   cargo rustc -p navree-native-core --locked --release --target x86_64-pc-windows-msvc --crate-type cdylib
   mkdir packages/windows/native/win-x64
   copy target\x86_64-pc-windows-msvc\release\navree_native_core.dll packages\windows\native\win-x64\
   ```

2. From this folder, with the .NET 10 SDK (`global.json` picks it):

   ```
   dotnet build Navree.Native.sln -c Release
   dotnet test Navree.Native.sln -c Release --no-build
   ```

The DLL is copied next to every program that uses `Navree.Core`. The "Native clients" workflow does both on a Windows runner, and starts the demo from its build folder.

Every project restores the packages its lock file names (`packages.lock.json`, beside the project), and where `CI` is `true` a restore that would change one fails. A restore for one runtime alone asks for another set of runtimes than that file names, so it is held to a second file beside the first, named for the runtime: `packages.win-x64.lock.json`. The demo's package is built from such a restore. When a version in `Directory.Packages.props` changes, both are written again, with `CI` not set:

```
dotnet restore Navree.Native.sln --force-evaluate
dotnet restore demo/Navree.Demo.Packaged/Navree.Demo.Packaged.csproj --force-evaluate
dotnet restore demo/Navree.Demo.Packaged/Navree.Demo.Packaged.csproj -r win-x64 -p:RuntimeIdentifier=win-x64 --force-evaluate
```

A build without the DLL stops with an error that says where it was looked for. The DLL is built for x64 only. When the DLL is missing as the app starts, cannot be loaded, or is for another processor, making the `ShellHost` throws `CoreUnavailableException`, whose words name the file and the one folder it was looked for in (the program's own); the demo shows them in a `StartFailureWindow`, which ends the app when the person closes it, and an app does the same.

## The demo

`Navree.Demo` runs the client on the store demo's recorded answers (`packages/android/fixtures/store-demo`, found above the program), or on a server with `--server https://...`. `--dark` and `--light` choose the theme, `--rtl` the direction. `--walk <folder>` walks it through its screens at three widths and writes a picture of the window's content and of each page whole, and `walk.txt` saying what was done. `scripts/take-pictures.ps1` runs the demo on a Windows machine with a desktop, pictures its window in each way there is, and walks it in light, dark and right to left.


## What is not drawn

The client tells the core which kinds it has no drawing for (`ShellOptions.Undrawable`, from the one list in `Navree.Design/Undrawable.cs`), and the core shows a page that holds one in the web view, whole, never with a hole: a web region and the range field. A test reads the renderer's sources against the list, so a kind gains a drawing and leaves the list in the same change, and a kind that loses its drawing cannot be forgotten.

## The web view

A page of the app's own origins can be shown in the system's web view (WebView2). Every request it makes, from the page, its frames and its workers (service workers and shared workers too), is asked of the client first, and one that is not for the app's own origins is refused; a web view runtime too old to ask about the requests of workers shows no page, and says that updating the WebView2 Runtime lets it be shown. A WebSocket is not such a request, so the client cannot refuse one: the server's Content-Security-Policy `connect-src` is what keeps a page's WebSockets to the app's own origins. A download a page starts is refused, and the person is told it was not saved.

A page in the web view cannot pick a file and cannot be given one by a drop or paste. WebView2 offers no callback by which the client could answer or check a file picker before the page reads the file, so `<input type="file">` is disabled, programmatic file pickers (`showOpenFilePicker`, `showDirectoryPicker`, `showSaveFilePicker`, `showPicker`), file drops and file pastes are blocked, a navigation to a local file is cancelled without telling its path to anyone, and the page states why and points to native screens of the app for sending files.

## The colour field and the file field

A colour field is a field-shaped button: a swatch, the value in words (`#16a34a`), and for a screen reader its label, the colour's name and the value one character at a time. It opens a flyout with the system's own `ColorPicker` and OK and Cancel; only OK sends the colour, as `#rrggbb`.

A file field is a row: the label, a Choose button, and each file chosen with its name, its size and a button to take it out. Files come from the system's file picker (`Microsoft.Windows.Storage.Pickers.FileOpenPicker`, made with the window's `WindowId`; a run that must not open it gives `ShellHost.FilePicker` its own) or are dropped on the field. A dropped folder, or a dropped thing with no path on this computer (a file on a phone seen through Explorer, a link from a browser), is refused with words at the field, and so is a picker that fails; neither can end the app. Each is checked against the field's `accept` and against the most bytes of the field together (`ShellOptions.MostFileBytes`, 100 MiB; the protocol carries none), and a file that does not fit is refused with words at the field. The core is told a token, the name, the type and the size, never a path; the request's body is written from the file as it is then, streamed, and a file that can no longer be read is left out of it (never sent empty) and shown as gone. What a file is comes from its first bytes: a JPEG saved as `.jfif`, with no extension or with another one is a JPEG, an MP4 or QuickTime movie with no extension is known by its boxes, and a file with no known extension is sent with the type its bytes say. A file's name never makes it be read as another kind than its bytes say; it can only make the client more careful: a file named as a camera's raw picture is refused though its bytes are a plain TIFF, and so is a file named as a picture, as a video, as a raw picture or as a picture editor's document whose bytes are of no kind the client knows. In a field that does not keep the place a photo or video was made (`keep_location`), a file the client knows as a picture or a video, by its bytes or by its name, leaves the device only if the client can say where every place in it could be and has emptied or removed each; what it cannot be sure of is refused with words at the field, never sent as it is. For pictures, the place is taken out of four kinds: JPEG, PNG, WebP and TIFF. GIF, BMP and SVG are searched for a place and refused when they name one. Every other picture kind the client knows is refused; they are named below. For videos, ISO base media and QuickTime containers (MP4, M4V, MOV, 3GP) are read and written by the client's own box walker (`PlaceVideo.cs`): location atoms (`©xyz`, `loci`, `gps `, GoPro `GPMF`, DJI `djmd` and `dbgi`, Canon EXIF `uuid`, XMP boxes holding a place, QuickTime `mdta` location keys and their `ilst` entries with surviving keys renumbered, and iTunes `mdir` location items and geotagged cover art) are stripped and `stco` and `co64` chunk offsets are shifted to match `mdat`; a video with nothing of a place is sent byte for byte; a video whose location sits in a timed telemetry or subtitle track inside `mdat`, alongside `iloc`, `sidx` or fragment base offsets, in another video container (WebM, Matroska, AVI, Windows Media, FLV, MPEG, Ogg), or in a malformed container is refused with words at the field. A field that asks for `keep_location` gets the photo or video as it is, without a copy. A file that is neither a picture nor a video, by its bytes or by its name, is sent as it is. A form that asks for a camera's raw picture or for a picture editor's document has to keep the place, since the client takes it out of neither. Cleaned files are kept as copies in the app's own folder, so the person's own file on disk and the media stream itself (a JPEG's scans, a PNG's image chunks, a TIFF's strips and tiles, an MP4's `mdat` samples) are never changed. JPEG: every segment up to the end of the picture is read, the ones between the scans of a progressive picture too; the EXIF block's GPS directory, maker's note and GeoTIFF tags are emptied and its thumbnail is cleaned as a picture of its own; Photoshop's resources are read (the IPTC city, sub-location, state and country are emptied); application segments the client does not read (a GoPro's, JUMBF, a maker's own) are emptied, and the colour profile, Adobe's colour transform and the multi-picture index are kept; every picture after the first (the further pictures of a multi-picture file, an Ultra HDR gain map) is cleaned as a picture of its own. A motion photo is refused with words, because its appended video is not stripped inside a JPEG: save it as a still. Anything else after the pictures, and a picture cut short, is refused. TIFF: every directory, the XMP, IPTC and Photoshop tags and the thumbnail; a camera's raw picture is refused, by its extension or its bytes, and so is a file where emptying a place would touch the picture's own data. PNG: the `eXIf` chunk is cleaned; a text chunk holding an XMP packet with a place goes, compressed or not (expanded only up to 8 MiB, past which the file is refused), and so does a profile written as text and any ancillary chunk the client does not know; a file with something after `IEND` is refused. WebP: the `EXIF` and `XMP ` chunks, and an unknown chunk is emptied. An XMP packet anywhere that holds any property about a place, by its name in any namespace and any letter case, such as `exif:GPSLatitude`, `drone-dji:GpsLatitude`, `photoshop:City` or `Iptc4xmpCore:Location`, goes whole; an extended XMP packet in JPEG is read whole, its pieces joined in order first. GIF, BMP and SVG are searched for such a property and refused when one is found. Known by their bytes and refused with words, whatever the file is named: HEIC, HEIF, AVIF, JPEG XL, JPEG 2000, JPEG XR and BigTIFF; any other file of the ISO media family that is not a cleanable MP4 or MOV video; WebM, Matroska, AVI, Windows Media, FLV, MPEG and Ogg videos; a Photoshop document (which keeps the EXIF and XMP of the photo it was made from), a GIMP document and an OpenRaster document; and a camera's raw picture whose first bytes say what it is (Fujifilm, Sigma, Minolta, Olympus, Panasonic, Canon's CRW and CR2). Refused by its name, when its bytes are of no kind the client knows: a file with a picture's extension (`.jpg`, `.png`, `.heic`, `.jxr` and the others the client has a picture's type for), with a video's extension (`.mp4`, `.mov`, `.webm`, `.mkv`, `.avi` and the others the client has a video's type for), with a raw picture's (`.dng`, `.nef`, `.arw` and the like), or with a picture editor's (`.psd`, `.psb`, `.xcf`, `.ora`, `.kra`, `.pdn`, `.afphoto`, `.afdesign`). A raw picture that is a plain TIFF by its bytes is known by its name, and read as a TIFF under another name. Not looked into: words a person or a program wrote (a caption, a comment, a title) that name no coordinate or XMP place property, which are kept; the camera (`capture` opens the file picker, as it does in the Apple client).

## The app's place in Windows

Each feature is offered only where the build can do it, and the client's capability list and the About page say which. With a package: the taskbar badge, the jump list, the startup task. Without: an overlay icon on the taskbar button, the person's own list of programs to run at sign-in. Either way: the icon in the notification area with a small window by it, app notifications (not to an app that runs as an administrator), the share sheet, several windows over the one core, and one running app (a second start hands what it was asked to the first). `Activation.Claim` can be told to let every start run, which is for the walks of this repository and not for an app: two running apps share what is kept and the web view's folder, and a sign-out in one does not reach the other. `--system-walk <folder>` walks these and writes what each answered; `--probe <file>` runs the app for a while so a second start can be tried on it; `scripts/take-system-pictures.ps1` does both with and without a package.

## Signing in

Sign-in through the browser is not available on Windows yet; an app signs people in with its own sign-in page inside the app. That page comes to the client as any page of the app does: drawn by the client, its form sent with the client's own requests, so the session's cookie lands in the client's own cookie store. A sign-in page that holds a part the client does not draw is shown in the web view instead, and a sign-in there signs in the web view, not the app: the web view keeps its own cookies. A server that offers the hand-over to apps names its routes to every client, and on Windows that sign-in does not start, so such an app cannot sign people in on Windows yet.

Until the hand-over is offered for Windows, the client starts no sign-in in the browser, listens on no port for one, registers and claims no scheme of its own, and drops any address that arrives on its scheme, with or without a sign-in open: it is never opened as a page and never taken as a sign-in's return. Whether it is offered is decided in one place, `Navree.Presence/BrowserSignIn.cs`.

## What signing out does

Signing out ends the session on this device for good. From its first moment nothing more is written for the person who is leaving: the cookies go from memory, the requests, streams and timers under way are cancelled, and an answer to a request made before cannot put a cookie back. Then, in this order: the cookie file; what the web view keeps (its pages are emptied, and it asks nothing of the network meanwhile); the core is told and lets go of the person; everything else kept; the copies of chosen photographs and videos; the notifications that wait and those shown, the count on the taskbar button and the jump list; the pictures of the pages (which also go from memory at the first moment and, when it is the client that ends the session, once more just before the core is told, so a screen of whoever signs in next is never handed a picture that was drawn for the person who left). A mark is written to disk before any of it and taken away only when all of it has finished and the core has let go, so an app that is ended in the middle (killed, or a power cut) finishes the sign-out at its next start, before it reads anything it kept. When the core has one last thing to ask the server before it lets go of the person (to forget what the server holds for this device), it says the session is ending in the same breath, and the sign-out begins there, not at the answer: the mark is on disk, the cookies are out of memory, the web view's folder has moved on and everything kept is being taken away while the core still waits, so an app ended in that wait finishes the sign-out at its next start. That one request alone is let through: it is made with the cookies of the moment before, it is not cancelled, its answer is told to the core, and nothing of its answer is kept. Until the core lets go, everything else it asks is still the leaving person's and is refused, and nothing is written; when it does let go, nothing of the sign-out runs a second time, and the core asks anew for what it asked while it waited. The core lets go once for each time it said a session is ending, whatever ends its wait: the server's answer, of any kind, or the client's own sign-out. So the two can cross. When the person signs out in the client while the core waits, the core is told, drops its last request and lets go at once; when the core's word reaches the window after a sign-out of the client's own has begun, no second sign-out begins for it. Either way the app starts again when both are over. A part of a sign-out that fails, its very first included, does not stop the parts after it: the rest is still taken away and the core is still told, so the app can be used by whoever signs in next, and what failed keeps the mark and is said to the person. A kept file that another program holds at that start does not stop the app from starting: the app starts signed out, the file is set aside, never read again, and deleted at a later start. Not reached: what the person copied to the clipboard and files they saved.

What the web view keeps is in a folder of the session's own, inside the app's web folder, and that folder is never used for another session: whoever signs in next gets a new one, which the profile of the person who left was never in. The new folder is in force from the first moment of a sign-out, before anything of the old one is emptied, so a web page asked for while the old folder is still being emptied is opened in the new one or not at all. Not at all is for the screens of the person who is leaving, which stay up until the core lets go of them: a web page such a screen asks for in that time is not loaded, so nothing of the person who is leaving is ever put in the folder of whoever comes next. At a sign-out every web view that was made for the session is emptied and closed, in the main window and in a window of its own, and what they kept is cleared through one of them or deleted with the folder; a web view left alive from an earlier session is closed too, and a profile cleared through it counts for nothing. A folder that was cleared and cannot be deleted yet (the browser behind it is still ending) is deleted at a later sign-out or start. A web page shown in a window or a sheet is closed with it. When what the web view kept can be neither cleared nor deleted, the sign-out is not finished: the person is told so in the main window, by a bar that stays until the app is started again and has a button that starts it again (a main window that is hidden shows the bar when it is next opened; a window a screen was opened in does not show it), no web page is shown for the rest of that run, and the next start finishes the sign-out and goes on in a new folder.

## When another person signs in with no sign-out

A session can end with no sign-out on this device: it runs out, or the server ends it and answers with a plain redirect to its sign-in page. The sign-in is then put up over the work, the work stays, and the person who signs in again finds everything as it was; their reminders are held meanwhile, as told below. When somebody else signs in instead, the core lets go of the person before, and no effect of the core says so. The client knows it by the key the core gives for the person who is signed in (`app.user.key`): the same for one person and another for another account, made by the core from the id the server names the person by. The client keeps the key of the person named last, and when a state carries another key with no sign-out between, it takes away what it keeps of its own for the person before:

- the web view's folder moves on, and every web view that was started in the old one is closed and what they kept is cleared or deleted, as at a sign-out;
- the snapshot, the widths given to tables' columns and the notifications that wait are deleted;
- the notifications shown, the count on the taskbar button and the jump list go, and the jump list is written again from the destinations of the person who is here now;
- the copies of chosen photographs and videos and the pictures of the pages go.

It begins before the windows are given that state. By then the web view's folder has moved on, so a web page of the person who is here now is opened in the new one; the pictures are let go of; nothing waits to be notified and no count is shown; and what was kept has its turn to be deleted ahead of anything that is kept from then on. The rest (closing the old web views and clearing what they kept, what the system still shows, the copies of chosen photographs and videos) follows at once, each part with a limit, as at a sign-out.

The cookies stay: they are already those of the person who is here now, set by the sign-in that brought them. Nothing is refused or held back meanwhile, because the core has already let go of the person before: what it asks from that state on is for the person who is here now, and what is kept from then on stays.

Nothing of the person before is fetched or shown between the sign-in and the shell's answer that names who signed in. From a `401` (including one whose way in opens outside on another origin) or a cover going up, the core clears `app.user`, parks any web screens underneath, and after the sign-in holds a locked waiting cover over the app until the shell asked after the sign-in answers (showing the failure with a Try again button and retrying when that shell cannot be reached). Every locked cover (`modal.Locked`) is drawn across the whole main window over an opaque surface — hiding the navigation pane, title-bar search, account menu and settings, with neither a Close button nor Escape dismissal — while secondary windows blank what they show and every live web view under the cover is emptied and closed (leaving the session's web folder on disk for the same person if they come back, or deleting it first if the shell names another person).

The key of the person named last is kept beside the rest, as the mark of whom the rest is kept for; nothing of the person can be read from it. With it a start sees a change of person that happened across a restart: a session that ran out while the app was closed, and another person who signs in after it. The mark is written each time the core names the person until it is on disk, so a write that failed is tried again with the next state. It is replaced only when every part of a change has finished. An app that is ended in the middle, or a part that fails (which is said in a problem line), leaves the mark of the person before, and the next start, when it hears the person who is here named, does the change over; what was kept for that person meanwhile goes with it. A sign-out takes the mark with everything else, so whoever signs in after one is not compared with anybody.

A start that reads no mark, and finds something kept all the same (a reminder that waits, a snapshot, the widths of a table, or anything in the web view's folder), cannot say whose it is: the mark was never written (a build from before the mark was kept wrote none), or cannot be opened any more. The reminders that wait for a person are deleted at that start, before any of them is set to come due, so none is shown to whoever is in front of the app while nobody is named. The start then takes the first person named for another, and what was kept goes before they see anything. The cookies alone do not count: they are the session, and say nothing of anybody else.

A reminder that waits is kept with the mark of the person it is for, which is the person who was signed in when it was asked for, and it is shown only while that person is signed in. To the client nobody is signed in while the state names nobody (from any `401` or session end until the shell answers); while a locked cover is up over the app (both the sign-in cover and the waiting cover held after a sign-in until the shell answers, as well as any other locked cover); while a sign-out is under way; and at a start until this launch's shell names somebody. A reminder that comes due in any of these times is held and not shown. When a reminder for a signed-in person comes due after the app has heard nothing from its server for a long while (`PlaceOptions.ReminderSilence`, fifteen minutes by default), the client asks the shell first: the reminder is shown when the shell names the same person or when the server cannot be reached, and held when nobody or another person is named (or when the server answers with something other than a shell for them). When the shell later names the same person, what came due meanwhile is shown then, however long it was held (one that comes every day is shown once); when it names somebody else, what waited goes with the rest before the windows are given that state, and none of it is shown. A start keeps, of the reminders that are a person's, only those of the person its mark names, and a reminder that does not say whose it is (a build from before this wrote them so) is not read.

A reminder asked for while nobody is signed in, in any of the times above, is nobody's. It is shown only while nobody is signed in, never while a signed-in person is here. It is given to a person only when they are the first person named since a sign-out or since a start that kept nothing of a person (when there was no person before). It never goes to the person before: when a cover goes up after a person was kept, when the person before becomes signed in again after nobody was named, or at a start that read a person's mark, every reminder that waited for nobody is let go of, also when a newcomer was never named for their whole session. When the shell names another person instead, what waits goes with the rest.

One thing the client cannot know is a server that names nobody by id and ends a session some other way than a `401` with a way in — for example by answering a page with a redirect to an ordinary sign-in screen that is not presented as a cover, before the silence limit next asks the shell again. On a server that names people by id, as Navree's server does, an answer without that id clears who is named and covers the screens while asking the shell at once; on a server that names nobody by id, the state goes on naming the person before until a `401` puts up a cover, the silence check asks the shell, or the shell is otherwise fetched again.

Two accounts with the same name and the same email, or none, are two people to the client, because the core gives each its own key; and a person whose name or email changes is still the same person. That holds when the server names people by id, as Navree's server does. A server that names nobody by id leaves the core only the name and email to make the key from: then two accounts of one name and email are one person, and a person whose name or email changes is another, so what the client kept for them goes once. A core that gives no key at all is not the one this client is built with: the client says so once in a problem line, and makes its own mark from the name and email. The two kinds of mark are never held to each other. A mark made from a name and an email is another person's when a key arrives, and a key is another person's when the core gives none, whatever the name and the email are, since they say nothing of which account it is: what was kept goes once at each.

## What is kept on the device

What the app keeps between launches (the cookies, the pages the core may keep, the snapshot it starts again from, the widths of a table's columns, the notifications that wait, each with the mark of the person it is for, and the mark of whom all of it is kept for) is in its own folder under the local application data, each value protected with Windows' data protection (`CryptProtectData`) for the Windows user the app runs as. It is kept in two parts. The pages the core may keep are a cache: the core has it emptied after every change a person sends, and emptying it touches nothing else. The cookies, the snapshot, the widths a person gave a table's columns and the notifications that wait are the person's, and stay until the person signs out, which takes both parts, or until another person signs in with no sign-out between, which takes all of them but the cookies. That protection keeps what is kept from other people who sign in to the same computer. It does not keep it from other programs: any program that runs as the same Windows user can read it, and a user with a roaming profile can open it on another computer.

## The data table's columns

A column first gets the room its own words need, measured from the rows held (its heading too): never less than its least and never more than its most. A name asks for at most 240, so one very long name does not push the others out. A table whose columns all fit what they hold cuts nothing. When there is room left over it goes to the name column first. When there is too little, columns give way in this order, and only then is a word cut: the secondary columns first (the last one first), then the other columns of words, numbers and states, each in proportion to what it can give, down to its least; the name last, down to its least; then the table scrolls sideways, keeping the frozen columns in place. A width a person gave a column, a column of controls and a picture are not taken back. Rows that join later and hold wider words make a column grow, never narrow. A table too narrow for its least widths is a list.
