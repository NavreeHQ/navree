# Navree Native for Android

The Android client of Navree Native: `navree-native` (the library: the runtime core's Kotlin side, the effects, the drawing), `navree-push-fcm` (notifications through Firebase Cloud Messaging, for apps that send them) and `demo` (an app that is the library plus resources, and the template for one).

An app declares `com.navree.client.NavreeActivity` in its manifest and sets its origin, name and colour in its resources (`demo/src/main/res/values/navree.xml`). An app that needs more subclasses the activity and overrides `config()`.

## What the library does by itself

These hold for every app built on the library, with nothing to configure.

- **Addresses.** Every request, server-sent event stream, address the web view is given and picture is checked against the app's origins before it is made: the origin it was built for and the others `NavreeConfig.also` names (a host that starts with `*.` stands for every host under that name; the client does not know which names are public suffixes, so a pattern such as `*.co.in` would make every host under it the app's own, cookies included: a pattern names the app's own registered domain, `*.shop.co.in`). Plain `http` is used only for the machine itself, and only when `navree_loopback_http` is true, which a release build must never set. Connections use TLS 1.2 or 1.3 with modern cipher suites. An answer's body is at most 8 MiB, a line of an event stream at most 256 KiB, a picture at most 10 MiB and is decoded at most 2048 pixels on its longest side.
- **Outside the app.** An address the server asks to open outside the app is handed to the system only when it is `http`, `https`, `mailto`, `tel`, `sms` or `geo`.
- **The web view.** A page shown in the web view is always on the app's origins. What it loads inside it (scripts, styles, fonts, pictures, frames, and what its scripts fetch) is asked for only from the app's origins and the hosts in `NavreeConfig.webHosts`: the client checks the first address of every request, and is not asked where a redirect then takes it (see "What the web view does not guarantee about redirects" below). On the tested emulator's system web view (API 35) a beacon, a `keepalive` fetch, a link's `ping`, an `EventSource`, a `<link rel="prefetch">` and a module worker's imports are asked of the client as any request is, and a device test shows each refused for another origin. A link the person taps is handed to the core; every other way of leaving (a redirect, a posted form, a script) is stopped, and a page taken off the origins ends as a failed screen with "Try again". The web view's callbacks see the first address of each request but not where a redirect takes a frame or a posted form, so a script that runs at the start of every document in every frame (`WebViewCompat.addDocumentStartJavaScript`) stops and empties a document from any other origin before anything in it runs, and puts the same check in front of the page's own `WebSocket`, `WebSocketStream`, `Worker` and `SharedWorker`: one is made only for an address on the app's origins or a host in `webHosts`, so never from a `blob:` or `data:` address. What that check holds against, and the two ways round it that remain, are under "What the web view does not guarantee" below. A failure inside that script empties the document. **A web page is not shown without these two guards**: on a system web view too old for the script at the start of a document (`WebViewFeature.DOCUMENT_START_SCRIPT`) or for the listener a document says where it is through (`WebViewFeature.WEB_MESSAGE_LISTENER`), or that cannot take the setting for a service worker's requests, a web region shows the failed screen with "Try again" (the guards are asked for again each time), and the log says what is missing every time it happens (tag `Navree`, level warning). The rest of the app works, and there is no option to switch this off. A service worker a page registers has its requests held to the same origins, by their first address as a page's are (answered 403 otherwise). The framework's own pages also carry a content policy that the web engine checks on every redirect. The app bar takes a title only from a page on the app's origins. A web view whose process ends is replaced once, then the screen offers "Try again".
- **The end of a session.** When the person signs out, the client deletes, in order and before anything of the next session is stored (unless that takes longer than five seconds, below): the sealed page cache, the snapshot of the launch, the copies of the files chosen for forms, the app's notifications in the shade, every cookie, the web view's cache, history and form data, what pages stored in the web view, and then whatever the web view's own call left of what pages stored. **Nothing a page of the session stored in the web view is there for a page of the next one**, on either kind of system web view:
  - Where the system's web view has it (`WebViewFeature.DELETE_BROWSING_DATA`), what pages stored goes by `WebStorageCompat.deleteBrowsingData`, whose reference says it deletes "all data stored by websites", "network cache, cookies, and any JavaScript-readable storage", and which says when it is done. The reference gives it no limit of time and does not name service workers: the cookies do not wait for it (they go before it is asked), its word is waited for no longer than four seconds, and on this kind of web view too each origin is then shown the client's own document (below), which unregisters, deletes and counts what is left, so nothing is called gone on that call's word alone.
  - A system web view without that feature has only `WebStorage.deleteAllData`, whose reference names only the Web SQL database and Web Storage and which does not say when it is done. **The system web view of the tested emulator (API 35) is one without it**: there that call takes local storage and IndexedDB and leaves Cache Storage and the service workers. Those the client takes away itself. For each of the app's origins and web hosts it loads, in a web view that is never drawn, an address of that origin which it answers itself with an empty document, and a script at the start of that document (`WebViewCompat.addDocumentStartJavaScript`) unregisters every service worker registration of the origin, deletes every cache and every IndexedDB database, empties local storage (the older call's reference does not promise IndexedDB, and gives no moment at which it is done), waits a quarter of a second, counts all four again, and says what is left through a message listener only that origin is given (`WebViewCompat.addWebMessageListener`), with a word that is in the script and not in the address. The address is a path made at random for that one go, and the client answers it wherever the web view asks about it: for the page's own request, and for a service worker's (`ServiceWorkerClient.shouldInterceptRequest`, whose reference says that where an answer is returned "the return response and data will be used"), so a worker of the session that ended which fetches what its pages ask for is handed the client's document, and the address is not sent to the app's server. The script runs before anything of the page and empties the document first, so a worker that answers the address with a page of its own does not stop it. A worker that answers it with what is no document (a redirect, an empty answer) keeps its own origin from being cleared, and only its own (below). A document made with `loadDataWithBaseURL` cannot do this: it has the origin of its base address, but the engine gives it no service worker client, so it cannot ask for the registrations. Nor can the web view's profile be dropped at sign-out: `ProfileStore.deleteProfile` refuses the default profile, a profile with a living web view and one loaded in this run of the app. The origins are those the configuration names as one host, and every origin a document of the app was on in the web view since the last deletion that finished, however it got there. The client writes an origin down, to a file and before it goes on, when a request for a document is sent to it, when a redirect is followed to it and when a page starts on it; and every document of the app says where it is at its start, through a message listener the web view gives only to the app's origins (`WebViewCompat.addWebMessageListener`: the web view itself names the origin a message came from, and what is posted is not read). That is how a host under a `*.` pattern is known, one a page or a frame reached only through a redirect among them.

  The client waits for the web view to say it is done, for up to five seconds (a limit there so that a failure cannot hold the app). **Until the web view has said so, no web page is shown**: a web region says in words that what the last session's pages kept is still being removed and what the person can do (try again in a moment; close the app and open it again; update the system's web view), with "Try again", which sets the deletion going again, and the next start of the app goes on with it before any web page. A page that is held back only asks whether it may be shown, each time it is drawn again, and asking begins nothing: a deletion begins when a session ends, when another person is signed in with no sign-out between (below), when the app starts, and when the person asks. The mark that something is owed is written, and forced to the disk, the moment the client is told the session ended, before the store's queue is waited for and before anything is deleted, and it says how much is owed: from that moment until every cookie is gone and written to the disk, it owes the whole of the list above, and a start of the app that finds it so (the run before ended part way) does all of it again before anything of the new run is read, kept or shown; after that it owes only what pages stored at the origins. The cookie store is waited for no longer than four seconds: where it has not said by then that its cookies are gone, the web view's cache and what pages stored are deleted without its word, no origin is shown the client's document, the deletion is called over, and the mark goes on owing the whole, so the next start does all of it again; where the store says so later, the mark is narrowed then and the documents follow. The client is told at the first moment the core knows. For an app with a push token registered, the core says `session_ending` in the same answer in which it asks the server to remove the token, after that request: the client writes the mark and begins all of the above then, and does not wait for the removal to be answered (the removal's request was given its cookies before, in its turn). `forget_session`, which follows when the removal is answered or five seconds have passed, finds the end of the session begun or done, begins nothing a second time, and empties the shade once more. Without a push token to remove, `forget_session` comes with the sign-out's own answer and begins it. Each end of a session has a number: what a deletion begun for one says to the mark is dropped once a later session has ended, so the first to finish never calls a later one done, and a go that is still at its origins when a later one begins ends there, its web view with it, so there is one go at a time and its address is the only one answered as the client's document. One origin does not hold the others: each is shown the client's document up to two times, three seconds each time, and one that has not said by then that nothing is left is left for later while the go moves on. After the go, pages on the origins that said so are shown again; **pages and frames on an origin that was left stay refused**, with the same words; the mark of what is owed stays, now naming those origins; and "Try again" there, and every start of the app, has another go at them. A device test shows a page that stored a cookie, local storage, IndexedDB, Cache Storage and a service worker, the end of the session, and a page of the same origin afterwards that finds none of the five; a second does the same with a worker that answers every page of its origin itself, a third with a page reached only through a redirect to a second origin of the app, which the client that ends the session does not name, and a fourth with a worker that fetches every page of its origin from a server that redirects an address it does not know, where the server is never asked for the client's document; and a fifth leaves the device as a run of the app that ended part way does, starts the client again, and finds no cookie and nothing else of the five; a sixth holds the store busy, ends the session, and finds the mark on the disk when the effect returns; and a seventh has the core say the session is ending while the server leaves the push token's removal unanswered, and finds the mark written at once, the removal sent with its cookie, and everything gone before any answer to it (and, with a push service of the test's own, what the paragraph on the push service's token below says of that moment and of the next start). Both run on the tested emulator, so on a web view without the feature: **no device test runs the path that uses `deleteBrowsingData`.** What is not reached on a web view without the feature: what a frame from a host on another site stored, where the engine keeps a frame's storage apart from what the same host stores as a page (the reference of `deleteBrowsingDataForSite` speaks of such partitioned storage). A web page that is on the screen when the client is told the session ended is taken down then, its web view with it, and while the deletion runs no document is loaded in any web view of the app; a service worker that is still running a request of the session and stores its answer within that quarter of a second is counted as left, and the origin is tried again; one that stores it later than that is not seen.

  **The push service's token** (with `navree-push-fcm`) has a mark of its own, a second file no backup takes, written and forced to the disk at that same first moment, before the other mark: the token's deletion is owed from then until the push service has said the token is deleted, whatever becomes of the rest. The push service is asked to delete it at that moment too, so at `session_ending` for an app with a token registered, without waiting for the server to answer the token's removal. When the push service has said the token is gone, the shade is emptied again and a new token is asked for. Until it has said so:
  - the library draws no message that arrives, since it was sent to the token of the person who left, and that holds in a process the system starts only for the message, after a run of the app that ended before the push service answered;
  - the client asks the push service for no token, since the one it would give is the one to delete;
  - a deletion the push service says failed (no network) is asked for again each time the app comes to the front and when a token is wanted, and one it had not answered when the app ended, at the next start of the app. So an app that cannot reach the push service draws no notification until it can.

  For an app with a token registered the shade is emptied three times: in the end of the session's own turn, when the server has answered the token's removal (`forget_session`), and when the push service says the token is gone. What the library cannot hold back in between is a message the Firebase library draws itself (a `notification` message that arrives while the app is in the background, under "Notifications" below): it is in the shade until the next of those three, and after a run of the app that ended part way, until the next start has the push service's answer. JVM tests hold the push service's answer back and show the order of each of these, and the seventh device test above shows the push service asked at `session_ending`, not asked again at `forget_session`, and asked again by a client made afterwards; **no test has a real push service**, so what Firebase delivers after it was asked to delete a token is not tested.
- **Another person, with no sign-out between.** A session can end with no sign-out on this device: it runs out, or the server ends it and says nothing of it to the client. The way in is then put up over the work, the work stays, and the person who signs in again finds everything as it was. When somebody else signs in instead, the core lets go of the person before, takes their screens down and has its own page cache emptied, and tells the client nothing more. So the client remembers who the core last named, as a mark: made from the key the core gives the person it names (`app.user.key`: the same for one person and another for two accounts, whatever their names; the core makes it from the id the app's server gave the person, where it gave one), or, from a core that gives no key, from the name and email (a SHA-256 over both, made the same way on every Navree client). Nothing of the key, the name or the email is read from the mark. It is kept in a file no backup takes beside the origin it was heard at, and read at every start, so a change of person while the app was closed is seen too. It hears who the core names each time the core's answer is read back, before anything is drawn from it and before any effect of that answer is carried out. Who the core names comes from the shell the app's server answered: nothing a page says is heard. What the core says while a session is ending is skipped, and a sign-out deletes the mark, so whoever signs in after one is compared with nobody. When the core names somebody else than the mark, with no sign-out between, the client takes away what it keeps of its own for the person before, then and there:
  - the app's notifications in the shade;
  - what the web view keeps: its cache, history, form data and saved sign-ins for sites at once, and what pages stored (local storage, IndexedDB, Cache Storage, service workers) as at the end of a session, origin by origin through the client's own document. That is owed and written down from the same moment, **no web page is shown until it is gone**, and a start of the app goes on with what a run did not finish;
  - the copies of the files chosen for forms, the snapshot of the launch, and the cookies the web view's side put in the store (below).

  **The cookie store is emptied then, and only the cookies the answers to the client's own requests set are given back.** On Android the native requests and the web view share the one cookie store, and the session in it is already the new person's, set by the sign-in that brought them. So the client remembers, for as long as the app runs, each cookie an answer to one of its own requests set, as the answer set it. At a change of person it empties the store and sets those again, each only where the store still held it with the value the answer gave it: the sign-in's cookies are among them, so the person who is here now stays signed in. Everything the web view's side put in the store goes: a cookie a page's script set (a support chat's, say), a cookie an answer inside a page set, and every cookie of a host in `webHosts`. This is done in the store's turn, before any request of the client's own that was asked after the change. What it cannot tell apart: a cookie an answer to the client's own requests set for the person before, under a name the sign-in did not set again, is given back with the rest (the session's own cookie is not one of those, being set again by the sign-in). And two cases in which the person signs in once more, because their session's cookie is not among those the client remembers and goes with the rest: where they signed in inside a web page, and where the change is seen at a start of the app after a run that ended in the middle of one. The client keeps nothing else for a person: pictures are held only by the screens that draw them, which the core has taken down, and the client schedules no notification and writes no count or shortcut of its own. The push token stays: the core registers it again for the person who is here now.

  **While what pages stored is being taken away, a service worker's requests are refused.** The client clears an origin by showing it a document of its own, and that starts the service workers the origin's pages registered: the workers of the person before. What such a worker sends on its own (a queue of writes it sends again when it starts, a sync, a refresh of its caches) would leave with the cookies in the store at that moment, the new person's. So for as long as that deletion runs, every request of a service worker's that the web view asks the client about (its fetches and imports) is answered 403, all but the one for the client's own document; a socket a worker opens is not asked about (see "What the web view does not guarantee about sockets and workers" below); where the deletion is only at the origins an earlier one left, the requests to those origins are. And whether or not a deletion is running at that moment, a service worker's request to an origin whose pages are held back is refused as its pages are, so a worker that outlives the deletion at an origin it could not clear sends nothing there either. The same holds at the end of a session and at a start of the app. The pages of those origins are held back all that time, so nothing a person is using is refused. What this does not reach: the moment between the deletion's end at an origin it cleared and the web engine ending that origin's worker, whose registration is gone by then; a deletion only at the origins an earlier one left refuses requests by where they go, so a worker it starts there can still send to the app's other origins; and pages are held until the deletion ends, not until the cookie store has been emptied and given its own cookies back, so where the store is slower than the deletion a page can be shown while cookies a script of the person before set are still in the store.

  The mark is replaced only when the store's turn has done its part: the files deleted, and the cookie store emptied and given its own cookies back. An app that ends before that, or a cookie store that does not say within four seconds that its cookies are gone, leaves the mark of the person before, and the next start, when it hears the person who is here named, does all of this over. By the core's key two accounts of one name are two people, and a person who is renamed stays the same person. **From a core that gives no key** the client tells two people apart by name and email, which is then all the core says of them: **a person whose name or email changes is taken for another person, once** (the files chosen for a form not yet sent go, and what their pages stored in the web view), and **two people with the same name and no email are one to it**, as are two with the same name and email. The marks of the two kinds never match, since a name and email say too little to be taken for the person a key names: where a mark made from a name and email is kept and the core names somebody by key, that is another person, whatever their name and email, and what was kept goes, once; and so it is where a key's mark is kept and the core names somebody with no key. Name and email are compared only where neither side has a key. A mark kept at another origin than the app's is not compared with: an app has one origin, and a build pointed at another server starts with nobody remembered. JVM tests show the mark and each of these orders, and a device test shows a page that stored a cookie, local storage, IndexedDB, Cache Storage and a service worker, an answer to one of the client's own requests setting a session's cookie, the core naming another person, and a page afterwards that finds that session's cookie and none of the five; in the same test the worker sends a write of its own whenever a page of its origin is asked for, and the one it sends for the client's own document never reaches the server.
- **Cookies.** The cookie store's cookies go only to the app's origins: a picture host is sent none by the client's own requests, and nothing it sets is kept. Inside the web view, a frame from another site is refused cookies (the system's default for third-party cookies, said again by the library); a host in `webHosts` under the same registrable domain as the app (`pay.shop.example` beside `shop.example`) is the same site to the web engine and gets the cookies scoped to that domain.
- **Files a form sends.** A file field opens the system's own picker (the photo picker for a field that takes only pictures and video, the file picker otherwise), which asks for no permission. Each file chosen is copied at once, off the main thread and as a stream, into the app's cache folder under a token the client makes (never into a backup or a transfer), and the form's request streams the copy: the file is never held whole in memory. A file is at most `NavreeConfig.mostFileBytes` (100 MiB unless the app sets another), and so are all the files of one field together; a file over it is refused at the field in words that say the limit. It guards the device's storage, since each file is copied; the server's own limit is the server's (the protocol's file field carries none, so the server cannot tell the client). A file that is not a kind the field takes is not added. Where a file is kept (a provider) may stop answering while it is read: one that gives nothing for twenty seconds, no answer and no byte, is given up, the file is refused at the field in words, and the field goes on (the platform promises no way to interrupt such a read, so the thread that asked is left to it). A field that takes one file keeps the last one chosen; one that takes several has no limit on the count. Unless the field says to keep it, the place a picture was taken is taken out of the copy, by what the copy's own first bytes say it is and never by the type the provider gave or the file's name. From a JPEG, a PNG or a WebP (the kinds the platform's `ExifInterface` writes) go every GPS tag of its Exif data (the place it points to, `GPSDest`, among them), an XMP packet that names a place (a property found by its own name, under any prefix and in any letter case: a GPS property, a latitude, a longitude or an altitude, a location, a city, a state, a country or an address), every Exif block after the first, the blocks other programs keep Exif, XMP or IPTC data in (a JPEG's Photoshop block, a PNG's "Raw profile type" text), a JPEG's index of further pictures, and everything after the end of the picture (the video of a motion photo, a second picture); what is left is read again, and the picture is refused when a place is still found in it. A HEIC (from API 28), an AVIF (from API 31) or a GIF that holds a place is refused, since the client cannot rewrite those; a HEIC or an AVIF on an older system, a TIFF and a camera's raw picture are refused whether they hold one or not, since the system cannot read them for it (`ExifInterface` reads "HEIC (on API 28+)" and "AVIF (on API 31+)", and writes "JPEG, PNG, WebP"). Each refusal says why in words. **The place a video was taken is not taken out**, nor one in the Exif data of a thumbnail inside a picture's Exif data. A copy the system cleared while the app was away is shown as gone and sent as no file. The copies go when the form's write has its last answer (an answer under 400 that is not a 307 or a 308, after which the same body, with its files, is sent again), when the person leaves the form's screen, when a file is removed or replaced, at the end of a session, when another person signs in with no sign-out between, when the app starts again after the system ended it, and, each time a file is chosen, any copy more than a day old. A file is sent under the name the provider shows, cut to its last part and without control or format characters, and with the type the provider gave: a provider can name and type a file as it likes, so the server checks both itself.
- **Backups.** The library's manifest sets `android:fullBackupContent` (Android 11 and earlier) and `android:dataExtractionRules` (Android 12 and later, cloud backup and device transfer). The page cache and the snapshot live in the no-backup folder, which no backup takes; the rules leave out the web view's folder (`app_webview`), which holds the session cookie.
- **Touches.** A touch is ignored while another app's window covers the app (`NavreeConfig.filterObscuredTouches`, on by default).
- **A runtime core that stopped.** A failure inside the runtime core stops it for good, and from then on every answer it gives says so. The app then sends it nothing more and draws nothing it held: it tells the person the app has stopped and must be started again, and offers to. "Start again" makes a new session with a new core in the same process, which starts plainly, with no snapshot of the launch before; the person stays signed in, since the cookies are not the core's. A host that draws `NavreeApp` itself gives it the restart (`startAgain`); without one the app shows the words and no button.
- **A keyboard.** Tab goes through a window in the order a person reads it, laid out left to right or right to left, and with the focus nowhere it comes in at the first stop of that order (the rules, and what Compose and the system do by themselves, are in `design/RULES.md`). A dialog, a menu and a sheet are windows of their own, where the first Tab goes where the system's default focus goes.

## What an app must do itself

- **Pages that load from another host.** A page the web view shows may load from another host only when that host is in `NavreeConfig.webHosts` (`checkout.pay.example`, `*.cdn.example`, with `:port` where it is not 443; `https` only). An app that lets a payment frame or a captcha into its page's policy names the same host once more in `webHosts`. A host there serves what a page loads inside it, and the page's own sockets and workers may go to it, and nothing else: never a page itself, a native request, a stream, a picture or a cookie of the client's own requests. A `*.` pattern needs at least two labels after it (`*.cdn.example`, never `*.com`); one under a shared hosting name (`*.cloudfront.net` and the like) trusts everybody who publishes there. Three things a listed host does not change:
  - A frame from a listed host can take the app to another screen after a tap, as any frame can in a browser: the core then opens an address of the app, or the system's browser for one elsewhere.
  - A widget that needs its own cookies inside the page (some captchas and payment frames) will not work even when listed: the web view refuses other sites' cookies.
  - A bank's card-verification pages sit on hosts nobody can list, so an app sends a card payment to the system's browser tab (a Custom Tab: a link the page marks to open in the system's browser inside the app), not into the web view.
- **What the web view does not guarantee about redirects.** The platform asks the web view's client about the first address of a request and never about the address a redirect sends it to (`WebViewClient.shouldInterceptRequest` on developer.android.com: "In the case of redirects, this is only called for the initial resource URL, not any subsequent redirect URLs"). So a script, a style or a picture that the app's origin or a host in `webHosts` answers with a redirect is loaded from wherever the redirect points, and a form posted to an address that answers 307 carries its body there. On the system web view of the tested emulator (API 35) the address a `fetch` is redirected to is asked of the client, and refused when it is elsewhere; the reference promises only the first address, so another version of the web view may not ask. A document reached that way (a frame, a posted form) is still emptied by the script at the start of every document, and the main frame is still never shown from another origin; everything else is held only by the content security policy of the page, which the web engine checks on every redirect: `script-src`, `style-src`, `img-src`, `font-src`, `connect-src` and `form-action` that name only the app's origins and its web hosts. An app with an open redirect on its own origin (an address that sends the browser wherever a parameter says) lets a page's loads out through it unless that policy is sent. A device test shows a picture and a script through a redirect reaching another origin with the client's checks on, a fetch's hop refused by the client, and all three stopped by `default-src 'self'` on the page.
- **What the web view does not guarantee about sockets and workers.** A socket and a worker are not requests the web view's client is asked about. The script at the start of every document checks the address the page's own scripts give `WebSocket`, `WebSocketStream`, `Worker` and `SharedWorker`, and refuses one that is not on the app's origins or a host in `webHosts`. Whatever of the page's can run while one is made is read once, before the check, into copies of the script's own (the address turned into a string, a list of protocols, the fields of the options); the address is then resolved against the document's base as it is at that moment, that absolute address is what is checked, and the real constructor is given that same absolute address and the copies, so a base element the page's code puts into the document afterwards, or a getter that answers differently the second time, changes nothing. It takes everything that check calls (`URL` and the getters of its parts, `String`, `Reflect.apply` and `Reflect.construct`, the document's base address, the real constructors) before any script of the page runs, and calls only those, so it holds against a page's scripts that run after it, in the documents it runs in, whatever they replace. "Before any script of the page" has one limit: a frame's first, empty window is kept when the frame then goes to a document of the same origin, so what a page replaced in that window beforehand (`Reflect.apply`, `URL`) is what the script takes there. That gives the page nothing the empty frame did not give already, the first of the two ways round. Two ways round it remain, and the client cannot close them: the first, empty document of a frame the page creates and has not navigated, where the script does not run, gives the page an unchecked `WebSocket` and an unchecked `Worker` (so a worker from a `blob:` address too); and a script inside a worker of any kind (a dedicated worker, a shared worker, a service worker) opens what sockets it likes, since the script does not run inside a worker. What holds in every case is the content security policy the app's server sends: `connect-src` for sockets and `worker-src` for workers (below). A dedicated worker's fetch and importScripts are asked of the client, and a service worker's requests (its fetches and its importScripts) go to the guard on service workers: both are refused for any other origin, and a registration whose script is on another origin is refused by the browser. That is what the system web view of the tested emulator (API 35) does and a device test shows each; the platform's reference for a service worker's client says only that it is asked about "a resource request", so another version of the web view may ask for less. What can close a socket inside a worker is the worker's own content security policy, and the page's policy does not do it: a worker loaded from a network address follows the policy sent with its own script (a `Content-Security-Policy` header on the response that delivers the worker's script), and only a worker from a `blob:` or `data:` address inherits the page's (MDN, "Using web workers", the section on content security policy). An app that wants sockets in workers closed therefore sends `connect-src` on its worker scripts as well as on its pages, and sends `worker-src 'self'` on its pages, which is what stops workers from `blob:` and `data:` addresses and from other origins (MDN, the `worker-src` directive). The client also does not check what a page sends through WebRTC (a connection to a STUN or TURN server of the page's choice), through WebTransport, or through a connection the page asks the engine to open ahead of time (`<link rel="preconnect">`): none of them is a request the client is asked about, and the platform has no setting that turns them off (`WebSettings` and `WebSettingsCompat` on developer.android.com name none), so a page can reach an address of its choice with each. A device test shows each of the three with the client's checks on. Nor does the client see the name lookup a `<link rel="dns-prefetch">` asks for: a page can have the device look up a name of its choosing, and so tell whoever answers for that name's domain what it puts in the name; a device test cannot see a lookup, so this is said and not tested.
- **Leave the service worker guard alone.** The client's guard on a service worker's requests is the one client of the process's `ServiceWorkerController` (the platform has one per process). Code of the app that sets a client of its own there replaces the guard without a word, and the client cannot tell (the platform gives no way to read which client is set): web pages are then still shown, and a page's service worker reaches any origin. An app does not set its own.
- **Its own backup rules.** An app that sets `android:fullBackupContent` or `android:dataExtractionRules` itself replaces the library's (the manifest merger reports the clash; resolve it with `tools:replace="android:fullBackupContent,android:dataExtractionRules"` on the app's `<application>`). Its rules must then leave out the web view's folder too: `<exclude domain="root" path="app_webview" />` in `<full-backup-content>`, and in both `<cloud-backup>` and `<device-transfer>` of `<data-extraction-rules>`. An app that sets `android:allowBackup="false"` has no cloud backup, but on Android 12 and later device transfer still follows the extraction rules. Backup rules take no patterns, so the library cannot name every folder that may hold a session. What an app checks for itself: a web view data folder of its own (`WebView.setDataDirectorySuffix` makes `app_webview_<suffix>`, to leave out as `app_webview` is); the push service's own files, which hold this install's token (Firebase does not document their names; Android's backup guide names push registration tokens as something to leave out); and, on Android 16 QPR2 and later, a `<cross-platform-transfer>` section, which the library's rules do not have, if the app turns that transfer on.
- **The screen.** `navree_screen` in resources (or `NavreeConfig.screen`) says how much of the app the system may show elsewhere:
  - empty (the default): the system's own behaviour;
  - `hidden_in_recents`: no picture of the app in the recent-apps list, with `Activity.setRecentsScreenshotEnabled(false)` on Android 13 (API 33) and later; before that the only means is the secure window flag, so there it behaves as `no_capture`;
  - `no_capture`: no screenshot, no screen recording, no picture in the recent-apps list and nothing on a display that is not secure, with `WindowManager.LayoutParams.FLAG_SECURE` (API 1).
  A value the library does not know is taken as `no_capture`.
- **Notifications.** What a locked screen shows of a notification the library draws is `navree_notification_lock_screen` in the app's resources: empty (the default) for the system's way, where the person's own lock-screen setting decides whether the title and text show (where it hides them, the app's name and "New notification" stand in); `nothing` for nothing of it on a secure locked screen (`VISIBILITY_SECRET`). The library draws a message only when Firebase hands it over: a **data message** (`title`, `body` and `href` in `data`, no `notification` block) always; a message with a `notification` block only while the app is in front. A message the server sends as a `notification` message is drawn by the push SDK itself while the app is in the background, with its title and text, and never reaches the library: an app that needs the option to hold has its server send data messages. Signing out removes the app's notifications from the shade, and from then until the push service has said this install's token is deleted the library draws no message that arrives (under "The end of a session" above); a `notification` message the push SDK draws itself in that time is removed when the token is gone.
- **The activity.** As the template does: `android:taskAffinity=""` so no other app's activity can join the app's task, `android:launchMode="singleTop"`, and an app-link filter (`android:autoVerify="true"`) for the app's host that names only the paths the app opens (`android:path`, `android:pathPrefix`) and the path the sign-in returns to.
- **Pictures from another host.** Pictures load from the app's origins; a host that serves them (a CDN) is named in `NavreeConfig.pictureHosts` and is used only over `https`.
- **Shrinking.** The library's consumer rules keep the core's native methods and the serializers; an app needs no rules of its own for them.

## Checking the client on a device

- **The device tests** (`navree-native/src/androidTest`) run on an emulator of a phone and of a tablet (on its side and upright), each in four looks (light, dark, the largest text, right to left). They draw the app through the activity's own host, against recorded answers and against the store, inbox and board demos, and photograph each screen. Beside every picture they write what a screen reader is told by the screen, in order, with the size of each control and the faults found (a control with no name, a touch area under 48 dp) as `.sem.txt`, and, for the light look, the screen's tree as `.tree.json`.
- **The walk** (`scripts/walk.sh`, `scripts/ui.py`) drives the demo app itself on a phone with `adb`: a start second by second with and without a network, back, turning the device, a link from outside, a form, and the app ended by the system and opened again. It needs the store demo answering on the address the debug build is given (`10.0.2.2:8787`) and prints `PASS` or `FAIL` for each step. A step reads only a dump of the screen made for it: where none could be made the step fails, and a question about what is not on the screen is never answered from a missing dump. What it expects after the system ended the app depends on what the demo's shell says: when it names a person (`x-navree-person`) the app returns to the place it was in, and when it does not the app starts at its first screen. `scripts/ui_test.py` and `scripts/walk_test.sh` test the helpers and run in the "Native clients" workflow.
- Both run in the "Native clients" workflow (`android-screens`).
