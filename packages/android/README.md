# Navree Native for Android

The Android client of Navree Native: `navree-native` (the library: the runtime core's Kotlin side, the effects, the drawing), `navree-push-fcm` (notifications through Firebase Cloud Messaging, for apps that send them) and `demo` (an app that is the library plus resources, and the template for one).

An app declares `com.navree.client.NavreeActivity` in its manifest and sets its origin, name and colour in its resources (`demo/src/main/res/values/navree.xml`). An app that needs more subclasses the activity and overrides `config()`.

## What the library does by itself

These hold for every app built on the library, with nothing to configure.

- **Addresses.** Every request, server-sent event stream, address the web view is given and picture is checked against the app's origins before it is made: the origin it was built for and the others `NavreeConfig.also` names (a host that starts with `*.` stands for every host under that name). Plain `http` is used only for the machine itself, and only when `navree_loopback_http` is true, which a release build must never set. Connections use TLS 1.2 or 1.3 with modern cipher suites. An answer's body is at most 8 MiB, a line of an event stream at most 256 KiB, a picture at most 10 MiB and is decoded at most 2048 pixels on its longest side.
- **Outside the app.** An address the server asks to open outside the app is handed to the system only when it is `http`, `https`, `mailto`, `tel`, `sms` or `geo`.
- **The web view.** A page shown in the web view is always on the app's origins. What it loads inside it (scripts, styles, fonts, pictures, frames) comes from the app's origins and from the hosts in `NavreeConfig.webHosts`, and from nowhere else. A link the person taps is handed to the core; every other way of leaving (a redirect, a posted form, a script) is stopped, and a page taken off the origins ends as a failed screen with "Try again". The web view's callbacks see the first address of each request but not where a redirect takes a frame or a posted form, so a script that runs at the start of every document in every frame (`WebViewCompat.addDocumentStartJavaScript`) stops and empties a document from any other origin before anything in it runs; on a system web view without that feature (`WebViewFeature.DOCUMENT_START_SCRIPT`) the request checks are what holds. The framework's own pages also carry a content policy that the web engine checks on every redirect. The app bar takes a title only from a page on the app's origins. A web view whose process ends is replaced once, then the screen offers "Try again".
- **The end of a session.** When the person signs out, the client deletes, in order and before anything of the next session is stored: the sealed page cache, the snapshot of the launch, what pages stored in the web view, the web view's cache, history and form data, the app's notifications in the shade, and every cookie. With `navree-push-fcm`, the device's push token is deleted and a new one is asked for.
- **Cookies.** The cookie store's cookies go only to the app's origins: a picture host is sent none by the client's own requests, and nothing it sets is kept. Inside the web view, a frame from another site is refused cookies (the system's default for third-party cookies, said again by the library); a host in `webHosts` under the same registrable domain as the app (`pay.shop.example` beside `shop.example`) is the same site to the web engine and gets the cookies scoped to that domain.
- **Backups.** The library's manifest sets `android:fullBackupContent` (Android 11 and earlier) and `android:dataExtractionRules` (Android 12 and later, cloud backup and device transfer). The page cache and the snapshot live in the no-backup folder, which no backup takes; the rules leave out the web view's folder (`app_webview`), which holds the session cookie.
- **Touches.** A touch is ignored while another app's window covers the app (`NavreeConfig.filterObscuredTouches`, on by default).

## What an app must do itself

- **Pages that load from another host.** A page the web view shows may load from another host only when that host is in `NavreeConfig.webHosts` (`checkout.pay.example`, `*.cdn.example`, with `:port` where it is not 443; `https` only). An app that lets a payment frame or a captcha into its page's policy names the same host once more in `webHosts`. A host there serves what a page loads inside it and nothing else: never a page itself, a native request, a stream, a picture or a cookie of the client's own requests. A `*.` pattern needs at least two labels after it (`*.cdn.example`, never `*.com`); one under a shared hosting name (`*.cloudfront.net` and the like) trusts everybody who publishes there. Three things a listed host does not change:
  - A frame from a listed host can take the app to another screen after a tap, as any frame can in a browser: the core then opens an address of the app, or the system's browser for one elsewhere.
  - A widget that needs its own cookies inside the page (some captchas and payment frames) will not work even when listed: the web view refuses other sites' cookies.
  - A bank's card-verification pages sit on hosts nobody can list, so an app sends a card payment to the system's browser tab (a Custom Tab: a link the page marks to open in the system's browser inside the app), not into the web view.
- **Its own backup rules.** An app that sets `android:fullBackupContent` or `android:dataExtractionRules` itself replaces the library's (the manifest merger reports the clash; resolve it with `tools:replace="android:fullBackupContent,android:dataExtractionRules"` on the app's `<application>`). Its rules must then leave out the web view's folder too: `<exclude domain="root" path="app_webview" />` in `<full-backup-content>`, and in both `<cloud-backup>` and `<device-transfer>` of `<data-extraction-rules>`. An app that sets `android:allowBackup="false"` has no cloud backup, but on Android 12 and later device transfer still follows the extraction rules. Backup rules take no patterns, so the library cannot name every folder that may hold a session. What an app checks for itself: a web view data folder of its own (`WebView.setDataDirectorySuffix` makes `app_webview_<suffix>`, to leave out as `app_webview` is); the push service's own files, which hold this install's token (Firebase does not document their names; Android's backup guide names push registration tokens as something to leave out); and, on Android 16 QPR2 and later, a `<cross-platform-transfer>` section, which the library's rules do not have, if the app turns that transfer on.
- **The screen.** `navree_screen` in resources (or `NavreeConfig.screen`) says how much of the app the system may show elsewhere:
  - empty (the default): the system's own behaviour;
  - `hidden_in_recents`: no picture of the app in the recent-apps list, with `Activity.setRecentsScreenshotEnabled(false)` on Android 13 (API 33) and later; before that the only means is the secure window flag, so there it behaves as `no_capture`;
  - `no_capture`: no screenshot, no screen recording, no picture in the recent-apps list and nothing on a display that is not secure, with `WindowManager.LayoutParams.FLAG_SECURE` (API 1).
  A value the library does not know is taken as `no_capture`.
- **Notifications.** What a locked screen shows of a notification the library draws is `navree_notification_lock_screen` in the app's resources: empty (the default) for the system's way, where the person's own lock-screen setting decides whether the title and text show (where it hides them, the app's name and "New notification" stand in); `nothing` for nothing of it on a secure locked screen (`VISIBILITY_SECRET`). The library draws a message only when Firebase hands it over: a **data message** (`title`, `body` and `href` in `data`, no `notification` block) always; a message with a `notification` block only while the app is in front. A message the server sends as a `notification` message is drawn by the push SDK itself while the app is in the background, with its title and text, and never reaches the library: an app that needs the option to hold has its server send data messages. Signing out removes the app's notifications from the shade.
- **The activity.** As the template does: `android:taskAffinity=""` so no other app's activity can join the app's task, `android:launchMode="singleTop"`, and an app-link filter (`android:autoVerify="true"`) for the app's host that names only the paths the app opens (`android:path`, `android:pathPrefix`) and the path the sign-in returns to.
- **Pictures from another host.** Pictures load from the app's origins; a host that serves them (a CDN) is named in `NavreeConfig.pictureHosts` and is used only over `https`.
- **Shrinking.** The library's consumer rules keep the core's native methods and the serializers; an app needs no rules of its own for them.
