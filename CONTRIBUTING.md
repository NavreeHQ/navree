# Contributing to Navree

Thank you for helping. This guide is for people working on Navree itself:
how the repository is laid out, how to build and test it, how the docs and
the code change together, and how releases happen. To build an app *with*
Navree, start with the
[documentation](https://navree.com/docs/prologue/introduction/).

For a question or an idea, open a
[discussion](https://github.com/NavreeHQ/navree/discussions). For a bug, open
an issue with the bug form and say which crate it is in. For a
vulnerability, never open an issue: write to security@navree.com (see
[`SECURITY.md`](SECURITY.md)).

When you add a crate, give it a row in the [crate hierarchy](#crate-hierarchy)
table below, in `crates/navree/tests/dependency_graph.rs` (HIERARCHY) and on
the docs page `docs/architecture/crate-hierarchy.mdx`.

## The repositories

Navree lives in a few repositories under [NavreeHQ](https://github.com/NavreeHQ):

| Repository | What it holds |
|---|---|
| [`navree`](https://github.com/NavreeHQ/navree) | This repository: the crates, the command line, the docs, the agent skills and the npm packages |
| [`skeleton`](https://github.com/NavreeHQ/skeleton) | The starting point of a new app: the output of `navree new`, kept current at each release |
| [`crm`](https://github.com/NavreeHQ/crm) | The reference CRM, an app built on the published crates and packages |
| [`benchmarks`](https://github.com/NavreeHQ/benchmarks) | Navree's benchmark app, harness, method and results |

navree.com is built from this repository's `docs/` and crate manifests, in a
separate private repository for the site itself.

## This repository

One Cargo workspace of small module crates, one pnpm workspace of npm
packages, the docs and the example apps:

- `crates/`: the crates that are published, one per module, plus the
  `navree` facade and the `navree-cli` command line (which also holds the
  starter kits in `templates/`). Three crates are for the repository only
  and are never published: `docs-snippets`, `skill-snippets` and
  `navree-template-peak`.
- `docs/`: the documentation, as MDX pages in one folder per section. The
  docs sit beside the code, so a change to an API and to its page is one pull
  request. `docs/ui-data/` is generated by `cargo run -p ui-docs` and is never
  edited by hand.
- `skills/`: the agent skills, one `SKILL.md` per directory. `navree
  skills:install` copies them into a project.
- `packages/js/`: the front-end npm packages (`@navree/client`,
  `@navree/bff`, `@navree/next`, `@navree/nuxt`, `@navree/theme`), a pnpm
  workspace, with `deepmerge`, a private helper they share.
- `apps/`: apps that are not published.
  - `board-demo`, `store-demo` and `inbox-demo`: example apps on Navree UI.
    A board of 20,000 cards that move by mouse, touch or keys; a store's
    back office with 200,000 orders; a support inbox with 100,000
    conversations read lazily. All on SQLite, all live over server-sent
    events. Their views are drawn into the docs by `ui-docs`.
  - `theme-demo` and `agent-demo`: a themed app and an app that uses the AI
    SDK.
  - `ui-docs`: writes `docs/ui-data/`. `ui-proof` and `ui-table-proof` serve
    every component and the data table for the browser tests in `e2e/ui`.
  - `system-app`: the system app, one Navree application that wires every
    package and tool. It is built into a Docker image and run under load by
    the system tests in `e2e/` (see [`e2e/README.md`](e2e/README.md)).
- `e2e/`: the system tests and the browser tests (the compose stack, load
  scenarios, UI tests).
- `fuzz/`: fuzz targets for the parsers of untrusted input (its own
  workspace).
- `supply-chain/`, `deny.toml`, `osv-scanner.toml`, `.semgrep/`,
  `.gitleaks.toml`: the supply-chain and static-analysis configuration.
- `scripts/`: helpers for CI and local services.
- `xtask/`: the release tool, run as `cargo xtask release ...` (see
  [Releases](#releases)).
- `.github/`: CI, release workflows, code owners and the issue and pull
  request templates.

## Crate hierarchy

The crates form layers: the framework from L0 to L5, ecosystem
libraries at L6, packages built on them at L7, and the facade and CLI at L8.
A crate may depend only on crates in lower layers, dev-dependencies included,
and its runtime dependencies must also match the table of allowed edges
in `crates/navree/tests/dependency_graph.rs`. Cross-cutting needs (audit,
events, broadcasting, sessions, health checks, jobs, the current principal)
go through traits in `navree-contracts`, so modules don't depend on each
other sideways. `crates/navree/tests/dependency_graph.rs` checks every edge on
each test run.

```
L9+ apps/ (example apps and the system app, built on the facade)
L8  navree (facade: re-exports + prelude)       navree-cli (binary `navree`; no runtime navree deps, uses navree-dock, navree-harbor and navree-navigator)
L7  navree-billing  navree-search  navree-lighthouse  navree-logbook  navree-fleet  navree-helm  navree-workflows  navree-media  navree-directory  navree-domains (packages built on other packages)
L6  navree-social  navree-sso  navree-webhooks  navree-integrations  navree-sheets  navree-oauth  navree-flags  navree-settings  navree-graphql  navree-grpc  navree-mcp  navree-ai  navree-micro  navree-i18n  navree-documents (ecosystem libraries)
L5  navree-auth  navree-workspace  navree-redis  navree-mongo
L4  navree-session  navree-validation  navree-queue  navree-audit  navree-access  navree-schedule  navree-notify  navree-ui  navree-orm  navree-browser
L3  navree-db  navree-testing  navree-observe  navree-api  navree-mail  navree-realtime  navree-storage  navree-time
L2  navree-http  navree-log  navree-crypto  navree-events  navree-view  navree-cache  navree-http-client  navree-schema  navree-navigator (dev tool)
L1  navree-contracts  navree-config  navree-telemetry
L0  navree-kernel  navree-bounded  navree-pdf  navree-glob  navree-markdown  navree-openapi    navree-macros  navree-orm-macros  navree-i18n-macros  navree-validation-macros (proc-macros; no runtime navree deps)   navree-dock, navree-harbor (tools; no navree deps)
```

## Requirements

- Rust 1.95 or newer (edition 2024; CI uses the current stable release). On
  Windows, the MSVC build tools (the workspace's tests run on SQLite, compiled
  from source through the bundled `libsqlite3-sys`; a PostgreSQL or MySQL
  build of `navree` compiles none).
- Optional: [sccache](https://github.com/mozilla/sccache), to share compiled
  dependencies between target directories. The repository doesn't set a
  compiler wrapper; set `RUSTC_WRAPPER=sccache`, or `rustc-wrapper =
  "sccache"` under `[build]` in a Cargo config outside the repository (for
  example `~/.cargo/config.toml`).
- For the npm packages, the docs data checks and the browser tests: Node.js 20.9 or newer (CI uses 24) and pnpm 11.

No OpenSSL, CMake or NASM is needed: TLS is rustls with the `ring` provider
everywhere. No database server is needed either: tests and development use
SQLite.

## Running the tests

### Rust

```sh
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all -- --check
```

`cargo test --workspace` runs every crate's unit and integration tests,
including the docs tests and the dependency-graph test. Each test that
touches a database gets its own temporary SQLite file.

Several builds (people or CI jobs) often run at the same time. Cargo
locks the target directory, so give each one its own (and, if you use it, let
sccache share the compiled dependencies):

```sh
CARGO_TARGET_DIR=target/builds/<label> cargo test -p <crate>
```

For example `CARGO_TARGET_DIR=target/builds/http cargo test -p navree-http`.
Use `-p <crate>` while working on one crate, and keep `CARGO_BUILD_JOBS`
moderate when memory is tight.

### Rust, against real servers

A suite that needs a server reads its address from a `NAVREE_TEST_*` variable
(`NAVREE_TEST_POSTGRES_URL`, `NAVREE_TEST_MYSQL_URL`, `NAVREE_TEST_MONGODB_URL`,
`NAVREE_TEST_REDIS_URL`, `NAVREE_TEST_S3_URL`, `NAVREE_TEST_GCS_URL`,
`NAVREE_TEST_AZURE_URL`, `NAVREE_TEST_MAILPIT_URL`, and so on; the module comment
of each suite names its own). Without the variable the test prints a `SKIPPED`
notice and passes, so a plain `cargo test` on a laptop proves nothing about a
server. Set `NAVREE_TEST_REQUIRE_SERVICES=1` to make a missing server, Chrome,
Node.js or FFmpeg a failure; CI and the final gate always set it. Crates that
take their database from `NAVREE_TEST_DATABASE` (`sqlite`, the default,
`postgres` or `mysql`) run once per value.

With Docker, `scripts/ci-services.sh start` starts every server the suites use
(PostgreSQL with TimescaleDB, pgvector, MySQL, MariaDB, MongoDB, Redis, S3,
Google Cloud Storage and Azure Blob emulators, Qdrant, Typesense, Meilisearch,
stripe-mock, Pebble, NATS, MQTT, Kafka, RabbitMQ and four Mailpit servers) on
`127.0.0.1`, waits until each answers, and prints the variables, including
`NAVREE_TEST_REQUIRE_SERVICES=1`. The servers are described in
`scripts/services/compose.yml`. A server that does not answer is started once
more and then named, with its log and the memory of the machine, and the rest
are left running. `scripts/ci-services.sh drop SERVICE...` removes only the
servers named, `scripts/ci-services.sh stop` removes them all, and
`scripts/ci-services.sh check-skips LOG` counts the skip notices in the output
of a run made with `cargo test ... -- --show-output`; the by-design skips are
listed in `scripts/services/skips.allow`. On Windows without Docker,
`scripts/dev-databases.ps1 start` runs PostgreSQL with TimescaleDB, MySQL and
MongoDB from portable archives.

`.github/workflows/rust-suites.yml` runs every suite on demand and on a
schedule: weekly on Linux against all of those servers, with each
database-switchable crate on SQLite, PostgreSQL, MySQL and MariaDB (11.4 and
10.6), and monthly on Windows against SQLite. It also builds the projects
`navree new` generates once a month.

The connectors that need more than one container run against real servers and
emulators in a second workflow, `.github/workflows/integrations.yml` (weekly,
and on demand): SMTP over TLS, SES (Moto), IMAP and POP3 (GreenMail),
Gmail's Pub/Sub push, SAML and OpenID Connect (Keycloak), LDAP (OpenLDAP),
SCIM (scim2-cli), OTLP (an OpenTelemetry Collector), DNS (CoreDNS), Dock, Harbor
(an Ubuntu host with systemd and sshd) and the paid providers' sandbox modes.
`scripts/integration-services.sh start [mail|identity|infra|harbor]` starts the
servers of `scripts/services/integrations.yml` and prints their `NAVREE_TEST_*`
variables. Their tests are marked `#[ignore]`: run them with
`cargo test ... -- --ignored`.

## Dependencies and security

Every new or updated Rust dependency goes through three gates in CI
(`.github/workflows/supply-chain.yml` and `vulnerabilities.yml`), which you
can run locally first:

```sh
cargo install --locked cargo-deny cargo-vet   # once
cargo deny check                              # advisories, licenses, bans, sources (deny.toml)
cargo vet                                     # every crate audited or exempted (supply-chain/)
```

- `deny.toml` allows crates.io, a fixed list of permissive licenses, and bans `openssl`,
  `openssl-sys`, `native-tls` and `rsa`; use rustls and ring. A new duplicate
  version of a crate warns; remove it or name it under `skip` with a reason.
  A vulnerability that has no fixed release gets an entry with a reason and
  an expiry date in both `osv-scanner.toml` and `deny.toml`.
- A new crate version needs a review or a deliberate exemption in
  `supply-chain/`; [`supply-chain/README.md`](supply-chain/README.md) says how.
- GitHub Actions are pinned to a full commit SHA with the version in a
  comment (`uses: owner/action@<sha> # v1.2.3`), workflows declare the least
  `permissions:` they need, and checkouts that don't push set
  `persist-credentials: false`. Dependabot proposes SHA bumps.
- Changes to `.github/`, `deny.toml`, `supply-chain/` and the security-critical
  crates (auth, crypto, sso, oauth, session, access, orm, schema, db, http)
  need a review from the code owners (`.github/CODEOWNERS`).
- Tagged releases get a CycloneDX SBOM from `.github/workflows/sbom.yml`.
- Semgrep and Gitleaks run in CI on every change; see
  [Static analysis](#static-analysis) for what they check and how to run
  them locally.
- Report a vulnerability to security@navree.com, never in a public issue; see
  [`SECURITY.md`](SECURITY.md).

### Fuzzing

Every parser that reads untrusted bytes has a libFuzzer target in `fuzz/` (its
own workspace: it needs a nightly compiler). A target checks that its parser
does not panic, hang (`-timeout`) or use unbounded memory (`-rss_limit_mb`),
and, where it can, an invariant: print and parse give the same value, a signed
token's claims read back, a rendered query holds only the user's words.

| Target | What it feeds |
|---|---|
| `jose_token`, `jose_keys` | compact JWS verification against fixed keys and key sets; PEM, DER, certificates and JWKs |
| `auth_jwt` | the bearer-token check of `JwtService`, against an oracle for each claim |
| `openapi_schema`, `api_markdown` | `Schema` reading JSON and writing it back; the reference page's Markdown, whose output holds only what the reader writes |
| `mcp_protocol`, `mcp_server` | JSON-RPC parsing and stdio framing; a booted MCP server over HTTP and stdio |
| `http_client_ip`, `http_cors` | `X-Forwarded-For`, `X-Real-IP`, trusted proxies, the rate-limit key; CORS origins; signed URLs |
| `http_compression` | `Accept-Encoding` and the response headers that decide compression, and bodies handed over in any pattern of chunks, waits, trailers and failures: a gzipped body decodes to what the handler sent, in frames of at most 4 KiB |
| `http_routing`, `http_extract` | route patterns, path matching and precedence, path checks and parameter decoding; query strings, forms and JSON bodies through the extractors |
| `http_multipart`, `ws_handshake` | `multipart/form-data` boundaries, delimiters, part heads, `Content-Disposition` parameters and limits, split into chunks of every size and checked against a reference that reads the body whole; the headers of a WebSocket handshake |
| `host_names` | email domains, custom-domain normalization, the `Host` header |
| `glob_match` | a glob pattern against a text, checked against a table-driven matcher |
| `docx_read` | Word files: any bytes as a file, and any bytes as the main part of a well-formed package, within tight limits |
| `sso_saml_response`, `sso_saml_metadata`, `sso_xml` | SAML responses, identity provider metadata, XML and Canonical XML |
| `webhooks_signatures` | the signature headers and bodies of every incoming webhook verifier |
| `phone_parse` | phone numbers from any text in any region: what parses fits its plan, is E.164 and reads back from every format it writes |
| `validation_international` | E.164 phone numbers, names, countries, locales, sanitized HTML |
| `validation_html` | the HTML sanitizer under policies built from the input: the output parses back to the tree it checked and holds nothing the policy doesn't allow |
| `search_query` | query text and filter values rendered for each search engine |
| `sheets_workbook` | uploaded spreadsheets read into a table: whole files, and XLSX, XLSB and ODS workbooks built around one fuzzed part |
| `sheets_xls` | XLS workbooks: the compound file, and the BIFF5 and BIFF8 records of the workbook stream |
| `schedule_cron` | cron expressions: `parse`, `next_after`, `is_due` |
| `config_sources` | the `.env` parser, TOML and JSON files, environment merging |
| `qr_roundtrip`, `totp_uri` | QR encode then decode with `rqrr`; `otpauth://` URIs and base32 secrets |
| `scim_filter`, `mail_inbound`, `micro_envelope`, `time_parse` | SCIM filters and paths; raw MIME messages; broker envelopes; zone names, days and send windows |
| `openapi_client` | OpenAPI documents (JSON, deep nesting, `$ref` chains, lists of types, odd descriptions) through the generator behind `navree openapi:client`; the file it writes has matching braces and its five declarations |
| `small_parsers` | the logbook search box, OAuth `scope`, `X-Request-ID`, the app key, Web Push keys |
| `pdf_read`, `pdf_content` | whole PDF files read as navree-documents and navree-media read them (cross-reference, repair, object streams, filters, encryption, page tree, text), and saved again; the operations of a content stream |

Run them in Docker, so the nightly toolchain and cargo-fuzz are the pinned
ones (`fuzz/Dockerfile`) and nothing is built inside the checkout. The script
builds the image, mounts the repository and keeps build output, the cargo
registry and the working corpora in named volumes:

```sh
fuzz/docker.sh list                                  # the targets
fuzz/docker.sh build                                 # build every target
fuzz/docker.sh run jose_token -- -max_total_time=300 -timeout=10 -rss_limit_mb=2048 -max_len=8192
```

Without the script, the same thing by hand (one line):

```sh
docker build -t navree-fuzz fuzz && docker run --rm -v "$PWD:/work" -v navree-fuzz-target:/fuzz-target -v navree-fuzz-registry:/usr/local/cargo/registry -v navree-fuzz-corpus:/corpus navree-fuzz cargo fuzz run jose_token /corpus/jose_token /work/fuzz/seeds/jose_token -- -max_total_time=300
```

- Seeds (test fixtures and documentation examples) are in `fuzz/seeds/<target>/`
  and always read; what a run finds goes to the corpus volume.
- A crash is written to `fuzz/artifacts/<target>/crash-*`. Reproduce it with
  `fuzz/docker.sh run <target> artifacts/<target>/crash-...`, minimize it
  with `fuzz/docker.sh tmin <target> artifacts/<target>/crash-...`, then fix the
  parser and add a regression test to **the crate's own tests** (not only to `fuzz/`).
- A new parser of untrusted input gets a target: add
  `fuzz/fuzz_targets/<name>.rs`, a `[[bin]]` entry in `fuzz/Cargo.toml`, seeds,
  and a line in the table above (CI runs every target `cargo fuzz list`
  prints). Internals a target needs are exposed through a
  hidden `fuzzing` feature of the crate (`navree_mcp::fuzzing`, for example),
  never through the public API.
- CI (`.github/workflows/fuzz.yml`) builds the targets once and runs them one
  after another in a single job: 15 seconds each on pushes to main that change
  `fuzz/`, 5 minutes each every Sunday, and as long as you ask when you run the
  workflow by hand. It caches the corpora between runs and uploads the inputs
  that crashed.

## Static analysis

`.github/workflows/sast.yml` runs two scanners on every push to `main`, every
pull request and once a week. A finding fails the job. Each job sends its SARIF
report to GitHub code scanning and keeps the SARIF and text reports as a
workflow artifact (`semgrep-reports`, `gitleaks-reports`, 30 days).

- **[Semgrep](https://semgrep.dev)** (open source) runs the registry rulesets
  for Rust, TypeScript, JavaScript, React, GitHub Actions and Dockerfiles, and
  Navree's own rules in [`.semgrep/`](.semgrep/). Warnings and errors fail the
  run. On a pull request it reports only what the change introduces; the weekly
  run scans everything again, so a registry rule that learns something new
  fails there rather than staying hidden.
- **[Gitleaks](https://gitleaks.io)** scans every commit on every branch and
  the working tree for secrets, with the allowlists in
  [`.gitleaks.toml`](.gitleaks.toml). On a pull request it scans the commits
  the pull request adds.

Navree's own rules, one file per rule in `.semgrep/` with the reasoning at the
top of the file and a fixture that proves what it flags and what it leaves alone:

| Rule | What it stops |
|---|---|
| `navree-sql-built-from-strings` | SQL text built with `format!` (a DML statement with an interpolated value) and passed to a statement-running API or made into a statement; bind parameters instead. `navree-sql-built-from-strings-in-async` matches the same inside `async` blocks, where Semgrep's taint analysis does not look |
| `navree-shell-command-string` | `sh -c`, `bash -c`, `cmd /C`, `powershell -Command`: a string handed to a shell; spawn the program and pass arguments |
| `navree-process-outside-tooling` | spawning a process outside the crates that own that (CLI, Harbor, Dock, browser, documents, media, fleet, Navigator, test kit) |
| `navree-tls-verification-disabled` | certificate verification switched off, in Rust and in Node code |
| `navree-secret-in-log` | a password, token, key or cookie recorded in a `tracing` event |
| `navree-unwrap-on-request-data` | `.unwrap()` / `.expect()` on a value derived from a handler's request extractors |
| `navree-no-sea-orm` | any use of `sea_orm`, `sea_orm_migration` or `sea_query` in source, and any `sea-*` dependency in a `Cargo.toml` (`.semgrep/no-sea-orm.yml`): navree-db, navree-orm and navree-schema are the data layer |
| `navree-raw-html` | `dangerouslySetInnerHTML`, `innerHTML =`, `insertAdjacentHTML`, `document.write`; `navree-raw-html-vue` does the same for `v-html` |
| `navree-workflow-pull-request-target` | a workflow triggered by `pull_request_target` |
| `navree-workflow-unpinned-action` | an action not pinned to a full commit SHA |

**Run them locally.** You need Docker; the scanner images are pinned by digest in
`scripts/sast.sh`, the same script CI runs.

```sh
scripts/sast.sh semgrep-test    # the custom rules against their fixtures
scripts/sast.sh semgrep         # Semgrep over the repository (needs network for the registry rulesets)
scripts/sast.sh secrets         # Gitleaks over the history and the working tree
scripts/sast.sh all             # all three

SAST_CUSTOM_ONLY=1 scripts/sast.sh semgrep         # only .semgrep/, fast and offline
SEMGREP_BASELINE=origin/main scripts/sast.sh semgrep   # only what your branch adds
```

Reports are written to `sast-reports/` (git-ignored). The first full Semgrep run
takes a few minutes.

**Fix first.** Most findings are real: bind the parameter, drop the shell,
return an error instead of unwrapping. Only suppress a finding that is a false
positive, and always say why in the same place.

**Suppress a Semgrep false positive** with a `nosemgrep` comment naming the rule,
on the line before the finding (or at its end), with the reason above it:

```rust
// A list of `?` placeholders built here; every value is a bound parameter.
// nosemgrep: navree-sql-built-from-strings
let rows = uow.fetch_all(Statement::new(backend, sql, values)).await?;
```

In JSX the comment goes between the attributes; in a Dockerfile or a workflow it
is a `#` comment; in a Vue template it is `<!-- nosemgrep: navree-raw-html-vue -->`.
Name the rule, not just `nosemgrep`, so one suppression never hides another
rule's finding. A suppressed finding is left out of the report sent to code
scanning, which would otherwise show it as an open alert; every finding,
suppressed ones included, stays in `sast-reports/semgrep-with-suppressed.sarif`.

**Suppress a Gitleaks false positive** in `.gitleaks.toml`: add an `[[allowlists]]`
entry with a `description` that says why the value is fake (a test fixture, a
documented sample value, a throwaway local secret), and keep it narrow, an exact
value or a fixtures path rather than a whole directory of source. For a single
line, a trailing `gitleaks:allow` comment works too. A real credential is never
allowlisted: revoke and rotate it, then tell security@navree.com.

## Design decisions

- **Token authentication.** Stateless JWT access tokens (HS256, 15 minutes)
  plus opaque rotating refresh tokens (30 days, SHA-256 at rest; reusing
  one revokes its whole family), a pluggable `Strategy` trait, a global
  guard with a `#[public]` opt-out and a `CurrentUser` extractor.
  `navree-session` (cookie sessions and CSRF) is a separate, optional
  module.
- **The browser never holds tokens.** A Next.js or Nuxt server is a BFF
  (`@navree/bff`) that keeps them in httpOnly cookies and forwards
  `Authorization: Bearer`.
- **One error shape.** Every error is `{statusCode, message, error, code}`,
  with validation failures as 400 plus `errors: {field: [..]}`; a front end
  branches on `code`, never on the English message. Statuses 422 and
  419 are not used.
- **PostgreSQL.** The PostgreSQL-only paths (`FOR UPDATE`, `SKIP LOCKED`,
  advisory locks) are written behind `Backend` checks and the `postgres`
  feature, and the benchmarks repository runs on PostgreSQL;
  the default test suite runs on SQLite, and the database tests run on
  real PostgreSQL/TimescaleDB, MySQL and MongoDB servers when
  `target/test-databases.env` is sourced (`scripts/dev-databases.ps1 start`).
- **Real time is in-process.** Navree ships a Pusher-protocol WebSocket
  server, so pusher-js and any Pusher client connects. Processes that don't
  serve the sockets, such as queue workers, send their broadcasts to the
  serving process over a signed HTTP relay.
- **Framework crates implement `Module`, `Injectable` and `Controller` by
  hand** instead of using `navree-macros`, which sits at L0 with no runtime
  dependencies. Apps and the facade's tests use the macros.

  --all-targets -- -D warnings` for the crates you changed before you push.
- Changes to `.github/`, `deny.toml`, `supply-chain/` and the security-critical
  crates need a review from the code owners (`.github/CODEOWNERS`).

## Releases

You do not need this section to contribute. It says how a release happens.

- **One version for everything.** All published crates, the `navree-cli`
  starter kits and the five `@navree/*` packages share one `X.Y.Z`, and each
  release has one tag, `vX.Y.Z`. The crates require each other at that exact
  version (`=X.Y.Z`), so a release always resolves as the set that was tested.
- **Prepare.** The *Prepare release* workflow takes a version, sets it
  everywhere with `cargo xtask release prepare <version>`, adds a heading to
  `CHANGELOG.md` and opens a pull request. Edit the changelog wording in that
  pull request. `cargo xtask release check` fails when a version differs, a pin
  is not exact or a crate depends on another in a loop.
- **Publish.** Merging that pull request and pushing the `v*` tag starts the
  *Release* workflow: it runs the checks and a dry run of the whole publish,
  then publishes the crates in dependency order (`cargo xtask release publish`,
  which resumes after a rate limit or a failure), publishes the npm packages
  with provenance, builds the command line for Linux, macOS and Windows and
  writes the GitHub Release. Publishing needs a maintainer's approval in the
  repository's release environments, and no token lives in the repository.
- **Patch and minor releases** follow the same steps from `main`; a patch
  adds no public API. What counts as public API, how long a line is supported
  and the MSRV policy are in the
  [versioning and support](https://navree.com/docs/prologue/versioning-and-support/)
  page.

| `apps/*-demo`, `apps/ui-*` | Example apps on Navree UI, the docs data writer and the pages the browser tests drive |
| `apps/system-app` | The system app: a Navree application wiring every package and tool, with domain models and seeders, for the system tests |
| `e2e/` | The system tests: the compose stack (`docker/`), the system app's Dockerfile, k6 load profiles and scenarios (`load/`), HTTP check rows (`checks/`), browser screenshots (`browser/`), the browser tests (`ui/`) and `run.sh` |
| `fuzz/` | Fuzz targets for the parsers of untrusted input (its own workspace) |
| `xtask/` | The release tool (`cargo xtask release ...`) |
| `scripts/` | CI and local service helpers |
| `supply-chain/`, `deny.toml`, `.semgrep/`, `.github/` | The supply-chain, static-analysis and CI configuration |

### Features and drivers

- Databases: every driver is its own opt-in feature of `navree` (or
  `navree-db`): `postgres`, `mysql` and `sqlite` (the bundled SQLite library,
  the one place that compiles it). Crates whose tests run on SQLite turn
  `navree-db/sqlite` on in their `[dev-dependencies]`. `crates/navree/tests/dependency_graph.rs`
  checks that `navree` with `postgres` and without `sqlite` has no
  `libsqlite3-sys`.
- External versions live only in the root `[workspace.dependencies]`; crates
  use `dep = { workspace = true }`.
