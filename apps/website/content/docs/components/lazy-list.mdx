`LazyList` is the default way to show a list that can grow without end: an inbox, a conversation, a feed, a log. The page draws its first page. When the reader nears either end, the `lazy` module asks your server for the next page, by the cursor of the item at that end. It never asks by offset, so a page deep in the list costs what the first does. The [support inbox example app](/showcase/inbox/) draws its conversations and its threads with it.

```rust
use navree::ui::*;

LazyList::new("conversations", "Conversations", "/inbox/rows")
    .items(first_page.iter().map(|row| LazyItem::new(row.id.to_string(), row.cursor(), draw(row))))
    .more_after(format!("/inbox?after={}", last.cursor()))
    .since(revision.to_string())
    .live_on(LiveStream::topics(["conversations"]).on("conversations"), LazyEnd::Start)
```

## Lazy is the default

Draw a long list with `LazyList` unless you have a reason not to:

- **The first screen costs one page.** Fifty rows, or thirty messages, whatever the table holds.
- **Every next page costs the same.** Answer it by keyset, `WHERE (last_at, id) < (?, ?)`, with an index that ends in the key.
- **The page stays small.** Past `.max(...)` items (300 by default) the far end is dropped and fetched again on the way back, so the page holds the same few hundred nodes after the reader has scrolled through thousands.

Choose a [DataTable](/docs/ui/data-table/) instead when people compare and act on rows: sort by any column, filter by many at once, select across pages, export. Choose a `LazyList` for a stream read in one order.

## Your server's side

The runtime asks the list's source with `dir=start` or `dir=end` and the `cursor` of the item at that end, or with `dir=live` and `since`. `LazyQuery` reads the question and never fails. `LazyPage` answers a page of items and whether more lie beyond:

```rust
async fn rows(ask: LazyQuery, uow: Uow) -> Result<LazyPage> {
    let (rows, more) = match ask.ask() {
        LazyAsk::After(cursor) => older_than(&uow, cursor, 50).await?,
        LazyAsk::Before(cursor) => newer_than(&uow, cursor, 50).await?,
        _ => first_page(&uow, 50).await?,
    };
    Ok(LazyPage::new(rows.iter().map(item), more))
}
```

Cursors compare as text when a live item is placed, so make them sort: pad the numbers (`format!("{last_at:012}{id:012}")`).

A time in whole seconds ties when two things happen in the same second, and the id then puts them in the order they were made, not the order they happened. Put a number that grows with every write between the two, such as the revision the change was written at: order by `(last_at, last_rev, id)`, page by `WHERE (last_at, last_rev, id) < (?, ?, ?)`, and write the cursor as `format!("{last_at:012}{last_rev:012}{id:012}")`. Of two items written to in one second, the later then comes first.

## Oldest first

`.order(LazyOrder::Ascending)` runs the cursors the other way: a conversation, oldest message first, opened at its newest. Older messages load as the reader scrolls up, and the message they were reading stays where it was.

## Live

With `.since(revision)` and `.live_on(live, end)`, the list asks what changed whenever its stream says one of its names: usually a topic on the app's [live hub](/docs/ui/live-hub/), which your code nudges when it writes (`.live_from(url, event, end)` follows any other stream). Answer with `LazyPage::changes(items, new_revision, gone_keys)`: an item the list has changes where it stands, node by node, so a focused link, a caret and the scroll stay where the reader left them; a new one goes where its cursor sorts, and a gone one goes. No item is ever in the list twice. Send only what changed. The ask carries the cursors of the window the page holds, `LazyQuery::window()`, so you can also send an item whose text moves with no write of its own, such as a clock counting down, when it reads differently than it did. An answer that holds only part of what changed says `.more(true)`, and the list asks again.

### Take the revision where it commits

The list moves its revision to the newest one an answer holds, so a change must never become visible after a reader has seen a later one. Take the revision inside the transaction that writes the change, from something one writer holds at a time:

```rust
// In the writing transaction: the row stays locked until it commits.
let rev: i64 = uow
    .fetch_scalar(&Statement::portable("UPDATE desk SET rev = rev + 1 WHERE id = 1 RETURNING rev", []))
    .await?;
```

On SQLite, which has one writer at a time, a row id the database gives as it inserts works too. A number from a counter in memory, taken before the write, does not: a later number can commit first, and the reader moves past the earlier one for good.

### Announce what arrives

`.announce_new("{n} new messages", "A new message")` reads out items that arrive live, politely, once they stop coming: one announcement for a burst. An item says its own words when it arrives alone, `LazyItem::announce("New message from Harleen Kaur")`, and one the reader made themselves, `LazyItem::quiet()`, says nothing.

`.seen_by(url)` tells your server, with a `POST` of an empty form, that the reader saw what the list shows: when the page shows it, and when new items arrive, only while the page is in sight. Use it to mark a conversation read, so opening its page with a `GET` changes nothing. With no script, offer a button for it.

`.view(...)` names what the list shows. A page drawn again for the same view, when someone opens a row, keeps the rows the reader loaded and where they scrolled. `.current(key)` marks the row the page is about.

## Keyboard and accessibility

<UiA11y>

- The items are a list (`role="list"`) named by the label. Each end is a link, "Show more" by default: it is what loads with the keyboard, and what a page with JavaScript off follows.
- A status line announces each page that arrives, "50 more loaded", and, with `.announce_new`, what arrives live, once a burst is over.
- Items added above keep the reader's place, so focus and the reading position don't jump. A live change keeps the focused element itself, even when its item moves.
- With JavaScript off each end goes to a page that holds the next part of the list.

</UiA11y>
