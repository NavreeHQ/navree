## Introduction

<Badge feature="observe" /> In one binary, the [request log line](/docs/basics/logging/#the-request-log-line) and its request id tell you what a request did. Across services, one click in the web app becomes an HTTP request to `crm-api`, a `deals.move` message to the deals service, a few queries, a `deal.won` event to two more services, and a queued mail. A **trace** ties them together: each step is a **span** with a start, a duration, attributes and a parent, and the spans of one click form one tree.

Navree records traces with [OpenTelemetry](https://opentelemetry.io), the open standard for them:

- every request, message, gRPC call, GraphQL operation, query, job and mail is a span, named and labeled with OpenTelemetry's conventions;
- the trace context travels with every hop: HTTP calls, messages and events, gRPC calls and queued jobs;
- spans go to any OpenTelemetry backend over OTLP;
- every log line carries its trace id;
- [Lighthouse](/docs/tools/lighthouse/) links each issue to the trace where it happened.

Spans and propagation are always on, so trace ids appear in your logs from the first request. Export starts when you give Navree an endpoint.

```text
GET /api/v1/deals/{id}/move             crm-api         182 ms
+- send deals.move                      crm-api         171 ms
   +- process deals.move                deals           164 ms
      +- SELECT deals                   deals             2 ms
      +- UPDATE deals                   deals             3 ms
      +- db.transaction commit          deals             4 ms
      +- publish deal.won               deals             2 ms
         +- process deal.won            notifications    38 ms
         |  +- INSERT notifications     notifications     2 ms
         |  +- dispatch mail.send       notifications     1 ms
         |     +- job mail.send         notifications   310 ms
         +- process deal.won            activities       12 ms
            +- INSERT activities        activities        2 ms
```

## Exporting traces

Tracing is part of `ObserveModule`, in the `observe.tracing` section. Point it at an OTLP endpoint, usually an OpenTelemetry Collector:

```toml title="config/app.toml"
[observe.tracing]
endpoint = "http://127.0.0.1:4317"
```

That's all a service needs. Its spans are named after `micro.service` (or `app.name`), batched in the background and sent over OTLP/gRPC.

| Key | Default | Meaning |
|---|---|---|
| `observe.tracing.enabled` | `true` | Record spans and propagate trace context. `false` turns both off. |
| `observe.tracing.endpoint` | none | The OTLP endpoint. Without one, nothing is exported. |
| `observe.tracing.protocol` | `grpc` | `grpc` (port 4317) or `http` (OTLP/HTTP with protobuf, port 4318). |
| `observe.tracing.headers` | `{}` | Headers sent with every export, such as a vendor's API key. |
| `observe.tracing.service_name` | `micro.service`, then `app.name`, then the binary's name | The `service.name` of every span. |
| `observe.tracing.resource` | `{}` | Extra resource attributes, such as `{ "deployment.environment" = "production" }`. |
| `observe.tracing.sample_ratio` | `1.0` | The share of new traces recorded. See [sampling](#sampling). |
| `observe.tracing.trust_incoming` | `true` | Continue traces from incoming `traceparent` headers. See [public edges](#public-edges). |
| `observe.tracing.stdout` | `false` | Also print finished spans to stdout, for development. |
| `observe.tracing.timeout_ms` | `10000` | The time limit of one export. |
| `observe.tracing.max_queue_size` | `2048` | Spans waiting for export; when full, new spans are dropped. |
| `observe.tracing.trace_url` | none | Your backend's trace page, with `{trace_id}`, for [Lighthouse links](#lighthouse). |

As environment variables: `APP_OBSERVE__TRACING__ENDPOINT=http://otel-collector:4317`, `APP_OBSERVE__TRACING__SAMPLE_RATIO=0.2`. Navree also reads OpenTelemetry's standard variables, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_SERVICE_NAME`, `OTEL_TRACES_SAMPLER_ARG` and `OTEL_RESOURCE_ATTRIBUTES`, for any setting the `observe.tracing` section doesn't set.

### Locally

Run a backend that accepts OTLP, such as Jaeger's all-in-one image, and point every service at it:

```sh
docker run --rm -p 16686:16686 -p 4317:4317 jaegertracing/all-in-one
```

```env title=".env"
APP_OBSERVE__TRACING__ENDPOINT=http://127.0.0.1:4317
```

Click through the web app, then open `http://localhost:16686` and pick `crm-api`: each request is a trace, with the spans of every service it reached.

## What is traced

Navree names spans and sets attributes the way OpenTelemetry's semantic conventions say, so backends recognize HTTP, messaging, RPC and database spans and draw them accordingly.

| What | Span name | Kind | Main attributes |
|---|---|---|---|
| An HTTP request | `GET /api/v1/deals/{id}` (method and route template) | server | `http.request.method`, `http.route`, `http.response.status_code`, `client.address`, `navree.request_id`, `enduser.id` |
| An outgoing HTTP call (`HttpClient`) | `GET` | client | `http.request.method`, `server.address`, `url.full` (no query string), `http.response.status_code` |
| A message sent | `send deals.move` | client | `messaging.system`, `messaging.destination.name`, `messaging.message.id`, `navree.service` |
| A message handled | `process deals.move` | server | the same, plus `navree.reply_status` |
| An event published | `publish deal.won` | producer | `messaging.system`, `messaging.destination.name`, `messaging.message.id` |
| An event handled | `process deal.won` | consumer | the same, plus `messaging.consumer.group.name`, `navree.attempt` |
| A gRPC call served | `crm.deals.v1.Deals/GetDeal` | server | `rpc.system`, `rpc.service`, `rpc.method`, `rpc.grpc.status_code` |
| A gRPC call made | `crm.deals.v1.Deals/GetDeal` | client | the same |
| A GraphQL operation | `query DealBoard`, `mutation MoveDeal` | internal | `graphql.operation.type`, `graphql.operation.name` |
| A database query | `SELECT deals` | client | `db.system.name`, `db.operation.name`, `db.collection.name`, `db.query.text` |
| A commit or rollback | `db.transaction commit` | internal | `navree.outcome` |
| A job dispatched | `dispatch contacts.export` | producer | `navree.queue`, `navree.job_id` |
| A job run | `job contacts.export` | consumer | `navree.queue`, `navree.job_id`, `navree.attempt` |
| A cache call | `cache get` | internal | `navree.cache.store`, `navree.cache.hit` |
| A mail sent | `mail send` | client | `navree.mail.transport` |
| An in-process event | `emit deal.won` | internal | `navree.listeners` |

Some rules hold for every span:

- **No values from your data.** `db.query.text` is the statement with its placeholders, never the bound parameters; URLs lose their query string; payloads, bodies and headers are never recorded.
- **Redaction applies.** An attribute whose name contains one of the `log.redact` fragments (`password`, `token`, `secret`, ...) is written as `[redacted]`, as in [logs](/docs/basics/logging/#redaction).
- **Errors mark the span.** A 5xx response, an error reply, a failed job attempt or a failed query sets the span's status to error, with the error's message. A 4xx is a client's mistake, not the server's: an HTTP server span keeps status unset for it, as the conventions say.

## Context propagation

Navree uses W3C Trace Context (`traceparent` and `tracestate`) and W3C Baggage on every hop, so spans from different services join the same trace, whatever language a service is written in:

| Hop | Carried in | The span on the other side is |
|---|---|---|
| HTTP into a Navree app | request headers | a child of the caller's span |
| `HttpClient` out of a Navree app | request headers, added by Navree | a child of the `GET` client span |
| `ServiceClient::send` | message headers | `process` is a child of `send` |
| `ServiceClient::emit` and forwarded events | message headers (and the outbox row) | each service's `process` is a child of `publish` |
| gRPC, both ways | call metadata | a child of the caller's span |
| Queued jobs, queued listeners, queued mail | the job's envelope | `job` is a child of `dispatch` |
| GraphQL subscriptions | the WebSocket's `connection_init` | each event's span links to the subscription |

An event published through the [outbox](/docs/microservices/events/#the-outbox) keeps the context of the code that emitted it: the outbox stores it with the row, so the `publish` span sits under the request that changed the deal even when a relay on another instance sent it.

Browsers can join too. The app's CORS settings allow the `traceparent` and `tracestate` request headers, so a front end instrumented with OpenTelemetry's web SDK starts the trace at the click, and the backend's spans continue it.

### Public edges

By default an incoming `traceparent` is trusted: the request's spans join the caller's trace, and the caller's sampling decision holds. That's right between your own services and for your own front end. On an API that strangers call, a client could pick trace ids or force sampling on. Set `observe.tracing.trust_incoming = false` on the edge service: each request then starts a new trace, which keeps a link to the client's span so you can still follow it.

## Your own spans

Navree records spans through the [`tracing`](https://docs.rs/tracing) crate, which your app already uses for logs. Any span you create becomes an OpenTelemetry span, with its fields as attributes, in the right place in the tree:

```rust title="services/deals/src/scoring.rs"
use tracing::instrument;

impl DealScorer {
    /// Scores a deal against the owner's history. Shows up as `score_deal`
    /// under the message or request that asked for it.
    #[instrument(name = "score_deal", skip(self, uow), fields(deal_id = %deal.id))]
    pub async fn score(&self, uow: &Uow, deal: &deal::Model) -> Result<u8> {
        let history = self.history(uow, deal.owner_id).await?;
        let score = compute(deal, &history);
        tracing::Span::current().record("score", score);
        Ok(score)
    }
}
```

Log lines written inside a span at `warn` or `error` are also recorded as span events, so the trace shows them at the moment they happened.

To show users a reference they can quote to support, read the current trace id:

```rust
use navree::observe::current_trace_id;

let reference = current_trace_id().map(|id| id.to_string()).unwrap_or_default();
```

## Sampling

Recording every trace is right in development and for most apps. At high volume, record a share of them with `observe.tracing.sample_ratio`:

- the decision is made when a trace starts, from its trace id, so every service makes the same decision for the same trace;
- a request that arrives with a `traceparent` follows the caller's decision, so traces are never cut in half;
- unsampled requests still get a trace id: it is in the logs and propagated to the next service, but not exported.

A ratio below `1.0` drops error traces too, since nobody knows at the start that a request will fail. To keep every trace with an error and a share of the rest, keep `sample_ratio = 1.0` and let an OpenTelemetry Collector make the decision at the end of each trace (tail sampling).

## Logs and traces

Every log line written inside a span carries the trace id and the span id. In the JSON format, they sit next to the request id:

```json title="One line, formatted"
{
  "timestamp": "2026-10-26T08:18:20.384068Z",
  "level": "INFO",
  "target": "notifications::alerts",
  "fields": { "message": "owner notified", "deal_id": "0199c1d2-6f7e-7a31-b5d4-2f0c8e9a1b23" },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "span": {
    "name": "message",
    "pattern": "deal.won",
    "request_id": "01a17749fe5f71caaee8974e482b5659"
  }
}
```

The request id stays the same across services too: `ServiceClient`, gRPC channels and queued jobs pass it on. Search your logs for a trace id to get the lines of every service that took part, or start from the logs and open the trace. In development, [Logbook](/docs/tools/logbook/) shows the same ids on its entries.

## Lighthouse

[Lighthouse](/docs/tools/lighthouse/) stores the trace id with every exception, slow request, slow query and failed job it groups into an issue. Tell it where your traces live:

```toml
[observe.tracing]
endpoint = "http://otel-collector:4317"
trace_url = "https://grafana.example.com/explore?traceId={trace_id}"
```

Each occurrence of an issue then links to its trace. When `deal.won` keeps failing in the notifications service, you go from the issue to the trace and see the click in the web app, the `deals.move` message and the commit that led to it.

## In production

- **Export to a Collector**, as an agent on each host or a gateway for the cluster, rather than straight to a vendor. The Collector batches, retries, samples by tail, and lets you change backends without redeploying services.
- **Export never slows requests.** Spans are queued and sent in the background. When the queue is full (`max_queue_size`), new spans are dropped and counted in the `navree_tracing_spans_dropped_total` metric on `/metrics`.
- **Shutdown flushes.** On Ctrl-C or SIGTERM, Navree exports what's left in the queue within the app's shutdown timeout.
- **Resource attributes** identify each process: `service.name`, `service.version` (your crate's version), `service.instance.id` (unique per process), plus `observe.tracing.resource`.

## Testing

`SpanRecorder` collects finished spans in memory. Install its exporter in place of the app's, then assert on the tree:

```rust title="services/crm-api/tests/tracing.rs"
use navree::micro::{MicroFake, Reply};
use navree::observe::testing::SpanRecorder;
use navree::prelude::*;
use navree::testing::{TestApp, principal};
use serde_json::json;
use uuid::Uuid;

#[tokio::test]
async fn a_message_joins_the_request_trace() {
    let spans = SpanRecorder::new();
    let micro = MicroFake::new();
    let app = TestApp::builder()
        .config("observe.metrics", false)
        .module(ObserveModule::from_config())
        .module(MicroModule::for_root(micro.transport()))
        .module(GatewayModule)
        .override_value(spans.exporter())
        .build()
        .await;
    micro.on("deals.get", Reply::json(&sample_deal()));

    app.acting_as(principal(Uuid::now_v7()))
        .get(&format!("/api/v1/deals/{}", Uuid::now_v7()))
        .header("traceparent", "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01")
        .send()
        .await
        .assert_status(200);

    let request = spans.find("GET /api/v1/deals/{id}");
    let send = spans.find("send deals.get");
    assert_eq!(request.trace_id.to_string(), "4bf92f3577b34da6a3ce929d0e0e4736");
    assert_eq!(send.trace_id, request.trace_id);
    assert_eq!(send.parent_span_id, Some(request.span_id));
    assert_eq!(send.attributes["messaging.destination.name"], json!("deals.get"));

    app.shutdown().await.unwrap();
}
```

`spans.all()` returns every finished span, `spans.find(name)` the first with that name (and fails the test without one), and each recorded span has its `name`, `kind`, `trace_id`, `span_id`, `parent_span_id`, `status` and `attributes`. The recorder sees spans whether or not an endpoint is configured, so tests never export anything.
