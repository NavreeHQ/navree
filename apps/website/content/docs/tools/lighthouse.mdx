## Introduction

<Badge feature="lighthouse" /> Lighthouse watches your app in production and tells you what went wrong. It records every exception, slow request, slow query, failed job and failing outgoing call, groups them into **issues** by fingerprint, and shows them on a dashboard served by your own app at `/_lighthouse`. When something new breaks, it sends an alert to email, Slack or a webhook. Your coding agent can read and resolve issues through MCP tools, and everything can also go to an OpenTelemetry collector.

Lighthouse runs inside your app and stores its data in your database. There is no agent to install, no service to host and no data leaving your servers unless you configure an alert or an export.

- **Every process reports.** `serve`, `queue:work`, `schedule:work`, [Fleet](/docs/tools/fleet/) workers and one-off commands all write to the same store, so a job that fails on a worker shows up next to the request that queued it.
- **No code changes.** Lighthouse reads what the framework already produces: the request pipeline, the `navree::error` log target, query timings from navree-db, job outcomes from navree-queue, scheduled runs and the HTTP client. You add the module; the rest is configuration.
- **Off the request path.** Recording copies a few fields into an in-memory buffer. A background task writes them to the database in batches, so a request never waits for Lighthouse.

## Installation

The `lighthouse` feature of the `navree` facade brings the crate `navree-lighthouse`. It is part of `full`, the default, so an app made with `navree new` already has it, and its `src/app.rs` already includes the module. To add it to an existing app, put `LighthouseModule` after the modules it builds on:

```rust title="src/app.rs" {9}
pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(LoggerModule::from_config())
        .module(CryptoModule::from_config())
        .module(HttpModule::from_config())
        .module(DatabaseModule::from_config())
        // ... queue, mail, auth, access and your own modules
        .module(LighthouseModule::from_config())
}
```

`LighthouseModule` is global. It needs:

| Module | Why |
|---|---|
| `DatabaseModule` | Lighthouse stores issues, occurrences and samples in the app's database (or in [its own](#storage)). |
| `AuthModule` and `AccessModule` | The dashboard signs users in and checks their abilities. Turn the dashboard off with `lighthouse.dashboard = false` in an app without them. |
| `CryptoModule` | The dashboard's session cookie is encrypted with the application key. |
| `MailModule` | Only for [email alerts](#email). |
| `QueueModule` | Optional. Alerts are sent as `lighthouse.alert` jobs when the app has a queue, and from the background writer otherwise. |
| `ScheduleModule` | Optional. Lighthouse schedules its own [pruning](#retention-and-pruning) when the app has a scheduler. |

The module contributes the migration set `lighthouse`, which `migrate` runs with your app's migrations. It creates five tables, all prefixed `lighthouse_`: `issues`, `occurrences`, `samples` (request, job and query samples with their spans), `aggregates` (per-minute counts and latency histograms) and `alerts` (the alerts sent).

```sh
navree migrate
```

Then give yourself access and open the dashboard. Lighthouse registers the subject `Lighthouse` with the permission prefix `lighthouse`, so the [permission](/docs/security/authorization/#permission-strings) `lighthouse.view` lets a role look and `lighthouse.resolve` lets it change issues:

```sh
navree access:grant manager lighthouse.view
navree access:grant manager lighthouse.resolve
```

Users with the super-admin role need nothing: they pass every check. Open `http://127.0.0.1:8080/_lighthouse` and sign in with your app's account.

## What Lighthouse records

| Kind | Recorded when | Kept as |
|---|---|---|
| Exception | A request answers 500 or above, a handler panics, or your code [reports an error](#reporting-errors-yourself) | An occurrence of an issue |
| Request | Every request completes | Counts, error rates and latency per route, every request; a [sampled](#sampling) trace |
| Slow request | A request takes longer than `lighthouse.thresholds.slow_request_ms` (1 s) | An issue per route, with the full trace of each occurrence |
| Slow query | A query takes longer than `lighthouse.thresholds.slow_query_ms` (200 ms) | An issue per normalized statement, with the route or job that ran it |
| Job | A queued job finishes an attempt | Counts and runtimes per job type; a failed attempt with its error |
| Failed job | A job uses up its attempts and moves to the failed jobs | An issue per job type and error |
| Scheduled task | A task of the [scheduler](/docs/digging-deeper/scheduling/) fails or overlaps | An issue per task |
| Outgoing request | A call through `HttpClient` fails or takes longer than `lighthouse.thresholds.slow_outgoing_ms` (2 s) | Counts and latency per host; an issue per host and failure |

A 4xx response is not an exception: it is the app working as intended. Requests answering 4xx count towards the route's error rate on the dashboard, and that's all.

Each record carries the context Lighthouse can find without your help:

- the request id (the `X-Request-Id` your client saw), the method, the route template and the status;
- the signed-in user's id, and with [workspaces](/docs/workspaces/introduction/) the workspace's id and slug;
- the release, the environment, the server's host name and the process (`serve`, `queue:work`, the command's name);
- for a job, its id, type, queue and attempt, and the request that dispatched it;
- the trace id, which is also the one [exported to OpenTelemetry](#opentelemetry-export).

### Traces

A trace is the timeline of one request or job: every query, outgoing call, cache call and queued job it made, as spans with their durations. Lighthouse keeps the trace of every slow request and slow job, and of a [sample](#sampling) of the others. A trace shows you where the time went: in the slow request below, eleven identical queries for contacts take most of the 1.4 seconds.

```text title="GET /api/v1/deals/board · 1,412 ms · trace 4bf92f3577b34da6"
    0 ms  db    SELECT ... FROM deals WHERE stage <> ?          38 ms
   39 ms  db    SELECT ... FROM companies WHERE id IN (...)     12 ms
   52 ms  db    SELECT ... FROM contacts WHERE id = ?  x 11  1,203 ms
1,256 ms  cache get dashboard:wins:0192f0c1...                   1 ms
1,258 ms  http  GET https://api.exchangerate.example/latest    150 ms
```

### Reporting errors yourself

Some errors never reach a 500: you catch them, log them and carry on. Report them to Lighthouse so they still become issues. Inject `Arc<Lighthouse>` and call `report`:

```rust title="src/modules/billing/webhooks.rs"
use navree::lighthouse::Lighthouse;
use navree::prelude::*;

#[injectable]
pub struct PaymentWebhooks {
    lighthouse: Arc<Lighthouse>,
    invoices: Arc<InvoiceService>,
}

impl PaymentWebhooks {
    pub async fn handle(&self, event: PaymentEvent) -> Result<NoContent> {
        if let Err(error) = self.invoices.mark_paid(&event).await {
            // Answer 204 so the provider stops retrying, but keep a record.
            self.lighthouse.report(&error);
        }
        Ok(NoContent)
    }
}
```

`report` takes any `&(dyn std::error::Error + 'static)` and returns at once: the occurrence goes into the buffer with the context of the current request or job. For more control, build a `Report`:

```rust
use navree::lighthouse::{Level, Report};

self.lighthouse.capture(
    Report::error(&error)
        .level(Level::Warning)
        .context("invoice_id", invoice.id)
        .tag("provider", "acme-pay")
        .fingerprint(["acme-pay", "card-declined"])
        .backtrace(),
);

// No error value: something that should never happen.
self.lighthouse.capture(Report::message("Payment event without a customer").level(Level::Warning));
```

| Method | What it does |
|---|---|
| `Report::error(&e)`, `Report::message(text)` | Starts a report from an error (its whole source chain is kept) or from a message. |
| `.level(Level::Error)` | `Error` (the default), `Warning` or `Info`. The dashboard filters by level, and [alerts](#alerts) ignore `Info`. |
| `.context(key, value)` | Adds a value shown on the occurrence. Any `Serialize` value. |
| `.tag(key, value)` | Adds a tag: a short string you can filter and search issues by. |
| `.fingerprint([..])` | Replaces the [fingerprint](#fingerprints), so these reports group together however their messages differ. |
| `.user(id)` | Sets the user when there is no request, for example in a job working for someone. |
| `.backtrace()` | Captures a backtrace where the report is built. |

To tag everything the current request or job reports, call `self.lighthouse.tag_current("plan", "pro")` once early on, for example in a guard. The tag also goes on the request's sampled trace.

## Issues

An issue is every occurrence of one problem. Lighthouse computes a **fingerprint** for each record and adds it to the issue with that fingerprint, opening a new issue the first time it sees one. The dashboard then shows one line per problem with its count, the users and workspaces it affected, and when it was first and last seen, instead of a thousand identical errors.

### Fingerprints

Rust errors don't carry a stack trace, so Lighthouse fingerprints what they do carry: the error's type chain, where it happened (the route or the job), and the message with its variable parts taken out. Numbers, UUIDs, quoted strings, email addresses and hexadecimal ids in a message are replaced before hashing, so `deal 0199c1d2-… not found` and `deal 0199c1e7-… not found` are one issue.

| Kind | Grouped by |
|---|---|
| Exception | Error type chain + route or job + normalized message |
| Panic | File and line of the panic + normalized message |
| Slow request | Method + route template |
| Slow query | The normalized statement: literals become `?`, `IN` lists collapse to one item |
| Failed job | Job type + error type chain + normalized message |
| Scheduled task | Task name + normalized message |
| Outgoing request | Host + status class or error kind (`timeout`, `connect`, `5xx`) |

Panics carry their location, and Lighthouse captures a backtrace for each. For a report you build yourself, `.backtrace()` adds one, and `.fingerprint([..])` decides the grouping outright.

### Statuses

| Status | Meaning |
|---|---|
| Open | New, or seen again after it was resolved. Open issues send [alerts](#alerts). |
| Resolved | You fixed it. A new occurrence reopens it as a **regression**. |
| Resolved in next release | Reopens only when it happens again in a release after the current one, so stragglers from the old release don't reopen it. |
| Ignored | Kept and counted, but never alerts. Ignore forever, until a date, or until it occurs N more times. |

The release comes from `lighthouse.release`. [Harbor](/docs/tools/harbor/) sets it to the release id on every deploy (`APP_LIGHTHOUSE__RELEASE`); without it, Lighthouse uses the version of your app's package.

## The dashboard

The dashboard is a single-page app compiled into the crate and served by your app at `lighthouse.path` (`/_lighthouse`), outside the API prefix. No Node.js, no CDN and no separate process. It updates live while you watch.

- **Overview.** A row of figures for the selected period (the last hour, 24 hours or 7 days): requests per minute, the error rate, the 95th percentile latency, failed jobs and open issues. Below them, a timeline of requests and exceptions, and a live feed of new occurrences sliding in at the top.
- **Issues.** One line per issue: its title (the first line of the message), the route or job it comes from, a sparkline of the last 24 hours, the number of occurrences, users and workspaces affected, and first and last seen. Filter by status, kind, level, release, environment, route, job, tag, user or workspace, and sort by last seen, first seen or count.
- **An issue.** The message and the error's source chain, the backtrace when there is one, and the latest occurrence's context: the request (method, route, headers with secrets masked), the user, the workspace, the release, the server, tags and your report's context values. A chart shows occurrences over time, and a list shows every occurrence with a link to its trace. Buttons resolve, resolve in the next release, ignore or reopen it.
- **Requests.** Every route with its throughput, error rate and p50, p95 and p99 latency, slowest first. A route's page lists its slowest traces, each drawn as a waterfall of spans.
- **Queries.** Normalized statements with how often they ran, their total and p95 time, and the routes and jobs that ran them.
- **Jobs.** Every job type with throughput, runtime, failed attempts and failed jobs. For queue workers and wait times in depth, see [Fleet](/docs/tools/fleet/).
- **Outgoing.** Every host your app calls through `HttpClient`, with latency, error rate and the slowest calls.

### Signing in and access

The dashboard's sign-in screen uses your app's own users: an email and password through `AuthService`, then a two-factor code when the account has [two-factor authentication](/docs/security/account-flows/) on. It is subject to the same login throttle as `POST /api/auth/login`. The session lives in an encrypted, httpOnly, `SameSite=Strict` cookie scoped to `/_lighthouse`, so the rest of your API never sees it, and every change the dashboard makes carries a CSRF token.

Its JSON API, under `/_lighthouse/api`, also accepts an access token in `Authorization: Bearer`, for scripts and tests.

Every route of the dashboard and its API checks an [ability](/docs/security/authorization/) on the subject `Lighthouse`:

| Action | Allows | Permission |
|---|---|---|
| `view` | Opening the dashboard and reading everything on it | `lighthouse.view` |
| `resolve` | Resolving, ignoring and reopening issues | `lighthouse.resolve` |

Grant the permissions to a role, as in [installation](#installation), or write the rules in your abilities function:

```rust title="src/abilities.rs"
pub fn define(ctx: &AbilityCtx, rules: &mut Rules) {
    ctx.grant_permissions(rules);

    if let Some(user) = &ctx.user {
        if user.has_role("ops") {
            rules.can("view", "Lighthouse");
            rules.can("resolve", "Lighthouse");
        }
    }
    // ...
}
```

A signed-in user without `view` gets a 403 page; a guest goes to the sign-in screen.

## Alerts

Lighthouse sends an alert when something needs a person. Each channel says which kinds of alert it wants:

| Kind | Sent when |
|---|---|
| `new_issue` | An issue is opened for the first time. |
| `regression` | A resolved issue occurs again. |
| `spike` | An issue occurs more than `alerts.spike.occurrences` times (50) within `alerts.spike.minutes` (5). |
| `failed_job` | A job moves to the failed jobs. |
| `long_wait` | A queue's oldest job has waited longer than its threshold. [Fleet](/docs/tools/fleet/#long-wait-alerts) raises it. |

Configure the channels in the `lighthouse.alerts` section:

```toml title="config/app.toml"
[lighthouse.alerts]
cooldown_minutes = 30   # at most one alert per issue and kind in this window
spike = { occurrences = 50, minutes = 5 }

[lighthouse.alerts.email]
to = ["oncall@example.com"]
on = ["new_issue", "regression", "spike"]

[lighthouse.alerts.slack]
# webhook_url: APP_LIGHTHOUSE__ALERTS__SLACK__WEBHOOK_URL
on = ["new_issue", "regression", "spike", "failed_job", "long_wait"]

[lighthouse.alerts.webhook]
url = "https://ops.example.com/hooks/lighthouse"
# secret: APP_LIGHTHOUSE__ALERTS__WEBHOOK__SECRET
on = ["new_issue", "regression"]
```

A channel without `on` gets `new_issue`, `regression` and `spike`. Issues at level `Info` and ignored issues never alert. Every alert links to the issue on the dashboard at `lighthouse.url`, which defaults to `app.url` followed by the path; set it when your API has its own host, as in `https://api.crm.example.com/_lighthouse`.

### Email

Email alerts go through your app's `Mailer`, queued when the app has a queue, from the configured sender. The message names the issue, its kind, count, release and environment, and links to it. `to` takes one address or a list; from the environment, a comma-separated string (`APP_LIGHTHOUSE__ALERTS__EMAIL__TO=oncall@example.com,cto@example.com`).

### Slack

Create an incoming webhook in your Slack workspace and set its URL. Keep it out of committed files: it is a secret.

```env
APP_LIGHTHOUSE__ALERTS__SLACK__WEBHOOK_URL=https://hooks.slack.com/services/T000/B000/XXXXXXXX
```

Each alert is one message with the issue's title, the route or job, the count and an **Open in Lighthouse** button.

### Webhooks

A webhook alert is a `POST` of JSON to your URL, signed following the [Standard Webhooks](https://www.standardwebhooks.com) specification: `webhook-id`, `webhook-timestamp` and `webhook-signature` headers, an HMAC-SHA256 over the id, the timestamp and the body with your `secret`. Verify the signature before you trust the body.

```json title="POST https://ops.example.com/hooks/lighthouse"
{
  "type": "lighthouse.new_issue",
  "issue": {
    "id": "0199c1d2-6f7e-7a31-b5d4-2f0c8e9a1b23",
    "title": "cannot charge invoice: card declined",
    "kind": "exception",
    "level": "error",
    "status": "open",
    "culprit": "POST /api/v1/invoices/{id}/charge",
    "count": 1,
    "users": 1,
    "first_seen": "2026-10-26T09:14:02Z",
    "last_seen": "2026-10-26T09:14:02Z",
    "url": "https://api.crm.example.com/_lighthouse/issues/0199c1d2-6f7e-7a31-b5d4-2f0c8e9a1b23"
  },
  "environment": "production",
  "release": "20261026-091512-3f2a9c1"
}
```

A failed delivery is retried with backoff, like any job. The `lighthouse_alerts` table and the issue's page show each alert and whether it was delivered.

### Your own channels

Implement `AlertChannel` to send alerts anywhere else, and register it with `m.alert_channel::<C>()`:

```rust title="src/modules/ops/sms.rs"
use navree::BoxFuture;
use navree::lighthouse::{Alert, AlertChannel, AlertKind};
use navree::prelude::*;

#[injectable]
pub struct OnCallSms {
    sms: Arc<SmsGateway>,
}

impl AlertChannel for OnCallSms {
    fn name(&self) -> &str {
        "on-call-sms"
    }

    fn wants(&self, alert: &Alert) -> bool {
        matches!(alert.kind, AlertKind::Regression | AlertKind::Spike)
    }

    fn send<'a>(&'a self, alert: &'a Alert) -> BoxFuture<'a, Result<(), BoxError>> {
        Box::pin(async move {
            self.sms.send("+15550100", &format!("{}: {}", alert.kind, alert.issue.title)).await?;
            Ok(())
        })
    }
}

#[module(register = Self::wire)]
pub struct OpsModule;

impl OpsModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.alert_channel::<OnCallSms>();
    }
}
```

To check every channel, `navree lighthouse:test-alerts` sends a test alert through each one (or `navree lighthouse:test-alerts slack` through one) and prints whether it was delivered.

## Sampling

Counts are always exact: every request, job and exception is counted towards its route's throughput and error rate and its issue's occurrences. Sampling decides how many **details** are stored: traces of ordinary requests and jobs, and occurrences of busy issues.

```toml title="config/app.toml"
[lighthouse.sample]
requests = 0.1    # store the trace of 1 request in 10
jobs = 0.25
exceptions = 1.0  # store every occurrence (counts stay exact either way)
```

- Slow requests, slow jobs, failed jobs and the first 100 occurrences of each issue per hour are always stored, whatever the rates.
- The latency percentiles on the Requests page come from per-minute histograms of every request, not from samples.
- Sampling is per request: a sampled request keeps its whole trace, with every query in it.

On a busy app, start with `requests = 0.1` and raise it if you want more traces to look at.

## Retention and pruning

`lighthouse:prune` deletes samples, occurrences, aggregates and sent alerts older than `lighthouse.retention_days` (14), and resolved or ignored issues with no occurrence left. Open issues are kept with their counts.

```sh
navree lighthouse:prune
navree lighthouse:prune --days 7
```

```text wrap
Pruned 182,340 samples, 2,114 occurrences, 40,320 aggregate rows and 12 issues older than 14 days.
```

When the app includes `ScheduleModule`, Lighthouse adds the command to the schedule itself, every day at `lighthouse.prune_at` (`"03:10"`, UTC), without overlapping; a [`schedule:work`](/docs/digging-deeper/scheduling/) process runs it. Set `prune_at = ""` to schedule it yourself, or run it from cron in an app without a scheduler.

## Storage

By default Lighthouse writes to the app's database. To keep monitoring writes away from your data, give it its own:

```env
APP_LIGHTHOUSE__DATABASE_URL=postgres://lighthouse:secret@db.internal:5432/crm_lighthouse
```

`migrate` then runs the `lighthouse` migrations against that database, and the dashboard reads from it. The URL takes the same forms as `database.url`.

The background writer flushes the buffer every second, or as soon as it holds 500 records. If the database can't keep up and the buffer reaches `lighthouse.buffer` records (10,000), Lighthouse drops samples first and occurrences last, never counts, and says so: the dashboard shows a banner with the number dropped, and `/metrics` has `lighthouse_dropped_total`. On shutdown the writer flushes what it holds before the app exits.

## Privacy and security

Lighthouse stores what your app handles, so it treats it with care:

- **Secrets are masked.** Header values, context values and query bindings whose names contain a fragment of `log.redact` (`password`, `token`, `authorization`, `cookie`, `secret` by default) are stored as `[redacted]`, plus any fragment you add to `lighthouse.redact`. `Authorization`, `Cookie` and `Set-Cookie` headers are always masked.
- **No bodies by default.** Request bodies are not recorded unless you set `lighthouse.capture.request_body = true`, and then only JSON bodies up to 16 KiB, with the same masking. Response bodies are never recorded.
- **Client addresses.** The client IP is stored with each request sample. Set `lighthouse.capture.ip = false` to leave it out.
- **The dashboard denies by default.** Nobody sees it without the `view` ability, sign-in attempts are throttled, the cookie is encrypted and scoped to the dashboard's path, and its pages are served with a strict Content Security Policy.
- **Data stays with you.** Nothing leaves your servers except the alerts and exports you configure.

Lighthouse's own routes are left out of its recordings, as are the paths in `lighthouse.ignore.routes` (`/health/*` and `/metrics` by default). Ignore noisy jobs with `lighthouse.ignore.jobs`.

## MCP tools for agents

Lighthouse gives AI agents the same view you have. It registers these tools:

| Tool | What it returns or does | Ability |
|---|---|---|
| `lighthouse_list_issues` | Open issues, newest or most frequent first, with filters for kind, route, job and release | `view` |
| `lighthouse_get_issue` | One issue: the message, the source chain, the backtrace, recent occurrences with their context, and the trace of the latest one | `view` |
| `lighthouse_slow_routes` | The slowest routes over a period, with p95 latency and their slowest trace | `view` |
| `lighthouse_slow_queries` | The slowest normalized statements and where they run | `view` |
| `lighthouse_failed_jobs` | Failed jobs grouped by type and error | `view` |
| `lighthouse_resolve_issue` | Resolves an issue, now or in the next release, with a comment | `resolve` |
| `lighthouse_ignore_issue` | Ignores an issue, with a comment | `resolve` |

When your app includes `McpModule`, Lighthouse adds the tools to your app's own [MCP server](/docs/ai/mcp-servers/), where each one checks its ability for the token that calls it: give an agent a token for a user with `lighthouse.view` to let it read, and `lighthouse.resolve` to let it close issues. During development, [Navigator](/docs/ai/navigator/) (`navree mcp`) offers the five read tools next to its own, reading Lighthouse's tables read-only the way it reads the rest of your local database. Set `lighthouse.mcp = false` to leave the tools out.

A session with a coding agent then looks like this: you ask it to fix the newest Lighthouse issue; it calls `lighthouse_list_issues`, reads the backtrace and the failing request with `lighthouse_get_issue`, opens the code, writes the fix and a test, and resolves the issue in the next release with a comment linking the change.

## OpenTelemetry export

Lighthouse can send its traces and metrics to any OpenTelemetry collector over OTLP, alongside its own dashboard:

```toml title="config/app.toml"
[lighthouse.otel]
endpoint = "http://otel-collector.internal:4318"   # OTLP over HTTP; use port 4317 with protocol = "grpc"
protocol = "http"
service_name = "crm-api"
headers = { "x-api-key" = "..." }                  # better: APP_LIGHTHOUSE__OTEL__HEADERS__X_API_KEY
```

- **Traces.** A span for each request, job, scheduled task and command, with child spans for queries, outgoing calls and cache calls, named and attributed following the OpenTelemetry semantic conventions for HTTP and databases. Exceptions are recorded as span events.
- **Metrics.** Request counts and durations by route and status, job counts and runtimes by type and outcome, and queue wait times.
- **Context propagation.** Lighthouse reads the W3C `traceparent` header on incoming requests and sends it on outgoing calls through `HttpClient`, and a queued job continues the trace of the request that dispatched it. A request that crosses several of your services is one trace; see [distributed tracing](/docs/microservices/tracing/).
- **Logs and traces together.** Log lines written during a request carry its `trace_id` and `span_id`, so your log platform can jump from a line to its trace.

`lighthouse.otel.sample` (1.0) is the fraction of traces exported, independent of what Lighthouse stores. The standard `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_SERVICE_NAME` variables are read when the keys aren't set. To use only the export, set `lighthouse.store = "off"`: nothing is written to the database and the dashboard isn't mounted.

## Configuration

Every key of the `lighthouse` section is optional. As environment variables: `APP_LIGHTHOUSE__RETENTION_DAYS=30`, `APP_LIGHTHOUSE__SAMPLE__REQUESTS=0.1`, and lists as comma-separated strings (`APP_LIGHTHOUSE__IGNORE__ROUTES=/health/*,/metrics,/internal/*`). An invalid value, such as a sample rate above 1 or an unknown alert kind, fails the boot with a message naming the key.

| Key | Default | What it does |
|---|---|---|
| `lighthouse.enabled` | `true` | Record anything at all. When off, the dashboard still shows what was recorded. |
| `lighthouse.store` | `database` | `database`, or `off` to only [export](#opentelemetry-export). |
| `lighthouse.database_url` | none | A separate database for Lighthouse's tables. |
| `lighthouse.dashboard` | `true` | Mount the dashboard and its API. |
| `lighthouse.path` | `/_lighthouse` | Where the dashboard is served. |
| `lighthouse.url` | `app.url` + `path` | The dashboard's public URL, for links in alerts. |
| `lighthouse.environment` | `production` in release builds, `development` in debug builds | The environment label on every record. |
| `lighthouse.release` | the package version | The release label. Harbor sets it on deploy. |
| `lighthouse.server` | the host name | The server label. |
| `lighthouse.thresholds.slow_request_ms` | `1000` | When a request is slow. |
| `lighthouse.thresholds.slow_query_ms` | `200` | When a query is slow. |
| `lighthouse.thresholds.slow_job_ms` | `30000` | When a job attempt is slow. |
| `lighthouse.thresholds.slow_outgoing_ms` | `2000` | When an outgoing request is slow. |
| `lighthouse.sample.requests` | `1.0` | Fraction of request traces stored. |
| `lighthouse.sample.jobs` | `1.0` | Fraction of job traces stored. |

| `lighthouse.capture.request_body` | `false` | Store JSON request bodies (up to 16 KiB) with exceptions and slow requests. |
| `lighthouse.capture.request_headers` | `true` | Store request headers, masked. |
| `lighthouse.capture.ip` | `true` | Store the client address. |
| `lighthouse.redact` | `[]` | Name fragments masked in addition to `log.redact`. |
| `lighthouse.ignore.routes` | `["/health/*", "/metrics"]` | Paths never recorded (`*` matches one or more segments at the end). |
| `lighthouse.ignore.jobs` | `[]` | Job types never recorded. |
| `lighthouse.mcp` | `true` | Register the MCP tools. |
| `lighthouse.alerts.cooldown_minutes` | `30` | Minimum time between two alerts for one issue and kind. |
| `lighthouse.alerts.spike.occurrences` | `50` | Occurrences that make a spike. |
| `lighthouse.alerts.spike.minutes` | `5` | The spike window. |
| `lighthouse.alerts.email.to` | none | Recipients of email alerts. |

| `lighthouse.alerts.webhook.url` | none | Where webhook alerts are posted. |
| `lighthouse.alerts.webhook.secret` | none | The signing secret (at least 32 bytes). Required with `url`. |
| `lighthouse.alerts.webhook.on` | `new_issue`, `regression`, `spike` | Kinds sent to the webhook. |
| `lighthouse.otel.endpoint` | `OTEL_EXPORTER_OTLP_ENDPOINT`, else off | The OTLP collector. |

To configure the module in code instead:

```rust
use navree::lighthouse::{LighthouseOptions, Thresholds};

Navree::app().module(LighthouseModule::for_root(LighthouseOptions {
    retention_days: 30,
    thresholds: Thresholds {
        slow_request_ms: 500,
        ..Thresholds::default()
    },
    ..LighthouseOptions::default()
}))
```

## Commands

| Command | What it does |
|---|---|
| `lighthouse:prune [--days N]` | Deletes what is older than the retention period (or N days). |
| `lighthouse:test-alerts [channel]` | Sends a test alert through every channel, or one, and reports the result. |

Both run in your app's binary, so `navree lighthouse:prune` works in development and `./crm-api lighthouse:prune` on a server.

## Testing

`LighthouseFake` records reports instead of storing them, so a test can check that your code reports what it should. Install its `Lighthouse` in place of the app's, the way you install a [queue fake](/docs/testing/fakes/):

```rust title="tests/webhooks.rs"
use navree::lighthouse::{Level, LighthouseFake};
use navree::prelude::*;
use navree::testing::TestApp;

#[tokio::test]
async fn a_payment_for_an_unknown_invoice_is_reported() {
    let fake = LighthouseFake::new();
    let app = TestApp::builder()
        .temp_database()
        .module(DatabaseModule::from_config())
        .module(LighthouseModule::from_config())
        .module(BillingModule)
        .override_value(Arc::new(fake.lighthouse()))
        .build()
        .await;

    let webhooks = app.get::<PaymentWebhooks>().await;
    webhooks.handle(PaymentEvent::paid("inv_missing")).await.unwrap();

    fake.assert_reported::<InvoiceError>(|error| matches!(error, InvoiceError::NotFound(_)));
    fake.assert_reported_times(1);
    assert_eq!(fake.reports()[0].level, Level::Error);
    app.shutdown().await.unwrap();
}
```

| Method | What it does |
|---|---|
| `assert_reported::<E>(predicate)` | Asserts an error of type `E` (anywhere in the source chain) was reported and `predicate(&error)` holds. |
| `assert_reported_message(text)` | Asserts a report whose message contains `text`. |
| `assert_reported_times(n)` | Asserts exactly `n` reports. |
| `assert_nothing_reported()` | Asserts there was no report. |
| `reports()` | Every recorded report: message, level, fingerprint, tags, context. |
| `alerts()` | The alerts that would have been sent, with their kind and channel. |
| `clear()` | Forgets what was recorded. |

The fake also records the exceptions the framework captures for you. A handler that answers 500 in a test shows up in `reports()` with its route, so you can assert that an error you expect is reported once and an error you handle isn't reported at all. In tests that don't install the fake, set `lighthouse.enabled = false` to keep Lighthouse out of the way.
