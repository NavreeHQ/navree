## Introduction

Harbor takes your app from your repository to your servers. `navree harbor:provision` turns a fresh Ubuntu server into one ready to run a Navree app: a firewall, Caddy with automatic TLS, PostgreSQL, Redis and systemd units for the web server, the queue workers and the scheduler. `navree deploy` builds a release, uploads it, migrates the database, starts it next to the running one, and switches traffic only once its health check passes. `navree deploy:rollback` goes back to the previous release the same way.

Everything lives in one file, `harbor.toml`, in your repository: the servers and their roles, the processes, the environment, and the secrets, encrypted. Harbor is part of the `navree` CLI and works over SSH. Nothing runs on your servers but your app and the services it uses: no agent, no control panel, no account.

[Deployment](/docs/getting-started/deployment/) explains what a Navree deployment involves: the binary, the settings, the processes, the proxy and the health checks. Harbor does all of it for you, following the same rules, and this page says exactly what it sets up so you always know what is on your servers.

## What you need

- **The CLI**: `cargo install --git https://github.com/NavreeHQ/navree navree-cli`.
- **One or more servers running Ubuntu 22.04 or 24.04 LTS**, on x86-64 or ARM64, from any provider, with SSH access as `root` using a key. A server with 1 GB of memory runs a small app with its database; 2 GB or more is comfortable.
- **A domain** whose DNS `A` (and `AAAA`) record points at the server that takes web traffic, so Caddy can get a certificate.
- **To build on macOS or Windows**, Docker or Podman: Harbor builds the Linux binary in a container. On Linux it can build natively.

## Getting started

<Steps>
<Step title="Create harbor.toml">

From your app's directory:

```sh
navree harbor:init
```

```text
  created  harbor.toml
  created  harbor.key        # the secrets key: never commit it
  updated  .gitignore        # ignores harbor.key
```

</Step>
<Step title="Describe your server">

Edit `harbor.toml`: the package to deploy, the domain, and the server's address. One server can hold every role:

```toml title="harbor.toml"
app = "crm-api"
domain = "crm.example.com"

[build]
features = ["postgres"]

[servers.app-1]
host = "203.0.113.10"
roles = ["web", "worker", "scheduler", "postgres", "redis"]

[env]
APP_APP__URL = "https://crm.example.com"
APP_MAIL__FROM = "Navree CRM <crm@example.com>"
```

</Step>
<Step title="Add your secrets">

Generate the application key and store the SMTP URL. Both are encrypted into `harbor.toml`:

```sh
navree harbor:secrets set APP_KEY --generate
navree harbor:secrets set APP_MAIL__TRANSPORT
```

The second command asks for the value without echoing it.

</Step>
<Step title="Provision the server">

```sh
navree harbor:provision
```

Harbor connects as `root`, installs and configures everything the roles need, and records the server's SSH host key in `harbor.toml`. It takes a few minutes the first time.

</Step>
<Step title="Deploy">

```sh
navree deploy
```

Your app is live at `https://crm.example.com`. Commit `harbor.toml`; from now on, `navree deploy` is the whole release process.

</Step>
</Steps>

## harbor.toml

`harbor.toml` is the single description of where and how your app runs. This one runs the CRM on one server:

```toml title="harbor.toml"
# The package to build and run, and the domain it answers on.
app = "crm-api"
domain = "crm.example.com"

[build]
features = ["postgres"]       # Cargo features of the release build

[deploy]
keep_releases = 5             # releases kept on each server for rollbacks
health_check = "/health/ready"
health_timeout_secs = 60
shared = ["storage"]          # directories that survive releases

[processes]
web = { command = "serve" }
worker = { command = "queue:work", instances = 2 }
scheduler = { command = "schedule:work" }

[servers.app-1]
host = "203.0.113.10"
roles = ["web", "worker", "scheduler", "postgres", "redis"]
host_key = "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIJz…"   # written by harbor:provision

[env]
APP_APP__URL = "https://crm.example.com"
APP_MAIL__FROM = "Navree CRM <crm@example.com>"
APP_LOG__LEVEL = "info"

[secrets]
APP_KEY = "harbor:v1:wq3xT9…"
APP_MAIL__TRANSPORT = "harbor:v1:Pz0k1c…"
APP_DATABASE__URL = "harbor:v1:b2Nr7Q…"   # written by harbor:provision
```

### Roles

A server's `roles` say what it runs. Give one server every role, or spread them over several:

| Role | The server runs |
|---|---|
| `web` | Caddy, and your app's `web` process behind it |
| `worker` | The `worker` process: `queue:work`, or `fleet` with [Fleet](/docs/tools/fleet/) |
| `scheduler` | The `scheduler` process: `schedule:work` |
| `postgres` | PostgreSQL, with your app's database and user |
| `redis` | Redis |

### Processes

`processes` says what each role runs. The defaults are the ones above; change a command or run more instances of it:

```toml
[processes]
web = { command = "serve" }
worker = { command = "fleet" }            # Fleet supervises its own workers
scheduler = { command = "schedule:work" }
```

`instances` runs that many copies of a worker on each server with the role. The scheduler always runs once per server, and running it on several servers is safe: each task runs once per tick however many schedulers share the database.

### The environment

Your app reads its settings from `APP_*` environment variables, as [configuration](/docs/getting-started/configuration/) describes. On a server, Harbor writes them to `/etc/<app>/env`, readable only by root and the app's user, from three sources, later over earlier:

1. the settings Harbor knows: `APP_HTTP__ADDR` for each web instance, `APP_HTTP__TRUSTED_PROXIES` (Caddy on loopback, plus `deploy.trusted_proxies`), `APP_DATABASE__MIGRATE_ON_BOOT=false`, `APP_REALTIME__RELAY_URL` (Caddy's internal entry, so workers reach the live web instance) and `APP_LIGHTHOUSE__RELEASE` (the release id, for [Lighthouse](/docs/tools/lighthouse/#statuses));
2. `[env]`, for settings that aren't secret;
3. `[secrets]`, decrypted on your machine during the deploy.

Releases also carry your `config/app.toml`, so settings that are the same everywhere can stay there. As on any server, an environment variable overrides the TOML file.

## Provisioning

`navree harbor:provision` prepares every server in `harbor.toml`; `navree harbor:provision app-1` prepares one. It connects as `ssh.provision_user` (`root`) with your key and configures the server for its roles. Running it again is safe: it brings the server in line with `harbor.toml` and changes only what differs, so you also use it after adding a role, a server or a worker.

```text
Provisioning app-1 (203.0.113.10, Ubuntu 24.04, x86_64)
  base      updates, unattended upgrades, chrony, 2 GB swap, UTC
  users     navree, with 2 SSH keys
  ssh       no passwords, root by key only, host key recorded
  firewall  ufw: 22/tcp, 80/tcp, 443/tcp, 443/udp; fail2ban
  postgres  PostgreSQL 17, database crm_api; URL saved to [secrets]
  redis     Redis 7 on 127.0.0.1; URL saved to [secrets]
  caddy     Caddy 2, site crm.example.com
  systemd   crm-api-web@blue, @green, crm-api-worker@1, @2, scheduler
Provisioned app-1 in 3m 12s. Run `navree deploy` next.
```

### What a server gets

| Area | What Harbor sets up |
|---|---|
| System | Package updates, `unattended-upgrades` for security updates, `chrony` for time, a swap file on servers with less than 4 GB of memory, the time zone set to UTC, journald capped at 1 GB. |
| Users | A `navree` user that owns the app and runs its processes, with the keys in `ssh.authorized_keys`. Its `sudo` rights are limited to managing the app's systemd units and reloading Caddy. |
| SSH | Password logins off; `root` may log in by key only. The host key is recorded in `harbor.toml` as `host_key`, and every later connection checks it. |
| Firewall | `ufw`, denying all incoming traffic except SSH, and on `web` servers ports 80 and 443 (TCP, and UDP for HTTP/3). On `postgres` and `redis` servers, ports 5432 and 6379 open to your other servers only. `fail2ban` watches SSH. |
| Caddy (`web`) | The reverse proxy in front of your app, with a certificate from Let's Encrypt for `domain`, renewed automatically; HTTP redirected to HTTPS; HTTP/2 and HTTP/3; compression; WebSocket upgrades for [broadcasting](/docs/digging-deeper/broadcasting/). `/metrics` answers only the addresses in `web.metrics_allow`. |
| PostgreSQL (`postgres`) | PostgreSQL 17 from the PostgreSQL project's apt repository, a database and a user for the app with a generated password, `scram-sha-256` authentication, connections from your servers only, and a daily `pg_dump` kept for `postgres.backup_days` (7) in `/var/backups/postgresql`. |
| Redis (`redis`) | Redis 7, a generated password, `maxmemory` with `allkeys-lru`, listening on loopback or the private network only. |
| systemd | Units for the app's processes, below. |

The database URL (`APP_DATABASE__URL`) and the Redis URL (`REDIS_URL`), with their generated passwords, go straight into `[secrets]`: you never see or copy them.

### The systemd units

Harbor runs your app's processes under systemd, with the same graceful shutdown the [deployment](/docs/getting-started/deployment/#processes-to-run) page describes. The web server runs in two **slots**, `blue` and `green`, so a new release can start while the old one still serves:

```text title="/etc/systemd/system/crm-api-web@.service"
[Unit]
Description=crm-api web (%i)
After=network-online.target postgresql.service redis-server.service
Wants=network-online.target

[Service]
Type=simple
User=navree
Group=navree
WorkingDirectory=/srv/crm-api/%i
EnvironmentFile=/etc/crm-api/env
EnvironmentFile=/etc/crm-api/%i.env
ExecStart=/srv/crm-api/%i/crm-api serve
Restart=on-failure
RestartSec=5
TimeoutStopSec=100
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/srv/crm-api/shared

[Install]
WantedBy=multi-user.target
```

`/etc/crm-api/blue.env` sets `APP_HTTP__ADDR=127.0.0.1:8081`, and `green.env` port 8082. The worker unit, `crm-api-worker@.service`, and the scheduler unit, `crm-api-scheduler.service`, are the same with `WorkingDirectory=/srv/crm-api/current` and their own commands. Every unit has the same hardening: the app can write to `shared/` and nowhere else.

### The Caddy site

```text title="/etc/caddy/Caddyfile"
crm.example.com {
    encode zstd gzip

    @metrics path /metrics
    respond @metrics 404

    reverse_proxy 127.0.0.1:8081
}

# Internal entry for workers and the scheduler, always pointing at the live slot.
http://127.0.0.1:8079 {
    reverse_proxy 127.0.0.1:8081
}
```

Caddy sends `X-Forwarded-For` and `X-Forwarded-Proto`, and Harbor sets `APP_HTTP__TRUSTED_PROXIES=127.0.0.1,::1`, so your app sees each client's real address, as [behind a reverse proxy](/docs/getting-started/deployment/#behind-a-reverse-proxy) explains. A deploy rewrites the two `reverse_proxy` lines and reloads Caddy gracefully. When your app includes `GrpcModule`, Harbor proxies with `h2c://127.0.0.1:8081`, so [gRPC](/docs/microservices/grpc/) works end to end over HTTP/2.

## Secrets

Secrets live in `[secrets]`, encrypted with AES-256-GCM under the key in `harbor.key`. Each value is encrypted with its name as associated data, so a value can't be copied under another name, and the names stay readable: a pull request that adds a secret shows which one.

```sh
navree harbor:secrets set STRIPE_SECRET          # asks for the value, without echo
navree harbor:secrets set APP_KEY --generate     # a new application key
echo "$TOKEN" | navree harbor:secrets set APP_OBSERVE__METRICS_TOKEN --stdin
navree harbor:secrets list                       # names only
navree harbor:secrets reveal APP_MAIL__TRANSPORT
navree harbor:secrets unset STRIPE_SECRET
```

- **The key never leaves your machine.** `harbor.key` is in `.gitignore`. Share it with your team through a password manager. In CI, put its contents in the `NAVREE_HARBOR_KEY` environment variable instead.
- **Values are decrypted only during a deploy**, on the machine running it, and written over SSH to `/etc/<app>/env`. They never appear in Harbor's output or logs, and never in a release directory.
- **Rotate the key** with `navree harbor:secrets rotate-key`: it re-encrypts every value under a new key and writes the new `harbor.key`.

Rotating a secret itself is setting it again and deploying.

## Deploying

```sh
navree deploy
```

```text
Deploying crm-api to production (1 server)
  build     crm-api for x86_64-unknown-linux-gnu, in a container (1m 42s)
  upload    app-1  releases/20261026-091512-3f2a9c1, 14.2 MB (3s)
  env       app-1  4 settings, 3 secrets
  migrate   app-1  2 migrations ran (1s)
  start     app-1  green on 127.0.0.1:8082
  health    app-1  GET /health/ready 200 after 0.4 s
  switch    app-1  Caddy -> green, current -> 20261026-091512-3f2a9c1
  drain     app-1  blue stopped after its requests finished
  restart   app-1  worker x2, scheduler
  prune     app-1  1 old release removed
Released 20261026-091512-3f2a9c1 in 1m 53s.
```

A release id is the UTC time of the deploy and the short Git commit. Step by step:

1. **Build.** Harbor builds the release binary for your servers' architecture: natively when the machine running the deploy is Linux on the same architecture with a glibc no newer than the servers', otherwise in a container (`build.method`). Container builds keep Cargo's cache in a volume, so the second build is incremental.
2. **Upload.** The binary and the directories in `deploy.include` (`config` and `resources`, when present) go to a new directory under `releases/` on every server, compressed. The directories in `deploy.shared` are links to `shared/`, so `storage/` survives releases.
3. **Environment.** `/etc/<app>/env` is written from the [three sources](#the-environment).
4. **Migrate.** `migrate` runs once, from the new release, on the first `web` server. If a migration fails, the deploy stops here and nothing else changes.
5. **Start.** The idle slot (green) is pointed at the new release and started on its own port, next to the live one.
6. **Health check.** Harbor requests `deploy.health_check` (`/health/ready`) on the new instance until it answers 200, for up to `deploy.health_timeout_secs` (60). [Readiness](/docs/digging-deeper/health-and-metrics/#readiness) runs every health check your modules register, the database included, so a release that can't reach its database never gets traffic. If it doesn't pass, Harbor stops the new instance, prints its last log lines, and the old release goes on serving as if nothing happened.
7. **Switch.** Caddy is pointed at the new instance and reloads gracefully: connections in flight finish on the old one. The `current` link moves to the new release in one atomic rename.
8. **Drain.** The old slot gets SIGTERM and finishes its requests in flight (`http.shutdown_grace_secs`, 30 seconds) before it exits.
9. **Restart workers.** The worker and scheduler processes restart on the new release. Each finishes the jobs it is running first.
10. **Prune.** Releases beyond `deploy.keep_releases` (5) are removed.

<FileTree title="/srv/crm-api/">{`
releases/
  20261026-091512-3f2a9c1/ *
    crm-api
    config/
    storage -> ../../shared/storage
  20261025-163003-9b17e44/
current -> releases/20261026-091512-3f2a9c1
blue -> releases/20261025-163003-9b17e44
green -> releases/20261026-091512-3f2a9c1
shared/
  storage/
`}</FileTree>

| Option | What it does |
|---|---|
| `--server <name>` | Deploy to one server. |
| `--env <name>` | Use `harbor.<name>.toml`; see [environments](#environments). |
| `--no-migrate` | Skip the migrations. |
| `--maintenance` | Turn on [maintenance mode](/docs/digging-deeper/maintenance-mode/) before migrating and off after the switch, for migrations the running release can't work with. |
| `--release <id>` | Deploy a release already built and uploaded, without building. |

### Zero downtime, and what it asks of you

The old release keeps serving until the new one is healthy, and requests in flight finish where they started, so users see no errors during a deploy. Two things make that work, and they are yours to keep:

- **Migrations must suit both releases.** The new release migrates the database while the old one still serves. Add columns and tables freely; rename or drop one over two deploys: first stop using it, then remove it. When that isn't possible, deploy with `--maintenance`.
- **WebSockets reconnect.** Connections held by the old instance close when it drains, and Pusher clients reconnect to the new one within seconds. Real-time clients see a reconnect, not an error.

Workers and the scheduler finish their running jobs before they restart, so no job is cut off by a deploy; give your longest jobs a `timeout_secs` that fits in the units' stop timeout.

## Rollbacks

```sh
navree deploy:rollback
```

```text
Rolling back crm-api on app-1 to 20261025-163003-9b17e44
  start     app-1  blue on 127.0.0.1:8081
  health    app-1  GET /health/ready 200 after 0.3 s
  switch    app-1  Caddy -> blue, current -> 20261025-163003-9b17e44
  drain     app-1  green stopped after its requests finished
  restart   app-1  worker x2, scheduler
Rolled back in 6s.
```

A rollback switches to the previous release with the same start, health check, switch and drain as a deploy, without building or uploading anything. `--to <release>` picks an older one, and `navree deploy:releases` lists them:

```text
20261026-091512-3f2a9c1  current  feat: stage probabilities
20261025-163003-9b17e44           fix: deal board ordering
20261024-110741-52ad0f3           chore: dependencies
```

Rollbacks don't undo migrations: the database stays as the newer release left it, which is why migrations must suit both releases. To undo the last batch as well, run `navree harbor:run migrate:rollback` before rolling back.

## Several servers and roles

As your app grows, give each role its own servers:

```toml title="harbor.toml"
app = "crm-api"
domain = "crm.example.com"

[deploy]
trusted_proxies = ["10.0.0.0/24"]   # the load balancer's network

[servers.web-1]
host = "203.0.113.11"
private_ip = "10.0.0.11"
roles = ["web", "scheduler"]

[servers.web-2]
host = "203.0.113.12"
private_ip = "10.0.0.12"
roles = ["web"]

[servers.worker-1]
host = "203.0.113.21"
private_ip = "10.0.0.21"
roles = ["worker"]

[servers.data-1]
host = "203.0.113.31"
private_ip = "10.0.0.31"
roles = ["postgres", "redis"]
```

- **Private network.** Servers with a `private_ip` talk to each other over it: PostgreSQL and Redis listen on it, and the firewall admits only your servers' addresses. Without one, they connect over the public addresses with TLS required.
- **Rolling deploys.** Harbor builds once, uploads to every server in parallel and migrates once. Then it switches the web servers one at a time, each after its own health check. If one fails, Harbor switches the ones it already moved back to the previous release, so all web servers always run the same release. Workers and the scheduler restart once every web server is on the new release.
- **A load balancer in front.** With more than one web server, put your provider's load balancer in front, forwarding ports 80 and 443 to each one. Caddy still terminates TLS. Turn on `web.proxy_protocol = true` when the balancer speaks the PROXY protocol, so Caddy, and then your app, see each client's address.
- **SQLite or PostgreSQL.** SQLite suits one server. With several servers, use the `postgres` role and the `postgres` feature.

To add a server, add its table, run `navree harbor:provision <name>`, then `navree deploy`.

In a Cargo workspace of several services, each service's package directory has its own `harbor.toml` with its own servers or roles. Run `navree deploy` from that directory to release one service without touching the others.

## A front end next to your API

An app with a web front end in `web/`, such as one made by `navree new --ui next` or the [SaaS starter kit](/docs/getting-started/starter-kits/), deploys it in the same release. Describe it in `[frontend]`:

```toml title="harbor.toml"
[frontend]
path = "web"
build = "pnpm install --frozen-lockfile && pnpm build"
command = "pnpm start"
health_check = "/"
```

- Harbor builds it during the deploy's build step, uploads it with the binary into the release, and installs Node.js LTS on `web` servers when it provisions them.
- It runs in its own blue and green slots (ports 3001 and 3002) with its own health check, and switches together with the API, so a page and the API it calls always come from the same release.
- Caddy serves `domain` from the front end. The API stays on loopback, where the front end's server calls it; set `api_domain` to also serve the API publicly, for example `api.crm.example.com` for mobile clients.

## Environments

Each environment has its own file: `harbor.toml` for production, `harbor.staging.toml` for staging, with its own servers, settings, secrets and key (`harbor.staging.key`). Pass `--env` to any command:

```sh
navree harbor:provision --env staging
navree deploy --env staging
navree harbor:secrets set APP_KEY --generate --env staging
```

`NAVREE_HARBOR_ENV=staging` does the same for a whole shell or CI job.

## Working with your servers

| Command | What it does |
|---|---|
| `navree harbor:status` | Each server's roles, its processes and their state, the current release, disk and memory. |
| `navree harbor:logs` | Your app's log lines from journald, merged across servers, newest last. `--server`, `--process web`, `--lines 200` and `--follow` narrow them down. |
| `navree harbor:run <command> [args]` | Runs one of your app's commands on the first `web` server (or `--server`), from the current release with its environment: `navree harbor:run migrate:status`, `navree harbor:run queue:retry all`. |
| `navree harbor:ssh [server]` | Opens a shell on a server as the `navree` user. |
| `navree harbor:backup` | Runs the PostgreSQL backup now; `--download` also copies it to your machine. |

## Container images

Harbor servers run your binary under systemd; they don't need a container runtime. For platforms that run containers, `navree build:image` builds an OCI image of your app with Docker or Podman:

```sh
navree build:image
navree build:image --tag registry.example.com/crm-api:1.4.0 --push
navree build:image --platform linux/arm64
```

```text
Built crm-api:3f2a9c1 (linux/amd64) with docker.
```

The image builds in two stages and runs on a slim Debian base:

| | |
|---|---|
| Contents | The binary at `/app/crm-api`, and `config/` and `resources/` when present |
| Working directory | `/app`, so the binary finds `config/app.toml` |
| User | An unprivileged user, uid 10001 |
| Writable | `/app/storage`, declared as a volume |
| Environment | `APP_HTTP__ADDR=0.0.0.0:8080`, `EXPOSE 8080` |
| Entry point | `/app/crm-api`, with `serve` as the default command |

The same image runs every process: pass the command.

```sh
docker run -p 8080:8080 --env-file production.env registry.example.com/crm-api:1.4.0
docker run --env-file production.env registry.example.com/crm-api:1.4.0 queue:work
docker run --env-file production.env registry.example.com/crm-api:1.4.0 migrate
```

`navree harbor:secrets export > production.env` writes `[env]` and the decrypted `[secrets]` as an env file; keep the file out of your repository, and prefer your platform's secret store. Point the platform's liveness and readiness probes at [`/health/live` and `/health/ready`](/docs/digging-deeper/health-and-metrics/).

To change the image, `navree build:image --dockerfile` writes the `Dockerfile` and `.dockerignore` it uses into your app; later builds use your copy.

## Push to deploy with GitHub Actions

`navree harbor:ci github` writes a workflow that tests and deploys every push to `main`:

```yaml title=".github/workflows/deploy.yml"
name: Deploy

on:
  push:
    branches: [main]

concurrency:
  group: deploy-production
  cancel-in-progress: false

jobs:
  deploy:
    runs-on: ubuntu-24.04
    environment: production
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
      - run: cargo test --locked
      - run: cargo install --git https://github.com/NavreeHQ/navree navree-cli --locked
      - run: navree deploy
        env:
          NAVREE_HARBOR_KEY: ${{ secrets.NAVREE_HARBOR_KEY }}
          NAVREE_HARBOR_SSH_KEY: ${{ secrets.NAVREE_HARBOR_SSH_KEY }}
```

Set it up once:

1. Create a key pair for CI (`ssh-keygen -t ed25519 -f ci-deploy -N ""`), add `ci-deploy.pub` to `ssh.authorized_keys`, and run `navree harbor:provision` so the servers accept it.
2. In the repository's settings, add two secrets: `NAVREE_HARBOR_KEY`, the contents of `harbor.key`, and `NAVREE_HARBOR_SSH_KEY`, the contents of `ci-deploy`.

The runner verifies each server against the `host_key` in `harbor.toml`, so it needs no `known_hosts` file. The `concurrency` group makes deploys queue one after another instead of overlapping, and a failing test stops the deploy before anything is built.

## Security

- **SSH.** Keys only, host keys pinned in `harbor.toml`, `fail2ban` on the SSH port. Deploys use the `navree` user, whose `sudo` covers only the app's units and Caddy.
- **Network.** A deny-by-default firewall; databases reachable from your servers only; the app itself listens on loopback, behind Caddy.
- **TLS.** Certificates from Let's Encrypt, renewed automatically, HTTP redirected to HTTPS. Navree's own `Strict-Transport-Security` header tells browsers to stay on HTTPS.
- **Secrets.** Encrypted at rest in the repository, decrypted only on the deploying machine, stored on servers in a file only root and the app's user can read.
- **The app's processes.** Run as an unprivileged user, with systemd hardening: no new privileges, a read-only system, a private `/tmp`, and write access to `shared/` alone.
- **Updates.** Security updates install automatically. Harbor never reboots a server on its own; `navree harbor:status` says when one needs a reboot.

## Reference

### Commands

| Command | What it does |
|---|---|
| `navree harbor:init` | Writes `harbor.toml` and `harbor.key`, and ignores the key in Git. |
| `navree harbor:provision [server]` | Prepares every server, or one, for its roles. Safe to run again. |
| `navree harbor:secrets set <NAME> [--generate] [--stdin]` | Encrypts and stores a secret. `--generate` makes an application key. |
| `navree harbor:secrets list`, `reveal <NAME>`, `unset <NAME>` | Lists names, prints one value, removes one. |
| `navree harbor:secrets export` | Prints `[env]` and the decrypted `[secrets]` as an env file. |
| `navree harbor:secrets rotate-key` | Re-encrypts every secret under a new key. |
| `navree deploy` | Builds, uploads, migrates, health-checks and switches to a new release. |
| `navree deploy:rollback [--to <release>]` | Switches back to the previous release, or to one you name. |
| `navree deploy:releases` | Lists the releases on the servers. |
| `navree harbor:status`, `harbor:logs`, `harbor:run`, `harbor:ssh`, `harbor:backup` | See [working with your servers](#working-with-your-servers). |
| `navree harbor:ci github` | Writes the GitHub Actions workflow. |
| `navree build:image [--tag] [--push] [--platform] [--dockerfile]` | Builds an OCI image of the app. |

Every command takes `--env <name>`.
