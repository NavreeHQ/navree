## Navree 0.2.0

0.2.0 replaces the data layer, makes SQLite an opt-in feature, puts Navree's own router, extractors and validation derive in place of the routing and validation crates it used before, swaps eight more third-party building blocks for code Navree owns, hardens sign-in, rate limiting and the edge, and adds supply-chain checks, fuzzing and tests that clean up after themselves. Everything shares one version number: the crates, the `navree` CLI, the starter kits and the `@navree/*` npm packages are all 0.2.0.

<Callout type="warning" title="Upgrading from 0.1">

0.2.0 breaks apps that use the SeaORM-based data API or garde, and it changes routing details, a few other APIs, defaults and behaviors. [Upgrading from 0.1](#upgrading-from-01) lists each change with the steps to take.

</Callout>

### The data layer is Navree's own

Navree no longer builds on SeaORM, sea-query or sea-orm-migration, and no `sea-*` crate is in the dependency tree (a test keeps it that way).

- **`navree-db`** runs directly on sqlx: pools that honor every `database.*` setting, statements, rows, errors classified the same way on every database (`DbError` with an `ErrorKind`), transactions with savepoints, and the `Executor` that pools, transactions, units of work and `Db` share. A unit of work always runs on `navree-db`'s own transaction.
- **`navree-orm`** writes its own SQL for PostgreSQL with TimescaleDB, MySQL and MariaDB, and SQLite, and runs it through `navree-db`.
- **`navree-schema`** is the only migration system: the schema builder, the migrator and schema dumps.
- **Every crate moved with them.** Authentication, access, audit, workspaces, queues, notifications, mail, billing, flags, settings, sign-in, OAuth, SSO, webhooks, workflows, localization, integrations, media, AI, Logbook, Fleet, search, Helm, Lighthouse, imports and exports, directory sync, custom domains, time zones, sessions, scheduling, microservices and the generators and starter kits now use [models](/docs/orm/models/), `navree-db` statements and schema-builder migrations. Existing tables need no change by hand: models read the same columns, and a database migrated by 0.1 keeps its migration history. Two migrations are new (custom domains and, on SQLite, search); `migrate` runs them.
- Statements stay correct on PostgreSQL and MySQL when a placeholder's value type changes between runs, and SQLite migrations begin `IMMEDIATE`, so they queue for the write lock instead of failing with "database is locked".

### SQLite is opt-in

SQLite is no longer compiled into every build. It is the `sqlite` Cargo feature of `navree` (and of `navree-db`), off by default like `postgres` and `mysql`, so a PostgreSQL or MySQL build compiles no SQLite C code: the bundled SQLite library is most of the C in a build, and `cargo tree -i libsqlite3-sys` finds nothing without the feature. `navree new` writes the driver feature you chose, and `sqlite` in `[dev-dependencies]`, because tests run on SQLite files. [Upgrading from 0.1](#2-turn-on-the-sqlite-feature-where-you-use-it) has the steps.

### Validation is Navree's own

`#[derive(Validate)]` and its `#[validate(...)]` field rules are Navree's code, in the new `navree-validation-macros` crate and the rule runtime of `navree-validation`; garde is gone from every manifest, and so are its vet exemptions. Every field states its rules or `#[validate(skip)]`, so a field added later can't go unchecked: a field without either is a compile error (`#[validate(skip_unmarked)]` on the type opts out). The rules are `required`, `length`, `range`, `email`, `url`, `ip`, `ipv4`, `ipv6`, `ascii`, `alphanumeric`, `credit_card`, `contains`, `starts_with`, `ends_with`, `pattern` (checked at compile time), `same_as`, `custom`, `nested`, `each(...)` and `rename`. The email (RFC 5321) and URL (RFC 3986) parsers are Navree's own, with property tests and a libFuzzer target. A failure is a `Violation`: a rule key and parameters, or a text, at a dotted path that follows serde's `rename` and `rename_all`. The [400 response](/docs/basics/validation/#error-responses) keeps its format and its messages. `navree-validation` has an optional `time` feature that implements `Validate` for the zones, days and day ranges of `navree-time`.

### Navree's own router and extractors

`navree-http` routes requests itself. The router matches the path as the client sent it, segment by segment, and never rewrites it: static segments before parameters before catch-alls, percent-decoded parameter values, `HEAD`, `OPTIONS` and 405 with `Allow`, and boot-time checks for conflicting routes. Handlers are async functions whose arguments are extractors: `Path`, `Query`, `RawQuery`, `Form`, `Json`, `Multipart`, `WebSocketUpgrade`, `Extension`, `Scoped`, `ClientIp` and `CurrentPrincipal` are Navree's own, with body limits, limits on every part of a form and on WebSocket frames, an urlencoded parser and media-type parsing, and rejections that render in the unchanged JSON error format. `RouteDef::on(method, path, handler)` takes such a handler. `HeaderMap`, `Method`, `Uri`, `Version`, `Extensions`, `Bytes`, `String` and `Request` are extractors too. [Upgrading from 0.1](#5-check-the-routing-changes) lists the behaviors that changed.

### Navree's own code in place of third-party crates

- **Tokens.** `navree_crypto::jose` signs and verifies JSON Web Signatures (HS256, EdDSA, ES256, RS256 and their siblings) on `ring` and reads and publishes JSON Web Keys; `navree-auth` issues its tokens through it. Tokens issued by 0.1 still verify.
- **Two-factor codes and QR codes.** `navree_crypto::totp` (RFC 6238, with `otpauth://` URLs) and `navree_crypto::qr` (ISO/IEC 18004, as SVG) make the two-factor setup. The secrets, URLs and codes are the same as before, so enrolled authenticator apps keep working.
- **Cron.** `navree_schedule::CronExpression` is Navree's own parser and next-run search, with a documented language and clear errors.
- **Configuration.** `navree-config` has its own loader for `.env`, TOML and JSON files and `APP_*` variables, with limits on file size and nesting and secrets kept out of errors.
- **CORS.** `navree-http` has its own CORS layer, used by the HTTP pipeline and the gRPC edge. The `http.cors.*` keys are unchanged.
- **MCP.** `navree-mcp` has its own protocol layer and transports (protocol versions `2024-11-05` to `2025-11-25` and the stateless `2026-07-28`), checked against the official MCP TypeScript SDK's client. Navigator's own stdio server uses it too.
- **Cache.** The in-memory cache store is `navree-bounded`'s bounded store: at most 1,000,000 entries, with SIEVE eviction.
- **Compression.** Responses are compressed with gzip; Brotli is gone.
- **API docs and GraphiQL.** The API reference UI and GraphiQL ship inside the app instead of loading scripts from a CDN.

### Security hardening

- **IPv6 clients count by network.** The per-IP limit, the login, social and OAuth throttles count an IPv6 client as its network (`http.rate_limit_ipv6_prefix`, default 64), so one host can't dodge a limit by changing addresses within its prefix. `X-Forwarded-For` entries may carry a port.
- **One sign-in policy for every path.** `navree-auth` asks every `SignInPolicy` before a password, magic link, emailed code, passkey, social, token-exchange or second-step sign-in, and before an email change. `navree-sso` enforces single sign-on through it, so an SSO domain refuses every other way in, not only passwords. Helm's panel sign-in asks the same policies. Sign-in domains are normalized, so every spelling of an SSO domain matches.
- **Offboarding in one call.** `revoke_credentials_of_domain` (and `revoke_all_credentials`) revokes every credential of the users of a domain.
- **OAuth endpoint limits.** The token, introspection, revocation and device endpoints have per-client and per-IP rate limits (`oauth.rate_limits`); public clients are limited per IP only.
- **Custom domain claims by proof of control.** A pending claim never blocks the owner of a domain, a verified claim wins, a transfer needs fresh proof, and failed claims are deleted after `domains.verification.failed_retention_hours`.
- **Tighter content security policies.** The API reference and GraphiQL load scripts from the app itself (`script-src 'self'`), GraphiQL's WebSockets may only reach the request's host, and GraphQL hides its internal types from introspection.
- **Client addresses behind proxies.** The `@navree/bff` backend-for-frontend forwards the browser's address (`clientIpHeader`, `NAVREE_CLIENT_IP_HEADER`), and Harbor's Caddy trusts the load balancer's `X-Forwarded-For` (`deploy.trusted_proxies`).
- **Parser limits and fixes.** Fuzzing found crashes in the parsers for host names, phone numbers, email domains and SCIM filters; they are fixed, and SCIM filters are capped at 16 KiB and 32 levels.
- **Lighthouse counts exactly under load.** Counts are never queued, the detail queue is bounded and samples what it drops (`lighthouse_sampled_out_total`), and the default trace sampling is 0.1.

### Supply-chain checks, fuzzing and test folders

- **Gates on every change.** `cargo-deny` (advisories, licenses, bans, sources), `cargo-vet`, OSV-Scanner over every lockfile, Semgrep with Navree's own rules, Gitleaks over the history, a daily vulnerability scan, and GitHub Actions pinned to commit SHAs. Tagged releases get a CycloneDX SBOM. [Contributing](/docs/prologue/contributing/) lists them, `SECURITY.md` says how to report a vulnerability and `CODEOWNERS` names the reviewers.
- **Fuzzing.** A separate `fuzz/` workspace has a target for every parser of untrusted input; CI runs each briefly when `fuzz/` changes and for longer every week.
- **Test folders clean up after themselves.** Every temporary folder a test makes is named `navree-test-*`; `TempDirGuard` deletes it, retrying for a short while on Windows where an open handle blocks the delete, and a sweep that runs at most every ten minutes removes the `navree-test-*` folders more than an hour old that a crashed run left behind.

### The CLI and the starter kits

- New apps depend on `navree` with the driver feature of the database you chose and `sqlite` in `[dev-dependencies]`. When `navree new` finds no checkout to point at, the dependency is the CLI's own version (`0.2.0`), not a fixed one. Generators write models and schema-builder migrations, and no generated `Cargo.toml` lists `sea-orm`.
- `navree new` runs `git init` (nothing is committed) unless the directory is inside a repository, and writes `harbor.key` for apps that ship a `harbor.toml` (the starter kits). `navree harbor:init` on an existing `harbor.toml` writes only a missing key. `navree make:resource <module> <Model>` reads `models/<model>.rs`.
- The starter kits run on the new APIs. Their `kit_version` is 0.2.0, the SaaS kit's `.env.example` gains `NAVREE_TRUSTED_PROXY_HOPS` and `NAVREE_CLIENT_IP_HEADER`, and the kits' CI, READMEs and `AGENTS.md` files follow the changes above. To pick up a kit's changes, generate a fresh copy and compare, as [Starter kits](/docs/getting-started/starter-kits/#updating) describes.

### Fixes

- Search: typo tolerance and engine edge cases (`search.postgres.typo_threshold`), SQLite full-text rows keyed by rowid, Qdrant date ranges and Meilisearch `drop_index`.
- Scheduling: interval-style crons follow the wall clock through clock changes, and fixed-time crons run each local time once.
- Microservices: `start_listener` and `micro:listen` return once the transport has confirmed its subscriptions, so a request sent right after boot over NATS is no longer lost.
- Browser testing: a screenshot brings its page to the front first, failure screenshots included.
- Harbor: SSH options, key-only `harbor:init`, the `harbor:ci` workflow in an app that its repository ignores, and running Harbor on Windows.

## Upgrading from 0.1

Work through these steps in order and build after each. Most apps need steps 1 to 5 and a look at step 7.

### 1. Raise the version

Point the `navree` dependency at 0.2.0: `cargo update -p navree` for a Git dependency on the branch you track, or `version = "0.2.0"` once the crates are published, or a `path` to a 0.2.0 checkout. Reinstall the CLI so that `navree new` and the generators match:

```sh
cargo install --git https://github.com/NavreeHQ/navree navree-cli --force
```

If your front end uses `@navree/client`, `@navree/bff`, `@navree/next`, `@navree/nuxt` or `@navree/theme`, move them to 0.2.0 together. Run `navree skills:install` again to refresh the agent skills.

### 2. Turn on the `sqlite` feature where you use it

SQLite is no longer built in. Add the `sqlite` feature wherever SQLite runs:

- **An app on SQLite**: `navree = { git = "https://github.com/NavreeHQ/navree", features = ["sqlite"] }`. `navree new --database sqlite` writes it.
- **An app on PostgreSQL or MySQL** changes nothing it runs on, but its tests run on SQLite files (`TestApp`'s `temp_database()` and `memory_database()`, and the default of `#[navree::test]`). Add the same entry to `[dev-dependencies]`: `navree = { git = "https://github.com/NavreeHQ/navree", features = ["sqlite"] }`.
- **`database.url` left out** still means `sqlite://storage/app.db?mode=rwc`, so an app built without the feature stops at boot with "enable the `sqlite` feature of navree-db" instead of falling back to a file. Set the URL, or turn the feature on.
- **Logbook's `file` store** is a SQLite file of its own, so it needs the feature too (`navree`'s `sqlite`, or `navree-logbook`'s). Without it `logbook.store` defaults to `memory`, and `logbook.store = "file"` fails at boot. A generated PostgreSQL app therefore keeps its Logbook entries in memory under `navree dev` unless you add the feature to its `[dependencies]`.
- **Crates that depend on `navree-db` directly** turn `sqlite` on where their tests need it (`navree-db = { git = "https://github.com/NavreeHQ/navree", features = ["sqlite"] }` in `[dev-dependencies]`).
- **Apps that use `micro` with `DatabaseModule`** must enable a driver feature (`postgres`, `mysql` or `sqlite`); the `micro` feature turns on `db` but no driver.

### 3. Move from SeaORM to models and the schema builder

An app has one data API now: [models](/docs/orm/models/) and records, the [schema builder](/docs/database/schema-builder/), and the `Executor`, `Statement` and `Uow` types of `navree::db`.

1. **Drop the dependencies.** Remove `sea-orm`, `sea-orm-migration` and `sea-query` from `Cargo.toml`, along with `async-trait` if only migrations used it. `#[derive(Model)]` needs no crate of its own.
2. **Rewrite each entity as a model** (below), and each migration as a schema-builder migration (below). Existing tables need no change: models read the same columns, and a database migrated by the old migrator keeps its history.
3. **Replace the old calls** using the table below. The compiler finds them all: every removed name is gone from `navree::db`.
4. **Match on the new errors.** `DbErr` becomes `DbError`, and queries made through models return `OrmError`.

| Before | Now |
|---|---|
| `navree::db::sea_orm`, `navree::db::sea_orm_migration` | Removed |
| A module with `Model`, `Relation` and `ActiveModel` types, `DeriveEntityModel` | A struct with `#[derive(Model)]` and `#[model(table = "...", timestamps)]` |
| `Entity::find()`, `Column::X.eq(..)`, `ActiveModel { .. }.insert(..)` | `Post::query()`, `Post::TITLE.eq(..)`, `Post::create(&uow, ..)` |
| `Repo::<E>::insert`, `update`, `delete`; `navree::db::{Repo, Reader, Factory, create, create_many}`; `navree::prelude::Repo` | `Model::create(&uow, ..)`, `record.save(&uow)`, `record.delete(&uow)`. They record the same change events. |
| `navree::db::paginate`, `cursor_paginate`, `cursor_paginate_desc` on a `Select` | `Builder::paginate(&uow, page)` and `Builder::cursor_paginate(&uow, cursor)` with `CursorRequest`; the `Page` shape is unchanged |
| `seed::Factory` with `type Entity`; `ModelFactory` as `navree_db::Factory` | [Model factories](/docs/orm/factories/): `navree::orm::factory::ModelFactory` (still in the prelude, under the `orm` feature) |
| `uow.tx()`, `uow.open_tx()`, `DatabaseTransaction` | A `Uow` is an `Executor`: pass `&uow`. Nest work with `uow.savepoint()`; begin your own transaction with `Db::begin`. |
| `DatabaseConnection`, `db.conn()`, `db.read_conn()`, `Db::from_connection`, `Db::reader` | `Db` is an `Executor`; `db.pool()` and `db.read_pool()` give the pools, `db.read_executor()` the replica to read from |
| `ConnectionTrait` (`execute_raw`, `query_one_raw`, `query_all_raw`, `execute_unprepared`) | `Executor::{execute, fetch_optional, fetch_all, execute_script}` |
| `Statement::from_sql_and_values`, `from_string`; `QueryResult::try_get`; `ExecResult` | `Statement::new(backend, sql, values)`, `Statement::portable(sql, values)` (`?` placeholders), `Statement::text(sql)`; `Row::get::<T>(name)`; `Executed { rows_affected, last_insert_id }` |
| `DbErr`, `SqlErr`; `DbBackend` | `DbError` with `ErrorKind` (`is_unique_violation()`, `is_foreign_key_violation()`, `is_not_found()`, `is_retryable()`); `Backend`. Model queries return `OrmError` (`db_error()` gives the `DbError` inside). |
| `map_db_error(&DbErr)` | `map_db_error(&DbError)` |
| `ChangeObserver::observe(&self, &DatabaseTransaction, &Uow, changes) -> Result<(), DbErr>` | `ChangeObserver::observe(&self, &Uow, changes) -> Result<(), DbError>` |
| `LoggedQuery { values: Vec<sea_orm::Value>, backend: DbBackend }` | `values: Vec<navree_db::Value>`, `backend: Backend` |
| `navree_orm::Value::BigInt(Some(42))`, `Value::BigInt(None)` | `Value::I64(42)`, `Value::Null(Kind::I64)`: `navree_orm::Value` is `navree_db::Value` |
| `Field::from_sql(&QueryResult, ..)`; `Row::sql()` | `Field::from_sql(&navree_db::Row, ..)`; `Row::db_row()`, `Row::into_db_row()` |
| `From<sea_query::Condition>` and `From<sea_query::Expr>` for `Filter`; `Where::Sql` | `Filter::raw(Statement::portable(..))` or builder conditions (`Post::TITLE.eq(..)`, `where_raw`); `Where::Tree` |
| `navree_orm::sql::compile_*`; `Dialect::from_backend`, `to_sea_orm` | `navree_orm::sql::render_*`; `Dialect::backend()` |
| `OrmError::Db(DbErr)`, the `source` of `ModelNotFound` and `Timeout` | The same variants hold a `DbError`; `OrmError` no longer converts into `DbErr` |
| `prune_time_series(conn: &impl ConnectionTrait, ..)` | `prune_time_series(&impl Executor, ..)` |
| `MigrationTrait`, `SchemaManager`, `MigrationName`; `MigrationSet::migration(impl MigrationTrait)` | `navree::schema::Migration` and the schema builder; register with `migration!` (or `SchemaMigration::new(name, m)`) |
| `Schema::new(db.conn())`; a custom `SchemaConnection` over a SeaORM connection | `Schema::new(&db)` (a `Db`, `Pool`, `Transaction` or `Uow`); a custom `SchemaConnection` implements `backend() -> Dialect`, `execute(&str)` and `query(&str, &[SchemaValue]) -> Vec<SchemaRow>` |
| `SchemaError::Database` holding a `DbErr`; `From<SchemaError> for DbErr`; `Dialect::of` | A boxed database error (a `DbError` on `navree-db` connections); the conversion and `Dialect::of` are gone |
| `sea_query` filters (`Expr`, `Condition`) | Builder conditions (`Post::TITLE.eq(..)`, `where_raw`) or a `Statement::portable` fragment |

`Db::transaction(|uow| async move { .. })` is the shorter form for work that returns `Result<_, DbError>`, as statement-only work does. A model call returns `OrmError`, which does not convert into `DbError`, so work with models belongs in a service that takes the request's `&Uow`, or in a unit of work you open yourself and run in its scope:

```rust
let uow = db.uow(Some(user_id), None).await; // the actor the audit log records
let result = uow
    .scope(async {
        let mut post = Post::find_or_fail(&uow, id).await?;
        post.delete(&uow).await?;
        Ok::<_, OrmError>(())
    })
    .await;
match result {
    Ok(()) => uow.commit().await?,
    Err(error) => {
        uow.rollback().await?;
        return Err(error.into());
    }
}
```

Builds of the main branch between the two releases had a `database.native_units_of_work` option and a `NAVREE_TEST_NATIVE_UNITS_OF_WORK` variable. Both are gone and nothing reads them; delete any you set. A unit of work always runs on `navree-db`'s own transaction.

A migration written for the old API:

```rust
use navree::db::sea_orm_migration::prelude::*;

#[derive(DeriveMigrationName)]
pub struct Migration;

#[async_trait::async_trait]
impl MigrationTrait for Migration {
    async fn up(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        manager
            .create_table(
                Table::create()
                    .table(Alias::new("posts"))
                    .col(ColumnDef::new(Alias::new("id")).uuid().not_null().primary_key())
                    .col(ColumnDef::new(Alias::new("title")).string().not_null())
                    .to_owned(),
            )
            .await
    }
}
```

becomes:

```rust
use navree::schema::prelude::*;

pub struct Migration;

impl navree::schema::Migration for Migration {
    async fn up(&self, schema: &Schema<'_>) -> SchemaResult {
        schema
            .create("posts", |t| {
                t.uuid_primary();
                t.string("title");
            })
            .await
    }

    async fn down(&self, schema: &Schema<'_>) -> SchemaResult {
        schema.drop_if_exists("posts").await
    }
}
```

and the entity that read the table:

```rust
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, Serialize)]
#[sea_orm(table_name = "posts")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub id: Uuid,
    pub title: String,
}
```

becomes a model:

```rust
#[derive(Model, Clone, Debug, Default, PartialEq, Serialize)]
#[model(table = "posts")]
pub struct Post {
    pub id: Uuid,
    pub title: String,
}
```

Read it with `Post::query().where_(Post::TITLE.eq("Hello")).get(&uow)` and write it with `Post::create(&uow, Post { title: "Hello".into(), ..Post::default() })`.

### 4. Move from garde to `#[derive(Validate)]`

The derive comes with `navree`, so the app needs no validation crate of its own.

1. **Drop `garde`** from `Cargo.toml`, and replace `use garde::Validate;` with `use navree::validation::Validate;` (it is also in the prelude). A `build.rs` that adds `#[derive(garde::Validate)]` and `#[garde(..)]` to generated gRPC messages writes `#[derive(navree::validation::Validate)]` and `#[validate(..)]` instead.
2. **Rename the attribute and the rules.** `#[garde(...)]` is `#[validate(...)]`. Every field still states its rules or `#[validate(skip)]`. An old rule name is a compile error that names the new spelling, so the compiler leads you through the rest.
3. **Check the `length` rules.** `length(min = 1)` now counts characters; garde's plain `length` counted bytes. Write `length(bytes, max = 255)` where a byte limit is what you meant, and drop `chars` from `length(chars, ...)`.
4. **Rewrite custom rules.** A rule is a function of the value alone, returning `Result<(), E>` with `E: Into<Violation>`; a `Violation`, a `String` and a `&str` all qualify. Rules that need request data read it from the `InputContext`, and rules that query the database are async rules.
5. **Replace the bounds and the report.** `Validate<Context = ()>` is `Validate`, and `garde::Report` is `Violations`. `navree::validation::garde` is gone.

| Before | Now |
|---|---|
| `#[garde(...)]` | `#[validate(...)]`; `skip`, `required`, `range`, `email`, `url`, `pattern`, `custom`, `ascii`, `alphanumeric`, `contains`, `ip`, `ipv4`, `ipv6` and `credit_card` keep their names |
| `length(chars, min = 1)`; plain `length(min = 1)` on a string | `length(min = 1)`, which counts characters; `length(bytes, min = 1)` counts bytes |
| `dive` | `nested` |
| `inner(...)` | `each(...)` on a list, set or map; on an `Option`, the rules go on the field itself, since they apply to the `Some` value and pass on `None` |
| `prefix("x")`, `suffix("x")`, `matches(other)` | `starts_with("x")`, `ends_with("x")`, `same_as(other)` |
| `#[garde(allow_unvalidated)]` | `#[validate(skip_unmarked)]` on the type |
| `fn rule(value: &T, _ctx: &()) -> garde::Result` | `fn rule(value: &T) -> Result<(), E>` with `E: Into<Violation>` |
| `garde::Error::new(text)` | `Violation::text(text)`, or return the `&str` or `String` |
| `rule_error(key, params)` returning a garde error | `rule_error(key, params)` returns a `Violation` (also `Violation::rule(key).with(name, value)`) |
| `rules::{uuid, date_ymd, one_of, confirmed, unicode_name, country, locale, phone}` taking a context parameter; `navree_time::rules::time_zone(value, ctx)` | The same functions without the context: `fn(&T) -> Result<(), Violation>`; `one_of` and `confirmed` return `impl FnOnce(&T) -> Result<(), Violation>` |
| `AsStr`, `HasSimpleLength` and `Bounds` of garde, implemented for your own wrapper types | `navree::validation::rules::{RuleInput, Length, Range}` |
| `Validate<Context = ()>` bounds, on `Import::Row`, on settings groups, on agent tool arguments and on your own generic code | `Validate` |
| `#[garde(context(...))]`, which the extractors never supported | `custom` expressions can read `self`, request data comes from the `InputContext`, and database rules are async rules |
| `garde::Report` from `value.validate()` | `Violations`: each `Violation` has `key()`, `params()` and `message()`, and it displays one message per line with the field paths |
| `AsyncRule::passes<C: ConnectionTrait>(&C)`; `RuleError::Database { source: DbErr }`; `unique` and `exists` taking `sea_orm::Value` | `passes<E: Executor + ?Sized>(&E)`; `source: Box<DbError>`; `impl Into<navree_db::Value>` |

What else changes for an app that keeps its DTOs:

- **Field paths follow serde.** A rule failure names the field the way serde does, with `rename` and `rename_all` applied, so a DTO with `#[serde(rename_all = "camelCase")]` reports `firstName` in its `errors` map where 0.1 reported the Rust name for rule failures and the serde name for parse failures. `#[validate(rename = "...")]` overrides the name. A front end that reads the `errors` map by key needs no change when the DTO has no renamed fields.
- **`length` on a collection** reports the `elements` message (`tags must contain at least 1 elements`), also when the input came from a query string. The `characters` message is for text and `bytes` for `length(bytes, ...)`.
- **Stricter parsers.** `email` accepts ASCII dot-atom addresses (at most 254 bytes, a local part of at most 64) with a host name or an address literal, with punycode for internationalized domains. `url` accepts ASCII RFC 3986 absolute URLs and requires a host for `http`, `https`, `ws`, `wss` and `ftp`. `Phone` rejects numbers with more than 15 digits, the E.164 limit.
- **New compile errors.** A rule given twice on a field (only `custom` may repeat), `length()` or `range()` with no bound, a literal `min` above `max`, `same_as` naming no field, and `skip` combined with other rules.

### 5. Check the routing changes

`navree-http` has its own router and extractors. Handlers, `#[controller]` routes and `RouteDef::on` keep their shape; these behaviors change:

- **Paths the router can't route unambiguously are a 400 before any guard or handler runs**: a `.` or `..` segment (raw or percent-encoded), a backslash, and `%2F`, `%5C` or `%00` in the value of a `{name}` parameter. A value that isn't UTF-8 once decoded is a 400 too. A proxy or a test that sent such paths and expected a 404 now gets a 400.
- **An empty segment no longer matches a parameter.** `/deals//move` and a trailing slash are a 404 for `/deals/{id}/move` and `/deals/{id}`. Parameter values arrive percent-decoded, and `+` stays `+`.
- **A parameter must be a whole segment.** `#[get("/v{n}")]` and `#[get("/{name}.json")]` are compile errors; capture the segment and parse it in the handler.
- **Routes that differ only in parameter names fail the boot.** `/deals/{id}` and `/deals/{deal}` for one method name the same route twice: keep one name. `HttpModule` lists every such conflict in the boot error.
- **`OPTIONS` answers 204 with an `Allow` header** for a known path, without running a route, unless a route handles `OPTIONS` itself. CORS preflights are still answered by the CORS layer first. A client that treated the old 405 on `OPTIONS` as a signal needs a change.
- **`Form` checks its media type exactly.** It reads `application/x-www-form-urlencoded` only (parameters allowed), and answers 415 for anything else. `Json` reads `application/json` and `+json` types. A request with two `Content-Type` headers is a 415 for both.
- **Hand-written extractors lose the state parameter.** Implement `navree::http::extract::FromRequestParts` (or `FromRequest`, for one that reads the body) without the `S` that the traits of `navree::axum` took, as in the example below the list. There is one set of extractor traits: an extractor still written against the old ones doesn't compile in a handler.
- **Imports move.** `Path`, `Form`, `Extension`, `Json` and `Query` are `navree::http::{Path, Form, Extension, Json, Query}`, and `navree::http::body::Bytes` and `navree::http::extract::Request` replace their `navree::axum` twins. The prelude's `Path`, `Json` and `Query` are Navree's. `IntoResponse`, `IntoResponseParts`, `Response`, `Html`, `Redirect`, `AppendHeaders` and the server-sent events types are Navree's own, in `navree::http::response`, and `Body` and `to_bytes` in `navree::http::body`. They read the same on the wire. A body's error is a `BoxError`, and `Event::json_data` fails with a `serde_json::Error`. `navree::axum` is gone from the facade: `HeaderMap`, `Method`, `Uri`, `Version` and `StatusCode` come from the `http` crate, which your app adds to its dependencies.
- **Middleware moves too.** `from_fn`, `from_fn_with_state`, `Next` and `State` are `navree::http::middleware::*`, with `navree::http::extract::Request`: a function written for `navree::axum::middleware::Next` needs only its imports changed, and `State` must be its first argument. `build_router` returns an `AppRouter`, which is what a `GlobalLayer` wraps. It has `layer`, and it is a Tower service, so `tower::ServiceExt::oneshot` calls it in a test. `AppRouter::new` takes any service, and `AppRouter::from_handler` a catch-all handler.
- **`Multipart` moves, and has limits.** Import `navree::http::extract::Multipart`, with `Field` and `MultipartError` beside it. A form may have 1,000 parts, a part without a file name 1 MiB and a part's headers 16 KiB (413 past them; `http.multipart`, or `form.with_limits(..)` in a handler), and a file answers to the route's body limit as before. `field.text()` keeps to the 1 MiB whatever the part calls itself. A form with a boundary over 70 characters, two boundaries or two `Content-Type` headers is a 400. A body that's too slow is a 408. `MultipartError` is an enum now, and its `Display` is the same message as `body_text()`. A form that needs more sets its own limits: see [Multipart forms](/docs/basics/requests/#multipart-forms).
- **WebSockets move, and are smaller.** Import `WebSocketUpgrade`, `WebSocket`, `Message`, `CloseFrame` and `Utf8Bytes` from `navree::http::ws`. A client's frame and message are limited to 1 MiB each, down from 16 MiB and 64 MiB: raise them with `max_frame_size` and `max_message_size`. The handshake is stricter: `Sec-WebSocket-Key` must be one base64 value of 16 bytes, `Sec-WebSocket-Version` one header saying `13`, `Connection` and `Upgrade` are read as lists of tokens (so `Connection: not-upgrade` no longer passes, and `keep-alive` and `Upgrade` on two lines does), and an HTTP/1.0 request can't upgrade. A wrong version's 400 now names `Sec-WebSocket-Version: 13`. `accept_unmasked_frames`, `on_failed_upgrade` and `set_selected_protocol` are gone, and a socket's errors are `WebSocketError`. See [WebSockets](/docs/basics/requests/#websockets).
- **`RouteDef` takes Navree handlers.** `RouteDef::on(method, path, handler)` takes an async function or closure whose arguments are extractors, and its `handler` field is an `Endpoint`. `RouteDef::new(method, path, method_router)` is gone: use `RouteDef::on`.
- **All the decoded path parameters** are a `PathParams` extractor (`navree::http::PathParams`) for the handlers and extractors that need more than `Path<T>` gives them.

A hand-written extractor changes like this:

```rust
// before
impl<S: Send + Sync> FromRequestParts<S> for Tenant {
    type Rejection = AppError;
    async fn from_request_parts(parts: &mut Parts, _state: &S) -> Result<Self, AppError> { .. }
}

// now
impl FromRequestParts for Tenant {
    type Rejection = AppError;
    async fn from_request_parts(parts: &mut Parts) -> Result<Self, AppError> { .. }
}
```

### 7. Check the defaults and behaviors that changed

- **Sign-in.** Every sign-in path asks the `SignInPolicy`s, including the second step of two-factor sign-in and email and password changes, and an SSO domain refuses every non-SSO method. A password change or email change by an SSO user answers 403 `sso_required`. Tokens now carry a `sign_in` claim for challenge tokens; the header is `{"alg","typ"}`; verification refuses tokens over 8 KiB and tokens with a `kid` or `crit` header. Tokens issued before the upgrade still verify.
- **Rate limits.** An IPv6 client counts as its /64 network (`http.rate_limit_ipv6_prefix`). The OAuth endpoints are limited per minute, per client and per IP: token 300 and 120, introspection 1200 and 600, revocation 300 and 60, device authorization 60 and 30. Set a limit to `0` to turn it off, for example for a load test.
- **Compression.** `http.compression` is gzip only; a client that accepts only `br` gets an uncompressed response.
- **Cron.** These expressions are refused at boot now: names in the minute, hour or day-of-month field (`MON * * * *`), a weekday name as the month, empty list items (`1,,2`), a lone `L` in the day of week, `1-5#2`, `?/5` and a bare `*` inside a list. A task with `in_zone`, `in_default_zone` or `per_*_local` and a `*` in the minute or hour field (`0 * * * *`, `*/15 * * * *`, `@hourly`) follows the wall clock: it runs in both passes of a repeated hour and catches nothing up after a gap. UTC tasks are unchanged.
- **Lighthouse.** `lighthouse.sample.requests` and `lighthouse.sample.jobs` default to `0.1` (they were `1.0`): set them to `1.0` to keep every trace. The metric `lighthouse_dropped_total` is `lighthouse_sampled_out_total`, and `Overview` has a `sampled_out` field. `lighthouse.buffer` bounds the detail queue only; counts are exact.
- **Logbook.** `logbook.store` defaults to `memory` unless the `sqlite` feature is on (step 2).
- **API reference and GraphiQL.** Their scripts are served by the app (`GET {api_prefix}/docs/assets/{file}` and `GET <graphiql path>/assets/{file}`) and the content security policy is `script-src 'self'`. Behind a proxy, forward the `Host` header: GraphiQL's WebSockets are allowed to the request's host only.
- **gRPC.** The edge uses `navree_http::CorsLayer`: origins match byte for byte, `*` is never sent, a request with two `Origin` headers is refused and preflights never reach the service. The `http.cors.*` keys are unchanged.
- **Custom domains.** `custom_domains.host` is no longer unique: the owner is the row with `verified_host` set (the new migration backfills it). `domain_taken` means "verified for another workspace, or this workspace already holds a claim", and a pending claim of another workspace blocks nobody. SQL of your own against `custom_domains` must use `verified_host` for the owner.
- **Harbor.** After setting `deploy.trusted_proxies`, run `navree harbor:provision` and then `navree deploy`: Caddy then trusts the load balancer's `X-Forwarded-For`, and the front end's environment sets `NAVREE_TRUSTED_PROXY_HOPS=1`.
- **Microservices.** `start_listener` and `micro:listen` return after the transport confirms its subscriptions. Custom `MicroTransport`s compile unchanged.
- **Search.** The `search` migration creates nothing on MySQL, and the `postgres` engine is refused there at boot. On SQLite a new migration rebuilds the full-text table keyed by rowid.
- **Outgoing HTTP.** The default `user_agent` of `navree-http-client` is `navree-http-client/<version>` of the running crate.
- **Telemetry.** The `method` label of `http_requests_total` and `http_request_duration_seconds`, and `RequestHandled.method`, is one of the standard methods or `OTHER`.

## Connection limits

The `serve` command runs on `navree::http::serve`, which bounds what a client can hold (slow headers, slow bodies, idle connections, responses it stops reading, unanswered HTTP/2 pings, the number of connections in all and per address) with the safe defaults of [`http.server`](/docs/getting-started/deployment/#connection-limits). A full server closes its longest-idle connection for a client that's waiting and has sent something. Behind a reverse proxy, list it in `http.trusted_proxies`, or its connections count against `http.server.max_connections_per_ip` (256). WebSockets are bounded only if you set `http.server.upgraded_idle_timeout_ms`. A request head over 32 KiB or with over 100 headers is a 431, and the peer's address is `navree::http::serve::ConnectInfo`. A gRPC client's `grpc-timeout` can shorten `grpc.timeout_secs` but not extend it, so raise that key if a method needs longer than the default of `http.timeout_secs`.

## The framework

### Foundation

- **`navree-kernel`**: the module graph, a type-keyed dependency-injection container with singleton, request and transient scopes, lifecycle hooks, graceful shutdown and the command runner behind `serve`, `migrate` and every other command. The graph is validated before anything is constructed, and `check --graph` prints it.
- **`navree-macros`**: `#[module]`, `#[injectable]`, `#[controller]`, the route attributes (`#[get]`, `#[post]`, `#[put]`, `#[patch]`, `#[delete]`) and the helper attributes for access, throttling, timeouts, transactions, audit actions and OpenAPI metadata. A route without an access declaration doesn't compile.
- **`navree-contracts`**: the small shared traits and types that let modules cooperate without depending on each other: `Secret<T>`, `RequestId`, `Principal`, jobs and dispatchers, sinks for audit and events, `Broadcaster` and `Clock`.
- **`navree-config`**: typed configuration from `.env`, TOML and JSON files and `APP_*` environment variables, validated at boot, with secrets redacted in logs and errors. The loader is Navree's own, with limits on file size and nesting.
- **`navree-log`**: a tracing subscriber with pretty or JSON output, field redaction, per-target levels and rotating log files.

### HTTP

- **`navree-http`**: the HTTP module, with a default pipeline (request ids, client IP resolution through trusted proxies, panic catching, timeouts, security headers, compression, a per-IP rate limit, body limits, maintenance mode), controllers, deny-by-default route access, per-route throttles, signed URLs, CORS and one JSON error shape for every error (`{ "statusCode", "message", "error", "code" }`, validation failures as 400 with `errors`), whose stable `code` a front end translates.
- **`navree-validation`**: `#[derive(Validate)]` rules with `Valid<Json<T>>`, `Valid<Query<T>>` and friends, with one readable message per broken rule and async `unique` and `exists` rules. International input: phone numbers in E.164 with a per-request default region, rich text sanitized by a configurable policy, names and digits in any script, ISO 3166-1 countries and BCP 47 locales.
- **`navree-api`**: an OpenAPI 3.1 document built from route metadata at `/api/openapi.json`, a docs UI at `/api/docs`, `openapi:export`, and API resource helpers.
- **`navree-session`**: encrypted session cookies with memory and database stores, and CSRF protection for single-page apps that use cookies.

### Data

- **`navree-db`**: a database engine on sqlx (pools, statements, rows, transactions and the `Executor` they share) with a unit of work per request (a transaction that commits when the response succeeds) that records change events, per-module migration sets, seeders, pagination and the `migrate`, `migrate:rollback`, `migrate:fresh`, `migrate:status` and `db:seed` commands. TimescaleDB is the default database (`navree new` sets it up and Dock runs it), with hypertables for Navree's own time-series tables and chunk-dropping pruning (`prune_time_series`); plain PostgreSQL with the same `postgres` feature, MySQL and MariaDB with `mysql`, and SQLite with `sqlite`.
- **`navree-orm`**: the [ORM](/docs/orm/getting-started/). Models are structs with `#[derive(Model)]` and typed column constants; a query builder with joins, subqueries, unions, aggregates, JSON and full-text conditions, row locks and bulk writes; records with dirty tracking; relationships of every kind with batched eager loading and lazy-loading prevention; casts, accessors and serialization; model events, observers and broadcasts; global and local scopes, soft deletes and pruning; offset and cursor pagination, chunks and streams; factories with fake data; `#[navree::test]` databases with templates and assertions; route model binding; and workspace and access-control scoping. It runs in the unit of work on PostgreSQL with TimescaleDB, MySQL and MariaDB, SQLite and, with `navree-mongo`, MongoDB.
- **`navree-schema`**: the [schema builder](/docs/database/schema-builder/) migrations are written with: tables, columns, indexes, foreign keys and check constraints in Rust, written as each database's SQL, SQLite table rebuilds, TimescaleDB hypertables, reading the live schema, and [schema dumps](/docs/database/squashing-migrations/) that replace a long migration history.
- **`navree-cache`**: a bounded memory cache store with `remember`, tags, stale-while-revalidate and atomic locks.

### Security

- **`navree-auth`**: 15-minute JWT access tokens and 30-day rotating refresh tokens with reuse detection, pluggable authentication strategies, `CurrentUser`, registration, password change and reset, email verification, TOTP two-factor authentication with recovery codes and a policy that requires it per role or per workspace, and login throttling. Users list and end their sessions; `#[recent_auth]` asks for the password or a code again before sensitive actions; support staff impersonate users behind `#[not_while_impersonating]` guards, with the impersonator on every audit entry; magic links, emailed sign-in codes and passkeys (ES256 and Ed25519) sign users in without a password; platform administrators sign in apart with two-factor authentication always; and trusted sibling systems hand their users over with signed tokens.
- **`navree-access`**: roles, permissions and abilities, record checks for `#[can(.., from = "id")]` routes, SQL list filters with `Accessible`, the abilities endpoint that shares the rules with front ends (in the JSON form `@casl/ability` reads), management routes and the `access:role`, `access:grant` and `access:explain` commands.
- **`navree-crypto`**: AES-256-GCM encryption with key rotation, Argon2id password hashing on a bounded blocking pool, token helpers and `key:generate`. `navree_crypto::jose` signs and verifies JSON Web Signatures (HS256, EdDSA, ES256, RS256 and their siblings) on `ring`, reads and publishes JSON Web Keys and key sets, and loads PKCS#8 keys such as Apple's `.p8` files and the public keys of X.509 certificates; it also signs and reads the HS256 tokens of `navree-auth`. `navree_crypto::totp` makes and checks time-based one-time passwords (RFC 6238, with `otpauth://` URLs) and `navree_crypto::qr` encodes QR codes (ISO/IEC 18004) as SVG, for the two-factor flows.
- **`navree-audit`**: an audit log of data changes, sign-ins, permission changes and access denials, with `audit:prune`.

### Workspaces

- **`navree-workspace`**: multi-tenancy at the workspace level, on in the default features. `WorkspaceModule`, the `CurrentWorkspace` extractor, the `Workspaces`, `Members` and `Invitations` services, the `Owner`, `Admin`, `Member` and `Viewer` roles plus your own, workspace-scoped permissions for `navree-access`, resolution from a header, a subdomain, a path prefix or a token claim, a time zone and country per workspace, isolation by row, schema or database, demo workspaces seeded from fixtures, read-only or reset every night, with an `X-Navree-Demo` header for a Live/Demo switch, and shared libraries: tables of global, organization and workspace content (`m.library::<M>()`) that each workspace reads as one list and clones to change, kept consistent by a `CHECK` constraint. See [Workspaces](/docs/workspaces/introduction/), [Demo workspaces](/docs/workspaces/demo-workspaces/) and [Shared libraries](/docs/workspaces/shared-libraries/).

### Background work

- **`navree-queue`**: database and memory job queues with workers, retries with backoff, unique and delayed jobs, failed-job storage and the `queue:work`, `queue:failed`, `queue:retry` and `queue:flush` commands. Jobs dispatched during a request are queued only if its transaction commits. [Batches](/docs/digging-deeper/batches-and-operations/) run many jobs as one with `then`, `catch` and `finally` callbacks, jobs report progress with `ctx.progress`, and operations show long work to users: `GET /api/operations/{id}`, an SSE progress stream, a private channel, cooperative cancel and a watchdog that fails or restarts stalled work.
- **`navree-events`**: a typed event bus with synchronous and queued listeners.
- **`navree-schedule`**: schedules on cron expressions in UTC, in a time zone (`in_zone`) or once per workspace at its local time (`per_workspace_local`), overlap prevention, single-node runs across servers sharing a database, and `schedule:run`, `schedule:work` and `schedule:list`.
- **`navree-time`**: time zones for users, workspaces and organizations. `CurrentZone`, local days and report windows counted in the tenant's days, send windows with weekends and public holidays, `AT TIME ZONE` with a checked zone, zone names every PostgreSQL accepts, and the public zone list at `/api/time/zones`. See [Time zones](/docs/digging-deeper/time-zones/).

### Communication

- **`navree-mail`**: mailables rendered from templates, with CSS inlined and a text body generated; SMTP (DKIM-signed), SES, Mailgun, Postmark, Resend, log, array and failover transports; queued sending. For products that send for their customers: transports per sending domain, workspace and organization, a delivery log fed by provider webhooks, automatic suppressions, mail held for approval, open and click tracking, and SPF, DKIM and DMARC checks. And for mail coming in: messages parsed with every header, body, attachment and forwarded message, routed to mailboxes by address, signed reply addresses, the raw `.eml` kept on a disk, sources for Amazon SES, Mailgun, Postmark and raw MIME, and a customer's own Microsoft 365 and Gmail mailboxes watched through their integration connection. See [Inbound mail](/docs/digging-deeper/inbound-mail/).
- **`navree-notify`**: notifications over mail, the database, broadcasts, Slack, Microsoft Teams, SMS, WhatsApp and web push, with read state. People and workspaces choose the channels of each category, mail batches into hourly, daily or weekly digests, quiet hours and send windows hold deliveries on the recipient's clock until `notify:release` sends them, and each workspace restyles its notification mail. See [Notification preferences](/docs/digging-deeper/notification-preferences/).
- **`navree-realtime`**: an in-process WebSocket server that speaks the Pusher protocol, so pusher-js and any Pusher client connects, with public, private and presence channels and a signed relay that lets workers broadcast through the serving process.
- **`navree-view`**: MiniJinja templates for mail and other text.

### Integrations and operations

- **`navree-storage`**: named disks on object_store, streaming, signed temporary URLs and upload checks.
- **`navree-http-client`**: outgoing HTTP with retries, timeouts, an SSRF policy and fakes for tests.
- **`navree-observe`**: `/health/live`, `/health/ready` with per-module checks, and Prometheus metrics at `/metrics`.

### Testing

- **`navree-testing`**: `TestApp` to boot an app or a few modules on a temporary database, an in-process `TestClient` with cookies, `acting_as`, JSON assertions and validation-error assertions, and fakes.

## The CLI

The `navree` binary (crate `navree-cli`) creates apps, generates code and runs the dev loop:

- `navree new <name>`, with `--kit` for a [starter kit](/docs/getting-started/starter-kits/), `--ui next` for a Next.js front end that keeps tokens in httpOnly cookies, and `--navree-path` to choose the Navree checkout.
- `navree make:module <name> [--crud]` and `make:<kind>` generators for controllers, services, entities, migrations, jobs, events, listeners, mail, notifications, policies, commands, AI agents and tests. Generators never overwrite files; they register what they create at marker comments.
- `navree dev`, which rebuilds and restarts the app when its code changes, and keeps the last good build serving when a build fails.
- The ecosystem's commands: `navree dock up`, `navree deploy`, `navree fleet`, `navree mcp` and `navree skills:install`.
- Every other command is forwarded to the app's binary.

## Typst templates become HTML

Before 0.1.0, `navree-documents` compiled `.typ` templates with the Typst crates. Those crates brought six dependencies that are no longer maintained (`bincode`, `paste`, `rustybuzz`, `ttf-parser`, `unsafe-libyaml` and `yaml-rust`), which the vulnerability scan reports, so the Typst engine is replaced by a native engine built on maintained crates (krilla, HarfRust, Skrifa, unicode-bidi, ICU4X). It reads the same `.html` templates as Chrome, and [Documents built in code](/docs/packages/documents/#documents-built-in-code) adds `PdfDocument`.

If your app used Typst templates:

- **Rewrite each `.typ` template as `.html`.** The render's data are template variables (`{{ name }}`, not `json("/data.json")`), `{{ locale }}` and `{{ dir }}` replace `sys.inputs`, `@page { size; margin }` sets the page, and a `<footer>` with `<span class="pageNumber">` and `<span class="totalPages">` numbers pages. [The native engine](/docs/packages/documents/#the-native-engine) lists the HTML it reads; the same file also prints in Chrome.
- **Renamed**: the crate feature `typst` is `native` (on by default), `TypstEngine` is `NativeEngine`, `TypstOptions` is `NativeOptions`, `EngineKind::Typst` is `EngineKind::Native`, and the `documents.typst` section is `documents.native` (`bundled_fonts`, `font_dirs` and `timeout_secs` keep their names; `print` is new). `engine = "native"` and `documents:render --engine native` name the engine; `typst` is refused with a message that says so.
- **Removed**: `Render::typst`, `TemplateSource::Typst`, `TYPST_EXTENSION` and `documents.typst.packages_dir`.
- **Changed**: `Render::html(..)` no longer sends a render to Chrome by itself. `documents.engine` decides, `native` by default; set it to `chrome`, or call `.engine(EngineKind::Chrome)` on the render, to keep printing with Chrome.
- **Added**: Noto Serif, Noto Sans Mono and Noto Sans Hebrew join the bundled fonts, in both engines.

## Design decisions

- **Token authentication for APIs.** `navree-auth` issues stateless JWT access tokens and rotating refresh tokens, and a backend-for-frontend keeps them in httpOnly cookies for browsers. Cookie sessions with CSRF protection are a separate module, [Sessions and CSRF](/docs/basics/sessions-and-csrf/), for apps that want them.
- **One error shape.** Every error is JSON in Navree's shape, `{ "statusCode", "message", "error", "code" }`, with `errors` for validation failures. The `code` is machine-readable and stable (`not_found`, `invalid_credentials`), so front ends show every refusal in the user's language. Input errors are 400s and CSRF failures are 403s.
- **Real time is built in.** Navree ships an in-process Pusher-protocol server. Processes that don't serve the sockets send their broadcasts to the one that does over a signed HTTP relay.
- **The framework's own crates don't use the macros.** They implement `Module`, `Injectable` and `Controller` by hand, the escape hatch every app can use too. Apps use the macros.
