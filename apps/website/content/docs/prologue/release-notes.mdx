## Navree 0.1.0

0.1.0 is Navree's first release. It ships the framework (the kernel, the shared contracts, the module crates, the `navree` facade that re-exports them, the attribute macros and the `navree` CLI) together with the first-party ecosystem: tools for monitoring, debugging, queues, administration, deployment and local services, and packages for search, AI, microservices, OAuth, billing and more. Everything shares one version number, is open source under MIT or Apache-2.0 and is free to self-host.

<Callout type="note" title="Installing from Git">

Install the CLI from the Git repository, and let new apps depend on the repository or a local checkout; [Installation](/docs/getting-started/installation/) shows how.

</Callout>

## The framework

### Foundation

- **`navree-kernel`**: the module graph, a type-keyed dependency-injection container with singleton, request and transient scopes, lifecycle hooks, graceful shutdown and the command runner behind `serve`, `migrate` and every other command. The graph is validated before anything is constructed, and `check --graph` prints it.
- **`navree-macros`**: `#[module]`, `#[injectable]`, `#[controller]`, the route attributes (`#[get]`, `#[post]`, `#[put]`, `#[patch]`, `#[delete]`) and the helper attributes for access, throttling, timeouts, transactions, audit actions and OpenAPI metadata. A route without an access declaration doesn't compile.
- **`navree-contracts`**: the small shared traits and types that let modules cooperate without depending on each other: `Secret<T>`, `RequestId`, `Principal`, jobs and dispatchers, sinks for audit and events, `Broadcaster` and `Clock`.
- **`navree-config`**: typed configuration from `.env`, TOML files and `APP_*` environment variables, validated at boot, with secrets redacted in logs and errors.
- **`navree-log`**: a tracing subscriber with pretty or JSON output, field redaction, per-target levels and rotating log files.

### HTTP

- **`navree-http`**: Axum integration with a default pipeline (request ids, client IP resolution through trusted proxies, panic catching, timeouts, security headers, compression, a per-IP rate limit, body limits, maintenance mode), controllers, deny-by-default route access, per-route throttles, signed URLs, CORS and one JSON error shape for every error (`{ "statusCode", "message", "error", "code" }`, validation failures as 400 with `errors`), whose stable `code` a front end translates.
- **`navree-validation`**: `Valid<Json<T>>`, `Valid<Query<T>>` and friends on garde, with one readable message per broken rule and async `unique` and `exists` rules. International input: phone numbers in E.164 with a per-request default region, rich text sanitized by a configurable policy, names and digits in any script, ISO 3166-1 countries and BCP 47 locales.
- **`navree-api`**: an OpenAPI 3.1 document built from route metadata at `/api/openapi.json`, a docs UI at `/api/docs`, `openapi:export`, and API resource helpers.
- **`navree-session`**: encrypted session cookies with memory and database stores, and CSRF protection for single-page apps that use cookies.

### Data

- **`navree-db`**: SeaORM integration with a unit of work per request (a transaction that commits when the response succeeds), `Repo` with change events, per-module migration sets, seeders, model factories, pagination and the `migrate`, `migrate:rollback`, `migrate:fresh`, `migrate:status` and `db:seed` commands. TimescaleDB is the default database (`navree new` sets it up and Dock runs it), with hypertables for Navree's own time-series tables and chunk-dropping pruning (`prune_time_series`); plain PostgreSQL with the same `postgres` feature, MySQL and MariaDB with `mysql`, and SQLite built in.
- **`navree-orm`**: the [ORM](/docs/orm/getting-started/). Models are structs with `#[derive(Model)]` and typed column constants; a query builder with joins, subqueries, unions, aggregates, JSON and full-text conditions, row locks and bulk writes; records with dirty tracking; relationships of every kind with batched eager loading and lazy-loading prevention; casts, accessors and serialization; model events, observers and broadcasts; global and local scopes, soft deletes and pruning; offset and cursor pagination, chunks and streams; factories with fake data; `#[navree::test]` databases with templates and assertions; route model binding; and workspace and access-control scoping. It runs in the unit of work on PostgreSQL with TimescaleDB, MySQL and MariaDB, SQLite and, with `navree-mongo`, MongoDB.
- **`navree-schema`**: the [schema builder](/docs/database/schema-builder/) migrations are written with: tables, columns, indexes and foreign keys in Rust, written as each database's SQL, SQLite table rebuilds, TimescaleDB hypertables, reading the live schema, and [schema dumps](/docs/database/squashing-migrations/) that replace a long migration history.
- **`navree-cache`**: a memory cache store on moka with `remember`, tags, stale-while-revalidate and atomic locks.

### Security

- **`navree-auth`**: 15-minute JWT access tokens and 30-day rotating refresh tokens with reuse detection, pluggable authentication strategies, `CurrentUser`, registration, password change and reset, email verification, TOTP two-factor authentication with recovery codes and a policy that requires it per role or per workspace, and login throttling. Users list and end their sessions; `#[recent_auth]` asks for the password or a code again before sensitive actions; support staff impersonate users behind `#[not_while_impersonating]` guards, with the impersonator on every audit entry; magic links, emailed sign-in codes and passkeys (ES256 and Ed25519) sign users in without a password; platform administrators sign in apart with two-factor authentication always; and trusted sibling systems hand their users over with signed tokens.
- **`navree-access`**: roles, permissions and abilities, record checks for `#[can(.., from = "id")]` routes, SQL list filters with `Accessible`, the abilities endpoint that shares the rules with front ends (in the JSON form `@casl/ability` reads), management routes and the `access:role`, `access:grant` and `access:explain` commands.
- **`navree-crypto`**: AES-256-GCM encryption with key rotation, Argon2id password hashing on a bounded blocking pool, token helpers and `key:generate`. `navree_crypto::jose` signs and verifies JSON Web Signatures (HS256, EdDSA, ES256, RS256 and their siblings) on `ring`, reads and publishes JSON Web Keys and key sets, and loads PKCS#8 keys such as Apple's `.p8` files and the public keys of X.509 certificates.
- **`navree-audit`**: an audit log of data changes, sign-ins, permission changes and access denials, with `audit:prune`.

### Workspaces

- **`navree-workspace`**: multi-tenancy at the workspace level, on in the default features. `WorkspaceModule`, the `CurrentWorkspace` extractor, the `Workspaces`, `Members` and `Invitations` services, the `Owner`, `Admin`, `Member` and `Viewer` roles plus your own, workspace-scoped permissions for `navree-access`, resolution from a header, a subdomain, a path prefix or a token claim, a time zone and country per workspace, isolation by row, schema or database, and demo workspaces seeded from fixtures, read-only or reset every night, with an `X-Navree-Demo` header for a Live/Demo switch. See [Workspaces](/docs/workspaces/introduction/) and [Demo workspaces](/docs/workspaces/demo-workspaces/).

### Background work

- **`navree-queue`**: database and memory job queues with workers, retries with backoff, unique and delayed jobs, failed-job storage and the `queue:work`, `queue:failed`, `queue:retry` and `queue:flush` commands. Jobs dispatched during a request are queued only if its transaction commits. [Batches](/docs/digging-deeper/batches-and-operations/) run many jobs as one with `then`, `catch` and `finally` callbacks, jobs report progress with `ctx.progress`, and operations show long work to users: `GET /api/operations/{id}`, an SSE progress stream, a private channel, cooperative cancel and a watchdog that fails or restarts stalled work.
- **`navree-events`**: a typed event bus with synchronous and queued listeners.
- **`navree-schedule`**: schedules on cron expressions in UTC, in a time zone (`in_zone`) or once per workspace at its local time (`per_workspace_local`), overlap prevention, single-node runs across servers sharing a database, and `schedule:run`, `schedule:work` and `schedule:list`.
- **`navree-time`**: time zones for users, workspaces and organizations. `CurrentZone`, local days and report windows counted in the tenant's days, send windows with weekends and public holidays, `AT TIME ZONE` with a checked zone, zone names every PostgreSQL accepts, and the public zone list at `/api/time/zones`. See [Time zones](/docs/digging-deeper/time-zones/).

### Communication

- **`navree-mail`**: mailables rendered from templates, with CSS inlined and a text body generated; SMTP (DKIM-signed), SES, Mailgun, Postmark, Resend, log, array and failover transports; queued sending. For products that send for their customers: transports per sending domain, workspace and organization, a delivery log fed by provider webhooks, automatic suppressions, mail held for approval, open and click tracking, and SPF, DKIM and DMARC checks.
- **`navree-notify`**: notifications over mail, the database and broadcasts, with read state.
- **`navree-realtime`**: an in-process WebSocket server that speaks the Pusher protocol, so pusher-js and any Pusher client connects, with public, private and presence channels and a signed relay that lets workers broadcast through the serving process.
- **`navree-view`**: MiniJinja templates for mail and other text.

### Integrations and operations

- **`navree-storage`**: named disks on object_store, streaming, signed temporary URLs and upload checks.
- **`navree-http-client`**: outgoing HTTP with retries, timeouts, an SSRF policy and fakes for tests.
- **`navree-observe`**: `/health/live`, `/health/ready` with per-module checks, and Prometheus metrics at `/metrics`.

### Testing

- **`navree-testing`**: `TestApp` to boot an app or a few modules on a temporary database, an in-process `TestClient` with cookies, `acting_as`, JSON assertions and validation-error assertions, and fakes.

## The ecosystem

### Tools

- **[Lighthouse](/docs/tools/lighthouse/)** (`navree-lighthouse`): application monitoring inside your app, with a dashboard at `/_lighthouse`. Exceptions grouped by fingerprint, slow requests and queries, failed jobs, sampled traces, alerts to email, Slack and signed webhooks through the queue, a JSON API so scripts can read and resolve issues, and MCP tools, an issue resource and a fix-this-issue prompt for agents (with the `mcp` feature).
- **[Logbook](/docs/tools/logbook/)** (`navree-logbook`): a local debugging timeline at `/_logbook` of every request, query, job, mail, event, cache call and log line, with filters and request replay. Development only.
- **[Fleet](/docs/tools/fleet/)** (`navree-fleet`): a queue dashboard at `/_fleet` and a worker supervisor (`navree fleet`) with auto-balanced workers per queue, throughput, wait and runtime metrics, retries for failed jobs, pause and continue, and long-wait alerts.
- **[Helm](/docs/tools/helm/)** (`navree-helm`): an admin panel at `/admin` generated from your entities, with fields, filters, actions and metrics per resource (`navree make:resource`). It respects your access rules.
- **[Harbor](/docs/tools/harbor/)**: server provisioning and zero-downtime deployments from the CLI (`navree harbor:provision`, `navree deploy`, `navree deploy:rollback`), configured in `harbor.toml`, with health-checked atomic releases, encrypted secrets, several servers and roles, container images and push-to-deploy from GitHub Actions.
- **[Dock](/docs/tools/dock/)**: local services for development. `navree dock up` starts TimescaleDB (or plain PostgreSQL), Redis, Meilisearch, Mailpit, MinIO and NATS in Docker or Podman, configured in `dock.toml`.
- **[Navigator](/docs/ai/navigator/)**: the MCP server for your coding agent (`navree mcp`). It lists routes, the module graph and providers, the database schema, recent logs and the last error, runs read-only SQL and searches the docs for your version.

### Packages

- **[Search](/docs/packages/search/)** (`navree-search`): full-text and vector search over your entities with `#[derive(Searchable)]`, on PostgreSQL full text, Meilisearch, Typesense or embedded Tantivy, with vectors in pgvector or Qdrant and indexes kept in sync through the queue.
- **[AI SDK](/docs/ai/ai-sdk/)** (`navree-ai`): text, structured output, streaming, [agents with tools](/docs/ai/agents-and-tools/), [embeddings and RAG](/docs/ai/embeddings-and-rag/), with provider failover across Anthropic, OpenAI, Google Gemini, Mistral, Ollama and AWS Bedrock, and `AiFake` for tests.
- **[MCP servers](/docs/ai/mcp-servers/)** (`navree-mcp`, feature `mcp`): expose your app's tools, resources and prompts to AI clients with `#[mcp_server]`, over streamable HTTP at `/mcp` or stdio (`mcp:serve --user`), authenticated by your app's bearer tokens or OAuth (RFC 9728 metadata), with per-tool permissions, filtered lists, `McpTestClient` and `navree make:mcp`. Built on the official Rust MCP SDK.
- **[Microservices](/docs/microservices/introduction/)** (`navree-micro`): request-response and events between services over TCP, NATS, Kafka, RabbitMQ, Redis Streams and MQTT, and hybrid apps that serve HTTP and messages from one binary.
- **[gRPC](/docs/microservices/grpc/)** (`navree-grpc`) and **[GraphQL](/docs/microservices/graphql/)** (`navree-graphql`): gRPC, gRPC-Web and Connect services on tonic, and GraphQL on async-graphql with dataloaders and subscriptions, both sharing your modules, guards and access rules.
- **[OAuth server](/docs/packages/oauth-server/)** (`navree-oauth`): OAuth 2.1 and OpenID Connect for third-party apps, with PKCE, client credentials, device codes, scopes and consent, and personal access tokens.
- **[Social sign-in](/docs/packages/social-sign-in/)** (`navree-social`): sign-in with Google, GitHub, Apple, Microsoft, GitLab, Slack, LinkedIn, Discord, X and any OpenID Connect provider, linked to Navree users and ending with normal Navree tokens.
- **[Single sign-on](/docs/security/single-sign-on/)** (`navree-sso`): SAML 2.0 and OpenID Connect sign-in per organization or workspace, verified email domains that route sign-in and can refuse passwords, and just-in-time provisioning with group to role mapping. SAML signatures are verified in Rust (exclusive canonicalization, RSA-SHA256 and ECDSA on `ring`; SHA-1 refused), with `SsoFake` for tests.
- **[Billing](/docs/packages/billing/)** (`navree-billing`): subscriptions, trials, usage metering and invoices with Stripe or Paddle, for users or workspaces.
- **[Redis](/docs/digging-deeper/redis/)** (`navree-redis`, feature `redis`): one set of reconnecting Redis connections for the app, and Redis drivers so every process shares the cache and locks, the queue, sessions, named rate limits and WebSocket broadcasts and presence (`cache.store`, `queue.driver`, `session.store` and `realtime.backplane` set to `redis`).
- **[MongoDB](/docs/orm/mongodb/)** (`navree-mongo`, feature `mongo`): `MongoModule` with pooled connections and a readiness check, the ORM's document driver (models, queries, aggregation pipelines, relations, sessions and transactions), the schema builder on collections (validators, indexes, time-series collections) and migrations.
- **[Feature flags](/docs/packages/feature-flags/)** (`navree-flags`): roll features out per user, workspace or percentage, stored in your database.
- **[Webhooks](/docs/packages/webhooks/)** (`navree-webhooks`): signed outgoing webhooks with queue-backed retries and a delivery log, and verified incoming ones from Stripe, GitHub, Paddle, AWS SNS, Google Pub/Sub, Microsoft Graph, Twilio, Slack, Mailgun, Postmark and Standard Webhooks senders, with their handshakes answered.
- **[Integrations](/docs/packages/integrations/)** (`navree-integrations`): each workspace or organization connects its own Microsoft 365 (admin consent and app-only tokens), Google Workspace (service-account keys with domain-wide delegation), Slack, OAuth 2.0 APIs and API keys; credentials encrypted with the application key, tokens refreshed once under a lock, least-privilege scope sets per feature, scheduled health checks that emit `ConnectionUnhealthy`, and typed clients such as `Connection<MicrosoftGraph>`.
- **[Documents](/docs/packages/documents/)** (`navree-documents`): PDF from HTML templates or documents built in code, laid out in process by the native engine (HarfRust shaping, bidirectional text, tables whose headers repeat, page-numbered headers and footers, tagged PDF, bundled Noto fonts for Latin, Arabic, Hebrew and Devanagari) or printed by headless Chrome, DOCX, merge, stamps and overlays, and queued renders to a storage disk, behind an operation your users follow when you want one. See [Typst templates become HTML](#typst-templates-become-html).
- **[Imports and exports](/docs/packages/imports-and-exports/)** (`navree-sheets`): CSV with a byte-order mark and formula escaping and XLSX with typed cells from `#[derive(Exportable)]` rows, streamed or queued to a disk with a signed link; imports that detect the encoding (UTF-16, Windows-1256 and the rest), read CSV, XLSX, XLS and ODS, map headers automatically or from saved mappings, validate every row with garde, stage the rows for a preview and apply them in queue batches with duplicates skipped, updated or refused, and write an error file.
- **[Workflows](/docs/packages/workflows/)** (`navree-workflows`): durable workflows as `#[workflow]` async functions, whose steps are stored and replayed on resume, with retries, sleeps of minutes or months, event waits with timeouts, versions, cancellation and leases that survive crashes; and **[automations](/docs/packages/automations/)** people build in your app from `#[trigger]`, `#[condition]` and `#[action]` blocks, with JSON Schemas for the editor, versioned definitions per workspace, enrollment policies, waits, simulation and templates.
- **[Localization](/docs/packages/localization/)** (`navree-i18n`): Fluent translations, plurals, locale negotiation and translated validation messages.
- **[Browser testing](/docs/packages/browser-testing/)** (`navree-browser`): drive a real browser from your tests over the Chrome DevTools Protocol.
- **[Starter kits](/docs/getting-started/starter-kits/)**: `navree new <name> --kit saas`, `--kit api` or `--kit micro`. The SaaS kit has a Next.js and shadcn/ui front end with sign-in, workspaces, billing, settings and admin.

### AI-native

## The CLI

The `navree` binary (crate `navree-cli`) creates apps, generates code and runs the dev loop:

- `navree new <name>`, with `--kit` for a [starter kit](/docs/getting-started/starter-kits/), `--ui next` for a Next.js front end that keeps tokens in httpOnly cookies, and `--navree-path` to choose the Navree checkout.
- `navree make:module <name> [--crud]` and `make:<kind>` generators for controllers, services, entities, migrations, jobs, events, listeners, mail, notifications, policies, commands, AI agents and tests. Generators never overwrite files; they register what they create at marker comments.
- `navree dev`, which rebuilds and restarts the app when its code changes, and keeps the last good build serving when a build fails.
- The ecosystem's commands: `navree dock up`, `navree deploy`, `navree fleet`, `navree mcp` and `navree skills:install`.
- Every other command is forwarded to the app's binary.

## The reference CRM

`apps/crm-api` is a CRM API built on Navree: companies, contacts, a deals pipeline, activities, a dashboard, users and roles, with live updates over WebSockets, queued notifications, scheduled reminders and an audit log. `apps/crm-web` is its Next.js front end, whose server holds the tokens for the browser. Unit, feature and Playwright end-to-end tests cover both. The [CRM tour](/docs/example-app/crm-tour/) walks through it.

## Performance

A Navree app is one binary that needs a few megabytes at idle and starts in milliseconds. [Performance](/performance/) has Navree's measurements, the workload behind them, the method and how to reproduce them on your own machine.

## Typst templates become HTML

Before this release, `navree-documents` compiled `.typ` templates with the Typst crates. Those crates brought six dependencies that are no longer maintained (`bincode`, `paste`, `rustybuzz`, `ttf-parser`, `unsafe-libyaml` and `yaml-rust`), which the vulnerability scan reports, so the Typst engine is replaced by a native engine built on maintained crates (krilla, HarfRust, Skrifa, unicode-bidi, ICU4X). It reads the same `.html` templates as Chrome, and [Documents built in code](/docs/packages/documents/#documents-built-in-code) adds `PdfDocument`.

If your app used Typst templates:

- **Rewrite each `.typ` template as `.html`.** The render's data are template variables (`{{ name }}`, not `json("/data.json")`), `{{ locale }}` and `{{ dir }}` replace `sys.inputs`, `@page { size; margin }` sets the page, and a `<footer>` with `<span class="pageNumber">` and `<span class="totalPages">` numbers pages. [The native engine](/docs/packages/documents/#the-native-engine) lists the HTML it reads; the same file also prints in Chrome.
- **Renamed**: the crate feature `typst` is `native` (on by default), `TypstEngine` is `NativeEngine`, `TypstOptions` is `NativeOptions`, `EngineKind::Typst` is `EngineKind::Native`, and the `documents.typst` section is `documents.native` (`bundled_fonts`, `font_dirs` and `timeout_secs` keep their names; `print` is new). `engine = "native"` and `documents:render --engine native` name the engine; `typst` is refused with a message that says so.
- **Removed**: `Render::typst`, `TemplateSource::Typst`, `TYPST_EXTENSION` and `documents.typst.packages_dir`.
- **Changed**: `Render::html(..)` no longer sends a render to Chrome by itself. `documents.engine` decides, `native` by default; set it to `chrome`, or call `.engine(EngineKind::Chrome)` on the render, to keep printing with Chrome.
- **Added**: Noto Serif, Noto Sans Mono and Noto Sans Hebrew join the bundled fonts, in both engines.

## Design decisions

- **Token authentication for APIs.** `navree-auth` issues stateless JWT access tokens and rotating refresh tokens, and a backend-for-frontend keeps them in httpOnly cookies for browsers. Cookie sessions with CSRF protection are a separate module, [Sessions and CSRF](/docs/basics/sessions-and-csrf/), for apps that want them.
- **One error shape.** Every error is JSON in Navree's shape, `{ "statusCode", "message", "error", "code" }`, with `errors` for validation failures. The `code` is machine-readable and stable (`not_found`, `invalid_credentials`), so front ends show every refusal in the user's language. Input errors are 400s and CSRF failures are 403s.
- **Real time is built in.** Navree ships an in-process Pusher-protocol server. Processes that don't serve the sockets send their broadcasts to the one that does over a signed HTTP relay.
- **The framework's own crates don't use the macros.** They implement `Module`, `Injectable` and `Controller` by hand, the escape hatch every app can use too. Apps use the macros.
