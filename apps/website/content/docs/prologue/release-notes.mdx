## Navree 1.0.0

Navree 1.0.0 is Navree's first release. It ships the framework (the kernel, the shared contracts, the module crates, the `navree` facade that re-exports them, the attribute macros and the `navree` CLI) with [Navree UI](#navree-ui), a toolkit for drawing an app's screens in Rust, and the first-party ecosystem: tools for monitoring, debugging, queues, administration, deployment and local services, packages for search, AI, microservices, OAuth, billing and more, and [agent skills](#ai-native) for your coding agent, two of which bring an existing product or design into Navree. Everything shares one version number: the crates, the `navree` CLI, the starter kits and the `@navree/*` npm packages are all 1.0.0. Navree is open source under MIT or Apache-2.0 and free to self-host, and from 1.0 it follows semantic versioning (see the [roadmap](/docs/prologue/roadmap/)).

<Callout type="note" title="Installing from Git">

Install the CLI from the Git repository, and let new apps depend on the repository or a local checkout; [Installation](/docs/getting-started/installation/) shows how.

</Callout>

The sections below list what Navree includes. They describe the code of this release.

## Connection limits

The `serve` command runs on `navree::http::serve`, which bounds what a client can hold (slow headers, slow bodies, idle connections, responses it stops reading, unanswered HTTP/2 pings, the number of connections in all and per address) with the safe defaults of [`http.server`](/docs/getting-started/deployment/#connection-limits). A full server closes its longest-idle connection for a client that's waiting and has sent something. Behind a reverse proxy, list it in `http.trusted_proxies`, or its connections count against `http.server.max_connections_per_ip` (256). WebSockets are bounded only if you set `http.server.upgraded_idle_timeout_ms`. A request head over 32 KiB or with over 100 headers is a 431, and the peer's address is `navree::http::serve::ConnectInfo`. A gRPC client's `grpc-timeout` can shorten `grpc.timeout_secs` but not extend it, so raise that key if a method needs longer than the default of `http.timeout_secs`.

## The framework

### Foundation

- **`navree-kernel`**: the module graph, a type-keyed dependency-injection container with singleton, request and transient scopes, lifecycle hooks, graceful shutdown and the command runner behind `serve`, `migrate` and every other command. The graph is validated before anything is constructed, and `check --graph` prints it.
- **`navree-macros`**: `#[module]`, `#[injectable]`, `#[controller]`, the route attributes (`#[get]`, `#[post]`, `#[put]`, `#[patch]`, `#[delete]`) and the helper attributes for access, throttling, timeouts, transactions, audit actions and OpenAPI metadata. A route without an access declaration doesn't compile.
- **`navree-contracts`**: the small shared traits and types that let modules cooperate without depending on each other: `Secret<T>`, `RequestId`, `Principal`, jobs and dispatchers, sinks for audit and events, `Broadcaster` and `Clock`.
- **`navree-config`**: typed configuration from `.env`, TOML and JSON files and `APP_*` environment variables, validated at boot, with secrets redacted in logs and errors. The loader is Navree's own, with limits on file size and nesting.
- **`navree-glob`**: the matcher behind every glob pattern you configure as a string: the hosts `http_client.ssrf.allow_hosts` lets through, the routes `logbook.ignore.routes` leaves out and `session.csrf_except` exempts, the stubs of the fake HTTP client and the URLs a browser test waits for. `*` matches any run of characters (`/` and `.` included) and `?` matches one; every other character, brackets and braces too, matches itself, and the whole input has to match. A pattern is matched in at most its length times the input's length steps, however many `*` it has.
- **`navree-log`**: a tracing subscriber with pretty or JSON output, field redaction, per-target levels and rotating log files.

### HTTP

- **`navree-http`**: the HTTP module, with a default pipeline (request ids, client IP resolution through trusted proxies, panic catching, timeouts, security headers, compression, a per-IP rate limit, body limits, maintenance mode), controllers, deny-by-default route access, per-route throttles, signed URLs, CORS and one JSON error shape for every error (`{ "statusCode", "message", "error", "code" }`, validation failures as 400 with `errors`), whose stable `code` a front end translates. Responses are compressed with gzip (`http.compression`) by Navree's own `CompressionLayer` on flate2, which streams: what a handler has sent is flushed to the client whenever its body waits. A client that accepts only `br` gets an uncompressed response. A route opts out with `no_compression()` (`#[no_compression]`) and a response with `Cache-Control: no-transform`, for a page with a secret and reflected input in one body (BREACH; see [Compression and secrets](/docs/basics/responses/#compression-and-secrets-breach)); a strong `ETag` becomes a weak one on a compressed response, a 206 is never compressed, a `HEAD` response has the headers its `GET` response has, and a 304 carries `Vary: accept-encoding` like the 200 it stands in for. The per-IP limit and the login, social and OAuth throttles count an IPv6 client as its network (`http.rate_limit_ipv6_prefix`, default 64), so one host can't dodge a limit by changing addresses within its prefix, and `X-Forwarded-For` entries may carry a port. The CORS layer is Navree's own and serves the HTTP pipeline and the gRPC edge: origins match byte for byte, `*` is never sent, a request with two `Origin` headers is refused and, on the gRPC edge, preflights never reach the service.
- **Routing**: `navree-http` routes requests itself. The router matches the path as the client sent it, segment by segment, and never rewrites it: static segments before parameters before catch-alls, percent-decoded parameter values (`+` stays `+`), `HEAD`, `OPTIONS` and 405 with `Allow`, and boot-time checks for conflicting routes. A path it can't route unambiguously is a 400 before any guard or handler runs: a `.` or `..` segment (raw or percent-encoded), a backslash, `%2F`, `%5C` or `%00` in the value of a `{name}` parameter, and a value that isn't UTF-8 once decoded. An empty segment doesn't match a parameter, so `/deals//move` and a trailing slash are a 404 for `/deals/{id}/move` and `/deals/{id}`. A parameter is a whole segment: `#[get("/v{n}")]` and `#[get("/{name}.json")]` are compile errors, so capture the segment and parse it in the handler. Routes that differ only in parameter names (`/deals/{id}` and `/deals/{deal}` for one method) fail the boot, and `HttpModule` lists every such conflict in the boot error. `OPTIONS` on a known path answers 204 with an `Allow` header without running a route, unless a route handles `OPTIONS` itself; CORS preflights are answered by the CORS layer first.
- **Extractors**: handlers are async functions whose arguments are extractors, and `RouteDef::on(method, path, handler)` takes such a handler. `Path`, `Query`, `RawQuery`, `Form`, `Json`, `Multipart`, `WebSocketUpgrade`, `Extension`, `Scoped`, `ClientIp` and `CurrentPrincipal` are Navree's own, with body limits, limits on every part of a form and on WebSocket frames, an urlencoded parser and media-type parsing, and rejections that render in the JSON error format. `HeaderMap`, `Method`, `Uri`, `Version`, `Extensions`, `Bytes`, `String` and `Request` are extractors too, and `PathParams` (`navree::http::PathParams`) gives all the decoded path parameters. `Form` reads `application/x-www-form-urlencoded` only (parameters allowed) and answers 415 for anything else; `Json` reads `application/json` and `+json` types; a request with two `Content-Type` headers is a 415 for both. A hand-written extractor implements `navree::http::extract::FromRequestParts`, or `FromRequest` for one that reads the body. `IntoResponse`, `IntoResponseParts`, `Response`, `Html`, `Redirect`, `AppendHeaders` and the server-sent events types are in `navree::http::response`, `Body` and `to_bytes` in `navree::http::body`, and `from_fn`, `from_fn_with_state`, `Next` and `State` in `navree::http::middleware`. `HeaderMap`, `Method`, `Uri`, `Version` and `StatusCode` come from the `http` crate, which your app adds to its dependencies. `build_router` returns an `AppRouter`, which is what a `GlobalLayer` wraps; it is a Tower service, so `tower::ServiceExt::oneshot` calls it in a test.
- **Multipart forms**: `navree::http::extract::Multipart`, with `Field` and `MultipartError` beside it, on Navree's own streaming `multipart/form-data` parser (RFC 2046, RFC 7578): values reach the handler as they arrive, `Content-Disposition` is read parameter by parameter after the type `form-data`, and `filename*` (RFC 8187) gives the file name when it decodes, alone or with an equal `filename`. A form may have 1,000 parts, a part without a file name 1 MiB and a part's headers 16 KiB (413 past them; `http.multipart`, or `form.with_limits(..)` in a handler), and a file answers to the route's body limit. `field.text()` keeps to the 1 MiB whatever the part calls itself. A form with a boundary over 70 characters, two boundaries or two `Content-Type` headers is a 400, and so is a part with two `Content-Disposition` or `Content-Type` headers, a parameter given twice, or a head or `Content-Disposition` that two readers could take differently (a type other than `form-data`, a `filename` and a `filename*` that differ, a name that ends in a backslash; a delimiter counts only at the start of the body or of a line); a body that's too slow is a 408. See [Multipart forms](/docs/basics/requests/#multipart-forms).
- **WebSockets**: `WebSocketUpgrade`, `WebSocket`, `Message`, `CloseFrame` and `Utf8Bytes` are in `navree::http::ws`, and a socket's errors are `WebSocketError`. A client's frame and message are limited to 1 MiB each (`max_frame_size` and `max_message_size` raise them). The handshake is strict: `Sec-WebSocket-Key` must be one base64 value of 16 bytes, `Sec-WebSocket-Version` one header saying `13` (a wrong version's 400 names `Sec-WebSocket-Version: 13`), `Connection` and `Upgrade` are read as lists of tokens (so `Connection: not-upgrade` fails and `keep-alive` and `Upgrade` on two lines passes), and an HTTP/1.0 request can't upgrade. See [WebSockets](/docs/basics/requests/#websockets).
- **`navree-validation`**: `#[derive(Validate)]` rules with `Valid<Json<T>>`, `Valid<Query<T>>` and friends, with one readable message per broken rule and async `unique` and `exists` rules. International input: phone numbers in E.164 with a per-request default region (a number with more than 15 digits is refused), rich text sanitized by a configurable policy (Navree's own sanitizer on html5ever, which parses its output again and returns it only when a browser would build the tree it checked), names and digits in any script, ISO 3166-1 countries and BCP 47 locales. The derive and its `#[validate(...)]` field rules are Navree's own, in the `navree-validation-macros` crate and the rule runtime of `navree-validation`. Every field states its rules or `#[validate(skip)]`, so a field added later can't go unchecked: a field with neither is a compile error (`#[validate(skip_unmarked)]` on the type opts out). The rules are `required`, `length`, `range`, `email`, `url`, `ip`, `ipv4`, `ipv6`, `ascii`, `alphanumeric`, `credit_card`, `contains`, `starts_with`, `ends_with`, `pattern` (checked at compile time), `same_as`, `custom`, `nested`, `each(...)` and `rename`. `length` counts characters; `length(bytes, ...)` counts bytes. A rule given twice on a field (only `custom` may repeat), `length()` or `range()` with no bound, a literal `min` above `max`, `same_as` naming no field, and `skip` combined with other rules are compile errors. A custom rule is a function of the value alone, returning `Result<(), E>` with `E: Into<Violation>` (a `Violation`, a `String` and a `&str` all qualify); rules that need request data read it from the `InputContext`, and rules that query the database are async rules. The email (RFC 5321) and URL (RFC 3986) parsers are Navree's own, with property tests and a libFuzzer target: `email` accepts an ASCII dot-atom address of at most 254 bytes with a local part of at most 64, and a host name or an address literal, with punycode for internationalized domains; `url` accepts ASCII absolute URLs and requires a host for `http`, `https`, `ws`, `wss` and `ftp`. A failure is a `Violation`: a rule key and parameters, or a text, at a dotted path that follows serde's `rename` and `rename_all` (`#[validate(rename = "...")]` overrides the name), so a DTO with `#[serde(rename_all = "camelCase")]` reports `firstName`. `length` on a collection reports the `elements` message (`tags must contain at least 1 elements`), also when the input came from a query string. `Violations` displays one message per line with the field paths. The [400 response](/docs/basics/validation/#error-responses) has the JSON error format. `navree-validation` has an optional `time` feature that implements `Validate` for the zones, days and day ranges of `navree-time`.
- **`navree-openapi`**: the OpenAPI 3.1 document model and `#[derive(ToSchema)]`, which reads serde's attributes.
- **`navree-api`**: an OpenAPI 3.1 document built from route metadata at `/api/openapi.json`, an API reference page at `/api/docs` that loads nothing from a third party, `openapi:export`, and API resource helpers.
- **`navree-session`**: encrypted session cookies with memory and database stores, and CSRF protection for single-page apps that use cookies.

### Data

- **`navree-db`**: a database engine on sqlx: pools that honor every `database.*` setting, statements, rows, errors classified the same way on every database (`DbError` with an `ErrorKind`), transactions with savepoints, and the `Executor` that pools, transactions, units of work and `Db` share. A unit of work per request (a transaction that commits when the response succeeds) always runs on `navree-db`'s own transaction and records change events. It also has per-module migration sets, seeders, pagination and the `migrate`, `migrate:rollback`, `migrate:fresh`, `migrate:status` and `db:seed` commands. TimescaleDB is the default database (`navree new` sets it up and Dock runs it), with hypertables for Navree's own time-series tables and chunk-dropping pruning (`prune_time_series`); plain PostgreSQL with the same `postgres` feature, MySQL and MariaDB with `mysql`, and SQLite with `sqlite`. Statements are correct on PostgreSQL and MySQL when a placeholder's value type differs between runs, and SQLite migrations begin `IMMEDIATE`, so they queue for the write lock rather than failing with "database is locked".
- **SQLite is opt-in.** It is the `sqlite` Cargo feature of `navree` (and of `navree-db`), off by default like `postgres` and `mysql`, so a PostgreSQL or MySQL build compiles no SQLite C code: the bundled SQLite library is most of the C in a build, and `cargo tree -i libsqlite3-sys` finds nothing without the feature. `navree new` writes the driver feature you chose, and `sqlite` in `[dev-dependencies]`, because tests run on SQLite files (`TestApp`'s `temp_database()` and `memory_database()`, and the default of `#[navree::test]`). With `database.url` left out the database is `sqlite://storage/app.db?mode=rwc`, so an app built without the feature stops at boot with "enable the `sqlite` feature of navree-db". Logbook's `file` store is a SQLite file of its own, so it needs the feature too (`navree`'s `sqlite`, or `navree-logbook`'s): without it `logbook.store` defaults to `memory`, and `logbook.store = "file"` fails at boot. An app that uses `micro` with `DatabaseModule` enables a driver feature (`postgres`, `mysql` or `sqlite`); the `micro` feature turns on `db` but no driver.
- **`navree-orm`**: the [ORM](/docs/orm/getting-started/). Models are structs with `#[derive(Model)]` and typed column constants; a query builder with joins, subqueries, unions, aggregates, JSON and full-text conditions, row locks and bulk writes; records with dirty tracking; relationships of every kind with batched eager loading and lazy-loading prevention; casts, accessors and serialization; model events, observers and broadcasts; global and local scopes, soft deletes and pruning; offset and cursor pagination, chunks and streams; factories with fake data; `#[navree::test]` databases with templates and assertions; route model binding; and workspace and access-control scoping. It writes its own SQL and runs it through `navree-db` in the unit of work on PostgreSQL with TimescaleDB, MySQL and MariaDB, SQLite and, with `navree-mongo`, MongoDB. Queries made through models return `OrmError` (`db_error()` gives the `DbError` inside), and `navree_orm::Value` is `navree_db::Value`. The framework's own tables are models, and the modules that own tables migrate them with schema-builder migrations.
- **`navree-schema`**: the only migration system, built on the [schema builder](/docs/database/schema-builder/): tables, columns, indexes, foreign keys and check constraints in Rust, written as each database's SQL, SQLite table rebuilds, TimescaleDB hypertables, reading the live schema, and [schema dumps](/docs/database/squashing-migrations/) that replace a long migration history.
- **`navree-cache`**: a bounded memory cache store (at most 1,000,000 entries, with SIEVE eviction; `MemoryStore::with_capacity`, `capacity`, `len`, `is_empty` and `sweep`) with `remember`, tags, stale-while-revalidate and atomic locks.

### Security

- **`navree-auth`**: 15-minute JWT access tokens and 30-day rotating refresh tokens with reuse detection, pluggable authentication strategies, `CurrentUser`, registration, password change and reset, email verification, TOTP two-factor authentication with recovery codes and a policy that requires it per role or per workspace, and login throttling. Every sign-in path asks each `SignInPolicy` (`check(&self, &SignInAttempt)`, with `SignInMethod`, `SignInAudience` and `email_domain`): password, magic link, emailed code, passkey, social, token-exchange and second-step sign-in, and an email or password change. Sign-in domains are normalized, so every spelling of an SSO domain matches. An SSO user's password or email change answers 403 `sso_required`. A refused sign-in is `AuthError::SignInRefused { code, message }`. `revoke_credentials_of_domain` (and `revoke_all_credentials`) revokes every credential of the users of a domain, for offboarding in one call. Tokens carry a `sign_in` claim for challenge tokens, the header is `{"alg","typ"}`, and verification refuses tokens over 8 KiB and tokens with a `kid` or `crit` header. Users list and end their sessions; `#[recent_auth]` asks for the password or a code again before sensitive actions; support staff impersonate users behind `#[not_while_impersonating]` guards, with the impersonator on every audit entry; magic links, emailed sign-in codes and passkeys (ES256 and Ed25519) sign users in without a password; platform administrators sign in apart with two-factor authentication always; and trusted sibling systems hand their users over with signed tokens.
- **`navree-access`**: roles, permissions and abilities, record checks for `#[can(.., from = "id")]` routes, SQL list filters with `Accessible`, the abilities endpoint that shares the rules with front ends (in the JSON form `@casl/ability` reads), management routes and the `access:role`, `access:grant` and `access:explain` commands.
- **`navree-crypto`**: AES-256-GCM encryption with key rotation, Argon2id password hashing on a bounded blocking pool, token helpers and `key:generate`. `navree_crypto::jose` is Navree's own: it signs and verifies JSON Web Signatures (HS256, EdDSA, ES256, RS256 and their siblings) on `ring`, reads and publishes JSON Web Keys and key sets, and loads PKCS#8 keys such as Apple's `.p8` files and the public keys of X.509 certificates; it also signs and reads the HS256 tokens of `navree-auth`. `navree_crypto::totp` makes and checks time-based one-time passwords (RFC 6238, with `otpauth://` URLs) and `navree_crypto::qr` encodes QR codes (ISO/IEC 18004) as SVG, for the two-factor flows; both are Navree's own code.
- **`navree-audit`**: an audit log of data changes, sign-ins, permission changes and access denials, with `audit:prune`.

### Workspaces

- **`navree-workspace`**: multi-tenancy at the workspace level, on in the default features. `WorkspaceModule`, the `CurrentWorkspace` extractor, the `Workspaces`, `Members` and `Invitations` services, the `Owner`, `Admin`, `Member` and `Viewer` roles plus your own, workspace-scoped permissions for `navree-access`, resolution from a header, a subdomain, a path prefix or a token claim, a time zone and country per workspace, isolation by row, schema or database, demo workspaces seeded from fixtures, read-only or reset every night, with an `X-Navree-Demo` header for a Live/Demo switch, and shared libraries: tables of global, organization and workspace content (`m.library::<M>()`) that each workspace reads as one list and clones to change, kept consistent by a `CHECK` constraint. See [Workspaces](/docs/workspaces/introduction/), [Demo workspaces](/docs/workspaces/demo-workspaces/) and [Shared libraries](/docs/workspaces/shared-libraries/).

### Background work

- **`navree-queue`**: database and memory job queues with workers, retries with backoff, unique and delayed jobs, failed-job storage and the `queue:work`, `queue:failed`, `queue:retry` and `queue:flush` commands. Jobs dispatched during a request are queued only if its transaction commits. [Batches](/docs/digging-deeper/batches-and-operations/) run many jobs as one with `then`, `catch` and `finally` callbacks, jobs report progress with `ctx.progress`, and operations show long work to users: `GET /api/operations/{id}`, an SSE progress stream, a private channel, cooperative cancel and a watchdog that fails or restarts stalled work.
- **`navree-events`**: a typed event bus with synchronous and queued listeners.
- **`navree-schedule`**: schedules on cron expressions in UTC, in a time zone (`in_zone`) or once per workspace at its local time (`per_workspace_local`), overlap prevention, single-node runs across servers sharing a database, and `schedule:run`, `schedule:work` and `schedule:list`. `navree_schedule::CronExpression` is Navree's own parser and next-run search, with a documented language, `CronError` and `MAX_EXPRESSION_LEN` (256). These are refused at boot: names in the minute, hour or day-of-month field (`MON * * * *`), a weekday name as the month, empty list items (`1,,2`), a lone `L` in the day of week, `1-5#2`, `?/5` and a bare `*` inside a list. In a zone (`in_zone`, `in_default_zone` and `per_*_local`), an expression with a `*` in the minute or hour field (`0 * * * *`, `*/15 * * * *`, `@hourly`) follows the wall clock: it runs in both passes of a repeated hour and catches nothing up after a gap, and fixed-time crons run each local time once.
- **`navree-time`**: time zones for users, workspaces and organizations. `CurrentZone`, local days and report windows counted in the tenant's days, send windows with weekends and public holidays, `AT TIME ZONE` with a checked zone, zone names every PostgreSQL accepts, and the public zone list at `/api/time/zones`. See [Time zones](/docs/digging-deeper/time-zones/).

### Communication

- **`navree-mail`**: mailables rendered from templates, with CSS inlined and a text body generated; SMTP (DKIM-signed), SES, Mailgun, Postmark, Resend, log, array and failover transports; queued sending. For products that send for their customers: transports per sending domain, workspace and organization, a delivery log fed by provider webhooks, automatic suppressions, mail held for approval, open and click tracking, and SPF, DKIM and DMARC checks. And for mail coming in: messages parsed with every header, body, attachment and forwarded message, routed to mailboxes by address, signed reply addresses, the raw `.eml` kept on a disk, sources for Amazon SES, Mailgun, Postmark and raw MIME, and a customer's own Microsoft 365 and Gmail mailboxes watched through their integration connection. See [Inbound mail](/docs/digging-deeper/inbound-mail/).
- **`navree-notify`**: notifications over mail, the database, broadcasts, Slack, Microsoft Teams, SMS, WhatsApp and web push, with read state. People and workspaces choose the channels of each category, mail batches into hourly, daily or weekly digests, quiet hours and send windows hold deliveries on the recipient's clock until `notify:release` sends them, and each workspace restyles its notification mail. See [Notification preferences](/docs/digging-deeper/notification-preferences/).
- **`navree-realtime`**: an in-process WebSocket server that speaks the Pusher protocol, so pusher-js and any Pusher client connects, with public, private and presence channels and a signed relay that lets workers broadcast through the serving process.
- **`navree-view`**: templates for mail and other text, on `navree-template`, Navree's own template engine: the Jinja syntax, autoescaping by file name (HTML for anything not known to be text or JSON) that a template rendered inside another can only make stricter, a `|tojson` safe in scripts and attributes, a sandboxed value model and caps on depth, loops, work, output, allocation and stack that hold by construction.

### Integrations and operations

- **`navree-storage`**: named disks, streaming, signed temporary URLs and upload checks. Local and memory disks are Navree's own: writes go through a private staging file that is flushed to the device and renamed over the file, which keeps its permission bits; paths are joined under the root one segment at a time (on Windows a `:` in a name is written as `%3A`, and names that end in a dot or a space, device names and short names are refused, so one file has one name); symlinks are followed by reads and listings; only regular files are files; and deleting a file removes the directories it leaves empty. S3, Google Cloud Storage and Azure disks use the object_store client, compiled in only with their features. `StorageError::Backend` carries the backend's error as a boxed error.
- **`navree-http-client`**: outgoing HTTP with retries, timeouts, an SSRF policy and fakes for tests. Retry delays start at `http_client.retry_base_ms`, double up to 30 seconds and carry random jitter; they run on Tokio's clock, so tests with paused time step through them. The default `user_agent` is `navree-http-client/<version>` of the running crate.
- **`navree-observe`**: `/health/live`, `/health/ready` with per-module checks, and Prometheus metrics at `/metrics`. The `method` label of `http_requests_total` and `http_request_duration_seconds`, and `RequestHandled.method`, is one of the standard methods or `OTHER`.

### Testing

- **`navree-testing`**: `TestApp` to boot an app or a few modules on a temporary database, an in-process `TestClient` with cookies, `acting_as`, JSON assertions and validation-error assertions, and fakes.

## Navree UI

[Navree UI](/docs/ui/overview/) draws an app's screens in Rust: the toolkit in `navree::ui` (the `navree-ui` crate). It is the `ui` feature of `navree`, on by default, and `UiModule::from_config()` serves its files and picks ops or a page for each reply.

- **Typed components, rendered on the server.** A handler returns components. Each is a struct with builder methods that turns into one `Node`, variants are Rust enums, and `render` writes the tree to HTML in one pass. The browser's own elements do what they already know: dialogs are `<dialog>`, accordions `<details>`, popovers `popover`, and they work with no script.
- **[The components](/docs/components/overview/)**, in eight groups (actions, inputs, display, feedback, overlays, layout, navigation and data). Each has a live preview rendered by the toolkit, an anatomy of its `data-slot` parts, its variants and states, its API read from the code, and keyboard notes. `cargo test -p ui-docs` fails when the docs fall behind the code.
- **[Forms](/docs/ui/forms/)** from a validated struct. `Submit<T>` reads only the struct's own fields and refuses a body from another site (403), a body that isn't a form (415) and more than 1,000 fields (413).
- **[The app shell](/docs/ui/app-shell/)**: a sidebar with groups, items, counts and a user menu, collapsed with `Ctrl+B` and remembered in a cookie, and a top bar with the breadcrumb.
- **[DataTable](/docs/ui/data-table/)**: one `#[derive(TableRow)]` definition drives the URL, the query through navree-orm with an allow-list, the drawing, the CSV export and the bulk actions. Sort, filters, the page and the columns live in the URL, so a reload or a shared link restores them, and it all works with JavaScript off.
- **[Select](/docs/components/select/), [Combobox](/docs/components/combobox/), [MultiSelect](/docs/components/multi-select/) and [Command](/docs/components/command/)**: a styled listbox over a native `<select>` that posts with JavaScript off, a searchable combobox that can ask the server (`OptionQuery`, `ChoiceList`, and `OptionSource` over navree-orm, with the caller's own scoped query), chips with a limit, and a command palette on `Ctrl+K`. A form picks with them through `#[form(widget = ...)]`, and a handler checks what was posted with `Choice::all_among` or `OptionSource::all_pickable`.
- **[Commands and ops](/docs/ui/commands-and-ops/)** and **[regions](/docs/ui/regions/)**: a form or a command posts to a handler, which answers with a `Reply`: ops for the runtime (morph this element, show a toast, close this dialog), or a redirect or a full page when JavaScript is off.
- **Little in the browser.** Every page loads one stylesheet, and script only for what its markup uses (`core`, `overlay`, `sidebar`, `table`, `select`); a page with nothing interactive has no `<script>` at all. The files are embedded in the binary and served at content-hash URLs under `/_navree/ui/`. `tests/budgets.rs` holds the ceilings: the `core` runtime 12 KB gzip, the stylesheet 25 KB, every module together under 60 KB.
- **A strict content security policy.** Scripts, styles, fonts and requests from the page's own origin only, no inline script or style, and no framing. Text goes through one escaper, every URL through `Href`, which refuses `javascript:`, and `Reply::redirect` refuses a URL that leaves the site.
- **`TestView`** drives a page in a plain test, with no browser: check what it shows, click by name, fill a form and read it back as your struct.
- **Still to come.** Navree UI grows one module at a time. Tabs, menus, charts and date pickers aren't in 1.0; [Coming next](/docs/ui/coming-next/) lists what comes, in order.

You can also draw the screens in JavaScript, beside the same API: `navree new <name> --ui next` creates a Next.js app that carries its own backend-for-frontend, `@navree/next` adds that layer to a Next.js app you already have, and `@navree/nuxt` is the module for a Nuxt app you create yourself (there is no Nuxt starter kit). [Choosing a UI](/docs/ui/choosing-a-ui/) says what each costs and gives. [Logbook](/docs/tools/logbook/)'s pages are drawn with Navree UI.

## The CLI

The `navree` binary (crate `navree-cli`) creates apps, generates code and runs the dev loop:

- `navree new <name>`, with `--kit` for a [starter kit](/docs/getting-started/starter-kits/), `--ui next` for a Next.js front end that keeps tokens in httpOnly cookies, and `--navree-path` to choose the Navree checkout. New apps depend on `navree` with the driver feature of the database you chose and `sqlite` in `[dev-dependencies]`. When `navree new` finds no checkout to point at, the dependency is the CLI's own version (`1.0.0`). It runs `git init` (nothing is committed) unless the directory is inside a repository, and writes `harbor.key` for apps that ship a `harbor.toml` (the starter kits); `navree harbor:init` on an existing `harbor.toml` writes only a missing key.
- `navree make:module <name> [--crud]` and `make:<kind>` generators for controllers, services, models, factories, seeders, migrations, jobs, events, listeners, mail, notifications, policies, commands, AI agents, MCP servers and tests. Generators write models and schema-builder migrations, never overwrite files, and register what they create at marker comments. `navree make:resource <module> <Model>` reads `models/<model>.rs`.
- `navree dev`, which rebuilds and restarts the app when its code changes, and keeps the last good build serving when a build fails.
- `navree openapi:client` exports the app's OpenAPI document and writes the front end's `schema.d.ts` (`paths`, `components`, `operations` and `webhooks`, typed for `createNavreeClient<paths>()`). The generator is part of the binary, so the front ends and the SaaS kit's `gen:api` script run no Node tool to make the types; with `--input` it reads a JSON document and needs no app.
- `@navree/client` has no runtime dependencies. Its typed fetch core (`createClient` from `@navree/client/fetch`) covers path, query and header parameters, JSON, form and multipart bodies, responses read by status and `parseAs`, abort signals and middleware, all typed from the generated `paths`. `createNavreeClient<paths>()` is built on it, and the CRM front ends carry a copy of it.
- The ecosystem's commands: `navree dock up`, `navree deploy`, `navree fleet`, `navree mcp` and `navree skills:install`.
- Every other command is forwarded to the app's binary.

The starter kits record `kit_version = "1.0.0"` in the app's `Cargo.toml`. The SaaS kit's `.env.example` has `NAVREE_TRUSTED_PROXY_HOPS` and `NAVREE_CLIENT_IP_HEADER`, and the kits ship their CI workflow, READMEs and `AGENTS.md`. A kit is a template, so a later kit's changes reach new apps only: to pick them up, generate a fresh copy and compare, as [Starter kits](/docs/getting-started/starter-kits/#updating) describes.

## Security hardening

- **Client addresses behind proxies.** The `@navree/bff` backend-for-frontend forwards the browser's address (`clientIpHeader`, `NAVREE_CLIENT_IP_HEADER`), and Harbor's Caddy trusts the load balancer's `X-Forwarded-For` (`deploy.trusted_proxies`).
- **Content security policies.** The API reference and GraphiQL load scripts from the app itself (`script-src 'self'`), GraphiQL's WebSockets may only reach the request's host, and GraphQL hides its internal types from introspection.
- **Parser limits.** The parsers for host names, phone numbers, email domains and SCIM filters are fuzzed. SCIM filters are capped at 16 KiB and 32 levels.
- **Imports are limited by shape as well as size.** `sheets.imports.max_columns` (default 16,384, the width of an Excel sheet) and `sheets.imports.max_cells` (default 10,000,000) refuse a file with a message on the import. Every row counts at the header's width, because a short CSV with a very wide header is padded to that width on every row, so a few hundred kilobytes could otherwise ask for tens of gigabytes. `sheets.imports.max_rows` is checked while the file is read, not after every row is in memory.
- **How each format is read.** CSV, TSV, XLSX, XLSB, ODS and XLS files are refused while they are read, a record or a cell at a time, without their rows being held; workbooks are read by the module's own readers, which stream the sheet and hold memory for the cells the table keeps, not for the area between the first and the last. An ODS row or cell that repeats is read once and counts against the limits for every copy. Dates and times are dates and times in every workbook format (ODS too, by its null date), an error cell is its text whatever its name (`#SPILL!`), in ODS too, and an ODS tab or line break is a tab or a line break. XLSX and XLSB parts are found through their relationships, as relative references, wherever a file keeps them, and Excel 4 macro sheets hold no cells. An encrypted XLS file is refused. A header repeated thousands of times is named in linear time. Staging reads the file on the blocking pool so the job's timeout can fire, and the reading stops when it does: a workbook's sheet within 64 KiB of its part (an XLS sheet within 1,024 records), whether or not what it reads gives a cell, and a text file at its next record. Times are read to the millisecond in every format, and a number past the largest double (`INF`, `1.797693134862316e+308`) is the largest double of its sign, in every format; `NaN` is refused. A sheet whose cells are not in row order (Excel never writes one) is held only up to those limits, and is refused when it has more cells with a value than `max_cells` even if the table would have fitted.
- **Workbooks that unpack to a lot.** `sheets.imports.max_inflated_bytes` (default 1 GiB) refuses a workbook with a part that unpacks to more than that by the size its zip file declares, before it is read: `max_upload_bytes` bounds the file, not what it unpacks to, and the XLSX and XLSB readers keep the shared strings for the whole reading; the number of strings a file declares sets no memory aside. Opening can't be interrupted, so it is bounded in memory and in work: everything it keeps (strings, sheet names, relationships, formats) counts against one budget of that size, a workbook has at most 65,535 sheets, one element or string takes at most 16 MiB, nesting stops at 256, each part is read in one pass, and opening unpacks at most four times the limit in all. The check applies to every file opened as a workbook, however its format was detected, and bounds an XLS file's workbook stream before it is copied. `sheets.imports.max_text_bytes` (default 256 MiB) bounds the text the table keeps, counting a shared string again for each cell it is in, so a small file of any format can't ask for gigabytes of copies, and an ODS row whose cells repeat a space a billion times is refused before the spaces are made, counting the whole row and, across the sheet, every row; spaces that end a cell, and rows and cells that give nothing, are never made. An XLS file's shared strings count against it as they are decoded.
- **A wrong API document doesn't boot.** Two different types with one name refuse the boot and the error names both, however deep they are, and `navree-mcp`, `navree-ai` and `navree-workflows` refuse them the same way; generic types get a component per argument (`Page<Note>` is `Page_Note`). `#[derive(ToSchema)]` follows serde's one-way names and fields with `readOnly` and `writeOnly`, and refuses to compile what it can't describe. `/api/docs` and `/api/openapi.json` are public and served outside production: in the `production` environment they are off unless `api.docs_ui` and `api.openapi_json` turn them on, an app with no environment serves them from a debug build only, and `openapi:export` writes the document in every environment.
- **Secrets in URLs stay out of what is kept.** `RequestBuilder::secret_url` shows only the host in errors, logs and telemetry; Lighthouse's Slack and webhook alerts, the Slack and Teams notification webhooks, outgoing webhooks and web push send with it.
- **A hidden column is hidden everywhere in Helm.** Field rules and `#[model(hidden)]` hold on every route: titles, pickers, related columns, forms, exports, search, sort, filters and metrics, from one place every route asks. `make:resource` makes no field for a hidden column or one named like a secret.
- **A Helm export follows the user's access.** Every chunk reads it again, so a role or a permission taken away ends the file, and `helm.export_max_secs` ends a slow one. The audit log says the workspace, the rows sent and how it ended.
- **The schema generator is bounded.** `navree openapi:client` reads a document of at most 64 MiB that nests at most 128 levels, follows a `$ref` through at most 64 others, runs on a stack of its own, and stops when the TypeScript for one document would pass about 32 MiB, so a crafted document is refused with a message and cannot exhaust the machine. It refuses a document that is not OpenAPI 3, has a `$ref` that leads nowhere or outside the file, or uses an `operationId` twice.
- **Rich text has limits.** `SafeHtml` refuses an input over `validation.html.max_input_bytes` (512 KiB) before parsing it, and stops a parse past `max_nodes` (131,072) or `max_depth` (128, at most 256, counting elements and not the text in them; browsers read markup past 512 levels flat), each a 400 on the field; `clean` keeps 256 levels at most whatever the policy says, and a limit of 0 fails the boot. A parse at the limit takes at most about 0.2 s in a release build, and no input is parsed more than twice. The extractors read a body of 16 KiB or more on Tokio's blocking pool, whatever fields it holds, so it doesn't hold the async worker that reads the request. A policy can't allow `on*`, `srcdoc` or `http-equiv`, `link_rel` goes on `area` as well as `a`, `srcset` and `ping` are checked URL by URL, and a URL with a host and no scheme (`//x`) stays only when `http` and `https` are both allowed. See [Limits on rich text](/docs/basics/validation/#limits-on-rich-text).
- **Inbound mail is read by Navree's own MIME reader, off the async threads.** The reader is linear in the message, never recurses past `mail.inbound.max_depth` nested multiparts (default 32), and refuses a message with more than `mail.inbound.max_parts` parts, `mail.inbound.max_headers` header fields or `mail.inbound.max_addresses` addresses in one field (each default 1,000) while it reads it, so a few bytes of MIME can't declare their way to gigabytes of parts, fields or addresses. It is fuzzed. `Inbound::receive` and `Inbound::read` parse on Tokio's blocking pool, and a message the reader refuses, or that makes it panic, is `InboundError::Unparseable` (a 400). When a source reports the envelope, mailboxes route on it alone: a header can't reach another mailbox. `mail.from` is empty unless the head holds one `From` that is an address, or a name and an address in angle brackets, and nothing else (no group, list, stray separator, quoted string beside the address or mixed line ends), and decoded subjects, names, addresses and file names hold no control characters. Only Amazon SES reports verdicts: Mailgun and Postmark keep theirs in headers the sender can also write, so none is read, and a Postmark payload reports no envelope sender.
- **Limits on reading PDFs and images.** Reading a PDF's text is held to a budget of work, 128 MiB a page and 1 GiB a document, that counts the content decoded (a form drawn again counts again), each operation, character code and object looked up, everything a filter reads and writes whether the content can be used or not, the fonts read, and the actual text of marked content. The time is in proportion to it: the slowest shape found takes about 22 s for all of it on one core, and a test holds every known shape to the rate, pages of a million glyphs, cold lookups and compressing included. A page is also held to 1,000,000 character codes shown, 8 MiB of text (64 MiB for the document), 256 levels of `q` and of marked content, and 50,000,000 comparisons attaching marks. A font's `ToUnicode` map, which comes before its `Encoding`, is held to caps by the one reader of the map, as it reads: more than 64 codespace ranges, 131,072 lines, 256 texts in one list or 65,792 in all lists is refused. The map is counted by what reading it builds (two ranges for each line that maps codes, and the texts kept; a range is one entry however many codes it covers), as are an encoding's `Differences`, so a `ToUnicode` map of a few bytes builds only what its lines say. A glyph name over 127 bytes and a map's text over 512 bytes read as nothing. The actual text of marked content that is open counts against the text of a page. Fonts and maps are read once for all the fonts that share them and kept within 256 MiB per document (plus the widths of one font); past that the least recently used are dropped and read again, at a cost in work, and a map that would take more on its own is refused. These limits hold for `Pdf::text` and `Pdf::page_texts` and for navree-media's `text::extract`, which reads PDFs with the same code.
- **Image limits.** The native engine refuses a PNG, GIF or WebP with more pixels than `documents.native.max_image_pixels` (default 25,000,000; 0 fails the boot, from configuration or from `DocumentsModule::for_root`) before decoding it; a JPEG goes into the PDF undecoded and is not counted. These refusals are `DocumentsError::TooLarge`, a 413, whose message names the limit but no template file.
- **Reading a PDF is held to a budget.** navree-pdf, the PDF layer under navree-documents and navree-media, reads the cross-reference when a PDF is loaded and each object the first time it is needed, counting what it builds: 256 MiB of objects for a document (each object stream and cross-reference stream inflated, up to 8 MiB each, included), for which the process holds at most twice that, and 1 GiB of bytes looked at: what a parse reached before it failed and what every filter reads and writes count too, each object looked up costs 32 bytes, a chain of references stops at 8, a stream has at most 8 filters, and tables are looked up by key, so time is linear in the file until the limit stops it. An object is 32 bytes, so a tagged spreadsheet of 10,000 rows (250,000 objects) is half of the memory, plain or with object streams, and a book of 3,000 pages an eighth. A file of a few kilobytes whose objects would take gigabytes, objects of an object stream that share their bytes, or a cross-reference that sends the reader over the same bytes again and again, is refused with `DocumentsError::TooLarge` (413) once it reaches the budget. A stream ends before the next object starts, whatever its `Length` says, and an edit writes at most the bytes of the files it read plus 256 MiB, and may add what is counted as 256 MiB, refused before it is held; saving compresses with Flate at its fastest level for 2 bytes of work a byte. `merge` and `overlay` hold all their inputs to those limits together, each read with what the ones before it left, and a merge counts of an input only the pages it keeps and what they lead to. It reads cross-reference tables and streams, object streams, incremental updates, linearized files, a broken cross-reference (rebuilt from the objects in the file), the Flate, LZW, ASCII85, ASCIIHex and RunLength filters (image codecs stay encoded), and files encrypted without a password to open them (RC4 and AES of 40 to 256 bits); a file that needs a password is refused. `merge`, `stamp`, `overlay` and `with_metadata` write through the same layer.
- **Stamps, overlays and merges keep shared resources shared.** Resources that pages inherit or share stay one object, so stamping a document of many pages and many fonts doesn't copy every font onto every page, and a page the page tree lists twice is stamped once.
- **Word file errors.** Bytes given to `DocxFile::from_bytes` that are not a Word document that can be read are `DocumentsError::InvalidDocx`, a 400 with its message; a file over a reading limit is `TooLarge`, a 413. Writing a Word file failing is `DocumentsError::Docx`, a 500, without details.
- **PDF errors.** A PDF that cannot be read, or that an edit would lose part of because an object its page tree, contents or resources lead to cannot be read, is `DocumentsError::Pdf`, a 400 with its message. A fault of the server while writing an edited PDF is `DocumentsError::Engine` with `engine: "pdf"`, and an edit the app should not have asked for (merging nothing, a text stamp Helvetica cannot show) is `DocumentsError::Edit`; both are 500, without details.
- **FFmpeg starts with a clean environment.** `ProcessRunner` passes `ffmpeg` and `ffprobe` only `PATH`, the temporary directory (`TMPDIR`; `TEMP` and `TMP` on Windows, where a tool without them would write its temporary files in the Windows directory) and, on Windows, `SystemRoot`, so a file they open cannot reach the server's secrets through the process. A build that needs `LD_LIBRARY_PATH` goes behind a wrapper script named in `media.ffmpeg.ffmpeg`. `Archive::extract_to` inflates on the blocking pool.

## Supply-chain checks, fuzzing and test folders

- **Gates on every change.** `cargo-deny` (advisories, licenses, bans, sources), `cargo-vet`, OSV-Scanner over every lockfile, Semgrep with Navree's own rules, Gitleaks over the history, a daily vulnerability scan, and GitHub Actions pinned to commit SHAs. Tagged releases get a CycloneDX SBOM. [Contributing](/docs/prologue/contributing/) lists them, `SECURITY.md` says how to report a vulnerability and `CODEOWNERS` names the reviewers.
- **Fuzzing.** A separate `fuzz/` workspace has a target for every parser of untrusted input; CI runs each briefly when `fuzz/` changes and for longer every week.
- **Test folders clean up after themselves.** Every temporary folder a test makes is named `navree-test-*`; `TempDirGuard` deletes it, retrying for a short while on Windows where an open handle blocks the delete, and a sweep that runs at most every ten minutes removes the `navree-test-*` folders more than an hour old that a crashed run left behind.

## Design decisions

- **Token authentication for APIs.** `navree-auth` issues stateless JWT access tokens and rotating refresh tokens, and a backend-for-frontend keeps them in httpOnly cookies for browsers. Cookie sessions with CSRF protection are a separate module, [Sessions and CSRF](/docs/basics/sessions-and-csrf/), for apps that want them.
- **One error shape.** Every error is JSON in Navree's shape, `{ "statusCode", "message", "error", "code" }`, with `errors` for validation failures. The `code` is machine-readable and stable (`not_found`, `invalid_credentials`), so front ends show every refusal in the user's language. Input errors are 400s and CSRF failures are 403s.
- **Real time is built in.** Navree ships an in-process Pusher-protocol server. Processes that don't serve the sockets send their broadcasts to the one that does over a signed HTTP relay.
- **The framework's own crates don't use the macros.** They implement `Module`, `Injectable` and `Controller` by hand, the escape hatch every app can use too. Apps use the macros.
