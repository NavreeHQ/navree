## Introduction

Navree isn't one big crate. It's a workspace of small crates, one per module, arranged in layers from L0 (the kernel and the macros) through the ecosystem libraries (L6), such as [feature flags](/docs/packages/feature-flags/), and the packages built on them (L7), such as [Helm](/docs/tools/helm/), to L8 (the `navree` facade and the CLI), with applications on top. A crate may depend only on crates in lower layers, plus a few listed crates of its own layer, and only on the ones its row allows. A test checks every dependency edge in the workspace each time the tests run.

This keeps the framework honest: the kernel knows nothing about HTTP, HTTP knows nothing about databases, and authentication builds on everything else rather than the other way round. You can read, test or use any crate with only what's below it. Most apps never see the split, because they depend on the facade, but it explains why things are where they are.

The lists are what's allowed; some crates use less (`navree-access` doesn't use the cache today). Some edges join crates of one layer, each listed on purpose, such as `navree-config` to `navree-contracts` (L1), `navree-mail` to `navree-db` (L3) and `navree-audit` to `navree-orm` (L4). The table never points upwards and has no cycles.

Three exceptions apply to dev-dependencies, so tests can boot what they need:

- A crate's tests may use any Navree crate in a **lower** layer. That's how every crate from L4 up tests with `navree-testing` (L3), and how navree-notify's tests boot `ViewModule` for `MailModule`.
- A crate's tests may depend on the crate itself, to turn on its own features (navree-workspace's `testing`).
- `navree-macros` may dev-depend on any runtime crate, because its tests expand the macros against the crates the generated code calls.

The framework's own crates implement `Module`, `Injectable` and `Controller` by hand instead of using the macros. The macros sit at L0 with no runtime dependencies, and the generated code names whichever crates the user's crate depends on.

## Cross-cutting needs: `navree-contracts`

Some needs cut across modules. The HTTP pipeline records refused requests in the audit trail; notifications broadcast to WebSocket channels; the database layer hands jobs to the queue after a commit. Letting `navree-http` depend on `navree-audit` would point up the hierarchy.

Instead, the shared shape lives in `navree-contracts` (L1) as a trait. One module implements it and registers it as a `dyn Trait` provider; the others resolve it, usually as optional:

| Contract | Implemented by | Used by |
|---|---|---|
| `AuditSink`, `AuditEntry`, `AuditKind` | navree-audit | navree-http (route audit actions, security events), navree-access (denials), navree-auth, navree-session (CSRF failures) |
| `Broadcaster` | navree-realtime | navree-notify, navree-access, navree-auth (ending a user's subscriptions) |
| `EventSink` | navree-events | Modules that publish events by name |
| `Dispatcher`, `Job`, `JobRegistration`, `JobOptions` | navree-queue | navree-events (queued listeners), navree-mail (queued mail), navree-notify, navree-schedule |
| `HealthCheck`, `HealthStatus` | navree-db, navree-cache, navree-storage, navree-redis, navree-mongo, navree-micro (as multi-bindings) | navree-observe (readiness) |
| `SessionStore`, `SessionRecord` | navree-session's memory and database stores, navree-redis's store | The session layer |
| `Principal`, `AuthState`, `AuthVia` | navree-auth (through navree-http's `Authenticator`) | Every module that needs the current user |
| `CredentialRevoker`, `RevokedByKind` | Modules that issue credentials to users, such as navree-oauth, as multi-bindings (`m.credential_revoker::<R>()`) | navree-auth (`revoke_credentials_of_domain`, `revoke_all_credentials`) |
| `Clock` | `SystemClock`, `FixedClock` (tests), registered by your app | Modules that need "now" and tests that fix it |
| `ZoneSource`, `ZoneOwner`, `ZoneLevel`, `ZoneRequest` | navree-workspace (workspaces), your app (users), as multi-bindings | navree-time (`CurrentZone`, `Zones`), navree-schedule (per-workspace schedules) |

Two plain types live there too: `RequestId`, which the HTTP pipeline creates for each request and which logs and audit entries carry, and `Secret<T>`, the wrapper configuration structs use for keys and passwords so they never show up in logs.

Your own code can use the contracts the same way. This function audits an export when the app has an audit trail, and does nothing otherwise:

```rust
use navree::contracts::{AuditEntry, AuditKind, AuditSink};
use navree::prelude::*;
use uuid::Uuid;

pub async fn record_export(ctx: &AppContext, user: Uuid) -> Result<(), BoxError> {
    if let Some(audit) = ctx.try_get::<dyn AuditSink>().await {
        let entry = AuditEntry::new(AuditKind::Custom, "contacts.exported").actor(user);
        audit.record(entry).await?;
    }
    Ok(())
}
```

And a service that must broadcast can inject the contract instead of the realtime module's types:

```rust
use navree::contracts::Broadcaster;

#[injectable]
pub struct DealBroadcasts {
    broadcaster: Arc<dyn Broadcaster>,
}

impl DealBroadcasts {
    pub async fn updated(&self, deal: serde_json::Value) -> Result<(), BoxError> {
        self.broadcaster
            .broadcast(
                vec!["private-crm.deals".to_owned()],
                "deal.updated".to_owned(),
                serde_json::json!({ "deal": deal }),
            )
            .await
    }
}
```

Two seams aren't in `navree-contracts` because they need HTTP types: `Authenticator` and `RouteAuthorizer` live in `navree-http`. navree-auth implements the first and navree-access the second, and the pipeline resolves both as `dyn` providers.

## The dependency-graph test

`crates/navree/tests/dependency_graph.rs` encodes the table above, one row per workspace crate. Run it on its own:

```sh
cargo test -p navree --test dependency_graph
```

It reads the workspace with `cargo metadata` and checks that:

- every dependency edge between workspace crates (normal, dev and build) is allowed;
- every workspace crate has a row, and every row is a workspace crate;
- the table itself never points upwards and has no cycles;
- `Cargo.lock` contains none of `aws-lc-sys`, `aws-lc-rs`, `aws-lc-fips-sys`, `openssl`, `openssl-sys`, `native-tls` or `cmake`: TLS is rustls with the `ring` provider everywhere, so building needs no CMake, NASM or OpenSSL;
- `Cargo.lock` contains none of `rsa`, `p256`, `p384` or `ed25519-dalek`: RSA, ECDSA and Ed25519 signatures go through `ring`, wrapped in `navree_crypto::jose`;
- `Cargo.lock` contains no other data layer's packages, and no workspace crate declares one: the data layer is navree-db, navree-orm and navree-schema;
- `Cargo.lock` contains no other HTTP router: navree-http matches routes itself, on `hyper` and `tower`;
- a build of `navree` with `postgres` or `mysql` and without `sqlite` compiles no `libsqlite3-sys` or `sqlx-sqlite`, and a build with `sqlite` alone compiles neither `sqlx-postgres` nor `sqlx-mysql`.

A forbidden edge fails with a message that says what the crate may use instead:

```text wrap
crate hierarchy violations:
  navree-http (L2) -> navree-crypto (L2) (Normal) is not an allowed edge; navree-http may depend on: [navree-openapi, navree-kernel, navree-contracts, navree-config, navree-telemetry]
```

The applications are in the table too. The CRM has `crm-core` at L9, `crm-testkit` at L10, the feature crates (`crm-users`, `crm-companies`, `crm-deals`, `crm-activities`) at L11 and the `crm-api` binary at L12. They may depend only on the `navree` facade and the CRM crates below them. The `evidence-app` binary, which the Docker evidence harness in `e2e/` runs under load, the Navree UI binaries `ui-proof` and `ui-table-proof`, and `store-demo`, `inbox-demo` and `board-demo`, example apps on Navree UI, are at L9, as is `skill-snippets`, which compiles the Rust blocks of the agent skills. Each depends only on the facade. `ui-docs`, which writes the website's UI docs, is at L10: it draws the example apps' views for the website, so it depends on `store-demo`, `inbox-demo` and `board-demo` as well as the facade.

The tests in `crates/navree/tests/facade.rs` keep the facade's [features](/docs/architecture/facade-and-features/) in step with the hierarchy.

<Callout type="note" title="Adding a crate to the workspace">

Give it a row in `HIERARCHY` in `dependency_graph.rs`, with its layer and the crates it may use, before you add dependencies. A workspace crate without a row fails the test.

</Callout>

## Applying the idea to your app

The same discipline works for an application. The CRM's feature crates all build on `crm-core`, which holds the shared models, migrations, abilities and platform setup, and none of them depends on another feature crate. When two features need to cooperate, they do it through something lower down: an event, a trait in the shared crate, or a service the shared crate exports. Inside a single crate, [modules](/docs/architecture/modules/) give you the same structure: a feature imports only what it uses, and the boot fails when it reaches for something it didn't import.
