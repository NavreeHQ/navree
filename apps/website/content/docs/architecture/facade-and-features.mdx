## Introduction

Navree is split into [small crates](/docs/architecture/crate-hierarchy/), but an app doesn't have to know that. The `navree` crate, the facade, is the one dependency an app needs: it re-exports every module crate, the attribute macros and a prelude of everyday names. Each module crate sits behind a Cargo feature of the same name. The default feature, `full`, turns on all of them except the opt-in ecosystem libraries, tools and database drivers, so you can start with everything and trim later.

## Depending on Navree

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree" }
serde = { version = "1", features = ["derive"] }
```

The crates aren't on crates.io yet, so the dependency comes from Git: `cargo add --git https://github.com/NavreeHQ/navree navree` adds it for you. An app created with `navree new` depends on a local checkout of Navree instead (a `path` dependency); see [where new apps get Navree from](/docs/getting-started/installation/#where-new-apps-get-navree-from).

`main` needs nothing else: `AppBuilder::run` starts its own Tokio runtime. Add `tokio` when you write `#[tokio::test]` tests, and add `serde` directly when you use its derives, because derive macros name their own crate. `#[derive(Validate)]` and `#[derive(ToSchema)]` come with `navree`.

Then one import brings the usual names into scope:

```rust title="src/main.rs"
use navree::prelude::*;

#[injectable]
pub struct GreetingController;

#[controller("/greeting", version = "1")]
impl GreetingController {
    #[get("/{name}")]
    #[public]
    async fn show(&self, Path(name): Path<String>) -> Json<String> {
        Json(format!("Hello, {name}!"))
    }
}

#[module(controllers = [GreetingController])]
pub struct GreetingModule;

fn main() -> Result<(), BoxError> {
    Navree::app()
        .module(ConfigModule::for_root(ConfigSources::defaults()))
        .module(HttpModule::from_config()) // GET /api/v1/greeting/{name}
        .module(GreetingModule)
        .run()
}
```

The facade's root also has:

- **The macros:** `navree::module`, `navree::injectable` and `navree::controller`, with the route attributes `get`, `post`, `put`, `patch` and `delete` (which `#[controller]` consumes, so you don't import them). With `micro`, `navree::message_handlers` and the `message_pattern` and `event_pattern` attributes it consumes. With `orm` and `testing`, `#[navree::test]`, an `async fn` test on a runtime of its own that gets a database of its own when it takes a `TestDb` parameter.
- **The kernel types** apps use most: `Navree`, `App`, `AppBuilder`, `AppContext`, `Module`, `ModuleBuilder`, `ModuleId`, `Injectable`, `Factory`, `Lazy`, `Resolver`, `ProviderKey`, `Scope`, `KernelError`, `BoxError` and `BoxFuture`.
- **`navree::Result<T, E = AppError>`**, a handler's result type (with `http`).

The `http` crate's types (`StatusCode`, `HeaderMap`, `Method`) come from `http`, which you add to your own dependencies.

It also imports every `ModuleBuilder` extension trait anonymously (`as _`), so methods such as `m.config::<T>()`, `m.controller::<C>()`, `m.migrations(..)`, `m.job::<J>()`, `m.listen::<E, L>()`, `m.templates(..)`, `m.schedule(..)` and, with `graphql`, `m.resolver::<R>()` and `m.dataloader::<L>()`, and with `micro`, `m.message_handlers::<T>()` and `m.forward_event::<E>()`, work without naming the traits.

Three details to know:

- **`Result` is Navree's.** With `http`, the prelude's `Result<T>` is `navree::Result<T>`, whose error type defaults to `AppError`, and it shadows the standard prelude's `Result`. Name the error type when it isn't an `AppError`: `fn main() -> Result<(), BoxError>`.
- **Two factories.** `Factory` is the kernel's provider factory. The ORM's model factory trait (for test data) is `ModelFactory` in the prelude, with `orm`; the rest of the factory API is in `navree::orm::factory`.
- **Test helpers aren't in the prelude.** Import them from `navree::testing`.

## Cargo features

The facade has one feature per module crate, named after it (`http-client` for `navree::http_client`). The default feature, `full`, turns on all of them except the opt-in ecosystem libraries, packages and tools (`social`, `oauth`, `flags`, `graphql`, `grpc`, `documents`, `media`, `billing`, `search`, `mcp`, `ai`, `redis`, `i18n`, `mongo`, `micro` with its transports, `dock`, `harbor`, `navigator` and `browser`), which you list by name: `features = ["flags"]`. It includes the S3 storage driver (`storage-s3`); the Google Cloud Storage and Azure drivers are opt-in (`storage-gcs`, `storage-azure`), and so are the database drivers and `otel`. To build only what you use, turn the defaults off and list the modules:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", default-features = false, features = ["http", "log"] }
```

`navree-kernel`, `navree-bounded`, `navree-glob`, `navree-contracts`, `navree-config`, `navree-openapi` and `navree-macros` are always included. A module's feature also turns on the features of the modules its crate builds on, so `navree::<that module>` is always there to name their types:

| `fleet` | `telemetry`, `http`, `events`, `view`, `db`, `observe`, `queue`, `access` |
| `helm` | `http`, `view`, `db`, `crypto`, `storage`, `validation`, `audit`, `access`, `auth`, `orm` |
| `workflows` | `http`, `db`, `events`, `schedule`, `workspace` |
| `directory` | `http`, `crypto`, `events`, `db`, `orm`, `queue`, `schedule`, `workspace`, `integrations` |
| `domains` | `http`, `crypto`, `events`, `db`, `orm`, `schedule`, `workspace` (with `lighthouse` on too, certificates close to expiry are reported to Lighthouse) |
| `sqlite` (opt-in) | `db`, navree-db's SQLite driver (the bundled library), and `logbook`'s SQLite file store |
| `postgres` (opt-in) | `db`, and navree-db's PostgreSQL driver |
| `mysql` (opt-in) | `db`, and navree-db's MySQL and MariaDB driver |
| `validation-phone` | `validation`, and navree-validation's `Phone` (E.164 numbers, on the rlibphonenumber crate) |
| `validation-html` | `validation`, and navree-validation's `SafeHtml` (rich text sanitized by Navree's own sanitizer on html5ever) |
| `storage-s3` (in `full`) | `storage`, and navree-storage's S3 driver (AWS, MinIO, Cloudflare R2, DigitalOcean Spaces) |
| `storage-gcs`, `storage-azure` (opt-in) | `storage`, and navree-storage's Google Cloud Storage or Azure Blob Storage driver |
| `otel` (opt-in) | `observe`, and navree-observe's OTLP exporter for the spans of `observe.tracing` |
| `browser` (opt-in) | `http` |
| `dock`, `harbor` (opt-in) | Nothing else |
| `navigator` (opt-in) | `dock` |

`validation-phone` and `validation-html` are part of `full`. They add the [international types](/docs/basics/validation/#international-input) that need a dependency of their own; names, digits, countries and locales come with `validation` alone.

With `workspace` on too, `testing` also adds `navree::workspace::testing`, the [isolation suites](/docs/testing/isolation-tests/); neither feature turns the other on.

The database drivers are features of their own, and none is in `full`. Each turns on `db` and the matching driver of navree-db: `postgres` adds the PostgreSQL driver, for TimescaleDB (the default database of a new app) and plain PostgreSQL, `mysql` the driver for MySQL and MariaDB, and `sqlite` the SQLite driver, with the bundled SQLite library compiled from C source (it also turns on the `file` store of `logbook` when that is on). A build with `postgres` or `mysql` and without `sqlite` compiles no SQLite code at all; an app opens a database only with a driver it was built with, and otherwise stops with a message naming the feature to enable. A new app's tests run on SQLite, so `navree new` turns `sqlite` on in `[dev-dependencies]` only. The `storage-*` features add [object storage drivers](/docs/digging-deeper/storage/#cloud-disks); they talk HTTPS through rustls with ring, so they need no system library. Navree's [performance](/performance/) harness runs it on PostgreSQL 17 and the test suite runs on SQLite; [the database pages](/docs/database/getting-started/#postgresql) list which PostgreSQL-only paths to try in staging first.

Tests in `crates/navree/tests/facade.rs` keep this table true: every module crate sits behind a feature named after it, each module feature turns on exactly the features of the crates its crate depends on (no fewer, no more), and `full` is the default and covers every module except the opt-in ones (`social`, `oauth`, `flags`, `graphql`, `grpc`, `documents`, `media`, `billing`, `search`, `mcp`, `ai`, `redis`, `micro`, `i18n`, `mongo`, `dock`, `harbor`, `navigator`, `browser`), which you list yourself: `features = ["billing"]`.

<Callout type="note">

Turning a feature off removes the module's crate from the build, along with its re-export, its prelude names and its third-party dependencies. Features only decide what is compiled: a module that is compiled in does nothing until the app adds it with `.module(..)` or a module imports it.

</Callout>

## How the macros find the crates

`#[module]`, `#[injectable]` and `#[controller]` expand into code that calls the runtime crates. They look in your `Cargo.toml` to decide how to name them:

1. If the crate depends on `navree`, the code names `::navree::kernel`, `::navree::http` and `::navree::access`. A renamed dependency is honoured: with `framework = { package = "navree", git = "https://github.com/NavreeHQ/navree" }`, the code names `::framework::kernel`.
2. Otherwise it names the individual crates: `::navree_kernel`, `::navree_http`, `::navree_access`.
3. If neither is there, the attribute fails to compile with: ``this attribute needs the `navree` crate (or `navree-kernel`) in the [dependencies] of your Cargo.toml``.

`#[controller]` needs navree-http, `#[can]` with marker types such as `#[can(Update, Deal)]` needs navree-access, `#[flag]` and `#[requires_flag]` need navree-flags (`::navree::flags`), and `#[agent]` needs navree-ai (`::navree::ai`); with the facade, that means the `http`, `access`, `flags` and `ai` features. `#[mcp_server]` names `::navree::mcp` (or `::navree_mcp`), so it needs the `mcp` feature; import it from `navree::mcp`.

## Using a crate on its own

Every module crate is a normal library you can depend on directly, without the facade. The kernel alone gives you modules, dependency injection, lifecycle hooks and commands:

```rust
use navree_kernel::{Module, ModuleBuilder, Navree};

struct GreetingModule;

impl Module for GreetingModule {
    fn register(&self, m: &mut ModuleBuilder) {
        m.value(String::from("hello")).exports::<String>();
    }
}

fn main() -> Result<(), navree_kernel::BoxError> {
    Navree::app().module(GreetingModule).run()
}
```

The macros work with the individual crates too. This is the greeting app without the facade:

```toml title="Cargo.toml"
[dependencies]
navree-kernel = { git = "https://github.com/NavreeHQ/navree" }
navree-config = { git = "https://github.com/NavreeHQ/navree" }
navree-http = { git = "https://github.com/NavreeHQ/navree" }
navree-macros = { git = "https://github.com/NavreeHQ/navree" }
```

```rust title="src/main.rs"
use navree_config::{ConfigModule, ConfigSources};
use navree_http::{HttpModule, Json, Path};
use navree_kernel::{BoxError, Navree};
use navree_macros::{controller, injectable, module};

#[injectable]
pub struct GreetingController;

#[controller("/greeting", version = "1")]
impl GreetingController {
    #[get("/{name}")]
    #[public]
    async fn show(&self, Path(name): Path<String>) -> Json<String> {
        Json(format!("Hello, {name}!"))
    }
}

#[module(controllers = [GreetingController])]
pub struct GreetingModule;

fn main() -> Result<(), BoxError> {
    Navree::app()
        .module(ConfigModule::for_root(ConfigSources::defaults()))
        .module(HttpModule::from_config())
        .module(GreetingModule)
        .run()
}
```

You give up the prelude and the single version to keep in step, so the facade with `default-features = false` is usually the better way to build a small app. Depending on one crate directly makes sense for a library that extends one module, such as a new cache store or authentication strategy: it then depends only on the crates it extends.
