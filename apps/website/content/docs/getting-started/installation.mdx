Navree is a Rust framework, so you need a Rust toolchain and the `navree` command-line tool. The CLI creates applications, generates code and runs the development loop. Your application is an ordinary Cargo package that depends on the `navree` crate.

## Requirements

| What | Version | Why |
|---|---|---|
| Rust | 1.95 or newer | Navree uses edition 2024. Install it with [rustup](https://rustup.rs). |
| A C compiler | the one your Rust toolchain links with | The `navree` tool and any build with the `sqlite` feature compile SQLite from source (the bundled `libsqlite3-sys`); a PostgreSQL or MySQL build of your app compiles none (its `cargo test` does, because the tests run on SQLite files). On Windows, a C compiler means the MSVC build tools. |
| `rustfmt` | any | Optional. When it is installed, the generators format the code they write. |
| Docker or Podman | Docker with Compose v2, or Podman with a compose provider | Runs the app's database, TimescaleDB, with `navree dock up` ([Dock](/docs/tools/dock/)). Not needed for an app made with `--database sqlite`. |
| Node.js and npm | Node.js 20.9 or newer | Only for the optional Next.js front end (`navree new --ui next`). |

You don't need OpenSSL, CMake or NASM: TLS is rustls with the `ring` provider everywhere. You don't need to install a database server either: new apps use [TimescaleDB](/docs/database/timescaledb/), Navree's default database, and Dock runs it in a container. `navree new --database sqlite` makes an app that needs nothing at all (see [Database: getting started](/docs/database/getting-started/)).

## Installing the CLI

<Callout type="note" title="Navree is not on crates.io yet">

The 0.1 crates haven't been published, so `cargo install navree-cli` doesn't work yet. Until they are, install the CLI from the Git repository. Once they're published, `cargo install navree-cli` will be all you need.

</Callout>

<Tabs>
<Tab label="From Git">

```sh
cargo install --git https://github.com/NavreeHQ/navree navree-cli
```

Cargo builds the `navree` binary from the repository and puts it in `~/.cargo/bin`.

</Tab>
<Tab label="From a clone">

```sh
git clone https://github.com/NavreeHQ/navree
cargo install --path navree/crates/navree-cli
```

Use a clone when you want to pick the Navree version your apps build against, or to work on Navree itself.

</Tab>
</Tabs>

Check that it works:

```sh
navree --version
```

```text
navree 0.1.0
```

### Where new apps get Navree from

The CLI doesn't depend on the framework; it writes the dependency into your app's `Cargo.toml`. `navree new` picks it like this:

1. With `--navree-path <path>`, the Navree checkout at that path (the repository, or its `crates/navree` directory).
2. Otherwise, the checkout the CLI was built from, when it still exists. After `cargo install --path`, that is your clone. After `cargo install --git`, it is Cargo's own copy of the repository under `~/.cargo/git/checkouts`.
3. Otherwise, the published crate: `navree = "0.1.0"`.

Until the crates are published, the third case fails to build. For an app you plan to keep, clone the repository and either install the CLI from the clone or pass `--navree-path`. Cargo's Git checkouts are a cache that Cargo can clean up.

### Adding Navree to an existing project

To use Navree in a Cargo package you already have, add it from the Git repository:

```sh
cargo add --git https://github.com/NavreeHQ/navree navree
```

This adds a Git dependency with every module, since the `full` feature is on by default. No database driver is on by default, so turn on the one you use with `--features`: `postgres` (TimescaleDB and PostgreSQL), `mysql` (MySQL and MariaDB) or `sqlite` (a file, nothing to install; it also compiles the bundled SQLite library):

```sh
cargo add --git https://github.com/NavreeHQ/navree navree --features postgres
```

serde's derive macros name their own crate, so add `serde` too (the ORM's `#[derive(Model)]` and the validation derive `#[derive(Validate)]` come with `navree`); a new app's `Cargo.toml` shows the versions and features.

## Creating an application

`navree new` creates an app in a new directory:

```sh
navree new blog
```

```text
Created blog in /home/you/code/blog
It depends on navree at /home/you/code/navree/crates/navree.

Next steps:
  cd blog
  navree dock up             # TimescaleDB on 127.0.0.1:5432
  navree key:generate        # then set APP_KEY in .env
  navree dev                 # http://127.0.0.1:8080/api/docs
```

The name must start with a lower-case letter and use lower-case letters and digits separated by single `-` or `_`; Rust keywords and names such as `std`, `test` and `navree` are refused. The directory must not exist, or must be empty. `navree new` doesn't run Cargo or `git init`.

The app is complete and working: a root module with every common platform module configured, JWT authentication at `/api/auth/*`, roles and abilities, an example `users` module, OpenAPI docs and tests. [Directory structure](/docs/getting-started/directory-structure/) walks through every file.

### Options

| Option | Default | What it does |
|---|---|---|
| `--kit <saas\|api\|micro>` | none | Creates the app from a [starter kit](/docs/getting-started/starter-kits/): a SaaS app with a Next.js front end, an API or a microservice. |
| `--ui next` | `--ui none` | Also creates a Next.js front end in `web/`. Its server is a backend-for-frontend: it calls the API and keeps the tokens in httpOnly cookies, so the browser never sees them. With a kit, only `saas` takes it (its front end is Next.js already); `api` and `micro` have no front end. |
| `--database <db>` | `timescaledb` | The database: `timescaledb` (PostgreSQL with hypertables, run by `navree dock up`), `postgres` (plain PostgreSQL, run by `navree dock up` too), `mysql` (MySQL or MariaDB, on a server of yours) or `sqlite` (a file in `storage/`, nothing to install). It sets `database.url`, the driver feature of the `navree` dependency (`postgres`, `mysql` or `sqlite`: only the driver you chose is compiled into the app) and, for the first two, `dock.toml`. Tests of every app run on SQLite files, so `navree new` also turns `sqlite` on in the app's `[dev-dependencies]`. The kits run on `timescaledb` or `postgres`. |
| `--navree-path <path>` | the checkout the CLI was built from | Depends on the Navree checkout at `<path>`: the repository or its `crates/navree`. |

```sh
navree new blog --ui next --navree-path ~/code/navree
```

### Starting from a kit

A [starter kit](/docs/getting-started/starter-kits/) gives you a production-ready app instead of a blank one. The `saas` kit comes with a Next.js and shadcn/ui front end, sign-in, workspaces, billing, settings and an admin panel; `api` is API-only; `micro` is a microservice:

```sh
navree new acme --kit saas
```

## Local services with Dock

A new app runs on TimescaleDB, and its `dock.toml` tells [Dock](/docs/tools/dock/) to run it in a container (Docker or Podman). Start it before anything that boots the app, `navree key:generate` included:

```sh
cd blog
navree dock up
```

When your app also uses Redis, Meilisearch, Mailpit, MinIO or NATS, `navree dock:add <service>` adds the service to `dock.toml`, and the same command starts them all. `navree dev` and the app commands the CLI runs get their settings, the database URL included.

## Running the application

With the database running, generate an application key. It encrypts data and signs tokens; without it, every restart signs every user out.

```sh
navree key:generate
```

```text
base64:G60q3lWREHaFECJUwNhN58ArvmrSl0sptSaOEWgeBLk=
```

The first run compiles the framework, which takes a few minutes; later builds are incremental. The command boots the app, so log lines may appear before the key. Paste the key into `.env`:

```env title=".env"
APP_KEY=base64:G60q3lWREHaFECJUwNhN58ArvmrSl0sptSaOEWgeBLk=
```

Then start the development server:

```sh
navree dev
```

`navree dev` builds the app, starts its `serve` command and watches the code. When a file in `src/`, `config/` or `migrations/` changes, or `Cargo.toml`, `.env` or `build.rs` does, it rebuilds and restarts the server. If a build fails, the previous build keeps serving. With a `web/` front end it also runs `npm run dev` there (or `pnpm`/`yarn`, chosen by the lockfile).

The API listens on `http://127.0.0.1:8080`. Open `http://127.0.0.1:8080/api/docs` for the generated API reference, or check the health endpoint:

```sh
curl http://127.0.0.1:8080/health/live
```

```json
{"status":"up"}
```

### Dev server options

| Option | Default | What it does |
|---|---|---|
| `--debounce-ms <ms>` | `300` | How long files must be quiet before a rebuild. |
| `--no-web` | off | Doesn't start the front end's dev server. |
| `-- <args>` | none | Arguments for the app's `serve` command, such as `-- --addr 0.0.0.0:8080`. |

<Callout type="note" title="Two limits of `navree dev`">

The listening socket isn't kept open across restarts, so requests fail for the moment the server restarts. If `navree dev` itself is killed forcibly, the server it started keeps running; stop it by hand.

</Callout>

## Running the app's own commands

Every command other than `new`, `make:*` and `dev` belongs to your app's binary. `navree <command>` runs `cargo run --quiet -- <command>` in the app, so these are the same:

```sh
navree migrate
cargo run --quiet -- migrate
```

`navree list` prints every command your app has. Don't use `navree help` for that: it prints the CLI's own help. Your app's commands are covered in [Console commands and the CLI](/docs/digging-deeper/cli/).
