This tutorial builds **Planner**, a small JSON API for to-do lists. People sign up, sign in, create tasks and tick them off, and nobody can see or change anyone else's tasks. Along the way you use the generators, write a migration and a model, validate input, protect routes with access attributes, test the API with real users, and draw the task list in a browser with Navree UI.

Every command and file that builds the API comes from a real run of the CLI, and the finished API passes its tests and `cargo clippy -- -D warnings`. The last step adds a screen on top of it.

## Before you start

You need Rust 1.95 or newer and the `navree` CLI. [Installation](/docs/getting-started/installation/) covers both. A new app runs on TimescaleDB, which `navree dock up` starts in a container, so you also need Docker or Podman; to follow this tutorial with nothing else installed, create the app with `navree new planner --database sqlite` and skip `navree dock up` below. The commands use a POSIX shell; on Windows, run them in Git Bash or WSL, or adapt the `curl` quoting for PowerShell.

## Create the app

```sh
navree new planner
cd planner
navree dock up
navree key:generate
```

`navree new` writes the app; [Directory structure](/docs/getting-started/directory-structure/) explains each file. `navree dock up` starts the app's database. `navree key:generate` compiles the app (a few minutes the first time) and prints a key. Put it in `.env`:

```env title=".env"
APP_KEY=base64:G60q3lWREHaFECJUwNhN58ArvmrSl0sptSaOEWgeBLk=
```

The app already has accounts: `AuthModule` serves `/api/auth/register`, `/api/auth/login` and the rest, and stores users in its own `users` table. You add the tasks.

The module's files:

| File | What it holds |
|---|---|
| `mod.rs` | `TasksModule`: its providers, controller, the import that registers `Task` with the access module, and its migrations |
| `controller.rs` | `TaskController`: five routes under `/api/v1/tasks`, each with an access check |
| `service.rs` | `TaskService`: listing, creating, updating and deleting, in the request's unit of work |
| `entity.rs` | `Task`, the ORM model of the `tasks` table, which is also the access subject |
| `dto.rs` | The request bodies and their validation rules |
| `migrations/` | The migration that creates the `tasks` table |
| `tests/mod.rs` | Tests that boot the module on a fresh SQLite database |

A generated resource has a `name` column. A task needs a `title` and a `done` flag, so the next sections change the migration, the model, the request bodies and the service.

## Define the table

Open the migration and replace the `name` column with `title` and `done`:

```rust title="src/modules/tasks/migrations/m20261026_081038_create_tasks_table.rs"
schema
    .create("tasks", |t| {
        t.uuid_primary();
        t.uuid("owner_id").nullable().index();
        t.string("name"); // [!code --]
        t.string("title"); // [!code ++]
        t.boolean("done").default(false); // [!code ++]
        t.timestamp_tz("created_at");
        t.timestamp_tz("updated_at");
    })
    .await
```

Migrations are written with the [schema builder](/docs/database/schema-builder/), which writes the SQL for whichever database the app runs on: TimescaleDB or PostgreSQL, MySQL, or SQLite (the tests use SQLite); MariaDB is [untested](/docs/database/mysql/). Each module owns a migration set (`MigrationSet::new("tasks")`), and `navree migrate` runs every module's set in dependency order. [Migrations](/docs/database/migrations/) covers the rest.

## Update the model

The model is the Rust shape of a row. It is also what the API returns, since the generated routes serialize it as it is. `#[derive(Model)]` generates the queries and the typed columns (`Task::TITLE`), and `subject` makes `Task` the access subject: rules call it `Task` and permissions start with `tasks.`:

```rust title="src/modules/tasks/entity.rs"
#[derive(Model, Clone, Debug, Default, PartialEq, Eq, Serialize)]
#[model(table = "tasks", timestamps, subject)]
pub struct Task {
    /// A UUID v7, generated when the record is created, so ids sort by
    /// creation time.
    pub id: Uuid,
    /// The user who created it (abilities can test `owner_id`).
    pub owner_id: Option<Uuid>,
    /// The name. // [!code --]
    pub name: String, // [!code --]
    /// What needs doing. // [!code ++]
    pub title: String, // [!code ++]
    /// Whether it is done. // [!code ++]
    pub done: bool, // [!code ++]
    /// When the record was created.
    pub created_at: DateTime<Utc>,
    /// When the record last changed.
    pub updated_at: DateTime<Utc>,
}
```

The ORM generates the key and fills `created_at` and `updated_at` when it creates or saves a record, so the service never sets them. See [models](/docs/orm/models/).

## Validate the input

Request bodies are plain structs with `#[derive(Validate)]` rules. The `Valid` extractor checks them before the handler runs. Replace `dto.rs`:

```rust title="src/modules/tasks/dto.rs"
//! Request bodies of the tasks API, with their validation rules
//! (checked by the `Valid` extractor before the handler runs).

use navree::validation::Validate;
use serde::Deserialize;

/// The body of `POST /api/v1/tasks`.
#[derive(Debug, Deserialize, Validate)]
pub struct CreateTask {
    /// 1 to 200 characters.
    #[validate(length(min = 1, max = 200))]
    pub title: String,
}

/// The body of `PATCH /api/v1/tasks/{id}`: only the fields present change.
#[derive(Debug, Deserialize, Validate)]
pub struct UpdateTask {
    /// 1 to 200 characters.
    #[validate(length(min = 1, max = 200))]
    pub title: Option<String>,
    /// Marks the task done or not done.
    #[validate(skip)]
    pub done: Option<bool>,
}

impl UpdateTask {
    /// The fields this update changes, for field-level ability checks.
    pub fn changed_fields(&self) -> Vec<&'static str> {
        let mut fields = Vec::new();
        if self.title.is_some() {
            fields.push("title");
        }
        if self.done.is_some() {
            fields.push("done");
        }
        fields
    }
}
```

Every field needs a rule, so `done` says `#[validate(skip)]`; serde already guarantees it is a boolean. `changed_fields` feeds field-level access rules, which you can add later without touching the controller. [Validation](/docs/basics/validation/) lists the rules and the error format.

## Write the service

The service does the work. Change the two methods that set columns:

```rust title="src/modules/tasks/service.rs"
/// Creates a task owned by the acting user. The ORM generates the id
/// (a UUID v7) and sets the timestamps.
pub async fn create(&self, uow: &Uow, input: CreateTask) -> Result<Record<Task>, OrmError> {
    Task::create(
        uow,
        Task {
            owner_id: uow.actor(),
            name: input.name, // [!code --]
            title: input.title, // [!code ++]
            ..Task::default()
        },
    )
    .await
}

/// Applies the fields present in `input`.
pub async fn update(
    &self,
    uow: &Uow,
    mut task: Record<Task>,
    input: UpdateTask,
) -> Result<Record<Task>, OrmError> {
    if let Some(name) = input.name { // [!code --]
        task.name = name; // [!code --]
    } // [!code --]
    if let Some(title) = input.title { // [!code ++]
        task.title = title; // [!code ++]
    } // [!code ++]
    if let Some(done) = input.done { // [!code ++]
        task.done = done; // [!code ++]
    } // [!code ++]
    // Writes only the changed columns, sets `updated_at` and records the
    // change.
    task.save(uow).await?;
    Ok(task)
}
```

`Uow` is the request's unit of work: a transaction that opens on first use and commits when the response status is below 400, or rolls back otherwise. `uow.actor()` is the signed-in user's id, so every task records its owner. `create` and `save` write through the unit of work and record a change event for each write, which the audit log and change observers receive at commit; `save` writes only the columns that changed. See [The unit of work](/docs/database/unit-of-work/).

## Protect the routes

The controller needs no changes. Here is what the generator wrote:

```rust title="src/modules/tasks/controller.rs"
#[controller("/tasks", version = "1")]
impl TaskController {
    /// Lists the tasks the user may read, newest first
    /// (`?page=2&per_page=50`).
    #[get("/")]
    #[can(Read, Task)]
    #[api(summary = "List tasks", tag = "Task")]
    async fn index(
        &self,
        uow: Uow,
        scope: Accessible<Task, Read>,
        page: PageQuery,
    ) -> Result<Page<Record<Task>>> {
        Ok(self.tasks.list(&uow, scope, page).await?)
    }

    /// Creates a task owned by the caller.
    #[post("/")]
    #[can(Create, Task)]
    #[api(summary = "Create a task", tag = "Task", status = 201)]
    async fn store(
        &self,
        uow: Uow,
        Valid(Json(input)): Valid<Json<CreateTask>>,
    ) -> Result<Created<Record<Task>>> {
        let task = self.tasks.create(&uow, input).await?;
        Ok(Created(format!("/api/v1/tasks/{}", task.id), task))
    }

    /// Updates the fields present in the body.
    #[patch("/{id}")]
    #[can(Update, Task, from = "id")]
    #[api(summary = "Update a task", tag = "Task")]
    async fn update(
        &self,
        uow: Uow,
        task: Authorized<Task, Update>,
        Valid(Json(input)): Valid<Json<UpdateTask>>,
    ) -> Result<Json<Record<Task>>> {
        task.check_fields(&input.changed_fields())?;
        let task = self.tasks.update(&uow, task.into_inner(), input).await?;
        Ok(Json(task))
    }

    // ... show and destroy
}
```

- `#[controller("/tasks", version = "1")]` mounts the routes at `/api/v1/tasks`: the `http.api_prefix`, the version, then the path.
- `#[can(Create, Task)]` lets the request through only if the caller's abilities allow creating a `Task`. A guest gets 401 and a signed-in user without the ability gets 403.
- `#[can(Update, Task, from = "id")]` loads the task named by the `{id}` path parameter, checks the ability against that record, and hands it to the handler as `Authorized<Task, Update>`. A missing task is a 404.
- `Accessible<Task, Read>` turns the same rules into a SQL filter, so the list holds only the tasks the user may read.

Routes are deny-by-default: a route without `#[public]`, `#[authenticated]`, `#[roles]`, `#[permissions]` or `#[can]` doesn't compile. [Access control on routes](/docs/basics/access-control/) lists every attribute.

## Decide who may do what

The `#[can]` checks consult the user's abilities. Right now nobody has any on `Task`, so every task route answers 403. Generate a policy:

```sh
navree make:policy tasks task
```

```text
  created  src/modules/tasks/policies/task.rs
  created  src/modules/tasks/policies/mod.rs
  updated  src/modules/tasks/mod.rs
  updated  src/abilities.rs
```

The generator also calls the policy from the app's abilities function:

```rust title="src/abilities.rs" {3}
    ctx.grant_permissions(rules);
    // Module policies (`navree make:policy` adds them above the marker).
    crate::modules::tasks::policies::task::define(ctx, rules);
    // navree:policies
```

Now write the rules: any signed-in user may create tasks, and may read, update and delete their own.

```rust title="src/modules/tasks/policies/task.rs"
//! Abilities on `Task`, added to every user's rules by the app's
//! abilities function (`src/abilities.rs`).

use navree::access::{AbilityCtx, CREATE, DELETE, READ, Rules, UPDATE, field};

/// The rules on `Task` for one user (or guest). Rules and conditions
/// name database columns; later rules win.
pub fn define(ctx: &AbilityCtx, rules: &mut Rules) {
    let Some(user) = &ctx.user else {
        return;
    };
    rules.can(CREATE, "Task");
    for action in [READ, UPDATE, DELETE] {
        rules
            .can(action, "Task")
            .when(field("owner_id").eq(user.id));
    }
}
```

Each rule allows an action on a subject, optionally under conditions on the record's columns. `owner_id` is a column, so the same condition checks a single task and filters the list in SQL. Users with the `admin` role pass every check (`super_admin_role` in `src/app.rs`). [Authorization](/docs/security/authorization/) covers roles, permissions and field rules.

## Update the module's tests

The generator's tests in `src/modules/tasks/tests/mod.rs` still send and check `name`. Replace every `name` in that file with `title`: the JSON bodies, the `assert_json_path` paths (`data.0.name` becomes `data.0.title`) and `assert_validation_error("name")`.

These tests boot only the tasks module, with `acting_as(principal(id))` standing in for a signed-in user and their own test abilities, so they stay fast and focused. [Testing](/docs/testing/getting-started/) explains `TestApp`.

## Write a feature test

Now test the whole app the way a client uses it: real sign-ups, real bearer tokens and the real abilities. Create `tests/tasks.rs`:

```rust title="tests/tasks.rs"
//! The tasks API end to end: real accounts, real access tokens.

use navree::config::ConfigSources;
use navree::crypto::generate_key;
use navree::testing::{TempDirGuard, TestApp, temp_sqlite_url};
use serde_json::{Value, json};

/// The whole app on a fresh database, with fast password hashing.
async fn app() -> (TestApp, TempDirGuard) {
    let (url, guard) = temp_sqlite_url();
    let sources = ConfigSources::new()
        .set("app.key", generate_key())
        .set("database.url", url)
        .set("database.migrate_on_boot", true)
        .set("http.per_ip_rate_limit", Value::Null)
        .set("mail.transport", "array")
        .set("observe.metrics", false)
        .set("logbook.enabled", false)
        .set("hashing.memory_kib", 1024)
        .set("hashing.iterations", 1);
    let app = TestApp::from_builder(planner::app(sources)).await;
    (app, guard)
}

/// Registers an account and returns its access token.
async fn sign_up(app: &TestApp, email: &str) -> String {
    let body = app
        .client()
        .post("/api/auth/register")
        .json(&json!({ "name": "Ada", "email": email, "password": "correct horse" }))
        .send()
        .await
        .assert_status(201)
        .json_value();
    body["access_token"].as_str().unwrap().to_owned()
}

#[tokio::test]
async fn guests_cannot_list_tasks() {
    let (app, _guard) = app().await;
    app.client()
        .get("/api/v1/tasks")
        .send()
        .await
        .assert_status(401);
}

#[tokio::test]
async fn users_manage_their_own_tasks() {
    let (app, _guard) = app().await;
    let token = sign_up(&app, "ada@example.com").await;
    let client = app.client();

    let task = client
        .post("/api/v1/tasks")
        .bearer(&token)
        .json(&json!({ "title": "Write the docs" }))
        .send()
        .await
        .assert_status(201)
        .assert_json_path("done", json!(false))
        .json_value();
    let path = format!("/api/v1/tasks/{}", task["id"].as_str().unwrap());

    client
        .patch(&path)
        .bearer(&token)
        .json(&json!({ "done": true }))
        .send()
        .await
        .assert_status(200)
        .assert_json_path("done", json!(true));
    client
        .get("/api/v1/tasks")
        .bearer(&token)
        .send()
        .await
        .assert_status(200)
        .assert_json_path("meta.total", json!(1))
        .assert_json_path("data.0.title", json!("Write the docs"));
}

#[tokio::test]
async fn other_users_cannot_see_or_change_them() {
    let (app, _guard) = app().await;
    let ada = sign_up(&app, "ada@example.com").await;
    let grace = sign_up(&app, "grace@example.com").await;
    let client = app.client();

    let task = client
        .post("/api/v1/tasks")
        .bearer(&ada)
        .json(&json!({ "title": "Private" }))
        .send()
        .await
        .assert_status(201)
        .json_value();
    let path = format!("/api/v1/tasks/{}", task["id"].as_str().unwrap());

    client
        .get("/api/v1/tasks")
        .bearer(&grace)
        .send()
        .await
        .assert_json_path("meta.total", json!(0));
    client
        .get(&path)
        .bearer(&grace)
        .send()
        .await
        .assert_status(403);
    client
        .delete(&path)
        .bearer(&grace)
        .send()
        .await
        .assert_status(403);
}

#[tokio::test]
async fn titles_are_validated() {
    let (app, _guard) = app().await;
    let token = sign_up(&app, "ada@example.com").await;
    app.client()
        .post("/api/v1/tasks")
        .bearer(&token)
        .json(&json!({ "title": "" }))
        .send()
        .await
        .assert_validation_error("title");
}
```

A few things make this test fast and hermetic:

- `ConfigSources::new()` starts empty, so the test never reads `.env`, `config/app.toml` or your environment. Each `.set` supplies a setting the app needs.
- `temp_sqlite_url()` gives each test its own SQLite file, deleted when the `TempDirGuard` drops.
- `logbook.enabled` set to `false` keeps [Logbook](/docs/tools/logbook/), which is on in debug builds, out of the tests.
- `hashing.memory_kib` and `hashing.iterations` make Argon2id cheap. Keep the defaults in production.
- `http.per_ip_rate_limit` set to null turns off the 600-requests-a-minute limit, which every in-process request would share.
- `TestApp::from_builder(planner::app(sources))` boots exactly what `main` boots, and the client calls it in-process, without a network socket.

## Draw the tasks with Navree UI

The API answers clients that send a bearer token. A browser can show the same tasks too: [Navree UI](/docs/ui/overview/) draws a page on the server, from the same service and under the same rules. This step adds the page and the sign-in a browser needs.

Three modules go beside `AuthModule` in `src/app.rs`. `SessionModule` keeps a browser signed in on a cookie, `UiModule` serves the toolkit, and `AuthPages` draws the sign-in pages on top of `AuthModule`:

```rust title="src/app.rs"
use navree::auth::AuthPages; // [!code ++]
use navree::session::SessionModule; // [!code ++]
use navree::ui::UiModule; // [!code ++]
```

```rust title="src/app.rs" {2-4}
        .module(AuthModule::from_config())
        .module(SessionModule::from_config())
        .module(UiModule::from_config())
        .module(AuthPages::new().app_name("Planner"))
```

Then write the page. It is a controller like the one the generator wrote, with three differences: its path starts with `!`, which leaves out the `/api/v1` prefix; `#[page]` makes its errors pages, so a guest gets a page with a button to sign in instead of JSON; and it returns a `View`. Create `src/modules/tasks/pages.rs`:

```rust title="src/modules/tasks/pages.rs"
//! The tasks as a page: the same service and the same rules as the JSON API.

use std::sync::Arc;

use navree::access::{Accessible, Read};
use navree::db::{PageQuery, Uow};
use navree::http::Result;
use navree::ui::{Badge, Card, Node, Row, Stack, Text, View};
use navree::{controller, injectable};

use super::entity::Task;
use super::service::TaskService;

#[injectable]
pub struct TaskPages {
    tasks: Arc<TaskService>,
}

#[controller("!/tasks")]
#[page]
impl TaskPages {
    /// `GET /tasks`: the tasks the signed-in user may read, newest first.
    #[get("/")]
    #[can(Read, Task)]
    async fn index(
        &self,
        uow: Uow,
        scope: Accessible<Task, Read>,
        page: PageQuery,
    ) -> Result<View> {
        let tasks = self.tasks.list(&uow, scope, page).await?;
        let rows: Vec<Node> = tasks
            .data
            .iter()
            .map(|task| {
                Row::gap(3)
                    .children((
                        Badge::new(if task.done { "Done" } else { "To do" }),
                        Text::new(task.title.clone()),
                    ))
                    .into()
            })
            .collect();
        Ok(View::new("Tasks")
            .body(Card::titled("Your tasks").body(Stack::gap(3).children(rows))))
    }
}
```

`TaskService::list` is the method the JSON route calls, and `Accessible<Task, Read>` is the same SQL filter, so the page lists the signed-in user's own tasks and no one else's. Add the controller to the module:

```rust title="src/modules/tasks/mod.rs"
mod pages; // [!code ++]
pub use pages::TaskPages; // [!code ++]

#[module(
    // ...
    controllers = [TaskController, TaskPages], // [!code ++]
)]
```

Start the app with `navree dev` and open `http://127.0.0.1:8080/tasks`. You are not signed in, so the page answers 401 with a button to the sign-in page. Sign in with the account you registered above (`ada@example.com` and `correct horse`), and the browser comes back to `/tasks` with its task list:

```text
To do   Write the docs
```

Tick the task off with the `PATCH` call from [Try it](#try-it) and reload: the badge says Done. The page is plain on purpose. The [app shell](/docs/ui/app-shell/) adds a sidebar and a top bar, [DataTable](/docs/ui/data-table/) adds search, filters and pages, and [forms](/docs/ui/forms/) add a page that creates a task.
