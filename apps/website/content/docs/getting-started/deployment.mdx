A Navree app deploys as one binary. The same executable serves HTTP, runs queue workers, runs the scheduler and migrates the database; you pick the job with its first argument. This page covers building that binary, the settings production needs, the processes to run, and putting the app behind a reverse proxy with health checks.

The examples use Linux with nginx and systemd because they are common. Navree doesn't depend on either: any reverse proxy that forwards HTTP and any process manager that runs a command and sends it a stop signal will do.

## Deploying with Harbor

[Harbor](/docs/tools/harbor/) does everything on this page for you. `navree harbor:provision` prepares Ubuntu servers over SSH for the roles you give them: a firewall, Caddy with TLS and systemd units for the web server, the queue workers and the scheduler, plus PostgreSQL and Redis on the servers with those roles. `navree deploy` ships a release and switches to it atomically once its health check passes, and `navree deploy:rollback` goes back to the previous one. Servers, their roles and the encrypted environment secrets live in `harbor.toml`. `navree new` writes the key that encrypts them to `harbor.key`, which stays out of Git, for the apps that ship a `harbor.toml` (the starter kits).

A load balancer in front of Harbor's Caddy goes in `deploy.trusted_proxies` (addresses or CIDR ranges): Caddy keeps the balancer's `X-Forwarded-For`, and `navree deploy` sets the app's `http.trusted_proxies` to loopback followed by the same addresses.

```sh
navree harbor:provision
navree deploy
```

The rest of this page explains what a deployment involves, for when you run your own servers, containers or tooling.

## Building a release binary

```sh
cargo build --release
```

The binary is `target/release/<package>`, for example `target/release/planner` (`planner.exe` on Windows). Build it on the platform you deploy to, or cross-compile for it. TLS uses rustls, and an app built with the `sqlite` feature has SQLite compiled in, so the binary doesn't need OpenSSL or a SQLite library at runtime. A PostgreSQL or MySQL build compiles no SQLite at all.

A release build changes two defaults: logs are written as JSON lines instead of the pretty format, and templates are read once instead of reloaded when they change. See [Configuration: environments](/docs/getting-started/configuration/#environments).

If you want more speed from the binary at the cost of longer builds, tune the release profile in your `Cargo.toml`. The build behind Navree's [performance](/performance/) measurements uses these settings:

```toml title="Cargo.toml"
[profile.release]
lto = "thin"
codegen-units = 1
```

<Callout type="note" title="Until Navree is on crates.io">

A new app depends on a local Navree checkout by path (see [Installation](/docs/getting-started/installation/#where-new-apps-get-navree-from)). Whatever builds your release, such as a CI job or a container build, needs that checkout at the same path, or a `navree` dependency pointing at the Git repository instead.

</Callout>

## What to copy to the server

The binary reads `.env` and `config/app.toml` from its **working directory**, and keeps runtime data in `storage/` by default. A deployment directory looks like this:

<FileTree title="/srv/planner/">{`
planner             # the release binary
config/
  app.toml          # copied from the repository
storage/            # writable by the app's user
`}</FileTree>

Copy `config/app.toml` with the binary and run every command from this directory (systemd's `WorkingDirectory=`). Template files under `resources/views/`, if your app uses them, go here too. Templates generated by `make:mail` are compiled into the binary.

## Production settings

Production settings come from environment variables. They override `config/app.toml`, keep secrets out of the repository, and work the same for every process.

```env title="/etc/planner/planner.env"
# The application key: the same one for every process of the app.
APP_KEY=base64:G60q3lWREHaFECJUwNhN58ArvmrSl0sptSaOEWgeBLk=

# Listen on loopback only; nginx is the public entry point.
APP_HTTP__ADDR=127.0.0.1:8080
# nginx runs on this machine: trust its X-Forwarded-For.
APP_HTTP__TRUSTED_PROXIES=127.0.0.1,::1

# Run migrations as a deploy step, not at every boot.
APP_DATABASE__MIGRATE_ON_BOOT=false

# The public URL, for links in mail.
APP_APP__URL=https://planner.example.com

APP_MAIL__TRANSPORT=smtps://user:password@smtp.example.com:465
APP_MAIL__FROM="Planner <hello@example.com>"

# Require a bearer token on GET /metrics.
APP_OBSERVE__METRICS_TOKEN=a-long-random-string
```

Check these before the first deploy:

| Setting | Why |
|---|---|
| `APP_KEY` | Without it, JWTs and signed URLs use a random key per process, so every restart invalidates the access tokens already issued, and encryption fails. Every process needs the same key. See [The application key](/docs/getting-started/configuration/#the-application-key). |
| `database.migrate_on_boot` | New apps set it to `true` in `config/app.toml`. In production, run `migrate` as a deploy step instead, so a failed migration stops the deploy, not the server. |
| `database.url` | A new app's `config/app.toml` sets a TimescaleDB URL for development, and the environment variable overrides it. Left out altogether, it is `sqlite://storage/app.db?mode=rwc`, which needs the `sqlite` feature: an app built without the driver of its URL stops at boot with a message naming the feature. Build with `postgres` (TimescaleDB and PostgreSQL) or `mysql`. See [Database: getting started](/docs/database/getting-started/). |
| `http.addr` | `127.0.0.1:8080` by default. Use `0.0.0.0:8080` when the proxy runs on another host or in another container. |
| `http.trusted_proxies` | Without it, behind a proxy every request seems to come from the proxy's address, so the per-IP rate limit (600 requests a minute by default) and the login throttle apply to all your users together, and the proxy's connections count against `http.server.max_connections_per_ip`. |
| `app.url` | Absolute links in mail, such as email verification, use it. Navree doesn't read `X-Forwarded-Proto` or `Host` to build URLs. |
| `observe.metrics_token` | `GET /metrics` is public by default. Set a token, or block the path at the proxy. |
| `http.server.max_connections` | 10,000 at once by default, WebSockets included. Keep it below the process's open-file limit, and raise both for an app with many sockets. See [Connection limits](#connection-limits). |

Keep the environment file readable only by root and the app's user: it holds the application key and the passwords. Navree never logs them; `Config`'s debug output masks secret-looking keys and URL passwords.

## The commands an app ships

The binary runs one command and exits, except for the long-running ones. Every command except `check`, `introspect`, `list` and `help` boots the app first, connecting to the database and, with `migrate_on_boot`, migrating it, so it needs the same configuration as the server. `planner list` prints them all; a new app has these:

| Command | What it does |
|---|---|
| `serve [--addr HOST:PORT]` | Runs the HTTP server until it gets a stop signal. Running the binary with no command does the same. |
| `queue:work [--queue a,b] [--once] [--stop-when-empty] [--max-jobs N]` | Runs queued jobs until it gets a stop signal. |
| `queue:failed`, `queue:retry <id or all>`, `queue:flush` | Lists, retries or deletes failed jobs. |
| `migrate` | Runs every pending migration. |
| `migrate:status` | Shows which migrations have run. |
| `migrate:rollback` | Rolls back the last batch. |
| `migrate:fresh [--seed]` | Drops every table and migrates again. Never run it in production. |
| `db:seed [name...]` | Runs the seeders. |
| `down [--retry SECS] [--message TEXT]`, `up` | Turns [maintenance mode](/docs/digging-deeper/maintenance-mode/) on and off. |
| `cache:clear` | Empties the cache store. |
| `routes [--json]` | Lists the routes and their access rules. |
| `openapi:export [path]` | Writes the OpenAPI document to a file. |
| `access:role`, `access:grant`, `access:explain` | Creates roles, grants permissions and explains access decisions. |
| `key:generate` | Prints a new application key. |
| `check [--graph]` | Validates the module graph without starting anything. |

Modules add their own. With `ScheduleModule` in the app you get `schedule:work`, `schedule:run` and `schedule:list`, and with `AuditModule` you get `audit:prune`. A new app includes `ScheduleModule` (it schedules `model:prune` daily) but not `AuditModule`. See [Console commands and the CLI](/docs/digging-deeper/cli/).

## Processes to run

A typical deployment runs up to three long-lived processes from the same binary and configuration:

| Process | Command | Needed when |
|---|---|---|
| Web server | `planner serve` | Always. |
| Queue worker | `planner queue:work` | You queue jobs, queued mail or queued listeners. New apps use the database queue driver. |
| Scheduler | `planner schedule:work` | The app includes `ScheduleModule` and declares scheduled tasks. A new app does: it prunes models marked `prunable` daily. |

Instead of `schedule:work`, you can run `planner schedule:run` from cron every minute. Each tick of each task runs once however many schedulers share the database, so running the scheduler on several servers is safe.

All of them stop cleanly on `SIGTERM` (or Ctrl-C):

- `serve` stops accepting connections, closes connections with nothing in flight, and waits up to `http.shutdown_grace_secs` (30 seconds) for requests in flight.
- `queue:work` finishes the jobs it is running (up to `queue.workers`, 4 by default) and takes no new ones.
- Then the app waits up to 30 seconds for background tasks, and up to 30 seconds more for shutdown hooks, before it exits.

Give your process manager a stop timeout longer than that total.

If the app broadcasts over WebSockets (`RealtimeModule`), only `serve` holds the sockets. Workers and the scheduler post their broadcasts to it over HTTP: set `realtime.relay_url` (`auto` means `http.addr`) and give every process the same `APP_KEY`. See [Real-time broadcasting](/docs/digging-deeper/broadcasting/).

## Running under systemd

One unit per process. This one runs the web server:

```text title="/etc/systemd/system/planner.service"
[Unit]
Description=Planner API
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=planner
Group=planner
WorkingDirectory=/srv/planner
EnvironmentFile=/etc/planner/planner.env
ExecStart=/srv/planner/planner serve
Restart=on-failure
RestartSec=5
# Requests drain for up to 30 s, background tasks and shutdown hooks for up to 30 s each.
TimeoutStopSec=100

[Install]
WantedBy=multi-user.target
```

The queue worker's unit is the same with another description and command:

```text title="/etc/systemd/system/planner-queue.service"
[Unit]
Description=Planner queue worker
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=planner
Group=planner
WorkingDirectory=/srv/planner
EnvironmentFile=/etc/planner/planner.env
ExecStart=/srv/planner/planner queue:work
Restart=on-failure
RestartSec=5
TimeoutStopSec=100

[Install]
WantedBy=multi-user.target
```

Enable and start them:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now planner planner-queue
```

Logs go to standard output, so `journalctl -u planner` shows them, as JSON lines in a release build. To also write rotating log files, set `log.file`; see [Logging](/docs/basics/logging/).

## A deploy, step by step

<Steps>
<Step title="Build and copy">

Build the release binary and copy it and `config/app.toml` to the server, next to the running version.

</Step>
<Step title="Migrate">

Run the migrations from the deployment directory, with the production environment:

```sh
cd /srv/planner
sudo -u planner sh -c 'set -a; . /etc/planner/planner.env; set +a; ./planner migrate'
```

For a migration the running version can't work with, put the app in maintenance mode first with `./planner down`, and run `./planner up` afterwards.

</Step>
<Step title="Restart">

```sh
sudo systemctl restart planner planner-queue
```

Requests that arrive while the server restarts fail: Navree doesn't hand its listening socket over to a new process. Run two instances behind the proxy and restart them one at a time if that matters.

</Step>
</Steps>

## Behind a reverse proxy

Navree serves plain HTTP. Put a reverse proxy in front of it to terminate TLS, and tell Navree which proxies to trust so it sees each client's real address.

This nginx server block proxies everything to the app on loopback:

```text title="/etc/nginx/sites-available/planner.conf"
server {
    listen 443 ssl;
    server_name planner.example.com;

    ssl_certificate     /etc/ssl/certs/planner.example.com.pem;
    ssl_certificate_key /etc/ssl/private/planner.example.com.key;

    # Navree's own limit is http.body_limit_bytes (2 MiB by default).
    client_max_body_size 2m;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Prometheus metrics: for your scraper, not the internet.
    location = /metrics {
        deny all;
    }

    # WebSockets, if the app uses RealtimeModule (ws://host/app/{key}).
    location /app/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_read_timeout 300s;
    }
}

server {
    listen 80;
    server_name planner.example.com;
    return 301 https://$host$request_uri;
}
```

With `APP_HTTP__TRUSTED_PROXIES=127.0.0.1,::1`, Navree takes the client's address from `X-Forwarded-For` on requests that come from nginx. It reads the header from the right and takes the first address that isn't a trusted proxy, so a client can't choose its address by sending its own `X-Forwarded-For`. Requests from any other peer are identified by the peer's own address. `trusted_proxies` accepts addresses and CIDR blocks such as `10.0.0.0/8`, which suits a load balancer with changing addresses.

`http.trust_proxy = true` trusts the headers from every peer. Use it only when nothing can reach the app except through the proxy; `trusted_proxies` is safer.

Navree sends security headers by default, including `Strict-Transport-Security`, which tells browsers to use HTTPS only. Serve the app over HTTPS, as above. See [CORS and security headers](/docs/basics/cors-and-security-headers/).

## Connection limits

A client can hold a connection without ever finishing a request: sending its headers a byte at a time, stopping halfway through a body, connecting and saying nothing, or asking for a response and not reading it. The server bounds all of these, with or without a proxy in front, on every listener the app opens (`http.addr`, `domains.acme.https_addr` and `grpc.addr`). The defaults are meant for production, so most apps set nothing.

| Setting | Default | What it limits |
|---|---|---|
| `http.server.header_read_timeout_ms` | `10000` | Connecting and sending a whole request head, TLS handshake apart. A client that takes longer is disconnected, however steadily it sends. On HTTP/2, a new connection has this long to open its first stream. On a keep-alive connection, the time starts at the first byte of the head. A head pipelined after a request with a body can't be seen until it's complete, so it has `idle_timeout_ms` instead. |
| `http.server.idle_timeout_ms` | `75000` | How long a connection stays open with no request in flight. HTTP/2 connections get a GOAWAY first, and nothing a client sends extends it. |
| `http.server.body_read_timeout_ms` | `20000` | How long a handler reading a request body waits on the client. A stall this long is a 408, and the connection closes. On HTTP/2 only the stream ends. |
| `http.server.body_min_bytes_per_sec` | `256` | The slowest a body may arrive, on average, so a client dripping bytes runs out of `body_read_timeout_ms` even though it never stalls for long. |
| `http.server.http2_keep_alive_interval_ms` | `30000` | How often a quiet HTTP/2 connection is pinged, which finds dead peers while a request is in flight. |
| `http.server.http2_keep_alive_timeout_ms` | `20000` | How long a client has to answer a ping before the connection closes. |
| `http.server.http2_max_concurrent_streams` | `200` | Requests open at once on one HTTP/2 connection. |
| `http.server.max_connections` | `10000` | Connections open at once, WebSockets and TLS handshakes included. |
| `http.server.max_connections_per_ip` | `256` | Connections open at once from one client address. It limits what one address can hold, not a client with many addresses. Reverse proxies you list in `http.trusted_proxies` aren't counted. |
| `http.server.max_header_bytes` | `32768` | The largest request head: the request line and headers on HTTP/1, the header list on HTTP/2, where each header also counts 32 bytes. Over it, the answer is a 431, though a client still sending when the connection closes may see a reset instead. At least 8192. |
| `http.server.max_headers` | `100` | Headers on a request. Over it, the answer is a 431 and the request never reaches your app. On HTTP/2 a browser may send each cookie as a header of its own, and each counts. |
| `http.server.write_stall_timeout_ms` | `60000` | How long a response may go without moving because the client has stopped taking it. |
| `http.server.upgraded_idle_timeout_ms` | Off | How long an upgraded connection, such as a WebSocket, may go with no bytes from its client. |

```toml title="config/app.toml"
[http.server]
idle_timeout_ms = 120000
max_connections = 50000
```

Or from the environment: `APP_HTTP__SERVER__MAX_CONNECTIONS=50000`. The time a handler takes isn't here: `http.timeout_secs` covers that.

**At the cap** new clients aren't refused: they wait, nearly all of them in the operating system's listen backlog, nothing is read from them, and they're served in turn as connections close. A burst over the cap is absorbed this way. For a client that's waiting and has sent something, the connection that has been idle the longest closes, the way it would at its idle timeout, so keep-alive connections can't keep anyone out. A connection that has only started its next request counts as idle, so that can't keep anyone out either. Each waiting client costs one connection at most, and a client that has sent nothing costs none: it has `header_read_timeout_ms` to wait, and gives way to newer clients once a good many are waiting. Connections that haven't finished a request lose their slots at the limits above, within seconds. WebSockets are the exception, below. A client still waiting when the backlog overflows, or when its own timeout runs out, gets a connection error. The log says `http.server.max_connections reached` at most once a minute.

**One address** can hold `max_connections_per_ip` connections. That limits what one address can hold: it doesn't stop a client with many addresses, which `max_connections` is then the limit for. IPv4 clients are counted per address and IPv6 clients per network, by `http.rate_limit_ipv6_prefix`, as the rate limits are. A connection over the limit is closed at once rather than queued, because the server only learns the address by accepting it. The log says `http.server.max_connections_per_ip reached` at most once a minute.

A proxy's connections all come from one address, so peers in `http.trusted_proxies` aren't counted, and with `http.trust_proxy = true` no peer is. Behind a proxy, list it, or raise this limit: it needs to be listed for the rate limits anyway, and a busy proxy that isn't hits this limit and its requests fail. The limit sees the socket's peer, so it can't tell the clients behind a proxy apart: limit those at the proxy. The default of 256 leaves room for an office sharing one address, but a large carrier NAT or a backend that isn't a proxy and opens more connections than that needs a higher limit, or `None`.

**A response on its way** isn't idle, so neither `idle_timeout_ms` nor a waiting client cuts it off, even once your handler has finished. **A response nobody reads** can't hold a connection, though. When the socket takes nothing for `write_stall_timeout_ms`, the connection closes. When an HTTP/2 client stops one response with flow control, the socket is fine, so only that stream is reset, and the rest of the connection carries on. Each byte the socket takes starts the limit over, and on HTTP/2 each 16 KiB the client takes from a response, so a slow download that keeps moving is never cut off. A client that pauses for longer loses the response, including a video player that stops reading while it's paused, and has to ask for the rest. A gRPC client that stops reading a stream that long gets the same.

**Behind a load balancer**, keep `idle_timeout_ms` above the balancer's idle timeout (often 60 seconds), so the balancer closes first and never sends a request into a connection the app is closing.

**WebSockets** are the one thing these limits don't bound by default. A WebSocket keeps its slot for as long as it's open, and no limit above ends a quiet one, because it may well be healthy and the server can't tell it from a client doing nothing. So check who may open one in the handler, and give the protocol a heartbeat that drops a peer that stops answering. To have the server close silent ones, set `upgraded_idle_timeout_ms` above that heartbeat: past it with no bytes from the client, the socket closes and the handler's read fails, so the handler must be reading. Only the client's bytes count, so the client has to answer the heartbeat: the server's own pings don't keep a silent client's socket open. On HTTP/2, a WebSocket is one stream of its connection. The timeout starts once nothing else is left on the connection, only `DATA` frames count, not keep-alive pings or the other frames that look after a connection, and a connection whose WebSockets have closed goes back to `idle_timeout_ms`. `write_stall_timeout_ms` doesn't reach an HTTP/2 WebSocket that the client holds back with flow control, because the server can't tell a write waiting for the client from a socket with nothing to say. `upgraded_idle_timeout_ms` ends one whose client has gone silent, and a handler that writes to a client it doesn't trust should put a timeout on its writes.

**A request body that isn't an upload** can opt out of the pace: `serve` puts a `navree::http::serve::BodyReadLimit` in the extensions of a request with a body, and `lift()` ends the limit for that request. Client and bidirectional streaming gRPC methods do this once a call has passed its access check.

The keys of type `Option<..>` (all but the HTTP/2 timeout and streams and the two header limits) are turned off the way [`http.per_ip_rate_limit`](/docs/basics/rate-limiting/#the-per-ip-limit) is, with `None` in code: `0` fails the boot.

## Health checks

`ObserveModule`, which new apps include, serves two probes outside the API prefix, without authentication:

| Endpoint | Answers | Use it for |
|---|---|---|
| `GET /health/live` | Always `200 {"status":"up"}` while the process serves HTTP. It runs no checks. | Liveness: restart the process when it fails. |
| `GET /health/ready` | `200` when every health check is up, `503` when one is down. Each check has 2 seconds. | Readiness: take the instance out of the load balancer while it fails. |

```sh
curl -s http://127.0.0.1:8080/health/ready
```

```json wrap
{"status":"up","checks":{"cache":{"status":"up","latency_ms":0},"database":{"status":"up","latency_ms":0}}}
```

`DatabaseModule`, `CacheModule` and `StorageModule` each register a check, and your modules can add their own. Both probes and `/metrics` keep answering during maintenance mode (`http.maintenance_except`), so an orchestrator doesn't restart instances that are down on purpose. Don't send an `Authorization` header to the probes: a present but invalid token is a 401 on every route, public ones included. [Health and metrics](/docs/digging-deeper/health-and-metrics/) has the details.

## Containers

The same rules apply in a container: the binary, `config/` in the working directory, settings from the environment, and `APP_HTTP__ADDR=0.0.0.0:8080` so the server listens outside the container. Navree's [performance](/performance/) harness runs its app in a two-stage image, building with `rust:1-bookworm` and running on `debian:bookworm-slim`; `bench/frameworks/navree/Dockerfile` is a working example. Because that app depends on Navree by path, the Dockerfile copies the repository's `crates/` into the build stage, and an app of yours needs the same until the crates are published. [Harbor](/docs/tools/harbor/) builds images for you with `navree build:image`.

## The database in production

A new app runs on [TimescaleDB](/docs/database/timescaledb/), so production wants a TimescaleDB server too: a managed TimescaleDB service, or PostgreSQL 16 to 18 with the `timescaledb` package and `shared_preload_libraries = 'timescaledb'`. Set `APP_DATABASE__URL`, create the extension in the app's database once (`CREATE EXTENSION timescaledb`, as a superuser) unless the app's database user is one, and set `APP_SCHEMA__TIMESCALEDB=require`, so a migration stops on a server without TimescaleDB instead of creating regular tables. Plain PostgreSQL works too: every migration runs there, and hypertables are regular tables, with a notice.

[Harbor](/docs/tools/harbor/)'s `postgres` role installs PostgreSQL from the PostgreSQL project's repository, without TimescaleDB. Keep `schema.timescaledb = "auto"` there, or install TimescaleDB on that server before the first deploy.

Navree's performance harness runs on PostgreSQL (the pool, the unit of work, pagination, inserts and the auth user lookup) while the test suite runs on SQLite; [what has been run on PostgreSQL](/docs/database/getting-started/#postgresql) lists the paths to try in staging first, such as the queue's `FOR UPDATE SKIP LOCKED` job reservation.

An app made with `--database sqlite` keeps its database in a file, which suits a single server: Navree opens it in WAL mode with a 5-second busy timeout, so the server, workers and scheduler on one machine can share the file. Keep `storage/` on a persistent disk and back the file up.
