title: "Directory structure"
description: "What every file of a new Navree app is for, where generated code goes, and how the framework's own repository is laid out."
---

A Navree app is an ordinary Cargo package. `navree new` gives it a conventional layout: the app root module in `src/app.rs`, one directory per feature module under `src/modules/`, settings in `config/` and `.env`, and runtime data in `storage/`. Nothing in the framework depends on these paths except the configuration files and a few defaults (the maintenance file in `storage/`, templates in `resources/views/`), all relative to the working directory; the generators expect the layout, though, and keeping to it makes apps look alike.

## A new application

This is what `navree new planner` writes:

<FileTree title="planner/">{`
.env                  # local settings and secrets (git-ignored)
.env.example          # the keys .env needs, committed
.gitignore
Cargo.toml            # the package; depends on navree
README.md
config/
  app.toml            # settings shared by every environment
src/
  main.rs             # the binary: runs the app with the default config sources
  lib.rs              # exposes app(), abilities and modules
  app.rs *            # the root module: every module, configured once
  abilities.rs        # what each user may do
  modules/
    mod.rs            # declares the feature modules
    users/            # an example feature module
      mod.rs
      controller.rs
      service.rs
      entity.rs
      dto.rs
      migrations/
        mod.rs
        m20261026_081033_create_user_profiles_table.rs
      tests/
        mod.rs
storage/
  .gitignore          # ignores everything else in storage/
tests/
  app.rs              # boots the whole app
`}</FileTree>

### The root directory

- **`Cargo.toml`** names the package and its dependencies: `navree`, plus `serde`, `sea-orm`, `sea-orm-migration` and `garde`, whose derive macros name their own crates, and `chrono`, `uuid` and `serde_json`. It ends with an empty `[workspace]` table, so the app is a workspace of its own; remove it to make the app a member of an enclosing workspace. The `[profile.dev]` settings keep debug builds quick to link and compile Argon2 with optimisations, which keeps password hashing bearable in development.
- **`.env`** holds this machine's settings and secrets, such as `APP_KEY`. `navree new` creates it from `.env.example`, and git ignores it. See [Configuration](/docs/getting-started/configuration/#the-env-file).
- **`.env.example`** lists the keys `.env` needs, without secrets. Commit it.
- **`config/app.toml`** holds the settings every environment shares: the listening address, the database URL, the log level, the mail transport and so on.
- **`README.md`** lists the everyday commands.

### `src/`

- **`main.rs`** is the binary. It calls `planner::app(ConfigSources::defaults()).run()`, which runs the command on the command line: `serve` when there is none, or `migrate`, `queue:work` and the rest. A deployed app needs only this binary and its configuration.
- **`lib.rs`** exposes `app`, `abilities` and `modules`, so tests in `tests/` can boot exactly what `main` boots.
- **`app.rs`** is the root module. It adds every module the app uses, each configured once: `ConfigModule`, `LoggerModule`, `CryptoModule`, `HttpModule`, `DatabaseModule`, `CacheModule`, `EventsModule`, `ViewModule`, `MailModule`, `QueueModule`, `ValidationModule`, `AuthModule`, `AccessModule`, `ApiModule`, `ObserveModule`, then the feature modules. Remove the platform modules you don't need, and add the others (`ScheduleModule`, `StorageModule`, `RealtimeModule`, `NotifyModule`, `AuditModule`, ...) when you do.
- **`abilities.rs`** is the function that builds each user's access rules. It grants the permissions of the user's roles, then the rules of each module's policy. See [Authorization](/docs/security/authorization/).
- **`modules/`** holds the feature modules, one directory each.

### Feature modules

A feature module keeps everything about one feature together. `navree make:module` creates one with this shape:

| File | What it holds |
|---|---|
| `mod.rs` | The module struct and its `#[module(...)]` declaration: imports, providers, controllers, exports, and a `wire` method for registrations the attribute has no key for, such as migrations |
| `controller.rs` | The controller: HTTP routes with their access attributes |
| `service.rs` | The business logic, as an injectable service |
| `entity.rs` | The SeaORM entity of the module's table |
| `dto.rs` | Request and response bodies, with validation rules |
| `migrations/` | The module's migration set; each module owns its tables |
| `tests/` | Tests that boot the module alone on a fresh database |

The example `users` module serves `GET` and `PUT /api/v1/profile`, a profile for each signed-in user. Accounts themselves come from `AuthModule`, which owns the `users` table and the `/api/auth/*` routes. Keep `users` as a model or delete it, along with its line in `app.rs` and `modules/mod.rs` and the profile test in `tests/app.rs`.

The `make:<kind>` generators add files in a directory per kind, inside the module:

| Command | Writes |
|---|---|
| `navree make:controller tasks admin` | `controllers/admin.rs` |
| `navree make:service tasks pricing` | `services/pricing.rs` |
| `navree make:entity tasks draft` | `entities/draft.rs` |
| `navree make:migration tasks add_due_date` | `migrations/m<timestamp>_add_due_date.rs` |
| `navree make:job tasks send_digest` | `jobs/send_digest.rs` |
| `navree make:event tasks task_completed` | `events/task_completed.rs` |
| `navree make:listener tasks notify_owner --event task_completed` | `listeners/notify_owner.rs` |
| `navree make:mail tasks digest` | `mail/digest.rs`, `mail/digest.html`, `mail/digest.txt` |
| `navree make:notification tasks task_due` | `notifications/task_due.rs` |
| `navree make:policy tasks task` | `policies/task.rs` |
| `navree make:command tasks prune_done` | `commands/prune_done.rs` |
| `navree make:test tasks completing` | `tests/completing.rs` |

Every generator also declares the new file's module and, where the item must be registered, adds the registration. [Console commands and the CLI](/docs/digging-deeper/cli/) covers each one.

### Generator markers

The generators never overwrite a file. To register what they create, they edit existing files only at marker comments:

| Marker | In | What the generators add above it |
|---|---|---|
| `// navree:modules` | `src/app.rs` | `.module(...)` for each new feature module |
| `// navree:wire` | each module's `mod.rs` | registrations of controllers, services, jobs, listeners, mail templates, commands and new migration sets |
| `// navree:policies` | `src/abilities.rs` | the call to each new policy |

Leave the markers in place. If one is missing, the generator prints the line to add by hand, prefixed with `next`.

### `storage/`

`storage/` holds data the app writes at runtime, and its `.gitignore` keeps it out of git:

- the SQLite database, `storage/<app>.db` by default, with its `-wal` and `-shm` files;
- `storage/framework/down`, which exists while the app is in [maintenance mode](/docs/digging-deeper/maintenance-mode/);
- log files and local disks, when you configure them (`log.file`, [File storage](/docs/digging-deeper/storage/)).

### `tests/`

`tests/app.rs` boots the whole app on a temporary database and checks that the module graph is valid, `/health/live` answers and the profile route needs a signed-in user. Add your own end-to-end tests next to it; module tests live in each module's `tests/` directory. See [Testing](/docs/testing/getting-started/).

### Other directories

These appear as you use more of Navree:

- **`resources/views/`** is where `ViewModule` looks for template files (`view.dirs`). Templates generated by `make:mail` are embedded in the binary instead.
- **`target/`** is Cargo's build output.

## With a front end

`navree new planner --ui next` adds a Next.js app in `web/`:

<FileTree title="planner/web/">{`
package.json          # next, react, react-dom; dev, build, start, typecheck
tsconfig.json
next.config.ts
.env.example          # NAVREE_API_URL, where the API listens
README.md
lib/
  bff.ts              # calls the API and keeps the tokens in httpOnly cookies
app/
  layout.tsx
  page.tsx
  login/
    page.tsx
  api/
    auth/
      login/
        route.ts      # signs in through the API, sets the cookies
      logout/
        route.ts
    [...path]/
      route.ts        # forwards every other /api call with the bearer token
`}</FileTree>

The browser only talks to the Next.js server, which talks to the API. The tokens stay in httpOnly cookies on that server, and the browser never sees them. `navree dev` starts the front end's dev server too.

## The framework repository

Navree is developed in one repository, [NavreeHQ/navree](https://github.com/NavreeHQ/navree): the framework's crates, the CLI, the agent skills, a reference application, the performance harness and this website.

<FileTree title="navree/">{`
Cargo.toml            # the workspace: crates/*, apps/crm-api, apps/crm-api/crates/*
Cargo.lock
rustfmt.toml
.cargo/
  config.toml         # sccache as the compiler wrapper
crates/
  navree/             # the facade; dependency-graph and full-stack tests
  navree-kernel/      # one crate per module...
  navree-http/
  navree-db/
  ...
  navree-cli/         # the navree binary and its templates
apps/
  crm-api/            # the reference CRM API, a Navree app
    src/
    crates/           # crm-core, crm-companies, crm-deals, crm-activities, crm-users, crm-testkit
    tests/
  crm-web/            # the CRM front end (Next.js), Vitest and Playwright
  website/            # navree.com and these docs
skills/               # the agent skills, one SKILL.md per directory
bench/                # the performance harness: SPEC.md, the load runner, results
docs/                 # product requirements, build design, plans, notes
assets/               # the logo
deploy/               # scripts that deploy navree.com
`}</FileTree>

Each framework crate has the usual `src/`, and most keep their integration tests in one binary under `tests/<name>/`, such as `crates/navree-config/tests/config/main.rs`. `crates/navree-cli/templates/` holds the templates behind `navree new` and the generators, so it is the reference for what a new app contains.

The crates form eight layers, from the kernel up to the facade and the CLI, and a test checks every dependency between them against the allowed edges. [The crate hierarchy](/docs/architecture/crate-hierarchy/) explains them, and [Contributing](/docs/prologue/contributing/) explains how to build and test the repository.
