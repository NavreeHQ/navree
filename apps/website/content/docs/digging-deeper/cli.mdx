title: "Console commands and the CLI"
description: "The `navree` CLI (`new`, every `make:*` generator, `dev`), your app's own commands (`serve`, `migrate`, `queue:work`, ...), and writing your own."
---

Navree has two command lines:

- **The `navree` CLI** creates apps, generates code and runs the development loop. It depends on no runtime crate of Navree, only on the tool crates behind `navree dock`, Harbor's commands and `navree mcp`: everything it knows about the framework is in the code it writes.
- **Your app's binary** owns the runtime commands: `serve`, `migrate`, `queue:work` and the rest, registered by the modules you use, plus your own. `navree <command>` forwards to it, so you rarely call the binary yourself.

## Installing the CLI

The CLI is the `navree-cli` crate. Navree isn't published on crates.io yet, so install it from the Git repository:

```sh
cargo install --git https://github.com/NavreeHQ/navree navree-cli
```

From a clone of the repository, `cargo install --path crates/navree-cli` does the same.

```sh
navree --help
```

## Creating an app

`navree new <name>` creates a working app in `./<name>`:

```sh
navree new blog
```

```text
Created blog in /home/ada/code/blog
It depends on navree at /home/ada/src/navree/crates/navree.

Next steps:
  cd blog
  navree dock up             # TimescaleDB on 127.0.0.1:5432
  navree key:generate        # then set APP_KEY in .env
  navree dev                 # http://127.0.0.1:8080/api/docs
```

.env.example
.gitignore
AGENTS.md                 # conventions for coding agents

  app.toml                # http, database, schema, log, mail, queue, auth, api

| Option | What it does |
|---|---|
| `--kit <saas\|api\|micro>` | Creates the app from a [starter kit](/docs/getting-started/starter-kits/) instead of the minimal app. |
| `--database <db>` | The database: `timescaledb` (the default; PostgreSQL with hypertables, run by `navree dock up`), `postgres` (plain PostgreSQL, also run by Dock), `mysql` (MySQL or MariaDB, a server of yours) or `sqlite` (a file in `storage/`). `timescale`, `postgresql` and `mariadb` are accepted as aliases. It sets `database.url`, the driver feature of the `navree` dependency (`postgres`, `mysql` or `sqlite`: only that driver is compiled into the app) and, for the first two, `dock.toml`. The tests run on SQLite, so `[dev-dependencies]` turns `sqlite` on in every app. The [starter kits](/docs/getting-started/starter-kits/) run on `timescaledb` or `postgres` and refuse the other two. |
| `--ui <next\|none>` | `next` also creates `web/`, a Next.js front end that talks to the API through its own server and keeps the tokens in httpOnly cookies, like the [CRM's](/docs/example-app/crm-tour/#the-web-app). `navree dev` starts it. Default: `none`, API only. With a kit, only `saas` has a front end (`--kit saas --ui next` is the same as `--kit saas`); the `api` and `micro` kits refuse `--ui next`. |
| `--navree-path <path>` | Depend on a local checkout (the repository or its `crates/navree`). Without it, the app gets a `path` dependency on the checkout the CLI was built from when it still exists (after `cargo install --git`, Cargo's own copy of the repository), else `navree = "1.0.0"` (the CLI's own version), which won't build until the crate is on crates.io. |

The name starts with a lower-case letter and uses lower-case letters and digits, with single `-` or `_` between words (`my-shop`). Rust keywords, Windows device names and `navree` itself are refused. `navree new` refuses a directory that exists and isn't empty, formats the generated code with `rustfmt` when it is installed, and runs `git init` (nothing is committed) unless the app is inside a repository already or Git is missing. For the starter kits, which ship a `harbor.toml`, it also writes `harbor.key` and keeps it out of Git. The app is its own Cargo workspace; remove the `[workspace]` table from its `Cargo.toml` to make it a member of an enclosing one. See [Your first app](/docs/getting-started/your-first-app/) for a walk through it.

## Generators

Run generators anywhere inside your app: the CLI finds the package from the current directory. They never overwrite a file (`refusing to overwrite` stops them before anything is written). They register what they create by adding `mod` declarations, adding a `.migration(..)` call to a module's migration set and inserting lines above marker comments:

| Marker | In | Where generators add |
|---|---|---|
| `// navree:modules` | `src/app.rs` | `.module(...)` lines for new modules |
| `// navree:wire` | a module's `wire` method | registrations: controllers, providers, jobs, listeners, templates, commands, migrations, seeders, models, agents, MCP servers and Helm resources |
| `// navree:policies` | `src/abilities.rs` | calls to new policies |

When a marker is missing (in code you wrote by hand), the generator prints the line to add as a `next` hint instead. Names are `snake_case`; anything else fails with a suggestion (`blog_posts` for `BlogPosts`). `make:model`, `make:factory`, `make:seeder` and `make:resource` also take a model's name as `Deal` or `deal`.

### make:module

`navree make:module <name>` generates a feature module and adds it to the app:

```sh
navree make:module posts --crud
```

```text
  created  src/modules/posts/mod.rs
  created  src/modules/posts/controller.rs
  created  src/modules/posts/service.rs
  created  src/modules/posts/entity.rs
  created  src/modules/posts/dto.rs
  created  src/modules/posts/migrations/mod.rs
  created  src/modules/posts/migrations/m20261026_081536_create_posts_table.rs
  created  src/modules/posts/tests/mod.rs
  updated  src/modules/mod.rs
  updated  src/app.rs
```

With `--crud`, the module serves the five JSON resource routes under `/api/v1/posts` (list, show, create, update, delete), each guarded by abilities on its model, with validated DTOs and tests. Without it, the module has one authenticated `index` route to start from. Use the plural for the name: `posts` gets the model `Post` and the table `posts`. `--path` changes the modules directory (default `src/modules`).

### Other generators

Every other generator adds one item to an existing module: `navree make:<kind> <module> <name> [--path src/modules]`.

```sh
navree make:job posts publish_post
```

```text
  created  src/modules/posts/jobs/publish_post.rs
  created  src/modules/posts/jobs/mod.rs
  updated  src/modules/posts/mod.rs
  updated  src/modules/posts/mod.rs
```

The report lists a file once per edit: here `mod.rs` gets the `pub mod jobs;` declaration and the job's registration.

| Command | Creates (in the module) | Registers |
|---|---|---|
| `make:controller posts admin` | `controllers/admin.rs`, `AdminController` | the controller, in `wire` |
| `make:service posts pricing` | `services/pricing.rs`, `PricingService` | `m.provider::<..>()`, in `wire` |
| `make:model posts Tag` | `models/tag.rs`, an [ORM model](/docs/orm/models/) for `tags`. The name may be `tag` or `Tag`. Options: `--migration` (`-m`), `--factory` (`-f`), `--seeder` (`-s`), `--controller` (`-c`), `--policy` and `--all` (`-a`) add the companions, each referring to the others; `--pivot` (`-p`) makes the table of a many-to-many between the two models its name joins (`post_tag`), and with `--all` adds a migration, a factory and a seeder only | `m.model::<..>()` and each companion's registration, in `wire`; with `--policy`, also `m.import(AccessModule::for_feature::<..>())` |
| `make:factory posts tag` | `factories/tag.rs`, a [model factory](/docs/orm/factories/) (`--model <model>` when its name differs from the model's; the model must exist) | nothing; `#[model(factory = ..)]` links it, and the command prints the line to add |
| `make:seeder posts demo_data` | `seeders/demo_data.rs`, a [seeder](/docs/database/seeding-and-factories/) named `demo_data` | the seeder, in `wire`; prints `navree db:seed demo_data` |
| `make:entity posts tag` | `entities/tag.rs`, a minimal [ORM model](/docs/orm/models/) for `tags` (an id and the two timestamps) | nothing; prints the `make:migration` to run next |
| `make:migration posts create_tags_table` | `migrations/m<timestamp>_create_tags_table.rs` | adds it to the module's migration set. A `create_<table>_table` name generates a table-creating migration; an `add_stage_to_deals` or `remove_notes_from_deals_table` name (the last `_to_`, `_from_` or `_in_` names the table) generates an alter-table one |
| `make:job posts publish_post` | `jobs/publish_post.rs`, a job named `posts.publish_post` | the job, in `wire` |
| `make:event posts post_published` | `events/post_published.rs` | nothing (events need no registration) |
| `make:listener posts notify_followers --event post_published` | `listeners/notify_followers.rs` | `listen::<PostPublished, NotifyFollowers>`, in `wire`. Without `--event`, prints the line to add |
| `make:mail posts welcome` | `mail/welcome.rs` with `welcome.html` and `welcome.txt` | the templates, in `wire` |
| `make:notification posts post_liked` | `notifications/post_liked.rs`, a database and broadcast notification | nothing |
| `make:policy posts moderation` | `policies/moderation.rs`, ability rules | a call in `src/abilities.rs` |
| `make:command posts publish_scheduled` | `commands/publish_scheduled.rs`, the command `posts:publish-scheduled` | `m.command(..)`, in `wire` |
| `make:agent posts assistant` | `agents/assistant.rs`, an [agent](/docs/ai/agents-and-tools/) `Assistant` named `posts-assistant` with one read-only tool (needs the `ai` feature) | `m.agent::<..>()`, in `wire` |
| `make:test posts publishing` | `tests/publishing.rs`, a test booting the module | declares it in `tests/mod.rs` |
| `make:mcp posts assistant` | `mcp/assistant.rs`, `AssistantMcp`, an [MCP server](/docs/ai/mcp-servers/) with one tool (`assistant_echo`) | `m.mcp_server::<..>()`, in `wire`; prints the steps it leaves to you (the `mcp` feature, `McpModule`) |

`make:listener --event` needs the event to exist (`make:event` first). The guides for each kind say what to fill in: [controllers](/docs/basics/routing/), [models](/docs/orm/models/), [migrations](/docs/database/migrations/), [jobs](/docs/digging-deeper/queues/), [events and listeners](/docs/digging-deeper/events/), [mail](/docs/digging-deeper/mail/), [notifications](/docs/digging-deeper/notifications/), [policies](/docs/security/authorization/), [tests](/docs/testing/getting-started/) and [MCP servers](/docs/ai/mcp-servers/).

## The development server

`navree dev` builds the app, runs its `serve` command, and rebuilds and restarts it when the code changes:

```sh
navree dev
navree dev --no-web -- --addr 0.0.0.0:8080
```

| Option | Default | What it does |
|---|---|---|
| `--debounce-ms <ms>` | `300` | How long the files must be quiet before a rebuild. |
| `--no-web` | | Don't start the front end in `web/`. |
| `-- <args>` | | Arguments for the app's `serve` command. |

- It watches `src/`, `config/`, `migrations/` and `crates/`, and `Cargo.toml`, `.env` and `build.rs` at the root. Template files under `resources/` aren't watched: [views reload](/docs/digging-deeper/views/#reloading-during-development) on their own.
- It runs a copy of the binary, so the next build can replace the original while the current server keeps answering, and restarts the server only once the new build succeeds. When a build fails, the previous one keeps serving and the compiler errors are shown.
- With a `web/package.json`, it also starts the front end's dev server once, with `pnpm`, `yarn` or `npm` depending on the lockfile (or on the `packageManager` field of `package.json` before a lockfile exists).

Two limits: the listening socket isn't kept across restarts, so requests fail for the moment the new server takes to start (and open WebSockets drop and reconnect), and if `navree dev` itself is killed forcibly, the server it started keeps running.

## Running your app's commands

Any command the CLI doesn't know is forwarded to your app: `navree migrate:fresh --seed` runs `cargo run --quiet -- migrate:fresh --seed` in the current directory and exits with the command's exit code. When the app has a `dock.toml`, forwarded commands and `navree dev` also get its services' settings as environment variables ([Dock](/docs/tools/dock/#how-your-app-finds-the-services)). You can also run the binary directly, which is what you do in production:

```sh
navree migrate:status
cargo run -- migrate:status        # the same, without the CLI
./target/release/blog migrate      # a release build
```

Your app's `main` hands the command line to `AppBuilder::run`:

```rust title="src/main.rs"
fn main() -> Result<(), navree::kernel::BoxError> {
    // `.env`, then `config/app.toml`, then `APP_*` environment variables.
    blog::app(ConfigSources::defaults()).run()
}
```

- With no command, it runs `serve` when a module registers it (`HttpModule` does), otherwise it prints the help.
- `help` (also `list`, `--help` and `-h`) lists every command, `check [--graph]` validates the module graph, and `introspect --json` prints the module graph and the commands as JSON; none of them boots the app. Through the CLI, use `navree list`: `navree help` and `navree --help` print the CLI's own help.
- Every other command **boots the whole app** (configuration, database, every module), runs, then shuts the app down gracefully. A command therefore needs a working configuration and database, even `key:generate`. The exception is a command a module marks as offline (`CommandSpec::offline()`): it runs against the module graph, builds only the providers it asks for and runs no lifecycle hook. `config:show` and `config:check` are offline, so they work without a database.
- An unknown command fails before the app boots. A failing command prints its error and exits with status 1. The error is printed in its `Debug` form, because `main` returns it (`Error: UnknownCommand { name: "x" }`). Ctrl-C (and `SIGTERM` on Unix) stops long-running commands such as `serve` and `queue:work` gracefully.

### The built-in commands

`check` validates every import, export and provider dependency without constructing anything, which makes it a cheap CI step:

```sh
navree check
```

```text
module graph OK: 37 modules, 122 providers
```

`check --graph` prints the module tree instead: each module with its providers, their dependencies, its exports and its commands.

`introspect --json` prints the same graph as JSON for tools, again without constructing anything: the Navree version, every module (dependency order, the implicit root `App` last) with `global`, `imports`, `exports`, its `providers` (`type`, `scope`, `exported`, `multi`, `dependencies`) and `commands`, then every command with its module. [Navigator](/docs/ai/navigator/) reads it.

`navree check` runs this `check` first, then the app's `conformity:check` command when a module registers it (`ApiModule` and `WorkspaceModule` do). It boots the app once and runs every check: routes documented, models classified, workspace isolation, translations and migrations. See [Conformity checks](/docs/testing/conformity-checks/).

## Writing commands

A command is a `CommandSpec`: a name, a one-line description for `list`, and an async function that gets the booted app's `AppContext` and the arguments after the command name. `navree make:command <module> <name>` generates one; here is a complete example:

```rust title="src/modules/exports/commands/clear.rs"
use navree::kernel::{AppContext, BoxError, CommandSpec};
use navree::storage::Disk;

/// `exports:clear [--dry-run]`: deletes every generated export.
pub fn clear_exports() -> CommandSpec {
    CommandSpec::new(
        "exports:clear",
        "Delete every generated export ([--dry-run])",
        run,
    )
}

async fn run(ctx: AppContext, args: Vec<String>) -> Result<(), BoxError> {
    let dry_run = args.iter().any(|arg| arg == "--dry-run");
    if let Some(unknown) = args.iter().find(|arg| *arg != "--dry-run") {
        return Err(format!("unknown option `{unknown}` (expected --dry-run)").into());
    }
    let disk = ctx.get::<Disk>().await?;
    let files = disk.list("exports").await?;
    if !dry_run {
        for file in &files {
            disk.delete(file).await?;
        }
    }
    println!("{} {} export(s).", if dry_run { "Would delete" } else { "Deleted" }, files.len());
    Ok(())
}
```

Register it in the module's `wire` method with `m.command(..)`:

```rust title="src/modules/exports/mod.rs"
mod commands;

use navree::prelude::*;

#[module(register = Self::wire)]
pub struct ExportsModule;

impl ExportsModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.command(commands::clear::clear_exports());
        // navree:wire
    }
}
```

```sh
navree exports:clear --dry-run
```

```text
Would delete 3 export(s).
```

- **Names** are unique across the app; two modules registering the same name fail at boot (and in `check`). Prefix them with the module (`exports:clear`, `crm:task-reminders`), like Navree's own `queue:work`.
- **Arguments** arrive as plain strings, with no parsing: read flags and values from `args` yourself, and return an error for anything you don't understand, as above.
- **Services** come from the context: `ctx.get::<T>().await?` resolves any provider, ignoring module visibility.
- **Output** goes to standard output with `println!`; logs go through `tracing` as usual.
- **Failure**: return `Err(..)` and the binary prints it and exits with status 1.

### Scheduling a command

A command can run on a schedule, as the CRM's daily reminders do (see [Task scheduling](/docs/digging-deeper/scheduling/)):

```rust
fn wire(&self, m: &mut ModuleBuilder) {
    m.command(clear_exports());
    m.schedule(|s| {
        s.command("exports:clear", &[]).daily_at("04:00").without_overlapping();
    });
}
```

### Testing commands

`TestApp::run_command` runs a command against the test app, without booting a second one:

```rust title="src/modules/exports/tests/mod.rs"
use navree::prelude::*;
use navree::storage::{Disk, DiskConfig, StorageOptions};
use navree::testing::TestApp;

use super::ExportsModule;

#[tokio::test]
async fn clearing_exports_deletes_them() {
    let app = TestApp::builder()
        .module(StorageModule::for_root(StorageOptions {
            default: "memory".into(),
            disks: [("memory".to_owned(), DiskConfig::Memory)].into(),
            ..StorageOptions::default()
        }))
        .module(ExportsModule)
        .build()
        .await;
    let disk = app.get::<Disk>().await;
    disk.put("exports/contacts.csv", "id,name\n").await.unwrap();

    app.run_command("exports:clear", &[]).await.unwrap();

    assert!(disk.list("exports").await.unwrap().is_empty());
    assert!(app.run_command("exports:clear", &["--force"]).await.is_err());
    app.shutdown().await.unwrap();
}
```
