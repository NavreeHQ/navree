<Badge feature="observe" /> Load balancers and orchestrators need to know whether your app is alive and ready for traffic, and you want numbers on how it behaves. `navree-observe` serves both: a liveness probe, a readiness probe that runs every registered health check, and a Prometheus endpoint with the request metrics Navree records for you. Underneath, every module reports what it does as [telemetry events](#telemetry-events) that your own sinks can receive.

## Setup

Add `ObserveModule` to your app:

```rust title="src/app.rs"
use navree::prelude::*;

pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(HttpModule::from_config())
        .module(ObserveModule::from_config()) // section `observe`
}
```

It mounts three routes. Their paths are absolute (no API prefix, no version), they are public, and every response carries `Cache-Control: no-store`:

| Route | What it answers |
|---|---|
| `GET /health/live` | `200 {"status":"up"}` while the process serves HTTP. |
| `GET /health/ready` | `200` when every health check is up, `503` when one is down, with a report. |
| `GET /metrics` | The Prometheus text exposition (unless `observe.metrics` is off). |

All three keep answering in [maintenance mode](/docs/digging-deeper/maintenance-mode/): they are in the default `http.maintenance_except` list, so an orchestrator doesn't restart instances that are only down for maintenance.

The `observe` section is optional:

```toml title="config/app.toml"
[observe]
metrics = true
metrics_token = "a-long-random-string"   # better: APP_OBSERVE__METRICS_TOKEN in .env
```

| Key | Default | What it does |
|---|---|---|
| `observe.metrics` | `true` | Install the Prometheus recorder and serve `GET /metrics`. |
| `observe.metrics_token` | none | When set, `GET /metrics` requires `Authorization: Bearer <token>`. An empty token fails the boot. |

In code: `ObserveModule::for_root(ObserveOptions { metrics: true, metrics_token: Some(Secret::new(token)) })`, with `Secret` from `navree::contracts`.

## Liveness

`GET /health/live` runs no checks: it only proves the process answers HTTP. Use it for restarts, so a slow database never gets a healthy process killed.

```json title="200 OK"
{"status":"up"}
```

## Readiness

`GET /health/ready` runs every registered health check concurrently and reports each one. Use it to decide whether an instance gets traffic. This is the reference CRM's answer:

```json title="200 OK" wrap
{"status":"up","checks":{"cache":{"status":"up","latency_ms":3},"database":{"status":"up","latency_ms":3}}}
```

When a check is down, the status is `503` and the check carries its reason:

```json title="503 Service Unavailable" wrap
{"status":"down","checks":{"database":{"status":"up","latency_ms":2},"payments":{"status":"down","latency_ms":1000,"error":"request to https://status.payments.example.com/v1/ping timed out"}}}
```

- Each check has 2 seconds (`DEFAULT_CHECK_TIMEOUT`). A check that takes longer, or panics, is down.
- Down checks are logged as warnings under the `navree::health` target.
- Two checks with the same name are reported as `name`, `name#2`, and so on.
- With no checks registered, the app is ready.

Navree's modules register these checks when you add them:

| Check | Module | What it does |
|---|---|---|
| `database` | `DatabaseModule` | Pings the connection pool. |
| `cache` | `CacheModule` | Writes, reads back and forgets a key. |
| `storage` | `StorageModule` | Writes, reads back and deletes a small file on every disk. |

<Callout type="warning" title="The readiness report is public">

Anyone who can reach `/health/ready` sees each check's name and error message, and every request runs every check. Keep secrets and internal details out of `HealthStatus::Down` messages, and don't expose the route to the internet if your checks are expensive: let your load balancer reach it on an internal network.

</Callout>

## Writing a health check

A health check implements `HealthCheck` from `navree::contracts`: a name and an async `check` that returns `HealthStatus::Up` or `HealthStatus::Down(reason)`. Register it as a multi-binding of `dyn HealthCheck`; readiness collects every one at boot:

```rust title="src/modules/payments/health.rs"
use std::time::Duration;

use navree::BoxFuture;
use navree::contracts::{HealthCheck, HealthStatus};
use navree::http_client::HttpClient;
use navree::prelude::*;

/// Ready when the payment provider answers its status endpoint.
pub struct PaymentsHealth {
    http: Arc<HttpClient>,
}

impl HealthCheck for PaymentsHealth {
    fn name(&self) -> &str {
        "payments"
    }

    fn check(&self) -> BoxFuture<'_, HealthStatus> {
        Box::pin(async move {
            let response = self
                .http
                .get("https://status.payments.example.com/v1/ping")
                .timeout(Duration::from_secs(1))
                .retries(0)
                .send()
                .await;
            match response {
                Ok(response) if response.is_success() => HealthStatus::Up,
                Ok(response) => HealthStatus::Down(format!("status {}", response.status())),
                Err(error) => HealthStatus::Down(error.to_string()),
            }
        })
    }
}

#[module(register = Self::wire)]
pub struct PaymentsModule;

impl PaymentsModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.multi(Factory::<dyn HealthCheck>::new(|r: Resolver| async move {
            let http = r.get::<HttpClient>().await?;
            Ok(Arc::new(PaymentsHealth { http }) as Arc<dyn HealthCheck>)
        }));
    }
}
```

Keep checks fast and give outgoing calls a timeout below the 2-second budget, as above. A [`HttpClientError`](/docs/digging-deeper/http-client/#errors) message never contains query strings or credentials, so it is safe to report.

To run the checks from your own code, inject `Arc<Health>` (from `navree::observe`): `health.check().await` returns a `HealthReport` with `is_up()` and the `checks` map.

### Probes in Kubernetes

```yaml title="deployment.yaml"
livenessProbe:
  httpGet: { path: /health/live, port: 8080 }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /health/ready, port: 8080 }
  periodSeconds: 5
  timeoutSeconds: 3
```

## Metrics

`GET /metrics` serves every metric recorded in the process in the [Prometheus text format](https://prometheus.io/docs/instrumenting/exposition_formats/). Navree's HTTP pipeline records two for every request:

| Metric | Type | Labels |
|---|---|---|
| `http_requests_total` | counter | `method`, `route`, `status` |
| `http_request_duration_seconds` | histogram | `method`, `route`, `status` |

`route` is the route's template (`/api/v1/deals/{id}`), not the request path, so the number of series stays small; requests that match no route are labelled `unmatched`. Histograms whose name ends in `_seconds` use the buckets 5 ms, 10 ms, 25 ms, 50 ms, 100 ms, 250 ms, 500 ms, 1 s, 2.5 s, 5 s and 10 s.

```text title="GET /metrics"
# HELP http_requests_total HTTP requests by method, route template and status.
# TYPE http_requests_total counter
http_requests_total{method="GET",route="/api/v1/deals",status="401"} 1
http_requests_total{method="GET",route="/health/live",status="200"} 2
http_requests_total{method="GET",route="/health/ready",status="200"} 1

# HELP http_request_duration_seconds HTTP request latency by method, route template and status.
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{method="GET",route="/api/v1/deals",status="401",le="0.005"} 1
http_request_duration_seconds_bucket{method="GET",route="/api/v1/deals",status="401",le="0.01"} 1
...
http_request_duration_seconds_sum{method="GET",route="/api/v1/deals",status="401"} 0.0010231
http_request_duration_seconds_count{method="GET",route="/api/v1/deals",status="401"} 1
```

These are the HTTP metrics `ObserveModule` records. Queue throughput, wait and runtime are on [Fleet](/docs/tools/fleet/)'s dashboard and, with `FleetModule` in the app, in `GET /metrics` too; [Lighthouse](/docs/tools/lighthouse/) covers the rest of monitoring.

### Metrics read when Prometheus scrapes

Some numbers are not counted as things happen but read from somewhere else, such as the size of a backlog in your database. Implement `MetricsCollector`, set gauges with the [`metrics`](https://docs.rs/metrics) crate's macros (add it to your dependencies), and register the collector as a `dyn MetricsCollector` multi-binding: `GET /metrics` runs every collector, one after the other, before it renders, so its gauges are fresh on every scrape. Each collector gets 2 seconds (`COLLECT_TIMEOUT`); one that takes longer is left behind and the exposition shows its previous values.

```rust title="src/modules/orders/metrics.rs"
use navree::BoxFuture;
use navree::observe::MetricsCollector;
use navree::prelude::*;

pub struct Backlog {
    db: Arc<navree::db::Db>,
}

impl MetricsCollector for Backlog {
    fn collect(&self) -> BoxFuture<'_, ()> {
        Box::pin(async move {
            if let Ok(count) = unshipped_orders(&self.db).await {
                metrics::gauge!("orders_unshipped").set(count as f64);
            }
        })
    }
}

// In the module's `wire`:
// m.multi(Factory::<dyn MetricsCollector>::new(|r: Resolver| async move {
//     Ok(Arc::new(Backlog { db: r.get().await? }) as Arc<dyn MetricsCollector>)
// }));
```

Fleet registers one this way for its `fleet_*` gauges.

### Protecting the endpoint

Metrics reveal your routes and traffic. Set `observe.metrics_token` to require a bearer token:

```sh
curl -H "Authorization: Bearer $METRICS_TOKEN" http://127.0.0.1:8080/metrics
```

A missing or wrong token gets `401` with `WWW-Authenticate: Bearer`, and the attempt is logged as a warning under `navree::security`. Tokens are compared in constant time. In Prometheus, pass the token in the scrape job:

```yaml title="prometheus.yml"
scrape_configs:
  - job_name: crm-api
    metrics_path: /metrics
    authorization:
      credentials_file: /etc/prometheus/crm-metrics-token
    static_configs:
      - targets: ["crm-api:8080"]
```

### Recording your own metrics

Navree uses the [metrics](https://docs.rs/metrics) facade, so anything your code records with its macros shows up on `/metrics`. Add the crate (the version Navree uses is 0.24) and record:

```toml title="Cargo.toml"
metrics = "0.24"
```

```rust
use std::time::Instant;

let started = Instant::now();
// ... write the export ...
metrics::counter!("invoices_exported_total").increment(rows.len() as u64);
metrics::histogram!("invoice_export_duration_seconds").record(started.elapsed().as_secs_f64());
```

Keep label values bounded (ids and paths make the number of series explode), and end duration histograms in `_seconds` to get the buckets above.

### Turning metrics off

With `observe.metrics = false`, no recorder is installed and `/metrics` isn't mounted. Do that when another library installs its own `metrics` recorder: there is one per process, and `ObserveModule` fails the boot if another one is already installed.

## Telemetry events

<Badge feature="telemetry" /> Navree's modules report what they do as typed events: every request answered, query run, job attempt, scheduled task, mail, notification, cache call, outgoing HTTP call, exception, log line and app event. [Tracing](/docs/microservices/tracing/) turns them into spans, [Lighthouse](/docs/tools/lighthouse/), [Logbook](/docs/tools/logbook/) and [Fleet](/docs/tools/fleet/) are built on them, and your own code can receive them by registering a **sink**. The types live in `navree::telemetry` (the `navree-telemetry` crate, in `full`).

| Event | Emitted by | When | Fields |
|---|---|---|---|
| `RequestHandled` | `HttpModule` | a response is ready | `method`, `route` (the template, `None` when no route matched), `path`, `status`, `duration`, `user_id`, `workspace_id`, `request_id`, `client_ip` |
| `QueryExecuted` | `DatabaseModule` | a statement ran | `sql` (with its placeholders, never the bound values), `duration`, `rows` (`None`: SeaORM doesn't report them), `connection` (the URL without its password), `failed` |
| `JobProcessed` | queue workers | a job attempt succeeded | `queue`, `job_type`, `job_id`, `attempt`, `duration` |
| `JobFailed` | queue workers | a job attempt failed, timed out or panicked | the same, plus `error` (the error chain) and `will_retry` |
| `ScheduledTaskRan` | `ScheduleModule` | a task ran (skipped ticks aren't reported) | `task`, `tick`, `duration`, `error` |
| `MailSent` | `MailModule` | the transport accepted a mail | `to`, `cc`, `bcc`, `from`, `subject`, `text`, `html`, `transport`, `duration` |
| `NotificationSent` | `NotifyModule` | a notification went out on one channel | `notification_id`, `notification_type`, `notifiable_type`, `notifiable_id`, `channel` |
| `CacheEvent` | `CacheModule` | a read hit or missed, a value was written, a key was forgotten | `operation` (`CacheOperation::Hit`, `Miss`, `Write`, `Forget`), `key` (without the prefix), `store` |
| `HttpClientRequest` | `HttpClient` | an outgoing call finished, after its retries | `method`, `url` (no query string, fragment or credentials), `status`, `duration`, `attempts`, `error`, `span_id` |
| `ExceptionReported` | `HttpModule`, or your code | a 500 (or a 5xx with an underlying error), a panicking handler | `message`, `chain` (the message, then each source's), `location` (the panic's or the reporting call's `file:line:column`), `panic`, `request` (method, path, route and status) |
| `LogRecord` | `LoggerModule` | a log line passed the level filter | `level`, `target`, `message`, `fields` (redacted, as in the output) |
| `EventEmitted` | `EventsModule` | an event was emitted or published, and every listener ran or was queued | `name`, `payload` (JSON), `listeners` (the ones that ran), `queued` (the ones whose job was dispatched), `failed`, `duration` |

A sink receives each one as a `TelemetryRecord`: the `event` (a `TelemetryEvent`), the time it was emitted (`at`) and its `context`, an `EventContext` with the request id or job id, the trace, the user id and the workspace id of the request or job it happened in. Records serialize to JSON with a `type` tag (`{"type": "query_executed", "sql": ...}`) and durations in milliseconds, ready to store or send.

### Writing a sink

A sink implements `TelemetrySink`: `interest` names the kinds it wants (all of them by default) and `record` receives each record. Register it with `m.telemetry_sink::<S>()`; the container builds it like any provider:

```rust title="src/modules/monitoring/mod.rs"
use navree::prelude::*;
use navree::telemetry::{EventKind, Interest, TelemetryEvent, TelemetryRecord, TelemetrySink};

/// Counts failed job attempts by queue and job type, on `/metrics`.
#[injectable]
pub struct JobFailureMetrics;

impl TelemetrySink for JobFailureMetrics {
    fn interest(&self) -> Interest {
        Interest::only([EventKind::JobFailed])
    }

    fn record(&self, record: &TelemetryRecord) {
        if let TelemetryEvent::JobFailed(job) = &record.event {
            metrics::counter!(
                "job_failures_total",
                "queue" => job.queue.clone(),
                "job" => job.job_type.clone(),
            )
            .increment(1);
        }
    }
}

/// Registers the app's own telemetry sinks.
#[module(register = Self::wire)]
pub struct MonitoringModule;

impl MonitoringModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.telemetry_sink::<JobFailureMetrics>();
    }
}
```

`m.telemetry_sink_value(sink)` registers a sink you built yourself, and `m.telemetry_sink_factory(Factory::<dyn TelemetrySink>::new(...))` one that needs setup. An app can have any number of sinks; each gets the kinds it asked for.

- **`record` runs on the emitting task**, in the middle of a request, a query or a log call. Keep it short and never block: a sink that stores or sends records hands them to a channel and does the work in a background task.
- **Interest is read once, at boot.** Sinks start receiving records once every provider is built, and stop at shutdown.
- **A sink can't loop.** A record emitted while a sink on the same thread is receiving one (a sink that logs, say) is dropped, not delivered back.

### What it costs

An app without a sink has no telemetry registry: each emitter holds a disabled handle, and every event costs one branch on a `None`. With sinks, an emitter checks one atomic before building an event, so kinds that no sink wants are never built. The `RequestHandled` of an app whose only sink wants `JobFailed` costs one load per request.

### Reporting your own errors

Inside a request, job or scheduled task, `Telemetry::current()` is the app's registry. Report an error you handled yourself, with its source chain and your code's location:

```rust
use navree::telemetry::Telemetry;

if let Err(error) = sync_calendar(&user).await {
    Telemetry::current().report_exception(&error);
}
```

Outside one, resolve the registry once with `Telemetry::from_app(ctx).await` and keep it. Both are disabled, and report nothing, when the app has no sink.

### Testing with `TelemetryRecorder`

`TelemetryRecorder` (from `navree::telemetry`) is a sink that keeps every record in memory. Add its module to a test app, then read what was emitted:

```rust title="tests/telemetry.rs"
use navree::axum::http::Method;
use navree::http_client::{FakeResponse, HttpClient};
use navree::prelude::*;
use navree::telemetry::{EventKind, TelemetryRecorder};
use navree::testing::TestApp;

#[tokio::test]
async fn the_rates_call_happens_inside_the_request() {
    let recorder = TelemetryRecorder::new();
    let (client, server) = HttpClient::fake();
    server.on(Method::GET, "https://rates.example.com/*", FakeResponse::new(200));
    let app = TestApp::builder()
        .module(HttpClientModule::from_config())
        .module(RatesModule)
        .module(recorder.module())
        .override_value(Arc::new(client))
        .build()
        .await;

    app.client().get("/api/v1/rates/eur").send().await.assert_status(200);

    let request = &recorder.requests()[0];
    assert_eq!(request.route.as_deref(), Some("/api/v1/rates/{currency}"));
    let call = &recorder.http_client_requests()[0];
    assert_eq!(call.url, "https://rates.example.com/v1/eur");
    let record = &recorder.of_kind(EventKind::HttpClientRequest)[0];
    assert_eq!(record.context.request_id.as_deref(), Some(request.request_id.as_str()));

    app.shutdown().await.unwrap();
}
```

The recorder has one accessor per event: `requests()`, `queries()`, `jobs_processed()`, `jobs_failed()`, `scheduled_tasks()`, `mails()`, `notifications()`, `cache_events()`, `http_client_requests()`, `exceptions()` and `logs()`. `records()` returns every record with its context, `events()` every event, `of_kind(kind)` the records of one kind, and `clear()` forgets them. For events emitted by background work, such as a queued job, `recorder.wait_for(EventKind::JobProcessed, Duration::from_secs(5)).await` waits until one arrives and returns whether it did. `TelemetryRecorder::only([EventKind::QueryExecuted])` records only those kinds.

## Monitoring with Lighthouse

Health checks and metrics tell an orchestrator and a dashboard whether the app is up. [Lighthouse](/docs/tools/lighthouse/) tells you what went wrong: it records exceptions grouped by fingerprint, slow requests and queries and failed jobs, shows them on a dashboard at `/_lighthouse`, sends alerts to email, Slack or webhooks, and exports to OpenTelemetry. It runs inside your app, so there is nothing else to host.

## Testing

The Prometheus recorder is installed once per process, so every app booted by your tests shares it. Turn metrics off in tests (`observe.metrics = false`), or assert on counts with `>=` rather than exact values. Test health checks through the route:

```rust title="tests/health.rs"
use navree::BoxFuture;
use navree::contracts::{HealthCheck, HealthStatus};
use navree::prelude::*;
use navree::testing::TestApp;

struct AlwaysDown;

impl HealthCheck for AlwaysDown {
    fn name(&self) -> &str {
        "payments"
    }

    fn check(&self) -> BoxFuture<'_, HealthStatus> {
        Box::pin(async { HealthStatus::Down("connection refused".into()) })
    }
}

#[module(register = Self::wire)]
struct DownModule;

impl DownModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.multi(Factory::<dyn HealthCheck>::new(|_| async {
            Ok(Arc::new(AlwaysDown) as Arc<dyn HealthCheck>)
        }));
    }
}

#[tokio::test]
async fn readiness_fails_when_payments_are_down() {
    let app = TestApp::builder()
        .config("observe.metrics", false)
        .module(ObserveModule::from_config())
        .module(DownModule)
        .build()
        .await;

    app.client()
        .get("/health/ready")
        .send()
        .await
        .assert_status(503)
        .assert_json_path("checks.payments.error", "connection refused".into());
    app.shutdown().await.unwrap();
}
```
