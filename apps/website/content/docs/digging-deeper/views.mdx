<Badge feature="view" /> Views are templates for text: the HTML and plain-text bodies of emails, CSV headers, the text of a notification. `navree-view` provides them on Navree's own template engine, `navree-template`, in the Jinja syntax. The pages of a web app are not templates: [Navree UI](/docs/ui/overview/) draws them from typed Rust components.

```jinja title="resources/views/mail/invoice.html"
<p>Hello {{ name }},</p>
<p>Invoice {{ number }} for {{ total_cents|money(currency) }} is due on {{ due_on|date("%-d %B %Y") }}.</p>
```

## Configuration

Add `ViewModule` to your app. It is global: every module can inject `Arc<Views>`.

```rust title="src/app.rs"
use navree::prelude::*;

pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(ViewModule::from_config()) // section `view`
}
```

```toml title="config/app.toml"
[view]
dirs = ["resources/views", "vendor/views"]
reload = false
```

| Key | Default | What it does |
|---|---|---|
| `view.dirs` | `["resources/views"]` | Template directories, searched in order. A directory that doesn't exist is skipped. Relative paths start from the working directory. |
| `view.reload` | on in debug builds, off in release builds | Pick up changed, new and deleted template files without a restart. |

From the environment: `APP_VIEW__DIRS=resources/views,vendor/views` (comma-separated) and `APP_VIEW__RELOAD=false`.

In code, pass `ViewOptions` or a single directory:

```rust
use navree::view::ViewOptions;

Navree::app().module(ViewModule::for_root(ViewOptions {
    dirs: vec!["resources/views".into(), "vendor/views".into()],
    reload: false,
}));

Navree::app().module(ViewModule::for_root("resources/mail")); // one directory, default `reload`
```

[`MailModule`](/docs/digging-deeper/mail/) needs `ViewModule` in the app, since every mail is rendered from templates.

## Where templates live

A template's **name** is its path relative to a template directory, with `/` separators: `resources/views/mail/invoice.html` is `mail/invoice.html`. Files count as templates when their extension is `html`, `htm`, `xml`, `txt`, `md`, `j2` or `jinja`; hidden files and directories are ignored.

Templates can also be **embedded** in a module's code, so the module works without template files. Register them in the module with `m.templates(..)`, usually with `include_str!`. The CRM's activities module ships its reminder mail this way:

```rust title="crates/crm-activities/src/reminders.rs"
/// The embedded mail templates.
pub(crate) const TEMPLATES: [(&str, &str); 2] = [
    (
        "mail/crm/tasks-due-today.html",
        include_str!("../templates/tasks-due-today.html"),
    ),
    (
        "mail/crm/tasks-due-today.txt",
        include_str!("../templates/tasks-due-today.txt"),
    ),
];
```

```rust title="crates/crm-activities/src/lib.rs"
impl ActivitiesModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.templates(&reminders::TEMPLATES);
        // ...
    }
}
```

Name embedded templates with their extension (`mail/welcome.html`): the extension decides the [escaping](#escaping) and lets lookups without an extension find them.

When the same name is defined more than once:

1. the first directory in `view.dirs` holding the name wins;
2. any file wins over an embedded template, so an app overrides a module's mail by dropping a file with the same name into `resources/views`;
3. among embedded templates, a module's template replaces one with the same name from a module it imports.

Every template is read and compiled when the app boots, off the async workers. A syntax error fails the boot and names the template.

## Rendering templates

Inject `Arc<Views>` and call `render(name, context)`. The context is any `Serialize` value: a struct, a map or `serde_json::json!`. Its fields are the template's variables.

```rust title="src/modules/billing/invoice_text.rs"
use navree::prelude::*;
use navree::view::{ViewError, Views};
use serde::Serialize;

#[derive(Serialize)]
pub struct InvoiceView<'a> {
    pub name: &'a str,
    pub number: &'a str,
    pub total_cents: i64,
    pub currency: &'a str,
    pub due_on: &'a str,
}

#[injectable]
pub struct InvoiceText {
    views: Arc<Views>,
}

impl InvoiceText {
    pub fn html(&self, invoice: &InvoiceView<'_>) -> Result<String, ViewError> {
        self.views.render("mail/invoice", invoice)
    }
}
```

A name without a template extension tries `.html`, `.txt` and `.j2`, in that order, then the bare name: `render("mail/invoice", ..)` finds `mail/invoice.html`. Use the full name to pick one (`mail/invoice.txt`). `views.exists(name)` tells you whether a name resolves, for example to send a plain-text part only when one exists.

To render template text that isn't in a file (kept in your database or in settings), call `views.render_source(name, source, context)`. The `name` stands for the file it would be: its extension picks the [escaping](#escaping), and errors name it. The text sees the same filters, the same undefined-variable rule and the registered templates, so it can `{% extends "layouts/mail.html" %}`.

`{% extends %}`, `{% include %}` and `{% import %}` take full names:

```jinja title="resources/views/mail/invoice.html"
{% extends "layouts/mail.html" %}
{% block body %}
  <p>Invoice {{ number }} is due on {{ due_on|date("%-d %B %Y") }}.</p>
{% endblock %}
```

A name can't leave its directory: `..`, absolute paths and backslashes find nothing. On Windows, neither does another name for a file: an 8.3 name such as `HIDDEN~1`, a trailing dot or space, or a device name such as `NUL.html`.

### Escaping

A template's name picks its mode, in any case and also before a trailing `.j2`, `.jinja` or `.jinja2`:

| Name | Mode | `Ada & <Co>` prints as |
|---|---|---|
| `.txt`, `.md` | as it is | `Ada & <Co>` |
| `.json`, `.json5`, `.js`, `.mjs`, `.cjs`, `.yaml`, `.yml` | JSON | `"Ada & <Co>"` |
| anything else: `.html`, `.htm`, `.xhtml`, `.xml`, `.svg`, a bare `.j2` or `.jinja`, an unknown extension, no extension | HTML | `Ada &amp; &lt;Co&gt;` |

Mark text you trust with `|safe`: it prints as it is in every mode.

The mode belongs to the text where it is written, and what lands in other text can only get stricter:

- A template rendered inside another (`extends`, `include`, a block) prints in its own mode and at least as strictly as the text it lands in. A `.txt` file included into an HTML page escapes HTML; a `.txt` child of an HTML layout prints the layout's values escaped, and an HTML child of a `.txt` layout does too.
- A `.js` or `.json` file included into HTML prints JSON that is also fit for HTML: `<`, `>`, `&` and `'` in strings print as `\u` escapes, so a value can't end a `<script>`.
- What a macro, a call block, `super()` or a `{% set %}` block returns is safe only for the mode it was escaped in. Printed in that mode it prints as it is; printed in another it is escaped again, its markup included. An HTML macro's output printed in a `.txt` template stays as the macro escaped it.
- `{% autoescape %}` reaches only the text inside it, not the macros it calls, the blocks of a child, `caller()` or a file it includes. It takes `true`, `false`, `"html"`, `"json"` or `"none"`, and anything else fails to compile. `true` means the template's own mode, or HTML if its own prints values as they are. Inside an HTML template, `"json"` prints JSON fit for HTML.

`|tojson` is safe wherever it is printed. Its strings have `<`, `>`, `&` and `'` as `\u` escapes. Printed into HTML, its quotes depend on where it lands: inside a `<script>` they stay quotes, and anywhere else they print as `&quot;`, which a double-quoted attribute reads back as a quote. Text that was captured first (`{% set x %}{{ v|tojson }}{% endset %}`, or a macro) has settled its quotes as `&quot;`, which is safe but isn't JSON inside a `<script>`: print `|tojson` directly there, or `{% set x = v|tojson %}`. A `<script>` that a macro's own text opens is captured text too, so `|tojson` inside a macro prints `&quot;` even there: pass the JSON in as an argument (`{{ chart(v|tojson) }}`), or mark it `|safe` where you know where it lands. The engine takes the same safe side where it can't be sure a script is one: once a template has printed `<noscript>`, `<math>`, `<frameset>`, `<![CDATA[`, a `<style>`, `<title>`, `<xmp>`, `<iframe>`, `<noembed>` or `<noframes>` inside a `<select>`, or an `<svg>` holding anything but plain shapes, text and groups, `|tojson` prints `&quot;` for the rest of the output. A plain inline icon that closes changes nothing. `join` and `replace` of JSON text follow the same rule when they land in HTML.

An `Environment` of your own, without `Views`, follows `default_auto_escape`: the same names, except that unknown extensions print values as they are. `strict_auto_escape` is the rule above, and `set_auto_escape_callback` sets another.

### Undefined variables

Printing, iterating or filtering a variable the context doesn't define is an **error**, not an empty string, so a typo can't send a blank email. Testing one is fine and is false:

```jinja
{% if title %}<h1>{{ title }}</h1>{% endif %}
```

Define every printed field in the context, using `null` for "no value" (`none` in the template).

### Errors

`render` returns a `ViewError`:

- `NotFound` lists every name it tried;
- `Template` names the template that failed to compile or render, with the engine's error: its kind, message, template name, line and column (`source.line()`, `source.column()`);
- `Io` names a template directory or file that can't be read.

Messages never contain context values, since a context may hold tokens or other secrets.

## Syntax

`{{ expression }}` prints, `{% statement %}` runs a statement and `{# ... #}` is a comment. A `-` directly inside a delimiter removes the whitespace on that side (`{%- if x -%}`).

| | |
|---|---|
| Statements | `if`, `elif`, `else`; `for` with `else`, a filter (`for x in xs if x.ok`), `loop`, `break` and `continue`; `set` (also as a block); `with`; `block` with `super()`; `extends`; `include` (with `ignore missing`); `import ... as`; `from ... import`; `macro`; `call` (with arguments); `filter`; `autoescape`; `do`; `raw` |
| Expressions | strings, numbers, `true`, `false`, `none`, lists, tuples and dicts; `a.b`, `a[b]`, `a[1:2]`; calls with keyword arguments; `and`, `or`, `not`; comparisons, `in`, `not in`; `+`, `-`, `*`, `/`, `//`, `%`, `**`, `~` (joins as text); `a if b else c` |
| `loop` | `index`, `index0`, `revindex`, `revindex0`, `first`, `last`, `length`, `previtem`, `nextitem`, `cycle(...)`, `changed(...)` |
| Filters | `abs`, `capitalize`, `count`, `d`, `date`, `default`, `e`, `escape`, `first`, `int`, `items`, `join`, `last`, `length`, `list`, `lower`, `min`, `money`, `replace`, `round`, `safe`, `split`, `string`, `tojson`, `trim`, `upper`, `urlencode` |
| Tests | `boolean`, `defined`, `divisibleby`, `endingwith`, `eq`, `equalto`, `escaped`, `even`, `false`, `filter`, `float`, `ge`, `gt`, `greaterthan`, `in`, `int`, `integer`, `iterable`, `le`, `lessthan`, `lower`, `lt`, `mapping`, `ne`, `none`, `number`, `odd`, `safe`, `sameas`, `sequence`, `startingwith`, `string`, `test`, `true`, `undefined`, `upper` |
| Functions | `range`, `dict` |

A template reaches its context, the environment's globals and its own variables, and nothing else: attributes are the keys of maps, values have no methods, and only templates can be included, by name. A file name in a template can't leave its directory.

### Your own filters and functions

A module adds them with `m.view_environment(..)`, and code holding `Views` with `views.configure(..)`. Parameters convert from `Value`, `&Value`, `&str`, `String`, `bool`, integers, floats and `Option<T>`; a last `Kwargs` parameter takes keyword arguments. The return value is anything that converts into a value, or a `Result` of one.

```rust
use navree::prelude::*;
use navree::view::ModuleBuilderViewExt;

impl BrandModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.view_environment(|env| {
            env.add_global("brand", "Acme");
            env.add_filter("shout", |text: &str| text.to_uppercase());
            env.add_function("greet", |name: &str| format!("Hello, {name}"));
        });
    }
}
```

### Limits

Every render is capped, whether the template comes from a file or from text in your database. A template that goes over a limit fails with an error naming the template and the line.

| Limit | Default | What it caps |
|---|---|---|
| `max_depth` | 100 | how deep macro calls, call blocks, blocks, includes and imports nest |
| `max_include_depth` | 32 | how deep includes, imports and `extends` chains nest |
| `max_loop_iterations` | 10,000,000 | loop iterations of one render |
| `max_operations` | 100,000,000 | work of one render: statements, expressions, the items filters go through, and every string it scans or copies, each 64 bytes counting as one |
| `max_output_bytes` | 64 MiB | the output, and any string a template builds; sequences hold at most 1/16 of this in items |
| `max_allocated_bytes` | 1 GiB | what one render allocates over its life for its output, its macro and `{% set %}` buffers, and the strings, sequences and maps it builds |
| `max_stack_bytes` | 768 KiB | the stack the compiles and renders on one thread use together |

Nesting in a template's source (150 levels, chains like `a + b + c` included) and in values (200 levels, keyword arguments and imported modules counted) is capped as well, and `range` gives at most 100,000 items.

What these guarantee:

- **Memory.** Each allocation is charged before it happens, freed or not, so what a render holds stays below `max_allocated_bytes` however it holds it. Text costs about twice its size when built (the buffer and the string); one character of a string turned into a list costs about 100 bytes. Not counted: the context you pass in, compiled templates, what your registered functions allocate, and a little bookkeeping per scope, which `max_depth` and the source's size bound.
- **Time.** Whatever scans or copies a string, or walks a value, is charged by its size, so a render ends within `max_operations` however large its values are. Your registered functions aren't counted.
- **Output.** Nothing a template builds passes `max_output_bytes`, including text that grows while it is built: upper case, JSON, a replacement. Each buffer is capped on its own; `max_allocated_bytes` caps them together.
- **Stack.** One budget per thread. It counts from where the thread's outermost compile or render started, so a render inside a function and a template compiled during a render share it, and comes back when the outermost one ends. A render also stops while 256 KiB of the thread's stack remain, wherever it started, where the end of the stack is known (Linux, macOS, Windows), which is what value walks need. So a thread with less than 256 KiB left fails with a limit error rather than overflowing; elsewhere only `max_stack_bytes` applies.

```rust
views.configure(|env| {
    let mut limits = env.limits();
    limits.max_output_bytes = 8 << 20;
    env.set_limits(limits);
});
```

The engine's types are at `navree::view::template`.

## Filters

Navree adds two filters to the built-in ones.

### money

`{{ cents|money("USD") }}` formats an integer amount in minor units (cents) with the currency's symbol, thousands separators and its number of decimals:

```jinja
{{ 123456|money("USD") }}   {# $1,234.56 #}
{{ 123456|money("EUR") }}   {# €1,234.56 #}
{{ 150000|money("JPY") }}   {# ¥150,000 #}
{{ 1999|money("CHF") }}     {# CHF 19.99 #}
{{ 1234567|money("KWD") }}  {# KWD 1,234.567 #}
```

`USD`, `EUR`, `GBP`, `JPY` and `INR` get their symbol; other currencies get their ISO code. The number of decimals follows ISO 4217 (0 for `JPY` or `KRW`, 3 for `KWD` or `BHD`, 2 otherwise). `none` prints nothing. A non-integer amount or a currency that isn't three letters is a render error. There is no locale-aware formatting.

### date

`{{ value|date("%d %b %Y") }}` formats a date with a [chrono `strftime`](https://docs.rs/chrono/latest/chrono/format/strftime/index.html) format, `%Y-%m-%d` by default. The value can be an RFC 3339 date-time (kept in its own offset), a date-time without an offset (`2026-10-25T14:30:00`), a date (`2026-10-25`) or a Unix timestamp in seconds (UTC). `none` prints nothing.

```jinja
{{ "2026-11-01"|date("%-d %B") }}                  {# 1 November #}
{{ "2026-10-25T14:30:00Z"|date("%d %b %Y, %H:%M") }}  {# 25 Oct 2026, 14:30 #}
```

## How mail uses templates

[Mail](/docs/digging-deeper/mail/) renders through the same `Views`. The quickest mail is a `TemplateMail`: give it a template name without an extension, and it renders `{name}.html` and `{name}.txt`, whichever exist, with your context.

```rust
use navree::mail::{Mailer, TemplateMail};
use serde_json::json;

mailer
    .send(
        &TemplateMail::new("ada@example.com", "Your invoice", "mail/invoice").context(json!({
            "name": "Ada",
            "number": "INV-0042",
            "total_cents": 129900,
            "currency": "EUR",
            "due_on": "2026-11-30",
        })),
    )
    .await?;
```

For more control, implement `Mailable` yourself: its `build(&self, views: &Views)` method renders whatever it needs. `navree make:mail <module> <name>` generates one, with its `.html` and `.txt` templates next to it, embedded under `<module>/mail/<name>.html` and registered in the module (see [Console commands and the CLI](/docs/digging-deeper/cli/#generators)).

The CRM's daily reminder is a `TemplateMail` on `mail/crm/tasks-due-today`, whose text version is:

```jinja title="crates/crm-activities/templates/tasks-due-today.txt"
Hello {{ name }},

{{ summary }}
{%- for task in tasks %}
- {{ task.subject }}, due {{ task.due }} UTC
{%- endfor %}

Open your tasks: {{ url }}
```

## Reloading during development

With `view.reload` on (the default in debug builds), each lookup checks the template file's modification time and size and picks up changed, new and deleted files, so you can edit a mail's wording without restarting. Templates are still compiled at boot, so syntax errors surface early. This costs a file-system check per lookup, which is why release builds turn it off: there, every template is read once at boot and rendering never touches the disk.

`navree dev` doesn't rebuild when files under `resources/` change, because reloading covers them; embedded templates live in `src/`, so changing one triggers a rebuild.

## Testing

`Views::from_templates` builds views from (name, source) pairs, with no directories and no app, which keeps template tests fast:

```rust title="src/modules/billing/tests/mod.rs"
use navree::view::Views;
use serde_json::json;

#[test]
fn the_invoice_mail_shows_the_total() {
    let views = Views::from_templates([(
        "mail/invoice.html",
        "<p>{{ name }} owes {{ total_cents|money(currency) }} by {{ due_on|date('%-d %B') }}.</p>",
    )])
    .unwrap();

    let html = views
        .render(
            "mail/invoice",
            json!({ "name": "Ada & Co", "total_cents": 123456, "currency": "EUR", "due_on": "2026-11-01" }),
        )
        .unwrap();

    assert_eq!(html, "<p>Ada &amp; Co owes €1,234.56 by 1 November.</p>");
}
```

To test a module's real templates, pass its `TEMPLATES` constant: `Views::from_templates(TEMPLATES.iter().copied())`. To check the mails your code sends, use the mail module's array transport; see [Mail](/docs/digging-deeper/mail/).
