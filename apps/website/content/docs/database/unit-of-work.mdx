Every HTTP request in a Navree app gets a **unit of work**. It carries the signed-in user and the request id, opens a database transaction the first time you use the database, collects the changes you make and the work that must wait for them, and then commits or rolls back exactly once, when the response is ready.

So a handler that fails halfway leaves nothing behind, and side effects that must only happen after a successful commit (queued jobs, mail, broadcasts) wait for it. Jobs, commands and seeders create units of work of their own.

## A request's unit of work

`DatabaseModule` adds a layer to the request pipeline, after authentication and before routing. For each request it:

1. creates a lazy `Uow` holding the actor (the user id of the authenticated principal, if any) and the request id;
2. runs the rest of the request (routing, access checks and your handler) with that unit of work as the [current one](#the-current-unit-of-work), in the task that serves the request. If the request is dropped before it finishes, because the client disconnected or the request timed out, what is left of it moves to a task on the app's task tracker, so the request still runs to completion;
3. when the response status is **below 400**, commits: [change observers](#change-events-and-observers) run inside the transaction, the transaction commits, then the [after-commit hooks](#after-commit-hooks) run;
4. otherwise (a 4xx, a 5xx, or a panic, which becomes a 500), rolls back and drops the recorded changes and hooks.

If the commit itself fails, the handler's response is replaced by an error response from the [database error mapping](/docs/database/getting-started/#database-errors): a 409 for a unique or foreign-key violation that is only detected at commit, a 500 for anything else.

The status decides, not where an error came from: if a handler writes a row and then returns a 400, the row is rolled back with everything else.

The unit of work is lazy: it opens no transaction until something asks for one. A request that never touches the database, or only reads through the pool, never opens a transaction.

## Using it in handlers

Take the unit of work as an extractor and pass it to your services as `&Uow`. Services take it as a parameter rather than having it injected, because it belongs to one request while services are shared:

```rust title="src/modules/deals/controller.rs"
#[controller("/deals", version = "1")]
impl DealsController {
    #[patch("/{id}")]
    #[authenticated]
    async fn update(
        &self,
        uow: Uow,
        Path(id): Path<Uuid>,
        Valid(Json(input)): Valid<Json<UpdateDeal>>,
    ) -> Result<Json<Record<Deal>>> {
        Ok(Json(self.deals.update(&uow, id, input).await?))
    }

    #[delete("/{id}")]
    #[authenticated]
    async fn destroy(&self, uow: Uow, Path(id): Path<Uuid>) -> Result<NoContent> {
        self.deals.delete(&uow, id).await?;
        Ok(NoContent)
    }
}
```

`Uow` is cheap to clone: clones are handles to the same unit of work. Without `DatabaseModule` in the app, the extractor answers 500.

### The transaction

A `&Uow` is an executor: pass it wherever a model method or a statement takes one, and the work runs in the unit of work's transaction. The first statement begins it; later ones reuse it.

```rust
pub async fn list(&self, uow: &Uow, page: PageQuery) -> navree::orm::Result<Page<Record<Deal>>> {
    Deal::query()
        .order_by_desc(Deal::CREATED_AT)
        .order_by_desc(Deal::ID)
        .paginate(uow, page)
        .await
}
```

For SQL the builder can't express, run a `Statement` on the same executor. Its `?` placeholders work on every database:

```rust
use navree::db::{DbError, ExecutorExt, Statement};

/// How many deals `owner_id` has, in the request's transaction.
pub async fn count_for(uow: &Uow, owner_id: Uuid) -> Result<i64, DbError> {
    let statement = Statement::portable(
        "SELECT COUNT(*) FROM deals WHERE owner_id = ?",
        [owner_id.into()],
    );
    uow.fetch_scalar::<i64>(&statement).await
}
```

`uow.savepoint()` opens a savepoint inside the transaction, for work that may fail without ending the unit of work.

How the transaction begins depends on the database:

- **SQLite**: `BEGIN IMMEDIATE`, which takes the write lock at once ([SQLite and concurrency](#sqlite-and-concurrency)).
- **PostgreSQL**: `BEGIN`, then `set_config` makes the actor and request id available to SQL as `current_setting('navree.actor', true)` and `current_setting('navree.request_id', true)` for the rest of the transaction.
- **MySQL and MariaDB**: `BEGIN`, then `SET @navree_actor = ?, @navree_request_id = ?` makes them available as session variables. Session variables outlive the transaction on the pooled connection, so Navree clears them right before `COMMIT` or `ROLLBACK` ([how Navree behaves on MySQL](/docs/database/getting-started/#how-navree-behaves-on-mysql)).

When no trigger or policy of yours reads the actor or the request id, set `database.transaction_settings = false`: PostgreSQL, MySQL and MariaDB transactions then start with a plain `BEGIN`, one statement (on MySQL two) fewer per unit of work. `uow.actor()` and `uow.request_id()` are unaffected.

Besides your own statements, model queries and writes given the unit of work (`Deal::create(&uow, ..)`) and the record checks of `#[can(.., from = "id")]` routes begin the transaction too.

### The actor and the request id

`uow.actor()` is the signed-in user's id (`Option<Uuid>`), and `uow.request_id()` the request's `X-Request-Id`. The audit log records both. A service can use the actor directly:

```rust
let author = uow.actor().ok_or_else(AppError::unauthenticated)?;
```

## After-commit hooks

Some work must only happen once the data is safely stored: telling other users about a change, or calling another system. Register it with `uow.after_commit`:

```rust title="src/modules/deals/service.rs"
use navree::contracts::Broadcaster;
use serde_json::json;

/// Broadcasts `deal` once the unit of work commits (never for a rollback).
pub fn broadcast_after_commit(uow: &Uow, broadcaster: Arc<dyn Broadcaster>, deal: &Deal) {
    let data = json!({ "deal": deal });
    uow.after_commit(move || {
        Box::pin(async move {
            let channels = vec!["private-deals".to_owned()];
            if let Err(error) = broadcaster
                .broadcast(channels, "deal.updated".to_owned(), data)
                .await
            {
                tracing::warn!(%error, "the deal.updated broadcast failed");
            }
        })
    });
}
```

Hooks run after a successful commit, in the order you registered them. A rollback drops them. A hook returns nothing, so it handles its own errors: the change has already been committed and the response can no longer fail because of it.

Several Navree services join the current unit of work for you, so you rarely need a hook for them:

- `Queue::dispatch` (and `later`, `push` and the `dyn Dispatcher`) called while a unit of work is running queues the job only if it commits; `dispatch_in(&uow, job)` names the unit of work explicitly. With the database queue driver the job row is written in the same transaction. See [queues](/docs/digging-deeper/queues/).
- `Mailer::queue` hands the mail to the queue, so in an app with `QueueModule` queued mail waits for the commit too. (Without a queue it sends at once.)
- `Notifier::send` called while a unit of work is running writes the database notification in its transaction and sends the other channels only once it commits. See [notifications](/docs/digging-deeper/notifications/).

## The current unit of work

`Uow::current()` returns the unit of work of the running task: the request's while its handler runs, or the one `uow.scope(future)` (or `Db::transaction`) runs code with. It returns `None` anywhere else, including inside tasks you start with `tokio::spawn`, which don't inherit it.

Code that can't take a `&Uow` parameter uses it to join the request's transaction: that is how `Queue::dispatch` and a `&Db` executor work. The current unit of work may already be finished (a handler can commit early), so check `uow.is_finished().await` before writing through it. `uow.same_as(&other)` tells whether two handles are the same unit of work.

## Outside HTTP: jobs, commands and seeders

Outside a request, nothing creates a unit of work for you. Create one from `Db`.

### Opening one, and `Db::transaction`

`db.uow(actor, request_id)` opens a unit of work. Run your code in its `scope`, so `&Db` executors join it too, then commit or roll back yourself. Here is a command that closes stale deals:

```rust title="src/modules/deals/commands.rs"
use chrono::{Duration, Utc};
use navree::db::Db;
use navree::kernel::CommandSpec;
use navree::prelude::*;

pub fn close_stale_command() -> CommandSpec {
    CommandSpec::new(
        "deals:close-stale",
        "Mark leads untouched for 90 days as lost",
        close_stale,
    )
}

async fn close_stale(ctx: AppContext, _args: Vec<String>) -> Result<(), BoxError> {
    let db = ctx.get::<Db>().await?;
    let uow = db.uow(None, None).await;
    let result: navree::orm::Result<usize> = uow
        .scope(async {
            let cutoff = Utc::now() - Duration::days(90);
            let stale = Deal::query()
                .where_(Deal::STAGE.eq(Stage::Lead))
                .where_(Deal::UPDATED_AT.lt(cutoff))
                .get(&uow)
                .await?;
            let count = stale.len();
            for mut deal in stale {
                deal.stage = Stage::Lost;
                deal.save(&uow).await?;
            }
            Ok(count)
        })
        .await;
    match result {
        Ok(closed) => {
            uow.commit().await?;
            println!("Closed {closed} stale deals.");
            Ok(())
        }
        Err(error) => {
            uow.rollback().await?;
            Err(error.into())
        }
    }
}
```

Each `save` records a change event, so the audit log shows the 90-day sweep deal by deal. Register the command in the module with `m.command(close_stale_command())` and run it with `navree deals:close-stale`. See [console commands](/docs/digging-deeper/cli/).

`db.transaction(|uow| async move { .. })` is the shorter form for a closure that returns `Result<_, DbError>`, as statement-only work does: it commits when the closure returns `Ok`, rolls back when it returns `Err`, and the unit of work is the current one while it runs. It has no actor.

### With an actor

The command above passes no actor. When the work is done for someone (a job a user started, say), pass the user's id to `db.uow(actor, request_id)`:

```rust title="src/modules/deals/jobs.rs"
use navree::contracts::{Job, JobContext};
use navree::db::Db;
use navree::prelude::*;
use serde::{Deserialize, Serialize};
use uuid::Uuid;

/// Deletes a deal on behalf of `requested_by`.
#[derive(Debug, Serialize, Deserialize)]
pub struct DeleteDeal {
    pub deal_id: Uuid,
    pub requested_by: Uuid,
}

impl Job for DeleteDeal {
    const NAME: &'static str = "deals.delete";

    async fn handle(self, ctx: JobContext) -> Result<(), BoxError> {
        let db = ctx.app.get::<Db>().await?;
        let uow = db.uow(Some(self.requested_by), None).await;
        let result = uow
            .scope(async {
                let mut deal = Deal::find_or_fail(&uow, self.deal_id).await?;
                deal.delete(&uow).await?;
                Ok::<_, navree::orm::OrmError>(())
            })
            .await;
        match result {
            Ok(()) => Ok(uow.commit().await?),
            Err(error) => {
                uow.rollback().await?;
                Err(error.into())
            }
        }
    }
}
```

The audit log then records the deletion as `requested_by`'s. Jobs get no unit of work automatically: `JobContext` gives you the app, and you open one as above.

Committing or rolling back a finished unit of work does nothing. Committing one that never opened a transaction only runs its after-commit hooks, unless changes were recorded by hand, in which case it first opens a transaction for the change observers.

## Locking rows

Two requests that read a row and then write it can overwrite each other's work. The databases prevent it differently:

- **SQLite** serialises writers: every unit of work starts with `BEGIN IMMEDIATE`, so a second writer waits until the first commits. There is nothing to lock.
- **PostgreSQL** and **MySQL** run units of work side by side, so read the rows you're about to change with `SELECT ... FOR UPDATE`.

Model queries lock with `lock_for_update()`, which writes `FOR UPDATE` where the database has row locks and leaves it out on SQLite ([locking rows](/docs/orm/query-builder/#locking-rows)):

```rust
/// The deals of `stage`, locked for the rest of the unit of work where the
/// database supports it.
pub async fn column(uow: &Uow, stage: Stage) -> navree::orm::Result<Collection<Deal>> {
    Deal::query()
        .where_(Deal::STAGE.eq(stage))
        .lock_for_update()
        .get(uow)
        .await
}
```

For a statement you write yourself, `uow.lock_for_update()` tells you which case you're in (true on PostgreSQL and MySQL, false on SQLite): add `FOR UPDATE` to the SQL only when it's true. The CRM locks a pipeline column this way before it renumbers the deals in it, and the record checks of `#[can(.., from = "id")]` routes lock the record they load. The ORM's real-server suite runs row locks between two units of work on PostgreSQL and MySQL: a second unit of work locking the same row waits until the first commits, then reads its change.

## Change events and observers

Models record a [change event](/docs/database/entities-and-repositories/#change-events) for each record they create, save or delete through the unit of work, and `uow.record_change` records one by hand. When the unit of work commits, every **change observer** receives all of them, in order, inside the transaction, right before it commits. `AuditModule` is an observer: it writes the audit rows, so they commit or roll back with the data they describe.

To write your own, implement `ChangeObserver` and register it with `m.change_observer::<O>()`. This one keeps a history of deal stages:

```rust title="src/modules/deals/stage_history.rs"
use navree::BoxFuture;
use navree::db::{ChangeEvent, ChangeObserver, ChangeOp, DbError, Executor, Statement, Value};
use navree::prelude::*;

/// Writes a `deal_stage_changes` row whenever a deal's stage changes, in the
/// same transaction as the change.
#[injectable]
pub struct StageHistory;

impl ChangeObserver for StageHistory {
    fn observe<'a>(
        &'a self,
        uow: &'a Uow,
        changes: &'a [ChangeEvent],
    ) -> BoxFuture<'a, Result<(), DbError>> {
        Box::pin(async move {
            for change in changes {
                if change.entity != "deals" || change.op != ChangeOp::Updated {
                    continue;
                }
                let (Some(old), Some(new)) = (&change.old, &change.new) else {
                    continue;
                };
                let Some(to) = new.get("stage").and_then(|v| v.as_str()) else {
                    continue;
                };
                let from = old.get("stage").and_then(|v| v.as_str());
                uow.execute(&Statement::portable(
                    "INSERT INTO deal_stage_changes (deal_id, from_stage, to_stage, changed_by) \
                     VALUES (?, ?, ?, ?)",
                    [
                        Value::from(change.id.as_str()),
                        Value::from(from.map(str::to_owned)),
                        Value::from(to),
                        Value::from(uow.actor().map(|id| id.to_string())),
                    ],
                ))
                .await?;
            }
            Ok(())
        })
    }
}
```

```rust title="src/modules/deals/mod.rs"
impl DealsModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.migrations(migrations::migrations());
        m.change_observer::<StageHistory>();
    }
}
```

An observer:

- runs once per commit, and only when changes were recorded;
- writes through the `uow` it is given, which is an `Executor` until the commit ends. The unit of work counts as finished once the commit starts, so opening a new transaction on it fails with "the unit of work is already committed or rolled back";
- can veto the commit: an error rolls the whole unit of work back, and the request answers 500 (409 when the error is a unique or foreign-key violation).

Queue jobs from an observer with `Queue::push_observed(uow, envelope)`, not `dispatch`: with the database driver the row is written through the `uow` the observer is given, so it joins the commit it observes (a commit that fails queues nothing). `dispatch` from an observer would write through the pool on SQLite, and that write waits for the very transaction that is committing.

## SQLite and concurrency

A unit of work holds one pool connection from its first query until it commits, and on SQLite it holds the database's write lock for that whole time. Two rules follow:

- **Don't wait for a second connection while you hold one.** Read through the `&Uow`, or through a `&Db` executor in code that has none (it joins the current unit of work), never through a transaction or pool connection you open yourself in a request. Otherwise, once about `max_connections` requests run together, each holds a connection while waiting for another, and they fail with "database is locked".
- **Keep units of work short.** Other writers queue behind yours for up to the 5-second busy timeout.

A transaction you begin yourself with `db.begin()` is a plain `BEGIN`, and SQLite fails a plain transaction that reads and then writes with "database is locked" at once, without waiting for the busy timeout, when another connection holds the write lock at that moment. If it may write after reading, begin it with `db.begin_for_write()` (or `db.begin_with(TxOptions::new().immediate())`): it takes the write lock when the transaction begins and queues for it. Migrations do this themselves.

The CRM has a regression test for the first rule: it boots the whole API with `database.max_connections = 1` and drives every route that combines a record check, `CurrentUser` and an embedded user. Any request that needed a second connection would time out. It's a cheap test to copy into your own app ([database tests](/docs/testing/database-tests/#catching-pool-starvation)).

## Testing

In a test, create a unit of work, write through it and look at what it recorded before you roll it back:

```rust
let db = app.get::<Db>().await;
let uow = db.uow(Some(owner), None).await;
let mut deal = Deal::find_or_fail(&uow, deal_id).await.unwrap();
deal.stage = Stage::Won;
deal.save(&uow).await.unwrap();

let changes = uow.changes();
assert_eq!(changes[0].op, ChangeOp::Updated);
assert_eq!(changes[0].old, Some(json!({ "stage": "lead" })));
assert_eq!(changes[0].new, Some(json!({ "stage": "won" })));
uow.rollback().await.unwrap();
```

Over HTTP, query the database after the request to see whether the work was committed. [Database tests](/docs/testing/database-tests/) has more.
