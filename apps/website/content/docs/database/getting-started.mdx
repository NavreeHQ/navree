A Navree app works with its data through the [ORM](/docs/orm/getting-started/): models are plain Rust structs with `#[derive(Model)]`, queried with typed columns and saved as records that track their own changes. Underneath, the `navree-db` crate (the `db` feature of the `navree` facade, on by default) owns the connections, which run on SQLx, and adds what an application needs around them:

- a connection pool configured from the `database` section of your configuration;
- a [unit of work](/docs/database/unit-of-work/) per request: one lazy transaction that commits when the response succeeds, and records every change for the [audit log](/docs/security/audit-log/);
- [migrations](/docs/database/migrations/) owned by modules and written with the [schema builder](/docs/database/schema-builder/) (with [TimescaleDB hypertables](/docs/database/timescaledb/)), [run](/docs/database/running-migrations/) by `migrate` and its sibling commands and [squashed](/docs/database/squashing-migrations/) by `schema:dump`;
- [seeders](/docs/database/seeding-and-factories/) and the `db:seed` command;
- [pagination](/docs/database/pagination/) with `{data, meta}` page responses;
- [models and records](/docs/database/entities-and-repositories/): how a table maps to a model, and the change events its writes record.

Navree supports four SQL databases:

- **TimescaleDB** is the default: PostgreSQL with hypertables for time-series data. `navree new` sets an app up for it and [Dock](/docs/tools/dock/) runs it on your machine ([below](#timescaledb)).
- **PostgreSQL** without TimescaleDB works the same; tables declared as hypertables are regular tables there ([below](#postgresql)). Both need the `postgres` Cargo feature.
- **MySQL** and **MariaDB** are behind the `mysql` Cargo feature ([below](#mysql-and-mariadb)).
- **SQLite** is behind the `sqlite` Cargo feature, and it is bundled: the feature compiles SQLite into your app, so there is nothing to install. Tests run on it, each in a file of its own ([below](#sqlite)).

Each driver is a feature of its own, and none is on by default: a PostgreSQL or MySQL build compiles no SQLite, and a SQLite build compiles no PostgreSQL or MySQL driver. Turn on the one you use (`navree = { git = "https://github.com/NavreeHQ/navree", features = ["postgres"] }`), and a second one only when the app talks to two kinds of server. An app whose `database.url` names a driver it was built without fails to boot with a message naming the feature to enable (for example "enable the `sqlite` feature of navree-db").

`navree new my-app` makes a TimescaleDB app with the `postgres` feature; `--database postgres`, `--database mysql` and `--database sqlite` make the others, each with its own feature. MongoDB is supported too, by the ORM's [document driver](/docs/orm/mongodb/).

## Configuration

`DatabaseModule` reads the `database` section of your configuration. Every key is optional:

```toml title="config/app.toml"
[database]
url = "postgres://navree:navree@127.0.0.1:5432/my_app"
max_connections = 10
min_connections = 0
connect_timeout_secs = 8
test_before_acquire = false
idle_timeout_secs = 600
max_lifetime_secs = 1800
log_queries = false
slow_query_ms = 200
migrate_on_boot = false
transaction_settings = true
```

| Key | Default | What it does |
|---|---|---|
| `url` | `sqlite://storage/app.db?mode=rwc` | The connection URL: `postgres://...` (TimescaleDB or PostgreSQL), `mysql://...`, `mariadb://...` or `sqlite://...`. A new app sets a TimescaleDB URL, the one Dock's `postgres` service serves. Without a URL, Navree uses a SQLite file, which needs the `sqlite` feature: an app built without it stops at boot and asks for the feature or a URL. |
| `read_urls` | `[]` | Read replicas of the database at `url`: reads outside a transaction go to them in turn, writes and transactions to `url`. From the environment, a comma-separated list. See [read replicas](/docs/orm/connections-and-transactions/#read-replicas). |
| `sticky` | `true` | After a unit of work wrote, its task reads from the writer, so a request sees its own writes while replicas catch up. |
| `direct_url` | unset | A direct connection to the same database that bypasses a transaction-mode pooler (PgBouncer, RDS Proxy) in front of `url`. Migrations run on it, and `db.direct()` hands it out for session work such as advisory locks. It must name the same kind of database as `url`. |
| `max_connections` | `10` | The most connections in the pool. Must be at least 1. |
| `min_connections` | `0` | The connections kept open while idle. Must not exceed `max_connections`. |
| `connect_timeout_secs` | `8` | How long opening a connection may take. Waiting for a free connection from the pool times out after four times this. |
| `test_before_acquire` | `false` | Pings every connection taken from the pool before handing it out, which costs one round trip per checkout. Off, only a connection that sat idle in the pool for 30 seconds or more is pinged first ([below](#the-pool)). |
| `idle_timeout_secs` | `600` | Closes a connection idle in the pool this long, as long as `min_connections` stay open. `0` keeps idle connections. |
| `max_lifetime_secs` | `1800` | Replaces a connection once it is this old. `0` sets no limit. |
| `log_queries` | `false` | Logs every statement at debug level. |
| `slow_query_ms` | `200` | Logs statements slower than this at warn level. `0` turns it off. When you leave it out, the logger's `log.slow_query_ms` applies. |
| `migrate_on_boot` | `false` | Runs pending migrations when the app boots. Handy in development and tests; run `migrate` in deployments instead. |
| `transaction_settings` | `true` | Makes the actor and request id of every unit of work readable in SQL: `navree.actor` and `navree.request_id` on PostgreSQL, `@navree_actor` and `@navree_request_id` on MySQL and MariaDB. Turn it off when no trigger or policy reads them: each transaction then saves the statement that sets them (and on MySQL the one that clears them). |

The sections `[database.postgres]` ([session settings](#session-settings)), `[database.mysql]` ([SQL mode and isolation level](#sql-mode-and-isolation-level)) and `[database.sqlite]` ([SQLite settings](#sqlite-settings)) shape the session of every connection to that kind of database, and `[database.connections.<name>]` adds [named connections](/docs/orm/connections-and-transactions/#named-connections), each with any key of this section.

Like every section, these keys can come from environment variables with the `APP_` prefix and `__` between levels: `APP_DATABASE__URL` sets `database.url`. Keep a production URL, and its password, in the environment rather than in `config/app.toml`. A `.env` entry only fills keys that `config/app.toml` leaves out, and a new app's `config/app.toml` sets `database.url`, so `APP_DATABASE__URL` in `.env` has no effect there. See [configuration](/docs/getting-started/configuration/) for the order in which sources apply.

An invalid section stops the boot with a message naming `database` and the problem (an empty `url`, `max_connections = 0`, `min_connections` above `max_connections`, a `direct_url` of another kind of database than `url`, a `database.mysql.modes` entry that isn't an SQL mode name, or a value `database.postgres` or `database.sqlite` doesn't accept). Navree never prints the password of the URL: `DbOptions`'s `Debug` output and connection errors show it as `***`.

## Registering the module

Add `DatabaseModule` to your app's root, after `ConfigModule`, and `OrmModule` after it:

```rust title="src/app.rs"
use navree::prelude::*;

pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(HttpModule::from_config())
        .module(DatabaseModule::from_config())
        .module(OrmModule::from_config())
        .module(CompaniesModule)
        .module(DealsModule)
}
```

`navree new` writes both. `OrmModule` reads the `orm` section, which configures the models ([ORM configuration](/docs/orm/getting-started/#configuration)). `DatabaseModule::from_config()` and a plain `.module(DatabaseModule)` both read the `database` section when the app boots. To configure the module in code instead, pass the options to `for_root`:

```rust
use navree::db::DbOptions;

Navree::app().module(DatabaseModule::for_root(DbOptions {
    url: "postgres://navree:navree@127.0.0.1:5432/my_app".into(),
    max_connections: 5,
    ..DbOptions::default()
}))
```

The module is global, so every module can inject `Arc<Db>` and `Arc<DbOptions>` without importing it. It also brings:

- the unit-of-work layer of the request pipeline and the `Uow` extractor;
- the mapping of database errors to error responses ([below](#database-errors));
- the `database` health check, which pings the pool (served by `GET /health/ready` when the app has `ObserveModule`, see [health and metrics](/docs/digging-deeper/health-and-metrics/));
- the commands `migrate`, `migrate:install`, `migrate:status`, `migrate:rollback`, `migrate:reset`, `migrate:refresh`, `migrate:fresh`, `schema:dump`, `db:seed`, `db:monitor` (the connections each database has open) and `db` (the database's own client: `psql`, `mysql`, `mariadb` or `sqlite3`; [watching statements](/docs/orm/connections-and-transactions/#watching-statements));
- closing the pool when the app shuts down, so SQLite checkpoints its write-ahead log.

## TimescaleDB

<Badge feature="postgres" /> TimescaleDB is PostgreSQL with an extension for time-series data, so it connects through the same driver: a `postgres://` URL and the `postgres` feature of the facade. Your tables are regular PostgreSQL tables until a migration makes one a [hypertable](/docs/database/timescaledb/), and Navree's own time-series tables (the audit log, webhook deliveries, job history, Lighthouse's events) become hypertables in their modules' migrations.

A new app is set up for it: `navree new` turns on the feature, writes the URL of Dock's `postgres` service into `config/app.toml`, and adds a `dock.toml` that runs TimescaleDB 2.31 on PostgreSQL 17:

```sh
navree dock up               # TimescaleDB on 127.0.0.1:5432
navree dev
```

In production, point `APP_DATABASE__URL` at a server with TimescaleDB and set `APP_SCHEMA__TIMESCALEDB=require`, so a migration stops instead of falling back to regular tables on a server without it. [TimescaleDB](/docs/database/timescaledb/#running-it) covers running it, and which tables to make hypertables.

## PostgreSQL

<Badge feature="postgres" /> Turn on the `postgres` feature of the facade. It adds SQLx's PostgreSQL driver to `navree-db` (and turns on `db`):

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["postgres"] }
```

The crates aren't on crates.io yet, so the dependency comes from git. An app made by `navree new` depends on the checkout the CLI was built from instead, with the feature already on for TimescaleDB and PostgreSQL apps: `navree = { path = "...", features = ["postgres"] }`.

Then point `database.url` at the server with an environment variable, which overrides `config/app.toml`:

```sh
export APP_DATABASE__URL=postgres://crm:secret@db.internal:5432/crm
```

Without the feature, the app fails to boot with "cannot connect to postgres://crm:***@db.internal:5432/crm: ... (enable the `postgres` feature of navree-db)".

On PostgreSQL, Navree behaves differently in a few places:

- Each unit-of-work transaction sets two transaction-local settings, `navree.actor` (the signed-in user's id, or an empty string) and `navree.request_id`, with one `SELECT set_config(..)` right after `BEGIN`. Triggers and row-level security policies can read them with `current_setting('navree.actor', true)`. With `transaction_settings = false` the statement isn't sent and the settings stay unset.
- `Uow::lock_for_update()` is true, so queries that call `lock_for_update()` and the record checks of `#[can(.., from = "id")]` routes read rows with `SELECT ... FOR UPDATE`. See [locking rows](/docs/database/unit-of-work/#locking-rows).
- `migrate:fresh` drops every table of the current schema with `CASCADE`.
- The case-insensitive search helpers use `LOWER(..) LIKE` ([below](#searching-text)).

<Callout type="warning" title="What has been run on PostgreSQL">

Most tests of Navree and of the reference CRM run on SQLite. On PostgreSQL 17, the app behind Navree's [performance](/performance/) measurements (`bench/frameworks/navree`) has exercised, under load: the pool, the unit of work (`BEGIN`, the `set_config` call, `COMMIT`), paginated queries, record inserts and navree-auth's user lookup. No Navree code had to change for it.

The ORM's real-server suite runs on PostgreSQL 17 with TimescaleDB 2.31, and on MySQL 8.4: records round-tripping every column type and cast (vectors with pgvector), conditions with JSON operators and regular expressions, joins, aggregates and compound queries, bulk writes and upserts, offset and cursor pagination, chunks, streams and cursors, row locks between two units of work (`SKIP LOCKED`, `NOWAIT` and shared locks), the unit of work's change events and rollbacks, relations and eager loading, model events, soft deletes and pruning, time buckets, statement timeouts and, on PostgreSQL, reads retried after a lost connection. `cargo test -p navree-orm --features postgres,mysql --test servers` runs it against your servers.

Migrations have run against PostgreSQL 17 with TimescaleDB 2.31 (and against MySQL 8.4) in the opt-in real-server tests of navree-schema and navree-db: the schema builder's statements, hypertables with their policies and continuous aggregates, migrations written with the schema builder, `--pretend`, `migrate:rollback`, `migrate:refresh`, `migrate:fresh`, and schema dumps loaded into empty databases.

The facade's `time_series` suite boots the audit, webhooks, Fleet, scheduling and Lighthouse modules on the same servers: their time-series tables become hypertables with the documented time columns, chunk intervals and keys on TimescaleDB, and stay regular tables with time indexes on MySQL; running their conversions again changes nothing; `audit:prune` drops whole chunks; and the [time-bucket queries](/docs/database/timescaledb/#time-bucket-queries) return the same buckets as on SQLite.

The queue's `SKIP LOCKED` job reservation, which is outside the ORM, has a real-server suite of its own: `NAVREE_TEST_DATABASE=postgres cargo test -p navree-queue --features postgres` with `NAVREE_TEST_POSTGRES_URL` set (see [Queues](/docs/digging-deeper/queues/)).

</Callout>

### Session settings

The `database.postgres` section shapes the session of every connection the pool opens. Every key is optional:

```toml title="config/app.toml"
[database.postgres]
search_path = ["app", "public"]
timezone = "UTC"
application_name = "crm-api"
synchronous_commit = "on"
isolation_level = "read_committed"
ssl_mode = "prefer"
```

| Key | What it does |
|---|---|
| `search_path` | The schemas unqualified names resolve in, in order. A list, or a comma-separated string from the environment (`APP_DATABASE__POSTGRES__SEARCH_PATH=app,public`). Each entry must be a schema name. |
| `timezone` | The session's time zone, such as `UTC` or `Europe/Berlin`. |
| `application_name` | The name the server shows for these connections (`pg_stat_activity.application_name`): at most 63 printable characters, without quotes or backslashes. |
| `synchronous_commit` | `on`, `off`, `local`, `remote_write` or `remote_apply`. |
| `isolation_level` | The isolation level transactions start with (`default_transaction_isolation`): `read_uncommitted`, `read_committed`, `repeatable_read` or `serializable`, in any case, with spaces or hyphens if you like. |
| `ssl_mode` | TLS: `disable`, `allow`, `prefer` (the default), `require`, `verify-ca` or `verify-full`. It overrides the URL's `sslmode`. |

Other databases ignore this section.

### The pool

Navree doesn't ping a connection every time it takes one from the pool: on a busy app that ping is one round trip on every query. A connection that has sat idle in the pool for 30 seconds or more is pinged first, since a server, a proxy or a firewall may have dropped it in the meantime; a connection in steady use goes straight out. Set `test_before_acquire = true` to ping on every checkout instead.

Connections idle for `idle_timeout_secs` are closed (down to `min_connections`), and connections older than `max_lifetime_secs` are closed and replaced with new ones as they are needed.

## MySQL and MariaDB

<Badge feature="mysql" /> Turn on the `mysql` feature of the facade. It adds SQLx's MySQL driver to `navree-db` (and turns on `db`). MariaDB speaks MySQL's protocol, so the same driver connects to both:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["mysql"] }
```

Then point `database.url` at the server. `mariadb://` works the same as `mysql://`:

```sh
export APP_DATABASE__URL=mysql://crm:secret@db.internal:3306/crm
```

Without the feature, the app fails to boot with "cannot connect to mysql://crm:***@db.internal:3306/crm: ... (enable the `mysql` feature of navree-db)". Navree supports MySQL 8.0 or later and MariaDB 10.6 or later.

### Connections

Every connection the pool opens starts its session with:

- the time zone `+00:00`, so `TIMESTAMP` columns store and read UTC;
- the `utf8mb4` character set, with the server's default collation for it;
- `PIPES_AS_CONCAT` and `NO_ENGINE_SUBSTITUTION` added to the SQL mode;
- strict SQL mode and, when you set one, an isolation level, from [`database.mysql`](#sql-mode-and-isolation-level).

The URL also takes the driver's parameters:

| Parameter | What it does |
|---|---|
| `ssl-mode` | `DISABLED`, `PREFERRED` (the default: TLS when the server offers it), `REQUIRED`, `VERIFY_CA` or `VERIFY_IDENTITY` (`VERIFY_CA` checks the server's certificate; `VERIFY_IDENTITY` also checks its host name) |
| `ssl-ca`, `ssl-cert`, `ssl-key` | The CA certificate file to verify the server with; a client certificate and its key |
| `socket` | Connects through the Unix socket at this path instead of TCP |
| `charset`, `collation` | The connection's character set (default `utf8mb4`) and collation (default: the server's for that character set) |
| `timezone` | The session time zone (default `+00:00`). Keep UTC: Navree stores and reads times as UTC. |
| `statement-cache-capacity` | How many prepared statements each connection keeps (default 100) |

For example, `mysql://crm:secret@db.internal:3306/crm?ssl-mode=VERIFY_IDENTITY&ssl-ca=/etc/ssl/db-ca.pem`.

### TLS and sign-in

MySQL 8 generates a certificate when it first starts, so with the default `ssl-mode=PREFERRED` connections use TLS out of the box.

MySQL 8's default account type, `caching_sha2_password`, sends the account's password itself the first time the account signs in after the server starts; later sign-ins use a hash the server caches. Over TLS that needs nothing more. Without TLS (`ssl-mode=DISABLED`, or a server that offers none), MySQL wants the password encrypted with the server's RSA key, and Navree leaves that exchange out: it needs the `rsa` crate, which Navree's crypto policy keeps out of the dependency tree. Such a connection fails with "... RSA auth backend disabled ... (this caching_sha2_password account needs TLS: use `ssl-mode=PREFERRED`, the default, or `REQUIRED` against a server that offers TLS)". Accounts that use `mysql_native_password`, MariaDB's default, sign in without TLS.

### SQL mode and isolation level

The `database.mysql` section shapes the session of every connection. Every key is optional:

```toml title="config/app.toml"
[database.mysql]
strict = true
# modes = ["STRICT_ALL_TABLES", "NO_ENGINE_SUBSTITUTION"]
# isolation_level = "read_committed"
```

| Key | Default | What it does |
|---|---|---|
| `strict` | `true` | Adds `ONLY_FULL_GROUP_BY`, `STRICT_TRANS_TABLES`, `NO_ZERO_IN_DATE`, `NO_ZERO_DATE` and `ERROR_FOR_DIVISION_BY_ZERO` to the server's SQL mode. A value too long or out of range for its column, or a zero date, is then an error instead of being cut or replaced, and a query that selects a column it neither groups by nor aggregates is refused, as on PostgreSQL. `false` removes `STRICT_TRANS_TABLES` and `STRICT_ALL_TABLES` from the session instead, whatever the server's default. |
| `modes` | unset | The session's exact SQL mode, replacing the server's, `strict`'s and SQLx's: a list, or a comma-separated string from the environment (`APP_DATABASE__MYSQL__MODES=STRICT_ALL_TABLES,NO_ENGINE_SUBSTITUTION`). `[]` clears the SQL mode. An entry that isn't a mode name (letters, digits and underscores) stops the boot. |
| `isolation_level` | unset | `read_uncommitted`, `read_committed`, `repeatable_read` or `serializable`, in any case, with spaces or hyphens if you like (`"READ COMMITTED"`). Unset keeps the server's level, `REPEATABLE READ` unless it's configured otherwise. |

`read_committed` is worth knowing about. Under MySQL's default `REPEATABLE READ`, InnoDB locks the gaps between index records as well as the records, so concurrent inserts into the same range can deadlock; `READ COMMITTED` locks only the records, and every statement sees the latest commits, as on PostgreSQL.

### How Navree behaves on MySQL

- Each unit-of-work transaction begins with `BEGIN`, then `SET @navree_actor = ?, @navree_request_id = ?`: the signed-in user's id as text, or `NULL`, and the request id. Triggers can read them. (With `transaction_settings = false`, neither this statement nor the one clearing the variables is sent.) The UUIDs that models write are 16 bytes on MySQL, in `BINARY(16)` columns ([below](#types-and-collations)), so a trigger that records who changed a row converts the text:

  ```sql
  CREATE TRIGGER deals_updated_by BEFORE UPDATE ON deals FOR EACH ROW
  SET NEW.updated_by = UNHEX(REPLACE(@navree_actor, '-', ''));
  ```

  Session variables belong to the connection, not to the transaction, and the connection goes back to the pool. Navree therefore clears them right before `COMMIT` or `ROLLBACK`, and rolls the unit of work back if it can't. Outside a unit of work they're `NULL`.
- MySQL has no row-level security, so with [workspaces](/docs/workspaces/isolation/) isolation is query scoping alone: `WorkspaceRepo` filters every query by the workspace, and nothing in the database stops a query that leaves the filter out.
- `Uow::lock_for_update()` is true, so queries that call `lock_for_update()` and the record checks of `#[can(.., from = "id")]` routes read rows with `SELECT ... FOR UPDATE`. See [locking rows](/docs/database/unit-of-work/#locking-rows).
- A deadlock (error 1213) makes MySQL roll back the whole transaction at once. Whatever the unit of work runs after that commits on its own, and its rollback can't undo it, so let the error end the request (`?` does, with a 500) instead of carrying on.
- MySQL commits every DDL statement on its own, so migrations run outside a transaction unless they ask for one. See [transactions](/docs/database/migrations/#transactions). `navree_migrations.applied_at` is a `DATETIME` holding UTC.
- `migrate:fresh` drops every base table of the current database in one `DROP TABLE`, on one connection with `FOREIGN_KEY_CHECKS = 0`, and turns the checks back on before the connection returns to the pool.
- A duplicate key (error 1062) and foreign key failures (1451, 1452 and their relatives) answer 409, as on every database ([below](#database-errors)).
- The case-insensitive [search helpers](#searching-text) ignore case under any collation and never ignore accents.
- Under `REPEATABLE READ`, a paginated query on a unit of work's transaction reads its `COUNT(*)` and its page from the transaction's single snapshot, so the total matches the page.

### Types and collations

The [schema builder](/docs/database/columns/#column-types) writes MySQL's types for you, and a few of them behave differently:

- Models write a `Uuid` as its 16 bytes, which belong in a `BINARY(16)` column. The schema builder's `uuid_primary()`, `uuid` and `foreign_uuid` columns are `CHAR(36)` on MySQL, which refuse those bytes, so declare UUID columns as binaries there ([UUID columns on MySQL](/docs/database/columns/#uuid-columns-on-mysql)). A UUID v7 sorts by creation time, so [cursor pagination](/docs/orm/pagination-and-streaming/#cursor-pagination) pages in creation order. In raw SQL, bind a `Uuid` value: a UUID string such as `'0199a7a0-…'` doesn't match a binary column (`UNHEX(REPLACE(?, '-', ''))` converts one).
- `timestamp_tz` columns (and `timestamps_tz()`) are `TIMESTAMP(6)`. They store UTC, but the type ends on 2038-01-19. `date_time_tz` columns are `DATETIME(6)`, which has no such limit, and `DateTime<Utc>` fields read and write both as UTC.
- Time columns keep microseconds, the schema builder's `default_time_precision`. A column declared without a precision (`.default_precision()`) keeps whole seconds, and MySQL rounds a longer fraction instead of storing it.
- Comparisons and unique indexes follow each column's collation. MySQL 8's default for `utf8mb4`, `utf8mb4_0900_ai_ci`, ignores case and accents: `WHERE name = 'equipe'` finds "Équipe", and a unique index refuses "Equipe" next to "Équipe". Give columns that must compare exactly a binary collation such as `utf8mb4_bin`.

<Callout type="note" title="What has been run on MySQL">

navree-db's MySQL test suite runs against MySQL 8.4: connections and their session settings, TLS sign-in, the unit of work and triggers reading its variables, model writes and row locks, offset and cursor pagination, the search helpers, migrations, rollbacks and `migrate:fresh`, constraint errors through HTTP, and the health check. To run it against your own server, give it a URL whose user may create databases (each test works in a database of its own):

```sh
NAVREE_TEST_MYSQL_URL=mysql://root:secret@127.0.0.1:3306/navree_test cargo test -p navree-db --features mysql --test mysql
```

The ORM's real-server suite runs on MySQL 8.4 as well ([above](#postgresql)), on tables whose UUID columns are `BINARY(16)`.

MariaDB connects through the same code but hasn't been run against a server yet, and the other modules' test suites (auth, queue, audit, workspaces and the rest) run on SQLite. Try them in a staging environment before you rely on them.

</Callout>

## SQLite

SQLite is the `sqlite` Cargo feature, and it is off unless you turn it on: `navree = { git = "https://github.com/NavreeHQ/navree", features = ["sqlite"] }`. `navree new my-app --database sqlite` writes that for you. The feature compiles the bundled SQLite library (a C library, built with the C compiler your Rust toolchain links with); a PostgreSQL or MySQL build compiles none of it. An app whose configuration has no `database.url` uses `sqlite://storage/app.db?mode=rwc`, and without the feature that default stops the boot with "enable the `sqlite` feature of navree-db", so an app on another database always sets its URL.

Tests run on SQLite, each in a file of its own, so an app on PostgreSQL turns the feature on for its tests only, in `[dev-dependencies]`, and its release build still compiles no SQLite. `navree new` writes this:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["postgres"] }

[dev-dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["sqlite"] }
```

Migrations that declare [hypertables](/docs/database/timescaledb/#one-migration-every-database) run on it too, as regular tables with the same keys and time indexes.

A SQLite URL names a file. `mode=rwc` creates the file if it doesn't exist, and Navree creates its directory, so `sqlite://storage/app.db?mode=rwc` works on a fresh checkout. A relative path is relative to the working directory the app runs in.

Navree opens every SQLite connection with:

- the write-ahead log (`journal_mode = WAL`), so readers don't block the writer;
- `busy_timeout = 5000`: a statement waits up to 5 seconds for a lock before failing;
- `foreign_keys = ON`, so foreign keys are enforced (SQLite's default is off).

Every unit-of-work transaction starts with `BEGIN IMMEDIATE`, which takes SQLite's write lock at once. Concurrent requests that write therefore queue for up to 5 seconds instead of failing halfway through. SQLite allows one writer at a time, so this is also its limit: a busy app that writes on most requests outgrows it.

<Callout type="warning" title="Don't use in-memory SQLite">

An in-memory database (`sqlite::memory:`) is private to one connection, so every connection in the pool would see a different, empty database. Tests use a temporary file instead; see [database tests](/docs/testing/database-tests/).

</Callout>

### SQLite settings

The `database.sqlite` section changes these, and adds pragmas, for every connection the pool opens. Every key is optional:

```toml title="config/app.toml"
[database.sqlite]
journal_mode = "wal"      # delete, truncate, persist, memory, wal or off
busy_timeout_ms = 5000    # how long a connection waits for a lock
foreign_keys = true
synchronous = "normal"    # off, normal, full or extra; SQLite's own default when unset
pragmas = { cache_size = "-20000", temp_store = "memory" }
```

`pragmas` runs further `PRAGMA name = value` statements on every connection: a name is letters, digits and `_`, a value letters, digits, `_`, `-` and `.`. Other databases ignore the section.

## Running queries

Queries go through [models](/docs/orm/models/): a struct with `#[derive(Model)]` maps a table, and its typed columns build the conditions:

```rust
let deals = Deal::query()
    .where_(Deal::STAGE.eq(Stage::Won))
    .latest()
    .get(&uow)
    .await?;
```

Every method that touches the database takes an **executor** first, and what Navree decides is which one you pass:

| Where the code runs | Executor |
|---|---|
| A handler, or a service that takes `&Uow` | The request's unit of work: `&uow` |
| A service with no `&Uow` | Its injected `Arc<Db>`, which joins the current unit of work |
| A command, seeder or test outside any unit of work | The pool, `&db`, or a unit of work you open and commit |

[Connections and transactions](/docs/orm/connections-and-transactions/) has the details, named connections and read replicas included.

### In a request

Take the request's unit of work as an extractor and pass it to the model. The transaction begins with the first statement and commits when the response status is below 400:

```rust title="src/modules/companies/controller.rs"
#[controller("/companies", version = "1")]
impl CompaniesController {
    #[get("/{id}")]
    #[authenticated]
    async fn show(&self, uow: Uow, Path(id): Path<Uuid>) -> Result<Json<Record<Company>>> {
        let company = Company::find_or_fail(&uow, id).await?;
        Ok(Json(company))
    }
}
```

`find_or_fail` answers 404 when no company has that id; [route model binding](/docs/orm/route-model-binding/) does the lookup for you. Services take the unit of work as a `&Uow` parameter rather than having it injected. [The unit of work](/docs/database/unit-of-work/) covers it in detail.

### In services without a unit of work

Some code can't take a `&Uow`: a service called from many places, or a trait whose signature you don't control. Inject `Arc<Db>` and pass it instead:

```rust title="src/modules/companies/directory.rs"
use navree::db::Db;
use navree::prelude::*;
use uuid::Uuid;

#[injectable]
pub struct CompanyDirectory {
    db: Arc<Db>,
}

impl CompanyDirectory {
    /// The company with `id`, unless it is soft-deleted.
    pub async fn find(&self, id: Uuid) -> navree::orm::Result<Option<Record<Company>>> {
        Company::find(&self.db, id).await
    }
}
```

A `Db` executor reads through the open transaction of the current task's unit of work (the request's, while a handler runs) when there is one, and through the pool otherwise; its writes join that unit of work too. That matters on SQLite: an open unit of work holds the write lock on its connection, and a request that then waits for a second pool connection can starve the pool once about `max_connections` requests run together. Reading through the transaction also sees the request's own uncommitted writes. `Company` declares [soft deletes](/docs/orm/scopes-and-soft-deletes/#soft-deletes), so `find` leaves deleted companies out by itself.

Where no unit of work is running (commands, seeders, test assertions), `&db` runs on the pool. To write atomically there, open a unit of work and commit it ([transactions in commands and jobs](/docs/orm/connections-and-transactions/#transactions-in-commands-and-jobs)).

### Raw SQL

When the query builder can't express a statement, write the SQL with `?` placeholders and pass the values; the ORM binds them on every database ([raw SQL](/docs/orm/query-builder/#raw-sql)):

```rust
use navree::orm::{raw, scalar};

let owned: Option<i64> =
    scalar(&db, raw("SELECT COUNT(*) FROM companies WHERE owner_id = ?", [owner_id])).await?;
```

Below the ORM, every executor (`&uow`, `&db`, a `Pool`, a `Transaction`) runs navree-db `Statement`s. `Statement::portable` takes `?` placeholders on every database; `Statement::new(backend, sql, values)` takes the backend's own (`$1`, `$2` on PostgreSQL). Rows come back as `Row`s whose columns you read with `get`:

```rust
use navree::db::{Executor, ExecutorExt, Statement};

let owner_id = Uuid::now_v7();
let statement = Statement::portable(
    "SELECT COUNT(*) AS n FROM companies WHERE owner_id = ?",
    [owner_id.into()],
);
let count: i64 = db.fetch_scalar(&statement).await?;

let rows = db.fetch_all(&Statement::text("SELECT id, name FROM companies")).await?;
for row in &rows {
    let name: String = row.get("name")?;
    println!("{name}");
}
```

`execute` runs a statement that returns no rows and reports how many it changed (`Executed { rows_affected, last_insert_id }`), `fetch_optional` and `fetch_one` read one row, `fetch` streams rows as the database sends them, and `execute_script` runs `;`-separated SQL without values. Errors are `DbError`s, classified the same way on every database ([below](#database-errors)).

### Searching text

SQLite's `LOWER`, `UPPER` and `LIKE` only fold ASCII letters, so `LOWER(name) LIKE '%équipe%'` misses "Équipe". On MySQL, comparisons follow the column's collation, which may ignore accents as well as case, or neither. The query builder has two column helpers that ignore case for every letter, and never ignore accents, on every database:

- `contains_ignore_case(term)`: the column contains `term`;
- `eq_ignore_case(value)`: the column equals `value`.

They are conditions for a model query's `where_`:

```rust
let companies = Company::query()
    .where_(Company::NAME.contains_ignore_case("équipe"))
    .get(&db)
    .await?;
```

On SQLite they build a `GLOB` pattern listing every case variant of each letter (`*[éÉ][qQ][uU][iI][pP][eE]*`); on PostgreSQL they use `LOWER(..) LIKE`. On MySQL and MariaDB they compare the lower-cased column byte for byte (`INSTR(CAST(LOWER(name) AS BINARY), CAST('équipe' AS BINARY)) > 0`), which ignores case under any collation, `_bin` and `_cs` ones included; the column must be `utf8mb4`, the connection's character set. Wildcards in the term (`%`, `_`, `*`, `?`) match themselves. Like any "contains" search, `contains_ignore_case` can't use an index, so it reads the whole table. The query builder's own `like` and `ilike` conditions ([conditions](/docs/orm/query-builder/#conditions)) fold case as each database does.

## Database errors

A handler can return an `OrmError` or a `DbError` with `?`. `DatabaseModule` turns it into an error response, and no SQL reaches the client:

| Error | Response |
|---|---|
| A missing record (`ErrorKind::NotFound`; `OrmError::ModelNotFound` from `find_or_fail`) | 404, "Not Found" |
| A unique constraint violation (`ErrorKind::UniqueViolation`) | 409, "A record with the same unique value already exists." |
| A foreign key violation (`ErrorKind::ForeignKeyViolation`) | 409, "The change conflicts with a related record." |
| Anything else | 500, logged with its details |

`DbError::kind()` classifies every error the same way on every database, with the server's own details in `code()` and `constraint()`; `is_unique_violation()`, `is_foreign_key_violation()`, `is_not_found()` and `is_retryable()` answer the questions a handler asks. `map_db_error(&error)` gives the response an error maps to, or `None` for a 500.

Navree recognises the violations on every database: SQLite's extended result codes, PostgreSQL's SQLSTATEs `23505` and `23503`, and MySQL's and MariaDB's error numbers (1062 for a duplicate entry, 1451 and 1452 for foreign keys, and their relatives, such as 1859 for a duplicate found while `ALTER TABLE` builds a unique index).

The same mapping applies to an error raised while the unit of work commits, after the handler returned: a constraint that is only checked at commit, or a constraint violation from a [change observer](/docs/database/unit-of-work/#change-events-and-observers), is a 409, and any other commit failure is a 500. The ORM's `OrmError` answers the same way, with a 404 for a record `find_or_fail` didn't find ([ORM errors](/docs/orm/getting-started/#errors)).

## Logging queries

Set `database.log_queries = true` to log every statement at debug level, and `database.slow_query_ms` to log slow ones at warn level. Both use the tracing target `navree_db::query`, so the [logger's](/docs/basics/logging/) level decides what you see. Only the SQL text is logged, never the bound values.
