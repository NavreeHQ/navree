## Introduction

<Badge feature="search" /> A CRM lives or dies by its search box. Typing "ada lov" should find Ada Lovelace the contact, Lovelace Analytics the company and the "Lovelace renewal" deal, ranked by relevance, in a few milliseconds, and only the records the person is allowed to see.

`navree-search` adds full-text and vector search to the entities you already have. You derive `Searchable` on a SeaORM model, register it with `SearchModule`, and from then on:

- every insert, update and delete made through [`Repo`](/docs/database/entities-and-repositories/) queues a sync job, so the index follows the database without code in your services;
- the `Search` service queries the index and returns your models, in relevance order, as a normal `Page`;
- `navree search:import Deal` builds or rebuilds an index from the table.

One API runs on five engines. Pick the one that fits your deployment and change it later without touching your queries:

| Engine | What it is | Good for |
|---|---|---|
| `postgres` | Full-text search in your PostgreSQL database (`tsvector`, GIN index, optional trigram typo tolerance) | Apps that want no extra service |
| `meilisearch` | A Meilisearch server | Typo tolerance and instant search out of the box |
| `typesense` | A Typesense server or cluster | High query volume, clustering |
| `tantivy` | An embedded Tantivy index on local disk, inside your binary | Single-server apps and offline tools |
| `memory` | An in-process index | Tests |

Vector search stores embeddings in **pgvector** or **Qdrant** next to the full-text index, so one query can mix keyword and semantic relevance.

## Installation

Turn on the `search` feature of the `navree` facade:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["search"] }
```

The `search` feature includes the PostgreSQL, Meilisearch, Typesense and memory engines; the server engines talk HTTP through [`navree-http-client`](/docs/digging-deeper/http-client/). The embedded engine compiles Tantivy into your binary, so it has a feature of its own:

```toml title="Cargo.toml"
navree = { git = "https://github.com/NavreeHQ/navree", features = ["search", "search-tantivy"] }
```

The `postgres` engine and the `pgvector` store need navree-db's PostgreSQL driver (the `postgres` feature). For local development, `navree dock:add meilisearch` starts a Meilisearch container next to your database (see [Dock](/docs/tools/dock/)).

## Configuration

Add `SearchModule` to your app root, after the database and the queue:

```rust title="src/app.rs"
use navree::prelude::*;

pub fn app(sources: ConfigSources) -> AppBuilder {
    Navree::app()
        .module(ConfigModule::for_root(sources))
        .module(DatabaseModule::from_config())
        .module(QueueModule::from_config()) // runs the sync jobs
        .module(SearchModule::from_config()) // section `search`
        .module(ContactsModule)
        .module(DealsModule)
}
```

The module is global: feature modules inject `Arc<Search>` without importing it. `from_config()`, and a plain `.module(SearchModule)`, read the `search` section:

```toml title="config/app.toml"
[search]
engine = "meilisearch"            # or postgres, typesense, tantivy, memory
url = "http://127.0.0.1:7700"     # meilisearch and typesense
prefix = "crm_"                   # put in front of every index name
queue = "search"                  # the queue sync jobs run on
sync = "queued"                   # queued | inline | off
chunk_size = 500                  # rows per batch for search:import
```

A queue other than the default one needs a worker: add it to `queue.queues` (`queues = ["default", "search"]`), or run `navree queue:work --queue search` next to your other workers.

Keep the engine's API key out of the TOML file. In `.env`:

```env title=".env"
APP_SEARCH__KEY=masterKey-from-your-meilisearch-server
```

Every key can come from the environment: prefix it with `APP_` and use `__` between levels, as in `APP_SEARCH__ENGINE=typesense` or `APP_SEARCH__TANTIVY__PATH=/var/lib/crm/search`. An invalid engine name, a missing `url` for a server engine or a missing `key` for Typesense fails the boot with a message that names the key.

To configure the module in code, pass an engine, or full `SearchOptions`, to `for_root`:

```rust
use navree::search::{Engine, SearchOptions};

// The engine alone, every other option at its default:
Navree::app().module(SearchModule::for_root(Engine::tantivy("storage/search")))

// Or the whole options struct:
Navree::app().module(SearchModule::for_root(SearchOptions {
    engine: Engine::meilisearch("http://127.0.0.1:7700"),
    prefix: "crm_".to_owned(),
    ..SearchOptions::default()
}))
```

### Choosing an engine

<Tabs>
<Tab label="PostgreSQL">

```toml
[search]
engine = "postgres"

[search.postgres]
language = "english"   # the text search configuration
trigram = true         # typo tolerance with pg_trgm
```

The module contributes a migration set named `search` that creates one table, `search_documents`, with a generated `tsvector` column and a GIN index. Your own tables are not changed. With `trigram = true` the migration also enables the `pg_trgm` extension, and short misspellings ("lovlace") still match. Queries run on the app's connection pool, inside no transaction.

</Tab>
<Tab label="Meilisearch">

```toml
[search]
engine = "meilisearch"
url = "https://search.internal:7700"
# key: APP_SEARCH__KEY
```

Navree creates each index on first use and pushes its settings (searchable, filterable and sortable fields, synonyms) at boot and with `search:settings`. Use a key with the `indexes.*`, `documents.*`, `search` and `settings.*` actions, not the master key, in production.

</Tab>
<Tab label="Typesense">

```toml
[search]
engine = "typesense"
url = "https://typesense-1.internal:8108"
nodes = ["https://typesense-2.internal:8108", "https://typesense-3.internal:8108"]
# key: APP_SEARCH__KEY (required)
```

Every index is a Typesense collection behind an alias, so `search:import --fresh` builds the new collection and swaps the alias in one step. `nodes` lists the other nodes of a cluster; requests fail over between them.

</Tab>
<Tab label="Tantivy">

```toml
[search]
engine = "tantivy"

[search.tantivy]
path = "storage/search"     # one directory per index
memory_budget_mb = 64       # writer buffer
```

The index lives in the process. Only one process may write to a Tantivy directory, so run the sync jobs in the server process (`sync = "inline"`) or on a single worker. Use it for single-server apps; switch to a server engine when you scale out.

</Tab>
</Tabs>

## Making an entity searchable

Derive `Searchable` on a SeaORM model and mark the fields that go into the index. This is the CRM's contact, with search added:

```rust title="crates/crm-core/src/entities/contact.rs"
use navree::search::Searchable;
use sea_orm::entity::prelude::*;
use serde::Serialize;

use crate::enums::ContactStatus;

#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, Serialize, Searchable)]
#[sea_orm(table_name = "contacts")]
#[searchable(name = "Contact", soft_delete = "deleted_at")]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub id: Uuid,
    #[searchable(boost = 3)]
    pub first_name: String,
    #[searchable(boost = 3)]
    pub last_name: String,
    #[searchable(boost = 2)]
    pub email: Option<String>,
    #[searchable]
    pub phone: Option<String>,
    #[searchable]
    pub title: Option<String>,
    #[searchable(filter)]
    pub status: ContactStatus,
    #[searchable(filter)]
    pub company_id: Option<Uuid>,
    #[searchable(filter)]
    pub owner_id: Uuid,
    #[searchable(sort)]
    pub created_at: DateTimeUtc,
    pub updated_at: DateTimeUtc,
    pub deleted_at: Option<DateTimeUtc>,
}
```

The derive implements `Searchable` for the module's `Entity`, so you search with the same type your [access rules](/docs/security/authorization/) use (`Contact`). The primary key is always stored; fields without `#[searchable]` stay out of the index.

| Field attribute | Effect |
|---|---|
| `#[searchable]` | Full-text field, matched by the query text |
| `#[searchable(boost = 3)]` | Full-text field that weighs 3 times as much as a plain one (1 to 10) |
| `#[searchable(filter)]` | Exact-match field for `filter`, `filter_in` and `range`; not matched by the text |
| `#[searchable(sort)]` | Field you can sort on |
| `#[searchable(filter, sort)]` | Both |
| `#[searchable(embed)]` | Text that goes into the record's [embedding](#vector-search) |
| `#[searchable(rename = "email_address")]` | The field's name in the index |

| Model attribute | Default | Effect |
|---|---|---|
| `name` | the table name | The name commands and results use: `navree search:import Contact`, `"__type": "Contact"` |
| `index` | the table name | The index name, after `search.prefix` (`crm_contacts`) |
| `soft_delete` | none | A nullable timestamp column: rows where it is set are removed from the index |
| `workspace` | the entity's `WorkspaceScoped` column | The column that scopes documents to a [workspace](#workspaces) |

Then register the entity with `SearchModule::for_feature`, in the module that owns it:

```rust title="crates/crm-core/src/module.rs"
#[module(
    imports = [
        AccessModule::for_feature::<Contact>(),
        SearchModule::for_feature::<Contact>(),
        SearchModule::for_feature::<Company>(),
        SearchModule::for_feature::<Deal>(),
    ],
    register = Self::wire,
)]
pub struct CrmCoreModule;
```

Registration does three things: it adds the index to `search:import` and `search:status`, pushes the index settings to the engine at boot, and subscribes the entity's changes to the sync observer.

### Documents with related data

The derive builds a document from the row alone. When a document needs data from other tables, implement `Searchable` by hand. A deal is easier to find by its company's name:

```rust title="crates/crm-deals/src/search.rs"
use crm_core::entities::{company, deal};
use navree::BoxFuture;
use navree::search::{Document, IndexSettings, SearchContext, Searchable};
use sea_orm::EntityTrait;

impl Searchable for deal::Entity {
    fn settings() -> IndexSettings {
        IndexSettings::new("Deal", "deals")
            .text("title", 3)
            .text("company_name", 2)
            .filter("stage")
            .filter("owner_id")
            .filter("company_id")
            .sort("amount_cents")
            .sort("expected_close_date")
    }

    fn document<'a>(
        deal: &'a deal::Model,
        ctx: &'a SearchContext,
    ) -> BoxFuture<'a, Result<Option<Document>, navree::BoxError>> {
        Box::pin(async move {
            let company = company::Entity::find_by_id(deal.company_id)
                .one(ctx.conn())
                .await?;
            Ok(Some(
                Document::new(deal.id)
                    .field("title", &deal.title)
                    .field("company_name", company.map(|c| c.name))
                    .field("stage", deal.stage.as_str())
                    .field("owner_id", deal.owner_id)
                    .field("company_id", deal.company_id)
                    .field("amount_cents", deal.amount_cents)
                    .field("expected_close_date", deal.expected_close_date),
            ))
        })
    }
}
```

Return `Ok(None)` to keep a record out of the index (an archived deal, a draft). A record that returns `None` after it was indexed is removed.

When a company is renamed, its deals' documents are stale. Queue them for a re-sync from an [event listener](/docs/digging-deeper/events/), or wherever you rename the company:

```rust
let ids: Vec<Uuid> = deals_of_company.iter().map(|d| d.id).collect();
search.reindex::<Deal>(ids).await?;
```

## Keeping indexes in sync

`SearchModule` registers a change observer on the [unit of work](/docs/database/unit-of-work/). When a unit of work that wrote a searchable entity through `Repo` commits, the observer queues one `search.sync` job per entity type with the changed ids. Because the job joins the same transaction:

- a request that fails (status 400 or above) rolls back its writes and queues nothing;
- the worker runs after the commit, so it always indexes committed data;
- a burst of writes to the same record collapses into one sync, since sync jobs are [unique](/docs/digging-deeper/queues/#unique-jobs) per entity and id for `search.unique_for_secs` (5 seconds).

The job loads the current rows and upserts or deletes their documents. It retries with backoff like any job, so an engine that is down for a minute catches up on its own.

| `search.sync` | Behavior |
|---|---|
| `queued` (default) | Sync jobs on the `search.queue` queue, run by `queue:work` |
| `inline` | The documents are written after the commit, in the request's task. The response does not wait for it. |
| `off` | Nothing is synced. Use `search:import` or `reindex` yourself. |

Writes that bypass `Repo` (raw SQL, `update_many`, a migration that backfills a column) are not observed. Re-sync those records with `search.reindex::<E>(ids)`, or rebuild the index with `search:import`.

To pause syncing for a block of work, such as a bulk import that ends with a full reindex, wrap it:

```rust
search
    .without_syncing(async {
        import_contacts_from_csv(&uow, &file).await
    })
    .await?;
search.import::<Contact>().await?;
```

## Importing and rebuilding indexes

`search:import` indexes every row of an entity, in batches of `search.chunk_size`:

```sh
navree search:import Contact
```

```text
Importing Contact into crm_contacts: 12,480 rows
[==========================================] 12480/12480  2.1s
Imported 12,480 documents (37 skipped by the document filter).
```

| Command | What it does |
|---|---|
| `search:import <Name>` | Upserts every row's document. Existing documents are replaced. |
| `search:import <Name> --fresh` | Builds a new index, imports into it and swaps it in. Searches keep working on the old index until the swap. |
| `search:import --all` | Every registered index. |
| `search:flush <Name>` | Removes every document from the index. |
| `search:settings [<Name>]` | Pushes index settings (fields, synonyms, stop words) to the engine. |
| `search:status` | Each index with its engine, document count, row count and pending sync jobs. |

Run `search:import --all --fresh` after you change a model's searchable fields, and as part of a deploy that changes them. `search.import::<E>()` does the same from code, for an admin screen or a scheduled task.

## Searching

Inject `Arc<Search>` and start a query with the entity type and the text. `paginate` takes a `PageQuery` and returns a `Page` of models, in relevance order:

```rust title="crates/crm-companies/src/contacts/controller.rs"
use crm_core::Contact;
use navree::prelude::*;
use navree::search::Search;
use serde::Deserialize;

#[derive(Debug, Deserialize, garde::Validate)]
pub struct SearchContacts {
    #[garde(length(min = 1, max = 200))]
    pub q: String,
    #[garde(skip)]
    pub status: Option<String>,
}

#[injectable]
pub struct ContactSearchController {
    search: Arc<Search>,
}

#[controller("/contacts/search", version = "1")]
impl ContactSearchController {
    /// `GET /api/v1/contacts/search?q=ada&status=customer`
    #[get("/")]
    #[can(Read, Contact)]
    async fn index(
        &self,
        scope: Accessible<Contact, Read>,
        Valid(Query(input)): Valid<Query<SearchContacts>>,
        page: PageQuery,
    ) -> Result<Page<ContactResource>> {
        let mut query = self.search.query::<Contact>(&input.q).accessible(scope);
        if let Some(status) = &input.status {
            query = query.filter("status", status);
        }
        let contacts = query.paginate(page).await?;
        Ok(contacts.map(ContactResource::from))
    }
}
```

```json
{
  "data": [
    { "__type": "Contact", "id": "0199c1d2-...", "full_name": "Ada Lovelace", "email": "ada@lovelace.io" }
  ],
  "meta": { "current_page": 1, "per_page": 15, "total": 1, "last_page": 1 }
}
```

The engine returns ids and scores. Navree loads the rows from the database in one query and keeps the engine's order, so you always return current data, and your resource types work unchanged. Rows deleted since the last sync are dropped from the page.

### Filters and sorting

Filters apply to `#[searchable(filter)]` fields; sorts to `#[searchable(sort)]` fields. Anything else fails with `SearchError::NotFilterable` or `NotSortable` before a request reaches the engine.

```rust
let deals = search
    .query::<Deal>("renewal")
    .filter("stage", "negotiation")
    .filter_in("owner_id", [ada_id, grace_id])
    .range("amount_cents", 1_000_000..)
    .sort_desc("amount_cents")
    .paginate(page)
    .await?;
```

| Method | Matches |
|---|---|
| `filter(field, value)` | Equal to `value` |
| `filter_not(field, value)` | Not equal to `value` |
| `filter_in(field, values)` | Equal to one of `values` |
| `range(field, range)` | Inside a Rust range: `10..20`, `10..`, `..=20` (numbers and dates) |
| `filter_null(field)` | Without a value |
| `sort_asc(field)`, `sort_desc(field)` | Sort by the field; relevance breaks ties. Without a sort, results are by relevance. |

An empty query text matches every document, so a filtered empty query is a fast list: `search.query::<Deal>("").filter("owner_id", me).sort_desc("expected_close_date")`.

### Access control

`accessible(scope)` takes the `Accessible<E, Read>` extractor from [authorization](/docs/security/authorization/). Navree turns the user's ability conditions into engine filters when they only use filterable fields (the usual `owner_id = me` rule becomes `filter("owner_id", me)`), so pages stay full and totals stay exact. Conditions on fields the index doesn't hold are applied when the rows are loaded, and records the user can't read are dropped from the page. Mark the columns your rules use as `filter` to keep totals exact.

### Hits and highlights

`hits` returns each record with its score and the matched text, marked up for the search box:

```rust
let page = search.query::<Contact>("lovlace").hits(page).await?;
for hit in &page.data {
    println!("{} {:?}", hit.score, hit.highlights.get("last_name"));
    // 0.94 Some("<mark>Lovelace</mark>")
}
```

`Hit<T>` has `record`, `score` (0 to 1, higher is better) and `highlights`, a map of field to text with `<mark>` around the matches. Change the tags with `.highlight_tags("<em>", "</em>")`. `Hit<T>` serializes as the record's fields plus `_score` and `_highlights`.

### Searching several entities at once

The command palette searches contacts, companies and deals in one call. `across` runs one query per index in parallel and merges the results by score:

```rust
let results = search
    .across("ada")
    .include::<Contact>(contacts_scope)
    .include::<Company>(companies_scope)
    .include::<Deal>(deals_scope)
    .limit(10)
    .run()
    .await?;

for hit in results {
    // hit.kind: "Contact" | "Company" | "Deal"; hit.id; hit.title; hit.score
}
```

Each `include` takes that entity's `Accessible` scope. A result carries the `name` of its index as `kind` and the first full-text field as `title`; call `hit.load::<Contact>(&uow)` for the whole record.

## Workspaces

In an app with [workspaces](/docs/workspaces/introduction/) and row isolation, a searchable entity that implements `WorkspaceScoped` stores its workspace column (`workspace_id` by default) in every document. Every query made during a request is then filtered to the request's `CurrentWorkspace`, as `WorkspaceRepo` filters rows, so one workspace's search never returns another's records. In jobs and commands, where there is no current workspace, name one:

```rust
search.query::<Contact>("ada").workspace(workspace_id).paginate(page).await?;
```

With `Schema` or `Database` isolation, each workspace gets its own index (`crm_contacts__acme`), created when the workspace is created and dropped when it is deleted.

## Vector search

Full-text search finds the words people type. Vector search finds records that mean the same thing: "customers unhappy with onboarding" finds the contact whose notes say "struggled to get the team set up". Mark the fields that describe a record with `#[searchable(embed)]`:

```rust
#[searchable(boost = 2, embed)]
pub title: String,
#[searchable(embed)]
pub notes: Option<String>,
```

On each sync, the embedded fields are joined into one text and turned into a vector with the app's `Embeddings` provider from the [AI SDK](/docs/ai/embeddings-and-rag/), so the app needs `AiModule`. Vectors are stored in the configured vector store:

```toml title="config/app.toml"
[search.vectors]
store = "pgvector"        # pgvector | qdrant
dimensions = 1536         # must match the embedding model
metric = "cosine"         # cosine | dot | euclidean

# store = "qdrant"
# url = "http://127.0.0.1:6334"   # APP_SEARCH__VECTORS__KEY for the API key
```

With `pgvector`, the `search` migration set adds an `embedding vector(1536)` column and an HNSW index to `search_documents`. With Qdrant, each index gets a collection of the same name.

Query by meaning with `similar`, or blend both kinds of relevance with `hybrid`:

```rust
// Nearest records to a text:
let similar = search
    .similar::<Contact>("customers unhappy with onboarding")
    .filter("status", "customer")
    .limit(10)
    .run()
    .await?;

// Nearest records to another record:
let like_this = search.similar_to::<Deal>(deal.id).limit(5).run().await?;

// Keyword and vector scores blended, 0.0 = keywords only, 1.0 = vectors only:
let deals = search.query::<Deal>("renewal risk").hybrid(0.4).paginate(page).await?;
```

Filters, workspaces and `accessible` work the same for vector queries. Embedding calls go through the AI SDK's provider failover and are cached by text, so re-syncing an unchanged record costs no tokens.

## Testing

Use the `memory` engine with inline syncing. Writes through `Repo` are then searchable as soon as the unit of work commits, and nothing leaves the process:

```rust title="apps/crm-api/tests/contact_search.rs"
use crm_testkit::{Role, TestCrm};
use navree::search::Search;
use serde_json::json;

#[tokio::test]
async fn finds_contacts_by_a_misspelled_name() {
    let crm = TestCrm::builder()
        .app(crm_api::app)
        .config("search.engine", "memory")
        .config("search.sync", "inline")
        .build()
        .await;
    let rep = crm.login_as(Role::Rep1).await;

    rep.post("/api/v1/contacts")
        .json(&json!({ "first_name": "Ada", "last_name": "Lovelace" }))
        .send()
        .await
        .assert_status(201);

    crm.get::<Search>().await.flush_pending().await.unwrap();

    rep.get("/api/v1/contacts/search")
        .query(&[("q", "lovlace")])
        .send()
        .await
        .assert_status(200)
        .assert_json_path("meta.total", json!(1))
        .assert_json_path("data.0.full_name", json!("Ada Lovelace"));
}
```

- `flush_pending()` waits until inline syncs that are still running have finished. With `sync = "queued"`, run the queue instead: `crm.run_queue().await`, or `app.get::<Queue>().await.run_pending().await` in a plain `TestApp`.
- The memory engine supports every query method, typo tolerance included, and ranks with the same field boosts, so tests and production agree on what matches. Exact scores differ between engines; assert on order and membership, not on `_score`.
- To check that a write queues a sync without running it, install a [`QueueFake`](/docs/testing/fakes/#the-queue) and assert on the sync job, `navree::search::SyncDocuments` (job name `search.sync`): `fake.assert_dispatched::<SyncDocuments>(|job| job.index == "contacts")`.
- `search.assert_indexed::<Contact>(id)` and `search.assert_not_indexed::<Contact>(id)` check the index directly.

### Configuration

| Key | Default | Meaning |
|---|---|---|
| `search.engine` | `postgres` | `postgres`, `meilisearch`, `typesense`, `tantivy` or `memory` |
| `search.url` | none | The server URL (Meilisearch, Typesense) |
| `search.key` | none | The API key; required for Typesense |
| `search.nodes` | `[]` | Further Typesense nodes; a comma-separated string from the environment |
| `search.prefix` | `""` | Put in front of every index name |
| `search.queue` | `default` | The queue of `search.sync` jobs |
| `search.sync` | `queued` | `queued`, `inline` or `off` |
| `search.unique_for_secs` | `5` | Window in which sync jobs for the same records collapse |
| `search.chunk_size` | `500` | Rows per batch for imports |
| `search.timeout_secs` | `5` | Time allowed for one engine request |
| `search.postgres.language` | `english` | The text search configuration |
| `search.postgres.trigram` | `false` | Typo tolerance with `pg_trgm` |
| `search.tantivy.path` | `storage/search` | Index directory |
| `search.tantivy.memory_budget_mb` | `64` | Writer buffer |
| `search.vectors.store` | none | `pgvector` or `qdrant`; vector search is off without it |
| `search.vectors.url`, `search.vectors.key` | none | The Qdrant server |
| `search.vectors.dimensions` | `1536` | Vector size |
| `search.vectors.metric` | `cosine` | `cosine`, `dot` or `euclidean` |
| `search.indexes.<index>.synonyms` | `{}` | Synonyms per index: `{ "acme" = ["acme corp"] }` |
| `search.indexes.<index>.stop_words` | `[]` | Words the index ignores |

### The Search service

| Method | Returns |
|---|---|
| `query::<E>(text)` | A query builder: `filter`, `filter_in`, `range`, `sort_desc`, `accessible`, `workspace`, `hybrid`, then `paginate(page)`, `hits(page)`, `ids(limit)` or `count()` |
| `similar::<E>(text)`, `similar_to::<E>(id)` | A vector query builder, run with `run()` |
| `across(text)` | A multi-index query: `include::<E>(scope)`, `limit`, `run()` |
| `reindex::<E>(ids)` | Queues a sync for those records |
| `import::<E>()`, `flush::<E>()` | Rebuilds or empties an index |
| `without_syncing(future)` | Runs the future with change syncing paused |
| `flush_pending()` | Waits for running inline syncs (tests) |

### Errors

A search that the engine can't answer returns `SearchError`. With `?` in a handler it becomes Navree's error shape: an invalid filter or sort field is a 400, an unreachable or timed-out engine is a 503:

```json
{ "statusCode": 503, "message": "Search is unavailable. Try again shortly.", "error": "Service Unavailable" }
```

The sync jobs log every failure at target `navree::search` with the index, the ids and the engine's answer, and retry it.
