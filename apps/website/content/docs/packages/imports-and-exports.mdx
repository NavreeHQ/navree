## Introduction

<Badge feature="sheets" /> Business apps live on spreadsheets. Customers export their contacts to Excel every Monday, and import ten thousand employees from a file someone saved in Excel on a Windows laptop set to Arabic. `navree-sheets` handles both directions.

**Exports.** You describe a row with `#[derive(Exportable)]` and return a `Download` from a handler. CSV files start with a byte-order mark, so Excel opens Arabic, accented and Japanese text correctly, and text that a spreadsheet would run as a formula is escaped. XLSX files have typed cells, date formats and a bold, frozen, filtered header row. A named export can also run on the [queue](/docs/digging-deeper/queues/): it writes the file to a [disk](/docs/digging-deeper/storage/) and hands back a signed link.

**Imports.** You describe a row with `#[derive(Deserialize, Validate, Importable)]` and say how a row is saved. Navree does the rest:

1. The upload is stored, and its reading is queued as an operation the client follows.
2. The text encoding is detected (UTF-8, UTF-16, Windows-1256, Shift_JIS and the others browsers know), and the CSV, TSV, XLSX, XLSB, XLS or ODS file is read.
3. The file's headers are matched to your columns: automatically, from a mapping saved for files with the same headers, or from one the user chooses.
4. Every row is read into your type and validated with its `#[derive(Validate)]` rules, in your app's validation wording. Rows that repeat an earlier row's key, and rows whose key your app already has, are found.
5. The user previews the rows by status, then applies the import: valid rows are saved in queue batches, each in its own unit of work, and duplicates are skipped, updated or refused.
6. An error file lists every row that was not saved, with the reason, ready to fix and upload again.

## Installation

The `sheets` feature of the `navree` facade is part of `full`, which is on by default. With `default-features = false`, turn it on:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", default-features = false, features = ["sheets"] }
```

It brings `navree::sheets` (with the `Exportable` and `Importable` derives) and puts `SheetsModule` in the prelude. Add the module to your app root. Downloads need nothing else; imports and queued exports need the database, the queue and a storage disk:

```rust title="src/app.rs"
Navree::app()
    .module(ConfigModule::for_root(sources))
    .module(HttpModule::from_config())
    .module(DatabaseModule::from_config())
    .module(QueueModule::from_config())
    .module(StorageModule::from_config())
    .module(SheetsModule::from_config()) // section `sheets`
    // ...
```

The module contributes the migration set `sheets`, which creates `imports`, `import_rows` (the staged rows) and `import_mappings` (saved mappings). It runs on SQLite, PostgreSQL and MySQL. Everything is pure Rust: XLSX is written with [rust_xlsxwriter](https://docs.rs/rust_xlsxwriter); XLSX, XLSB, ODS and XLS are read by the module's own readers (the zip file with [zip](https://docs.rs/zip), the XML with [quick-xml](https://docs.rs/quick-xml), XLS's compound file and records by the module itself); and encodings are decoded with [encoding_rs](https://docs.rs/encoding_rs) and guessed with [chardetng](https://docs.rs/chardetng).

## Configuration

```toml title="config/app.toml"
[sheets.csv]
bom = true                     # a UTF-8 byte-order mark, so Excel reads UTF-8
delimiter = ","                # ";" for spreadsheets set to a European locale
escape_formulas = true         # a leading ' on text starting with = + - @
crlf = true                    # RFC 4180 line endings

[sheets.exports]
disk = ""                      # the disk of queued exports ("": the default disk)
directory = "exports"
link_ttl_secs = 86400          # how long the link of a queued export works
page_size = 1000               # rows asked of an export at a time
max_rows = 1000000             # the most rows one export writes
routes = true                  # the /api/exports routes

[sheets.imports]
disk = ""                      # the disk of uploads and error files ("": the default disk)
directory = "imports"
max_upload_bytes = 20971520    # the largest upload (20 MiB)
max_rows = 100000              # the most data rows one file may have
max_columns = 16384            # the most columns one file may have
max_cells = 10000000           # the most cells (rows times columns) one file may hold
max_inflated_bytes = 1073741824  # the most a part of a workbook may unpack to (1 GiB)
max_text_bytes = 268435456     # the most text the cells of one file may hold (256 MiB)
chunk_size = 500               # rows per staging step and per apply job
keep_days = 7                  # sheets:prune deletes imports older than this
routes = true                  # the /api/imports routes
```

Every key also comes from the environment with the `APP_` prefix: `APP_SHEETS__IMPORTS__MAX_ROWS=250000`. `SheetsModule::for_root(SheetsOptions { .. })` configures the module in code. An invalid value (a delimiter that is not one ASCII character, a chunk size of 0) fails the boot and names the key.

## Exports

### Rows

An export row is a struct. `#[derive(Exportable)]` turns its fields into columns, in order, and each value into a cell:

```rust title="src/modules/contacts/export.rs"
use navree::sheets::Exportable;

#[derive(Exportable)]
#[export(sheet = "Contacts")]
struct ContactRow {
    #[export(header = "Name")]
    name: String,
    #[export(header = "Email", width = 30)]
    email: String,
    company: Option<String>,
    #[export(header = "VIP")]
    vip: bool,
}
```

A field without a `header` is headed by its name in sentence case: `company` is `Company`, `first_name` is `First name`.

| Attribute | Effect |
|---|---|
| `#[export(sheet = "Contacts")]` (on the struct) | The XLSX sheet name (default `Sheet1`; cut to Excel's 31 characters) |
| `#[export(header = "Email")]` | The header, or a translation key (see [translated headers](#translated-headers)) |
| `#[export(format = "#,##0.00")]` | The Excel number format of the column's numbers and dates (XLSX) |
| `#[export(width = 30)]` | The column width in characters, 1 to 255 (XLSX; otherwise fitted to the header and the first page, up to 60) |
| `#[export(with = "cents_to_cell")]` | A `fn(&FieldType) -> Cell` instead of the field's `IntoCell` |
| `#[export(skip)]` | Leaves the field out |

Each field becomes a `Cell` (`Empty`, `Text`, `Int`, `Float`, `Bool`, `Date`, `DateTime`) through `IntoCell`, which is implemented for strings, integers, floats, `bool`, `chrono` dates, date-times and times, `Uuid`, `serde_json::Value`, and `Option<T>` (`None` is an empty cell). Implement `IntoCell` for your own types, or point a field at a function with `with`.

### Downloads

The examples read `Contact`, a [model](/docs/orm/models/) of a `contacts` table, and turn it into the export row:

```rust title="src/modules/contacts/model.rs"
use navree::prelude::*;

#[derive(Model, Clone, Debug, Default, Serialize)]
#[model(table = "contacts")]
pub struct Contact {
    pub id: Uuid,
    pub email: String,
    pub name: String,
    pub company: Option<String>,
    pub vip: bool,
}

impl From<Contact> for ContactRow {
    fn from(contact: Contact) -> Self {
        ContactRow {
            name: contact.name,
            email: contact.email,
            company: contact.company,
            vip: contact.vip,
        }
    }
}
```

Return a `Download` from a handler. `Download::csv` and `Download::xlsx` write rows you have; `Download::csv_stream` writes rows as a stream yields them, so the response never holds the whole file:

```rust title="src/modules/contacts/controller.rs"
#[injectable]
struct ContactsController {
    exports: Arc<Exports>,
    db: Arc<Db>,
}

#[controller("/contacts", version = "1")]
impl ContactsController {
    /// Every contact as CSV, with the app's `sheets.csv` options.
    #[get("/export.csv")]
    #[permissions("contacts.export")]
    async fn export_csv(&self) -> Result<Download> {
        let contacts = Contact::query()
            .order_by(Contact::EMAIL)
            .get(&*self.db)
            .await?
            .into_models();
        Ok(self
            .exports
            .csv("contacts", contacts.into_iter().map(ContactRow::from)))
    }

    /// The same as an Excel workbook.
    #[get("/export.xlsx")]
    #[permissions("contacts.export")]
    async fn export_xlsx(&self) -> Result<Download> {
        let contacts = Contact::query()
            .order_by(Contact::EMAIL)
            .get(&*self.db)
            .await?
            .into_models();
        Ok(Download::xlsx(
            "contacts",
            contacts.into_iter().map(ContactRow::from),
        )?)
    }
}
```

The response is `200` with the file's content type, `Content-Disposition: attachment` with the file name (and its exact UTF-8 spelling in `filename*`, so `جهات الاتصال.csv` arrives intact), `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. A name without an extension gets `.csv` or `.xlsx`.

The `Download` constructors use the default CSV options and the headers as declared. The `Exports` service, which `SheetsModule` provides, does the same with your `sheets.csv` options and [translated headers](#translated-headers): `exports.csv(..)`, `exports.xlsx(..)`, `exports.csv_stream(..)`, and `exports.file(format, ..)` for a format the client chose.

What the files look like:

- **CSV** starts with a UTF-8 byte-order mark and ends lines with CRLF. Fields are quoted only when they need it. Numbers and booleans are written as they print, dates as `2026-10-27` and date-times as `2026-10-27 14:30:00`.
- **Formula escaping.** A cell that starts with `=`, `+`, `-`, `@`, a tab or a carriage return (or the full-width `＝`, `＋`, `－`, `＠`) is run as a formula when someone opens the file in a spreadsheet, so a contact named `=HYPERLINK("http://evil")` is an attack. Text like that is written with a leading `'`. Numbers are never escaped, so `-5` stays a number.
- **XLSX** has one sheet, named after the row type, with a bold, frozen and filtered header row. Numbers are numbers, booleans are booleans, and dates and date-times are Excel dates with a date format (`yyyy-mm-dd`, or the column's `format`). Text is always text, never a formula. Integers larger than 2<sup>53</sup> are written as text so no digit is lost, text longer than a cell holds (32,767 characters) is cut, and a sheet holds at most 1,048,575 data rows.

A streamed CSV download that hits an error after it started (the database went away) stops there: the client gets a cut-off file, and the error is logged at target `navree::sheets`.

### Translated headers

A header can be a translation key. With a `HeaderCatalog`, register the texts in your module:

```rust title="src/modules/contacts/mod.rs"
use navree::sheets::HeaderCatalog;

m.header_catalog(
    HeaderCatalog::new("en")
        .locale("en", [("contacts.email", "Email")])
        .locale("ar", [("contacts.email", "البريد الإلكتروني")]),
);
```

A header the catalog has no text for is written as it is. A regional locale falls back to its language (`ar-SA` to `ar`), then to the catalog's default. For headers from somewhere else, implement `HeaderTranslator` (`fn translate(&self, key, locale) -> Option<String>`) and register it as the app's `dyn HeaderTranslator`.

With [localization](/docs/packages/localization/) (the `i18n` feature), headers come from your Fluent files without a catalog: `contacts.email` is the `email` attribute of the `contacts` message, in the request's locale.

```text title="locales/fr/contacts.ftl"
contacts =
    .email = Adresse e-mail
```

Queued exports and imports run in the locale of the request that queued them, so a French user's queued export has French headers and their import's errors read "email doit être une adresse e-mail valide".

### Named exports

For exports that are big, or that a front end lists and runs by name, implement `Export`. It names the row type and the parameters, and fetches rows a page at a time:

```rust title="src/modules/contacts/export.rs"
use navree::sheets::{Export, ExportContext, ExportPage};

/// The filters of the contacts export.
#[derive(Default, Serialize, Deserialize)]
#[serde(default)]
struct ContactFilter {
    vip: Option<bool>,
}

#[injectable]
struct ContactsExport {
    db: Arc<Db>,
}

impl Export for ContactsExport {
    const NAME: &'static str = "contacts";
    type Row = ContactRow;
    type Params = ContactFilter;

    fn filename(&self, filter: &ContactFilter) -> String {
        match filter.vip {
            Some(true) => "vip-contacts".into(),
            _ => "contacts".into(),
        }
    }

    async fn rows(
        &self,
        _ctx: &ExportContext,
        filter: &ContactFilter,
        page: ExportPage,
    ) -> Result<Vec<ContactRow>, BoxError> {
        let mut query = Contact::query().order_by(Contact::EMAIL);
        if let Some(vip) = filter.vip {
            query = query.where_(Contact::VIP.eq(vip));
        }
        let contacts = query
            .offset(page.offset)
            .limit(page.limit)
            .get(&*self.db)
            .await?;
        Ok(contacts.into_models().into_iter().map(ContactRow::from).collect())
    }
}
```

Register it in its module with `m.export::<ContactsExport>()`. It is a provider of that module, so it can hold services. A page shorter than `page.limit` (`sheets.exports.page_size`) is the last, so order the rows by something stable. `ExportContext` carries the app, the user, the workspace and the locale the export runs for.

- **`permission()`** is `{NAME}.export` by default (`contacts.export`), checked app-wide or in the request's workspace. Return `None` to let every signed-in user run it.
- **`count()`** (optional) says how many rows there are. An export above `sheets.exports.max_rows` is then refused before anything is written, and a queued export reports real progress. Without it, an export that goes past the limit stops there.
- **`Params`** come from the query string of a download (`?vip=true`) and from `params` in the body of a queued export. Use `()` for an export without parameters.

The routes run it:

```http
GET /api/exports/contacts?format=xlsx&vip=true
```

returns `vip-contacts.xlsx`, built page by page in constant memory; with `format=csv` (the default), the CSV is streamed page by page. To run it later instead, queue it:

```http
POST /api/exports/contacts
Content-Type: application/json

{ "format": "xlsx", "params": { "vip": true } }
```

The answer is `202` with an [operation](/docs/digging-deeper/batches-and-operations/#operations) of kind `export.contacts`. The client follows it at `GET /api/operations/{id}/events`. Its job (`sheets.export`) writes the file to `sheets.exports.disk` under `exports/<date>/<operation id>/`, and the operation finishes with an `ExportResult`:

```json title="result"
{
  "url": "/storage/files/exports/2026-10-27/0192e1c4-.../vip-contacts.xlsx?expires=1761638400&signature=...",
  "filename": "vip-contacts.xlsx",
  "format": "xlsx",
  "rows": 1840,
  "bytes": 61273,
  "expires_at": "2026-10-28T09:20:00Z",
  "disk": "files",
  "path": "exports/2026-10-27/0192e1c4-.../vip-contacts.xlsx"
}
```

The link is signed and works for `sheets.exports.link_ttl_secs` without signing in: on cloud disks the provider signs it, on local and memory disks the storage module serves it. `disk` and `path` let your code attach the file to a mail instead. An export over the row limit fails its operation with "The export has more than 1000000 rows.".

From code, `exports.download::<ContactsExport>(params, ExportRequest::new(SheetFormat::Xlsx).user(id))` returns the download, and `exports.queue::<ContactsExport>(&uow, params, request)` queues it as part of a unit of work and returns the operation.

## Imports

### Row types

An import reads each row into a struct that serde deserializes and its `#[validate]` rules check. `#[derive(Importable)]` declares its columns:

```rust title="src/modules/contacts/import.rs"
use navree::sheets::Importable;

/// One row of a contacts file.
#[derive(Deserialize, Validate, Importable)]
struct ContactInput {
    #[import(header = "Email", aliases = ["E-mail", "Email address"])]
    #[validate(email)]
    email: String,
    #[validate(length(min = 1, max = 100))]
    name: String,
    #[import(aliases = ["Organization"])]
    #[validate(length(max = 100))]
    company: Option<String>,
    #[serde(default)]
    #[validate(skip)]
    vip: bool,
}
```

| Attribute | Effect |
|---|---|
| `#[import(header = "Email")]` | The header the template shows and automatic mapping looks for (default: the field in sentence case) |
| `#[import(aliases = ["E-mail", "Email address"])]` | Other headers automatic mapping accepts |
| `#[import(required)]`, `#[import(optional)]` | Whether the file must have the column (default: required unless the field is an `Option` or has `#[serde(default)]`) |
| `#[import(skip)]` | Not a column (so is a field with `#[serde(skip)]`) |

A column's field is the field's name, or its `#[serde(rename = "..")]`. `#[serde(rename_all)]` is a compile error: rename fields one by one.

Cells are read the way people type them:

- **Numbers** in any script's digits (`٣٦` is 36) and with a decimal comma when there is no point (`3,5` is 3.5). A whole number from a workbook (`36.0`) fills an integer field.
- **Booleans** from `true`, `false`, `yes`, `no`, `y`, `n`, `1`, `0`, `on`, `off`, in any case.
- **Dates** from workbook dates, or text in ISO 8601 (`2026-10-27`).
- **Enums** by variant name, in any case; **lists** split on `,`, `;`, `|` or line breaks.
- **Empty cells** are left out: `None` for an `Option`, the default for a field with `#[serde(default)]`, and "should not be empty" for anything else.

A cell that doesn't fit gets the message of your app's [validation](/docs/basics/validation/) rules ("age must be an integer number"), then the struct's rules run.

### The importer

`Import` says what a row is read into, how duplicates are found and how a row is saved:

```rust title="src/modules/contacts/import.rs"
use navree::sheets::{Import, ImportContext, RowRejected};

#[injectable]
struct ContactsImport {
    db: Arc<Db>,
}

impl Import for ContactsImport {
    const NAME: &'static str = "contacts";
    type Row = ContactInput;

    fn key(row: &ContactInput) -> Option<String> {
        Some(row.email.trim().to_lowercase())
    }

    async fn existing(&self, _ctx: &ImportContext, keys: &[String]) -> Result<HashSet<String>, BoxError> {
        let found = Contact::query()
            .where_(Contact::EMAIL.is_in(keys.to_vec()))
            .pluck(&*self.db, Contact::EMAIL)
            .await?;
        Ok(found.into_iter().collect())
    }

    async fn insert(&self, _ctx: &ImportContext, uow: &Uow, row: ContactInput) -> Result<(), BoxError> {
        if row.email.ends_with("@competitor.example") {
            return Err(RowRejected::new("Contacts at competitors are not imported").into());
        }
        Contact::create(
            uow,
            Contact {
                email: row.email.trim().to_lowercase(),
                name: row.name,
                company: row.company,
                vip: row.vip,
                ..Contact::default()
            },
        )
        .await?;
        Ok(())
    }

    async fn update(&self, _ctx: &ImportContext, uow: &Uow, row: ContactInput) -> Result<(), BoxError> {
        Contact::query()
            .where_(Contact::EMAIL.eq(row.email.trim().to_lowercase()))
            .update(
                uow,
                [
                    Contact::NAME.set(row.name),
                    Contact::COMPANY.set(row.company),
                ],
            )
            .await?;
        Ok(())
    }
}
```

Register it with `m.importer::<ContactsImport>()`. The module wiring of this page's examples:

```rust title="src/modules/contacts/mod.rs"
use navree::schema::migration;

#[module(controllers = [ContactsController], register = Self::wire)]
struct ContactsModule;

impl ContactsModule {
    fn wire(&self, m: &mut ModuleBuilder) {
        m.migrations(
            MigrationSet::new("contacts").migration(migration!(m20261027_000001_create_contacts)),
        )
            .importer::<ContactsImport>()
            .export::<ContactsExport>();
    }
}
```

| Item | Meaning |
|---|---|
| `NAME` | The importer's name in uploads and routes: letters, digits, `-`, `_` and `.` |
| `permission()` | `{NAME}.import` by default, checked app-wide or in the import's workspace; `None` lets every signed-in user import |
| `key(row)` | The row's duplicate key (an email, an employee number), or `None` (the default) when rows are never duplicates |
| `existing(ctx, keys)` | Which keys the app already has; asked once per chunk while staging |
| `insert(ctx, uow, row)` | Saves a new row as part of `uow` |
| `update(ctx, uow, row)` | Updates the record a duplicate stands for, when applying with `update`; by default duplicates cannot be updated |
| `completed(ctx, import)` | Runs once the import is applied, with its counts (send a notification, refresh a cache) |

Return `RowRejected::new("..")` from `insert` or `update` to refuse one row with a message for the error file. Any other error fails the row with "This row could not be saved" and is logged.

### Uploading a file

The client posts the file with the importer's name:

```http
POST /api/imports
Content-Type: multipart/form-data; boundary=...

importer=contacts, file=@contacts.csv
```

| Field | Meaning |
|---|---|
| `importer` | The importer's `NAME` (required) |
| `file` | The file (required) |
| `encoding` | The text encoding of a CSV file (`windows-1256`, `shift_jis`, `utf-16le`); detected when absent |
| `sheet` | The workbook sheet to read; the first when absent |
| `mapping` | A JSON object of field to header, to use instead of finding one |
| `save_mapping` | `true` to keep `mapping` for later files with the same headers |

The answer is `202` with the import (status `uploaded`) and its `operation_id`. The client follows the operation at `GET /api/operations/{id}/events`; when it finishes, `GET /api/imports/{id}` has the result. A file larger than `sheets.imports.max_upload_bytes` is `413`, an empty file or one that is plainly not a spreadsheet (a PDF, an image) is `400 unsupported_file`, and both happen before anything is stored.

From code, `imports.upload(&uow, "contacts", Upload::new(name, bytes), UploadOptions::default().owner(user_id))` does the same as part of a unit of work.

### Encodings and formats

Spreadsheet programs save CSV in whatever encoding the computer uses. Navree finds it in this order:

1. A byte-order mark: UTF-8, UTF-16LE or UTF-16BE (Excel's "Unicode Text" is UTF-16LE with tabs).
2. UTF-16 without a byte-order mark, recognized by its zero bytes.
3. Valid UTF-8.
4. [chardetng](https://docs.rs/chardetng)'s guess among the legacy encodings browsers know: Windows-1250 to 1258 (Windows-1256 for Arabic), ISO-8859, Shift_JIS, EUC-JP, EUC-KR, GBK, Big5, KOI8 and the rest.

The encoding found (or given with `encoding`) is the import's `encoding`. The delimiter is the most frequent of `,`, `;`, tab and `|` in the header line, outside quotes; `.tsv` and `.tab` files are always tab-separated.

Workbooks are recognized by their content, whatever their name: XLSX (and XLSM and XLSB), XLS and ODS. Numbers, booleans and dates keep their types. A number in a date or time format is a date (`2026-03-01`), or a date and time when it has a time; a time alone or a duration (`[h]:mm`) is a date and time on the first day of the workbook's date system (1899-12-31 or 1904-01-01). An ODS file's dates and times (`office:date-value`, `office:time-value`) are read as the same values, in the date system of the file's null date; a value that does not read as a date or time stays its text. An XLSX cell of type `t="d"` holds its date in ISO 8601 and reads as the same values. A number past the last day a workbook can show (9999-12-31) stays a number, and in the 1904 date system days count back one by one, since that system has no 1900-02-29. Times are read to the millisecond in every format, ISO 8601 text included. In an XLSX or XLSB workbook a cell format has the number format the file gives its id, so a custom code under a built-in id (`14` as `0.00`) is that code, and the built-in format of the id when the file gives none; an XLS file's FORMAT records give the ids BIFF8 lets them (5 to 8, 23 to 26, 41 to 44, 63 to 66 and 164 on). A number past the largest double is the largest double of its sign: writers round `1.7976931348623157e308` up (`1.797693134862316e+308`), and LibreOffice reads that as infinity and writes `INF`, so `1e999`, `INF` and an infinity in a binary workbook read as `1.7976931348623157e308` (or its negative). A cell that says it holds a number and holds `NaN`, or text that is no number, makes the file unreadable; a value without a type is a number when it is written with digits, and its text otherwise (`inf`, `NaN`, `n/a`). An error cell is its text: the classic errors as `#Div0`, `#NA`, `#Name`, `#Null`, `#Num`, `#Ref` and `#Value`, an error of another name as it is written (`#SPILL!`, `#CALC!`), and an XLSB or XLS error of another code by its code (`#Error(0x2c)`); an ODS error (`calcext:value-type="error"`) reads the same from the text of its paragraphs, and LibreOffice's own codes in ODS (`Err:502`) are kept as written, as the file says no more of the error than its text. In ODS text, `<text:tab/>` is a tab, `<text:line-break/>` a line break, `<text:s text:c="3"/>` three spaces, and paragraphs are joined with line breaks. A shape or a note anchored to a cell (`draw:frame`, `draw:custom-shape`, `office:annotation`) is not the cell's text.

The header row is the first row with a value; empty rows are skipped. A blank header is named `Column 3`, and a repeated one gets ` (2)`. Rows are numbered the way the spreadsheet shows them, so "row 14" in the preview is row 14 in Excel. A file with more than `sheets.imports.max_rows` data rows fails the import with "The file has more than 100000 rows.". CSV, TSV, XLSX, XLSB, ODS and XLS files are read a record or a cell at a time and the limits are checked as each row arrives, so a file that breaks one is refused without its rows being held in memory first. The limit is reported when the row that breaks it is read; the rest of a workbook's sheet is then still read through, keeping nothing, so that a sheet that can't be read at all is reported as unreadable rather than as over a limit. A file with more than `sheets.imports.max_columns` columns fails with "The file has more than 16384 columns.". Every row is padded to the width of the header, so the table is as large as the header's width times the number of rows however short the lines are; `sheets.imports.max_cells` bounds that product, and a file that goes past it fails with "The file has more than 10000000 cells (rows times columns).". The defaults are the width of an Excel sheet and 100,000 rows of 100 columns.

A workbook's reader holds what every sheet needs (the shared strings, which number formats show dates, the sheet names) and streams the sheet it reads, so a sheet takes memory for the cells the table keeps, not for the area between its first cell and its last: two cells at `A1` and `XFD1048576` are two cells. An ODS row or cell that says it repeats (`table:number-rows-repeated`, `table:number-columns-repeated`) is read once: empty rows that repeat are counted, not made, and a row with values counts against the limits once for each time it repeats, as rows of its own. As spreadsheets do, an ODS row stops at 16,384 columns and a sheet at 1,048,576 rows, and an XLSB sheet ends at a row past 1,048,576.

An XLSX or XLSB file is read as the package it is: the workbook is found through the package's relationships, and the shared strings, the styles and the sheets through the workbook's. A target is a relative reference (`../xl/worksheets/sheet1.xml`, `/xl/book.xml`, `worksheets/a&amp;b.xml`), and a part the relationships don't name is looked for under its usual name beside the workbook. Elements of a cell other than its value (`<extLst>`) are passed over. Chart sheets and Excel 4 macro sheets are listed among the sheets and hold no cells; XLS doesn't list them.

An XLS file is read a record at a time from its workbook stream, which is copied out of the compound file once and held for the reading, as the shared strings are; every sheet is read once when the file is opened, keeping nothing, so that a damaged sheet makes the file unreadable whichever sheet is asked for. A sheet's records run up to the next sheet the workbook lists: two sheets listed at one place, or a sheet that has not ended where the next one starts, make the file unreadable, so opening goes through the stream at most twice whatever the listing says. A file that starts as a compound file but does not read as XLS is read as a zip workbook, and an encrypted XLS file is refused ("The workbook cannot be read: the workbook is encrypted.").

A sheet whose cells are not listed by row and then by column (Excel never writes one; an ODS sheet always is) is kept as its cells with a value until the sheet ends (about 60 bytes for each cell), but no more than the limits allow: a cell in a column past `max_columns` is kept only as a mark that its row has something there, and the sheet is refused once it holds more than `max_rows` + 1 rows or more than `max_cells` cells. So such a sheet is refused when it has more than `max_cells` cells with a value, even if its header is narrow enough that the table made of it would have stayed within the limits; the same sheet in order is not.

`sheets.imports.max_upload_bytes` bounds the file as it is uploaded, not what a workbook unpacks to, and a small zip file can unpack to a thousand times its size. The XLSX and XLSB readers keep a workbook's shared strings in memory for the whole reading, and read the text of a cell whole while they read that cell; the sheet itself is read as a stream. `sheets.imports.max_inflated_bytes` (default 1 GiB, about twice the sheet XML of a workbook that holds `max_cells` cells) refuses a workbook, before any part is read, when a part of the zip file declares more than that once unpacked: "The workbook has a part that unpacks to more than 1073741824 bytes.". It is checked on every file opened as a workbook, whatever its first bytes say, so it covers XLSX, XLSB and ODS however the format was detected: a zip archive behind another header is checked too. For XLS it bounds the workbook stream, measured on the sectors that hold it before it is copied: "The workbook stream is larger than 1073741824 bytes.". A file cannot lie its way past it: the zip reader stops a part at the size the file declares for it, so a file that declares less than a part holds cannot be read, and one that declares more is refused. The bound is generous, not small. The shared strings are kept trimmed, in one text with 4 bytes for each string besides its text, and what they take counts against the same limit: a workbook whose strings take more fails with "The workbook's shared strings take more than 1073741824 bytes.". An XLSX part's strings take at most about the size of its XML; an XLSB part's text, UTF-16 in the file, can take up to half as much again as UTF-8. The number of strings a file declares (`uniqueCount`, or the count in `sharedStrings.bin`) sets no memory aside: the strings are counted as they are read.

Opening a workbook can't be interrupted, so what it may cost is bounded whatever the file says. Everything an XLSX, XLSB or ODS workbook keeps while it opens (the shared strings, the sheet names, the relationships, the number formats and cell formats) counts against one budget of `max_inflated_bytes`, and a file past it can't be read: "The workbook cannot be read: what it holds to be opened takes more than 1073741824 bytes.". A workbook that fills the budget holds up to about 1.7 times the limit once it is open (a relationship or a format takes more than it is counted as) and up to about 2.3 times for a moment while its strings grow, so about 1.7 and 2.3 GiB at the default; lower the limit on a host with less. A sheet is an entry in those lists, and one relationship that many sheets name is held once; a workbook has at most 65,535 sheets, in every format. One element's tag, one run of text or one string made of several runs, and one XLSB record take at most 16 MiB, far over the longest text a cell has in Excel: "The workbook cannot be read: its XML: ... an element or a text is longer than 16777216 bytes.". The reader holds a few buffers of that length, at most about 160 MiB, whatever the part's size. A sheet's dimension is read piece by piece, and a relationship target longer than 65,535 bytes, the longest name a part has, leads nowhere without being resolved, so neither takes memory beyond the bytes it is. Elements nest at most 256 deep, with names of at most 1,024 bytes, so the elements still open take at most 256 KiB. Each part is read in one pass, in time in proportion to its bytes, a number format is looked at once however many cell formats use it, and opening unpacks at most four times `max_inflated_bytes` in all (4 GiB by default), for all the parts of all the formats it tries: "The workbook takes more than 4294967296 bytes of reading to open.". That time goes down with the limit. An XLS workbook holds its stream and its shared strings, each under its own limit, with its other lists bounded by their formats (65,535 sheets, 65,536 cell formats and as many number formats), and goes through the stream at most twice. The zip file's directory is held too, in time and memory in proportion to the file, which `max_upload_bytes` bounds.

`sheets.imports.max_text_bytes` (default 256 MiB, 10,000,000 cells of 26 bytes) bounds the text the table keeps. `max_cells` counts cells, not bytes, and a shared string, which a workbook stores once, is copied into every cell that uses it, so a small file can ask for a text of a megabyte in ten thousand cells. The bytes of text (trimmed, as kept) of the header and of every cell the table keeps are counted as the file is read, the same text again for each cell it is in, and a file past the limit fails with "The file holds more than 268435456 bytes of text.". An XLS workbook's shared strings count against `max_text_bytes`, trimmed, as they are decoded, before the sheet is read: "The workbook's shared strings hold more than 268435456 bytes of text.". For every workbook format the text is counted before it is copied, so a shared string used in many cells, or a value in an ODS row or cell that repeats, is never copied past the limit, and a shared string is trimmed once however many cells use it. An ODS cell can repeat a space as many times as it says (`<text:s text:c="1000000"/>`): spaces that end a cell are held until text follows them and are never made when none does (before a tab, a line break or the end of a paragraph too), and spaces inside it count, with the rest of its row's text, against `max_text_bytes` before they are made, so a row that would hold more text than that fails with the same message; the spaces a sheet makes count together against it, whatever the shape of its rows, and are made a piece at a time. A row that repeats no time or lies past the last row, and a cell that repeats no time or lies past the last column, are read through and make no text. A cell in a column the table cuts makes no text: its own text is only counted, with the same limit and the same message. Error cells (`#Div0`) count as the text they are kept as. Numbers, dates and booleans hold no text, and a cell past the header's width is cut and not counted. CSV and TSV files are counted by the same rule, as their cells are taken.

The default lets through a workbook at the other limits whose cells average 26 bytes of text; the table also takes 24 bytes or more for each cell (about 60 for each cell of a sheet that is out of order), so a file near both limits takes about half a gigabyte for its cells and as much for its text. Text at the limit is in proportion to the cells at theirs, which is why the default is 256 MiB: a smaller one would refuse tables the cell limit lets through, and a larger one would let a small file's shared strings, copied into every cell, outgrow the table's cells many times over. A sheet that is out of order counts every cell it holds before the header is known, so there too a file can be refused for text that the header's width would have cut. The header's names are made of its cells' text, moved, and a set that keeps them apart holds them again, so a header whose cells are all one long shared string takes about 2.3 times the text limit while it is named.

When a sheet breaks a limit, the rest of a workbook's sheet is still read through, keeping nothing, so that a sheet that cannot be read is reported as such; that takes time in proportion to the unpacked size of the sheet (at most `max_inflated_bytes`), unless the job's timeout stops it first.

### Mapping columns

Staging needs to know which header each field reads. In order, it uses:

1. **The mapping given** with the upload or chosen later.
2. **A saved mapping** for this importer, workspace and set of headers. Files with the same headers in any order and case reuse it.
3. **Automatic mapping.** Each column takes the first unused header that matches its header, its field name or one of its aliases, comparing only letters and digits in lower case: `E-mail Address`, `email_address` and `EMAIL ADDRESS` match.

When a required column has no header, the import stops at `needs_mapping`, with the file's `headers`, the automatic `mapping` and the `missing` fields. The client shows the headers next to your columns and sends a mapping:

```http
PUT /api/imports/{id}/mapping
Content-Type: application/json

{ "mapping": { "email": "Mail", "name": "Full name" }, "save": true }
```

The import is staged again with it (`202`), and with `save` the next file with these headers maps itself. A mapping that names a field the importer lacks or a header the file lacks, reads one header twice, or leaves a required column unmapped is a `400` with the errors by field:

```json title="400 Bad Request"
{
  "statusCode": 400,
  "message": ["email is mapped to `Email`, which is not a column of the file", "email should not be empty"],
  "error": "Bad Request",
  "code": "validation_failed",
  "errors": {
    "email": ["email is mapped to `Email`, which is not a column of the file", "email should not be empty"]
  }
}
```

### Previewing

A staged import (`staged`) has its counts, and every row is in `import_rows` with its status, its values and its errors:

```http
GET /api/imports/{id}/rows?status=invalid&page=1&per_page=50
```

```json
{
  "data": [
    {
      "row": 14,
      "status": "invalid",
      "values": { "email": "ada@example", "name": "Ada Lovelace", "company": null },
      "errors": { "email": ["email must be a valid email address"] }
    }
  ],
  "meta": { "current_page": 1, "per_page": 50, "total": 3, "last_page": 1 }
}
```

`per_page` is 50 by default and at most 500. Without `status`, every row is listed.

| Row status | Meaning |
|---|---|
| `valid` | Read and validated; saved when the import is applied |
| `invalid` | A cell doesn't fit or a rule failed; `errors` says which |
| `duplicate` | Its key is one the app already has |
| `repeated` | Its key repeats an earlier row of the file (`"row": ["Repeats row 3"]`) |
| `created`, `updated` | Saved as a new record, or as an update of the existing one |
| `skipped` | A duplicate, left alone |
| `failed` | Saving it failed; `errors` says why |

### Applying

```http
POST /api/imports/{id}/apply
Content-Type: application/json

{ "duplicates": "update" }
```

| `duplicates` | Duplicates are |
|---|---|
| `skip` (the default) | Left alone, and listed in the error file |
| `update` | Saved with `update` |
| `fail` | Refused: applying is `409 import_has_duplicates` while the file has duplicates or repeated rows |

The answer is `202` (status `applying`) with a new operation. The rows to save are cut into jobs of `sheets.imports.chunk_size` rows (`sheets.import.apply`), dispatched as one [batch](/docs/digging-deeper/batches-and-operations/#batches) whose progress is the operation's. Each row is saved in its own unit of work, as the user who uploaded the file, so one failing row never rolls back another, and the row's new status commits with it. Repeated rows are never applied, whatever the mode.

When the batch is done, its last job (`sheets.import.finish`) counts the rows, writes the error file, marks the import `completed` and calls `completed`. Cancelling the operation (`DELETE /api/operations/{id}`) stops it between rows: the import goes back to `staged` with an `error` saying how many rows were saved, and applying it again saves the rest.

| Import status | Meaning |
|---|---|
| `uploaded` | Stored; reading it is queued |
| `staging` | Being read and checked |
| `needs_mapping` | A required column has no header: choose a mapping |
| `staged` | Ready to preview and apply |
| `applying` | Rows are being saved |
| `completed` | Every row was saved, skipped or reported |
| `failed` | The file could not be read; `error` says why |

### Error files

When rows are not saved, the import has an error file (`has_error_file`), written after staging and again after applying:

```http
GET /api/imports/{id}/errors
```

returns `contacts-errors.csv`: the row number, the mapped columns under the file's own headers, and the errors.

```text title="contacts-errors.csv"
Row,Email,Name,Errors
3,ada@example,Ada,email must be a valid email address
7,bob@competitor.example,Bob,Contacts at competitors are not imported
9,grace@example.com,Grace,A record with this key already exists
```

Because the headers are the file's own, the user fixes the rows and uploads the file again; it maps the same way, and the extra `Row` and `Errors` columns are ignored.

### Templates and the importers list

`GET /api/imports/templates/{importer}` returns an empty file with the importer's headers (`contacts-template.csv`, or `.xlsx` with `?format=xlsx`). `GET /api/imports/importers` lists the importers the user may use, with their columns (`field`, `header`, `aliases`, `required`), so a front end can build the mapping screen.

## Routes

Both controllers mount under `{http.api_prefix}` (default `/api`) when their `routes` key is true and the app has an authenticator. Every route needs a signed-in user. In an app with [workspaces](/docs/workspaces/introduction/) they act in the request's workspace, and permissions are checked in it.

| Route | Answer |
|---|---|
| `GET /exports` | `{data: [{name, columns: [{key, header}]}]}`: the exports the user may run |
| `GET /exports/{name}?format=csv&...` | The file; the query string fills the parameters |
| `POST /exports/{name}` `{format?, params?}` | `202`, the operation |
| `GET /imports?limit=20` | `{data: [Import]}`: the user's own imports, newest first (at most 100) |
| `POST /imports` (multipart) | `202`, the import |
| `GET /imports/importers` | `{data: [{name, columns}]}` |
| `GET /imports/templates/{importer}?format=csv` | The template |
| `GET /imports/{id}` | The import |
| `GET /imports/{id}/rows?status=&page=&per_page=` | A page of rows |
| `PUT /imports/{id}/mapping` `{mapping, save?}` | `202`, the import, staged again |
| `POST /imports/{id}/apply` `{duplicates?}` | `202`, the import |
| `GET /imports/{id}/errors` | The error file, `404` when there is none |
| `DELETE /imports/{id}` | `204`; `409` while it is being applied |

An import is visible to the users who hold its importer's permission in its workspace, and is a `404` to everyone else (for an importer without a permission, to everyone but the uploader). The `Imports` service has the same operations for your own code: `upload`, `find`, `list`, `rows`, `map`, `apply`, `discard`, `error_file`, `template` and `columns`.

## Testing

Run imports and exports in tests with the memory queue and a memory disk. `run_pending` runs the queued staging, apply and export jobs. `temp_database()` creates a SQLite file, so the test build needs the `sqlite` feature ([database tests](/docs/testing/database-tests/#a-database-for-every-test)):

```rust title="tests/contacts.rs"
let app = TestApp::builder()
    .temp_database()
    .config("queue.driver", "memory")
    .config("storage", json!({ "default": "files", "disks": { "files": { "driver": "memory" } } }))
    .module(DatabaseModule::from_config())
    .module(QueueModule::from_config())
    .module(StorageModule::from_config())
    .module(SheetsModule::from_config())
    .module(ContactsModule)
    .build()
    .await;
let imports = app.get::<Imports>().await;
let db = app.get::<Db>().await;

let uow = db.uow(Some(ADMIN), None).await;
let import = imports
    .upload(
        &uow,
        "contacts",
        Upload::new("contacts.csv", "Email address,Name\nada@example.com,Ada Lovelace\n"),
        UploadOptions::default().owner(ADMIN),
    )
    .await?;
uow.commit().await?;
app.get::<Queue>().await.run_pending().await?;
assert_eq!(imports.find(import.id).await?.status, ImportStatus::Staged);

let uow = db.uow(Some(ADMIN), None).await;
imports.apply(&uow, import.id, DuplicateMode::Update).await?;
uow.commit().await?;
app.get::<Queue>().await.run_pending().await?;
assert_eq!(imports.find(import.id).await?.counts.created, 1);
```

Over HTTP, post a `multipart/form-data` body with `importer` and `file` fields. Encode test files in the encoding you want to check: `encoding_rs::WINDOWS_1256.encode(text)` for Arabic, or a byte-order mark followed by `text.encode_utf16()` for Excel's Unicode text.

## Limits

- Staging reads the whole file into memory, so `sheets.imports.max_upload_bytes` bounds the file itself, and `sheets.imports.max_columns` and `sheets.imports.max_cells` bound the table made from it. It does not bound what a workbook unpacks to: `sheets.imports.max_inflated_bytes` does, per part, as the zip file declares it (see above). CSV, TSV, XLSX, XLSB, ODS and XLS files are refused as soon as a row breaks a limit, without the rows being held, and a sheet that is not in order is held up to the limits. `sheets.imports.max_text_bytes` bounds the text the table keeps, whatever the format.
- Staging reads the file on Tokio's blocking pool, so a large file doesn't hold up the app's async threads, and the queue's job timeout can fire while it reads. When it does, the reading stops instead of carrying on with a file and a table nobody will use, so a retry doesn't run beside it: a workbook's sheet within 64 KiB of its part (an XLS sheet within 1,024 records), whether or not what it reads gives a cell (empty cells, rows that repeat no time, the rest of a sheet after a limit), and a text file at its next record. Opening a workbook (its shared strings, its styles, for ODS a first reading of all of `content.xml`, for XLS a first reading of every sheet) can't be interrupted; the reading stops when it returns, so a retry can run beside it for that long. How long that can be is bounded by the unpacked bytes opening may read (see above), so lower `sheets.imports.max_inflated_bytes` to shorten it.
- Duplicates are found while staging. A record created between staging and applying is caught by your database's unique constraints: the row fails with your `insert`'s error.
- The jobs run on the `default` queue.
