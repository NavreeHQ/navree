## Quick start

The smallest setup: turn the feature on, write a message and look it up. The rest of the page explains each part.

```toml title="Cargo.toml"
navree = { git = "https://github.com/NavreeHQ/navree", features = ["i18n"] }
```

```text title="locales/en/main.ftl"
deal-created = { $count ->
    [one] One deal created
   *[other] { $count } deals created
}
```

```rust
// src/app.rs: .module(I18nModule::from_config())
let line = t!("deal-created", count = 3);
```

The defaults read `locales/` and support `en`. [Configuration](#configuration) adds locales and says how the request's locale is chosen; [translating in code](#translating-in-code) covers `t!` in full.

## Introduction

<Badge feature="i18n" /> `navree-i18n` lets one app answer a sales team in Lyon in French and one in Munich in German, from the same code. You write your text in [Fluent](https://projectfluent.org) files, one directory per locale, and look messages up by id:

```rust
// "3 deals created", or "3 affaires créées" in French:
let message = t!("deal-created", count = 3);
```

- **Fluent** handles what string tables can't: plurals with the rules of each language, selectors, terms and attributes, and numbers, amounts and dates formatted for the locale.
- **The locale is negotiated** for each request from, in an order you choose, a query parameter, the user's saved preference, the [workspace](/docs/workspaces/introduction/)'s saved locale, a cookie and `Accept-Language`.
- **It follows the work.** Mail rendered during a request is in the request's locale, and notifications render in the recipient's.
- **Validation messages** are translated, with field names, so a `400` reads "prénom ne doit pas être vide".
- **Checked in CI.** `navree i18n:check` fails on a syntax error or a message missing from a locale.

## Installation

The `i18n` feature of the `navree` facade is opt-in (it is not part of `full`, because it compiles in ICU4X's locale data), so turn it on by name:

```toml title="Cargo.toml"
[dependencies]
navree = { git = "https://github.com/NavreeHQ/navree", features = ["i18n"] }
```

It brings `navree::i18n` (the `navree-i18n` crate with `t!`, `args!` and `embed_locales!`) and puts `I18nModule` and `Locale` in the prelude.

Add `I18nModule` to your app root. Put it before `ValidationModule` and `MailModule`, whose messages it translates:

```rust title="src/app.rs"
Navree::app()
    .module(ConfigModule::for_root(sources))
    .module(HttpModule::from_config())
    .module(I18nModule::from_config()) // section `i18n`
    .module(ValidationModule::from_config())
    .module(ViewModule::from_config())
    .module(MailModule::from_config())
    // ...
```

The module is global. It adds a layer that negotiates each request's locale, the `Locale` extractor, the `I18n` service and the `t()` function in [templates](/docs/digging-deeper/views/). It contributes the migration set `i18n`, which creates `locale_preferences` for saved user and workspace locales when the app has `DatabaseModule`. The table has a row per user or workspace: `scope_type` (`user` or `workspace`), `scope_id` (a `uuid`, `BINARY(16)` on MySQL and MariaDB), `locale` and `updated_at`, with `(scope_type, scope_id)` as its key. Write it through `I18n`; `navree::i18n::migration::LocalePreferenceRow` is its `navree::db::Record`, for reading it yourself.

## Configuration

```toml title="config/app.toml"
[i18n]
default_locale = "en"
locales = ["en", "fr", "de", "pt-BR"]
dir = "locales"
negotiation = ["query", "user", "workspace", "cookie", "header"]
missing = "warn"          # warn | error | id
```

| Key | Default | Meaning |
|---|---|---|
| `i18n.default_locale` | `en` | The locale when negotiation finds nothing, and the last fallback for missing messages |
| `i18n.locales` | `["en"]` | The supported locales, as BCP 47 tags |
| `i18n.dir` | `locales` | Where the Fluent files are, relative to the working directory |
| `i18n.negotiation` | `["user", "workspace", "header"]` | The sources the locale comes from, first match wins |
| `i18n.query_param` | `locale` | The `query` source's parameter |
| `i18n.cookie` | `locale` | The `cookie` source's cookie name |
| `i18n.missing` | `warn` | A missing message: `warn` logs once and shows the id, `error` fails the lookup (and `t!` panics), `id` shows the id silently |
| `i18n.reload` | `false` | Reloads changed files without a restart, checked twice a second (development; not with embedded files) |
| `i18n.bidi_isolation` | `auto` | Unicode isolation marks around variables: `auto` uses them only when a locale is right-to-left, `always` (or `true`) and `never` (or `false`) |
| `i18n.routes` | `true` | Mounts `GET /api/i18n/locales` and `PUT /api/me/locale` |

From the environment: `APP_I18N__DEFAULT_LOCALE=fr`, and lists as comma-separated strings, `APP_I18N__LOCALES=en,fr,de`. A locale tag that doesn't parse, a `default_locale` that isn't in `locales`, a Fluent file with a syntax error or a message defined twice fails the boot, naming the key, or the file and line.

### Shipping the files in the binary

By default the files are read from `i18n.dir` at boot, so they must be deployed next to the binary. To build one self-contained binary, embed them at compile time instead:

```rust title="src/app.rs"
use navree::i18n::{I18nOptions, embed_locales};

Navree::app().module(I18nModule::for_root(I18nOptions {
    files: embed_locales!("locales"),
    locales: vec!["en".into(), "fr".into(), "de".into()],
    ..I18nOptions::default()
}))
```

`embed_locales!` reads the directory, relative to your crate's `Cargo.toml`, when you build, so a syntax error in a Fluent file becomes a compile error naming the file and line. Editing a file rebuilds the crate; a new file is picked up on the next build of the crate.

## Writing translations

Each locale has a directory under `locales/`, and each directory holds any number of `.ftl` files, also in subdirectories. The file names are only for you: every message of a locale shares one namespace, and a message defined twice is an error.

<FileTree title="Translations for three locales">{`
locales/
  en/
    main.ftl
    deals.ftl *
    mail.ftl
    validation.ftl
  fr/
    main.ftl
    deals.ftl *
    mail.ftl
    validation.ftl
  pt-BR/
    deals.ftl
`}</FileTree>

A message is an id, an equals sign and its text. Variables are `{ $name }`, and a selector picks a variant, with `*` marking the default one:

```text title="locales/en/deals.ftl"
deal-created = { $count ->
    [one] One deal created
   *[other] { $count } deals created
}

deal-won = { $owner } won { $title }.
deal-won-subject = You won { $title }
deal-stage-negotiation = Negotiation
deal-amount = { $amount }
deal-closes = Closes { DATETIME($date, dateStyle: "long") }

pipeline-empty = Your pipeline is empty. Create a deal to get started.
```

```text title="locales/fr/deals.ftl"
deal-created = { $count ->
    [one] Une affaire créée
   *[other] { $count } affaires créées
}

deal-won = { $owner } a gagné { $title }.
deal-won-subject = Affaire gagnée : { $title }
deal-stage-negotiation = Négociation
deal-amount = { $amount }
deal-closes = Clôture le { DATETIME($date, dateStyle: "long") }

pipeline-empty = Votre pipeline est vide. Créez une affaire pour commencer.
```

Plural categories (`zero`, `one`, `two`, `few`, `many`, `other`) follow each language's rules: Polish has `few` and `many`, Japanese only `other`. Exact numbers like `[0]` match before categories.

Arguments format with the locale's conventions:

- **Numbers** get the locale's separators: `{ $count }` is `1,234` in `en` and `1 234` in `fr`. `NUMBER()` takes `style` (`decimal`, `percent`, or `currency` with a literal `currency: "EUR"`), `useGrouping`, `minimumIntegerDigits`, `minimumFractionDigits` and `maximumFractionDigits`; a year is `{ NUMBER($year, useGrouping: "false") }`.
- **Amounts** are `Money` arguments: `t!("deal-amount", amount = Money::new(4_200_000, "EUR"))` reads `€42,000.00` in `en` and `42 000,00 €` in `fr`. Fluent's named arguments are literals, so a currency that varies travels inside the `Money` value.
- **Dates** are chrono values (`NaiveDate`, `NaiveDateTime`, `DateTime`): `Oct 26, 2026` in `en`, `26 oct. 2026` in `fr`. `DATETIME()` takes `dateStyle` (`short`, `medium`, `long`, `full`) and `timeStyle` (`short`, `medium`), which adds the time.

A message missing from `fr-CA` falls back to `fr`, then to `default_locale`. Region-specific files only need the messages that differ. A message's attributes are looked up as `id.attribute`: `t!("login.title")`.

## Translating in code

### The t! macro

`t!` looks a message up in the current locale. Arguments are `name = value`; numbers, strings, `bool`s, `Money`, chrono dates and `Option`s of those work:

```rust title="src/modules/deals/service.rs"
use navree::i18n::t;

pub fn import_summary(created: usize) -> String {
    t!("deal-created", count = created)
}

let line = t!("deal-won", owner = user.name.as_str(), title = deal.title.as_str());
```

During a request, the current locale is the one negotiated for it. Elsewhere (a job, a command, a scheduled task) it is `default_locale`. To translate in another locale, run the code inside `Locale::scope`, which takes a `Locale` or a tag:

```rust
use navree::i18n::Locale;

let subject = Locale::scope("de", async {
    t!("deal-won", owner = "Ada", title = "Lovelace renewal")
})
.await;
// "Ada hat Lovelace renewal gewonnen."
```

A tag is matched with the supported locales as a request's is, so `fr-CA` scopes to `fr`, and an unsupported one to `default_locale`. A [validated](/docs/basics/validation/) `navree::validation::Locale` from a request body works as a tag too: `Locale::scope(&input.locale, ...)`. Outside a request, `Locale::current()` and tags given to `Locale::scope` use the app that booted last in the process (`I18n::scope` and `I18n::locale` name one explicitly).

A job of your own runs in `default_locale`. To run it in the locale of the request that dispatched it, carry the tag in the job:

```rust
#[derive(Serialize, Deserialize)]
pub struct SendDigest {
    pub user_id: Uuid,
    pub locale: String, // Locale::current().tag().to_owned() when dispatched
}

impl Job for SendDigest {
    const NAME: &'static str = "deals.send_digest";

    async fn handle(self, ctx: JobContext) -> Result<(), BoxError> {
        Locale::scope(self.locale, async move {
            // t!(...) and templates are in the dispatching request's locale
            Ok(())
        })
        .await
    }
}
```

### The Locale extractor

Take `Locale` in a handler to see which locale was negotiated, or to format with it:

```rust
use navree::i18n::{Locale, t};

#[get("/summary")]
#[can(Read, Deal)]
async fn summary(&self, locale: Locale, uow: Uow) -> Result<Json<serde_json::Value>> {
    let open = self.deals.open_count(&uow).await?;
    Ok(Json(serde_json::json!({
        "locale": locale.tag(),                              // "fr"
        "headline": t!("deal-created", count = open),
        "total": locale.format_money(4_200_000, "EUR"),       // "42 000,00 €"
        "updated": locale.format_date(chrono::Utc::now()),   // "26 oct. 2026"
    })))
}
```

`Locale` also has `language()` (`pt` for `pt-BR`), `format_number`, `format_date_with(date, DateStyle::Long)`, `direction()` (`ltr` or `rtl`), `native_name()`, `translate(id, &args)` and `has(id)`. Every response that passes through the layer carries `Content-Language: fr`.

### The I18n service

`I18n` translates in an explicit locale, without changing the current one, and manages saved preferences:

```rust
use navree::i18n::{I18n, args};

let text = i18n.t("pt-BR", "deal-created", args!(count = 2))?; // "2 negócios criados"
let supported = i18n.locales(); // ["en", "fr", "de", "pt-BR"]
i18n.has("fr", "pipeline-empty"); // true

i18n.set_user_locale(&uow, user.id, "fr").await?;
i18n.set_workspace_locale(&uow, workspace.id, "de").await?;
```

`t` falls back like `t!`, translates in `default_locale` when the tag matches no supported locale, and returns `I18nError::InvalidLocale` for a string that is not a language tag. `has` looks at the locale and its parents, not at the default locale's fallback. Saving an unsupported locale is `I18nError::UnsupportedLocale`, and saving without `DatabaseModule` is `I18nError::NoDatabase`. `I18n::new(options)` builds one without an app, for tools and unit tests.

## Negotiating the locale

The layer tries the sources in `i18n.negotiation`, in order, and keeps the first supported locale:

| Source | Reads |
|---|---|
| `query` | `?locale=fr`, for links in mails and shared URLs |
| `user` | The signed-in user's saved locale |
| `workspace` | The saved locale of the [workspace](/docs/workspaces/introduction/) the request names, when the signed-in user is a member |
| `cookie` | The `locale` cookie, which a BFF can set |
| `header` | `Accept-Language`, by quality: `fr-CA;q=0.9, en;q=0.8` |

Matching is lenient where it helps: `fr-CA` falls back to `fr` when only `fr` is supported, and `pt` matches `pt-BR` when that is the first Portuguese locale. A source that names an unsupported locale is skipped, not an error, and nothing supported means `default_locale`.

Users save their locale with a built-in route, mounted when `i18n.routes` is on (the default) and the app has `DatabaseModule` and an authenticator:

```http
PUT /api/me/locale HTTP/1.1
Authorization: Bearer eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9...
Content-Type: application/json

{ "locale": "fr" }
```

The answer is `204`, and the matching supported locale is saved (`fr-FR` is saved as `fr`). An unsupported locale is a 400 with `errors.locale`, in the request's language. `GET /api/i18n/locales` lists the supported locales with their names in their own language for a language picker:

```json
{
  "data": [
    { "tag": "en", "name": "English", "direction": "ltr", "default": true },
    { "tag": "fr", "name": "Français", "direction": "ltr", "default": false },
    { "tag": "pt-BR", "name": "Português (Brasil)", "direction": "ltr", "default": false }
  ]
}
```

## Validation messages

With `I18nModule` in the app, [validation](/docs/basics/validation/) messages come from Fluent. Each message key from the [validation message table](/docs/basics/validation/#message-keys) becomes an id prefixed with `validation-`, with dots turned into hyphens (`min.string` is `validation-min-string`), and the placeholders become variables (`$attribute`, `$min`, `$max`, `$other`, `$values`, `$value`, `$format`, `$pattern`; numbers are numbers, so they select plural variants):

```text title="locales/fr/validation.ftl"
validation-required = { $attribute } ne doit pas être vide
validation-email = { $attribute } doit être une adresse e-mail valide
validation-min-string = { $attribute } doit contenir au moins { $min } { $min ->
        [one] caractère
       *[other] caractères
    }
validation-unique = { $attribute } est déjà utilisé

field-first_name = prénom
field-last_name = nom
field-email = adresse e-mail
```

`field-<path>` gives a field its display name, as `validation.attributes` does (a dotted path's dots become hyphens: `field-address-city`). A request in French then gets:

```json
{
  "statusCode": 400,
  "message": ["prénom ne doit pas être vide"],
  "error": "Bad Request",
  "code": "validation_failed",
  "errors": {
    "first_name": ["prénom ne doit pas être vide"]
  }
}
```

navree-i18n ships the validation messages in English, French, German, Spanish, Italian, Dutch and Brazilian Portuguese, used for every locale of those languages. They cover every key of the table, the international ones too (`phone`, `country`, `locale`, `unicode_name`). A message comes from, in order: your Fluent message for the locale or a parent of it; in the default locale's language, the `validation.messages` section; the shipped message for the locale's language; the `validation.messages` section; the default locale's message; the built-in English template. So `validation.messages` still overrides English when English is the default, and translated languages keep their translations. Copy the shipped messages into your `locales/` to edit them:

```sh
navree i18n:publish validation
```

It writes `locales/<locale>/validation.ftl` for each supported locale whose language is shipped, and keeps files that exist unless you add `--force`.

## Mail and notifications

Templates get a `t` function and a `locale()` function, and the `money` and `date` filters format for the current locale (`date` without a format uses the locale's medium style; with a `strftime` format it formats as before):

```jinja title="views/mail/deal-won.html"
<html lang="{{ locale() }}">
<h1>{{ t("deal-won", owner=owner.name, title=deal.title) }}</h1>
<p>{{ deal.amount_cents | money(deal.currency) }}</p>
<p>{{ t("mail-footer") }}</p>
```

A mail renders in the locale that is current when it is rendered, so translate the subject with `t!` where you build it:

```rust
let subject = t!("deal-won-subject", title = deal.title.as_str());
let mail = TemplateMail::new(&owner.email, subject, "mail/deal-won")
    .context(json!({ "owner": owner, "deal": deal }));
mailer.queue(&mail).await?;
```

`Mailer::queue` renders the mail before it dispatches the job, so queued mail is in the locale of the request that queued it. Mail to someone else, such as a deal owner who reads French while a German manager reassigns the deal, should use the recipient's locale. [Notifications](/docs/digging-deeper/notifications/) do that for you: navree-i18n renders each notification for a user (`via`, `to_mail`, `to_database`, and its mail when a queued notification is delivered) inside `Locale::scope` with the user's saved locale, or `default_locale` when the user saved none. For a mail you send yourself, wrap it:

```rust
let locale = i18n.user_locale(owner.id).await?; // saved, or default_locale
Locale::scope(locale, async { mailer.queue(&deal_won_mail(&owner, &deal)).await }).await?;
```

## Navree UI in the reader's language

With the `ui` and `i18n` features on together, `navree::i18n::ui` gives [Navree UI](/docs/ui/overview/) the reader's words, money and dates, so a page needs no translation work of its own to speak English or Hindi.

**Labels.** Every label struct of the toolkit (`TableLabels`, `StateLabels`, `UploadLabels`, `SelectLabels`, `ChartLabels` and the rest) has its words in Fluent. English and Hindi ship with the crate. A word you define under the same id in your own `locales/<tag>/*.ftl` wins over the shipped one, and a locale with no shipped words gets the toolkit's English, word by word, never a message id.

**Money.** `MoneyIn::display_in(&locale, currency)` prints an amount in minor units with the locale's grouping, separators and symbol: `Money(10_000_000)` of `INR` is `₹1,00,000.00` in `en-IN` and `hi`, `₹100,000.00` in `en`, and `100.000,00 €` in `de` with `EUR`.

**Dates.** `LocaleUi::date_locale` gives the date and time pickers the locale's month and weekday names, the order of a typed date, the first day of the week and the clock.

```rust
use navree::i18n::Locale;
use navree::i18n::ui::{LocaleUi, MoneyIn};
use navree::ui::{AppPage, AppShell, Money, TableLabels};

async fn deals(shell: AppShell, locale: Locale) -> AppPage {
    let labels = locale.labels::<TableLabels>();       // "खोजें" for the search box in hi
    let total = Money(10_000_000).display_in(&locale, "INR"); // ₹1,00,000.00 in en-IN and hi
    let dates = locale.date_locale();                  // for a picker's `.locale(dates)`
    // ... pass `&labels` to the table with `.labels(&labels)`
}
```

**Forms.** `I18nModule` also registers a `Localizer`, so a form that comes back with errors says its date, time and slider messages, its "Check this form" heading and its submit button in the language of the request. `LocaleUi::reader_words` gives those words to your own code.

## Checking translations

`i18n:check` parses every file of every locale and compares each locale with `default_locale`:

```sh
navree i18n:check
```

```text
locales/de/main.ftl:3: syntax error: Expected a message field for "welcome"
locales/fr  deal-lost: missing (defined in locales/en/deals.ftl:14)
locales/pt-BR  12 of 148 messages missing (falls back to en)
2 problem(s) in 4 locale(s)
```

It exits with status 1 when a file has an error or a message is defined twice, or when a locale other than a regional one (`pt-BR` falls back to `pt` or the default) is missing messages, so run it in CI. It loads the files leniently, so it reports syntax errors that would stop the app from booting. `i18n:missing fr` lists the missing ids of one locale, one per line, ready to send to a translator.

## Testing

Send `Accept-Language` (or `?locale=`) and assert on the translated text. Set `i18n.missing = "error"` in tests, so a missing message fails instead of showing its id:

```rust title="tests/locale.rs"
use navree::i18n::{Locale, t};
use navree::prelude::*;
use navree::testing::TestApp;
use serde_json::json;

#[tokio::test]
async fn validation_errors_are_in_the_requested_language() {
    let app = TestApp::builder()
        .config("i18n.locales", json!(["en", "fr"]))
        .config("i18n.missing", "error")
        .module(I18nModule::from_config())
        .module(ValidationModule::from_config())
        .module(ContactsModule)
        .build()
        .await;

    app.client()
        .post("/api/v1/contacts")
        .header("Accept-Language", "fr-FR,fr;q=0.9")
        .json(&json!({ "last_name": "Lovelace" }))
        .send()
        .await
        .assert_validation_error("first_name")
        .assert_json_path("errors.first_name.0", json!("prénom ne doit pas être vide"));
}

#[tokio::test]
async fn plurals_follow_the_language() {
    let app = TestApp::builder()
        .config("i18n.locales", json!(["en", "fr"]))
        .module(I18nModule::from_config())
        .build()
        .await;
    Locale::scope("fr", async {
        assert_eq!(t!("deal-created", count = 1), "Une affaire créée");
        assert_eq!(t!("deal-created", count = 3), "3 affaires créées");
    })
    .await;
    app.shutdown().await.unwrap();
}
```

`Locale::scope` works without a request, so unit tests of services that call `t!` don't need the HTTP client. Tests in one process share "the app booted last", so a test that boots apps with different locales should scope with `app.get::<I18n>().await.locale("fr")` instead of a tag.
