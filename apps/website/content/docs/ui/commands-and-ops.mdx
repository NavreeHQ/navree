Two closed lists cover everything a page does after it loads. A `Cmd` is something an element does in the browser with no request: show, hide, open, focus. An `Op` is a change the server sends back from an action: morph this element, show a toast, close that dialog. Both are data, which the runtime interprets: no expression is evaluated and nothing is `eval`ed.

## Commands

`.on_click(cmd)` on a button, or `Element::on(trigger, cmd)` on any element, runs commands in order when the trigger fires. The preview above toggles a paragraph with no request:

```rust
Button::outline("Show details").on_click(Cmd::toggle("deal-details"))
```

| Command | Does |
|---|---|
| `Cmd::toggle(id)`, `show(id)`, `hide(id)` | toggles, removes or sets `hidden` |
| `Cmd::open(id)`, `close(id)` | opens or closes a `<dialog>`, a popover or a `<details>` |
| `Cmd::focus(id)` | moves focus |
| `Cmd::submit(id)` | submits a form |
| `Cmd::copy(text)` | copies text to the clipboard |
| `Cmd::text(id, text)` | sets an element's text |
| `Cmd::count(id, max)` | writes how many characters the element's own field holds, as `12` or `12/160` |
| `Cmd::value(id, value)` | sets the value of a hidden field |
| `Cmd::fill(id)` | fills a dialog from the row the element sits in, and opens it |
| `Cmd::set_attr`, `remove_attr`, `toggle_attr` | changes a state attribute: `data-*` (not the runtime's own `data-ui-*`), `aria-*`, `hidden`, `open` or `disabled` |
| `Cmd::dispatch(name)` | sends a custom event from the element |

A command can't change where something points or what it runs. `set_attr` and its two siblings refuse any other attribute: a debug build stops where the command is built, and the runtime refuses it again. Triggers are `Trigger::Click`, `Change` and `Input`, on a button with `.on_click` and on any component or element with `.on(trigger, commands)`.

## Text, counts and values with no request

A price that changes with a plan, a counter under a field, a row's details in a dialog: each is something the page already knows, so nothing is asked of the server.

<UiPreview example="commands/text" />

```rust
Button::outline("Yearly").on_click(Cmd::text("plan-price", "$120 a year"))
```

`Cmd::count` counts characters the way the server's `length` rule does, so `12/160` in the browser means what the rule means. Put it on the field, on `Trigger::Input`:

<UiPreview example="commands/count" />

```rust
Textarea::new("bio")
    .attr("maxlength", 160_u32)
    .on(Trigger::Input, Cmd::count("bio-count", 160))
```

`Cmd::fill` copies a row's text into a dialog and opens it. The row is the nearest element with `data-key`; a [DataTable](/docs/ui/data-table/) row has one. In the dialog, `.fill_cell("title")` marks where a column's text goes and `.fill_key()` where the row's key goes. A hidden field marked either way gets it as its value, so a form in the dialog can post which row it acts on:

<UiPreview example="commands/fill" />

```rust
Button::ghost("Details").on_click(Cmd::fill("deal-details"))
// In the dialog:
el("strong").fill_cell("title")
el("input").attr("type", "hidden").attr("name", "id").fill_key()
```

`Cmd::value` sets a hidden field: the column a set of buttons sorts by, the intent of a form a command submits. Only a hidden field takes it, so a field the user types in keeps what was typed.

**What these can't do.** They write text. The runtime sets `textContent`, so a value holding `<img src=x onerror=...>` shows those characters and builds nothing. They refuse a `<script>` or `<style>` element, whose text would be code, and a field the user types in or picks from. `fill` reads cells as text too. The key a dialog's form posts is a request like any other: the handler checks the user may act on that row.

## Replies and ops

An action handler answers with a `Reply`. With the runtime, the request carries `X-Navree-UI: 1` and the answer is an envelope of ops; with JavaScript off, the same handler's answer is a redirect, a full page or `204`. `UiModule` picks between them, so you write the handler once.

Here `NewDeal` is the struct from [Forms](/docs/ui/forms/):

```rust
async fn update(Submit(deal): Submit<NewDeal>) -> Reply {
    Reply::ops_or_redirect("/deals/42")
        .morph("deal-title", Heading::h1(deal.title.clone()))
        .toast(ToastTone::Success, "Saved")
}
```

```json title="What the runtime receives"
{"build":"7dcd57c4af7d","ops":[
  {"op":"morph","target":"deal-title","html":"<h1 data-slot=\"heading\">Acme renewal</h1>"},
  {"op":"toast","tone":"success","text":"Saved"}
]}
```

`Reply::ops_or_redirect(href)` applies the ops you add and, with JavaScript off, redirects to `href`. `Reply::redirect(href)` also adds a `navigate` op, so the runtime goes to `href` after the other ops. `Reply::ops(ops)` answers `204` with JavaScript off, and `Reply::view(view)` shows its page.

| Op | Does |
|---|---|
| `morph` | morphs an element into new HTML, keeping focus, caret, selection, composition and typed values |
| `replace`, `append`, `prepend`, `remove` | replaces an element, adds to it, or removes it |
| `errors` | shows field errors under a form's inputs, or clears them |
| `toast` | shows a toast, and announces it to assistive technology |
| `open`, `close`, `focus` | opens or closes a dialog, popover or details; moves focus |
| `url` | changes the address bar without loading anything, on this site |
| `navigate` | goes to another page of this site, the way a boosted link does |
| `navigate_external` | leaves for another site, written only by `Op::navigate_external` and `Reply::redirect_external` |
| `reload` | reloads the page |
| `invalidate` | refetches a [region](/docs/ui/regions/) |

An envelope names the build of the toolkit it belongs to. A page from an older build reloads instead of running old JavaScript against new ops, so a deploy never breaks an open tab.

`Reply::redirect` and `Op::navigate` stay on this site: a URL that would leave it (`//host`, `/\host`, `https://host`) goes nowhere, so a `next` parameter from a request can't send a user away.

## Toasts

`Reply::toast(tone, text)` shows a short message after an action: "Saved", "Deleted 3 deals". With the runtime it appears at once and is announced; with JavaScript off it travels in a cookie and the next page shows it at the top, in the [app shell](/docs/ui/app-shell/). The tones are `ToastTone::Info`, `Success`, `Warning` and `Danger`.

## Links and forms, boosted

With the runtime, links on the site and forms load without a full page reload: the runtime fetches the next page and morphs it in. A form shows the pending state on its submit button and sets `aria-busy` while it posts. `data-ui-noboost` keeps a link out of this: it loads for real.

A form on its way ignores a second submit that would send the same thing: a double click or `Enter` twice writes once. A submit that sends something new, such as a field check sent on every keystroke, waits and goes when the first answer is back. Only the latest waits, so typing faster than the server answers loses nothing and sends no backlog. If the first answer leaves the page, what waited is dropped.

Field errors in an answer take focus only for a save the user asked for and is still waiting on. A check a command sent while the user types, or a save the user clicked and then moved on from, shows its errors and leaves focus where the user is.

In a filter form that updates a region, such as a [DataTable](/docs/ui/data-table/)'s toolbar, a tick, a radio or a select applies at once. Text waits for a pause in the typing: 100 ms, or what the table's `.debounce(wait)` says.

## Fetching ahead of a click

A link the toolkit knows is navigation (a sidebar item, a breadcrumb, a table's sort and page links) and a link marked with `.prefetch()` is fetched when the pointer rests on it or it takes focus, so the page is often there before the click. Only mark a link whose `GET` changes nothing.

Nothing is fetched with no hover unless a link asks: `.prefetch_eager()` on an element, a `Button` or a `NavItem` fetches it as soon as the page is quiet. It costs that page's bytes on every visit, so keep it for the one or two places users almost always go next. The runtime takes at most four such links a page, and none on a slow or data-saving connection. It pays most for a page that is the same for every user and says so with `View::cache("public, max-age=60")`. A page that differs per user stays `no-store`: what was fetched stands in for a click for only a few seconds, and a write in any tab drops it.
