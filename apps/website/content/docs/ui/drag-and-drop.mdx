A drag feels finished the moment the item lands, but the move is only real once your server has saved it. [Sortable](/docs/components/sortable/) does both: the page moves the item at once and posts the move; your handler checks it and saves it, or refuses it, and the page puts the item back with a toast.

## What a move says

A drop posts a `Move`: the item, the list the browser saw it in, the list it goes to, and the items on either side of where it landed.

| Field | Means |
|---|---|
| `item` | the key of the item that moved |
| `from_list` | where the browser saw it; if it is somewhere else now, someone moved it first |
| `to_list` | where it goes, the same list to reorder |
| `before` | the item it lands before |
| `after` | the item it lands after, sent too, for a drop below the last item the page holds |
| `position` | a number, from the form people use with JavaScript off |

It names neighbours, not an index. An index means something different to every page that has a different filter or a different number of items loaded; a neighbour means the same thing everywhere.

The form people use with JavaScript off sends a `position` instead, and the server reads it in the whole list. So when a filter draws only some of a list, give each item its place in the whole list with `SortItem::position`, and put the filters in the `post` address (`/board/moves?label=bug`) so the page the move goes back to is the filtered one.

## Checking a move

Lock the lists the move touches, read them in the transaction that writes the move, and hold the move to them:

```rust
mv.lock(&uow, &Column::KEY).await?; // a row per list, before anything is read
let lists = vec![
    ListState::new("ready", "Ready", ready_keys).limit(5),
    ListState::new("doing", "In progress", doing_keys).limit(3),
    ListState::new("done", "Done", done_keys).refuse_if(!user.is_lead(), "Only a lead can move cards to Done."),
];
match mv.check(&lists) {
    Ok(landing) => save(landing.to_list, landing.order),
    Err(refusal) => return Ok(mv.refused("/board", refusal.message())),
}
```

`check` refuses with a `Refusal`: `Stale` (the item has moved), `Moved` (its neighbour has), `Full`, `Refused`, `Gone`, `NoList` or `Malformed`. `refusal.is_stale()` says the page is out of date: add an op that fetches the board again.

## Long lists, by rank

A column of 12,000 cards can't be read whole for every move. Keep each item's place as a **rank**, a number, and order by it. `Move::place` asks your store for what it needs, one indexed read at a time: where the item is, how many the list holds, and the ranks beside where it goes. It returns one new rank between them, so a move writes one row.

```rust
impl RankedLists for MyStore<'_> {
    type Error = OrmError;

    fn lock(&self, lists: &[&str]) -> impl Future<Output = Result<(), OrmError>> + Send {
        let (uow, lists) = (self.uow, lists.to_vec());
        async move { sortable::lock_lists(uow, &Column::KEY, lists).await }
    }
    // spot(key), list(key, item), beside(list, rank, lower, item), nth(list, index, item), last(list, item)
}

match mv.place(&store).await? {
    Ok(Placement { rank: Some(rank), .. }) => write_rank(rank),
    Ok(Placement { rank: None, to_list, .. }) => {
        sortable::renew_ranks(&uow, &Card::LIST, &Card::RANK, &Card::ID, to_list).await?;
        // then place it again
    }
    Err(refusal) => /* refused */,
}
```

New lists start their ranks `RANK_GAP` apart (65,536). When two neighbours have no room left between them, the placement says so and you give that list fresh ranks. `sortable::renew_ranks` does it in one statement: the list is numbered once by `ROW_NUMBER()` and every rank is written by one `UPDATE`, so a column of 12,000 cards takes a fraction of a second instead of 12,000 round trips. The ranks pass through repeats while it runs, so keep the index on `(list, rank, id)` not unique.

## Two moves at once

Run the check and the write in one transaction that locks the lists the move touches before it reads them. `Move::place` takes that lock itself: before it reads anything it calls your store's `lock` with the lists, sorted and each named once, so two moves never wait for each other. With the `orm` feature, `sortable::lock_lists` is the lock: `SELECT ... FOR UPDATE` on one row per list on PostgreSQL and MySQL, one list at a time in that order, and nothing on SQLite, where Navree's units of work start with `BEGIN IMMEDIATE` and so already run one at a time. For lists you read whole, `mv.lock(&uow, &Column::KEY)` takes the same lock before you read them and call `check`.

Two moves at the same moment then queue, and the second is checked against what the first left: if both reach for the last place in a column, the second is refused as full; if both drop into the same gap, they get ranks of their own; if both move the same card, the second is refused as stale. The outcome depends only on the order the server takes them in. Without the lock, twenty moves racing for the one free place in a column on PostgreSQL or MySQL can all be taken.

On MySQL, a transaction keeps reading what was there at its first read (`REPEATABLE READ`, its default). Take the lock before anything else reads in the move's transaction, as `place` does when it comes first, or set `database.mysql.isolation_level = "read_committed"`.

In one page, moves go to the server one at a time, in the order they were made. A refused move puts its item back where the server last had it, and drops that item's other moves.

## When no answer comes

A move waits 15 seconds for its answer (`Sortable::deadline_ms`). A move with no answer, or with a failure from the server, may have landed all the same, so nothing is said yet: the item stays where it was dropped, and the lists are drawn again from the server. If the item is where it was dropped, the move landed and nothing went wrong. If it isn't, the page says the move wasn't saved, with a toast, and the item is where the server has it. If the server can't be reached to ask, or the sortable is in no [region](/docs/ui/regions/) to draw again, the item goes back to where the server last had it, and the toast says so. The core runtime leaves the telling to the sortable: its own "No connection" toast is not shown for a move.

## Live for everyone

Put the board in a [region](/docs/ui/regions/) that follows a server-sent event stream, and nudge the stream after each saved move. Every open board fetches itself again, and the cards slide to their new places. A region waits while someone is dragging in it, so nothing moves under their pointer, and its source keeps asking for as many items as the page has loaded.

## Lazy columns

Draw the first cards of each column and end it with `SortList::more(...)`: a form the page submits as it scrolls into sight, whose cursor is the last card drawn. Read it as "after this card, wherever it is now": look the card up, and page after its current rank. Fresh ranks between two pages then skip nothing, where a cursor of the old rank would skip the cards that moved up past it. If the card has left the column, carry on after as many cards as the page holds. Answer with `Sortable::page(key)`. Cap how many a column keeps in the page with `SortList::end_note(...)`, and let filters and search find the rest. The example board holds 20,000 cards this way.
