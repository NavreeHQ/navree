A Navree API is a bearer-token JSON API with an OpenAPI document, Navree's error shape, list queries, real-time channels over the Pusher protocol and operations you follow over server-sent events. A web front end needs the same pieces every time: a client typed from the document, a server that keeps the tokens out of the browser, sign-in with refresh and two-factor, abilities, live updates, data tables and a theme. The `@navree/*` packages are those pieces, tested once, so every front end on Navree works the same way. Screens drawn in Rust with Navree UI need none of this; [Choosing a UI](/docs/ui/choosing-a-ui/) compares the ways to draw them.

<Callout type="note" title="The packages are not on npm yet">

Until they are published, you install them from a Navree checkout with `link:` paths, as [Installing](#installing) shows, and use pnpm. When they are on npm you add them like any package and the build step, the `link:` paths and the bundler settings for a checkout all go away: [Once the packages are on npm](#once-the-packages-are-on-npm) shows what changes.

</Callout>

## The packages

| Package | What it gives you | Runs in |
|---|---|---|
| `@navree/client` | `createNavreeClient<paths>()` on the schema `navree openapi:client` generates, with no runtime dependencies; `NavreeError` with the error `code`; `listQuery()` and `checkListQuery()`, which write and read the one list-query grammar (`filter[field][operator]=value`, `sort`, `search`, `page`, `cursor`) that Navree servers, Navree UI tables and Helm share; page helpers; query keys; `followOperation`; text direction and error-code translation. Abilities (`@navree/client/abilities`) and real time (`@navree/client/realtime`) are separate entry points. | Browser, server, any JavaScript runtime |
| `@navree/bff` | The backend-for-frontend on web-standard `Request` and `Response`: httpOnly token cookies, single-flight refresh, two-factor sign-in, the `Origin` check, a streaming proxy, `ensureSession` for server rendering. | Node.js 20 and later |
| `@navree/next` | Route handlers, `auth()` and `client()` for server components, the proxy that guards pages and refreshes tokens, `useListQuery` (a list's filters, sort, search and page in the URL, in that grammar), `DataTable`, `useOperation`, workspaces, form errors; `AbilityProvider` and `<Can>`, `RealtimeProvider` and `useChannel`. | Next.js 15 and 16 |
| `@navree/nuxt` | A Nuxt module: the BFF as Nitro routes, a session gate, auto-imported composables (`useNavreeAuth`, `useWorkspace`, `useNavreeClient`, `useListQuery`, `useOperation`, `useChannel`, `useAbility`) and `<NavreeDataTable>`. | Nuxt 4.6.3 and later |
| `@navree/theme` | navree.com's dark theme: Tailwind CSS 4 tokens, shadcn/ui and shadcn-vue colors, the self-hosted fonts, and the tokens as data. | Any CSS pipeline |

The framework packages depend on `@navree/client` and `@navree/bff`, so a Next.js app installs `@navree/next`, `@navree/client` and `@navree/theme`, and a Nuxt app `@navree/nuxt`, `@navree/client` and `@navree/theme`. Optional features keep their libraries optional: CASL and pusher-js are only needed when you import the abilities or real-time entry points.

## Installing

The packages live in `packages/js/` of the Navree repository, a pnpm workspace. Build them once, then add them to your front end from the checkout:

```sh
cd navree/packages/js
pnpm install
pnpm build
```

```json title="web/package.json"
{
  "dependencies": {
    "@navree/client": "link:../../navree/packages/js/client",
    "@navree/next": "link:../../navree/packages/js/next",
    "@navree/theme": "link:../../navree/packages/js/theme"
  }
}
```

A Next.js app also needs a few settings in `next.config.ts`: see [installing from a checkout](/docs/frontend/nextjs/#installing-from-a-checkout). A Nuxt app links `@navree/nuxt` and `@navree/client` (and `@navree/theme`) the same way:

```json title="web/package.json"
{
  "dependencies": {
    "@navree/client": "link:../../navree/packages/js/client",
    "@navree/nuxt": "link:../../navree/packages/js/nuxt",
    "@navree/theme": "link:../../navree/packages/js/theme"
  }
}
```

Linked packages sit outside your app, so Vite and Nitro need a few settings in `nuxt.config.ts` and your app's `pnpm-workspace.yaml` needs one override: see [installing the Nuxt module](/docs/frontend/nuxt/#installing-from-a-checkout).

Then generate the typed client's schema from your app:

```sh
navree openapi:client
```

```text
  run      cargo run --quiet -- openapi:export web/src/lib/api/openapi.json
  wrote    web/src/lib/api/openapi.json
  wrote    web/src/lib/api/schema.d.ts
  next     createNavreeClient<paths>() from @navree/client, with `import type { paths } from "./schema"`
```

### Once the packages are on npm

Add them with your package manager, and nothing else in the setup changes:

<Tabs>
<Tab label="Next.js">

```sh
pnpm add @navree/client @navree/next @navree/theme
```

</Tab>
<Tab label="Nuxt">

```sh
pnpm add @navree/client @navree/nuxt @navree/theme
```

</Tab>
</Tabs>

What changes:

- **The build.** You no longer build `packages/js` in a checkout; the packages arrive built.
- **The `link:` paths.** `package.json` lists version ranges instead. `link:` is why pnpm is required today, because npm does not read it.
- **The Next.js settings for a checkout.** [Next.js](/docs/frontend/nextjs/#installing-from-a-checkout) needs no `turbopack.root`, `outputFileTracingRoot` or `transpilePackages` once the packages are published. [Nuxt](/docs/frontend/nuxt/#installing-from-a-checkout) lists its own settings for a linked package.

`navree new --ui next` and `navree new --kit saas` write this form when the CLI is a published build: they ask npm for `^1.0.0` and write no checkout settings. In an app you made earlier, replace the `link:` paths with the same range and delete those lines.

### Why a link

The packages are not on npm yet, and three things decide how an app takes them from a checkout:

- **They ship a built `dist/`.** Build them once (above), and again when their source changes.
- **A copy would not install.** The packages depend on each other with `workspace:*`, which pnpm resolves only inside `packages/js`, so a `file:` dependency (a copy of the folder) cannot install from outside it. A `link:` is a symlink: it never goes stale and needs nothing from the registry. npm does not read `link:`, so the app uses pnpm.
- **A linked package sits outside your app and brings its own `node_modules`**, with its own `react`, `react-dom` and `next`. The bundler must be allowed to read the folder and must use one copy of each library: [Next.js](/docs/frontend/nextjs/#installing-from-a-checkout) takes the checkout into its root and compiles the packages with the app, and [Nuxt](/docs/frontend/nuxt/#installing-from-a-checkout) dedupes in Vite.

`navree new --ui next` and `navree new --kit saas` write this setup for the checkout the CLI came from: the two `link:` paths in `package.json`, the settings in `next.config.ts`, and the steps to build the packages in the next steps it prints. A CLI that was installed from a published version writes version ranges (`^1.0.0`) instead, and says in the README that the packages install from a checkout until they are published. The reference CRM, `apps/crm-web`, links the packages the same way.

## How a request travels

The browser never holds a token. It calls its own origin, and the app's server (Next.js route handlers, or Nitro in Nuxt) forwards each call to the API with `Authorization: Bearer`:

| Step | Who | What happens |
|---|---|---|
| 1 | Browser | `POST /api/auth/login` with the email and password, same origin. |
| 2 | BFF | Calls the API's `POST /api/auth/login`, keeps the access token in `navree_at` and the refresh token in `navree_rt` (both httpOnly), returns only `{user}`. |
| 3 | Browser | `GET /api/v1/deals?filter[stage]=won` through the typed client, with `X-Workspace: agra`. |
| 4 | BFF | Forwards it with the bearer token. On a 401 it refreshes once (shared by every request holding the same refresh token), sets the new cookies and retries. |
| 5 | Server rendering | `auth()` (Next.js) or `getNavreeSession(event)` (Nuxt) calls the API with the token from the cookie; the proxy or session gate has already refreshed an expired one. |
| 6 | Browser | pusher-js connects to the API's WebSocket server; private channels are signed by `POST /broadcasting/auth` through the BFF. |
