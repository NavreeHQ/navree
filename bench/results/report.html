Keel vs. other web frameworks

Every framework implements the same API (bench/SPEC.md) and is measured alone: the app gets CPUs 0-7 and 4 GB, PostgreSQL 17 its own CPUs, wrk its own. 256 connections, 10 s warmup, then the median of 3 × 15 s runs. Docker 29.9.2 on a 24-core Intel Core Ultra 9 275HX laptop (Windows 11, WSL2).

What the numbers say about Keel

  • On the two realistic endpoints, Keel is 4th of the 10 full-stack frameworks. On the authenticated paginated list it does 15,458 req/s: level with Loco (16,202) and Spring Boot (16,256), behind ASP.NET Core (20,352), and 3.3× NestJS, 4.7× Rails, 6.9× Django and 8.8× Laravel Octane. On the validated insert it does 20,295 req/s: behind Loco (34,308), ASP.NET Core (29,245) and Spring Boot (28,540), ahead of NestJS (1.4×) and 4–6× Rails, Django and Laravel Octane.
  • Keel's own per-request cost is high. On the plain JSON test it is the slowest of the compiled and JIT frameworks: 214k req/s, against 542k for Loco, 963k for Axum (its own foundation) and 357k–644k for NestJS. On a single query it reaches 46.5k req/s, while Loco, ASP.NET Core, Spring Boot and NestJS all do 65k–80k. In both tests Keel used nearly all of its CPUs (772% of 800% on JSON; 586% on one query, with PostgreSQL only at 329%), so the time goes into Keel's request pipeline, not the database.
  • Same foundations, different results. Keel, Loco and Axum all run on Axum, Tokio and sqlx (Keel and Loco add SeaORM). Compared with Axum, Keel delivers 22% of the JSON throughput, 43% on one query and 41% on the insert. Compared with Loco, it delivers 40%, 61% and 59%.
  • Its resource use is excellent. It idles at 4 MB, peaks at 38 MB under load (NestJS: 2.7 GB, Spring Boot: 1 GB), is ready 23 ms after starting, has a 144 MB image, and had zero errors and steady p99 latency in every test.

Where Keel loses the time (from reading its code; fixing these is the next step)

  1. keel-db leaves sqlx's test_before_acquire on, so every pool checkout pings PostgreSQL first: /db costs 2 round trips instead of 1.
  2. Every unit-of-work transaction adds a SELECT set_config('keel.actor', …) round trip.
  3. keel-db's unit-of-work layer spawns a task for every request, /json included.
  4. Process-wide locks are taken on every request: maintenance mode (a Mutex and an RwLock) and the per-IP rate limiter (one global Mutex<HashMap>).
  5. The request-context layer builds metrics labels (fresh Strings) even when no metrics recorder is installed, plus a request scope and a UUID request id.
  6. CurrentUser finds AuthService by scanning every provider, and loads every user column, including the password hash and 2FA secrets.
  7. JSON bodies are parsed twice: into a serde_json::Value, then into the DTO.
  8. Repo::insert serializes each new row for a change event even when nothing listens for change events.

How to read these numbers

  • Fairness. Every app implements the same API (bench/SPEC.md) and passed the same 170-check conformance test before it was measured. Each runs in production mode on all 8 of its CPUs, with at most 64 database connections, using its own ORM, validation and JWT stack (full-stack frameworks) or the most common libraries (micro-frameworks, marked ·). Each app's README in bench/frameworks/ records its versions and choices.
  • Load-generator limit. On the JSON test the load generator was close to its 6 CPUs for Actix (586%), Axum (563%), NestJS on Fastify (499%) and Loco (454%), so their real JSON ceilings are higher than shown. Every other result has the app or PostgreSQL as its limit.
  • Database-bound tests. "20 queries" and the paginated list keep PostgreSQL busy (often 600–950% of its 1,000%), which compresses the differences between fast frameworks. Drivers that cache prepared statements (pgx in Gin, JDBC in Spring Boot) cost PostgreSQL much less per query, which is why Gin and Spring Boot lead "20 queries".
  • Laravel on PHP-FPM. By default it opens a new PostgreSQL connection for every request. With Docker's default kernel settings, those closed connections used up the container's ~28,000 local ports within seconds, and almost every database request failed. The figures shown come from a rerun with net.ipv4.tcp_tw_reuse=1, the standard fix (bench/results/extra/ keeps the failed run). Production setups usually put PgBouncer in front of PostgreSQL or use persistent connections.
  • Stability. Keel was measured again after all 15 frameworks had run (80 minutes of load on the laptop). Every test landed within 3.1% of the first run (JSON +3.1%, others within ±0.8%), so the machine did not thermally drift. The three measured runs per test are kept in the JSON files.
  • The machine. These are laptop numbers (Intel Core Ultra 9 275HX, 24 cores, Docker Desktop on WSL2, everything on one Docker bridge network). Absolute figures will differ on servers; the ordering is what to look at. wrk runs on the monotonic clock: stock wrk counted phantom timeouts when the VM's wall clock stepped backwards.
