# Spring Boot + Spring Data JPA

| | |
|---|---|
| Runtime | Java 25 LTS, Eclipse Temurin 25.0.4.1 (`eclipse-temurin:25-jre`, Ubuntu 26.04/glibc), G1 GC, `-XX:MaxRAMPercentage=75` |
| Framework | Spring Boot 4.1.2 (Spring Framework 7.0.10), Spring Web MVC |
| Server | Embedded Tomcat 11.0.27, one process, a virtual thread per request (`spring.threads.virtual.enabled=true`) |
| Database | Spring Data JPA 4.1.2 on Hibernate ORM 7.4.13, HikariCP 7.0.2 (one pool of 64), PostgreSQL JDBC 42.7.14 |
| JWT | Spring Security 7.1.2 OAuth2 resource server: `NimbusJwtDecoder.withSecretKey(...)` (nimbus-jose-jwt 10.9.1), HS256, `JwtValidators.createDefaultWithIssuer` (exp/nbf + `iss`), then the `User` entity is loaded |
| Validation | Jakarta Bean Validation (Hibernate Validator 9.1.5): `@Valid` on the request record, `@Min`/`@Max` on the query parameters |
| JSON | Jackson 3.1.7 |
| Build | Maven 3.10.0 in `maven:3.10.0-eclipse-temurin-25`. Every dependency and plugin version is pinned by the exact `spring-boot-starter-parent` version (Maven has no lockfile). |

Notes:
- **Startup: JDK AOT cache.** The image does a training run at build time (`-XX:AOTCacheOutput`, JEPs 483/514/515, with `spring.context.exit=onRefresh`) on the extracted jar, following Spring Boot's "Efficient deployments" docs, and starts with `-XX:AOTCache=app.aot`. There is no database at build time, so the training run gives Hibernate the dialect instead of letting it read JDBC metadata; at run time Hibernate detects PostgreSQL normally. In smoke runs the app was ready in about 1.5–3 s with the cache and about 4.7 s without it. I did not use Spring AOT (build-time bean processing) or a GraalVM native image, because neither is the mainstream JVM deployment. The JDK prints two harmless `[aot]` warnings at startup about one adapter stub in the AOT code cache.
- **Production config.** Root log level WARN, no access log, `spring.jpa.open-in-view=false`, `ddl-auto=none`. Tomcat otherwise keeps its defaults, including `maxKeepAliveRequests=100`: Tomcat closes a keep-alive connection after 100 requests and wrk reconnects.
- **Entities and repositories.** `World`, `User` (the whole existing `users` table) and `Deal` (with a lazy `@ManyToOne` owner) are mapped. Reads run in `@Transactional(readOnly = true)` service methods, the insert in a read-write one.
- **Deals list.** `DealRepository.findAll(Pageable)` is annotated `@EntityGraph(attributePaths = "owner")`, so each page is a single `deals JOIN users ... ORDER BY created_at DESC, id DESC OFFSET/FETCH` query, plus Spring Data's `count` query. Each request issues three statements: the user lookup, the page and the count. Spring Data skips the count when it can infer the total from a partial page; benchmark pages are always full, so the count always runs.
- **Auth.** A custom `Converter<Jwt, AbstractAuthenticationToken>` loads the user by `sub` through `UserRepository` and makes the `User` the principal (`@AuthenticationPrincipal User`). An unknown user raises `InvalidBearerTokenException`, which gives 401. The entry point is Spring's `BearerTokenAuthenticationEntryPoint` (status and `WWW-Authenticate`) with a JSON body added. Sessions are stateless and CSRF is off. `/json`, `/db` and `/queries` are `permitAll`.
- **Create.** The owner is set with `getReferenceById` because the user is already loaded, so Hibernate does not re-read it. `saveAndFlush` runs the INSERT before the response is built, so Hibernate's `@CreationTimestamp`/`@UpdateTimestamp` values are set. The flush would happen at commit anyway. Each request issues two statements: the user lookup and the INSERT.
- **Validation.** Query-parameter constraints use Spring MVC's built-in method validation (Spring Framework 6.1+). The controller deliberately has no class-level `@Validated`, because Spring's reference docs recommend removing it so the built-in support is used instead of the AOP proxy. A `@RestControllerAdvice` turns `HandlerMethodValidationException`, `MethodArgumentNotValidException`, `MethodArgumentTypeMismatchException` (`page=abc`) and `HttpMessageNotReadableException` (malformed JSON, or `10.5` for `amount_cents` with `spring.jackson.deserialization.accept-float-as-int=false`) into `400 application/json`. Spring's built-in `ProblemDetail` responses are not used because they are `application/problem+json`, which the conformance check does not accept as JSON.
- **JSON naming.** The deal DTOs are records with `@JsonNaming(SnakeCaseStrategy)`. A global snake_case strategy would break `/db`'s `randomNumber`. Jackson 3 writes `Instant` as ISO-8601 (`2026-01-01T16:40:00Z`).
- **`/queries`.** Runs N `findById` calls, one after another, in one read-only transaction. Hibernate's persistence context is a per-request identity map, so a repeated id within one request is served from it instead of a second SELECT. At N=20 out of 10,000 ids that is about 0.02 skipped lookups per request.
